## 本讲要解决的核心问题（SCQA）

**背景**：以 DeepSeek-OCR 为代表的端到端 OCR 模型，用大语言模型（LLM）当解码器，借助语言的先验分布提升了识别质量，让 OCR 重新站上舞台中央。

**冲突**：代价同样明显——输出序列越长，KV 缓存的内存消耗就越大，生成速度持续下降，甚至无法一次性完成多页长文档的识别。这和人类抄写长文本时效率毫不衰减的表现，差距十分明显。

**疑问**：能不能让模型像人一样"选择性记忆"，把几十页文档一口气读完？

**回答（中心思想）**：Unlimited-OCR 用一个极简的改动做到了——把解码器的全部注意力替换成**参考滑动窗口注意力 R-SWA（Reference Sliding Window Attention）**：原文全程可见、已输出内容只保留最近 128 个 token。KV 缓存因此从"随长度线性增长"变成"恒定大小"，首次在 32K 标准上下文内用单次前向传播转写几十页文档，精度还不降反升。

## 一、先把六个术语统一：KV 缓存、LLM、MHA、MoE、R-SWA、TPS

读懂这篇论文只需要六个术语。[【跳转到 00:55】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=55)

![术语总览幻灯片：KV cache、LLM、MHA、MoE、R-SWA、TPS](assets/Unlimited%20OCR：开启单次长序列OCR识别新时代/00055.webp)

- **KV cache（键值缓存）**：模型解码时为"已经生成过的内容"保存的记忆。本次优化的核心对象——传统 OCR 模型解码时，它随输出序列长度**线性增长**，拖慢推理、占用大量显存；
- **LLM（大语言模型）**：端到端 OCR 的解码器，靠语言先验"顺"出通顺文本；
- **MHA（多头注意力）**：传统解码器的标准注意力机制——记住全部历史，也是这次被 R-SWA 替换的基础组件；
- **MoE（混合专家架构）**：基线 DeepSeek-OCR 和 Unlimited-OCR 都采用的结构，控制激活参数量的同时保持模型能力；
- **R-SWA（参考滑动窗口注意力）**：本篇最核心的创新点，实现"KV 缓存恒定"的关键设计；
- **TPS（每秒生成 token 数）**：衡量推理效率的核心指标。

## 二、现有端到端 OCR 卡在哪：KV 缓存随输出线性增长

三个最直观的表现：输出序列变长 → KV 缓存不断膨胀；生成速度随长度增加持续下降；最关键的是——**没办法单次 forward 处理多页文档**。[【跳转到 02:15】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=135)

![现有模型的三个问题：缓存膨胀、速度下降、无法单次处理多页](assets/Unlimited%20OCR：开启单次长序列OCR识别新时代/00135.webp)

背后原因与注意力机制直接相关：标准全注意力要保留**所有**历史输出的 KV 信息，解码越长、内存占用越高、计算越慢。于是现在的模型只能**逐页循环处理**，每次重置内存——跨页上下文完全保留不了。[【跳转到 02:40】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=160)

结论非常明确：现有基于 LLM 解码的端到端 OCR，没法高效处理长序列多页文档，核心瓶颈就是 KV 缓存的线性增长。

论文给了一个有意思的对照：把模型和人类抄写放在一起看。现有模型逐页循环、重置内存、丢上下文，长文档效率极低；人类则**持续保留全局参考、只关注近期输出**——抄书时不需要记住前面抄过的所有内容，只要看着原书和刚抄的几行就能继续。落到本质上：模型"全注意力记忆"和人类"选择性记忆"之间存在根本差异。[【跳转到 03:05】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=185)

## 三、核心创新 R-SWA：全局参考 + 局部滑动窗口

R-SWA 的做法出奇简单：**解码阶段让 KV 缓存全程保持恒定大小**，不随输出变长而增长——从而支持单批次几十页的多页文档识别，精度还比基线更好。[【跳转到 03:52】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=232)

![全注意力 vs R-SWA：缓存越堆越长 vs 恒定大小](assets/Unlimited%20OCR：开启单次长序列OCR识别新时代/00257.webp)

看对比示意图：左边的普通全注意力把所有历史输出的 KV 都存下来，缓存越堆越长；右边的 R-SWA 只保留**全部的参考视觉 token**（原文图像编码出的内容）+ **最近固定数量的输出 token**。本质是把解码端的全历史注意力，改成"全局参考 + 局部滑动窗口"模式——和人类处理长文档的注意力模式非常接近。

具体逻辑：每个新生成的 token 只需关注全部参考视觉 token 和最近 **N=128** 个输出 token，不用保留所有历史输出。再搭配视觉编码器极高的图像压缩率，哪怕只用 32K 上下文窗口，也能支持几十页文档一次性完成识别。[【跳转到 04:42】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=282)

一个办公类比：把所有参考资料都摆在桌上作为全局参考，写内容时只要看刚写的几行就能继续往下写，完全不用把之前写的几百页都摊出来占地方。[【跳转到 05:07】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=307)

### R-SWA 的三条计算规则

[【跳转到 07:47】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=467)

![R-SWA 的三个核心设定：前缀全局可见、输出只看最近 N 个、N 默认 128](assets/Unlimited%20OCR：开启单次长序列OCR识别新时代/00467.webp)

1. 所有**前缀**——视觉参考 token 和提示词——全程对所有解码步骤**全局可见**；
2. 已经生成的**输出 token**，解码时仅能访问**最近的 N 个**；
3. 窗口长度 N 的默认取值是 **128**。

从数学定义看，R-SWA 把可访问的上下文拆成两部分：**固定的前缀集合 P** + **不断滑动的输出窗口集合 D**。[【跳转到 08:12】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=492)

![R-SWA 的数学定义：固定前缀集合 P + 滑动输出窗口集合 D](assets/Unlimited%20OCR：开启单次长序列OCR识别新时代/00492.webp)

这个拆分带来两个关键好处：其一，视觉参考 token 编码后**全程固定**，不会像普通滑动窗口那样被逐步挤出窗口，避免视觉特征模糊；其二，输出侧只保留最近上下文，**足够用来跟踪 OCR 的识别进度**，又不必存储全部历史。就像考试时试卷始终放在面前随时可看，答题时只需参考刚写的几行。[【跳转到 08:37】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=517)

一句话总结：R-SWA 把参考 token 和输出 token 做了**属性拆分**——分别用"全局保留"和"滑动窗口"两种策略管理，兼顾 OCR 精度与长序列生成效率。

## 四、整体架构：只换解码器注意力的"最小改动"

Unlimited-OCR 的整体架构有四个核心设计要点。[【跳转到 05:37】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=337)

![整体架构四大要点：DeepEncoder + MoE 解码器 + 全注意力换 R-SWA + 固定容量 KV 队列](assets/Unlimited%20OCR：开启单次长序列OCR识别新时代/00337.webp)

1. 沿用 DeepSeek-OCR 的 **DeepEncoder** 视觉编码器；
2. 采用 **MoE 结构**的大语言模型解码器；
3. 最关键的改动：把解码器的**全部注意力替换成 R-SWA**；
4. 把 KV 缓存改成**固定容量的队列**。

示意图对应的正是"软遗忘"的抄写直觉：只记住刚写的一小部分，不全程保留所有已写内容的完整记忆。

为什么只改注意力就能实现长序列 OCR？两个关键原因。[【跳转到 06:27】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=387)

- **第一，DeepEncoder 的压缩率极高**：可以把 1024×1024 的图像压缩成一百多个视觉 token，大幅减少预填充阶段（prefill，模型"读图"的阶段）的 KV 缓存占用；
- **第二，MoE 架构总参数 3B、实际激活参数只有 0.5B**，本身就有很好的推理效率基础。

所以这是一次非常轻量化的升级：仅针对性优化解码器的注意力模式，完全不改动编码器和基础模型结构——就像给汽车换更高效率的动力总成，车身和其他部件都不用改，就能跑得更快、更远、更省油。[【跳转到 07:17】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=437)

## 五、能省多少：缓存有固定上限，复杂度从 O(T) 到 O(1)

R-SWA 到底能减少多少 KV 缓存开销？核心结论：**缓存总大小有固定上限，不随解码输出长度增长**；输出序列越长，优化效果越明显。[【跳转到 09:17】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=557)

![R-SWA 缓存大小计算公式：固定前缀 + 最多 N 个最新输出](assets/Unlimited%20OCR：开启单次长序列OCR识别新时代/00582.webp)

计算公式一句话：**总缓存 = 固定的前缀视觉 token 长度 + 最多 N 个最新的输出 token**——无论解码多长都不会超过这个上限。对比标准 MHA（缓存随解码长度 T 线性增长、完全没有上限），R-SWA 的上限与总解码长度无关。[【跳转到 09:42】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=582)

本质是把解码侧的 KV 缓存管理，从"全量保留"改成了**固定容量的队列淘汰机制**——旧内容自动出局，总内存完全可控。[【跳转到 10:32】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=632)

幻灯片给了一个刷手机的类比：普通模式把看过的所有视频都存在本地，越用越卡；R-SWA 相当于只保留最近看过的几个，旧的自动清理，自然不会越用越慢。[【跳转到 10:57】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=657)

## 六、跑起来有多稳：延迟与显存双重恒定

R-SWA 在实际推理中的收益，解决的是"长序列解码越跑越慢"的核心痛点。[【跳转到 11:20】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=680)

![效率曲线对比：MHA 延迟持续走高并出现尖刺，R-SWA 全程平线](assets/Unlimited%20OCR：开启单次长序列OCR识别新时代/00680.webp)

看右侧效率曲线：上方红线是 DeepSeek-OCR 基线（标准 MHA），解码步数越多延迟越高，还会出现突然的尖刺；下方浅蓝线是用了 R-SWA 的效果——**全程几乎一条平线**。三个直观好处：推理延迟全程恒定；不会出现 MHA 常见的延迟突增；GPU 内存占用保持固定。[【跳转到 11:45】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=705)

背后原因有两点：一是注意力计算的复杂度恒定，每次解码的计算量不随序列长度变化；二是固定大小的 KV 缓存保证了**内存访问的局部性**，不会出现跨内存边界的效率下降。

跑步的类比：普通注意力像跑得越久、跑步机越慢、耗电越高；R-SWA 不管跑多久，速度和耗电都完全不变。[【跳转到 12:10】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=730) 最核心的本质：通过约束注意力范围，把推理的计算和内存访问复杂度从随序列线性增长的 **O(T)** 降到恒定的 **O(1)**——这就是它能支撑几十页文档连续解码的原因。[【跳转到 12:35】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=755)

## 七、精度不降反升：OmniDocBench SOTA 与九类文档验证

约束了注意力，精度会不会受损？答案是不仅没降，反而提升了。

在主流的 **OmniDocBench** 文档解析基准上，Unlimited-OCR 拿到了当前的 **SOTA**（最高水平）：V1.5 版本上比 DeepSeek-OCR 基线高出**六个百分点**；V1.6 版本的整体得分达到 **93.92**。[【跳转到 13:00】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=780)

![OmniDocBench 基准：V1.5 高出六个百分点，V1.6 整体 93.92](assets/Unlimited%20OCR：开启单次长序列OCR识别新时代/00780.webp)

R-SWA 为什么没有损失精度、反而带来提升？两个核心原因：[【跳转到 13:25】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=805)

这揭示了本篇工作最核心的发现：**OCR 这类解析类任务，并不需要访问全部历史的注意力——合适的局部注意力反而能提升密集识别的精度。**[【跳转到 13:50】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=830)

其中**阅读顺序**的精度优势尤其明显。原因有三：全局视觉参考保证复杂布局的空间信息不丢失；局部滑动窗口保证文本顺序的连续性；滑动窗口内的上下文传递模式本身，也比全注意力更贴合 OCR 这类顺序解析任务的特性。[【跳转到 15:05】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=905) 对比 DeepSeek-OCR，九类文档中有**七类**的文本和阅读顺序精度更优，整体表现更均衡。[【跳转到 15:30】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=930)

## 八、长序列差异点：40+ 页单次识别，越跑越快

## 九、局限与未来：32K 预填充边界，走向 128K 与"翻书式"加载

这项工作目前也有局限：仍受**预填充（prefill）长度约束**——用 32K 上下文训练的版本，输入页数太多会导致视觉 token 超限，没法一次性完成加载。[【跳转到 19:26】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=1166)

![当前局限：32K 上下文的预填充约束](assets/Unlimited%20OCR：开启单次长序列OCR识别新时代/01166.webp)

对应的规划有两条：**短期**把训练上下文扩展到 128K，支撑更多页面的预填充；**长期**打造 prefetch 式动态加载机制，模拟人翻书的行为——需要哪一页就调哪一页，真正实现"无限制"OCR。[【跳转到 19:51】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=1191)

另外值得记住的是：R-SWA 本身是**通用的参考类任务注意力机制**——ASR（语音识别）、翻译这类同样需要"全局参考 + 局部输出"的长序列任务，都可以天然适配，后续也会向这些领域拓展。[【跳转到 20:16】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=1216)

## 十、总结：从算盘到计算器

最后梳理这项工作的核心价值。[【跳转到 20:41】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=1241)

- **新解法**：通过模拟人类的注意力模式，首次实现高效、高精度的长序列端到端 OCR；
- **两点支撑**：R-SWA 证明解析类任务根本不需要全注意力，仅靠局部滑动窗口就能实现无精度损失的长序列处理；恒定的内存和延迟特性让长序列 OCR 的工程落地变得可行，再也不需要复杂的分页调度逻辑；
- **本质贡献**：为所有"参考型"长序列解析任务提供了通用的注意力范式，直接把计算和内存复杂度从线性降到常数级。[【跳转到 21:06】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=1266)

再和传统 OCR 范式对比：传统 OCR 分页处理、碎片化、工程调度复杂、容易丢失跨页上下文；Unlimited-OCR 单次处理、连续化、工程简单、完整保留全局上下文。[【跳转到 21:31】](https://www.bilibili.com/video/BV1KPut62Ekk/?t=1291)

![传统分页范式 vs 单次连读范式：算盘与计算器的对比](assets/Unlimited%20OCR：开启单次长序列OCR识别新时代/01291.webp)

幻灯片的收尾类比很传神：传统 OCR 就像**用算盘算长题**，记得内容越多算得越慢；Unlimited-OCR 就像**用计算器**，不管序列多长速度始终一致，还算得更准。

## 小结

- 痛点：LLM 解码器的 KV 缓存随输出线性增长，长文档 OCR 只能逐页循环、丢失跨页上下文；
- 方案：R-SWA——参考视觉 token 全程全局可见，输出 token 只保留最近 128 个，KV 缓存恒定；
- 架构：最小改动——沿用 DeepEncoder 与 MoE（3B 总参/0.5B 激活），只替换解码器注意力，缓存改为固定容量队列；
- 收益：缓存、延迟、显存三重恒定，复杂度从 O(T) 降到 O(1)，越跑越快而不是越跑越慢；
- 精度：OmniDocBench V1.5 比 DeepSeek-OCR 高 6 个百分点、V1.6 达 93.92（SOTA）；九类文档全部超基线，阅读顺序优势尤其明显；
- 长序列：40+ 页单次识别、编辑距离低于 0.1、6000 token 输出快 35%、6144 token 时基线 TPS 跌至 5.822 而它稳中有升；
- 局限与未来：当前受 32K 预填充约束，短期扩 128K、长期做 prefetch 式"翻书"动态加载；R-SWA 还可泛化到 ASR、翻译等参考型长序列任务。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| KV 缓存（KV cache） | 解码器为已生成内容保存的记忆，传统全注意力下随输出长度线性增长 |
| MHA（多头注意力） | 传统解码器的标准注意力机制，保留全部历史 KV，是本次被替换的对象 |
| MoE（混合专家） | 只激活部分参数的模型结构；Unlimited-OCR 总参数 3B、激活 0.5B |
| R-SWA（参考滑动窗口注意力） | 前缀全局可见 + 输出只看最近 128 个 token，使 KV 缓存恒定 |
| DeepEncoder | 沿用自 DeepSeek-OCR 的视觉编码器，将 1024×1024 页面压缩成一百多个视觉 token |
| 预填充（prefill） | 模型"读图建缓存"的阶段，其长度决定了单次能加载的页数上限 |
| 固定容量队列 | 输出侧 KV 的管理方式：新 token 进、旧 token 出，总量不超上限 |
| TPS（tokens/s） | 每秒生成的 token 数，衡量推理速度的核心指标 |
| 编辑距离 | 输出与标准答案的文本差异度量，越低越好 |
| OmniDocBench | 主流文档解析基准，V1.5/V1.6 两个版本口径 |
| O(T) / O(1) | 复杂度记号：随长度线性增长 / 与长度无关的常数 |
