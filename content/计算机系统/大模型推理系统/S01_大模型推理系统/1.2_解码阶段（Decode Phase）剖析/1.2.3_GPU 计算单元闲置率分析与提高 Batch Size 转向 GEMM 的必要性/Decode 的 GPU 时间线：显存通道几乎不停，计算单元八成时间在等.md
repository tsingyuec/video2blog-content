# Decode 的 GPU 时间线：显存通道几乎不停，计算单元八成时间在等

> 视频来源：[LLM Decode Is Memory-Bound, Prefill Is Compute-Bound. But Why?](https://www.youtube.com/watch?v=2AZJP_vjPEs)（YouTube · DevOps 2 AI）｜时长约 14 分 7 秒
> 简要导读：这支视频不推公式，而是把一次 decode 画成一条可播放的 GPU 时间线：上面一条是搬数据的通道，下面一条是做矩阵乘的 Tensor Core。看着紫色方块一次次亮起又熄灭，你就能明白「计算单元闲置」到底长什么样。本文顺着这条时间线走，把闲置率拆成并行度、Tensor Core 利用率和带宽三项，再用同一条时间线解释 batch 为什么能把形状从 GEMV 改回 GEMM，以及这条路要付什么账。权重字节数除以带宽那条延迟下界由 1.2.2 专门推导，GEMV 的形状退化由 1.2.1 推导，本文只引用结论。

## 本讲要解决的核心问题（SCQA）

**背景**：一块现代数据中心 GPU 每秒能做好几百万亿次浮点运算。同一块卡，跑 Prefill 时能把它用得相当满，跑 Decode 时却总感觉没使劲。

**冲突**：模型没换、权重没换、卡也没换，只是从「一次读一大段 prompt」变成「一次生成一个 token」，GPU 的行为就完全变了。如果说是算力不够，那么换更贵的卡应该更快；可现实是算力翻倍往往没什么用。更反直觉的是：显存其实一直在满负荷工作，慢的不是显存。

**疑问**：Decode 时 GPU 的两条通道各忙了多少？计算单元到底在等什么？为什么加算力没用、加 batch 却有用？batch 把什么变了、又在哪里撞墙？

**回答（中心思想）**：**Decode 的瓶颈不是「算得慢」，而是「每个权重搬进来只够干一点点活」。** 视频用一个归一化的教学时间线把这件事量化出来：batch size 为 1 时，显存通道有 86% 的时间在搬数据，而 Tensor Core 只有 17% 的时间在算，83% 的时间在等。**batch 的作用就是给同一块权重 tile 加行**——把「一次搬进来的权重只服务 1 行」变成「服务 B 行」，于是计算通道的忙碌比例从 17% 抬到 48%（B=4）、86%（B=16），形状上也就从矩阵-向量乘（GEMV）回到了矩阵-矩阵乘（GEMM）。但这条路要付两笔账：KV cache 显存随 batch 线性增长，单请求的每 token 延迟随 batch 变长。所以 batch 是吞吐与延迟之间的一个旋钮，不是一个免费的优化开关。

## 一、先把 GPU 拆成两条通道：一条搬数据，一条做数学

### 1.1 memory-bound 不等于「显存满了」

视频把 GPU 干的活分成两大类：**把需要的数据搬到计算单元（Tensor Core）**，以及**真正做那些计算**。

![GPU 的两类工作：数据从 HBM/VRAM 经存储层级搬到 SM 与 Tensor Core，再执行矩阵乘；图下方同时给出「每搬一份数据换来的有用计算」与当前状态](assets/Decode%20的%20GPU%20时间线：显存通道几乎不停，计算单元八成时间在等/00000.webp)

[【跳转到 00:00】](https://www.youtube.com/watch?v=2AZJP_vjPEs&t=0)

- 如果**计算本身**是最慢的一环，这个负载就是 **compute-bound（计算受限）**。
- 如果计算单元本来还能干更多活、却一直在等数据到达，这个负载就是 **memory-bound（访存受限）**。

视频特意强调了一句很容易被误解的话：**memory-bound 不意味着显存满了**。它说的是「搬数据的速度在决定节奏」，和容量无关。这一点值得记住，因为后面讲到 batch 的上限时，容量才会真正登场——那是另一堵墙。

### 1.2 权重已经在显存里，但它还得走一趟存储层级

初学者听到「decode 是 memory-bound」，第一反应往往是「模型是不是每次都被重新加载一遍」。视频明确否掉了这个理解：

> 模型权重已经常驻在 GPU 的 HBM（也就是 VRAM）里，这不是 SSD 读取，也不是模型重载。

但「已经在显存里」不等于「每个 Tensor Core 都能零成本地立刻用到每一个权重」。GPU 是把模型切成小块（tile）执行的，需要的权重仍然要沿着存储层级走一趟：从 HBM 出来，穿过各级缓存或片上存储，最后到达足够靠近执行单元的位置才能被用上。

![一个权重 tile 正在从 HBM 出发，沿访存通路走向 SM；此时 Tensor Core 的状态是 Waiting for required data](assets/Decode%20的%20GPU%20时间线：显存通道几乎不停，计算单元八成时间在等/00292.webp)

[【跳转到 04:52】](https://www.youtube.com/watch?v=2AZJP_vjPEs&t=292)

这张图右侧的小卡片给出了一个关键量：一块 100 MB 的权重 tile，在 batch size 为 1 时只能「解锁」10 GFLOP 的计算量。**10 GFLOP 除以 100 MB，就是这块 tile 的算术强度**——搬进来 100 MB，只换来很少的数学。视频没有把这个除法写出来，但它的可视化一直在用这个比值说话。

## 二、一次 decode 的完整时间线：显存 86%，计算 17%

### 2.1 只看模式：搬、算一小会儿、再等

视频把一次完整的模型前向（一个 token 要穿过所有层）压缩成 700 个归一化毫秒，然后逐段播放：

1. 一块需要的权重 tile 开始从 HBM 出发，沿访存通路走向计算单元；
2. 数据还在路上的时候，Tensor Core 还没拿到它需要的全部东西，只能等；
3. tile 到了，Tensor Core 做那次计算——但因为只有**一行** token 的工作，这次计算爆发非常短；
4. 计算在下一批需要的数据准备好之前就做完了，计算单元回去接着等；
5. 同样的模式重复：搬数据、算一小会儿、再等。

视频在这里补了一个重要的诚实说明：**真实的 GPU kernel 会做流水线、会重叠很多操作，真实硬件比这个模拟复杂得多**。这个动画的价值不是还原微架构，而是把「瓶颈在哪」隔离出来。

### 2.2 三个数字：86 / 17 / 83

把整趟时间线铺开，视频给出了这组归一化教学值：

| 指标 | batch size = 1 |
| --- | --- |
| 显存通道忙碌 | 86% |
| 显存通道等待 | 14% |

视频反复声明这些百分比是**为了教学归一化的数值，不是某块具体 GPU 的实测**，模式才是重点。但这组数字把「闲置」这件事讲得比任何形容词都清楚：**显存通道几乎一直在工作，计算通道八成以上的时间在等。**

由此得到视频里那句最实用的推论：

> 一块 GPU 可能有巨大的理论算力，但如果计算单元没法保持忙碌，这份算力就帮不上什么忙。**这就是为什么单纯堆 TFLOPS 并不会让低 batch 的 Decode 按比例变快。**

## 三、闲置率从哪来：一次只有 $N$ 个输出元素

视频用「有用计算 / 搬动的数据」这个比值解释了闲置，但没有把它换算成硬件上的并行度。这一节把这一步补上——**以下估算属于补充，不是讲者原话**，目的是让你能自己算一遍。

### 3.1 并行度只有 $N$

一个线性层的权重是 $W \in \mathbb{R}^{K \times N}$，decode 时输入是一个向量 $x \in \mathbb{R}^{K}$，输出是 $y \in \mathbb{R}^{N}$。

- 这 $N$ 个输出元素彼此独立，可以分给不同计算单元——**但也只有 $N$ 个**；
- 每个输出元素内部，还必须把 $K$ 个乘积串行累加起来。

于是可并行的独立工作数是 $N$，不是 $N$ 乘以别的什么。取一个常见配置：hidden size $N = 4096$，一块 H100 SXM 有 132 个 SM、每个 SM 最多 2048 个线程槽位，合计约 27 万个线程槽位。

$$
\frac{4096}{132 \times 2048} \approx 1.5\%
$$

也就是说，一次 GEMV 能提供的独立工作量，只够填满这块卡约 1.5% 的线程槽位。**这不是「实现得不好」，是形状本身就只有这么大。** 剩下的 98.5% 不是坏了，是没活干。

### 3.2 每个权重只做一次乘加，Tensor Core 的 MMA 基本用不上

第二重浪费在指令粒度上。Tensor Core 的矩阵乘累加指令（MMA）天生是**按块**工作的：一条指令吃进一小块 $M \times K$ 的输入和一小块 $K \times N$ 的权重，一次算出 $M \times N$ 的结果。当 $M = 1$ 时，这条指令里除了第一行，其余行全是空的。

换句话说：**搬进来一整块权重，Tensor Core 却只能拿它跟一行向量相乘**。视频的可视化里，权重 tile 的卡片写着「Used across 1 sequence row」，说的就是这件事。

### 3.3 三重浪费，但带宽那一项要看得细一点

把上面两条合起来，低 batch 的 decode 同时浪费三样东西：

1. **SM 占用率低**：可并行的输出元素远少于线程槽位，大量 SM 分不到活；
2. **Tensor Core 利用率低**：MMA 指令的有效行数只有 1，块状算力被浪费；
3. **带宽也没完全打满**：时间线上显存通道是 86% 而不是 100%——剩下那 14% 的等待，是因为计算单元还没准备好接收下一块 tile，供数节奏被下游卡住了。

第 3 点需要小心表述：**decode 的主瓶颈确实是带宽**（这也是 1.2.2 那条「延迟下界 = 权重字节 ÷ 带宽」的来源），这里说的只是「带宽也没有 100% 跑满」。两者不矛盾：带宽是天花板，而天花板之下还有一小段空隙，是计算单元的等待反向造成的。

## 四、对照组：同一块 GPU，Prefill 的显存只有 23% 忙

### 4.1 变的是工作的形状

视频接着做了一件很干净的事：**硬件一个都不换**，只把负载从「1 行 token」换成「10000 行 prompt」。

![同一块 GPU、同一份权重，只把负载换成 10000 个 prompt token：显存通道忙碌降到 23%，计算通道忙碌升到 92%](assets/Decode%20的%20GPU%20时间线：显存通道几乎不停，计算单元八成时间在等/00449.webp)

[【跳转到 07:29】](https://www.youtube.com/watch?v=2AZJP_vjPEs&t=449)

| 指标 | Decode（B=1） | Prefill（10000 token） |
| --- | --- | --- |
| 显存通道忙碌 | 86% | 23% |
| 计算通道忙碌 | 17% | 92% |
| 权重 tile 解锁的计算 | 10 GFLOP | 4000 GFLOP |
| 权重 tile 服务行数 | 1 | 很多 |

数字几乎是镜像的。视频的解释只有一句：

> **当一个权重 tile 到达计算单元时，它可以参与很多行 token 的计算，而不只是一行。于是同样一次权重数据的搬动，现在解锁了多得多的有用计算。**

这就是「工作的形状」这个词的分量：Prefill 天然把 $M$ 做得很大（$M = S$，prompt 长度），Decode 的 $M$ 只有 1。

### 4.2 一个必要的澄清：causal attention 没有被破坏

把很多 prompt 位置放在一起算，很容易让人怀疑「token 是不是能看到未来」。视频专门澄清：

> 把很多 prompt 位置放在一起处理，**并不意味着 token 能看到未来的 token**，那是不可能的。模型仍然使用因果注意力（causal attention），GPU 只是把**被允许的**计算有效地组织成大并行操作。

这一句值得记住，因为后面所有关于 batch 的讨论都建立在同一个前提上：**并行的是彼此独立的工作，不是把因果链打断。**

视频还留了一个诚实的边界：**Prefill 并不是在每一个可能的步骤上都神奇地 compute-bound**。prompt 长度、模型结构、精度、GPU、推理服务的实现，都会改变结果；只是对于足够大的 prompt 工作量，compute-bound 是常见模式。

## 五、batch 做的事：给同一个权重 tile 加行

### 5.1 为什么不能「一条序列并行生成多个 token」

在讲 batch 之前，视频先堵住了那条走不通的路：

> 我们通常没法让同一条序列并行生成很多未来的 token，因为每个新 token 都依赖前一个 token。

自回归的串行性是硬约束。但还有一条路：**把很多条独立序列的「下一个 token」放在一起算**。它们彼此之间没有依赖，天然可以拼成一批。

### 5.2 B=1 → 4 → 16：计算通道的忙碌比例一路爬升

视频把 batch 从 1 调到 4、16、64，硬件和权重全部保持不变：

![batch size 4：4 行 token 同时进入，计算通道忙碌从 17% 升到 48%，显存通道忙碌从 86% 降到 80%](assets/Decode%20的%20GPU%20时间线：显存通道几乎不停，计算单元八成时间在等/00569.webp)

[【跳转到 09:09】](https://www.youtube.com/watch?v=2AZJP_vjPEs&t=549)

![batch size 16：16 行 token 同时进入，计算通道忙碌升到 86%，显存通道忙碌降到 57%，权重 tile 解锁的计算量涨到 160 GFLOP](assets/Decode%20的%20GPU%20时间线：显存通道几乎不停，计算单元八成时间在等/00589.webp)

[【跳转到 09:29】](https://www.youtube.com/watch?v=2AZJP_vjPEs&t=589)

| batch size | 显存通道忙碌 | 计算通道忙碌 | 权重 tile 解锁的计算 |
| --- | --- | --- | --- |
| 1 | 86% | 17% | 10 GFLOP |
| 4 | 80% | 48% | 40 GFLOP |
| 16 | 57% | 86% | 160 GFLOP |

三个数字的走向非常干净：**显存通道从「几乎全程忙」退到「一半时间忙」，计算通道从「八成时间等」变成「八成时间算」。** 而权重 tile 解锁的计算量严格按 batch 倍数增长（10 → 40 → 160），因为同一块 100 MB 的权重被 4 行、16 行共用了。

视频对这一段的总结是：

> 当一个权重 tile 到达时，它可以参与好几条序列行的计算，**每搬运一个字节换来的有用工作量就上升了**。计算单元保持活跃的时间更长，等待的空隙变小。

### 5.3 计算的「爆发」也变长了

光看百分比还不够直观，视频还给了一个绝对量：

![batch size 16 时，一次矩阵乘（Math 1）持续 175 个归一化毫秒；batch size 1 时同样的计算爆发只有 55 毫秒](assets/Decode%20的%20GPU%20时间线：显存通道几乎不停，计算单元八成时间在等/00629.webp)

[【跳转到 10:29】](https://www.youtube.com/watch?v=2AZJP_vjPEs&t=629)

同一个 kernel，同一块 tile：**B=1 时计算只持续 55 毫秒，B=16 时持续 175 毫秒**。而搬这块 tile 的时间几乎没变（还是那 100 MB）。于是「计算做完要等数据」的空隙被填掉了大半。

### 5.4 形状上，这就是从 GEMV 变回 GEMM

把上面这些现象翻译成矩阵形状，只用一行：

$$
\underbrace{\begin{bmatrix} x_1 \\ x_2 \\ \vdots \\ x_B \end{bmatrix}}_{B \times K}
\cdot
\underbrace{W}_{K \times N}
\;=\;
\underbrace{\begin{bmatrix} y_1 \\ y_2 \\ \vdots \\ y_B \end{bmatrix}}_{B \times N}
$$

![16 行 token 同时进入 decode 矩阵：视频把这一步描述为「有效的 decode 输入被加宽到 16 倍 hidden size」](assets/Decode%20的%20GPU%20时间线：显存通道几乎不停，计算单元八成时间在等/00609.webp)

[【跳转到 10:09】](https://www.youtube.com/watch?v=2AZJP_vjPEs&t=609)

**batch 把 $M$ 从 1 变成了 $B$，于是 GEMV 变回了 GEMM。** 权重 $W$ 只读一次，服务 $B$ 行；这就是 1.2.1 里说的「权重复用次数」从 1 变成 $B$。

算术强度也跟着变。把激活和输出的字节也算进去：

$$
\text{AI}(B) \;=\; \frac{2BKN}{2KN + 2BK + 2BN}
$$

当 $B$ 远小于 $K$、$N$ 时，分母里的激活项可以忽略，$\text{AI}(B) \approx B$。取 $K = N = 4096$、$B = 16$：

$$
\text{AI}(16) \;=\; \frac{2 \times 16 \times 4096^2}{2 \times 4096^2 + 2 \times 16 \times 4096 \times 2} \approx 15.9
$$

从 1 抬到约 16。**这就是「提高 batch size 转向 GEMM」这句话的数学内容：不是换了一个算法，而是把同一个算法喂成更宽的形状，让每个搬进来的字节多干几次活。**

## 六、代价：batch 是吞吐与延迟的旋钮，不是免费的优化

视频在这一段说得很克制，但每一句都是后面几章的地基。

### 6.1 KV cache 显存随 batch 线性增长

![一次请求的五阶段流水线：Prompt 切 token、Prefill 处理 prompt 并建 KV、产出第一个 token、Decode 逐 token 生成、Append 追加新的 K/V；图中 KV cache 行已被 prompt 的每个位置填满](assets/Decode%20的%20GPU%20时间线：显存通道几乎不停，计算单元八成时间在等/00659.webp)

[【跳转到 10:59】](https://www.youtube.com/watch?v=2AZJP_vjPEs&t=659)

视频强调：

> **模型权重和 KV cache 是两样不同的东西。** 在 Prefill 期间，模型为 prompt 的 token 创建 KV；在每一个 decode 步骤里，注意力从已有的 KV cache 读取相关信息，同时模型在每一层为新生成的 token 追加新的 key 和 value 向量。

所以 decode 的显存流量有两个来源：权重，以及 KV cache。而 KV cache 是**每条序列各一份**的，batch 越大、上下文越长，它就越占地方。视频的结论是：

> 上下文更长、batch 更大时，**KV cache 的容量和带宽都可能成为主要约束**。

这就是 batch 的第一堵墙：**显存容量**。权重是固定开销，KV cache 随「batch × 上下文长度」线性增长，撞上去就是 OOM 或者被迫缩小 batch。

### 6.2 凑批和调度会拉长单请求延迟

视频列出的第二笔账是延迟：

> 更大的 batch 占用更多 KV cache 显存，而**等待凑批或调度批次又会影响单个请求的延迟**。

这句话有两层：

- **凑批**：为了把 batch 填满，新到的请求可能要等一会儿才被服务；
- **每步变长**：一个 batch 里有 $B$ 行，每一步要算 $B$ 行，单步耗时上升，于是单个请求的**每 token 延迟（TPOT）**变长。

所以 batch 的收益是**吞吐**（每秒吐出的 token 总数），代价是**延迟**（单个用户等下一个 token 的时间）。视频的原话是：

> 服务系统永远在**吞吐、延迟和显存容量**之间做平衡。

### 6.3 「更大」不自动更好

视频用一句话收住了这一节：

> 更大并不自动意味着永远更好。**重点在于 batching 改变了「工作量和数据量」的比例。**

这句话是整个 1.2.3 的核心。batch 不是让 GPU 变快了，而是让**同样的数据搬动换来更多有用的数学**。一旦这个比例已经足够高（计算通道已经接近满负荷），再加 batch 就只能让每一步变长，收益递减。

---

## 七、三种情形并排：变的只有工作的形状

视频最后把三种情形放在一张表里比较：

| 情形 | 每步可用的新 token 行数 | 每字节的有用工作 | 常见瓶颈 |
| --- | --- | --- | --- |
| Decode，batch = 1 | 1 行 | 低 | 显存带宽 |
| Prefill，长 prompt | $S$ 行（prompt 长度） | 高 | 计算 |
| Decode，batch = $B$ | $B$ 行 | 中到高 | 随 $B$ 增大向计算侧移动 |

视频的收尾句值得原样保留：

> 那么什么变了？**不是模型，不是权重，甚至不是 GPU。变的是工作的形状。** Prefill 暴露了很多 token 位置，为每一次数据搬动创造大量可并行的数学；低 batch 的 Decode 每条活跃序列只暴露一个新位置。

以及一个必须记住的限定：

> 而且这些是**常见的运行区间，不是普适定律**。真正的瓶颈取决于模型结构、prompt、上下文长度、batch size、kernel 实现以及 GPU 硬件等等很多因素。

---

## 小结

- **闲置率来自形状，不来自实现。** batch size 为 1 时，一次 GEMV 只有 $N$ 个独立输出元素，能铺开的并行工作远少于 SM 数乘以每 SM 线程容量；每个权重只做一次乘加，Tensor Core 的块状 MMA 指令里有效行只有 1 行。
- **时间线给出了可看的证据。** 同一块 GPU 上，decode（B=1）的显存通道 86% 忙、计算通道只有 17% 忙；把负载换成 10000 token 的 Prefill，两个数字几乎对调（23% / 92%）。
- **batch 的作用是给权重 tile 加行。** B 从 1 到 4 到 16，计算通道忙碌从 17% 到 48% 到 86%，权重 tile 解锁的计算从 10 GFLOP 到 40 到 160 GFLOP，一次计算爆发从 55 毫秒到 175 毫秒。
- **形状上就是从 GEMV 回到 GEMM。** $M$ 从 1 变成 $B$，算术强度从 1 抬到约 $B$（严格写是 $\frac{2BKN}{2KN + 2BK + 2BN}$）。
- **这条路要付两笔账。** KV cache 显存随 batch 线性增长（容量墙），单步要算 $B$ 行（TPOT 变长）。所以 batch 是吞吐与延迟之间的旋钮。
- **batch 变大之后，瓶颈会往计算侧移动。** 一旦计算通道接近满负荷，继续加 batch 的收益就递减——这正是「转向 GEMM 是必要条件而非充分条件」的另一半含义。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| compute-bound（计算受限） | 计算本身是最慢的一环，加带宽没用，只能加算力或减少运算量 |
| memory-bound（访存受限） | 计算单元还有余力却一直在等数据，搬数据的速度在决定节奏；与显存是否装满无关 |
| arithmetic intensity（算术强度） | 每搬动一个字节做了多少次浮点运算，单位 FLOP/Byte |
| GEMV | 矩阵乘向量，$M = 1$，decode 单请求的形状 |
| GEMM | 矩阵乘矩阵，$M > 1$，Prefill 与 batch decode 的形状 |
| weight tile（权重分块） | GPU 执行时把权重切成的小块，必须从 HBM 经存储层级搬到 SM 附近才能用 |
| Tensor Core | GPU 里做矩阵乘累加的专用单元，天生按块（MMA 指令）工作 |
| KV cache | 每条序列为已见 token 保存的 key/value，decode 每步读取并追加，显存随 batch 与上下文线性增长 |
| TPOT | 单 token 生成延迟，即相邻两个输出 token 之间的时间；batch 越大每步要算的行越多，它就越长 |
