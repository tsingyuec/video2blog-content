# 把 Goodput 当目标函数：聚合与分离都只是在 SLO 及格线上搬时间

> 视频来源：[大模型预填充和解码服务：提高有效吞吐量的新方法](https://www.bilibili.com/video/BV1Hd4zzaEMY/)（Bilibili · UP 主 Osito5）｜时长约 8 分钟
> 简要导读：这支 8 分钟的视频用「聚合派 vs 分离派 vs TaiChi」三方对垒的方式，把 Goodput 讲成了一场**及格率之争**：聚合把所有 GPU 都拿来接新请求，TTFT 漂亮但 TPOT 崩；分离把 Prefill 与 Decode 拆开，TPOT 漂亮但 TTFT 崩；TaiChi 则用「延迟转移」把已经及格的请求的余量匀给快要不及格的请求，把及格率往上抬，最终在同样的 SLO 下把 Goodput 提升 77%。本文按它的叙事展开，并把「Goodput 为什么是目标函数」「过载点长什么样」「峰值与帕累托前沿的关系」三层补足；凡是我补的工程解释，都标了「补充」。Goodput 的定义与计算口径见同小节的另一篇《Goodput 是给吞吐加一道 SLO 过滤》，TTFT / TPOT 的测量见 2.1.1 与 2.1.2。

## 本讲要解决的核心问题（SCQA）

**背景**：所有大模型的工作流程都能拆成两步——**预填充（Prefill）**把整段 prompt 读一遍，**解码（Decode）**一个字一个字往外吐。这两步对应两个用户体验指标：TTFT（多快见到第一个字）和 TPOT（之后每个字多快）。

**冲突**：这两个指标**互相拉扯**。想要 TTFT 短，就得让尽可能多的 GPU 随时能接新请求；可预填充的计算量极大，一旦和正在解码的请求挤在同一批 GPU 上，解码就被拖慢，TPOT 崩掉。反过来把两者拆开，TPOT 稳了，能接新请求的 GPU 又变少了，TTFT 崩掉。**只顾一头是不行的。**

**疑问**：既然两个指标没法同时压到最低，那「一套系统到底好不好」该用哪个数来衡量？在这个数上，聚合、分离、混合三种架构各自能走到哪一步？

**回答（中心思想）**：**用 Goodput——在 TTFT 与 TPOT 都达标的前提下，系统能同时处理多少个请求。** 它把「快」从两个互相拉扯的指标变成了一个单一的优化目标：不是把 TTFT 压到最低，也不是把 TPOT 压到最低，而是**让尽可能多的请求同时踩在两条及格线以内**。聚合与分离的差别，本质上只是把同一块 GPU 预算切给谁；TaiChi 的「延迟转移」则揭示了一个更本质的事实——**已经及格的请求身上有余量，把这份余量匀给快要不及格的请求，及格率就能整体抬升**。

![聊天机器人与文档总结器最在乎的不是同一个速度：前者要首字快，后者要整体生成快](assets/把%20Goodput%20当目标函数：聚合与分离都只是在%20SLO%20及格线上搬时间/00031.webp)

## 一、AI 的两种速度：TTFT 与 TPOT 对应两类产品

### 1.1 聊天机器人要「首字快」，文档总结器要「整体快」

视频开场先摆了一张对照表，把两类 AI 应用最在乎的东西分开：

| AI 应用 | 最重要的是什么 |
| --- | --- |
| 聊天机器人 | 快速吐出第一个字，让人感觉反应灵敏 |
| 文档总结器 | 快速生成完整的总结，以便迅速完成工作 |

这张表是理解 SLO 的起点：**SLO 的目标值不是拍脑袋定的，而是从产品形态里长出来的**。聊天场景里，用户盯着屏幕等第一个字，超过一两秒就开始怀疑网络；文档总结场景里，用户按下按钮就去干别的了，他关心的是「两分钟后回来能不能拿到完整结果」。

> 补充：这就是为什么同一套推理集群，面向聊天产品时会把 TTFT 的 SLO 定得很紧（比如 P99 ≤ 1–2 秒）、把 TPOT 定得相对宽松（比如 ≤ 100 ms/token，即每秒 10 字以上），而面向批处理/离线摘要时几乎不约束 TTFT、只约束总时长。代码补全又是第三种：它对 TTFT 极敏感（用户正在打字），但对 TPOT 反而没那么敏感。**SLO 是产品决策，不是技术参数。**

### 1.2 TTFT 量的是「等到第一个字」，TPOT 量的是「之后每个字」

视频接着把两个指标各自定义了一遍：

- **TTFT（首词响应时间）**：从你发出请求，到它吐出第一个字，花了多长时间。TTFT 越短，用户越觉得这个 AI 灵光、反应快。
- **TPOT（每词输出时间）**：生成后续每个词的平均时间。TPOT 越小，打字速度越快，整个任务完成得越利索。

![TPOT 的定义：生成后续每个词的平均时间，衡量的是整体生成速度](assets/把%20Goodput%20当目标函数：聚合与分离都只是在%20SLO%20及格线上搬时间/00085.webp)

### 1.3 只顾一头不行，于是有了 Goodput

视频在这里做了一个关键的转折：**我们既想要 TTFT 短，又想要 TPOT 低，只顾一头是不行的。** 所以工程师们真正的终极目标，是一个叫有效吞吐量、也就是 Goodput 的东西。

[【跳转到 01:44】](https://www.bilibili.com/video/BV1Hd4zzaEMY/?t=104)

![Goodput 的定义：在满足 TTFT 和 TPOT 目标的前提下，系统能处理的最大请求数](assets/把%20Goodput%20当目标函数：聚合与分离都只是在%20SLO%20及格线上搬时间/00104.webp)

视频给的措辞是「**在满足 TTFT 和 TPOT 目标的前提下，系统能处理的最大请求数**」。这句话里有两个词值得抠：

- **「满足目标」**是一个过滤条件，把不达标的请求排除在外；
- **「最大」**说明 Goodput 是一个**要优化的量**，而不是一个被动记录的观测值。

把这两点合起来看，Goodput 就是这台机器在给定 SLO 下的**有效产能**——和吞吐量的区别只在于「有效」二字（定义、算式与「100 QPS 里 78 个达标」的例子见同小节另一篇）。

## 二、聚合派：所有 GPU 都接新活，TTFT 漂亮，TPOT 崩

### 2.1 策略：为了让 GPU 别闲着，所有活扔给同一批 GPU

**聚合（Aggregation）**的思路特别直接：为了让 GPU 别闲着，把所有的活都扔给同一批 GPU 去跑。不管你是刚来的新请求、需要做预填充，还是正在生成答案的老请求、需要做解码，都在这排队一起处理。

[【跳转到 02:32】](https://www.bilibili.com/video/BV1Hd4zzaEMY/?t=152)

### 2.2 成绩单：TTFT 优秀，TPOT 一塌糊涂

视频给聚合派打的分是**一好一坏**：

- **TTFT 表现优秀**——因为所有实例都可以参与预填充，来个新活马上就能接；
- **TPOT 一塌糊涂**——生成速度非常不稳定。

![聚合派的成绩单：TTFT 优秀，因为所有实例都可以参与预填充](assets/把%20Goodput%20当目标函数：聚合与分离都只是在%20SLO%20及格线上搬时间/00173.webp)

### 2.3 罪魁祸首是「干扰」：一百人的大单占满了所有灶台

为什么 TPOT 会崩？视频的答案是两个字：**干扰**。

预填充阶段（模型消化你指令的时候）计算量超级大。视频用餐厅打比方：厨房突然接了个一百人的大单，这个大单直接占满了所有厨师和灶台，导致其他所有正在等上菜的散客，哪怕你只要一个拍黄瓜，都得等着。

**那些正在解码的任务，也就是正在一个字一个字生成答案的任务，全都被拖慢了。**

![预填充的计算强度极高，一旦和解码挤在同一批 GPU 上，解码就被拖慢](assets/把%20Goodput%20当目标函数：聚合与分离都只是在%20SLO%20及格线上搬时间/00203.webp)

> 补充：从指标上看，这就是 TPOT 的**分位数**被拉爆。平均 TPOT 可能还过得去，但只要 batch 里混进一个长 prompt，那一步的解码就被拉长几十毫秒，P99 TPOT 立刻超标。而 SLO 是分位数约束，所以「偶尔来一个大 prompt」这种看起来无害的波动，恰恰是聚合派最致命的弱点。

## 三、分离派：Prefill 与 Decode 拆开，TPOT 漂亮，TTFT 崩

### 3.1 策略：专业的人干专业的事

**分离（Disaggregation）**的思路跟聚合正好反着来：把 GPU 分成两组，一组专门处理新来的请求（做预填充），另一组专门生成答案（做解码），各干各的、互不干扰。视频点名 DistServe 是这个路子的典型代表。

[【跳转到 03:53】](https://www.bilibili.com/video/BV1Hd4zzaEMY/?t=233)

![分离派：Prefill 阶段算出 KV 状态后，把状态转移到 Decoding 阶段继续生成](assets/把%20Goodput%20当目标函数：聚合与分离都只是在%20SLO%20及格线上搬时间/00240.webp)

画面把这条链路画得很清楚：请求先进 **Prefilling Stage**，算完之后通过 **Transfer State** 把状态（也就是 KV Cache）送到 **Decoding Stage**，由后者一个字一个字吐出来。

### 3.2 成绩单：TPOT 优秀，TTFT 糟糕

结果正好反过来：

- **TPOT 表现优秀**——因为解码任务再也不会被大计算量的预填充任务干扰了，生成速度又快又稳；
- **TTFT 表现糟糕**——因为只有一部分实例处理新请求，新来的请求得排队。

![分离派的成绩单：TTFT 糟糕，因为只有一部分实例处理新请求；TPOT 优秀，因为消除了干扰](assets/把%20Goodput%20当目标函数：聚合与分离都只是在%20SLO%20及格线上搬时间/00263.webp)

### 3.3 代价是「接单能力」下降：10 个 GPU 只剩 3 个

视频把这个代价讲得非常直白：**系统的接单能力下降了**。本来你有 10 个 GPU 都能接新活，现在可能只有 3 个了。

[【跳转到 04:48】](https://www.bilibili.com/video/BV1Hd4zzaEMY/?t=288)

![分离派的代价：能接新请求的 GPU 从 10 个变成 3 个，新请求一多就只能排队](assets/把%20Goodput%20当目标函数：聚合与分离都只是在%20SLO%20及格线上搬时间/00293.webp)

**新请求一多，这 3 个 GPU 根本忙不过来，后面来的请求就只能等着，首词响应时间当然就长了。**

这张图其实是本节最值得记住的一张，因为它画的就是**过载点**：左边是一堆涌进来的请求，右边只有三台 GPU 在接，队列越积越长，时钟变红、表情变怒。

> 补充：这就是「过载」的典型形态——**到达率超过服务率，队列不收敛**。此时 TTFT 不是「慢一点」，而是随时间线性甚至超线性增长：队列里每多一个请求，新来的请求就多等一个服务时间。这也是为什么过载之后 Goodput 会**断崖式下跌**：达标率趋近于零，而吞吐量因为 GPU 一直满负荷反而看起来还行。**吞吐量和 Goodput 在过载区彻底分道扬镳，这正是必须用 Goodput 的原因。**

## 四、两难：这不是选边站，是同一块 GPU 预算的两种切法

视频把局面总结成一句话：要么响应快、生成慢，要么生成快、响应慢。**难道就没有两全其美的办法吗？**

[【跳转到 04:53】](https://www.bilibili.com/video/BV1Hd4zzaEMY/?t=293)

![在快速开始和快速完成之间，真的必须二选一吗](assets/把%20Goodput%20当目标函数：聚合与分离都只是在%20SLO%20及格线上搬时间/00319.webp)

在跳到答案之前，先把这个问题用 Goodput 的语言重述一遍，会清楚很多：

- **聚合派**：TTFT 达标率高、TPOT 达标率低 → Goodput 被 TPOT 卡住；
- **分离派**：TPOT 达标率高、TTFT 达标率低 → Goodput 被 TTFT 卡住；
- **混合**：能不能让两边都别成为短板？

因为 Goodput 要求**两个条件同时满足**，所以它天然是一个「短板指标」：**任何一头的达标率掉下来，Goodput 就跟着掉**。聚合与分离各自把一头做到极致、另一头做废，结果都是被短板拖住。

> 补充：这也解释了为什么「聚合 vs 分离」的优劣没有普适答案。如果 SLO 只约束 TPOT（比如离线批处理），分离派直接赢；如果 SLO 只约束 TTFT（比如极短输出的问答），聚合派反而更好。**只有把 SLO 摆出来，架构选择才有意义。**

## 五、TaiChi 的三步法：把「余量」变成「及格」

视频介绍的 TaiChi 系统，思路分三步。

### 5.1 第一步：差异化实例，P-heavy 与 D-heavy

它不搞一刀切，而是把 GPU 分成两种角色：

- **预填充重型（P-heavy）**：专门负责快速开工；
- **解码重型（D-heavy）**：专门负责稳定输出。

[【跳转到 05:32】](https://www.bilibili.com/video/BV1Hd4zzaEMY/?t=332)

![TaiChi 的三步法：差异化实例、混合模式推理、延迟转移](assets/把%20Goodput%20当目标函数：聚合与分离都只是在%20SLO%20及格线上搬时间/00332.webp)

> 补充：这一步的实质是把「异构」引入集群——不是所有 GPU 都干一样的活，而是按阶段特性配比。预填充吃算力，解码吃显存带宽，两类机器的最优配置本来就不同。

### 5.2 第二步：混合模式推理，请求像接力赛

一个请求可以先进到 P-heavy 的 GPU 那里快速完成预填充，然后再被转移到 D-heavy 的 GPU 那里去完成后面的生成。**这就有点像接力赛。**

注意这一步和「分离派」的区别：分离派是**静态**分工（这组机器只做预填充，那组只做解码），TaiChi 是**允许请求在两种实例之间流动**。流动意味着资源可以按当时的负载重新分配——这正是它比纯分离更灵活的地方。

### 5.3 第三步：延迟转移，从「富人」匀给「穷人」

这是 TaiChi 的核心创新。视频把论文原文念了一遍：

> **策略性地降低已满足 SLO 请求的延迟，将资源重新分配给有违规风险的请求。**

[【跳转到 06:07】](https://www.bilibili.com/video/BV1Hd4zzaEMY/?t=367)

![延迟转移的定义：策略性地降低已满足 SLO 请求的延迟，将资源重新分配给有违规风险的请求](assets/把%20Goodput%20当目标函数：聚合与分离都只是在%20SLO%20及格线上搬时间/00392.webp)

视频给它起了个外号叫「**GPU 界的罗宾汉**」，解释得非常到位：

- 系统里总有些请求运气好、处理得特别快，远远超过了我们的预期——这是「**富人**」；
- 也有些请求运气不好、快要超时了——这是「**穷人**」；
- 它干的事就是：**从富人请求那里稍微借一点点 GPU 资源**（反正它们已经很快了，再慢一点点也无所谓），**匀给那些快要不及格的穷人请求**，帮它们一把。

**这样一来，整个系统的及格率就大大提高了。**

### 5.4 为什么这能提高 Goodput：及格线之上是「浪费」

这一步值得展开讲，因为它是本节最重要的一条工程直觉。

**Goodput 只数「达标」与「不达标」两种结果，不区分「达标得多漂亮」。** 一个请求用 200 ms 完成，SLO 是 2 秒——它剩下的 1.8 秒余量对 Goodput **毫无贡献**，是纯粹的浪费。而另一个请求眼看要 2.1 秒才完成，差一点点就掉出及格线。

把前者的余量匀一点给后者：

- 前者从 200 ms 变成 400 ms，**仍然达标**，Goodput 不变；
- 后者从 2.1 秒变成 1.9 秒，**从不及格变成及格**，Goodput +1。

**净效果是 Goodput 上升，而总资源消耗几乎没变。** 这就是「延迟转移」的全部魔法：它不创造资源，只是把资源配置从「已经过剩的地方」搬到「边际收益最高的地方」。

> 补充：这个思路在排队论里的名字叫「**SLO 感知调度**」——调度目标不是最小化平均延迟，而是最大化「延迟落在阈值内的请求数」。两者的最优策略完全不同：最小化平均延迟会倾向于让所有请求都差不多快，最大化达标率则会**故意牺牲一部分请求**（让它们慢到刚好不超标）去救另一部分。这也是为什么 Goodput 优化出来的系统，延迟分布往往更「平」——贴着及格线走。

## 七、把 Goodput 当目标函数的三条工程结论

> 本节是补充：视频只讲了架构对比，下面三条是从「Goodput 是目标函数」这个前提出发的推论。

### 7.1 报吞吐必须同时报 SLO，否则数字没有意义

聚合派和分离派的「吞吐量」可能差不多，但它们的 Goodput 差很远。原因很简单：**吞吐量不区分达标与不达标**。所以看到任何「每秒 X 个 token」的宣传数字，第一个问题永远是「在什么 SLO 下、什么长度分布下」。

### 7.2 Goodput 峰值对应帕累托前沿上的一个点，换 SLO 就换峰值

把「吞吐 vs 延迟」平面上所有不可同时改进的配置连成一条前沿，SLO 在前沿上切出一段可行区间，**这段区间里吞吐最大的点就是 Goodput 峰值**。

- SLO 放宽 → 可行区间变长 → 峰值右移、变高；
- SLO 收紧 → 可行区间变短 → 峰值左移、变低。

这解释了为什么「同一套系统能报出好几个不同的峰值吞吐」——它们不是矛盾，而是对应不同的 SLO。聚合、分离、TaiChi 在这张图上的差别，是**前沿本身的形状不同**：TaiChi 把前沿往外推了，所以在同一 SLO 下能取到更靠右的点。

> 补充：具体怎么在前沿上选配置（并行策略、P/D 实例配比、batch 上限）属于 2.3.3 的内容，本文不展开。

### 7.3 过载之后，吞吐量和 Goodput 会分道扬镳

分离派那张「10 个 GPU 只剩 3 个」的图已经演示了这件事：队列越积越长时，GPU 仍然满负荷（吞吐量看起来还行），但几乎所有请求都超时（Goodput 趋近于零）。

**所以监控面板上应该同时有两条线**：一条吞吐量，一条 Goodput。当两条线开始分叉，就是过载的信号；这时候该做的不是继续加压，而是限流、降级、或者把请求拒掉——**拒绝一个请求只损失一个，排队会损失一整批**。

## 小结

- **Goodput = 在 TTFT 与 TPOT 都达标的前提下，系统能同时处理多少个请求**。它把两个互相拉扯的指标压成一个可优化的目标。
- **SLO 的目标值来自产品形态**：聊天要首字快，文档总结要整体快，代码补全对 TTFT 最敏感。SLO 是产品决策，不是技术参数。
- **聚合派**：所有 GPU 都接新活，TTFT 优秀，但预填充的巨量计算会干扰解码，TPOT 分位数崩掉。
- **分离派**：Prefill 与 Decode 拆到两组 GPU，TPOT 优秀，但接单能力下降（10 个 GPU 只剩 3 个），TTFT 崩掉。
- **两者都被短板卡住**，因为 Goodput 是双条件约束，任何一头掉下来它就跟着掉。
- **延迟转移的洞察是「及格线之上是浪费」**：已经远快于 SLO 的请求，余量对 Goodput 毫无贡献；匀给快要不及格的请求，就能净增加达标数。
- **77% 的 Goodput 提升等价于约 44% 的机器节省**，这比任何峰值吞吐数字都更能说明系统优化的价值。
- **过载之后吞吐量与 Goodput 分道扬镳**，监控上必须两条线一起看；分叉即过载，此时拒绝比排队好。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| Goodput（有效吞吐量） | 在 TTFT 与 TPOT 都达标的前提下，系统每秒能处理的请求数 |
| 预填充（Prefill） | 模型把整段 prompt 读一遍、算出第一个 token 的阶段，计算量大、算力受限 |
| 解码（Decode） | 逐 token 生成答案的阶段，访存受限、对干扰极敏感 |
| 聚合（Aggregation） | 预填充与解码跑在同一批 GPU 上，接单能力强但解码易被干扰 |
| 分离（Disaggregation） | 预填充与解码拆到两组 GPU，解码稳定但接单能力下降 |
| P-heavy / D-heavy | 预填充重型与解码重型实例，按阶段特性差异化配置的 GPU 角色 |
| 延迟转移（Latency Shifting） | 策略性降低已达标请求的延迟，把资源重新分配给有违规风险的请求 |
| SLO 达标率 | 满足 SLO 的请求占总请求的比例，Goodput 就是达标率乘以到达率 |
| 过载点 | 到达率超过服务率、队列不收敛的临界点，表现为 TTFT 线性增长、Goodput 断崖下跌 |
| 帕累托前沿 | 吞吐与延迟平面上不可同时改进的配置边界，Goodput 峰值是它被 SLO 截出的一段里最右的点 |
