# Goodput 是给吞吐加一道 SLO 过滤：只数达标的请求

> 视频来源：[TTFT与TPOT：吞吐更高，用户为什么反而觉得更卡？｜AI Infra 图解24](https://www.bilibili.com/video/BV1aYpH6zEas/)（Bilibili · UP 主 图解AI_Infra）｜时长约 1 分 12 秒
> 简要导读：一支 72 秒的图解短片，用「A 每秒 5000 token、B 每秒 3000 token，可用户觉得 A 更卡」这个反直觉的开场，把吞吐、TTFT、TPOT、P99、Goodput 五个概念串成一条线，最后落到一句可操作的定义：**先定标准，再只数达标的请求**。本文以它的画面与解说为骨架，把「Goodput 为什么才是可比的吞吐」「SLO 该怎么定」「怎么在 SLO 约束下找峰值」三层展开；凡是短片没讲、由我补的工程细节，都在文中标了「补充」。TTFT / TPOT 的测量口径见 2.1.1 与 2.1.2，QPS / 输入吞吐 / 输出吞吐的逐项定义见 2.2.1，本文不重复。

## 本讲要解决的核心问题（SCQA）

**背景**：同一款模型、两套部署，A 每秒一共能出 5000 个 token，B 只有 3000 个。按「吞吐量」这个最常用的指标，A 完胜。

**冲突**：可真实用户反而觉得 A 更卡。A 的吞吐更高，用户却在「等待中」；B 的吞吐低一截，用户却觉得流畅。**「快」从来不是一个数字**——吞吐量把所有人的等待平均掉了，而每个用户只经历自己那一次等待。

**疑问**：既然吞吐量不能代表「用户拿到的服务」，那该用什么指标？它怎么定义、怎么算？定好之后，又怎么在这个指标上把系统调到最优？

**回答（中心思想）**：**Goodput（有效吞吐量）= 单位时间内满足 SLO 的请求数**。它和吞吐量的唯一差别就是那个「满足 SLO」的过滤条件——先把 TTFT 与 TPOT 的目标值钉死，再只数达标的请求。于是吞吐量可以被无限加 batch 刷高，Goodput 不能；吞吐量在不同 SLO 下不可比，Goodput 在同一 SLO 下可比。找最大 Goodput 的过程，就是在「吞吐上升、延迟上升」这两条曲线的交叉点附近定位过载点，并在过载点之前用限流与降级把系统按住。

## 一、整机吞吐量回答的是「机器忙不忙」，不是「用户等多久」

### 1.1 吞吐量把所有人的等待加总后平均掉了

视频给的第三个数字是**吞吐**：整台机器每秒一共产出多少 token。它是一个**系统侧**的计数——把这一秒内所有请求吐出的 token 加起来，除以一秒。

问题就在这里：这个数字对「单个用户等了多久」完全不敏感。一万个用户同时在线、每个人都被拖慢到 2 秒才见首字，吞吐量可以很漂亮；只有一个用户在线、秒回，吞吐量反而很低。**吞吐量衡量的是机器的产出速率，不是用户的获得感。**

![画面把两套部署的同一时刻并排放：A 上的用户还卡在瓶颈上，B 上的用户已经在读字，中间那句是「快不是一个数字」](assets/Goodput%20是给吞吐加一道%20SLO%20过滤：只数达标的请求/00009.webp)

> 补充：吞吐量本身还有 QPS / 输入 token 吞吐 / 输出 token 吞吐等多种口径，它们彼此不能直接换算，详见 2.2.1。本节只讨论「为什么单看吞吐量不够」。

### 1.2 吞吐与延迟此消彼长：批量开大，每个人都更慢

视频用一张双曲线图说明了这个权衡：横轴是批量大小，绿线是吞吐，红线是每个人的等待。**批量开大，吞吐上去了，可每个人等得更久。**

[【跳转到 00:23】](https://www.bilibili.com/video/BV1aYpH6zEas/?t=23)

![吞吐与延迟此消彼长：横轴是批量大小，绿线吞吐上升，红线每人等待也上升](assets/Goodput%20是给吞吐加一道%20SLO%20过滤：只数达标的请求/00041.webp)

这条曲线是理解 Goodput 的地基。它意味着：**吞吐量这个指标没有上界意义上的「最优点」**——只要允许延迟无限变差，吞吐总能再高一点。一个没有约束的指标，无法用来比较两套系统谁更好，因为「更好」取决于你愿意付出多少延迟。

## 二、用户实际感受到的是两个数：TTFT 和 TPOT

视频把「快」拆成两个可测的量，这两个量就是后面 SLO 的两个维度。

### 2.1 TTFT：从按下回车到第一个字，时间花在排队和 Prefill 上

**TTFT（Time To First Token，首字延迟）**：从你按下回车，到屏幕上冒出第一个字，要等多久。

视频把它拆成两段：**排队 + Prefill**。排队是请求在调度队列里等 GPU 空出来；Prefill 是模型把你那一大段 prompt 完整读一遍、算出第一个 token。**提示词越长，Prefill 越久，等得越久。**

![TTFT 由两段构成：前面是排队，后面是 Prefill，提示词越长 Prefill 越久](assets/Goodput%20是给吞吐加一道%20SLO%20过滤：只数达标的请求/00019.webp)

### 2.2 TPOT：50 毫秒一个字，就是每秒 20 个字，已经比人读得快

**TPOT（Time Per Output Token，字间隔）**：第一个字之后，往外蹦字的速度。

视频给了一个非常好用的锚点：**间隔 50 毫秒 = 每秒 20 个字**，看起来已经很流畅——**再快人也读不过来**。

[【跳转到 00:11】](https://www.bilibili.com/video/BV1aYpH6zEas/?t=11)

![TPOT 50 毫秒每字等于每秒 20 个字，已经比人读书的速度快](assets/Goodput%20是给吞吐加一道%20SLO%20过滤：只数达标的请求/00030.webp)

这个锚点直接决定了 TPOT 的 SLO 该定在哪里：**它不是越快到死越好，而是过了人眼能感知的阈值之后，继续压低的收益迅速递减**。把 TPOT 从 50 ms 压到 25 ms，用户几乎感觉不到；但为此付出的 GPU 资源是实打实的。

## 三、只看平均数会骗人：要看 P99

视频的第四个动作很关键：**不能只看平均数，要看 P99——最慢的那 1% 请求等了多久。**

[【跳转到 00:35】](https://www.bilibili.com/video/BV1aYpH6zEas/?t=35)

![请求延迟分布示意：多数请求挤在平均值附近，但右侧有一条长尾，P99 落在远高于平均值的位置](assets/Goodput%20是给吞吐加一道%20SLO%20过滤：只数达标的请求/00046.webp)

为什么？因为延迟分布是**右偏**的：绝大多数请求很快，少数请求极慢，平均值被那堆快请求拉得很好看，而**用户记住的恰恰是那几次卡顿**。

> 补充：这也是 SLO 一律写成**分位数**约束（P95 / P99）而不是均值约束的原因。写成「平均 TTFT < 1 秒」时，系统可以让 95% 的请求 0.2 秒返回、5% 的请求 16 秒返回，均值仍然达标——但用户体验已经崩了。写成「P99 TTFT < 1 秒」时，那 1% 的慢请求被直接钉住，没法用平均值掩盖。

长尾的成因分类与治理手段属于 2.2.3 的内容，这里只需要记住一条：**SLO 是分位数约束，Goodput 里的「达标」也是按分位数判定的**。

## 四、Goodput：先定好标准，再只数达标的请求

### 4.1 定义：达标请求的到达速率

视频给出的定义只有一句话：**先定好标准，比如首字不超过 2 秒、字间隔不超过 50 毫秒，再只数达标的请求，每秒能服务多少个。**

[【跳转到 00:47】](https://www.bilibili.com/video/BV1aYpH6zEas/?t=47)

写成式子：

$$
\text{Goodput} = \frac{\#\{\, r \in \text{Requests} : \text{TTFT}(r) \le \text{TTFT}_{\text{SLO}} \ \wedge\ \text{TPOT}(r) \le \text{TPOT}_{\text{SLO}} \,\}}{\text{观测时长}}
$$

其中 $r$ 是一个请求，$\text{TTFT}_{\text{SLO}}$ 与 $\text{TPOT}_{\text{SLO}}$ 是事先钉死的两个目标值。注意分子里的两个不等号是**与**关系：一个请求必须两个条件同时满足才算「达标」，缺一个就不计入。

如果按输出 token 计，把分子换成达标请求吐出的 token 总数即可：

$$
\text{Goodput}_{\text{token}} = \frac{\sum_{r \in \text{达标}} \text{OutputTokens}(r)}{\text{观测时长}}
$$

### 4.2 一个具体例子：100 QPS 里只有 78 个达标

假设某套部署在压测中稳定接收 **100 QPS** 的请求，SLO 定为 TTFT ≤ 1 秒且 TPOT ≤ 100 毫秒。跑完之后统计：

- 100 个请求里有 **78 个**同时满足两个条件；
- 剩下 22 个里，15 个是 TTFT 超标（排队排太久），7 个是 TPOT 超标（batch 里挤了长 prompt，解码被拖慢）。

于是：

$$
\text{Goodput} = 78\ \text{QPS}, \qquad \text{吞吐量} = 100\ \text{QPS}
$$

**两个数字差了 22%。** 如果只报吞吐量，你会以为这套系统能扛 100 QPS；实际上它只能「有效」服务 78 QPS，剩下 22 QPS 是**用户不满意的产出**——机器确实在忙，但忙出来的东西没人愿意要。

> 补充：上例中的数字是为说明口径而构造的示意值，不是任何系统的实测结果。

### 4.3 画面里那张打勾的网格，就是 Goodput 的算法

视频用一张网格把这件事画了出来：每个格子是一个请求，绿色打勾是达标，红色打叉是超时。

![Goodput 的算法：每个格子是一个请求，绿色打勾是达标，红色打叉是超时，Goodput 等于每秒达标的请求数](assets/Goodput%20是给吞吐加一道%20SLO%20过滤：只数达标的请求/00056.webp)

这张图值得记住的地方在于：**红色格子并没有消失**。系统仍然处理了它们，仍然消耗了 GPU，只是它们不计入 Goodput。所以 Goodput 天然是一个「带惩罚」的指标——**超时的请求不是零收益，而是负收益**，因为它占掉了本可以让别的请求达标的资源。

## 五、为什么必须用 Goodput：它把「吞吐」锚定到「有用」

### 5.1 吞吐量可以靠无限加 batch 刷高，Goodput 不行

回到第一节那条双曲线。如果没有 SLO 这根绳，你可以把 batch 一路加到显存爆掉为止，吞吐量一直涨，延迟一直烂。**吞吐量这个指标对「烂延迟」是不敏感的**，所以它天然鼓励你把系统调到用户无法忍受的那一端。

加上 SLO 之后，情况变了：

- batch 加大 → 吞吐上升，但 TPOT 上升 → 达标的请求变少 → **Goodput 可能反而下降**；
- batch 减小 → 吞吐下降，但延迟变好 → 达标率上升 → **Goodput 可能反而上升**。

于是 Goodput 有了一个**内部最优点**，而吞吐量没有。**一个指标有最优点，才能用来做优化目标。**

### 5.2 吞吐量在不同 SLO 下不可比，Goodput 在同一 SLO 下可比

这是 Goodput 最实用的价值。假设两家厂商都宣称「每秒 5000 token」：

| 厂商 | 宣称吞吐 | 隐含的延迟条件 |
| --- | --- | --- |
| 甲 | 5000 tok/s | 未说明（实测 TPOT 300 ms，用户明显卡顿） |
| 乙 | 5000 tok/s | 未说明（实测 TPOT 60 ms，流畅） |

两个 5000 无法比较，因为你不知道它们各自付出了多少延迟。但如果两家都报「在 TTFT ≤ 2 s、TPOT ≤ 50 ms 下的 Goodput」，数字就直接可比了——**SLO 是那个把「吞吐」换算到同一坐标系里的汇率**。

> 补充：这也是为什么厂商在发布会报的峰值吞吐往往对应一个极宽松的 SLO（比如只约束吞吐、不约束 TPOT），而论文里的 Goodput 数字通常对应严格得多的 SLO。看到吞吐数字时，第一件事是问「在什么 SLO 下」。

### 5.3 同样的标准下，PD 分离多服务了 7.4 倍请求

视频最后给了一个具体的对比：第 11 期讲过的 PD 分离（Prefill-Decode 分离），比的就是 Goodput——**在同样的 SLO 标准下，多服务了 7.4 倍请求**。

![在同样的 SLO 标准下，PD 分离方案多服务了 7.4 倍请求](assets/Goodput%20是给吞吐加一道%20SLO%20过滤：只数达标的请求/00059.webp)

注意这句话里最重要的三个字是「**同样的标准下**」。7.4 倍这个数字之所以有意义，是因为两边用的是同一把尺子；如果一边报吞吐、一边报 Goodput，7.4 倍就毫无意义。PD 分离的机制属于第 10 章，本文不展开。

## 六、怎么在 SLO 约束下找到最大 Goodput

> 本节是补充：短片只给了定义与一个对比结果，没有讲怎么扫参数。下面这套流程是工程上的通行做法。

### 6.1 扫描到达率，同时画吞吐曲线与延迟曲线

做法是固定 SLO 与请求长度分布，把**到达率**（或并发数）从低到高扫一遍，每个点跑够时间，记录三组数：

1. 实际吞吐（token/s 或 QPS）；
2. TTFT 与 TPOT 的分位数（P50 / P95 / P99）；
3. 达标率，进而算出 Goodput。

把结果画成两条曲线叠在一张图上：横轴是到达率，纵轴一边是吞吐、一边是延迟分位数。

### 6.2 Goodput 在两条曲线的交叉点附近达到峰值

低负载区：延迟几乎不随到达率变化（系统有余量），吞吐线性上升，达标率接近 100%，**Goodput 跟着吞吐一起线性上升**。

接近饱和区：队列开始堆积，TTFT 分位数开始抬头，达标率开始掉，**吞吐还在涨但 Goodput 涨得慢了**。

过载区：延迟**非线性**上升，达标率断崖式下跌，**吞吐趋于平台甚至下降，Goodput 明确下降**。

Goodput 的峰值就落在「达标率开始明显下滑」与「吞吐还在上升」这两件事互相抵消的那个点上——**不是吞吐最大的点，也不是延迟最好的点，而是两者乘积最大的点**。

### 6.3 怎么识别过载点：三个可观测信号

- **延迟开始非线性上升**：到达率再涨 10%，P99 TTFT 涨了 50% 以上，说明队列已经进入正反馈。
- **Goodput 反而下降**：这是最直接的判据——继续加压，达标请求数不升反降。
- **队列长度持续增长不收敛**：说明到达率已经超过服务率，系统在「欠债」，此时任何短时抖动都会放大成雪崩。

> 补充：这三个信号里，第二个是唯一不需要额外监控就能从业务指标上看到的——**如果加压之后你的有效产出下降了，那一定已经过载了**。

### 6.4 优雅降级：拒绝比排队好，降级比超时好

一旦接近过载点，正确的动作不是继续排队，而是主动把一部分流量挡在门外或降级处理。三种手段按代价从低到高：

| 手段 | 做法 | 代价 |
| --- | --- | --- |
| 限流 | 超出容量的请求直接快速失败（返回 429 或排队提示） | 用户被拒，但没被拖慢 |
| 降级到小模型 | 把简单请求路由到更小/更快的模型 | 质量下降，但延迟达标 |
| 拒绝而非排队 | 队列长度设上限，满了就拒 | 同上，且保护了已在队列里的请求 |

核心逻辑是：**排队会把一个请求的失败扩散成一批请求的失败**。一个请求在队列里等 10 秒，它不仅自己超时，还占着队列位置让后面的请求也超时。快速拒绝只损失一个请求，排队可能损失一整批。

### 6.5 与帕累托前沿的关系：Goodput 峰值就是「在给定 SLO 下沿前沿能走到的点」

把「吞吐 vs 延迟」平面上所有**不可被同时改进**的配置连起来，就得到帕累托前沿：想更高吞吐就必须接受更高延迟，反之亦然。

- **SLO 在平面上画出一个矩形**（TTFT 上界 × TPOT 上界）；
- 前沿上落在矩形内的那一段，就是**这套系统在这条 SLO 下能走到的全部可行配置**；
- 其中吞吐最大的那个点，就是 **Goodput 峰值**。

所以：**换一条 SLO，就换一个 Goodput 峰值**。SLO 放宽，矩形变大，前沿上能取到更靠右的点，Goodput 峰值变高；SLO 收紧，峰值变低。这就是为什么「同一套系统能报出好几个不同的峰值吞吐」——它们对应不同的 SLO。

> 补充：怎么在前沿上选具体配置（并行策略、实例配比、batch 上限）属于 2.3.3 的内容，本文只讲 Goodput 峰值与前沿的对应关系。

## 七、测量要点：报 Goodput 时必须同时报 SLO 与长度分布

> 本节是补充，讲的是「怎么测才不骗人」。

### 7.1 固定长度分布，否则数字不可复现

输入长度决定 Prefill 开销，输出长度决定解码步数，两者共同决定 TTFT 与 TPOT。**换了长度分布，Goodput 就换了一个数**。所以压测必须固定一个明确的长度分布（比如输入 512 / 输出 256，或按真实流量采样），并在报告里写清楚。

### 7.2 用开环（固定到达率）压测，不要用闭环（固定并发）

- **闭环**：起 N 个并发客户端，每个发完一个再发下一个。系统变慢时，客户端自动变慢，**压力自动减小**——这叫「协调遗漏」（coordinated omission），会把延迟和 Goodput 都测好。
- **开环**：按固定到达率（比如每秒 100 个）发请求，不管系统回不回得来。系统变慢时压力不减，**这才是真实流量**。

测 Goodput 必须用开环，因为 Goodput 要回答的问题是「在这个到达率下，有多少请求能达标」——闭环压测根本产生不了这个到达率。

### 7.3 报告里必须同时出现三样东西

一个诚实的 Goodput 数字至少要有：**SLO 的具体值（含分位数）** + **长度分布** + **Goodput 值**。缺任何一样，这个数字都无法与别人的数字比较。

### 7.4 小心重试放大：它会把 Goodput 算高

超时的请求会被客户端重试。重试的请求如果成功了，会被计成一次达标——但**用户实际经历的是「先等了一次超时，又等了一次成功」**。于是 Goodput 被算高，而用户体验被高估。

处理办法：在压测与统计里**按请求 ID 去重**，或者把重试计入同一逻辑请求的端到端延迟。否则超时率越高、重试越多，Goodput 反而越好看。

---

## 小结

- **吞吐量衡量机器忙不忙，Goodput 衡量用户满不满意**。前者对延迟不敏感，可以被无限加 batch 刷高；后者有内部最优点，才能当优化目标。
- **Goodput = 单位时间内同时满足 TTFT 与 TPOT 目标的请求数**。100 QPS 里 78 个达标，Goodput 就是 78 QPS，而不是 100 QPS。
- **SLO 必须写成分位数**（P95 / P99），因为延迟分布右偏，平均值会被大量快请求掩盖长尾。
- **TTFT 的 SLO 来自「等多久算卡」**，**TPOT 的 SLO 来自「人读多快」**——50 ms/字（每秒 20 字）已经比人读得快，继续压低收益递减。
- **找最大 Goodput 就是扫到达率、画吞吐与延迟两条曲线**，峰值在达标率开始下滑与吞吐仍在上升互相抵消处；过载点的信号是延迟非线性上升、Goodput 反降。
- **过载时拒绝比排队好**：排队会把一个请求的失败扩散成一批。
- **Goodput 峰值 = 给定 SLO 下沿帕累托前沿能走到的最右点**；换 SLO 就换峰值，所以看吞吐数字先问「在什么 SLO 下」。
- **测量要用开环、固定长度分布、按请求去重**，并且报 Goodput 时同时报 SLO 与长度分布。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| 吞吐量（Throughput） | 整台机器每秒产出的 token 总数或每秒完成的请求数，不区分这些产出用户是否满意 |
| Goodput（有效吞吐量） | 单位时间内**满足 SLO** 的请求数（或这些请求产出的 token 数） |
| SLO（Service Level Objective） | 服务等级目标，对 TTFT / TPOT 等指标设定的分位数上界，如「P99 TTFT ≤ 2 s」 |
| TTFT | 从发出请求到收到第一个 token 的时间，由排队与 Prefill 两段构成 |
| TPOT | 第一个 token 之后平均每个 token 的生成时间，倒数即单用户出字速度 |
| P99 | 把所有请求按延迟排序后第 99 百分位的值，用来钉住最慢的那 1% |
| 过载点 | 到达率超过服务率、队列开始不收敛的临界点，表现为延迟非线性上升、Goodput 反降 |
| 开环压测 | 按固定到达率发请求、不因系统变慢而减速的压测方式，能暴露真实过载行为 |
| 闭环压测 | 固定并发数、发完一个再发下一个，系统变慢时压力自动减小，会低估延迟 |
| 协调遗漏（Coordinated Omission） | 闭环压测的固有偏差：慢请求期间本应发出的请求没被发出，导致延迟统计偏乐观 |
| 帕累托前沿 | 吞吐与延迟平面上所有不可被同时改进的配置连成的边界 |
