# 5 微秒的发射税：CUDA Graph 与 shape 分桶如何决定 decode 的尾部

> 视频来源：[The GPU Isn't Slow, It's Waiting: How CUDA Graphs Fix LLM Decode Latency](https://www.youtube.com/watch?v=A8CRIEBzja8)（YouTube）｜时长约 14 分 18 秒
> 简要导读：一支把「内核发射开销」讲到指令级的视频。它先算出小 batch decode 里 **80% 的时间在交「发射税」**，再讲 CUDA Graph 如何把 30 次发射压成 1 次，最后落到生产现场：**shape 分桶、未命中桶就掉回 eager、graph pool 吃掉 KV Cache**——这三件事正是 LLM 服务里「同一份代码、不同请求延迟差一个数量级」的直接来源。本文按这条线展开，并在末尾把本小节三篇博客覆盖的**六类抖动来源**汇总成一张对照表。TTFT / TPOT 的定义见 2.1.1、2.1.2，batch 与 Tensor Core 利用率的关系见 2.3.1，本文不重复。

## 本讲要解决的核心问题（SCQA）

**背景**：一块现代 GPU 执行一条指令不到一纳秒。按直觉，decode 阶段每步只算一个 token，应该快到几乎无感。

**冲突**：实际情况是，在小 batch 的推理循环里，**硅片等待的时间比计算的时间还长**，而罪魁祸首根本不在这块芯片上——它在**发射（launch）**上。更反直觉的是：**你把 GPU 上的 kernel 优化得越快，这个失衡就越严重**，因为每一次 GPU 侧的优化都在拉大 CPU 需要填补的缝隙。

**疑问**：一次 kernel 发射到底贵在哪里、贵多少？如果贵在「次数」而不是「内容」，能不能把很多次发射合并成一次？合并的代价是什么，这个代价在生产里会以什么形式变成延迟抖动？

**回答（中心思想）**：**小 batch decode 是「发射受限」而不是「算力受限」**。一次 kernel 发射要走六个跳、花 5–10 微秒，而这六个跳几乎全是主机侧的串行工作。CUDA Graph 把整段固定的工作捕获成一张可重放的图，一次发射驱动全部节点，于是单步延迟减半、在发射主导的场景里能降一个数量级。但图的代价是**冻结**：shape 不能变、指针不能变。生产系统用**shape 分桶**来满足这个契约，而**桶没覆盖到的请求会掉回 eager 路径**——那一刻的延迟跳变，就是尾部尖刺的来源。

![一次 kernel 发射的解剖：cudaLaunchKernel → driver ioctl → doorbell write → PCIe Express → 前端取指 → block dispatch，六个跳合计约 8 微秒，而且几乎全在主机侧串行](assets/5%20微秒的发射税：CUDA%20Graph%20与%20shape%20分桶如何决定%20decode%20的尾部/00060.webp)

## 一、发射税：一个 kernel 从源码到硅片要走六个跳

### 1.1 六个跳，5–10 微秒，几乎全在主机侧

视频把一次 kernel 发射拆成六段，每段都标了实测耗时：

| 跳 | 做什么 | 耗时 |
| :--- | :--- | ---: |
| `cudaLaunchKernel` | 运行时校验：stream 句柄、维度、参数打包 | 1.2 μs |
| driver `ioctl` | 加 stream 锁、在环形缓冲里占位 | 1.6 μs |
| doorbell write | 写一个 MMIO 寄存器，告诉图形引擎「有新活」 | 0.8 μs |
| PCIe Express | 命令包 DMA 过总线 | 1.4 μs |
| 前端取指 | GPC 命令解析器读包 | 1.5 μs |
| block dispatch | 调度器仲裁，然后线程块才真正醒来 | 1.5 μs |

合计约 **8 微秒**，视频的标注是「5–10 微秒，**几乎全部是主机侧的串行工作**」。这句话是后面所有结论的根：**这 8 微秒里 GPU 一点活都没干**。

视频用的比喻很准：**厨房做一道菜只要 5 微秒，但服务员传菜要 8 微秒**——机器被一个比厨房还慢的服务员一道一道地喂。

### 1.2 发射受限：GPU 饿死在两次发射之间

把这 8 微秒画到时间轴上，病理就出现了：

![发射受限的形态：主机侧一个接一个地发 launch（红色），GPU 侧每个 kernel 只要 5 微秒就跑完（蓝色），中间那些斜纹区是「饿着等发射」](assets/5%20微秒的发射税：CUDA%20Graph%20与%20shape%20分桶如何决定%20decode%20的尾部/00090.webp)

主机侧一个接一个地发 kernel，每个要花几微秒的驱动时间；GPU 侧每个 kernel 跑得比发射还快，于是**在两次到达之间就干涸了**。视频把这个状态叫 **launch-bound regime（发射受限区）**：设备利用率条直接塌到地板，而主机烧掉一整个核在派活。

注意视频那句加粗的因果：**你的 kernel 越快，这个失衡越严重**。因为你在 GPU 上省下的每一个微秒，都变成了 CPU 需要填补的缝隙。这是一种「把自己优化进角落」的典型形态——加速器被主板上的那条细管子限住了。

### 1.3 算一笔账：30 个 kernel，80% 的税

视频给了一个具体的 decode 步算术。一个紧凑的 transformer 层要发：MatMul、LayerNorm、Softmax、ElementWiseAdd……**大约 30 个 kernel**。按 8 微秒一次发射：

$$
T_{\text{step}} \approx \underbrace{30 \times 8\,\mu s}_{\text{发射税 } 240\,\mu s} + \underbrace{60\,\mu s}_{\text{真实计算}}
= 300\,\mu s
$$

![decode 步算术：30 个 kernel × 8 微秒 = 240 微秒发射税，真实计算只有 60 微秒，墙钟时间是 300 微秒，税率 80%](assets/5%20微秒的发射税：CUDA%20Graph%20与%20shape%20分桶如何决定%20decode%20的尾部/00120.webp)

**80% 的税**。视频的判词是：**吞吐不是被数据手册上的算力上限卡住的，而是被驱动接受订单的速度卡住的**。

> 补充：注意这个税率与 batch 大小的关系。计算量随 batch 增长，而发射税几乎不变——所以 batch 越大，税率越低。这解释了为什么「大 batch」在小 batch 场景里能带来巨大的相对收益，也解释了为什么**小 batch 的交互式服务才是发射税的重灾区**。batch 与 Tensor Core 利用率的关系见 2.3.1。

### 1.4 为什么这是「尾部」问题而不是「平均值」问题

单看上面这笔账，它像是均匀地让所有请求都慢 240 微秒。但它在尾部上的作用要尖锐得多，原因有三层：

1. **只有小 batch 才暴露**。大 batch 时 kernel 跑得久，发射被自然掩盖；小 batch 时每一微秒的发射都裸露在关键路径上。
2. **decode 的步数会把它乘起来**。一条输出 500 个 token 的请求，要付 500 次这样的税。**输出越长，累计的发射税越大**——而输出长度本身就是重尾分布的。
3. **一旦 shape 落在「没被优化过的路径」上，税率会突然跳一个档**。这一层是本文第三节的主题，也是真正的尾部来源。

## 二、CUDA Graph：把 30 次发射压成 1 次

### 2.1 机制：捕获一次，重放无数次

修法的思路借自操作系统：**不要为每次调用付一次开销，而是把它摊销到一个可重放的对象上**。

具体做法是**捕获（capture）**：让 stream 进入录制模式，此时所有 kernel 调用与内存操作**不执行、只记录**，每一次调用变成一个节点（node），你在代码里写的先后顺序变成边（edge）。结束捕获后，整张图被编译成设备常驻形式并上传到卡上。从此**发射整张图只是一次 doorbell 写入**，由它引爆整条依赖链。

视频强调了这一步带来的一个额外好处：因为调度是**提前声明**的，硬件不必再强加单一队列顺序，**互相独立的分支可以并发执行**——softmax 和残差加法可以重叠，调度器在输入就绪的瞬间就派发对应的 wavefront。**设备不再按「线」思考，而开始按「电路」思考**，原本被串行化结构性隐藏掉的延迟，直接从关键路径上消失了。

### 2.2 代价：世界被冻结了

视频说得很直白：**图的代价是一个冻结的世界**。

- **指针被烤进参数里**，所以每个张量在每次重放时都必须待在**同一个地址**。
- **shape 必须完全一致**——这正是推理服务器要把请求**按固定序列长度分桶**的原因。
- **捕获区内不能出现任何「每次工作都不一样」的操作**：读时钟、打印调试、resize 张量，都会让图无法表达。

视频把违约的失败模式称为「**最仁慈的失败模式**」：每一次违约都是**捕获期错误**，你在启动时就知道了，而不是在线上跑了一周才发现。

### 2.3 收益：单步减半，发射主导时一个数量级

视频给的数字是：**小 batch decode 上，开启图通常把单步延迟砍半；在发射主导的区间能降一个数量级**。

- **TTFT 下降**，因为引擎不再为每一层付派发开销。
- **TPOT 下降**，因为内核之间的空隙塌缩成一次提交。

但视频紧接着给了一条诚实的边界：**这些数字只在 kernel 很短的地方出现**，也就是交互式服务所在的位置；**在大 batch 处会衰减**，因为 kernel 跑得足够久，发射被自然掩盖了。

> 补充：这条边界很重要。它意味着「开 CUDA Graph」不是一个无条件正确的开关，而是一个**只在延迟敏感的左侧有效**的技术。如果你的服务是大 batch 离线批处理，收益会小得多。

## 三、shape 分桶：把「抖动」变成「容量规划」

### 3.1 prefill 保持 eager，decode 走图

视频指出，生产引擎的做法是**分开对待两个阶段**：

![引擎像一台「图播放器」：prefill 保持 eager（prompt 长度变化太大），decode 走捕获好的桶；右侧是启动时为 batch = 1/2/4/8/16/32 各捕获一张图](assets/5%20微秒的发射税：CUDA%20Graph%20与%20shape%20分桶如何决定%20decode%20的尾部/00480.webp)

- **prefill 保持 eager**：prompt 长度差异太大，捕获不过来。
- **decode 走图**：每一步的计算完全相同、重复几千次、batch 维度在一个请求的生命周期内是钉住的——**这是发射受限场景的完美代表**。

于是引擎变成一台「图播放器」，偶尔加载一卷新胶片。

### 3.2 桶表就是一张直方图，桶数就是一笔显存

分桶是「理论向内存妥协」的地方。视频讲得很清楚：

- 每张捕获好的图会**钉住一组设备缓冲区**，所以支持 32 个 batch size 的服务器，等于在 HBM 里持有 **32 个冻结的世界**。
- 引擎会把小请求**垫（pad）到最近的桶**，因此有一点浪费。
- 引擎会**精确地限制图的数量**，因为捕获本身很贵：每张图都要跑一遍模型、分配池、实例化设备镜像。

视频给了一个具体的账：观测到的流量按 batch size 分布是 b1 4%、b2 9%、b4 22%、b8 22%、b16 21%、b32 9%，每个桶的池子从 0.4 GB 到 3.9 GB。**工程旋钮就是这张直方图与「每桶多少 GB」之间的乘积。**

![分桶就是容量规划：左侧是观测到的 batch size 直方图与每桶的显存占用；右侧写着「把请求垫到最近的桶、限制图的数量、流量变了就要付捕获成本」](assets/5%20微秒的发射税：CUDA%20Graph%20与%20shape%20分桶如何决定%20decode%20的尾部/00510.webp)

### 3.3 未命中桶 = 掉回 eager = 尾部尖刺

这是本文最想强调的一句，也是视频里对「尾部」最直接的贡献：

> **把分布搞错了，你要么在几十张图之间把显存打碎，要么在流量尖峰的瞬间掉回慢速的 eager 回退路径。**

把这句话拆开看：

- **「流量尖峰的瞬间」**：突发流量进来时，同时在跑的请求数会冲到平时不常见的值。如果那个值**没有对应的桶**，引擎只能走 eager。
- **「慢速的 eager 回退」**：eager 路径意味着每一个 kernel 都要单独发射——也就是回到 80% 税的状态。**同一条请求，延迟可能差一倍甚至一个数量级，只因为它落在了桶与桶之间的缝里。**

于是「抖动」有了一个非常具体的机制：**它不是随机的，它是「shape 落在桶外」这个离散事件**。这和 2.2.3 另一篇里讲的「长 prompt 恰好排在你前面」是同一类东西——**尾部不是平均地慢，而是被少数特定事件打出来的**。

> 补充：这也解释了为什么「按 batch size 分桶」在 LLM 服务里还要叠加「按序列长度分桶」。decode 的 shape 由 batch 维度和序列长度共同决定；如果只按 batch 分桶而序列长度仍在变，桶命中率会随输出长度漂移，越到生成后期越容易掉出桶外。

### 3.4 图的另一笔账：它吃掉的是 KV Cache

视频把这一节叫「以 GB 计的图税」：

![显存账本：权重与激活 41.2 GB、图池（每桶）9.2 GB、你真正想要的 KV Cache 21.6 GB；图池被永久占用且不能与通用分配器共享](assets/5%20微秒的发射税：CUDA%20Graph%20与%20shape%20分桶如何决定%20decode%20的尾部/00690.webp)

- 每张捕获的图**钉住自己的内存池**，这些池**不与通用分配器的 arena 共享**，于是它占用的 GB 会在进程的整个生命周期里被永久占用。
- 在**小模型**上这是舍入误差；在**层数很深的大模型**上，图池会吃掉「你本来想最大化的那块 KV Cache」，于是**服务器开始拒绝它本可以服务的请求**。

这句话把两件事连起来了：**图的显存开销 → KV Cache 变小 → 并发上限下降 → 抢占与拒绝变多 → 尾部变差**。也就是说，一个为了降延迟而引入的优化，如果显存预算算错，会从另一条路径把尾部推回去。

> 补充：这条因果链的另一半（KV Cache 逼近上限时触发抢占、重算或换出）在 2.2.3 的另一篇里展开，本文只保留「图池挤占 KV Cache」这一环。

## 四、动态值怎么办：用间接，把「变」挡在冻结之外

KV Cache 是这套设计里最硬的约束：**它每一步都长一个位置，而图不允许新的分配**。

视频给的解法是一个小而漂亮的模式：**引擎预先分配好分页的块池，捕获的图里参数指向「块表」，内核在重放时通过块表解引用**。于是：

- **图保持冻结**（指针不变）。
- **块表的内容原地修改**（映射变了）。
- **地址从没动过，动的是映射。**

![把地址烤进去、让数据变：图的内核参数里 `table_ptr` 在捕获时冻结，块表的内容每一步原地重写，真正的数据块通过块表被间接寻址](assets/5%20微秒的发射税：CUDA%20Graph%20与%20shape%20分桶如何决定%20decode%20的尾部/00630.webp)

视频把这条提炼成一句通用规则：**对静态图里的每一个动态值，都取它的地址、而不是它的数据，让间接层承载变化**。然后说了一句很妙的话：一旦你看懂了这一点，你会在虚拟内存、文件系统、以及每一个「活过了真实系统接触」的冻结结构里看到同一个模式。

### 4.1 违约清单：图说「不」的时候，它其实在告诉你架构错了

视频列了一份捕获期会直接报错的清单，并给每一类配了一句诊断：

![图说「不」：区域内 synchronize、捕获中途懒初始化句柄、热路径上 resize 张量、按设备侧采样值分支——每一类违约都是同一句话：你的程序里有一个图无法表达的事实](assets/5%20微秒的发射税：CUDA%20Graph%20与%20shape%20分桶如何决定%20decode%20的尾部/00780.webp)

| 违约 | 为什么不行 |
| :--- | :--- |
| 区域内 `cudaStreamSynchronize` | 强制了一个图无法表达的次序 |
| 捕获中途懒初始化句柄 | 实际做的工作与录制时不同 |
| 热路径上 `tensor.resize_` | 地址移动，烤进去的指针失效 |
| 按设备侧采样值做分支 | 图没有「选择」这个词汇 |

视频对此的态度很明确：**专业的回应永远不是删掉这个约束，而是把动态决策抬到捕获边界之上，边界之下只留下「每一步都可证明完全相同」的工作**。而且它补了一句关键的判断：**大部分性能是在这次分诊（triage）里挣到的，不是在捕获本身**。

## 五、把这条因果链接回尾部：一份可操作的清单

视频最后给了它的判词：**CUDA Graph 不是一个可以随便撒上去的加速器，它是动态软件与硅片之间的一份契约**。把它落成 LLM 服务的操作清单：

1. **先确认你是不是发射受限。** 判据是「小 batch + 短 kernel + 每步几十次发射」。如果你的服务是大 batch 离线批处理，收益会明显衰减。
2. **只把 decode 放进图，prefill 留在 eager。** prompt 长度差异太大，硬捕获只会让桶命中率崩掉。
3. **分桶要按真实的 batch / 序列长度直方图来定，而不是按「可能的取值范围」。** 桶表就是容量规划文档。
4. **一定要留 eager 回退，并且监控它的触发频率。** 回退本身不是问题，**回退频率在突发时飙升**才是问题——那正是尾部尖刺。
5. **把图池计入显存预算。** 它挤占的是 KV Cache，而 KV Cache 变小会从「抢占变多」这条路径把尾部推回去。
6. **用间接层承载动态值。** 块表、句柄表、索引表——把「变」放在冻结之外。

### 5.1 本小节覆盖的六类抖动来源与对应治理

把三篇博客合起来看，本小节要回答的问题可以收成一张表。**同一类抖动，治理手段完全不同**——这也是为什么「买更大的 GPU」几乎从来不是答案。

| 抖动来源 | 机制 | 主要治理手段 | 详见 |
| :--- | :--- | :--- | :--- |

## 小结

- **小 batch decode 是发射受限，不是算力受限。** 一次 kernel 发射要走六个跳、花 5–10 微秒，且几乎全在主机侧串行。
- **30 个 kernel 的 decode 步，80% 的时间在交发射税。** 计算 60 微秒，发射 240 微秒，墙钟 300 微秒。
- **GPU 越快，失衡越严重。** 你在设备侧省下的每一微秒，都变成主机侧要填补的缝隙。
- **CUDA Graph 把 30 次发射压成 1 次**，代价是冻结：shape 不能变、指针不能变、动态决策必须抬到捕获边界之上。
- **收益只出现在 kernel 很短的地方**：小 batch 单步减半，发射主导时一个数量级，大 batch 处衰减。
- **shape 分桶是容量规划，不是配置项。** 桶表由真实流量直方图与每桶显存共同决定。
- **未命中桶就掉回 eager**——这是「同一条请求延迟差一倍」的直接机制，也是离散的尾部尖刺。
- **图池吃掉 KV Cache**，会从「并发上限下降 → 抢占变多」这条路径把尾部推回去。
- **六类抖动来源，六套不同的治理手段。** 先诊断是哪一类，再动手。

## 关键术语速查

| 术语 | 一句话解释 |
| :--- | :--- |
| 发射税（launch tax） | 每次 kernel 发射固定要付的主机侧开销，约 5–10 微秒 |
| 发射受限（launch-bound） | GPU 算得比 CPU 派活快，设备在两次发射之间空转 |
| CUDA Graph | 把一段固定的 kernel 序列捕获成一张可一次发射、多次重放的图 |
| 捕获（capture） | 让 stream 进入录制模式，只记录不执行，生成图的节点与边 |
| 重放（replay） | 一次发射驱动整张图，按预先声明的依赖执行 |
| 冻结契约 | 图要求 shape 与指针在每次重放时完全一致 |
| shape 分桶（bucketing） | 把请求垫到最近的固定 shape，使它能命中某张已捕获的图 |
| eager 回退 | 未命中桶时退回逐 kernel 发射的普通执行路径，延迟显著变高 |
| 图池（graph pool） | 每张图钉住、不可与通用分配器共享的显存区域 |
| 间接层（indirection） | 图里存指针、指针指向可原地修改的表，以此承载动态变化 |
