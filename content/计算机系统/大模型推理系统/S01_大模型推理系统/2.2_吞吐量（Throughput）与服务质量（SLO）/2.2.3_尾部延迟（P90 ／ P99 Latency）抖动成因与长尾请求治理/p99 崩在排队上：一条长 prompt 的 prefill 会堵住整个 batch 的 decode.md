# p99 崩在排队上：一条长 prompt 的 prefill 会堵住整个 batch 的 decode

> 视频来源：[Why Your vLLM p99 Latency Falls Apart in Production (and How to Fix It)](https://www.youtube.com/watch?v=kV2xZ0ceMfg)（YouTube）｜时长约 8 分 45 秒
> 简要导读：一支用「超市结账通道」一以贯之的短片。它把生产环境 p99 比压测差五到十倍的锅，从硬件身上挪到了**排队管理**上：长 prompt 的 prefill 一次性整块跑完，同 batch 里正在 decode 的请求全部冻结；连续批处理修好了吞吐，却没修掉这个堵塞。本文按它的叙事顺序展开——队头阻塞的机制、分块预填充的修法与代价、调度策略与抢占如何决定尾部、压测为什么在撒谎，最后落到一张「先判断堵在哪、再按顺序动旋钮」的清单。视频末段约一分钟是厂商推荐，本文略过。TTFT / TPOT / 端到端延迟的度量口径见 2.1.1–2.1.3，QPS 与 Goodput 的定义见 2.2.1、2.2.2，本文只用它们的结论。

## 本讲要解决的核心问题（SCQA）

**背景**：同一套模型、同一批 GPU、同一份代码，压测里 p99 看起来很健康。上线之后，p99 变成压测时的五到十倍。

**冲突**：第一反应是「硬件不够，加卡」。但同一份代码在压测里能跑出好数字，说明算力本身是够的——出问题的不是机器能算多快，而是**机器决定先算谁**。平均值这时还稳稳地待在原地，把这件事藏得严严实实。

**疑问**：一条长 prompt 到底是怎么拖慢其他所有人的？为什么连续批处理这种「业界标配」没能解决它？该动哪个旋钮，代价是什么？

**回答（中心思想）**：**LLM 服务的尾部延迟是一个排队管理问题，不是硬件问题**。根因是 prefill 与 decode 这两种尺寸悬殊的工作被塞进同一条队列：一辆装了 200 件商品的购物车进了快速通道，后面所有只买一盒牛奶的人就都停住了。修法有三层——把长 prefill 切片（chunked prefill）、选对调度策略（谁先上）、控制抢占（谁会被拉出队伍）；而验证修法是否有效，必须用**突发**流量而不是均匀流量去压。

![同一条通道上的两辆车：你只有 1 件商品，前面那辆有 200 件，于是你身后所有人都停住了](assets/p99%20崩在排队上：一条长%20prompt%20的%20prefill%20会堵住整个%20batch%20的%20decode/00035.webp)

## 一、一条长 prompt 进 batch，同批所有人的 token 间隔会被推高 28 倍

### 1.1 平均值是一个真实的数字，但对站在购物车后面的你毫无用处

视频开场是一个超市快速通道的场景：你手里只有一盒牛奶，前面那位推着 200 件商品过来，于是你、以及你身后所有人，全部停住。

这时候你去问超市「平均结账时间是多少」，他们会说 90 秒。**这是一个真实的数字，对你毫无用处**——因为你正站在这辆购物车后面，你实际等的时间远不止 90 秒。平均值把「买牛奶的人」和「推 200 件车的人」混在一起平均掉了，而排队体验是由**你前面那个人**决定的，不是由平均值决定的。

推理服务器的工作方式和这条通道一模一样。同一个模型、同样的 GPU、同一份在压测里表现良好的代码，真实流量一来，p99 就崩了。视频对此的判断很干脆：**你的测试没有错，它只是太干净了**。

> 补充：为什么平均值天然看不见尾部，可以用一个极简模型说明。假设 99% 的请求耗时 $t_{\text{fast}}$、1% 的请求耗时 $t_{\text{slow}}$，那么

$$
\bar{t} = 0.99\,t_{\text{fast}} + 0.01\,t_{\text{slow}}
$$

> 只要 $t_{\text{slow}}$ 是 $t_{\text{fast}}$ 的 50 倍，均值也只被抬高约 49%；但 P99 会**直接落在** $t_{\text{slow}}$ 上。均值对尾部是「稀释」，分位数对尾部是「放大」——这就是为什么优化均值经常和改善体验无关。

### 1.2 工作只有两种尺寸：decode 是买牛奶的，prefill 是那辆购物车

在 LLM 服务器里，工作只有两种截然不同的大小：

- **decode**：生成一个 token。它对应那位只买一盒牛奶的顾客——又快又轻，一步只算一个 token。
- **prefill**：在能回答之前，先把整段 prompt 读进去。它对应那辆堆满的购物车——**一次性整块处理**。

关键在于「一次性整块处理」。视频把 prefill 画成一根橙色的长条，后面跟着一串灰点（正在 decode 的请求）：长条在跑的时候，灰点全部不动。

![prefill 是「one big go」：一整块跑完，期间其他请求的 decode 步全部让路](assets/p99%20崩在排队上：一条长%20prompt%20的%20prefill%20会堵住整个%20batch%20的%20decode/00075.webp)

具体到请求序列上：请求一、二、三正在向各自的用户流式输出 token，请求四带着一条长 prompt 到达，它的 prefill 作为一整块运行，**另外三个就冻结了**。它们什么都没做错，只是被堵在那辆购物车后面。

### 1.3 28 倍：一个 prefill 就能把 token 间隔推上去

这不是舍入误差。视频引用了 Sarathi-Serve 研究者的测量：**一个 prefill 与 decode 共享同一个 batch，可以把 token 间隔（time-between-tokens）推高到纯 decode batch 的 28 倍**。

[【跳转到 01:15】](https://www.youtube.com/watch?v=kV2xZ0ceMfg&t=75)

这 28 倍落在哪里，取决于你怎么看：

- 落在**平均值**上，它只是让平均值难看一点点——因为被拖慢的请求只占那一小段时间里的一小部分。
- 落在**尾部**上，它就是灾难——因为「被拖慢」这件事不是随机的，它精确地发生在「长 prompt 恰好排在你前面」的那些请求身上。

这就是视频那句总结的由来：**你的平均值看起来很健康，而某个倒霉用户却眼看着响应卡住**。在 2.1.2 里我们已经知道 TPOT 决定阅读流畅度；这里要补上的是，TPOT 的 P99 往往不是被模型算得慢拖垮的，而是被别人的 prefill 拖垮的。

## 二、连续批处理修好了吞吐，却没修掉这条通道的堵塞

### 2.1 静态批处理：整条通道等所有人结完账

老办法是**静态批处理（static batching）**：一批请求凑齐后一起跑，一直跑到**队里每个人都生成完**，才放新的一批进来。

后果是木桶效应——批里最短的那个请求明明早就答完了，它的槽位却要空等到最长那个结束。这是吞吐上的巨大浪费，也是第 3 章要展开的话题。

![静态批处理：整条通道被圈在一起，队里所有人都结完账才放新的人进来](assets/p99%20崩在排队上：一条长%20prompt%20的%20prefill%20会堵住整个%20batch%20的%20decode/00115.webp)

### 2.2 连续批处理：人走一个，就招一个进来

**连续批处理（continuous batching）**修掉了这一点：顾客一结完账就离开，等待中的顾客立刻被招手进来。批不再是静态的一批，而是每一步都在换人。

这是一大进步，而且视频特意强调：**只要你跑的是 vLLM，你已经有它了**。所以它不是本文要讨论的解法。

### 2.3 但「把人更快地招进招出」，对那辆购物车毫无作用

视频在这里做了一个很关键的转折：连续批处理优化的是**换人的速度**，它没有改变**每个人手里有多少件商品**。

购物车仍然会落进某条通道，那条通道仍然会堵——因为连续批处理仍然倾向于把整车东西**一口气不间断地结完**。换句话说：

> 我们只是把堵塞点周围的其他部分变快了，堵塞本身还在。

这句话解释了为什么很多团队「已经上了 vLLM、已经开了连续批处理」，p99 依然难看。吞吐优化的默认方向是「让机器更忙」，而尾部延迟要的是「别让任何一个人等太久」——这两个目标在队头阻塞这件事上是冲突的。

## 三、分块预填充：把长 prompt 切片，与 decode 交错执行

### 3.1 机制：扫一小把，停下来给牛奶结账

修法的思路来自收银员的行为改变：**不要先把 200 件商品全扫完再去帮别人**，而是扫一小把、停下来给那盒牛奶结账、再扫几件、给下一位快顾客结账，交替进行。

![分块预填充的交错执行：橙色的 scan（prefill 分块）与蓝色的 ring up（decode 步）交替进行](assets/p99%20崩在排队上：一条长%20prompt%20的%20prefill%20会堵住整个%20batch%20的%20decode/00155.webp)

映射回推理系统，这就是**分块预填充（chunked prefill）**：把长 prompt 切成若干块，每一轮只处理一块，与已经在跑的 decode 步**并排**放进同一个 batch。

效果是：购物车照样会被结完，但**后面没有人需要永远等下去**，所有人的流式输出都保持平滑。这里要区分两个受害者：

| 谁 | 不加分块预填充 | 加了分块预填充 |
| :--- | :--- | :--- |
| 长 prompt 自己（TTFT） | 一次跑完，首字最快 | 被切成多轮，首字变慢 |
| 同 batch 的其他请求（TPOT） | 被整块 prefill 冻结，出现尖刺 | 每轮只让出一小块时间，尖刺被削平 |

### 3.2 收益：同样延迟目标下多吸收 2.6 倍到 6.9 倍流量

视频给了 Sarathi-Serve 的两个数字：在**同样的延迟目标**下，这样处理 prefill 让服务器多吸收最多 **2.6 倍**的流量（较小的模型），在**更大的模型**上最多 **6.9 倍**，硬件不变。

[【跳转到 02:55】](https://www.youtube.com/watch?v=kV2xZ0ceMfg&t=175)

这两个数字要连着「同样的延迟目标」一起读，否则会误读成「吞吐凭空涨了 6.9 倍」。它真正的含义是：**在 p99 这条约束线不动的前提下，你能塞进更多的请求**——这正好是 2.2.2 里 Goodput 的定义：满足 SLO 前提下的有效吞吐。分块预填充抬高的不是裸吞吐，是 Goodput。

### 3.3 代价：max_num_batched_tokens 是一个诚实的权衡

这里只有一个旋钮最关键，视频说它「有一个诚实的权衡」：**在停下来服务快顾客之前，你一次扫多少件商品**。

在 vLLM 里这个旋钮是 `max_num_batched_tokens`（每一步最多处理多少个 token，prefill 的分块大小与 decode 的 token 数都算在里面）。

- **扫得太少**（值小）：买牛奶的顾客很开心，TPOT 很稳；但购物车要结很久，**长 prompt 那位顾客的 TTFT 一路往上爬**。
- **扫得太多**（值大）：长 prompt 很快读完，但**你又回到了让所有人一起等**——分块退化成整块。

视频提到研究者在各自环境里调这个值，**512 和 2048 是可以起步的参考点**，但一定要拿自己的流量去测。这里没有普适最优值，因为最优值取决于你的输入长度分布和 SLO 的松紧。

> 补充：这也解释了为什么「分块预填充」不是免费的午餐。它把尾部尖刺从 TPOT 上搬到了 TTFT 上——总有人要多等一会儿，你只是在选择**让谁等、等多久**。这和第 3 章讨论的调度博弈是同一件事的两个视角。

### 3.4 破一个迷思：PagedAttention 不修延迟

视频特意停下来纠正一个流传很广的说法：「PagedAttention 修好了延迟」。

**它没有。** PagedAttention 管的是**内存**——重整仓库和打包区，让你能一次容纳更多顾客的东西而不溢出来。这确实有帮助，但是**间接的**：因为你能同时容纳更多顾客，收银员就不必被迫把通道压得很小，于是在「如何交错服务」上有了更多自由度。

但 PagedAttention **不决定谁先上**。视频的比喻很准：**它只是把舞台搭好**；真正管理队伍的是分块预填充和你的调度策略。块表机制本身在第 4 章展开，本文不重复。

## 四、谁先上：调度策略直接决定尾部形状

舞台搭好之后，下一个问题是「谁先上」。视频给了三种策略，并用超市的语言各自命名：

![三种调度策略：FCFS 是一条大公平队列，priority 是快速通道，SLA-aware 是盯着等待目标的巡场经理](assets/p99%20崩在排队上：一条长%20prompt%20的%20prefill%20会堵住整个%20batch%20的%20decode/00265.webp)

| 策略 | 超市里的对应物 | 行为 | 什么时候会崩 |
| :--- | :--- | :--- | :--- |
| FCFS（默认） | 一条大的公平队列 | 严格按到达顺序放人 | 一群巨型购物车同时到达时，所有人的等待一起爆掉 |
| Priority | 快速通道 | 某些请求可以插到前面 | 低优先级请求可能被长期饿死 |
| SLA-aware | 在现场巡场、盯着等待时间目标的大堂经理 | 不以「按顺序」为目标，以「命中等待时间目标」为目标 | 需要可信的剩余时间估计，估错就白调 |

视频对 FCFS 的评价是「没问题，**直到**一群巨型购物车同时到达」——注意这个「直到」。FCFS 在均匀流量下完全够用，它的失效条件是**突发**，而不是平均负载高。这也是为什么很多团队在压测里看不出问题：压测里没有「一群购物车同时到达」这种事。

## 五、抢占：罕见、痛苦，而 p99 恰恰只度量这种罕见

视频把「悄悄地主宰你尾部」的那部分单独拎出来讲：当收银台被压垮时，超市有时会把一个**结到一半的顾客**从队伍里拉出来，稍后再处理。

在 vLLM 里这就是**抢占（preemption）**。而要恢复这个被拉出去的请求，系统得做两件事之一：**重做它的工作**（recompute，把已生成的 token 连同 prompt 重新 prefill 一遍），或者**把它的数据挪出去再挪回来**（swap，KV Cache 换到 CPU 内存再换回显存）。

![抢占的三段式：请求在队伍里 → 被拉出去稍后处理 → 恢复时要么重做工作，要么把数据挪出去再挪回来](assets/p99%20崩在排队上：一条长%20prompt%20的%20prefill%20会堵住整个%20batch%20的%20decode/00285.webp)

视频对它的描述是精准的一句话：**它很罕见——但「罕见且痛苦」恰恰就是 p99 所度量的东西**。

这句话值得展开。假设抢占命中率是 2%：

- **平均值**：那 2% 的请求被拉长了几倍，摊到全体上几乎看不出来。平均那位顾客永远不会被拉出去。
- **P99**：P99 的定义就是「最慢的 1% 的起点」。如果 2% 的请求被抢占过，那么 **P99 几乎必然落在被抢占过的那批请求里**。

于是视频给出了这一节的结论：**控制 p99 的方式，就是控制谁会被拉出去、以及多久被拉一次**。在 vLLM 里对应的最直接手段是把 `max_num_seqs`（同时在跑的序列数上限）设成**你真实拥有的显存能撑住的量**——显存越紧，系统越倾向于把人拉出队伍。

> 补充：KV Cache 逼近上限时触发抢占、块分配失败、显存碎片，这三件事在成因上是一族的——都是「显存不够用了」。它们的机制细节属于第 4 章与 1.3 节的范围，本文只保留「显存压力 → 抢占 → 尾部尖刺」这条因果链。

## 六、压测在撒谎：它是早上六点的超市

### 6.1 均匀负载与真实流量的差别，不在平均值上

视频说那个「说一切都好」的压测撒谎了，因为它测的是**早上六点的超市**：顾客均匀到达、购物车大小都差不多、一次来一个。

**真实流量是周六下午**：人们成群地涌进来，购物车从一条口香糖到一个月的口粮都有。

两个独立研究给了证据：

![两份证据：ServeGen 发现真实请求到达的突发性让均匀测试模式完全失效；BurstGPT 在超过一千万条真实请求上看到同时在飞的请求数会突然堆积](assets/p99%20崩在排队上：一条长%20prompt%20的%20prefill%20会堵住整个%20batch%20的%20decode/00345.webp)

- **ServeGen**：真实请求的到达具有足够的突发性，**均匀的测试模式完全描述不了它们**。
- **BurstGPT**：在超过**一千万条**真实请求上看到同样的事——同时在飞的请求数会**突然堆积**。

而堆积正是购物车摞起来、堵住通道的时刻。注意这里的因果顺序：突发不直接让单次推理变慢，它让**排队变长**，进而让长 prefill 与短 decode 撞在一起的概率变大。

### 6.2 值得跑的测试：同一套配置，跑两遍，两个结果都看

视频给了一个非常便宜、但几乎没人做的实验：

![值得跑的测试：同一套配置，一边跑整齐均匀的负载，一边回放真实的突发模式，两个结果都看](assets/p99%20崩在排队上：一条长%20prompt%20的%20prefill%20会堵住整个%20batch%20的%20decode/00365.webp)

1. 拿一套固定配置。
2. 先在**整齐均匀**的负载下跑一遍。
3. 再把**真实的突发模式**回放到**完全相同**的配置上。
4. 两个结果都看。

预期结果是：**你的平均值几乎不动，你的 p99 跳起来**。

[【跳转到 06:05】](https://www.youtube.com/watch?v=kV2xZ0ceMfg&t=365)

视频把这两条线之间的差距称为「全部的关键」，并且指出它「恰恰是几乎所有压测都不屑于展示的部分」。这句话对写压测报告的人是一个直接的建议：**只报平均值的压测报告，等于没报**。这也呼应 2.2.1 里那句「吞吐必须连延迟分位数一起报」。

## 七、先判断堵在哪一种，再按顺序动旋钮

视频最后给了一张诊断表和一个动手顺序，这部分是全文最可直接照做的内容。

### 7.1 三种堵塞，对应三个不同的杠杆

| 你的流量长什么样 | 你堵在哪 | 该动的杠杆 |
| :--- | :--- | :--- |
| 长 prompt、短回答（RAG、大段 system prompt） | prefill 受限 | 分块预填充 |
| 回答很长 | decode 受限 | batch 大小与显存余量 |
| 平均值正常，但尾部在突发下崩掉 | 调度受限 | 调度策略与抢占 |

这张表的价值在于它**排除了错误方向**：如果你是 prefill 受限，去调 batch 大小是白费力气；如果你是调度受限，去买更大的 GPU 更是白费力气——因为你的瓶颈是「谁先上」，不是「算得多快」。

### 7.2 动手顺序

视频给的顺序是：

1. **有长 prompt 又有尾部问题 → 先打开分块预填充。**
2. **拿自己的流量分步调那个分块旋钮**（`max_num_batched_tokens`），一次只动一格。
3. **把最大序列数设成显存真能撑住的量**（`max_num_seqs`），这样请求被拉出队伍的次数就少。
4. **挑一个贴合你流量形态的调度策略**，而不是把默认值留着不管。

最后一条「一次只改一个旋钮」在工程上很重要：这几个参数互相影响，同时改三个，你无法归因是哪一个起了作用。

> 补充：视频末段约一分钟是托管服务的推荐（带前缀感知路由的 vLLM + OpenAI 兼容 API），其中与本文主题相关的只有一句——**前缀感知路由**会把带着相同 prompt 前缀的新请求送到「已经结了一半的那条通道」，从而把 prefill 的工作量直接省掉。这属于缓存与路由的话题，本文不展开，只把它记为「削峰」之外的另一种思路：不是把 prefill 切小，而是让它不必发生。

## 小结

- **p99 崩掉的原因通常不是硬件，是排队管理。** 同一份代码在压测里好、在生产里差五到十倍，说明算力够，是「先算谁」出了问题。
- **根因是两种尺寸悬殊的工作共用一条队列。** decode 是一盒牛奶，prefill 是 200 件商品的购物车；一个 prefill 进 batch，可以把同批的 token 间隔推高到 28 倍。
- **连续批处理修的是换人速度，不是购物车大小。** 它让吞吐变好，但队头阻塞原封不动。
- **分块预填充把长 prefill 切片，与 decode 交错执行。** 同样延迟目标下可多吸收 2.6–6.9 倍流量；代价是长 prompt 的 TTFT 变长，旋钮是 `max_num_batched_tokens`。
- **PagedAttention 不修延迟。** 它管内存，只是把舞台搭好；决定谁先上的是调度策略。
- **抢占罕见但痛苦，而 p99 只度量罕见。** 控制尾部就是控制「谁被拉出去、多久拉一次」，最直接的手段是让 `max_num_seqs` 匹配真实显存。
- **压测要跑两遍。** 均匀负载下平均值几乎不动、p99 跳起来，这两条线的差距才是要优化的对象。
- **先诊断再动手。** prefill 受限、decode 受限、调度受限对应三个完全不同的杠杆；一次只改一个旋钮。

## 关键术语速查

| 术语 | 一句话解释 |
| :--- | :--- |
| 尾部延迟（tail latency） | 分位数落在分布最右端的那部分请求的延迟，P99 指最慢的 1% |
| 队头阻塞（head-of-line blocking） | 队列前面一个大任务把后面所有小任务一起卡住 |
| prefill | 一次性把整段 prompt 读完、算出第一个 token 的阶段，计算量大且成块 |
| decode | 逐 token 自回归生成的阶段，每步只算一个 token，轻但步数多 |
| 静态批处理（static batching） | 一批请求凑齐一起跑，跑到全批结束才换人，短请求被迫空等 |
| 连续批处理（continuous batching） | 每步都能换人的批处理，请求一完成就腾出槽位 |
| 分块预填充（chunked prefill） | 把长 prompt 切成多块，每轮只跑一块，与 decode 步交错 |
| 抢占（preemption） | 显存或调度压力下把进行中的请求拉出队伍，之后重算或换出恢复 |
| FCFS | 先到先服务，默认调度策略，突发流量下等待时间会一起爆掉 |
| SLA 感知调度 | 以命中等待时间目标为优化对象，而不是按到达顺序放人 |
| BurstGPT | 基于超过一千万条真实请求的流量特征研究，说明到达是突发的 |
