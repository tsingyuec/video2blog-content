# batch 越过拐点之前单步时间不动，越过之后 TPOT 随 batch 线性变长

> 视频来源：[Exploring the Latency/Throughput & Cost Space for LLM Inference // Timothée Lacroix // CTO Mistral](https://www.youtube.com/watch?v=mYRqvB1_gRk)（YouTube · MLOps.community 访谈）｜时长约 30 分钟
> 简要导读：Mistral CTO 用一张「两条直线」的图，把「batch 变大 → 吞吐上升 / TPOT 变长」这件事变成了一道可以手算的题：一步 decode 的时间取「搬权重的固定时间」和「随 batch 线性增长的算力时间」中的较大者，两条线交点 $B^*$ 只由硬件的算力除以带宽决定。前半段讲这条曲线怎么来的，后半段用 vLLM 实测曲线收口。文中凡是访谈没讲、由我按它给的公式补算的地方，都标了「补充」。TTFT / TPOT 的测量口径见 2.1.1 与 2.1.2，QPS 与输出吞吐的定义见 2.2.1，本文不重复。

## 本讲要解决的核心问题（SCQA）

**背景**：decode 阶段每写一个 token，都要把整个模型权重从显存搬到计算单元一遍。单请求时，这块 GPU 的算力有 99% 以上在等数据（这条推导在 1.2.2 与 1.2.3 里已经做完）。

**冲突**：于是我们把多个请求拼成一批一起过网络。奇怪的是，**加 batch 的前一段几乎是白拿的**——batch 从 1 加到 8、加到 32，每个 token 的间隔几乎不变，吞吐却翻了几十倍；可再往上加，每加一点，用户就明显变慢。同一条曲线上出现了两种完全不同的行为。

**疑问**：这两种行为的分界点在哪？能不能算出来？为什么算出来的「理想 batch」常常大得根本装不下？工程上真正先撞到的又是哪一堵墙？

**回答（中心思想）**：**一步 decode 的时间只有两个来源——搬权重的时间（与 batch 无关）和做数学的时间（与 batch 成正比），实际耗时取两者较大值。两条线的交点 $B^*$ 只由「硬件算力 ÷ 显存带宽」决定，与模型大小无关。** $B^*$ 左边，单步时间是一条水平线，TPOT 不变、吞吐随 batch 线性上升，这是「免费区」；$B^*$ 右边，单步时间变成一条斜线，TPOT 随 batch 线性变长、吞吐趋平，这是「有代价区」。而真实系统里通常还没走到 $B^*$ 就被卡住：**长上下文时 KV Cache 的读取量会先超过权重，显存容量又会先把并发数按住。** 三个上限谁先撞，取决于上下文长度与模型大小，而不是取决于你多想把 batch 调大。

## 一、一步 decode 的时间只有两个来源

### 1.1 计算量随 batch 长，搬运量不长

讲者先把范围收窄：整场只讨论解码里「把 batch size 个 token 一起过一遍网络、算出下一批 token」这一段，不包括请求刚进来、可能有一大段 prompt 要一次性过网络的那一段（prefill）——那一段已经被优化得比较好，挑战没那么大。

![一步推理的两个量：计算量约等于 2 × 参数量 × batch size 次浮点运算，搬运量等于把整个模型搬一遍](assets/batch%20越过拐点之前单步时间不动、之后%20TPOT%20随%20batch%20线性变长/00318.webp)

[【跳转到 05:18】](https://www.youtube.com/watch?v=mYRqvB1_gRk&t=318)

对一个规模为 $P$ 的模型（讲者取 $P = 7\times10^9$，因为「我们喜欢这个尺寸」），做一步推理需要两样东西：

- **计算量**：约 $2 \times P \times B$ 次浮点运算，$B$ 是 batch size。每个权重参与一次乘、一次加，所以每个参数每个 token 两次运算。
- **搬运量**：把整个模型从显存搬进真正做运算的那部分芯片，也就是 $P$ 个参数要搬一遍。**这一步和 batch 无关**——多几个请求，权重还是那一份。

写成时间就是两个候选值：

$$
T_{\text{step}}(B) \approx \max\left(\underbrace{\frac{P}{\text{mem\_bandwidth}}}_{\text{搬权重的固定时间}},\ \underbrace{\frac{2PB}{\text{hardware\_flops}}}_{\text{做数学的时间}}\right)
$$

第一项是常数，第二项随 $B$ 线性增长。**真实耗时不会小于两者中较大的那个**——数据没搬完，算得再快也没用；数据搬完了算力不够，也只能排队算。

### 1.2 两条线相交的地方叫 $B^*$

把这两个量画在同一张「时间 - batch size」图上，就能一眼看出整件事的形状：

![两条线：水平的是「模型大小除以显存带宽」，也就是把权重搬一遍的最短时间；斜的是「2 × 参数量 × batch size 除以算力」，也就是做数学的时间](assets/batch%20越过拐点之前单步时间不动、之后%20TPOT%20随%20batch%20线性变长/00368.webp)

[【跳转到 06:08】](https://www.youtube.com/watch?v=mYRqvB1_gRk&t=368)

- **水平线**：$P / \text{mem\_bandwidth}$，把所有权重搬一遍所需的最短时间，每一步都要重付一次；
- **斜线**：$2 \times P \times B / \text{hardware\_flops}$，做这一步数学所需的时间；
- 两条线的交点，讲者记作 $B^*$。

![B* 的定义与两侧的行为：左边标着「浪费算力 / 延迟恒定 / 访存受限」，右边标着「延迟上升 / 计算受限」](assets/batch%20越过拐点之前单步时间不动、之后%20TPOT%20随%20batch%20线性变长/00393.webp)

[【跳转到 06:33】](https://www.youtube.com/watch?v=mYRqvB1_gRk&t=393)

讲者给的公式是：

$$
B^* = \frac{2 \times \text{hardware\_flops}}{\text{mem\_bandwidth}}
$$

他在幻灯片上写的结果是 **400，A10G 和 A100 都是 400**。这个数字的关键性质是：**它只取决于硬件，与模型大小无关**（除非你用的是 Transformer 之外的奇异架构）。

> **补充（一处容易算错的地方）**：如果严格按 fp16「每个参数占 2 字节」来算搬运量，常数项应该是 $2P/\text{BW}$ 而不是 $P/\text{BW}$，于是 $B^*$ 会退化成「算力 ÷ 带宽」——A100 的 FP16 算力约 312 TFLOPS、带宽约 2.04 TB/s，相除约 153，正好等于 1.2.3 里算出的那个屋脊点（ridge point）的算术强度。讲者把搬运量记成 $P$ 字节（而不是 $2P$），所以得到的是 2 倍的值。**两种算法只差一个常数因子 2，量级与结论完全一致**：$B^*$ 大致就是「屋脊点的算术强度」，几百这个量级。下面沿用讲者的 400。

### 1.3 $B^*$ 左边：延迟是常数，算力在浪费

这张图最有用的地方，是把 $B^*$ 两侧的行为写清楚了：

| 位置 | 谁在限制 | 单步时间 | 算力利用 | 用户体验 |
| --- | --- | --- | --- | --- |
| $B < B^*$ | 显存带宽 | 近似常数（水平线） | 大部分在空转 | 延迟恒定，最优 |
| $B = B^*$ | 两者同时到顶 | 最低的「不浪费」点 | 刚好喂饱 | 延迟仍是最优 |
| $B > B^*$ | 算力 | 随 $B$ 线性上升（斜线） | 已满，只能排队 | 延迟开始变差 |

讲者的原话是：**「在 $B^*$ 以下我们基本在浪费算力——计算是访存受限的，我们只是在等数据搬上 GPU，而计算单元跑得太快，所以延迟基本是常数。一旦超过 $B^*$，延迟就开始上升，因为变成计算受限了。」**

而 $B^*$ 恰好是那个「两头都对」的点：延迟最优、用户体验最优，同时又不浪费任何算力，**钱花得刚刚好**。

## 二、Tensor Core 利用率为什么随 batch 上升

讲者用「浪费算力」四个字概括了 $B < B^*$ 这一段，但没解释为什么多几行就能把算力填满。这一步 1.2.3 已经推完，这里只把结论接过来：

- 单请求 decode 是一次 **GEMV**（矩阵乘向量）：$M = 1$，权重矩阵的每一行只被一个数用一次，算术强度是 1；
- 把 $B$ 个请求拼成一批，就变成 **GEMM**：$M = B$，同一份权重被 $B$ 行同时用，算术强度约等于 $B$；
- 在硬件层面，矩阵乘被切成一个个 tile 交给 Tensor Core 的 MMA 指令。$M = 1$ 时 tile 的那一维只填了一行，**并行度只剩 $N$**；$M = B$ 时并行度变成 $B \times N$，tile 被填满，MMA 的流水线才真正跑起来。

所以「Tensor Core 利用率随 batch 上升」和「单步时间在 $B^*$ 左边不变」是同一件事的两种说法：**多出来的那些行没有多花搬运时间，却让原本空着的乘加单元有了活干。** 利用率随 $B$ 上升，到 $B^*$ 附近饱和——再往上加行，算力已经满了，只能让每一步变长。

## 三、吞吐与 TPOT：同一条曲线的两段

### 3.1 小 batch 区：吞吐随 batch 线性涨，TPOT 不动

吞吐的定义是「每秒产出多少 token」，而每个 token 要等一步：

$$
\text{吞吐} \approx \frac{B}{T_{\text{step}}(B)}
$$

在 $B < B^*$ 这一段，$T_{\text{step}}$ 是常数，所以**吞吐与 $B$ 成正比**。这就是那个「白拿」的区域：batch 翻倍，吞吐翻倍，而每个用户看到的两 token 间隔（TPOT）几乎不动。

讲者在这里给了一个很好记的用户体验标尺：**普通人的阅读速度大约是每分钟 250 词**，只要你的每 token 延迟低于这个速度，用户就不会觉得在等。

### 3.2 大 batch 区：吞吐趋平，TPOT 线性变长

越过 $B^*$ 之后，$T_{\text{step}} \propto B$，代进吞吐公式：

$$
\text{吞吐} \approx \frac{B}{c \cdot B} = \frac{1}{c} \quad (\text{常数})
$$

**吞吐不再涨了，而 TPOT 开始随 $B$ 线性变长。** 这一步的物理含义很直白：算力已经满了，多塞进来的请求只能排队等算，它们不增加每秒产出，只增加每个人的等待。

把两段接起来，就得到本节要的那条曲线：

```
吞吐
  ↑            ___________  ← 饱和：算力满了，加 batch 只加延迟
  │        __/
  │     __/                ← 线性区：T_step 是常数，吞吐 ∝ B
  │  __/
  └──────────────────────→ batch size
                    ↑
                    B*
```

## 四、三个上限：算力、KV 带宽、显存容量

讲者算完 $B^* = 400$ 之后说了一句很关键的话：**「但理想 batch size 是 400，这看起来相当大。」** 于是他开始算真实数字，而这一算，就撞出了另外两堵墙。

### 4.1 上限一：算力屋脊（$B^*$ 本身）

第一堵墙就是 $B^*$。它决定「最多能把多少行塞进一次权重搬运里而不变慢」。越过它，TPOT 就开始线性变长。

### 4.2 上限二：KV Cache 带宽——长上下文时它比权重还重

上面那个模型有个简化：它只算了「搬权重」。但每一步还要读 **KV Cache**——batch 里每条序列为它见过的每个 token 存下的 key 和 value。

![KV Cache 的大小公式：2（K 和 V 各一份）× 2（fp16）× 层数 × batch size × 序列长度 × 维度](assets/batch%20越过拐点之前单步时间不动、之后%20TPOT%20随%20batch%20线性变长/00493.webp)

[【跳转到 08:13】](https://www.youtube.com/watch?v=mYRqvB1_gRk&t=493)

讲者给的公式是：

$$
\text{KV bytes} = 2 \times 2 \times \text{layers} \times B \times \text{seq\_len} \times \text{dim}
$$

代入 Llama 7B（dim = 4096、layers = 32、fp16），**每个 token 的缓存约 0.5 MB**；在最长 4096 的上下文下，batch 里每个元素要占约 **2 GB** 显存。

> **补充（这一步讲者没展开，但很重要）**：KV Cache 不只是占显存，它**每一步都要被读一遍**。所以单步的搬运量其实是「权重 + 整批 KV」：
>
> $$
> \text{bytes}_{\text{step}} \approx \underbrace{2P}_{\text{权重}} + \underbrace{0.5\,\text{MB} \times \text{seq\_len} \times B}_{\text{KV}}
> $$
>
> 用讲者的数字：权重 14 GB，4K 上下文下每个请求的 KV 是 2 GB。**当 $B > 7$ 时，KV 的读取量就超过了权重。** 也就是说，在 4K 上下文下，「单步时间与 batch 无关」这个水平段只持续到 $B \approx 7$，之后单步时间就开始随 $B$ 线性上升——**这个上升是带宽造成的，不是算力造成的。**
>
> 两种「线性上升」的后果完全不同：算力造成的上升，吞吐会趋平（算力已经满了）；带宽造成的上升，吞吐同样趋平，但**天花板低得多**。按 A100 的 2.04 TB/s 算，算力天花板约 $312\text{ TFLOPS} / (2 \times 7\text{G}) \approx 22000$ token/s，而 4K 上下文下的 KV 带宽天花板只有 $2040\text{ GB/s} \div 2\text{ GB} \approx 1000$ token/s，差二十倍。**这就是为什么真实部署里你几乎总是「访存受限」，而不是「算力受限」。**

### 4.3 上限三：显存容量——KV 池装不下 $B$ 个请求

第三堵墙最简单：权重占掉一部分显存，剩下的才给 KV Cache 用。

![显存账：7B 模型 fp16 权重 14 GB，KV Cache 每个 batch 元素 2 GB（最长 4096 上下文），于是 A10G 24 GB 只能装约 5 个，A100 80 GB 只能装约 33 个](assets/batch%20越过拐点之前单步时间不动、之后%20TPOT%20随%20batch%20线性变长/00543.webp)

[【跳转到 09:03】](https://www.youtube.com/watch?v=mYRqvB1_gRk&t=543)

| 显卡 | 显存 | 权重 | 剩给 KV | 最大 batch（4K 上下文） |
| --- | --- | --- | --- | --- |
| A10G | 24 GB | 14 GB | 10 GB | 约 **5** |
| A100 | 80 GB | 14 GB | 66 GB | 约 **33** |
| 理想值 $B^*$ | — | — | — | **400** |

讲者的结论很直接：**「离 400 还差得远。所以几乎所有实际场景里，用 7B 模型做推理，解码都是彻底的显存带宽受限。」** 而这也解释了 Mistral 从第一天就在意的事：**模型和 KV Cache 占多少显存，直接决定允许的最大 batch size，而这个最大 batch size 才决定了效率高低。**

> 显存容量这堵墙的完整分析（分页、碎片、预留）归 2.3.2，这里只把它当作三个上限之一。

### 4.4 两个极端场景对照：谁先撞，取决于上下文长度与模型大小

把上面三个上限放在一起，就能回答「拐点到底在哪」这个问题——**它不是一个数，而是三个数里最小的那个**：

| 场景 | 权重 | 每个请求的 KV | KV 带宽超过权重的点 | 显存能装 | 算力拐点 $B^*$ | 实际先撞谁 |
| --- | --- | --- | --- | --- | --- | --- |
| 短上下文小模型（7B，512 token） | 14 GB | 约 0.25 GB | $B \approx 56$ | 约 264 个 | 300~400 | 先撞 KV 带宽，再撞显存容量 |
| 长上下文（7B，32K token） | 14 GB | 约 16 GB | $B \approx 1$ | 约 **4** 个 | 300~400 | 显存容量，几乎立刻 |

第二行是同一个模型、只把上下文拉长 8 倍的结果：**每个请求的 KV 从 2 GB 涨到 16 GB，一块 80 GB 的卡从装 33 个变成装 4 个。** 拐点从「几百」直接塌到「个位数」，而 $B^*$ 一动没动——因为 $B^*$ 只跟硬件有关。

这张表就是本节最该记住的一句话：**「拐点在哪」取决于你的上下文长度和模型大小，而不是取决于你多想把 batch 调大。** 上下文越长、模型越大，你离算力拐点就越远，越早被 KV 的读取量和显存容量按住。

### 5.1 固定硬件：一条从左上弯下来的曲线

![固定硬件下的吞吐 - 延迟曲线：随着吞吐提高，延迟上升；左下角那一段是延迟固定的访存受限区，往右进入浮点受限的线性区](assets/batch%20越过拐点之前单步时间不动、之后%20TPOT%20随%20batch%20线性变长/01209.webp)

[【跳转到 20:09】](https://www.youtube.com/watch?v=mYRqvB1_gRk&t=1209)

这条曲线和第三节那两条曲线是同一件事的两种画法：

- **左下角那一段几乎是竖直的**：吞吐在涨，延迟纹丝不动——对应 $B < B^*$ 的免费区；
- **往右拐过去之后变成斜的**：吞吐涨得越来越慢，延迟一路变长——对应 $B > B^*$ 的有代价区。

讲者把左下角叫「延迟固定区，也就是访存受限区」，把右边叫「浮点受限的线性区」。**曲线拐弯的那个点，就是 $B^*$。**

### 5.2 什么能把整条曲线往左上推

![换更好的硬件：整条曲线往左上平移，代价是每 GPU·小时的费用上升](assets/batch%20越过拐点之前单步时间不动、之后%20TPOT%20随%20batch%20线性变长/01201.webp)

[【跳转到 20:01】](https://www.youtube.com/watch?v=mYRqvB1_gRk&t=1201)

讲者把「让曲线变好」的手段分成两类，这两类的作用位置完全不同：

1. **换硬件**：整条曲线往左上平移，但每 GPU·小时的钱也涨。值不值得看你的具体情况。
2. **改代码或改模型**：**影响最大的地方在低吞吐、低延迟那一段，在大 batch 那边影响就小了，因为那里本来就容易优化。**

第二类是访谈里花时间最多的部分。这里只把它们标记为「各自移动哪个上限」，机制留到对应章节：

| 手段 | 动的是哪个量 | 效果（讲者原话/数字） |
| --- | --- | --- |
| GQA（分组查询注意力） | KV 字节 ÷ 4 | 算力不变，KV Cache 只花四分之一 |
| 量化 int8 / int4 | 权重字节 ÷ 2 或 ÷ 4 | 访存受限区整体快一倍；**不改变 $B^*$**（比值只由硬件决定）；顺带腾出更多显存给 KV |
| PagedAttention | 显存里能装的有效 KV 变多 | 当时声称相比标准实现有 20 倍吞吐提升 |
| 滑动窗口注意力 | 每条序列的 KV 上限固定 | 缓存变成环形缓冲区，长过窗口就覆盖写 |

## 七、为什么这条曲线就是帕累托前沿的雏形

把第五节那张图重新读一遍，会发现它有一个很强的性质：**曲线上的每一个点，都是「在给定延迟下能拿到的最大吞吐」；反过来也一样。**

- 曲线**上方**的点拿不到——那意味着更高的吞吐配更低的延迟，硬件不允许；
- 曲线**下方**的点是浪费——同样的延迟你能拿到更高吞吐，说明 batch 没配够；
- 所以真正可选的配置，只能落在**曲线上**。

这就是帕累托前沿的定义。于是「调 batch size」这件事的性质变了：**它不是「找到一个最优点」，而是在一条前沿上「选一个点」。** 选哪个点，等价于选你愿意给用户多长的 TPOT：

- 想守 0.1 秒/token 的阅读速度线，就停在黑线左边，吞吐只能到 12 query/s；
- 允许 1 秒/token，就能走到 14.5 query/s——只多 20% 的吞吐，代价是十倍的延迟。

**这就是为什么工程上要停在「吞吐还在涨、TPOT 还没陡」的膝点**：再往右走，你付出的延迟是线性的，换回来的吞吐却趋近于零。

不同 SLO 选不同点（实时交互 vs 离线批处理的具体配置策略）归 2.3.3，本文只点到为止。至于这条曲线在真实系统里怎么测出来——用一次并发扫描把每个并发级别下的吞吐与延迟都打出来——见同节的另一篇《吞吐先线性后饱和、TPOT 先平后陡》。

## 小结

- **一步 decode 的时间只有两个来源**：搬权重的时间（与 batch 无关）和做数学的时间（与 batch 成正比），实际耗时取两者较大值。
- **两条线的交点 $B^*$ 只由硬件决定**：$B^* \approx 2 \times \text{算力} / \text{带宽}$，讲者给的数是 400（A10G 与 A100 相同），与模型大小无关。严格按 fp16 两字节算会得到一半的值，量级一致。
- **$B^*$ 左边是免费区**：单步时间是水平线，TPOT 不变、吞吐随 $B$ 线性上升，Tensor Core 因为 $M = B$ 填满 tile 而利用率上升。
- **$B^*$ 右边是有代价区**：单步时间变成斜线，TPOT 随 $B$ 线性变长，吞吐趋平——算力满了，多塞的请求只能排队。
- **真实系统先撞的往往不是算力**：4K 上下文下每个请求的 KV 是 2 GB，$B > 7$ 时 KV 读取量就超过 14 GB 的权重；显存容量又把 7B 模型按在 5（A10G）和 33（A100）个并发上，离 400 差得远。
- **上下文长度决定你撞哪堵墙**：同一个 7B，4K 上下文能装 33 个，32K 上下文只能装 4 个，而 $B^*$ 一动没动。
- **在吞吐 - 延迟平面上，这条曲线就是帕累托前沿**：每个 batch 值对应前沿上的一个点，选点等于选 SLO；量化与 GQA 把曲线往左上抬，换硬件把整条曲线平移，但都不改变「先免费、后有代价」的形状。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| $B^*$（ideal batch size） | 搬权重的时间与做数学的时间相等的那个 batch size，只由硬件算力与带宽决定 |
| memory bound / compute bound | 被显存带宽限制 / 被算力限制；$B^*$ 两侧各是一种 |
| TPOT（s/token） | 每输出一个 token 花多少秒，也就是用户看到的出字间隔 |
| throughput（query/s） | 整机每秒能服务多少请求，与单请求延迟是两回事 |
| KV Cache | 每条序列为已见 token 存下的 key/value；大小随层数、维度、上下文长度、batch 线性增长，且每步都要读一遍 |
| 算术强度（arithmetic intensity） | 每搬一个字节做多少次运算；decode 单请求约 1，batch 后约等于 $B$ |
| 屋脊点（ridge point） | 算力除以带宽，A100 的 FP16 值约每字节 153 次运算 |
| 吞吐 - 延迟平面 | 横轴延迟、纵轴吞吐的图；固定硬件下是一条从左上弯下来的曲线，即可选配置的帕累托前沿 |
| GQA | 分组查询注意力，多个 query 共享一份 key/value，把 KV Cache 压到四分之一 |
| 阅读速度线 | 约每分钟 250 词；TPOT 低于它，用户不会觉得在等 |
