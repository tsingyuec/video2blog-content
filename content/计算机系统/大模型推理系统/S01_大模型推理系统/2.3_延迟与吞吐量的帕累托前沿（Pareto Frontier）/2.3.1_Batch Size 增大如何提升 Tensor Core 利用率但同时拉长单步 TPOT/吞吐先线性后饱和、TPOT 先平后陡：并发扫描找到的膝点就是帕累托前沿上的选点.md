# 吞吐先线性后饱和、TPOT 先平后陡：并发扫描找到的膝点就是帕累托前沿上的选点

> 视频来源：[Latency vs Throughput in LLM Inference, Explained](https://www.youtube.com/watch?v=6pvJ4K3Co-0)（YouTube · 动画解说短片）｜时长约 2 分 55 秒
> 简要导读：一支不到三分钟的动画短片，把「延迟按请求量、吞吐按整机量」这句话推到了工程结论：负载涨上去，吞吐先随并发线性上升、到 GPU 算力饱和后走平甚至下降，而延迟一路往上爬；这个拐点要靠一次**并发扫描**测出来，测出来之后**先定延迟目标、再取还能满足它的最高并发**。本文以它的解说与画面为骨架，把「为什么曲线长这样」「扫描脚本怎么写」「两个常见误区」三层展开；曲线背后的定量推导（$B^*$、KV 带宽、显存容量）见同节的另一篇《batch 越过拐点之前单步时间不动、之后 TPOT 随 batch 线性变长》，本文只在结尾对接。TTFT / TPOT 的测量口径见 2.1.1 与 2.1.2，QPS 与输出吞吐的定义见 2.2.1。

## 本讲要解决的核心问题（SCQA）

**背景**：一个推理服务器有两个互相拉扯的目标——尽快回答每一个请求，同时服务尽可能多的请求。前者是延迟，后者是吞吐。

**冲突**：这两个数各自都能被刷得很漂亮：把并发压到 1，延迟好看得不得了；把并发开到很大，吞吐也能冲上去。可没有人告诉你**该配多少并发**。更麻烦的是，直觉上「单请求延迟 × 用户数」应该能推出容量——短片明确说：**不行，它不是线性扩展的。**

**疑问**：负载涨上去时，吞吐和延迟各自怎么变？这个转折点怎么测出来？测出来之后又该怎么选？

**回答（中心思想）**：**吞吐随并发上升，直到 GPU 算力饱和；过了那个点，多出来的请求只能排队，吞吐走平甚至下降，而延迟继续往上爬。** 这个点要用一次**并发扫描**（concurrency sweep）找出来：固定并发级别跑一批请求，同时记录吞吐和延迟分位数，一个级别一个点，连起来就是曲线。**曲线的拐点（膝点）就是帕累托前沿上该停的位置**——而停在哪个膝点，取决于你先定下的延迟目标。

## 一、延迟按请求量，吞吐按整机量

短片开头就把两个指标的口径钉死了，这是后面所有讨论的地基：

| | 延迟 | 吞吐 |
| --- | --- | --- |
| 量的是什么 | 一个请求等了多久 | 整机每秒产出多少 |
| 具体口径 | 首字延迟、每输出 token 时间、端到端时间 | 每秒请求数、每秒总输出 token 数 |
| 谁在乎 | 用户 | 机器的账本 |

![吞吐是按整机量的：每秒请求数，或者每秒总输出 token 数](assets/吞吐先线性后饱和、TPOT%20先平后陡：并发扫描找到的膝点就是帕累托前沿上的选点/00025.webp)

一句话记住区别：**延迟是一个人等了多久，吞吐是一台机器干了多少活。** 把一万个人的等待平均掉，可以得到一个很漂亮的吞吐数字，而每个人仍然在等自己那一次。

> 这三个延迟口径的测量细节见 2.1.1（TTFT）、2.1.2（TPOT / ITL）与 2.1.3（端到端），两种吞吐口径的差别见 2.2.1，本文不重复定义。

## 二、把两者连起来的是批处理

短片用一句话点出了那根轴：**服务器让多个请求在同一次前向里一起过模型。**

- **吞吐为什么涨**：权重只读一遍，batch 里每个请求共享它；
- **延迟为什么变差**：更大的 batch 让每一步都变慢，于是 batch 里的每个请求都看到更高的延迟。

接下来它快速过了三代批处理，机制细节属于第 3 章，这里只取「它们各自把曲线的哪一段改变了」：

![静态批处理：等凑够固定一组请求，然后一起跑](assets/吞吐先线性后饱和、TPOT%20先平后陡：并发扫描找到的膝点就是帕累托前沿上的选点/00050.webp)

[【跳转到 00:25】](https://www.youtube.com/watch?v=6pvJ4K3Co-0&t=25)

1. **静态批处理**：服务器等凑够固定一组请求，然后一起跑。它的问题在「等」——整组会被按住，直到组里最长那个请求跑完。
2. **动态批处理**：加了一个超时窗口。窗口长一点能凑更大的 batch，短一点能保护延迟。**这个超时就是第一个显式的「吞吐换延迟」旋钮。**
3. **连续批处理**：不是在每个请求上调度一次，而是在**每一个解码步**上调度。一个请求写完了就立刻离开 batch，等待中的请求在下一步顶上它的位置。

![连续批处理：写完了的请求立刻离开 batch，等待中的请求在下一步顶上它的位置](assets/吞吐先线性后饱和、TPOT%20先平后陡：并发扫描找到的膝点就是帕累托前沿上的选点/00075.webp)

[【跳转到 01:15】](https://www.youtube.com/watch?v=6pvJ4K3Co-0&t=75)

短片对连续批处理的评价很克制：**「相比静态批处理，两个数都变好了，但最大 batch size 仍然要在这两者之间做取舍。」** 这句话很重要——**更好的调度能把曲线整体往左上推，但它消不掉曲线本身的斜率。** 只要你还想提高吞吐，就还得拿延迟去换。

短片还点出了 batch 内部的第二重张力：

![batch 内部的第二重张力：一个新请求的 prefill 很重，会把周围正在解码的请求卡住](assets/吞吐先线性后饱和、TPOT%20先平后陡：并发扫描找到的膝点就是帕累托前沿上的选点/00090.webp)

[【跳转到 01:30】](https://www.youtube.com/watch?v=6pvJ4K3Co-0&t=90)

**一个新请求的 prefill 很重，会把周围的解码卡住。** 这意味着「并发」这个数字并不等于「有效 batch」：即使你允许 64 个并发，某一瞬间真正在算 decode 的行数也可能远小于 64。这条线索的解法（chunked prefill、混合批次）在第 3 章。

## 三、负载涨上去：吞吐先升后平，延迟一路爬

这是短片的核心一段，只用了四个方框：

![负载增长的链条：更多并发 → 更高吞吐 → GPU 饱和](assets/吞吐先线性后饱和、TPOT%20先平后陡：并发扫描找到的膝点就是帕累托前沿上的选点/00100.webp)

[【跳转到 01:40】](https://www.youtube.com/watch?v=6pvJ4K3Co-0&t=100)

短片的原话是：**「吞吐随并发上升，直到 GPU 的算力饱和。过了那个点，多出来的请求只能排队：吞吐走平甚至下降，而延迟继续往上爬。」**

把这句话拆成两段，就是本节要的两条曲线：

```
吞吐 ↑                      TPOT ↑
     │      __________            │        /
     │    _/                      │      _/
     │  _/          ← 饱和         │    _/     ← 陡起来
     │ /                          │  _/
     └──────────────→ 并发         └──────────────→ 并发
          ↑                            ↑
        膝点                          膝点
```

- **膝点左边**：多一个并发就多一份产出，每个人的 TPOT 只是略微变长。这一段是「免费的」——因为权重搬运的时间被更多行摊薄了（为什么是免费的，见另一篇里的 $B^*$）。
- **膝点右边**：算力已经满了，多一个并发不会多一份产出，只是让所有人的 TPOT 一起变长。

**为什么吞吐会「走平甚至下降」而不是稳定在一个平台？** 短片没展开，这里补一句：走平是因为算力已经打满；**下降**则通常来自排队与调度开销——请求越多，队列越长，调度器每一步要处理的状态越多，prefill 与 decode 互相打断的次数也越多，有效算力反而被吃掉一点。

## 四、并发扫描：把这个点测出来

短片给的方法非常朴素：**固定一个并发级别，压一批请求，同时记录吞吐和延迟分位数；换下一个级别再跑一次。**

![并发扫描的脚本：一个信号量限制同时跑多少请求，每个请求记录自己的延迟，总输出量除以墙钟时间得到系统吞吐](assets/吞吐先线性后饱和、TPOT%20先平后陡：并发扫描找到的膝点就是帕累托前沿上的选点/00125.webp)

[【跳转到 02:05】](https://www.youtube.com/watch?v=6pvJ4K3Co-0&t=125)

画面里的脚本结构大致是：

```python
async def one(sem):
    async with sem:                       # 信号量 = 并发上限
        t = time.perf_counter()
        n = await generate()              # 返回这次生成了多少 token
        return time.perf_counter() - t, n

async def sweep(c, total=200):
    sem, t0 = asyncio.Semaphore(c), time.perf_counter()
    r = await asyncio.gather(*[one(sem) for _ in range(total)])
    tps = sum(n for _, n in r) / (time.perf_counter() - t0)   # 吞吐
    return quantiles([t for t, _ in r], n=100)[98], tps      # 延迟分位数 + 吞吐
```

三个细节值得抄下来：

1. **并发是「同时跑多少个」**，由信号量控制，不是「一共发了多少个」。总请求数 `total` 固定，改变的只有并发上限。
2. **吞吐用「总输出 token ÷ 墙钟时间」算**，不是把每个请求的速度加起来——后者会把排队时间漏掉。
3. **每个级别都要同时拿到「吞吐」和「延迟分位数」**，因为单独一个数没有意义。短片特别提醒：扫描返回的是**第 99 百分位延迟**，而不是平均值。

## 五、两个误区

### 5.1 单请求延迟 × 用户数，不等于容量

![它不会线性扩展：并发之下单请求延迟会上升，饱和之后排队时间接管一切](assets/吞吐先线性后饱和、TPOT%20先平后陡：并发扫描找到的膝点就是帕累托前沿上的选点/00140.webp)

[【跳转到 02:20】](https://www.youtube.com/watch?v=6pvJ4K3Co-0&t=140)

短片的原话是：**「一次只压一个请求，再乘以你预计的用户数——它不是线性扩展的。并发之下单请求延迟会上升，饱和之后排队时间接管一切。」**

这个误区的根源是：单请求压测量到的延迟里**没有排队**。可一旦并发上去，每个请求都要和别人的请求抢同一块 GPU，排队时间会变成延迟里最大的一项。**所以容量只能靠并发压测测出来，不能靠乘法算出来。**

### 5.2 均值会藏住慢请求

![判断标准：不要用平均值，要用尾部分位数](assets/吞吐先线性后饱和、TPOT%20先平后陡：并发扫描找到的膝点就是帕累托前沿上的选点/00150.webp)

[【跳转到 02:35】](https://www.youtube.com/watch?v=6pvJ4K3Co-0&t=155)

**「少数慢请求会藏在均值里，所以要看尾部分位数。」** 这条和 5.1 是同一件事的两面：均值把排队时间平均掉了，而用户感受到的正是被平均掉的那一部分。

> 尾部分位数为什么会在高并发下集体恶化、以及长尾请求怎么治理，是 2.2.3 的主题，本文只把它当作「评估口径」提一句。

## 六、怎么选：先定延迟目标，再取最高并发

短片给的决策顺序只有两步，但顺序不能反：

![按负载选 batch：聊天这类交互式应用把 batch 压小来保护延迟，离线任务把 batch size 推高来换吞吐和成本](assets/吞吐先线性后饱和、TPOT%20先平后陡：并发扫描找到的膝点就是帕累托前沿上的选点/00160.webp)

[【跳转到 02:50】](https://www.youtube.com/watch?v=6pvJ4K3Co-0&t=170)

1. **先把延迟目标定下来**（比如 TPOT 不超过某个值）；
2. **再挑还能满足它的最高并发**。

为什么不能反过来？因为「最高吞吐」这个目标没有上界——只要允许延迟无限变差，吞吐总能再高一点。**一个没有约束的目标函数，无法用来比较两套系统谁更好。** 先定延迟目标，等于先在前沿上画一条竖线，然后取竖线左边最高的那个点。

短片最后用一句话把两类负载分开：**「像聊天这样的交互式应用会把 batch 压小来保护延迟；离线任务则把 batch size 推高来换吞吐和成本。」** 具体参数怎么配（`max_num_seqs`、调度策略、超时窗口）属于 2.3.3，本文不展开。

![短片的总结页：延迟按请求、吞吐按整机、批处理在两者之间做交换、一次并发扫描能告诉你上限在哪里](assets/吞吐先线性后饱和、TPOT%20先平后陡：并发扫描找到的膝点就是帕累托前沿上的选点/00170.webp)

[【跳转到 02:55】](https://www.youtube.com/watch?v=6pvJ4K3Co-0&t=175)

## 七、这条曲线的每一段，对应哪个物理上限

短片停在「扫描能告诉你上限在哪里」。把扫描出来的曲线和硬件对上，还能再往前一步——**膝点的位置不是随机的，它由三个上限里最先撞到的那个决定**：

| 曲线上的特征 | 背后是谁 | 什么时候它先撞 |
| --- | --- | --- |
| 吞吐线性上升、TPOT 几乎不动 | 权重搬运被更多行摊薄 | 只要 KV 读取量还小于权重 |
| TPOT 开始线性变长、吞吐趋平 | 算力到顶，或 KV 带宽到顶 | 上下文越长、模型越大，越早到 |
| 曲线直接断掉、加不上并发 | 显存容量装不下更多 KV | 长上下文时最先撞的就是它 |

这三条在另一篇《batch 越过拐点之前单步时间不动、之后 TPOT 随 batch 线性变长》里有完整的算式（$B^* \approx 2 \times \text{算力} / \text{带宽}$、KV Cache 的字节公式、A10G 只装 5 个 / A100 只装 33 个的显存账）。**把两篇接起来读，就是本节要的那条完整因果链：**

$$
\text{batch} \uparrow \ \Rightarrow\ \text{Tensor Core 利用率} \uparrow \ \Rightarrow\ \text{吞吐} \uparrow \ \Rightarrow\ \text{撞上某个上限} \ \Rightarrow\ \text{TPOT} \uparrow
$$

而并发扫描做的事，就是把这条链在**你自己的硬件、你自己的上下文长度、你自己的模型**上量一遍——因为上限在哪，只有测了才知道。

## 小结

- **延迟按请求量，吞吐按整机量。** 把两者连起来的是批处理：权重读一遍分给 batch 里所有人，吞吐涨、每步变慢。
- **三代批处理改的是曲线的位置，不是曲线的斜率。** 静态等最长、动态加超时、连续按解码步调度；即便换成连续批处理，「最大 batch size 仍然要在吞吐与延迟之间做取舍」。
- **负载涨上去，吞吐先升后平（甚至下降），延迟一路爬。** 拐点是 GPU 算力饱和的那一刻。
- **拐点只能测，不能算乘法。** 固定并发、压一批请求、同时记录吞吐与延迟分位数，一个级别一个点；并发由信号量控制，吞吐用总输出除以墙钟时间。
- **两个误区**：单请求延迟 × 用户数不等于容量（漏了排队）；平均值会藏住慢请求（要看尾部分位数）。
- **选点顺序不能反**：先定延迟目标，再取还能满足它的最高并发。交互式应用压小 batch 保延迟，离线任务推高 batch 换吞吐与成本。
- **膝点就是帕累托前沿上的那个点**：曲线上方拿不到、下方是浪费，选点等于选 SLO。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| 延迟（latency） | 一个请求等了多久；按请求量，含 TTFT、TPOT、端到端 |
| 吞吐（throughput） | 整机每秒产出多少；按整机量，含每秒请求数与每秒输出 token 数 |
| 批处理（batching） | 让多个请求在同一次前向里一起过模型，权重只读一遍 |
| 静态 / 动态 / 连续批处理 | 等一组跑一组 / 加超时窗口凑批 / 按解码步调度、写完即走 |
| 并发（concurrency） | 同一时刻允许在跑的请求数，由信号量或调度器上限控制 |
| 并发扫描（concurrency sweep） | 逐个并发级别压测，记录每个级别下的吞吐与延迟分位数，连成曲线 |
| 膝点（knee） | 吞吐不再明显上升、延迟开始陡增的那个并发值 |
| 尾部分位数（P99 等） | 把请求按延迟排序后第 99% 处的值；均值会把慢请求藏起来 |
| prefill 阻塞 | 新请求的 prefill 很重，一次性算完会让周围正在解码的请求卡住 |
| 帕累托前沿 | 在给定延迟下能拿到的最大吞吐所构成的曲线；可选配置只能落在它上面 |
