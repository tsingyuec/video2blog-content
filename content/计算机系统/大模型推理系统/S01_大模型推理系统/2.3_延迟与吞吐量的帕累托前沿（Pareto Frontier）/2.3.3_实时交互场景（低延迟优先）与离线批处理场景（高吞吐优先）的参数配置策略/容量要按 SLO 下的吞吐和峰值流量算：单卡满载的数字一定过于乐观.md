# 容量要按 SLO 下的吞吐和峰值流量算：单卡满载的数字一定过于乐观

> 视频来源：[100. LLM Inference Cost Modeling: Size the Fleet, Not One GPU](https://www.youtube.com/watch?v=2okAnR41Hd8)（YouTube · Hitesh C.）| 时长约 3 分 32 秒
> 简要导读：这支三分半的短片用九行 Python 说明了一件事——**把一张卡跑满得到的每百万 token 成本，一定过于乐观**，因为真实机队不是按「满载」组的，而是按「峰值流量 + 余量，在延迟目标下达标」组的。本文以它的算式与数字为骨架，先补上它没明说的那一层（交互与批处理的目标函数为什么不同），再展开四环成本链、三个杠杆、混跑为什么互相伤害，最后给出一条可执行的六步决策流程。凡是我补的工程细节都标了「补充」。Goodput 的定义见 2.2.2，膝点与并发扫描见 2.3.1，本文不重复。

## 本讲要解决的核心问题（SCQA）

**背景**：要判断一套推理服务贵不贵，最直觉的做法是：拿一张卡跑到满负荷，量出每秒能出多少 token，再除以卡的小时价格，得到「每百万 token 多少钱」。

**冲突**：这个数字漂亮得不像真的——视频里的例子是 **每百万 token 0.37 美元**。可真实机队的账是 **每百万 token 1.60 美元**，差了四倍多。差在哪？**因为你不会让一张卡跑满。** 你会按峰值流量组一个机队，在某个延迟目标下达标，还要留出余量。

**疑问**：那容量到底该怎么算？「吞吐」这个数该在什么条件下测？峰值、均值、余量各占多少权重？如果同一套机队里既有交互业务又有批处理，又该怎么摆？

**回答（中心思想）**：**容量 = 峰值流量 × 余量 ÷ 在 SLO 下达标的单卡吞吐。** 这个式子里的每一个词都不能省：用均值代替峰值，峰值时队列会涨到所有人都不达标；用 benchmark 峰值代替「SLO 下的吞吐」，算出来的机队根本撑不住延迟目标；不留余量，一次突发或一次滚动发布就会打穿。而一旦你接受了这个式子，两类场景的差别就变得很清楚——**交互场景把 SLO 当硬约束去最大化并发，批处理场景把延迟当松约束去最大化总 token 数**，它们对同一批旋钮的取值方向是相反的。

## 一、两种场景的目标函数不是同一个

视频没有明写目标函数，但它整篇的推理都建立在「吞吐必须在 SLO 下测」这一条上。把这一条展开，就是本节要的两个式子。

**实时交互场景**（聊天、代码补全、客服机器人）：**人在等**。延迟不是成本，是**约束**——超过阈值就等于没服务。于是目标函数是「在延迟达标的前提下，把并发推到最大」：

$$
\max_{N}\ \ \text{Goodput}(N)\quad \text{s.t.}\quad P_{99}(\text{TTFT}) \le T^{*},\ \ P_{99}(\text{TPOT}) \le P^{*}
$$

其中 $N$ 是并发（对应 `max_num_seqs`），$T^{*}$ 与 $P^{*}$ 是产品定下的首字与每 token 时间上限。注意约束用的是 **P99** 而不是均值——视频在别处也强调过这一点：企业级 SLA 是按第 99 百分位考核的，**最差的那 1% 也必须过线**。

**离线批处理场景**（文档摘要、数据清洗、离线评测）：**没人在等**。延迟从约束降级为**超时线**，目标变成单位时间总产出最大：

$$
\max_{N}\ \ \frac{\sum_{i} \text{tokens}_i}{\Delta t}\quad \text{s.t.}\quad \text{makespan} \le D
$$

$D$ 是「这批任务必须多久跑完」的截止时间。只要不超时，单个请求等多久都无所谓。

两个式子的差别只有一处，但决定了所有参数的取值方向：**交互场景里延迟在约束项里（碰不得），批处理场景里延迟在约束项里但很松（可以让）。** 于是同一个旋钮，在一种目标函数下是成本，在另一种下是收益。

| | 实时交互 | 离线批处理 |
| --- | --- | --- |
| 谁在等 | 人 | 没人 |
| 延迟的角色 | 硬约束（P99 卡死） | 松约束（只受超时限制） |
| 吞吐的角色 | 目标 | 目标 |
| 优化问题 | 达标前提下最大化并发 | 不超时前提下最大化总 token 数 |
| 峰值/均值 | 峰值决定容量，且峰值很尖 | 可以把任务挪到低峰填谷 |

> 补充：上表最后一行是理解「混跑」的钥匙——交互业务的流量曲线是**尖的**（早晚高峰），批处理的流量曲线是**可塑的**（什么时候跑都行）。两者的曲线形状不同，才有「填谷」的空间。

## 二、单卡满载的每 token 成本一定过于乐观

视频开场就把这个错误点名：

> **「Price one GPU at full load, and you get a cost per token that's far too optimistic. Real fleets cost more.」**

![成本链的第一环：硬件价格，按每 GPU 小时计](assets/容量要按%20SLO%20下的吞吐和峰值流量算：单卡满载的数字一定过于乐观/00025.webp)

[【跳转到 00:25】](https://www.youtube.com/watch?v=2okAnR41Hd8&t=25)

原因一句话：**「因为你不会让一张卡跑满。你会按峰值流量组一个机队，在某个延迟目标下达标，还要留出余量。」**

这句话里其实藏了三个「不是」：

1. 不是按**满载**算，而是按**SLO 下**的吞吐算；
2. 不是按**均值**组，而是按**峰值**组；
3. 不是刚好够，而是**留余量**。

三个都不是，所以真实的每 token 成本必然比「满载单卡」高出好几倍。视频给的倍数是**四倍以上**。

## 三、四环成本链：硬件价格 → SLO 下的吞吐 → 机队规模 → 每 token 成本

视频把完整的成本模型串成四环：

> **「A full cost model chains four things: hardware price, throughput at your SLO, fleet size, and finally dollars per token.」**

![九行 Python 的成本模型：每 GPU 小时 2 美元、SLO 下每秒 1500 个输出 token、峰值 30000、均值 9000、余量 1.3](assets/容量要按%20SLO%20下的吞吐和峰值流量算：单卡满载的数字一定过于乐观/00050.webp)

[【跳转到 00:50】](https://www.youtube.com/watch?v=2okAnR41Hd8&t=50)

四环各自的定义，视频都给了：

| 环节 | 含义 | 视频里的取值 |
| --- | --- | --- |
| 硬件价格 | 每 GPU 小时的租金，或自购机器的摊销 | `$2.00 / GPU-h` |
| **SLO 下的吞吐** | 在延迟目标内、按**真实 prompt 与回答长度分布**测出的每秒输出 token 数 | `1,500 tok/s` |
| 机队规模 | 峰值流量 × 余量 ÷ 单卡 SLO 吞吐，向上取整 | 26 卡 |
| 每 token 成本 | 账单 ÷ **实际服务出去的** token 数 | 见下 |

第二环是整条链上最容易做假的一环，视频专门警告了一次：

> **「Throughput must be measured at your SLO on your real mix of prompt and answer lengths, not the peak from a benchmark.」**

三个限定词缺一不可：**在你的 SLO 下**（不是满载峰值）、**按你真实的 prompt 与回答长度混比**（不是等长合成请求）、**实测**（不是抄别人的 benchmark 数字）。

> 补充：为什么「SLO 下的吞吐」和「满载吞吐」差得远？因为满载吞吐对应的延迟通常已经烂到不可用——吞吐曲线在膝点之后还在涨，但延迟已经陡增。膝点的含义与并发扫描方法见 2.3.1；把「只数达标请求」的吞吐定义为 Goodput 的推导见 2.2.2。

## 四、算一遍：26 张卡、每百万 token 1.60 美元、23% 利用率

视频把九行代码跑了一遍，数字值得逐项核对：

```python
import math
gpu_hour, tps_at_slo = 2.00, 1500   # $/GPU-h; output tok/s
peak_tps, avg_tps = 30_000, 9_000   # traffic shape
headroom = 1.3                       # bursts, failover, deploys

gpus = math.ceil(peak_tps * headroom / tps_at_slo)   # 26
monthly = gpus * gpu_hour * 730                      # $37,960
tokens = avg_tps * 3600 * 730                        # 23.7 B
cost_per_m = monthly / tokens * e6                   # ~ $1.60
```

![机队规模那一行被高亮：gpus = ceil(peak_tps × headroom / tps_at_slo)](assets/容量要按%20SLO%20下的吞吐和峰值流量算：单卡满载的数字一定过于乐观/00075.webp)

[【跳转到 01:15】](https://www.youtube.com/watch?v=2okAnR41Hd8&t=75)

$$
\text{gpus} = \left\lceil \frac{30000 \times 1.3}{1500} \right\rceil = 26
$$

$$
\text{monthly} = 26 \times 2.00 \times 730 \approx \$37{,}960
$$

$$
\text{cost per million} = \frac{37960}{23.7\times 10^{9}} \times 10^{6} \approx \$1.60
$$

而单卡满载的估算只有 **每百万 token 0.37 美元**。差了 4.3 倍。视频把差额的来源算成了一个利用率：

![同一张卡两个答案：单卡满载 0.37 美元每百万，机队模型 1.60 美元每百万；有效利用率只有 23%](assets/容量要按%20SLO%20下的吞吐和峰值流量算：单卡满载的数字一定过于乐观/00100.webp)

[【跳转到 01:40】](https://www.youtube.com/watch?v=2okAnR41Hd8&t=100)

$$
\text{effective utilisation} = \frac{9000}{26 \times 1500} \approx 23\%
$$

**有效利用率 23%。** 也就是说，你付了 100% 的卡钱，只用到 23% 的产能——剩下 77% 是为峰值和余量买的保险。

视频的结论是：**「峰值与均值的比值，乘以余量，决定了机队里有多大一块是闲着的。」** 这个比值是业务属性，不是技术参数：峰值是均值 3.3 倍的业务，和峰值是均值 1.2 倍的业务，成本结构完全不同。

> 这也解释了为什么「把批处理挪到低峰」是省钱而不是省时间——它抬高的正是这个 23%。

## 五、三个杠杆：抬高峰值利用率，而不是压峰值

视频给了三个把成本压下去的杠杆，注意它们**都不是「把峰值削掉」**，而是「把均值抬起来」或「让机队跟着曲线走」：

### 5.1 前缀缓存（prefix caching）：减少 prefill 工作量

![vLLM 的 Automatic Prefix Caching 文档：它缓存已有查询的 KV，但明确写着「不减少生成新 token 的时间」](assets/容量要按%20SLO%20下的吞吐和峰值流量算：单卡满载的数字一定过于乐观/00125.webp)

[【跳转到 02:05】](https://www.youtube.com/watch?v=2okAnR41Hd8&t=125)

**前缀缓存复用共享 prompt 前缀的 KV Cache，于是 prefill 工作量下降、SLO 下的吞吐上升。** 但视频紧接着引了 vLLM 文档的原话，点出它的边界：

> **「It doesn't reduce the time of generating new tokens, so output heavy traffic gains less.」**

也就是说：**它对「输入重」的流量收益大，对「输出重」的流量收益小。** 一个把 8,000 token 文档塞进去、只回 200 token 的摘要任务，能吃到大部分收益；一个 prompt 只有 50 token、却要生成 2,000 token 的创作任务，几乎吃不到。

### 5.2 把批处理挪到低峰：抬高同一套机队的平均流量

**「Moving batch jobs into quiet hours raises average traffic on the same fleet.」**

这是混合场景最省钱的解法：**不新增卡，只是把「没有 SLO 的活」填进「有 SLO 的业务」的低谷。** 分子（账单）不变，分母（实际服务的 token）变大，每 token 成本直接下降。

### 5.3 自动扩缩：让机队跟着曲线走

**「Auto scaling lets the fleet follow the curve.」** 如果业务曲线可预测，让机队规模随曲线伸缩，比一直按峰值养着便宜。代价是冷启动与调度复杂度。

> 补充：这三个杠杆的优先级通常是 5.2 > 5.1 > 5.3。5.2 不需要改模型、不需要改代码，只是改调度；5.1 需要流量形态配合（前缀重复率要高）；5.3 需要成熟的弹性基础设施。

## 六、混跑一定互相伤害：为什么必须分池

视频只说了「把批处理挪到低峰」，没说为什么不能直接混跑。这一点值得补清楚，因为它是「按场景选参数」在集群层面的直接推论。

**混跑一定互相伤害，因为两类请求共享的是同一批不可分割的资源：**

| 共享的东西 | 交互请求要什么 | 批处理请求要什么 | 冲突结果 |
| --- | --- | --- | --- |
| `max_num_seqs` 槽位 | 少而精，保住 TPOT | 多而满，拉高吞吐 | 批处理占满槽位 → 交互请求排队，TTFT 崩 |
| 每步 token 预算 | 压小，保住 ITL | 放大，长 prompt 快算完 | 批处理的长 prompt 拉长步长 → 交互用户流式输出卡顿 |
| KV 池 | 留余量，防突发 | 吃满，多装并发 | 池子被批处理占满 → 交互请求被抢占/换出，尾部恶化 |
| 调度队列 | 优先级、抢占 | 先来先做 | 一个后台任务可以挤掉一个首屏请求 |

这就是为什么视频的解法是**时间上分开**（挪到低峰）而不是**同一个池子里混**。如果时间上分不开，还有三条路：

1. **按 SLO 分队列 + 优先级抢占**：交互请求高优先级，批处理低优先级；显存满时先牺牲批处理。代价是批处理被反复换出/重算，实际吞吐下降——所以它只适合「批处理可以等」的场景。
2. **分实例（分池）**：两组 GPU，一组跑交互、一组跑批处理，各自按自己的 SLO 配参数。最干净，也最贵，因为两组都要留余量。
3. **PD 分离 + 独立资源池**：把 prefill 与 decode 拆到不同实例，交互流量走低延迟池、批处理走吞吐池。机制细节属于第 10 章，本节只把它列为一种「物理隔离」的选项。

**判断标准很简单**：如果两类请求的 SLO 差一个数量级以上，就不要混；如果差得不多，可以用优先级抢占，但要接受批处理的实际吞吐打折。

## 七、一条可执行的六步决策流程

把视频的成本模型、2.3.1 的并发扫描、2.2.2 的 Goodput 口径串起来，就是一条能照着做的流程。**前两步来自视频，后四步是补充**：

**① 定 SLO（分位数，不是均值）**
交互场景定 $P_{99}(\text{TTFT}) \le T^{*}$ 与 $P_{99}(\text{TPOT}) \le P^{*}$；批处理只定 `makespan` 上限。这一步是产品决策，不是技术参数。

**② 扫并发，画出「吞吐 - TPOT」曲线**
固定并发级别压测，每个级别同时记录吞吐与延迟分位数，连成曲线（方法见 2.3.1）。**必须在真实 prompt/回答长度分布上扫**——这正是视频强调的「your real mix」。

**③ 取膝点，或 SLO 允许的最大点**
曲线上有两个候选位置：**膝点**（吞吐不再明显上升、延迟开始陡增）和 **SLO 允许的最大点**（在 $T^{*}$、$P^{*}$ 竖线左边最靠右的那个点）。交互场景取后者（SLO 是硬约束），批处理取前者或更右（延迟可以让）。

**④ 反推参数**
- `max_num_seqs` ← ③ 选中的并发值；
- KV 池大小 ← 该并发 × 平均上下文长度（容量墙的算式见 2.3.2）；
- `max_num_batched_tokens` ← 按 ② 的曲线选：交互压小保 ITL，批处理放大保 TTFT；
- `gpu_memory_utilization` ← 留出安全边际，不要顶到 1.0；
- 调度策略 ← 交互用优先级，批处理用 FCFS。

**⑤ 压测验证 P99，而不是均值**
用 ② 的脚本重跑一遍，确认 $P_{99}$ 达标。视频的警告在这里同样适用：**「average traffic suggests 6 GPUs」** 而峰值需求是容量的三倍多——用均值验收，等于用最宽松的时刻去证明最紧张的时刻没问题。

**⑥ 上线后按两个信号回调**
- **抢占率**（preemption rate）：持续大于零说明 KV 池不够或并发上限过高，要先降 `max_num_seqs`；
- **KV 使用率**：长期贴近上限说明没有余量，一次突发就会打穿 SLO。

## 八、其余旋钮在两种场景下的取值

除了前面几篇讲过的 `max_num_seqs`、`max_num_batched_tokens`、`max_model_len` 与调度策略，还有几个开关的取值方向也随场景反转。下表是补充整理（机制细节分别属于第 3、4、6、10 章）：

| 旋钮 | 实时交互（低延迟优先） | 离线批处理（高吞吐优先） | 为什么反向 |
| --- | --- | --- | --- |
| `gpu_memory_utilization` | 0.85–0.90，留安全边际 | 0.90–0.95，尽量吃满 | 交互要防突发 OOM 与碎片；批处理可承受偶发失败重跑 |
| KV 池大小 | 够用即可，留余量给突发 | 尽量大，多装并发 | 池子越大并发越高，但交互场景的尾部风险也越大 |
| CUDA Graph | 开（省掉每步的 kernel launch 开销） | 开，但收益让位于吞吐 | 交互场景每步很短，launch 开销占比高；批处理步长本来长 |
| 投机采样 | 开（降 TPOT，直接改善体验） | 视接受率而定，接受率低时反而亏 | 交互场景要的是每 token 更快；批处理要的是总算力效率 |
| PD 分离 | 开（把 prefill 抖动从 decode 里隔离出去） | 通常不必 | 交互场景怕 prefill 打断 decode；批处理没有人在等 |
| 前缀缓存 | 开（降 TTFT） | 开（降 prefill 工作量） | 两边都赚，但交互赚在首字、批处理赚在吞吐 |

## 九、四个常见错误配置

视频明确点出了两个，另外两个是补充：

**① 按均值定容量**（视频原话）

> **「Average traffic suggests 6 GPUs. At peak, demand is over three times their capacity. The queue grows and every user misses the SLO.」**

按均值算只要 6 张卡，峰值需求是它的三倍多。结果是队列一路涨，**每个用户都不达标**。这是最贵的一种错——不是多花钱，是花了钱还没服务好。

**② 用单卡满载的每 token 成本做决策**（视频原话）

满载数字过于乐观，会让「自建 vs 买 API」的判断整个反过来。视频给的盈亏平衡算法是：自建是固定月成本，API 随 token 线性增长，两条线有一个交点；**交点以下买 API 更便宜**（例子里是 15 亿 token 以下）。

**工程人力、存储与网络监控、以及「你能自托管的那个模型质量够不够」**——最后一条最容易被忽略：如果为了自建只能用一个小一号的模型，那么省下来的钱可能换来的是答不准。

**③ 把离线参数搬到线上**（补充）

批处理那套「`max_num_seqs` 拉满、预算放大、`gpu_memory_utilization` 顶到 0.95」的配置，搬到交互服务上就是灾难：并发拉满 → 每步变长 → TPOT 与 TTFT 一起崩；显存顶到 0.95 → 一次长 prompt 就 OOM。**同一份配置不能服务两种 SLO。**

**④ 不开 chunked prefill 却抱怨长 prompt 卡**（补充）

chunked prefill 在 vLLM V1 里默认开启，但如果你用的是旧版本或手动关掉了它，长 prompt 会独占一整步，正在解码的所有请求一起停顿。这时候该做的不是调小并发，而是把 chunked prefill 打开、再调预算。

## 小结

- **两种场景的目标函数不同**：交互场景把 P99 延迟当硬约束去最大化并发；批处理把延迟当松约束去最大化总 token 数。同一个旋钮在两种目标下是成本或收益，方向因此相反。
- **单卡满载的每 token 成本一定过于乐观**，因为真实机队是按「峰值 × 余量 ÷ SLO 下吞吐」组的；视频里的差距是 0.37 美元对 1.60 美元，有效利用率只有 23%。
- **四环链**：硬件价格 → SLO 下的吞吐 → 机队规模 → 每 token 成本。第二环必须在你自己的 SLO 下、用真实长度分布实测。
- **三个杠杆都在抬高峰值利用率**：前缀缓存（降 prefill，对输出重的流量收益小）、批处理挪到低峰（抬高均值）、自动扩缩（让机队跟曲线）。
- **混跑一定互相伤害**，因为槽位、token 预算、KV 池、调度队列都是共享的。解法是时间上分开、优先级抢占、分池，或 PD 分离。
- **六步流程**：定 SLO（分位数）→ 扫并发画曲线 → 取膝点或 SLO 允许的最大点 → 反推参数 → 压测验证 P99 → 上线按抢占率与 KV 使用率回调。
- **四个常见错误**：按均值定容、用满载的每 token 成本决策、把离线参数搬到线上、不开 chunked prefill 却抱怨长 prompt 卡。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| SLO | 服务等级目标；用分位数表达（如 P99 TTFT ≤ 1s），不是均值 |
| 峰值 / 均值流量 | 一段时间内的最高与平均请求速率；决定机队规模的是峰值 |
| 余量（headroom） | 为突发、故障转移、滚动发布预留的额外容量，例子里是 1.3 倍 |
| SLO 下的吞吐 | 在延迟目标内测出的每秒输出 token 数，不是 benchmark 峰值 |
| 有效利用率 | 实际服务的 token 数 ÷ 机队满负荷产能；例子中是 23% |
| 前缀缓存（prefix caching） | 复用共享 prompt 前缀的 KV Cache，减少 prefill 工作量；不减少 decode 时间 |
| 填谷（batch into quiet hours） | 把无 SLO 的批处理任务挪到业务低谷，抬高同一机队的平均流量 |
| 自动扩缩 | 让机队规模跟随流量曲线伸缩，替代「一直按峰值养着」 |
| 混跑（co-location） | 交互与批处理共享同一批 GPU；槽位与 KV 池的竞争会让双方都变差 |
| 分池 | 按 SLO 把请求分到不同实例组，各自配参数、各自留余量 |
| 抢占率 | 单位时间内因显存不足被换出/重算的请求比例；持续大于零说明并发上限过高 |
| 盈亏平衡量 | 自建（固定月成本）与 API（按 token 计费）两条成本线的交点 |
