# 三个旋钮各管一段预算：并发槽、每步 token 与单请求上下文，调大调小打的是不同的曲线

> 视频来源：[vLLM Explained in 10 Min: 3 Settings for Insanely Fast Throughput & Latency!](https://www.youtube.com/watch?v=ycEQJIyZ2sU)（YouTube · Lukasz Gawenda）｜时长约 10 分钟
> 简要导读：这支 10 分钟的动画讲解把 vLLM 的调度器拆成三个参数——`max_model_len`、`max_num_batched_tokens`、`max_num_seqs`——并且坚持用「一段被切开的预算」来解释它们，而不是罗列参数名。本文按它的动画顺序展开：三个参数各管哪一段预算、撞上各自上限时会发生什么、调度器在显存满时抢占谁、chunked prefill 如何把「不可切的预算」变成「可切的预算」，最后把三个旋钮的转向整理成一张「调大打到哪条曲线、代价是什么」的表。三个参数的具体数值只是这支视频的示例配置，不是推荐值；`max_model_len` 与显存容量的定量关系见 2.3.2，膝点与并发扫描见 2.3.1，本文不重复推导。

## 本讲要解决的核心问题（SCQA）

**背景**：vLLM 的启动命令上有几十个参数，但真正决定「这台机器能同时服务多少请求、每个请求等多久」的只有三个：单请求上下文上限、每步 token 预算、并发序列槽位数。

**冲突**：这三个参数的名字看起来都在说「上限」，于是很容易被当成三个可以一起调大的开关。可它们管的是**三段不同的预算**：一个管单个请求能有多长，一个管 GPU 一次前向能算多少 token，一个管同时有多少个请求在跑。把其中任何一个调大，被打到的曲线都不一样——有的让首字更快，有的让流式输出更顺，有的只是让更多请求挤进来。

**疑问**：这三个参数各自到底在限制什么？撞上各自的上限时，系统会怎么表现？把某一个调大或调小，究竟改善的是哪一条曲线、代价又落在谁身上？

**回答（中心思想）**：**把三个参数读成三段预算，就不会配错。** `max_model_len` 是**单个请求**的上下文天花板（prompt + 生成），撞上就被直接拒绝；`max_num_batched_tokens` 是**调度器一步**的 token 预算，撞上就把装不下的请求推到下一轮；`max_num_seqs` 是**同时在跑**的序列槽位数，撞上就让新请求排队。而 chunked prefill 之所以存在，正是因为第二段预算原本不可切分——一个 3 万 token 的 prompt 要么整段算完、要么整段不算，中间那些正在解码的请求只能干等。

## 一、三个参数是三段互不重叠的预算

视频开场直接把三个参数并排放在一张图上，每个下面写一句它的职责：

![三个参数并排：max_model_len 是单请求上下文天花板，max_num_batched_tokens 是每步 token 预算，max_num_seqs 是并行序列槽位](assets/三个旋钮各管一段预算：并发槽、每步%20token%20与单请求上下文，调大调小打的是不同的曲线/00025.webp)

[【跳转到 00:25】](https://www.youtube.com/watch?v=ycEQJIyZ2sU&t=25)

| 参数 | 视频里的示例值 | 它限制的是 | 撞上之后发生什么 |
| --- | --- | --- | --- |
| `--max-model-len` | 16,000 | 单个请求的 prompt + 生成 token 总数 | 请求被**直接拒绝** |
| `--max-num-batched-tokens` | 12,000 | 调度器**一步**里所有序列的 token 总数 | 装不下的请求**推到下一轮** |
| `--max-num-seqs` | 4 | 同时在跑的序列数（槽位） | 新请求**排队**等空槽 |

三者的作用域完全不同：第一个按**请求**算，第二个按**步**算，第三个按**槽**算。这就是为什么它们不能一起调大——它们不是同一个量纲上的三个刻度，而是三层嵌套的预算。

> 补充：这三个参数在 vLLM 里分别对应 `--max-model-len`、`--max-num-batched-tokens`、`--max-num-seqs`。视频里的 16K / 12K / 4 是一台小显存机器上的示例配置，换模型、换卡都要重算；本节只讲它们**各自管什么**，不推导数值该取多少。

## 二、`max_model_len`：单个请求的上下文天花板

视频先花了两分钟讲 KV Cache，因为第一个参数的作用对象就是它。

![每生成一个 token 就往 GPU 显存里存一对 Key / Value 向量，序列越长，KV Cache 越大，显存占用条一路涨到 100%](assets/三个旋钮各管一段预算：并发槽、每步%20token%20与单请求上下文，调大调小打的是不同的曲线/00069.webp)

[【跳转到 01:09】](https://www.youtube.com/watch?v=ycEQJIyZ2sU&t=69)

推理时，序列里每一个 token 都要在 GPU 显存里留一对 Key 向量和 Value 向量。序列从 10 个 token 长到 100 个、再到 1000 个，KV Cache 就**线性地**跟着长；而且这些向量一旦写进去，就要一直留到这个序列结束。视频把这件事称为 LLM 服务里的核心张力：**显存是有限的，KV Cache 却一直在长。**

`max_model_len` 就是给这条增长曲线加的天花板。它的定义是「单个请求的 prompt token 加上生成 token 的总数」：

![max_model_len 的判定：prompt token 加生成 token 必须小于等于它，1 / 16000 时放行](assets/三个旋钮各管一段预算：并发槽、每步%20token%20与单请求上下文，调大调小打的是不同的曲线/00084.webp)

[【跳转到 01:24】](https://www.youtube.com/watch?v=ycEQJIyZ2sU&t=84)

- 一个 10,000 token 的请求，落在 16K 以内 → **接受**。
- 一个 18,000 token 的请求 → 进度条冲过 16K 的红线 → **立刻拒绝**。

![18,000 token 超过 16K 上限，请求被拒绝](assets/三个旋钮各管一段预算：并发槽、每步%20token%20与单请求上下文，调大调小打的是不同的曲线/00134.webp)

[【跳转到 02:14】](https://www.youtube.com/watch?v=ycEQJIyZ2sU&t=134)

视频对这条规则的解释是：**它按序列给 KV Cache 的分配封了顶，从而防止单个请求吃掉全部显存、把其它请求饿死。**

这里有个容易混淆的点值得单独说清：`max_model_len` 是**准入检查**，不是**运行时限制**。它决定「这个请求能不能进来」，而不是「进来之后能跑多快」。所以它对延迟曲线的影响是**阶跃式**的——要么放行，要么 400 报错，中间没有渐变区。

## 三、`max_num_batched_tokens`：调度器一步的 token 预算

第二个参数换了量纲：它按**步**算，不按请求算。

视频给它的定义是「每次调度器迭代能处理的 token 总量」，并且明确说：**把它当成一个吞吐上限（throughput cap）。**

![max-num-batched-tokens 是每步的 token 预算：Seq A 装了 5,000，预算条走到 5,000 / 12,000](assets/三个旋钮各管一段预算：并发槽、每步%20token%20与单请求上下文，调大调小打的是不同的曲线/00234.webp)

[【跳转到 03:54】](https://www.youtube.com/watch?v=ycEQJIyZ2sU&t=234)

动画里的算例很清楚：预算是 12,000 token，队列里来了四段序列——A 5,000、B 4,000、C 3,000、D 2,000。

![预算装到 12,000 就满：A + B + C 正好 12,000，D 的 2,000 装不下，被推迟到下一轮迭代](assets/三个旋钮各管一段预算：并发槽、每步%20token%20与单请求上下文，调大调小打的是不同的曲线/00259.webp)

[【跳转到 04:19】](https://www.youtube.com/watch?v=ycEQJIyZ2sU&t=259)

A + B + C = 12,000，预算刚好用满；**D 装不下，被推迟到下一轮迭代。** 注意这不是「拒绝」，只是「晚一步」——D 还在队列里，下一轮会重新尝试。

这一段还藏着一个关键事实，视频在画面上用一句话点了出来：**`max-num-batched-tokens` 主要管的是 prefill；解码阶段每个序列每步只贡献 1 个 token。**

![prefill 一次算完整个 prompt 的所有 token、是计算受限；decode 一次只算一个 token、是访存受限](assets/三个旋钮各管一段预算：并发槽、每步%20token%20与单请求上下文，调大调小打的是不同的曲线/00209.webp)

[【跳转到 03:29】](https://www.youtube.com/watch?v=ycEQJIyZ2sU&t=209)

把两个阶段的资源画像并排放，就能看出这个参数为什么会变成「延迟旋钮」：

| | Prefill | Decode |
| --- | --- | --- |
| 一次算多少 token | prompt 的全部 token，并行 | 1 个 token |
| 瓶颈在哪 | GPU 计算（compute-bound） | 显存带宽（memory-bound） |
| 对应哪个延迟指标 | TTFT（首字延迟） | ITL / TPOT（每 token 时间） |

于是这个参数就有了两个方向的作用，而它们**互相冲突**：

- **调小**：每步装的 token 少，步长变短，正在解码的请求每步等待更短 → **ITL 更好**；但一个长 prompt 要分更多步才能算完 → 它自己的 **TTFT 变差**。
- **调大**：长 prompt 一步就能算完 → **TTFT 更好、吞吐更高**；但每步步长变长，正在解码的流式输出被拖慢 → **ITL 变差**。

视频在结尾的「Performance Tuning」小卡片上把这个方向写成了两行，可以当作口诀：

```
↓ max_num_batched_tokens  →  better ITL
↑ max_num_batched_tokens  →  better TTFT
↑ max_model_len           →  V0 behavior (still decode priority)
```

> 这个「汇率」的定量算例（预算 2,048、64 个解码请求、32K prompt 需要 17 步）见同小节的另一篇《chunk 预算是 TTFT 与 ITL 之间的汇率》，本文只保留方向。

## 四、`max_num_seqs`：同时在跑的序列槽位数

第三个参数最直观：**它就是 GPU 上的槽位（slot）数量。**

![max-num-seqs = 4：四个槽位，请求队列里排着六个请求](assets/三个旋钮各管一段预算：并发槽、每步%20token%20与单请求上下文，调大调小打的是不同的曲线/00309.webp)

[【跳转到 05:09】](https://www.youtube.com/watch?v=ycEQJIyZ2sU&t=309)

视频用静态批处理和连续批处理做对照，来说明这个槽位是怎么被复用的：

- **静态批处理**：四个槽位被请求 1–4 占满，请求 5、6 必须等**全部四个**都跑完才能进来。视频在画面上标了它的病根：`Wait for ALL to finish before accepting new requests → Head-of-line blocking`（队头阻塞）。一个「法国的首都是哪里」和一个「帮我起一个 Python web 服务」被绑在同一组里，短的那个跑完了也只能空等。
- **连续批处理**：槽位是**逐个释放**的。请求 2 一结束，槽位 2 立刻空出来，请求 5 下一步就填进去。

![连续批处理：请求 2 结束后槽位 2 立刻被请求 5 填上，不浪费 GPU 周期](assets/三个旋钮各管一段预算：并发槽、每步%20token%20与单请求上下文，调大调小打的是不同的曲线/00334.webp)

[【跳转到 05:34】](https://www.youtube.com/watch?v=ycEQJIyZ2sU&t=334)

所以 `max_num_seqs` 决定了「同一时刻最多有多少个请求在分享这台 GPU」：

- **调大**：更多请求挤进同一批，权重搬运被更多行摊薄 → **吞吐上升**；但每步要算的行数变多，每一步都变慢 → 每个请求的 **TPOT 变长**。
- **调小**：每个请求的 TPOT 更好看，但 GPU 上留着空槽，**吞吐浪费**。

视频对连续批处理的评价很克制：**「它大幅提升了负载下的吞吐」**——注意措辞，是吞吐，不是延迟。槽位复用解决的是「GPU 空转」，不解决「每个请求等多久」。

> 为什么 batch 变大能提升算力利用率、以及吞吐-TPOT 曲线为什么先平后陡，是 2.3.1 的内容；槽位数最终被显存容量卡住的那道墙是 2.3.2 的内容。本文只把 `max_num_seqs` 当成一个「并发上限」来用。

## 五、调度策略：显存满的时候，先牺牲谁

三个参数定完了「预算有多少」，还剩一个问题：**预算不够分的时候，调度器按什么顺序牺牲谁。** 这是视频里最容易被跳过、但对「按场景选参数」最关键的一段。

视频先讲默认策略：**FCFS（先到先服务）+ 显存满时抢占。**

![FCFS 的第一阶段：请求按到达顺序 A(0s)、B(1s)、C(2s) 排进队列，三个槽位都空着](assets/三个旋钮各管一段预算：并发槽、每步%20token%20与单请求上下文，调大调小打的是不同的曲线/00359.webp)

[【跳转到 05:59】](https://www.youtube.com/watch?v=ycEQJIyZ2sU&t=359)

A、B、C 依次进槽，三个请求同时算。随着解码推进，KV Cache 一路涨，直到 GPU 显存被填满。这时 FCFS 的规则是：**最老的请求留下，最新的请求被抢占**——也就是 C 被换出到 CPU（KV 数据暂停、让出显存），先让 A 跑完；A 结束后显存腾出来，C 再从 CPU 换回来继续。

然后是替代方案：**优先级调度。**

![优先级策略：显存满时抢占优先级最低的那个；X 优先级 1、Y 优先级 5、Z 优先级 3，于是 Z 被换出、X 先跑完](assets/三个旋钮各管一段预算：并发槽、每步%20token%20与单请求上下文，调大调小打的是不同的曲线/00434.webp)

[【跳转到 07:14】](https://www.youtube.com/watch?v=ycEQJIyZ2sU&t=434)

规则换成：**显存满时，优先级最低的那个被抢占。** 画面里 X 的优先级是 1、Y 是 5、Z 是 3，于是 Z 被换出，X 先跑完。视频给出的开关是 `policy: SchedulerPolicy = "priority"`。

这两种策略的差别，正好对上本节要区分的两类场景：

| 策略 | 谁被牺牲 | 适合谁 |
| --- | --- | --- |
| FCFS + 抢占（默认） | 最新到达的请求 | 批处理：请求之间没有轻重，先来先做最省心 |
| 优先级 | 优先级最低的请求 | 交互场景：付费用户/首屏请求不能被一个后台任务挤掉 |

> 抢占本身的机制（重算 vs 换出、KV 块回收）属于显存管理与调度章节，本节只把它当成「策略选项」。视频里画出的「KV Cache 100% 满」那一刻，是 2.3.2 讨论的显存容量墙在调度器里的表现。

## 六、chunked prefill：把一段不可切的预算变成可切的

三个参数都讲完之后，视频用一个真实失败案例把它们串了起来。

![失败案例：Qwen 3.5 Vision 处理视频，18,000 个视觉 token 加 12,000 个文本 token 共 30,000，同时撞穿 max_model_len 的 16K 和 max_num_batched_tokens 的 12K](assets/三个旋钮各管一段预算：并发槽、每步%20token%20与单请求上下文，调大调小打的是不同的曲线/00459.webp)

[【跳转到 07:59】](https://www.youtube.com/watch?v=ycEQJIyZ2sU&t=459)

一个多模态请求：18,000 个视觉 token + 12,000 个文本 token = 30,000 token。两道闸门依次把它拦下——先查 `max_model_len`（16K），超了；再查 `max_num_batched_tokens`（12K），也超了。视频的结论很直白：**这是配 Docker 或 VLM 服务时最常见的失败**，你必须事先知道「会来多少 token」和「一步能装多少 token」。

但真正麻烦的不是被拒绝的请求，而是**没被拒绝、却装不进一个 step 的长 prompt**。前面第三节已经说过：`max_num_batched_tokens` 是一步的预算，一个 30,000 token 的 prompt 如果整段塞进去，它就装不下；而如果为了让它装下把预算调到 30,000，那每一步都会变得极长，正在解码的所有请求一起卡住。

chunked prefill 就是为这件事准备的：**把长 prompt 切成预算大小的块，一步算一块。**

![chunked prefill：30K 的 prompt 切成 8 块（C1–C8），待解码的 D、E 排在前面优先处理](assets/三个旋钮各管一段预算：并发槽、每步%20token%20与单请求上下文，调大调小打的是不同的曲线/00484.webp)

[【跳转到 08:04】](https://www.youtube.com/watch?v=ycEQJIyZ2sU&t=484)

视频强调这是 **vLLM V1 的默认行为**：`decode 优先调度 + chunked prefill`。每一步的排法有固定顺序：

1. **先把所有待解码的请求排进去**，每个占 1 个 token；
2. **剩下的预算再排 prefill**；
3. **prefill 装不下就切一块刚好装得下的**。

![第一步：2,000 个 decode token 先占位，剩下 10,000 的预算分给 prefill 块](assets/三个旋钮各管一段预算：并发槽、每步%20token%20与单请求上下文，调大调小打的是不同的曲线/00509.webp)

[【跳转到 08:29】](https://www.youtube.com/watch?v=ycEQJIyZ2sU&t=509)

于是 30,000 token 的 prompt 被摊到多步里算完，而**每一步里解码都没停过**。视频总结了两个收益：

- **ITL 更好**：解码永远不会被 prefill 堵住；
- **GPU 利用率更高**：计算受限的 prefill 和访存受限的 decode 在同一步里共享同一批算力。

![八块全部算完：解码每一步都被优先处理，prefill 用剩余预算填满，右侧小卡片写着三个参数各自的调优方向](assets/三个旋钮各管一段预算：并发槽、每步%20token%20与单请求上下文，调大调小打的是不同的曲线/00559.webp)

[【跳转到 09:19】](https://www.youtube.com/watch?v=ycEQJIyZ2sU&t=559)

## 七、把三个旋钮的转向整理成一张表

视频最后那张「Performance Tuning」小卡片只给了两个方向。把它补全成一张完整的表，就是本节要的「按场景选参数」的查表依据——**每一行都写清「调大之后打的是哪条曲线、代价落在谁身上」**：

| 旋钮 | 调大之后 | 打到哪条曲线 | 代价落在谁身上 |
| --- | --- | --- | --- |
| `max_num_seqs` | 更多请求同时跑 | 吞吐 ↑ | 每个请求的 TPOT ↑（每步行数变多） |
| `max_num_batched_tokens` | 每步装更多 token | TTFT ↓、吞吐 ↑ | 正在解码的请求 ITL ↑（步长变长） |
| `max_model_len` | 允许更长的请求 | 准入率 ↑（长文档/多模态能进来） | 单序列 KV 上限 ↑，可容纳的并发序列 ↓ |
| chunk 块大小（≈ 预算） | 长 prompt 更快算完 | 长 prompt 的 TTFT ↓ | 混合流量下别人的 ITL ↑ |
| 抢占策略 → 优先级 | 高优请求先完成 | 高优请求的 P99 ↓ | 低优请求被换出/重算，尾部变差 |

而两类场景的取值方向，恰好在这张表上**互为镜像**：

| 旋钮 | 实时交互（低延迟优先） | 离线批处理（高吞吐优先） |
| --- | --- | --- |
| `max_num_seqs` | 压小，留出 TPOT 余量 | 拉满到显存允许的上限 |
| `max_num_batched_tokens` | 压小，保住 ITL | 放大，让长 prompt 一步算完 |
| `max_model_len` | 按产品真实上限设，别虚高 | 按语料最长样本设，尽量放宽 |
| 调度策略 | 优先级 + 抢占 | FCFS 即可 |
| 目标函数 | 在 TTFT/TPOT 达标前提下最大化并发 | 单位时间总 token 数最大，延迟只受超时约束 |

为什么方向会反过来？因为两个场景**优化的东西不是同一个**：交互场景里「人正在等」，延迟是硬约束、吞吐是目标；批处理场景里「没人在等」，吞吐是目标、延迟只是一个不能超时的松约束。同一个旋钮，在一种目标函数下是成本，在另一种目标函数下是收益。

> 两类场景的目标函数怎么写、容量怎么按 SLO 反推、同一集群里混跑怎么办，见同小节的另一篇《容量要按 SLO 下的吞吐和峰值流量算》。Goodput（满足 SLO 的吞吐）的定义见 2.2.2。

## 小结

- **三个参数是三段预算，不是三个开关。** `max_model_len` 按请求算（撞上就拒绝），`max_num_batched_tokens` 按步算（撞上就推到下一轮），`max_num_seqs` 按槽算（撞上就排队）。
- **`max_model_len` 是准入检查，不是运行时限制。** 它的作用是给单序列的 KV 分配封顶，防止一个请求吃掉全部显存；影响是阶跃式的（放行或 400），没有渐变区。
- **`max_num_batched_tokens` 主要管 prefill。** 解码阶段每序列每步只贡献 1 个 token，所以这个预算调小改善 ITL、调大改善 TTFT，两个方向互相冲突。
- **`max_num_seqs` 管槽位复用。** 连续批处理让槽位逐个释放、新请求立刻顶上，解决的是 GPU 空转，不是单请求延迟。
- **显存满时谁被牺牲，由调度策略决定。** FCFS 牺牲最新到达的，优先级策略牺牲优先级最低的——前者适合批处理，后者适合交互。
- **chunked prefill 把不可切的预算变成可切的。** 每步先排 decode（各 1 token），剩余预算切块喂 prefill，于是长 prompt 摊到多步、解码一步不停。
- **两类场景的取值互为镜像**，因为它们的延迟一个是硬约束、一个是松约束。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| `max_model_len` | 单请求的 prompt + 生成 token 总数上限；超出直接拒绝 |
| `max_num_batched_tokens` | 调度器一步能处理的 token 总数上限；主要约束 prefill |
| `max_num_seqs` | 同时在跑的序列数上限，即 GPU 上的并发槽位数 |
| 槽位（slot） | 一个正在跑的序列占的位置；连续批处理下逐请求释放 |
| 队头阻塞（head-of-line blocking） | 静态批处理要等整批跑完才收新请求，短请求被长请求拖住 |
| 抢占（preemption） | 显存不足时把某个请求的 KV 换出到 CPU（或丢弃重算），腾出空间 |
| FCFS | 先到先服务；默认策略，显存满时抢占最新到达的请求 |
| 优先级调度 | 显存满时抢占优先级最低的请求，用 `SchedulerPolicy="priority"` 开启 |
| chunked prefill | 把长 prompt 切成预算大小的块，一步算一块，与解码同批 |
| decode 优先调度 | 每步先排所有待解码请求（各 1 token），再用剩余预算排 prefill |
| prefill / decode | 一次并行算完整个 prompt（计算受限）/ 一次只算一个 token（访存受限） |
| 准入检查（admission） | 请求进来时的合法性判定，与运行时调度是两件事 |
