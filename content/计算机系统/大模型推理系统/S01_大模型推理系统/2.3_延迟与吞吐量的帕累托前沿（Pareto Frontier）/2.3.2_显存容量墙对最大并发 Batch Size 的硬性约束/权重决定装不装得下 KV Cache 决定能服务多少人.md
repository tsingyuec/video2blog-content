# 权重决定模型装不装得下，KV Cache 决定它能服务多少人

> 视频来源：[Why your GPU runs out of memory when the model fits](https://www.youtube.com/watch?v=jfaWOzANgeI)（YouTube · AI Lab）｜时长约 13 分钟
> 简要导读：这支视频只回答一个问题——模型明明装得下，为什么多来几个人就爆显存。它把答案压成一句话（权重决定能不能加载，KV Cache 决定能服务多少人），然后用一台真机器把「KV 池 → 最大并发」这条除法从头算到尾，包括 vLLM 拒绝启动、一个 flag 把并发翻倍、16 个请求挤爆缓存后只排队不崩溃。文中讲者没讲、由我补算或补背景的地方都标了「补充」。

## 本讲要解决的核心问题（SCQA）

**背景**：部署一个大模型，第一步永远是「装得下吗」。70B 用 BF16 要 141 GB，FP8 要 73 GB，NVFP4 只要 43 GB——算完这个数，模型能加载、第一个请求也正常，很多人就认为部署完成了。

**冲突**：然后多几个人开始用，GPU 就 OOM 了。**模型明明装得下。** 更让人困惑的是，把权重从 BF16 压到 FP8 省下 68 GB，问题并没有消失，只是从「装不下」变成「装得下但服务不了几个人」。

**疑问**：显存到底被谁吃了？「能服务多少人」这个数能不能提前算出来，而不是等用户来告诉你？

**回答（中心思想）**：**权重是一次性成本，付一次就完了；KV Cache 是「每个用户 × 每个 token」的成本，跑光的永远是这一部分。** 所以「能服务多少人」不是玄学，而是一条除法：把 KV 池的字节数除以单请求的 KV 字节数。vLLM 启动日志里那行 `Maximum concurrency` 就是这条除法的结果——它是这张卡真正的容量上限，比任何吞吐数字都更该先看。

## 一、显存里住着四个房客，大多数人只数了一个

视频开头把 GPU 显存里的东西分成四类：

| 房客 | 是什么 | 随什么增长 |
| --- | --- | --- |
| 权重 weights | 模型本身，一堆数字 | 参数量 × 每参数字节，**固定** |
| KV Cache | 模型对每段对话的记忆 | 用户数 × token 数，**持续增长** |
| 激活值 activations | 正在算的数学要用的草稿纸 | 当前 batch 的形状，波动 |
| 运行时 runtime | CUDA、推理引擎、通信缓冲 | 基本固定，但会被忽略 |

**大多数人的容量规划只算了第一项。** 这就是「模型装得下却跑爆」的全部秘密：前三项里只有第一项是固定的，第二项随用户数线性增长，而它恰恰是最容易被漏掉的那一项。

### 1.1 权重：一道乘法，算完就定了

权重的算法最简单：每个参数是一个数，每个数占若干字节。

![Llama 3.3 70B 在 BF16 下：70,553,706,496 个参数 × 2 字节 = 141 GB，超过 128 GB 的天花板](assets/权重决定装不装得下%20KV%20Cache%20决定能服务多少人/00169.webp)

[【跳转到 02:49】](https://www.youtube.com/watch?v=jfaWOzANgeI&t=169)

视频给的经验法则是：**16 位精度下，X 十亿参数的模型约需 2X GB**。Llama 3.3 70B 在 BF16 下是 141 GB，而他那台 DGX Spark 只有 128 GB，其中 GPU 实际只能拿到约 122 GB，其余归系统。

于是量化登场：FP8 每参数 1 字节，73 GB；NVIDIA 的 NVFP4 约 43 GB。视频还纠正了一个常见误解——**4 位并不真是 4 位**：每 16 个数值共享一个 8 位的小 scale，实际约合每数值 4.5 位。

这一段的价值不在数字，而在它给出的那个判断：**权重的账是「一次性」的，算完就结束了**。它决定的是「能不能装下」，不是「能服务多少人」。

### 1.2 统一内存的坑：你连「总显存」这个数都不一定有

视频插了一段很实用的提醒。数据中心 GPU（比如 H100）的显存就堆在芯片旁边，`nvidia-smi` 一看就清楚。但他那台 DGX Spark 是 128 GB 统一内存，CPU 和 GPU 共用同一个池子——于是操作系统、浏览器、桌面环境全都住在里面。

![在统一内存机器上跑 nvidia-smi，显存那一列直接显示 Not Supported，只能从进程列表里看谁在占](assets/权重决定装不装得下%20KV%20Cache%20决定能服务多少人/00119.webp)

[【跳转到 01:59】](https://www.youtube.com/watch?v=jfaWOzANgeI&t=119)

截图里那一列 `Not Supported` 不是故障：NVIDIA 文档说这是预期行为，因为没有独立的显存可报。**于是「总显存」这个减法的起点本身就是不确定的**——你必须从进程列表里逐项看谁在占：Xorg 107 MiB、gnome-shell 50 MiB、firefox 432 MiB、VLLM::EngineCore 31890 MiB。

> **补充**：这解释了一个常见的部署事故——在统一内存机器上把 `gpu_memory_utilization` 开到 0.95，权重加载正常、KV 池也切出来了，然后某个后台进程一涨，整机开始 swap，推理延迟从毫秒级掉到秒级。视频后面把这条列为第六个处置手段：统一内存机器上，别把整块内存都交给模型。

## 二、KV Cache：每个 token、每个用户都要付一次

### 2.1 为什么会有这块缓存

模型写答案是一个 token 一个 token 写的。每写一个新 token，它都要回头看前面所有的 token——你的整个 prompt 加上它已经写出来的全部内容。每一层都要为每个历史 token 留两个向量：一个 key、一个 value。

模型当然可以为每个新 token 重算所有这些 key 和 value，但那慢得离谱（这正是 1.2.2 讲的「权重重复搬运」的另一面）。所以它把它们留着：**你发的每个 token、它写的每个 token，都在每一层留下一个小包**。这就是缓存。

### 2.2 公式：五个因子，一个乘法

![KV Cache 每 token 的字节数：2（key 和 value）× 层数 × KV 头数 × 每头维度 × 每元素字节](assets/权重决定装不装得下%20KV%20Cache%20决定能服务多少人/00309.webp)

[【跳转到 05:09】](https://www.youtube.com/watch?v=jfaWOzANgeI&t=309)

$$
\text{bytes/token} = 2 \times L \times H_{kv} \times d_{\text{head}} \times b
$$

代入 Llama 3.3 70B：$2 \times 80 \times 8 \times 128 \times 2 = 320$ KiB/token。注意这里的 8 是 **KV 头数**，不是注意力头数——GQA 让多个查询头共享一组 KV 头，这一项直接决定了缓存的大小。这也是为什么 1.3.2 的公式在这里可以直接拿来当输入：**它已经是「每 token」的单位，乘上序列长度就是「每请求」。**

### 2.3 它随每个 token 增长，而且增长得很快

320 KiB 听起来不多。但视频把它乘上几个典型长度，画成三根柱子：

![同一个模型：8k 上下文 2.5 GiB、32k 上下文 10 GiB、128k 上下文 40 GiB](assets/权重决定装不装得下%20KV%20Cache%20决定能服务多少人/00333.webp)

[【跳转到 05:33】](https://www.youtube.com/watch?v=jfaWOzANgeI&t=333)

- 8,000 token 的对话：2.5 GiB
- 32,000 token：10 GiB
- 128,000 token（模型的完整上下文）：**40 GiB，而这只是一个用户**

把这三根柱子和第一节的权重放在一起，问题就浮出来了：

![模型装得下（FP8 权重 66 GiB），装不下的是对话——天花板是 121.69 GiB](assets/权重决定装不装得下%20KV%20Cache%20决定能服务多少人/00351.webp)

[【跳转到 05:51】](https://www.youtube.com/watch?v=jfaWOzANgeI&t=351)

视频的设定是：模型留在 FP8 的 73 GB，缓存也用 FP8，于是一段长对话 20 GB。在 121.69 GiB 的天花板下，满上下文只够约 2.5 个用户，**第三个就装不下了**。幻灯片标题写得很准：*The model fit. The conversations didn't.*

**这就是容量墙的第一次显形**：分母（每请求 20 GB）太大，分子（剩下的 40 多 GB）太小，除法结果小于 3。

## 三、把容量变成并发：真服务器上的四个数字

前面都是纸面计算。视频接着在一台真机器上起了一个 vLLM 服务（Qwen 3 8B，模型小一点方便看清每一步），并让你盯住启动日志里的四行：

![启动日志四行：权重 15.27 GiB、可用 KV 18.96 GiB、KV 池 138,016 token、对 32,768 token 请求最大并发 4.21x](assets/权重决定装不装得下%20KV%20Cache%20决定能服务多少人/00443.webp)

[【跳转到 07:23】](https://www.youtube.com/watch?v=jfaWOzANgeI&t=443)

```
bash serve.sh --gpu-memory-utilization 0.3 --max-model-len 32768
Model loading took 15.27 GiB memory and 85.595764 seconds
Available KV cache memory: 18.96 GiB
GPU KV cache size: 138,016 tokens, Maximum concurrency for 32,768 tokens per request: 4.21x
```

这四行正好对应第一节那道减法的每一步：

| 日志行 | 对应算式里的哪一项 |
| --- | --- |
| Model loading took 15.27 GiB | $M_{\text{weights}}$ |
| Available KV cache memory: 18.96 GiB | 减去权重与工作内存后剩下的分子 |
| GPU KV cache size: 138,016 tokens | 分子换算成 token 单位 |
| Maximum concurrency: 4.21x | 分子 ÷ 分母（32,768 token/请求） |

**4.21 就是这条除法的答案**：这台服务器一次能装下 4 个满长度对话，第 5 个装不下。视频的原话是：*That's the number to check.*

### 3.1 自己验算一遍，确认这不是魔法

视频做了一件很值得学的事：用手算核对引擎打印的数字。Qwen 3 8B 有 36 层、8 个 KV 头，按公式：

$$
2 \times 36 \times 8 \times 128 \times 2\ \text{bytes} = 147{,}456\ \text{bytes} \approx 144\ \text{KiB/token}
$$

用池子总量除以它：$138{,}016 \times 144\ \text{KiB} \approx 18.9\ \text{GiB}$，几乎正好等于日志里的 `Available KV cache memory: 18.96 GiB`。

**同一套数学，在真服务器上对得上。** 这一步的意义在于：从此以后你不必相信任何人的经验值，你可以自己拿模型的 `config.json` 算出每 token 字节数，再拿日志里的池子大小验证。

### 3.2 顺带看清 `gpu_memory_utilization` 的作用

这次启动只给了 `--gpu-memory-utilization 0.3`。视频的描述是：**vLLM 量了一下剩下多少，把约 19 GB 给了 KV Cache**。也就是说这个参数不直接等于「KV 池大小」，它是「引擎被允许用的上限」，真正切给 KV 的是「上限 − 权重 − 工作内存 − 预留」之后剩下的部分。

所以调这个参数有一个反直觉的后果：**它调大，KV 池变大、并发变多；但它同时压缩了运行时自己的余量**。这也是为什么它不该开到 1.0——不是保守，而是那条减法里还有几个你控制不了的项。

## 四、装不下的另一种表现：引擎直接拒绝启动

容量墙不只在运行时出现，它还会在启动时就把你拦住。视频把池子压到 4 GB，同时要求模型完整的 40,000 token 上下文：

![vLLM 拒绝启动：一段 40,960 token 的请求需要 5.62 GiB KV，而可用只有 4.0 GiB，并给出「最长约 29104」](assets/权重决定装不装得下%20KV%20Cache%20决定能服务多少人/00498.webp)

[【跳转到 08:18】](https://www.youtube.com/watch?v=jfaWOzANgeI&t=498)

报错信息本身就是一道除法，而且信息量极大：

- 它先说清冲突：**要服务至少一个请求，需要 5.62 GiB KV，而可用只有 4.0 GiB**；
- 它给出可行解：**按现有显存，最长上下文约 29104**；
- 它给出两条出路：调大 `gpu_memory_utilization`，或者调小 `max_model_len`。

注意一个细节：**权重加载得好好的**（`Model loading took 15.27 GiB`），失败的只有缓存。这正是本节的核心判断在工程上的具体表现——**「装得下」和「服务得了」是两件事，前者由权重决定，后者由缓存决定。**

> **补充**：这个「启动即失败」其实是一种幸运。它把容量问题暴露在部署阶段，而不是等线上流量上来才暴露。真正危险的是那些「刚好能启动」的配置——它们能起来，但并发只有 1 或 2，一有并发就排队。所以看到 `Maximum concurrency` 小于你的预期并发时，应该把它当成一次启动失败来处理。

## 五、一个 flag 换两倍用户：KV 量化

容量墙的除法只有三个输入，所以最省力的缓解手段就是动分母：**把每个 KV 元素的字节数从 2 降到 1**。

![同一个池子、同一个模型，只加 --kv-cache-dtype fp8：KV 池从 138,016 token 涨到 282,864 token，最大并发从 4.21x 变成 8.63x](assets/权重决定装不装得下%20KV%20Cache%20决定能服务多少人/00531.webp)

[【跳转到 08:51】](https://www.youtube.com/watch?v=jfaWOzANgeI&t=531)

```
bash serve.sh --gpu-memory-utilization 0.3 --max-model-len 32768 --kv-cache-dtype fp8
Available KV cache memory: 19.42 GiB
GPU KV cache size: 282,864 tokens, Maximum concurrency for 32,768 tokens per request: 8.63x
```

对比一下：可用显存几乎没变（18.96 → 19.42 GiB），但 KV 池的 token 容量翻倍（138,016 → 282,864），最大并发从 4.21 变成 8.63。**一个 flag，两倍用户。**

这就是「分母减半」的威力：它不改模型、不改硬件、不改上下文长度，只改每个数占几个字节。视频的提醒也很到位：**它可能损失一点精度，所以先在自己的 prompt 上验一遍答案。** 这句话是必须的——容量换来的用户数，如果换来的是答错，那就是负收益。

## 六、撞墙之后：不是崩溃，是排队

现在把负载加上去。视频一次发了 16 个长请求（每个约 20,000 token），然后盯住四个计数：running、waiting、KV cache 使用率、preempted。

![16 个请求同时打进来：running 缓慢上升、waiting 从 15 降下来、KV cache 使用率持续爬升、preempted 一直是 0](assets/权重决定装不装得下%20KV%20Cache%20决定能服务多少人/00566.webp)

[【跳转到 09:26】](https://www.youtube.com/watch?v=jfaWOzANgeI&t=566)

视频对这段的总结非常关键：

> **KV Cache 那一列爬到 87% 就停住了。vLLM 只跑 6 个请求，因为第 7 个塞不进缓存，另外 10 个排队。每完成一个，下一个就拿到内存。什么都没崩，只是变慢了。这就是生产环境里「KV Cache 用光」通常的样子：不是崩溃，是排队。**

这段话值得逐句拆开：

1. **使用率停在一个小于 100% 的位置**。这是分块分配的特征——池子是离散的块，剩下的零头不够一个请求用，于是使用率卡在 87% 而不是 100%。**「KV 使用率 87%」不等于「还有 13% 的余量可用」**，它可能意味着「再也塞不进一个请求了」。
2. **在跑的数量由容量决定，不由 `max_num_seqs` 决定**。即使你把并发上限设得很大，池子装不下就是装不下。
3. **排队而不是崩溃**。新请求不会失败，只是等；每完成一个就补一个进来。**用户感知到的不是错误，是首字越来越慢。**
4. **preempted 一直是 0**。这一点很重要：这次压测里引擎靠「不放进来的」就够了，还没到需要「把已经在跑的踢出去」的地步。

> **补充**：第 4 点说明「排队」和「抢占」是容量墙的两级响应。当等待队列还能吸收压力时，引擎只排队；当已经在跑的请求也需要新块而没有空闲块时，才会触发抢占（把某个请求的 KV 释放、之后重算）。抢占的代价比排队大得多——排队只是让新来的等，抢占是让已经在跑的人**倒退**。抢占的触发条件与代价，见本节的另一篇[《显存容量墙把最大并发变成一道除法》](显存容量墙把最大并发变成一道除法.md)第四节。

## 七、模型设计决定缓存需求：同样大小，差 8 倍

视频里最反直觉的一段，是它拿自己每天在跑的服务举例：一个 270 亿参数的 Qwen 模型，缓存超过一百万 token，够 4.3 段每段 25 万 token 的对话。

![Qwen3.8-27B-NVFP4：KV 池 1,132,052 token，对 262,144 token 的请求仍有 4.32x](assets/权重决定装不装得下%20KV%20Cache%20决定能服务多少人/00577.webp)

[【跳转到 09:37】](https://www.youtube.com/watch?v=jfaWOzANgeI&t=577)

它能做到这点，是因为 **64 层里只有 16 层保留完整缓存**。幻灯片标题就是结论：*Design matters: 16 of 64 layers.*

把两个模型并排放，差距更明显：

![Llama 3.3 70B 每 token 320 KiB，Qwen3.8-27B 每 token 约 37 KiB](assets/权重决定装不装得下%20KV%20Cache%20决定能服务多少人/00699.webp)

[【跳转到 11:39】](https://www.youtube.com/watch?v=jfaWOzANgeI&t=699)

- Llama 3.3 70B：**320 KiB/token**（80 层、8 个 KV 头）
- Qwen3.8-27B：**约 37 KiB/token**

差了将近 9 倍。视频的结论是：**同样大小的两个模型，需要的缓存可以差很多；更少的 KV 头、更少的完整注意力层，意味着同样的硬件能装更多用户。**

这条结论对容量规划的含义是：**「选模型」本身就是一次容量决策**。你按参数量选模型，是在算「装不装得下」；你按 bytes/token 选模型，才是在算「能服务多少人」。

## 八、处置顺序：先做便宜的，再做贵的

视频最后给了一个明确的六步顺序，从「最省事、收益最大」到「最麻烦」：

![量化权重：权重那一块缩小，空出来的显存直接被 KV Cache 吃掉](assets/权重决定装不装得下%20KV%20Cache%20决定能服务多少人/00611.webp)

[【跳转到 10:11】](https://www.youtube.com/watch?v=jfaWOzANgeI&t=611)

1. **量化权重**：BF16 → FP8 减半，NVFP4 减到三分之一以下。**省下的每一 GB 都直接变成缓存**——因为那条减法里权重和 KV 池争的是同一块显存。
2. **KV Cache 存成 FP8**：你刚看到一个 flag 就把用户数翻倍。代价是精度，先在自己 prompt 上验答案。
3. **限制每个用户能要多少**：没人真的需要 128k 就把 `max_model_len` 设成他们真正需要的长度；`max_num_seqs`（同时跑的请求数）同理。视频的原话是：**缓存是按每用户每 token 算的，这两个 flag 就是你的预算。**
4. **用会给缓存分页的服务器**：老式服务器为每个请求预留一整块、按它可能给出的最长答案来留，vLLM 团队测过其中 **60%~80% 是浪费的**；PagedAttention 按需分发小块，把浪费压到 **4% 以下**。
5. **按缓存挑模型**：看 KV 头数与完整注意力层数，而不是只看参数量。
6. **统一内存机器上留余量**：操作系统住在同一块内存里，别把它全交给模型。

这六步的顺序不是随意的：前两步改的是「分子」（省显存、降分母），第三步改的是「分母的业务定义」，第四步改的是「分子的可用比例」，第五步在选型阶段就把除法算好，第六步是防止减法里的项失控。**它们合起来就是一句话：容量问题要在四个不同的层面各解决一部分，没有单点银弹。**

---

## 小结

- **显存里有四个房客**：权重、KV Cache、激活值、运行时。大多数人只算了第一个，而跑光的永远是第二个。
- **权重是一次性成本，KV Cache 是每用户每 token 的成本**。前者决定「装不装得下」，后者决定「能服务多少人」。
- **每 token KV 字节数 = 2 × 层数 × KV 头数 × 头维度 × 字节数**。Llama 3.3 70B 是 320 KiB/token，8k 上下文 2.5 GiB、32k 是 10 GiB、128k 是 40 GiB。
- **最大并发就是一条除法**：KV 池 token 数 ÷ 每请求 token 数。日志里的 `Maximum concurrency for N tokens per request` 就是它。
- **装不下有两种表现**：启动时直接拒绝（并给出可行的最长上下文），或者运行时排队（KV 使用率卡住、新请求等）。
- **KV 量化是最便宜的翻倍手段**：`--kv-cache-dtype fp8` 让池子从 138,016 token 涨到 282,864，并发从 4.21 到 8.63，代价是精度。
- **模型设计决定缓存需求**：Llama 3.3 70B 的 320 KiB/token 与 Qwen3.8-27B 的约 37 KiB/token 差了近 9 倍，64 层里只有 16 层留完整缓存是关键。
- **处置有顺序**：量化权重 → FP8 缓存 → 限制长度与并发 → 分页 → 按缓存选模型 → 统一内存留余量。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| KV Cache | 每个请求在每一层为历史 token 保留的 key/value 向量，是模型对这段对话的记忆 |
| bytes/token | 每多一个 token 需要多占的缓存字节数，由层数、KV 头数、头维度、精度决定 |
| KV 池 | 显存里专门留给 KV Cache 的那一块，等于总显存减去权重、工作内存与预留 |
| Maximum concurrency | vLLM 启动日志里按「每请求 N token」算出的最大并发数，就是容量墙的位置 |
| gpu_memory_utilization | 引擎被允许使用的显存比例；它不等于 KV 池大小，只是减法的起点 |
| max_model_len | 单个请求 prompt + 输出的 token 上限，直接决定分母 |
| max_num_seqs | 同时跑的请求数上限，受容量墙约束 |
| GQA | Grouped Query Attention，多个查询头共享一组 KV 头，直接减小 bytes/token |
| 分页 KV cache | 按需分配小块而不是按最长预留，把预留浪费从 60~80% 压到 4% 以下 |
| 统一内存 | CPU 与 GPU 共用同一块内存，操作系统也住在里面，必须留余量 |
| NVFP4 | NVIDIA 的 4 位权重格式，每 16 个值共享一个 8 位 scale，实际约 4.5 位/值 |
