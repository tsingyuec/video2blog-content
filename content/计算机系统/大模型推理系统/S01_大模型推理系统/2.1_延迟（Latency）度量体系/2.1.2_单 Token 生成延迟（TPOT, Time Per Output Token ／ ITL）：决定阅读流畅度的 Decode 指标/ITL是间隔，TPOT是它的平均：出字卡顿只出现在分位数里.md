# ITL 是间隔，TPOT 是它的平均：出字卡顿只出现在分位数里

> 视频来源：[【LLM 推理】TTFT vs ITL：推理体验的两个 SLO，优化路径完全不同](https://www.bilibili.com/video/BV1VxgR6gEmj/)（Bilibili · UP 主「古希腊掌管代码的神」）｜时长约 4 分 55 秒
> 简要导读：这支短片用两种「卡」的体验把 TTFT 与 ITL 分开，并给出两者的决定因素与优化路径。本文只取 decode 侧那一条线：ITL 与 TPOT 的口径差异、平均值如何藏住停顿、以及 decode 每步明明一样重却仍会抖。TTFT 的定义与测量见 2.1.1，端到端分解见 2.1.3，阅读速度阈值与产品形态 SLO 见同小节另一篇。视频里的 ASR 把 prefill 写成「preview」、KV Cache 写成「kvcash」，本文已订正。

## 本讲要解决的核心问题（SCQA）

**背景**：大模型「卡」有两种完全不同的卡法。第一种：转圈两秒没反应，然后答案哗一下全涌出来。第二种：秒出第一个字，但后面一个字一个字往外蹦，像老头打字。

**冲突**：这两种卡对应两个不同的指标——前者是 **TTFT（Time To First Token，首字延迟）**，后者是 **ITL（Inter-Token Latency，token 间隔）**。可一旦落到工程上，这两个名字就开始打架：视频里直接说「ITL，也叫 TPOT」，而总时延公式又写成 $\text{TTFT} + (N-1) \times \text{ITL}$——**一个被当成间隔的量，却被拿去乘 token 数**。这说明大家口中的 ITL 有时指「某一个间隔」，有时指「所有间隔的平均」。混着用，报出来的数字就没法比。

**疑问**：ITL 和 TPOT 到底是不是同一个数？如果平均出字速度已经达标，用户为什么还是觉得卡？decode 每一步做的工作明明一样重，间隔为什么会抖？

**回答（中心思想）**：**ITL 是一个个间隔（一个请求里有几百个），TPOT 是这些间隔的平均值**；平均值会稀释尾部事件，所以一次长停顿在均值上几乎看不见、在 P90/P99 与最大间隔上刺眼。而抖动不是 decode 自己变了，是**每一步的组成变了**——batch 里挤进了别人的 prefill、batch 变大了、或者调度器做了别的选择。

## 一、一个请求的生命周期里，TTFT 是一个括号，ITL 是几百个括号

### 1.1 两个阶段，两个指标

视频把请求的生命周期压成两步：

1. **Prefill（预填充）**：把整段 prompt 一次性过完，把 KV Cache 都算好。这一段花的时间，就是第一个 token 出现之前的等待，即 **TTFT**。
2. **Decode（解码）**：一个 token 一个 token 地往外蹦。**相邻两个 token 之间的间隔**，就是 **ITL**。

一句话分工：**TTFT 决定「等不等得住」，ITL 决定「看得爽不爽」。**

![生命周期：prefill 之后是首 token，TTFT 到此刻结束；之后每蹦一个 token 就是一个 ITL](assets/ITL是间隔，TPOT是它的平均：出字卡顿只出现在分位数里/00040.webp)

### 1.2 顺手订正一处：$N$ 个 token 只有 $N-1$ 个间隔

视频同一支片子里出现了两个版本的公式：开头那页写 $\text{TTFT} + N \times \text{ITL}$，后面几页写 $\text{TTFT} + (N-1) \times \text{ITL}$。**正确的是后者**：$N$ 个 token 之间只有 $N-1$ 个空隙，第一个 token 之前的那段等待已经被 TTFT 收走了，不能再算一次。

这个订正不是吹毛求疵。分母差一，在短回答上就是百分之几的系统性偏差，而短回答恰好是聊天机器人的主场景。

## 二、ITL 与 TPOT 不是同一个数

### 2.1 视频里的混用，全行业都在混用

视频在生命周期那页给 ITL 加了一个括号注释：**「相邻 token 间隔（也叫 TPOT）」**。这句话在口语里没问题，但在指标口径上是把两个东西合并了：

- **ITL** 是**一个间隔**：$t_i - t_{i-1}$。一个 300 token 的回答有 299 个 ITL 观测值。
- **TPOT（Time Per Output Token）** 是**这些间隔的平均**：一个请求一个数。

为什么大家会混？因为**单用户、无干扰时两者几乎相等**：如果每一步都花 30 毫秒，那每个间隔都是 30 毫秒，平均值当然也是 30 毫秒。混用在「一切正常」的时候不会出错——**只有在出问题的时候才会露馅**，而那正是你最需要指标准确的时候。

### 2.2 把定义写清楚

$$
\text{ITL}_i = t_i - t_{i-1}, \qquad i = 2, 3, \dots, N
$$

$$
\text{TPOT} = \frac{1}{N-1}\sum_{i=2}^{N} \text{ITL}_i = \frac{t_N - t_1}{N-1}
$$

两行式子是等价的，但**它们携带的信息量完全不同**：第二行把 $N-1$ 个数压成了一个数。压的过程丢掉了什么？丢掉了「这些间隔是不是一样长」。

### 2.3 总时延公式其实偷偷用了平均值

视频给的「黄金法则」是：

$$
T_{\text{total}} = \text{TTFT} + (N_{\text{out}} - 1) \times \text{ITL}
$$

这个式子**只有在所有间隔都相等时才严格成立**。一般的写法应该是把间隔一个个加起来：

$$
T_{\text{total}} = \text{TTFT} + \sum_{i=2}^{N_{\text{out}}} \text{ITL}_i
$$

而 $\sum \text{ITL}_i = (N-1) \times \text{TPOT}$，所以那个「黄金法则」里被乘上去的 **ITL，其实是 TPOT**。这不是文字游戏：**平均值的所有毛病，都会顺着这个公式传进你对总时延的估计里。**

![黄金法则：总时延 = TTFT + (N-1) × ITL；被乘上去的那个 ITL，其实是平均值](assets/ITL是间隔，TPOT是它的平均：出字卡顿只出现在分位数里/00160.webp)

## 三、平均值会把停顿稀释掉

### 3.1 一个 50 毫秒的均值，可以藏住一次 800 毫秒

视频给的工程铁律是：**人类阅读的舒适速度大约每秒 20~30 个 token，所以 ITL 压到 50 毫秒以下，用户就感觉「比我读得快」**。

现在做一个**补充**的算术（不是视频原话，但只用它给的 50 毫秒这个数）：假设一个回答 50 个 token，其中**有一次 800 毫秒的停顿**，其余 49 个间隔都是 34.7 毫秒。

$$
\text{TPOT} = \frac{800 + 49 \times 34.7}{50} = \frac{800 + 1700}{50} = 50\ \text{ms}
$$

**平均值正好是 50 毫秒——完全达标。** 而用户的真实体验是：读到一半，屏幕冻了 0.8 秒。

这就是平均值的全部职责：**把一次性的长等待摊到所有 token 上**。摊得越薄，指标越好看，用户越难受。

### 3.2 所以要报的不是一个数，是一组数

工程上正确的报法是把分布的形状也报出来（**补充**，业界通行做法）：

| 统计量 | 它回答什么 | 典型用途 |
| --- | --- | --- |
| 平均 / P50 TPOT | 整体出字节奏 | 容量规划、每 token 成本 |
| **P90 ITL** | 每十个间隔里最慢的那个有多慢 | 体感是否「偶尔一顿」 |
| **P99 ITL** | 最慢的 1% 有多慢 | 卡顿告警的主指标 |
| **最大间隔（max ITL）** | 这个请求最难受的一下有多长 | 单请求复盘、badcase 归因 |

只报均值，等于只报「平均气温」——它不会告诉你今天有没有下冰雹。

### 3.3 视频给的 SLO 是均值口径，必须补一条分位口径

视频按场景列了一组 SLO，很实用：

| 场景 | TTFT SLO | ITL SLO | 关键工程 |
| --- | --- | --- | --- |
| Chatbot 聊天 | < 500 ms | < 50 ms | 短问答多看 TTFT |
| RAG 检索增强 | < 2 s | < 50 ms | Prompt Cache 救命 |
| 长文档摘要 | < 3 s | < 60 ms | PD 分离 + 长 prefill |
| Agent 多步 | < 800 ms | < 50 ms | TTFT 随 N 步累加 |

![四种典型场景的 SLO 侧重：Chatbot / RAG / 长文档摘要 / Agent 多步](assets/ITL是间隔，TPOT是它的平均：出字卡顿只出现在分位数里/00220.webp)

这张表有个共同点：**「ITL < 50 ms」全部是均值口径的写法**。按 3.1 的算术，一个均值 50 毫秒、但中间冻过 0.8 秒的服务，可以完美满足这一列。

所以落地时要把它写成一对数（**补充**）：**均值（或 P50）达标 + P99 不超过某个上限**，例如「TPOT ≤ 50 ms 且 P99 ITL ≤ 200 ms」。前者保证整体节奏，后者保证不出现用户能明确感知的停顿。

## 四、decode 每步近似恒定，为什么还会抖

### 4.1 基线：每一步都要把整个模型权重搬一遍

视频对 ITL 的决定因素只给了一句话，但这句话很硬：

> **Decode 是 memory-bandwidth-bound：每生成 1 个 token，整个模型权重都得从 HBM 搬一遍——瓶颈在带宽，不在算力。**

它还画了一条自回归链：$t_1 \to t_2 \to \dots \to t_8$，每一步下面标注「**每一步 = 一次完整 forward = 一次权重搬运**」。

这就是「每步时间近似恒定」的物理来源：**权重总量不变**，所以每步的搬运量不变，每步的耗时也就在一个稳定水平附近。视频顺手给了两个换算：

$$
\text{TPS}_{\text{单用户}} = \frac{1}{\text{ITL}}, \qquad \text{系统吞吐} = \text{batch\_size} \times \frac{1}{\text{ITL}}
$$

![ITL 就是 decode 每步的耗时：每步都要把全部权重从 HBM 搬一遍，瓶颈在带宽](assets/ITL是间隔，TPOT是它的平均：出字卡顿只出现在分位数里/00120.webp)

（权重搬运的量化推导见 1.2.2，把「带宽 ÷ 模型字节数」算成一个具体毫秒数的做法见同小节另一篇。）

### 4.2 抖动来源一：batch 里挤进了别人的 prefill

既然每步的搬运量恒定，抖动就只能来自「**某几步的组成变了**」。最典型的一种：**别人的长 prompt 挤进了同一个 batch**。

视频在 TTFT 的优化手段里提到了这件事：**Chunked Prefill，把超长 prompt 切成小块，和 decode 混着跑，避免长 prompt 阻塞别的请求。**

反过来读这句话，就得到了 ITL 抖动的机制：

- **不切块**：一个长 prompt 一次性 prefill，所有正在 decode 的流**整段冻住**——那是一个几倍于正常间隔的尖峰，用户明确感到「卡了」。
- **切块（chunked prefill）**：长 prompt 的工作被切成小块，摊到很多步里，**尖峰被削平**；代价是**每一步都稍微变重**，整体 ITL 抬高一点。

一句话：**chunked prefill 用「普遍略慢」换掉「偶发极慢」。** 对阅读体验来说这通常划算，因为人对一次 0.8 秒的停顿，比对整体慢 20% 敏感得多。（调度算法本身归 3.2。）

![Chunked Prefill：把长 prompt 切成小块与 decode 混跑，避免长 prompt 阻塞别的请求](assets/ITL是间隔，TPOT是它的平均：出字卡顿只出现在分位数里/00080.webp)

### 4.3 抖动来源二：continuous batching 让每步变重

视频列的第二个手段是 **Continuous Batching：把多个请求的 decode 步合并跑，摊薄权重搬运的成本**。

「摊薄成本」是站在**系统吞吐**的角度说的：一次权重搬运服务了更多用户，单位 token 的搬运成本下降。但站在**单个用户**的角度，同一件事的读法是：**这一步要算的 token 变多了，所以这一步变慢了。**

于是 batch 大小成了一个双向旋钮：

| batch 变大 | 系统吞吐 | 单用户 ITL |
| --- | --- | --- |
| 权重搬运被摊薄 | 上升 | — |
| 每步计算量上升 | — | 变差（间隔变长） |
| 新请求更容易插进来 | 上升 | 抖动变大 |

这也解释了视频那句「TPS 是单用户视角，系统吞吐还要乘以 batch size」为什么必须分开说：**这两个数经常朝相反方向走。**

### 4.4 量化、投机采样、换 GPU 改的是基线，不是抖动

视频剩下的两个手段是**量化（INT8 / FP8，权重量小一半，带宽压力立刻减半）**、**Speculative Decoding（小模型先猜几个 token，大模型一次性验证，减少大模型的 decode 步数）**，以及最直接的**换更好的 GPU（H100 的 HBM 带宽比 A100 高一截）**。

![ITL 的四个手段：Continuous Batching、投机采样、量化、更好的 GPU](assets/ITL是间隔，TPOT是它的平均：出字卡顿只出现在分位数里/00140.webp)

从「抖动」这个角度看，这四招的性质和 4.2/4.3 不同：

- **量化和换 GPU 降低的是基线**：每步搬的字节少了 / 带宽大了，整条 ITL 曲线整体下移，**分布形状基本不变**；
- **投机采样改变的是分布形状**：一次验证通过 $k$ 个草稿 token，它们在同一瞬间到达，于是间隔序列变成「长—短—短—短—长」——**均值可能变好，但单次间隔的方差变大**（算法细节归第 6 章）；
- **continuous batching 同时影响基线和抖动**：既摊薄成本，又让每步的组成随负载变化。

所以「ITL 降了」这句话必须问清楚：**是基线降了，还是尾巴降了？** 只降基线不降尾巴，用户仍然会在某些回答里遇到那一次长停顿。

## 五、短回答看 TTFT，长回答看 ITL

视频用三个算例把「哪个指标占大头」算得很清楚：

| 场景 | TTFT | ITL | 输出长度 | 总时延 |
| --- | --- | --- | --- | --- |
| Chatbot 短问答 | 300 ms | 30 ms | 50 | 1.77 s |
| RAG 检索问答 | 1.50 s | 40 ms | 200 | 9.46 s |
| 长文写作 | 800 ms | 50 ms | 1500 | 75.75 s |

![三个算例：短回答 TTFT 占大头，长回答 ITL 决定总时延](assets/ITL是间隔，TPOT是它的平均：出字卡顿只出现在分位数里/00200.webp)

读这张表要注意一件事：**它是用平均值算出来的**。长文写作那一行 75.75 秒，前提是 1500 个 token 每个都花 50 毫秒。如果中间有五次 1 秒的停顿，真实总时延还要再加 4.75 秒——**总时延的误差也来自尾部**。

由此得到两条判据：

- **短回答**（几十个 token）：TTFT 占大头，ITL 几乎无所谓——先把首字压下来；
- **长回答**（上千 token）：ITL 才是杀手，TTFT 那两秒在总长面前可以忽略——先把出字节奏稳住。

而「ITL 多少算够」这件事由人的阅读速度决定（约每秒 20–30 个 token，对应 50 毫秒以下），具体的阈值表与不同产品形态的目标值见同小节另一篇，这里不重复。

## 小结

- **两种卡，两个指标**：TTFT 管「等不等得住」，ITL 管「看得爽不爽」；$N$ 个 token 只有 $N-1$ 个间隔。
- **ITL 是一个间隔，TPOT 是这些间隔的平均**；视频里「ITL 也叫 TPOT」是行业普遍的混用，只在一切正常时不出错。
- **黄金法则 $\text{TTFT} + (N-1)\times\text{ITL}$ 里的 ITL 其实是 TPOT**，它假设所有间隔等长；一般形式是逐项求和。
- **平均值稀释尾部**：均值 50 毫秒可以藏住一次 800 毫秒；要报 P90 / P99 / 最大间隔，SLO 要写成「均值 + 分位」一对数。
- **decode 每步近似恒定**（每步搬一遍权重），抖动来自「这一步的组成变了」：别人的 prefill 挤进 batch、batch 变大、调度器做了别的选择。
- **chunked prefill 用「普遍略慢」换掉「偶发极慢」**；量化与换 GPU 降基线，投机采样改分布形状。
- **短回答看 TTFT，长回答看 ITL**；而且用平均值算出的总时延，本身也会低估尾部。

| 术语 | 一句话解释 |
| --- | --- |
| TTFT | 首字延迟，请求到第一个 token 出现的时间，由 prefill 决定 |
| ITL | token 间隔，相邻两个 token 之间的那一个空隙，一个请求有 $N-1$ 个 |
| TPOT | 每输出 token 时间，ITL 序列的平均值，一个请求一个数 |
| 均值稀释 | 把一次性的长等待摊到所有 token 上，让指标好看、体验变差 |

| Chunked Prefill | 把长 prompt 切成小块与 decode 混跑，削平 ITL 尖峰但整体略慢 |
| Continuous Batching | 把多个请求的 decode 步合并，摊薄权重搬运但让每步变重 |
| memory-bandwidth-bound | 每步耗时由「搬多少字节」而非「做多少运算」决定 |
