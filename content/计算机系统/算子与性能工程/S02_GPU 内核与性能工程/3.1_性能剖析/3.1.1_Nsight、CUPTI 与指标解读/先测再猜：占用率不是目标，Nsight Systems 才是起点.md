## 本讲要解决的核心问题（SCQA）

**背景**：你已经写出了正确运行的 CUDA 内核（这门课第三到第六部分干的就是这件事），也知道了那些「会让内核变慢」的候选原因：访存不合并、占用率低、共享内存 bank conflict……

**冲突**：麻烦在于，从「知道有哪些原因」到「知道这次是哪个原因」之间，隔着一个非常容易出错的环节——**猜测**。视频开篇就把这件事摆在台面上：一个内核跑得比你期望的慢，下一个念头通常是对原因的猜测，这个猜测感觉理所当然，但它经常是错的。而错一次，你就可能花一整天去优化一个本来就不是瓶颈的东西。

**疑问**：那怎么把猜测换成测量？一个内核慢，到底该先看什么？「占用率」这个人人都在提的指标，为什么不能当目标？整个程序里有五个 GPU 操作，怎么知道该深挖哪一个？

**回答（中心思想）**：**先宽后窄，先测再猜**。先用 **Nsight Systems** 看整条时间线，回答「哪一部分慢」，通常会发现一个操作占了主导；再用 **Nsight Compute** 深挖那一个内核，回答「它为什么慢」。而在这条路上必须先扔掉一个执念：**占用率是解释结果的工具，不是优化的目标**。视频的实测数据把这个执念打得粉碎——L4 上两个理论占用率都是 100% 的内核速度差 4.21 倍，而最快的手写内核实际占用率只有 18.50%。

## 二、案例：一个「一定是 DRAM 瓶颈」的猜测，错得很彻底

整章研究的内核是第八部分里的朴素矩阵乘：一个线程算一个输出元素，16×16 的 block，64×64 的网格，N=1024。在 L4 上它跑 **4.91 毫秒**，达到 **436.9 GFLOP/s**——只有那块机器实测 FP32 峰值的 **1.49%**。

慢得这么离谱，很自然就有猜测：

[【跳转到 03:29】](https://www.youtube.com/watch?v=kG1xr039u7I&t=209)

![被推翻的猜测：每个线程都要读一整行和一整列，所以内核一定在等 DRAM；它读了很多数据、又很慢，所以限制一定是 DRAM——这个推理让人很舒服，但在这里是错的](assets/先测再猜：占用率不是目标，Nsight%20Systems%20才是起点/00234.webp)

这个推理链条是：**每个线程读一整行 + 一整列 → 读了很多数据 → 内核很慢 → 所以 DRAM 是瓶颈**。每一步看起来都成立。

剖析器给出的数字是：

[【跳转到 03:54】](https://www.youtube.com/watch?v=kG1xr039u7I&t=234)

![剖析器实测：memory throughput 98.42%，DRAM throughput 0.44%——内存通路几乎满了，而 DRAM 几乎闲着](assets/先测再猜：占用率不是目标，Nsight%20Systems%20才是起点/00259.webp)

| 指标 | 值 |
| :--- | ---: |
| memory throughput | 98.42% |
| DRAM throughput | 0.44% |

**内存通路几乎满了，而显存芯片几乎闲着。**

这里的关键是认清这是**两行不同的指标**：

- `memory throughput` 是**芯片上最忙的那个内存单元**的活动水平。在这个内核里，那个单元是 **L1 的请求通路**（L1 request path）。
- `DRAM throughput` 是**真正出去到设备内存的那一趟**。

`memory throughput` 98.42% 说明 L1 请求通路快撑爆了；`DRAM throughput` 0.44% 说明数据其实没怎么从显存搬。所以「读得多所以等 DRAM」这个猜测，方向就错了——**瓶颈在请求的「形状」，不在 DRAM 能交付多少字节**。

再往下看一个更有诊断力的指标：**warp 为什么发不出指令**。在每条已发射指令的 **173.17 个 warp 周期**里，最大原因是 `LG Throttle`，占 **145.92 个周期（84.3%）**。

- `LG` 是 local 和 global 的缩写；
- `LG Throttle` 的意思是「那块内存工作的**队列**满了」；
- 于是 warp 在等的是「**发出请求**」这件事，而不是在等 DRAM 回应。

这个区分极其重要，因为两者的修法完全不同：等 DRAM 要减少数据量或提高复用；等请求队列要**改变请求的形状**（比如合并访存）。

## 三、占用率：一个比值，不是油门

7.2 节开头就把定义钉死：

[【跳转到 06:22】](https://www.youtube.com/watch?v=kG1xr039u7I&t=382)

![占用率的定义：一个 SM 上驻留的 warp 数，除以这个 SM 最多能装的 warp 数。L4 上一个 SM 最多 48 个 warp，这里驻留 32 个，占用率 66.67%](assets/先测再猜：占用率不是目标，Nsight%20Systems%20才是起点/00382.webp)

$$
\text{occupancy} = \frac{\text{resident warps on one SM}}{\text{max warps that SM can hold}}
$$

在 L4 上，上限是每 SM **48 个 warp**。图里 32 个槽被填上、16 个空着，于是 $32/48 = 66.67\%$。

三个必须记住的限定：

1. **占用率只统计「驻留在场、可以用来掩盖延迟」的 warp**，它对速度什么也没说。它的职责是**掩盖延迟**——它不创造带宽，也不减少工作量。
2. 它有两个版本：**理论占用率（theoretical）** 是内核资源允许的上限，**实际占用率（achieved）** 是剖析器真正测到的。
3. **占用率不是一个你可以随手拧的旋钮**。它是一个结果。

### 3.1 上限从哪来：最紧的那个资源说了算

寄存器、共享内存、block 大小各自限制一个 SM 上能放几个 block，**最紧的那个赢**。

[【跳转到 07:36】](https://www.youtube.com/watch?v=kG1xr039u7I&t=456)

![thread-tiled 内核的寄存器链：128 个寄存器/线程 × 256 线程 = 32768 寄存器/block；SM 有 65536 个寄存器，所以正好放 2 个 block；Nsight Compute 把这个上限按名字打出来：Block Limit Registers = 2](assets/先测再猜：占用率不是目标，Nsight%20Systems%20才是起点/00456.webp)

跟着这条链算一遍 L4 上的 `mm_threadtiled`：

$$
128\ \text{regs/thread} \times 256\ \text{threads} = 32768\ \text{regs/block}
$$

$$
65536\ \text{regs/SM} \div 32768\ \text{regs/block} = 2\ \text{blocks}
$$

2 个 block × 256 线程 = 512 线程 = 48 个 warp 里的 16 个，所以理论占用率是 $16/48 = 33.33\%$。

而 Nsight Compute 会把这个上限**按名字打出来**：`Block Limit Registers = 2`。这句话就是「你的占用率上限是被寄存器卡住的」的直接答案，不用自己算。

| :--- | ---: | ---: | ---: | ---: | ---: |

## 五、同一个内核扫六种 block 形状：曲线不是单调的

第二个实验更细：同一个内核、六种 block 形状、各计时两次。

| block 形状 | 线程数 | 占用率 | 时间（两次） |
| :--- | ---: | ---: | :--- |
| 32×1 | 32 | 50% | 1.8744 / 1.8920 ms |
| 32×2 | 64 | 100% | 约 1.46 / 1.48 ms |
| 32×4 | 128 | 100% | 约 1.47 ms |
| 32×8 | 256 | 100% | 约 1.40 ms |
| 32×16 | 512 | 100% | 约 1.37 ms |
| 32×32 | 1024 | 66.67% | **1.3140 / 1.3420 ms** |

[【跳转到 14:00】](https://www.youtube.com/watch?v=kG1xr039u7I&t=840)

![L4 上的六点曲线：占用率从 50% 爬到 100% 时时间下降（符合预期），然后最后一个配置占用率掉回 66.67%，时间却又降了，降到最低点](assets/先测再猜：占用率不是目标，Nsight%20Systems%20才是起点/00840.webp)

形状是这样的：时间随着占用率从 50% 爬到 100% 而下降——**这是所有人预期的行为**；然后最后那个配置占用率掉回 66.67%，时间**又降了**，降到最低点。这个形状在两次独立运行里都复现了。

而且——这是本段最该记住的一句——**它不是普遍规律**。在 Tesla T4 上（每 SM 32 个 warp 而不是 48 个），同样的扫描是**单调的**，而且 32-wide tiled 内核在那里达到了 100% 占用率。所以：**每一个关于占用率的结论，都要标上它来自哪块 GPU。**

### 5.1 CUDA 自带的建议 API 在优化错误的东西

CUDA 有 `cudaOccupancyMaxPotentialBlockSize` 这类 API，可以帮你建议 block 大小。视频对它的评价是：**它在优化错误的东西**。

- 它给 L4 上的 `mm_coalesced` 建议 **768 线程**；
- 实测最快的块大小是 **1024**——也就是占用率更低的那个配置。

所以 7.6 节的实验二里，答案很明确：**发更快的那个，不是更满的那个**，并且在每一块你瞄准的 GPU 上重跑一遍这个扫描。

## 六、Nsight Systems：先看整条时间线

到这里，7.3 节换了一个尺度：**在打开单个内核之前，先看整次运行。**

Nsight Systems 把每一次拷贝、每一个内核画在一条时间线上，而它通常显示**某一件事占了主导**。它只回答一个问题：**哪一部分慢？** 而 Nsight Compute 回答的是另一个问题：**它为什么慢？** 命令名就是 `nsys`（时间线）和 `ncu`（单个内核）。原则是**先宽后窄**。

### 6.3 把时间线压成一根柱：占比

把时间线压成一根柱，看各操作占 GPU 工作的比例（分母是 GPU 实际工作的 9.17 毫秒）：

| 项目 | 占 GPU 工作 |
| :--- | ---: |
| matmul_naive | **53.5%** |
| matmul_coalesced | 12.7% |
| 三次拷贝合计 | 33.8% |
| 内核合计 | 66.2% |

**五个操作里的一个内核，占了 GPU 工作的一半以上。** 9.87 毫秒的整个跨度里还有 0.70 毫秒的空闲时间。

`nsys` 也能打出一张**纯文本的内核表**，不需要看图。同一份抓取、L4、N=1024：

| kernel | 占内核时间 | 绝对时间 | 启动次数 |
| :--- | ---: | ---: | ---: |
| matmul_naive | 80.9% | 4,908,409 ns | 1 |

**别忘了拷贝**：L4 上三次拷贝搬了 12.6 MB，用了 3.10 毫秒——占这个程序里 GPU 工作的三分之一。这次运行里主机到设备约 5.5 GB/s、设备到主机约 2.6 GB/s，两者用的都是普通的可分页主机内存。

### 6.4 一个陷阱：API 行不是 GPU 行

[【跳转到 20:40】](https://www.youtube.com/watch?v=kG1xr039u7I&t=1240)

![CPU 侧 CUDA API 调用的耗时占比：cudaMalloc 90.8%、cudaDeviceSynchronize 4.7%、cudaMemcpy 3.8%、cudaLaunchKernel 0.4%、cudaFree 0.3%](assets/先测再猜：占用率不是目标，Nsight%20Systems%20才是起点/01240.webp)

这张图很容易被误读。`cudaMalloc` 占 API 时间 90.8%，看起来「内存分配是最大瓶颈」——但：

- **这一行量的是 CPU 侧的调用**，不是 GPU 的工作；
- 那根大柱是三次调用合计 116.3 毫秒，而**光第一次调用就 116.2 毫秒**——那是**一次性的上下文初始化**；
- 它「是真实的工作，但不是任何内核在等的工作」。

所以读 Nsight Systems 的第一条纪律是：**分清 GPU 行和 CPU 行**。

### 6.5 一条实用警告

在托管的 Colab 运行时上，`nsys` 是装着的，但**不在 PATH 里**——它住在 Nsight Compute 的目录树里，所以得用完整路径调用。而且**每次 `nsys stats` 都必须加 force export 标志**，否则一个残留的旧数据库文件会让下一次调用以一句干巴巴的用法提示失败。这个坑在 7.6 节的实验三里还会再出现一次，因为它能让实验还没开始就结束。

## 小结

- **先测再猜**。一个内核慢，下一个念头通常是猜测，而猜测经常错。案例里「读得多所以等 DRAM」的推理每一步都成立，结论却完全反了。
- `memory throughput` 与 `DRAM throughput` 是**两行不同的指标**：前者是芯片上最忙的内存单元（这里 98.42%，是 L1 请求通路），后者是出去到设备内存的那一趟（0.44%）。
- `LG Throttle`（145.92 / 173.17 个 warp 周期，84.3%）说明 warp 在等**发出请求**，不是在等 DRAM 回应。瓶颈是请求的**形状**。
- 占用率 = 驻留 warp 数 ÷ SM 最大 warp 数，上限由寄存器、共享内存、block 大小共同决定，**最紧的那个赢**。它的职责是掩盖延迟，不创造带宽、不减少工作量。
- 占用率**不是目标**：L4 上两个 100% 理论占用率的内核速度差 4.21 倍；最快的手写内核实际占用率只有 18.50%。而且这条曲线的形状**不是普遍规律**——T4 上就是单调的。
- `cudaOccupancyMaxPotentialBlockSize` 建议的 768 线程不是实测最快的 1024。**发更快的那个，不是更满的那个。**
- Nsight Systems 看整条时间线，回答「哪一部分慢」：这份抓取里一个内核占 GPU 工作 53.5%，拷贝占 33.8%，GPU 空闲 7.1%。
- 读 Nsight Systems 要分清 **GPU 行与 CPU 行**：`cudaMalloc` 90.8% 的 API 时间几乎全是一次性上下文初始化，没有内核在等它。
- 每个数字都要标 GPU 型号：同一个 `naive matmul` 在 L4 上 4.91 毫秒，在 T4 上 19.24 毫秒。

## 关键术语速查

| 术语 | 一句话解释 |
| :--- | :--- |
| Nsight Systems（`nsys`） | 系统级剖析器，画整条时间线（拷贝、内核、CPU API），回答「哪一部分慢」 |
| Nsight Compute（`ncu`） | 内核级剖析器，读硬件计数器，回答「这一个内核为什么慢」 |
| occupancy（占用率） | 驻留 warp 数 ÷ SM 最大 warp 数，职责是掩盖延迟，不是速度指标 |
| theoretical / achieved occupancy | 前者是资源允许的上限，后者是剖析器实测值 |
| `Block Limit Registers` | Nsight Compute 给出的「被寄存器卡住时一个 SM 能放几个 block」 |
| memory throughput | 芯片上最忙的内存单元的活动水平（占其峰值百分比） |
| DRAM throughput | GPU 与片外 DRAM 之间的流量占峰值的百分比 |
| `LG Throttle` | local/global 内存请求队列满，warp 卡在「发不出请求」 |
| Roofline 拐点（ridge） | 峰值算力 ÷ 峰值带宽，单位 FLOP/byte |
| eligible warps | 驻留且下一条指令已可发射的 warp 数，衡量延迟掩盖效果 |
