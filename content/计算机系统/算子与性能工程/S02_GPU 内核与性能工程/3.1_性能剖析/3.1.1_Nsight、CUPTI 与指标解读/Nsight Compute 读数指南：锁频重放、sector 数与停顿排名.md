## 本讲要解决的核心问题（SCQA）

**背景**：上一篇已经用 Nsight Systems 找到了热点：一个 `matmul_naive` 占了 GPU 工作的 53.5%。现在要用 `ncu` 打开这一个内核，回答「它为什么慢」。

**冲突**：`ncu` 给出的第一手数字里，有一半是不能直接用的。它为了读全硬件计数器，必须**把同一个内核重放 40 趟**；为了计数器可重复，它**把 SM 时钟锁在 795 MHz**。于是同一个内核，正常跑是 4.91 毫秒，在 `ncu` 下被报成 12.59 毫秒。更坑的是，如果你在 `ncu` 下跑自己的计时 benchmark，**你自己的 `printf` 也会骗你**——重放的那些趟就发生在你自己的计时器里面。

**疑问**：那 `ncu` 的哪些数字能用、哪些不能用？同一份报告里怎么比较两个内核？`memory throughput` 两个内核都是 98%，为什么说「不是同一个单元」？最后那个「只改一件」的纪律，具体怎么落到代码上？

**回答（中心思想）**：`ncu` 的报告要**分两类读**：**绝对时间不能用**（锁频 + 重放），**比值和派生量可以用**（4.21x 与 4.24x 高度一致）。而在所有派生量里，最该盯的是 **`sectors per request`**——它等于「碰到的 32 字节 sector 数 ÷ 发出的请求数」。案例里朴素内核是 **8.50**，合并访存后降到 **2.00**，而请求数**逐位相同**（67,108,864 个）。所以那 4.24 倍的加速，全部来自「同样的请求碰了 4.25 倍更少的 sector」。围绕这个数字，「测量 → 只改一件 → 再测量」的循环把每条指令的 warp 周期数从 173.17 一路压到 5.00。

## 一、`ncu` 的代价：一块 GPU 的计数器，一次读不完

7.4 节的第一句话就是机制说明：**一块 GPU 的计数器比它一次能读完的要多**，所以 `ncu` 会**重放（replay）**这个内核，每次读一组不同的计数器。

[【跳转到 22:59】](https://www.youtube.com/watch?v=kG1xr039u7I&t=1379)

在这份抓取里，`ncu --set full` 为一个内核需要 **40 趟重放**。这就是为什么被剖析的内核比同一个内核正常跑要慢得多——不是内核变慢了，是它被跑了 40 多遍。

这也解释了一个常见的误用：**一个程序在被剖析时报告的关于自己的数字是垃圾**。L4 上实测，朴素内核被报成 739.4 毫秒、cuBLAS 被报成 116 毫秒——而它们不挂剖析器运行时分别是 4.91 和 0.17 毫秒。**重放的那些趟就发生在你自己的计时器里面。**

## 二、锁频：绝对时间不能用，比值可以用

第二处「自欺」更隐蔽：**Nsight Compute 会锁住 SM 时钟**，为的是让它的计数器可重复。

[【跳转到 23:24】](https://www.youtube.com/watch?v=kG1xr039u7I&t=1404)

![同一个内核、同一块 GPU，只有时钟被锁了：不挂剖析器时 SM 时钟 2025–2040 MHz、CUDA event 计时 4.91 毫秒；在 ncu 下 SM 时钟锁在 795 MHz、ncu 报出 12.59 毫秒](assets/Nsight%20Compute%20读数指南：锁频重放、sector%20数与停顿排名/01404.webp)

| 条件 | SM 时钟 | 朴素内核耗时 |
| :--- | :--- | ---: |
| 不挂剖析器（CUDA event 计时） | 2025–2040 MHz | 4.91 ms |
| 在 `ncu` 下 | 795 MHz（锁定） | 12.59 ms |

**同一个内核、同一块 GPU，只有时钟被锁了。** 所以 `ncu` 的绝对时间不能用来和正常运行比较。

但**比值可以**：

[【跳转到 24:39】](https://www.youtube.com/watch?v=kG1xr039u7I&t=1479)

![比值活得下来，绝对时间不行：CUDA event 计时 4.9148 / 1.1664 毫秒，比值 4.21x；ncu 在 795 MHz 下报 12.59 / 2.97 毫秒，比值 4.24x——两个比值高度一致，毫秒数不一致而且本来就不该一致](assets/Nsight%20Compute%20读数指南：锁频重放、sector%20数与停顿排名/01479.webp)

| 计时方式 | naive | coalesced | 比值 |
| :--- | ---: | ---: | ---: |
| CUDA events | 4.9148 ms | 1.1664 ms | **4.21x** |
| `ncu`（795 MHz） | 12.59 ms | 2.97 ms | **4.24x** |

两个比值（4.21 和 4.24）非常接近；毫秒数却不接近，**而且本来就不该接近**。

于是两条可以背下来的纪律：

1. **在同一份报告内部比较内核，永远不要跨报告比较。**
2. **对外报的时间要来自正常运行，永远不要来自 `ncu`。**

## 三、同一份报告里的 SOL 对比：两个 98% 不是同一个单元

现在可以把两个内核放在同一份报告里横着读了。

[【跳转到 26:58】](https://www.youtube.com/watch?v=kG1xr039u7I&t=1618)

![同一份 ncu 报告里 naive 与 coalesced 的对比：Duration 12.59 / 2.97 ms、Compute (SM) throughput 23.16% / 98.04%、Memory throughput 98.42% / 98.04%、DRAM throughput 0.44% / 1.63%、实际占用率 96.73% / 96.54%、每线程寄存器 40 / 40，最后一行 sectors per request 8.50 / 2.00](assets/Nsight%20Compute%20读数指南：锁频重放、sector%20数与停顿排名/01618.webp)

| 指标 | naive | coalesced |
| :--- | ---: | ---: |
| Duration（`ncu`，795 MHz） | 12.59 ms | 2.97 ms |
| **Compute (SM) throughput** | 23.16% | **98.04%** |
| Memory throughput | 98.42% | 98.04% |
| DRAM throughput | 0.44% | 1.63% |
| Achieved occupancy | 96.73% | 96.54% |
| Registers per thread | 40 | 40 |
| **Sectors per request（派生量）** | **8.50** | **2.00** |

这张表里有三个必须讲清的点。

**第一，`Memory throughput` 两个都是 98%，但它不是同一个单元的两次测量。** 对朴素内核来说，最忙的单元是 **L1 请求通路**；对 coalesced 内核来说，L1 通路已经降到 **73.6%** 忙，最忙的单元变成了**内存管线**。同一个数字背后是不同的硬件单元——这正是 SOL 段「每个百分比的分母都是那个单元自己的上限」的含义。

**第二，`Speed of Light` 这个名字的定义**：这些百分比每一个都是相对**那个单元自己的上限**，而不是相对整机的 FP32 峰值。即便是 coalesced 内核，也只有整机峰值的 **6.27%**。所以看到「98%」不要以为「快到头了」——它只是说「这条管线快到头了」。

**第三，真正动过的那一行是 `sectors per request`。** 其他所有能想到的指标都几乎没变：实际占用率 96.73% vs 96.54%，每线程寄存器 40 vs 40。这一行是**派生量**——它等于 sector 数除以请求数。

## 四、`sectors per request`：真正的那个计数器

视频把这一页叫做「确凿证据（the smoking gun）」，因为它把一个「感觉」变成了一个**整数除法**。

[【跳转到 27:23】](https://www.youtube.com/watch?v=kG1xr039u7I&t=1643)

![同样的 load 请求数 67,108,864 个（两者逐位相同），朴素内核碰了 570,425,344 个 32 字节 sector，coalesced 内核只碰了 134,217,728 个——同样的指令、同样的请求，碰到的 sector 少了 4.25 倍](assets/Nsight%20Compute%20读数指南：锁频重放、sector%20数与停顿排名/01658.webp)

| 量 | naive | coalesced |
| :--- | ---: | ---: |
| 全局 load 请求数 | 67,108,864 | 67,108,864（逐位相同） |
| 碰到的 32 字节 sector 数 | 570,425,344 | 134,217,728 |
| **sectors per request** | **8.50** | **2.00** |

$$
\frac{570{,}425{,}344}{67{,}108{,}864} = 8.50,\qquad
\frac{134{,}217{,}728}{67{,}108{,}864} = 2.00
$$

视频对这张表的总结是整章最漂亮的一句：**同样的指令、同样的请求数——碰到的 32 字节 sector 少了 4.25 倍。**

再对比一下「没变」的清单：理论占用率 100% 和 100%；实际占用率 96.73% 和 96.54%；每线程寄存器 40 和 40；全局 load 请求数 67,108,864，**逐位相同**。唯一动过的输入是 sector 数：load sector 少 4.25 倍，store sector 少 4.00 倍。**光这一项就值那 4.24 倍的加速。**

### 4.1 停顿排名：把「为什么发不出指令」排个队

`ncu` 还会把「warp 为什么发不出指令」按**每条已发射指令的周期数**排个名。

[【跳转到 29:23】](https://www.youtube.com/watch?v=kG1xr039u7I&t=1763)

![停顿排名：matmul_naive 每条指令共 173.17 个周期，最大原因 LG Throttle 145.92（84.3%）；matmul_coalesced 共 40.81 个周期，最大原因还是 LG Throttle，27.27（66.8%）；eligible warp 从每个调度器 0.35 升到 1.67](assets/Nsight%20Compute%20读数指南：锁频重放、sector%20数与停顿排名/01768.webp)

| kernel | 每条指令总周期 | 最大停顿原因 | 周期数（占比） |
| :--- | ---: | :--- | ---: |
| matmul_naive | 173.17 | LG Throttle | 145.92（84.3%） |
| matmul_coalesced | 40.81 | LG Throttle | 27.27（66.8%） |

**瓶颈是同一个原因，只是规模小多了。** 这正是「合并访存」这个修法有效的原因：它没有换掉瓶颈的种类，只是把同一类瓶颈的规模压小了 5 倍多。

同一页还有一个指标值得记：**eligible warps**——驻留、且下一条指令已经可以发射的 warp 数——从每个调度器 **0.35 升到 1.67**。这个数字上升，说明延迟掩盖变好了。

### 4.2 Roofline 落点：170.7 是理想值，不是结论

[【跳转到 30:31】](https://www.youtube.com/watch?v=kG1xr039u7I&t=1831)

![L4 的 Roofline：天花板是实测 FP32 峰值 29380 GFLOP/s，斜线是实测读带宽 256 GB/s，两者交在 114.8 FLOP/byte 的拐点；N=1024 方阵矩阵乘的理想算术强度是 170.7 FLOP/byte，落在拐点右侧；naive 437、coalesced 1841 GFLOP/s 都远在天花板之下](assets/Nsight%20Compute%20读数指南：锁频重放、sector%20数与停顿排名/01831.webp)

这里有一个非常容易犯的推理错误，视频专门点出来了：

- $170.7$ FLOP/byte 是**理想**算术强度，把每个字节只算读一次；
- 它说明 **DRAM 原则上不是限制**；
- 它**并没有说**这两个内核受限于计算管线——剖析器已经告诉我们，朴素内核卡在**请求通路**上。

也就是说：**Roofline 只能排除「DRAM 是理论上限」，不能判定「你现在是计算受限」。** 判定要靠计数器。

## 五、优化循环：测量、只改一件、再测量

7.5 节把整套纪律压成三个盒子：

1. **测量**——用计时器，也用剖析器；
2. **只修一件**，由最大停顿原因选出来的那一件；
3. **再测量**。它真的动了吗？然后闭合循环，因为你刚移走的瓶颈**不是最后一个**。

第二步为什么只能是「一件」？视频给的理由很干脆：**一次改两样，你就分不清是哪一样起了作用**。如果内核变快了，你不知道是哪一处改动的功劳；如果变慢了，你也不知道该撤回哪一处。**一次改动、一次测量、一个结论。**

### 5.1 三轮实测：瓶颈会换身份

[【跳转到 35:12】](https://www.youtube.com/watch?v=kG1xr039u7I&t=2112)

![四个内核、三种答案：naive 是 LG Throttle 145.92，coalesced 还是 LG Throttle 但只有 27.27，tiled 换成了 MIO Throttle 20.85（由共享内存流量填满），thread-tiled 已经没有主导停顿、总代价 5.00；每条指令的 warp 周期数 173.17 → 40.81 → 39.01 → 5.00](assets/Nsight%20Compute%20读数指南：锁频重放、sector%20数与停顿排名/02112.webp)

| 轮次 | 改动 | 结果 | 最大停顿原因 |
| :--- | :--- | :--- | :--- |
| 起点 | — | 4.9148 ms | LG Throttle 145.92 |
| 第一轮 | 交换两个索引维度（合并访存） | 1.1664 ms（4.21x） | LG Throttle 27.27 |
| 第二轮 | 加共享内存分块 | 0.9415 ms（2281 GFLOP/s） | **MIO Throttle 20.85** |
| 第三轮 | thread-tiled | 0.3209 ms（15.32x） | 无主导停顿，总 5.00 |

- **第一轮**：报告说 8.50 sectors per request，修法很小——**交换两个索引维度**。内核从 4.9148 毫秒降到 1.1664 毫秒，快了 4.21 倍，sectors per request 从 8.50 掉到 2.00，**占用率和寄存器数都没变**。
- **第二轮**：加共享内存分块又帮了一次忙——而且这一次**最大停顿原因变了**。16-wide tiled 内核跑在 0.9415 毫秒（2281 GFLOP/s），最大停顿不再是 LG Throttle，而是 **MIO Throttle**，占 20.85 个周期。MIO 是内存输入输出管线，这里它承载的是**共享内存流量**。
- **第三轮**：把整个阶梯背后的那个计数器摆出来。全局 load 请求数：朴素 67,108,864 → 16-wide tiled 4,194,304 → 32-wide tiled 2,097,152 → thread-tiled **524,288**。从阶梯第一级到第四级，**请求数少了 128 倍**。

视频对第三轮的评语很关键：**没有人让内存变快——每个版本只是把同一份数据要了更少的次数。** thread-tiled 跑 0.3209 毫秒，是朴素内核的 15.32 倍。

### 5.2 一个测量习惯：冷着计时，测的是爬坡

还有一个容易忽略的坑：**GPU 空闲时在低频，忙起来才加速**。冷着计时，你有一部分测的是**爬坡过程**，而不是内核。

| GPU | 冷态 | 热态 | 空闲频率 → 加速频率 |
| :--- | ---: | ---: | :--- |
| Tesla T4 | 4893 GFLOP/s | 8036 GFLOP/s | 300 MHz → 约 1575 MHz |
| NVIDIA L4 | 29324 GFLOP/s | 29380 GFLOP/s | 几乎不受影响 |

T4 上冷热差 1.64 倍——这个差异足够让一次「优化」看起来成功了。

## 六、三个可以照着做的实验

7.6 节给了三个实验，每个都配了「先预测再看答案」的问题。

### 6.1 实验一：读一行 Speed of Light

[【跳转到 39:36】](https://www.youtube.com/watch?v=kG1xr039u7I&t=2376)

![实验一：L4、N=1024 上一个内核报出 Compute 23.16%、Memory 98.42%、DRAM 0.44%，问「挡住它的是什么」；提示先预测：忙的内存单元在片上还是 DRAM 上？内核做了很多算术吗？换更快的显存有帮助吗？](assets/Nsight%20Compute%20读数指南：锁频重放、sector%20数与停顿排名/02376.webp)

答案：**忙的那个单元 98.42% 在片上，不在显存芯片上**（显存只有 0.44%）。所以换更快的显存芯片没有帮助，修法是**让请求更少或形状更好——先合并（coalescing），再谈复用**。

### 6.2 实验二：从实测数据里选 block 大小

L4 上 coalesced 内核的两个配置：

| 线程数 | 理论占用率 | 耗时 |
| ---: | ---: | ---: |
| 512 | 100% | 1.3740 ms |
| 1024 | 66.67% | **1.3140 ms** |

先预测：哪个理论占用率更高？哪个更快？你发哪个？

答案：**发 1024 线程那版**（1.3140 毫秒），尽管它的占用率只有 66.67%。而 CUDA 自己的建议 API 在这里提的是 768 线程——**两个都不是**。所以：**发更快的那个，不是更满的那个，并且在每一块你瞄准的 GPU 上重跑一遍这个扫描。**

### 6.3 实验三：那些确实能用的命令

[【跳转到 41:58】](https://www.youtube.com/watch?v=kG1xr039u7I&t=2518)

![实验三的完整命令序列：nvcc 带 -lineinfo 并为 compute_75 与 compute_89 两段 gencode 编译；用 Nsight Compute 目录树里的完整路径调用 nsys profile 抓整个程序；nsys stats 必须加 --force-export true 并指定 cuda_gpu_kern_sum 报告；最后用 ncu -k regex:matmul_naive --launch-count 1 --set full -o report 只剖析那一个内核](assets/Nsight%20Compute%20读数指南：锁频重放、sector%20数与停顿排名/02518.webp)

```bash
# 1. lineinfo 用于源码映射，并为两种可能的 GPU 都编出代码
nvcc -O2 -lineinfo -o profile_demo profile_demo.cu \
     -gencode arch=compute_75,code=sm_75 \
     -gencode arch=compute_89,code=sm_89

# 2. 整个程序：哪个内核占主导？
NSYS=/opt/nvidia/nsight-compute/2025.1.1/host/target-linux-x64/nsys
$NSYS profile --force-overwrite true -o demo \
      --stats=false ./profile_demo 1024
$NSYS stats --force-export true \
      --report cuda_gpu_kern_sum demo.nsys-rep

# 3. 单个内核：-k 指定名字，--launch-count 只取一次启动
ncu -k regex:matmul_naive --launch-count 1 \
    --set full -o report -f ./profile_demo 1024
```

几个必须注意的点：

- 两段 `gencode`（7.5 对应 Tesla T4，8.9 对应 NVIDIA L4）让**同一个二进制在两块卡上都能跑**。
- **每次 `nsys stats` 都要加 `--force-export true`**，否则一个残留的旧数据库文件会让下一次调用以一句干巴巴的用法提示失败。
- **不加 `-k` 过滤的话，`ncu` 会剖析程序里每一次启动**，而每次启动都要自己一整套重放趟——40 趟 × N 次启动，时间会爆炸。
- `-o report` 写出 `report.ncu-rep`。托管运行时上没有图形查看器，所以要把它下载下来，在自己机器上用 Nsight Compute GUI 打开。
- 还有一个能让实验还没开始就结束的坑：在托管 Colab 运行时上，`which nsys` 什么也找不到，`pip` 和 `apt` 都装不上它——**它其实已经在机器上，就打包在 Nsight Compute 的目录里**。

## 七、最后一条警告：给每个数字标上 GPU 名字

7.6 节结尾回到开篇那条规矩：N=1024 的朴素矩阵乘在 L4 上花 **4.91 毫秒**，在 Tesla T4 上花 **19.24 毫秒**。同样的代码、同样的输入，**差 3.9 倍**。

> 一个旁边没写机器名的数字，无法被核查、无法被复现、也无法被质疑。

## 小结

- `ncu` 为一个内核要重放 **40 趟**（`--set full`），所以被剖析的内核慢得多；**程序在被剖析时自己打印的计时是垃圾**。
- `ncu` **锁住 SM 时钟**（L4 上锁到 795 MHz），所以绝对时间不能和正常运行比：同一个内核 4.91 ms 变成 12.59 ms。
- 但**比值活得下来**：CUDA event 计时 4.21x，`ncu` 报 4.24x。所以「在同一份报告内部比较内核，对外报时间来自正常运行」。
- `Speed of Light` 的每个百分比都是相对**那个单元自己的上限**，不是整机峰值；coalesced 内核也只有整机峰值的 6.27%。
- 两个内核 `Memory throughput` 都是 98%，但**不是同一个单元**：朴素是 L1 请求通路，coalesced 是内存管线（L1 通路降到 73.6%）。
- **`sectors per request` 是最有诊断力的派生量**：8.50 → 2.00，而请求数逐位相同（67,108,864）。4.25 倍更少的 sector 换来了 4.24 倍的加速。
- **停顿排名**按「每条已发射指令的周期数」排序：naive 173.17（LG Throttle 145.92，84.3%）→ coalesced 40.81（同为 LG Throttle，27.27）；`eligible warps` 从 0.35 升到 1.67。
- **Roofline 只能排除「DRAM 是理论上限」**（170.7 FLOP/byte 在拐点右侧），不能判定「你现在是计算受限」。
- 优化循环三步：**测量 → 只改一件 → 再测量**。一次改两样，你就分不清哪一样起了作用。
- 瓶颈会换身份：LG Throttle → MIO Throttle（共享内存流量）→ 无主导停顿，每条指令的 warp 周期数 173.17 → 40.81 → 39.01 → 5.00。
- 冷着计时测的是**爬坡**：T4 冷态 4893、热态 8036 GFLOP/s。
- 命令层面：`nsys stats` 必须 `--force-export true`；`ncu` 必须用 `-k` 过滤，否则每次启动都要一整套重放；`nsys` 在托管运行时上要用完整路径。

## 关键术语速查

| 术语 | 一句话解释 |
| :--- | :--- |
| replay（重放） | `ncu` 为读全计数器而把同一内核重复执行多趟，`--set full` 约 40 趟 |
| clock lock（锁频） | `ncu` 固定 SM 时钟以保证计数器可重复，代价是绝对时间失真 |
| Speed of Light | 每个百分比相对该单元自己的上限，而非整机峰值 |
| sectors per request | 碰到的 32 字节 sector 数 ÷ 请求数，理想值 1.0，访存效率的核心派生量 |
| LG Throttle | local/global 内存请求队列满，warp 卡在发不出请求 |
| MIO Throttle | 内存输入输出管线（含共享内存流量）排队满导致的停顿 |
| eligible warps | 驻留且下一条指令已可发射的 warp 数，衡量延迟掩盖效果 |
| Roofline 拐点 | 峰值算力 ÷ 峰值带宽，L4 上是 114.8 FLOP/byte |
| ideal arithmetic intensity | 每个字节只算读一次得到的算术强度，衡量「DRAM 原则上是否是限制」 |
| `--launch-count` | `ncu` 参数，限制只剖析前 N 次启动，避免重放次数爆炸 |
