# Roofline 屋顶线怎么画：H100 的峰值算力与峰值带宽交汇在 295 FLOP/B

> 视频来源：[你的 GPU 为什么跑不满？纳西妲讲 GPU 性能瓶颈：Roofline、算术强度、算子融合](https://www.bilibili.com/video/BV1KTn16ZEYV/)（Bilibili · ZnZrYb）｜时长约 17 分钟
> 简要导读：这支视频读的是 NVIDIA GPU 词典里 performance bottleneck（性能瓶颈）这个词条，连带它引用的 Horace He、Patterson、Harris 等人的资料一起讲。它的讲法是「先讲瓶颈是什么，再讲怎么用一张图把瓶颈画出来」。本文完整保留这条脉络，其中第四章（屋顶线怎么画）与第五章（怎么把真实 kernel 投到图上）是本小节的重点，讲得最细；decode/prefill 的落点推导只作为「拐点会移动」的例子点到为止。

## 本讲要解决的核心问题（SCQA）

**背景**：每张 GPU 的规格表上都有两个硬指标——峰值算力（TFLOPS，每秒能算多少次浮点运算）和峰值带宽（GB/s，每秒能从显存搬多少字节）。

**冲突**：这两个数字都很大，但一个 kernel 跑起来只能撞上其中一个天花板。麻烦的是，`nvidia-smi` 显示的「GPU 利用率 100%」只表示有 kernel 在跑，完全不代表算力被用满了；于是同一个「跑满」的字面现象，背后可能是完全相反的两种瓶颈，优化方向也完全相反。

**疑问**：有没有一张图，能同时画出这两个天花板，并且直接告诉我「我这个算子撞的是哪一个」？

**回答（中心思想）**：有，就是 Roofline（屋顶线）。它把硬件压缩成两条线——一条斜率等于带宽的斜线、一条高度等于峰值算力的平线——然后取二者的最小值。两条线的交点叫**屋脊点**（ridge point），它的算术强度等于「峰值算力 ÷ 峰值带宽」。H100 上这个数是 $989/3.35 \approx 295$ FLOP/B：算术强度低于 295 的算子落在斜线上（带宽受限），高于 295 的落在平线上（算力受限）。**画屋顶线的全部工作，就是查这两个硬件数字、做一次除法、再看你的算子落在交点哪一侧。**

## 一、先把「瓶颈」这个词钉死：约束理论的三步法

视频开篇没有直接讲屋顶线，而是先花了两分钟讲「瓶颈」本身，因为屋顶线本质上就是「把瓶颈画出来」（[【跳转到 00:00】](https://www.bilibili.com/video/BV1KTn16ZEYV/?t=0)）。

**什么是瓶颈**：两个瓶子装一样多的水，倒得多快只看最细的那一端。性能瓶颈就是限制任务完成速率的那一环，所以它是性能优化的靶子——第一步永远是先找到它（[【跳转到 00:25】](https://www.bilibili.com/video/BV1KTn16ZEYV/?t=25)）。

![细瓶颈与粗瓶颈的对比：同样的水量，出口最细的那一端决定流速](assets/Roofline%20屋顶线怎么画：H100%20的峰值算力与峰值带宽交汇在%20295%20FLOP／B/00025.webp)

**为什么不能乱优化**：视频给了一条三道工序的流水线——A 每秒做一件、B 每秒 0.4 件、C 每秒 0.8 件，整体产出被最慢的 B 卡在每秒 0.4 件。这时把 C 提速到每秒 1.6 件，整体产出**一点没变**；改去抬升 B，产出才升到每秒一件，而瓶颈随即换成了 A（[【跳转到 00:50】](https://www.bilibili.com/video/BV1KTn16ZEYV/?t=50)）。结论很硬：**在不是瓶颈的环节上优化等于白干**。

这套思路有个正式名字——约束理论（Theory of Constraints），来自高德拉特 1984 年的小说《目标》。核心是五步聚焦法：

1. **识别**：找出当前卡住产出的那个环节，线索是「活总堆在它前面」；
2. **利用**：先用现有资源把它榨干，别让它闲着；
3. **服从**：其余环节都配合它，上游别让它断粮，下游别把它堵住；
4. **抬升**：还不够就投入资源扩大它的能力，直到它不再是约束；
5. **重复**：约束转移了就回到第一步。

（词典的页面把这套流程压成了三步：找出、抬升、重复。）

视频还提了一句排产方法「鼓—缓冲—绳」：鼓是约束的节拍，全场跟着它走；缓冲是在约束前留一小段库存，保证它永远不断粮；绳是拉式投料，每用掉一件入口才放进一件，投得更早只会让在制品越堆越多。这段看似离 GPU 很远，其实对应到后面就是一句话：**让最贵的计算单元一直有活干，别让它等数据**（[【跳转到 02:55】](https://www.bilibili.com/video/BV1KTn16ZEYV/?t=175)）。

## 二、kernel 的时间只花在三件事上

第二章引用 Horace He 在 Jane Street 的演讲：GPU 上一个 kernel 的时间只花在三件事上（[【跳转到 03:20】](https://www.bilibili.com/video/BV1KTn16ZEYV/?t=200)）：

| 类别 | 做的事 | 工厂类比 |
| --- | --- | --- |
| 计算 | 在 CUDA Core 或 Tensor Core 上做浮点运算 | 工厂在开工 |
| 访存 | 在内存层级之间搬数据 | 把原料从远处仓库运进工厂、成品运回去 |
| 开销 | 其他一切，比如 CPU 上的 Python 和框架在决定下一步干什么 | 工厂在等订单 |

![仓库（显存 DRAM，又大又远）与工厂（SM 计算单元 + 小而快的 SRAM）之间的数据通路](assets/Roofline%20屋顶线怎么画：H100%20的峰值算力与峰值带宽交汇在%20295%20FLOP／B/00200.webp)

**三段里最长的那段就是瓶颈。** 这个类比立刻解释了一个反直觉的现实：如果工厂扩建了一倍、运输能力却没变，工厂就越来越难吃饱——算力翻了倍，实际性能远没有翻倍。Patterson 统计过：处理器带宽大约 1.6 年翻一倍，内存要 2.7 年，差距年年拉大，喂饱计算单元越来越难（[【跳转到 03:45】](https://www.bilibili.com/video/BV1KTn16ZEYV/?t=225)）。

Harris 给训练模型打了个比方，视频顺手借来用：过拟合的时候再加大模型是白费功夫；性能也一样——时间都花在搬数据上，提升算力没用；时间都花在矩阵乘上，减少派送的开销也没用。

## 三、三类瓶颈各长什么样

在画屋顶线之前，得先知道「落在屋顶上」到底意味着什么。视频把瓶颈分成三类，逐一给出识别特征。

### 3.1 compute-bound：被计算单元的算术吞吐卡住

典型例子是大矩阵乘。关键在于**可计算单元不止一种**（[【跳转到 05:00】](https://www.bilibili.com/video/BV1KTn16ZEYV/?t=300)）：

![H100 SXM 的两种峰值算力：Tensor Core（BF16 稠密矩阵乘）988 TFLOPS，CUDA Core（FP32 标量运算）67 TFLOPS](assets/Roofline%20屋顶线怎么画：H100%20的峰值算力与峰值带宽交汇在%20295%20FLOP／B/00300.webp)

- **Tensor Core**：一条指令就算一整块小矩阵（例如 `HMMA.16816.F32` 一条指令 = 16×8×16 = 2048 次乘加，由一个 warp 的 32 个线程合作完成，平均每线程 64 次）；
- **CUDA Core**：一条指令只算一个数。

所以**不是矩阵乘的运算，在 H100 上最多只能用到峰值的 7% 左右**。这句话是后面「屋顶要按计算单元分别画」的伏笔。

视频还给了 BERT 的一组反直觉数字（[【跳转到 05:34】](https://www.bilibili.com/video/BV1KTn16ZEYV/?t=334)）：

![BERT 里矩阵乘占 99.8% 的浮点运算量，却只占 61% 的运行时间；归一化占 25.5%、逐元素占 13.5%](assets/Roofline%20屋顶线怎么画：H100%20的峰值算力与峰值带宽交汇在%20295%20FLOP／B/00341.webp)

矩阵乘占了 99.8% 的浮点运算，却只占 61% 的运行时间；归一化和逐元素运算合起来只有 0.2% 的运算量，却吃掉了将近 40% 的时间。原因正是 Tensor Core 让矩阵乘快了大约十倍，其余运算没跟上，它们的时间占比就暴涨了。

### 3.2 memory-bound：被显存和 SM 之间的带宽卡住

典型例子是大向量的逐元素运算。数据从显存运到 SM，每个数只算一次就再运回去，时间几乎全耗在路上。视频算了一笔账（[【跳转到 06:02】](https://www.bilibili.com/video/BV1KTn16ZEYV/?t=362)）：

- A100 的显存带宽是 1.5 TB/s；
- 不用 Tensor Core 的算力是 19.5 TFLOPS；
- 做 20 万亿次运算的时间里，只能读进 4000 亿个 FP32 的数（再算上写回）。

也就是说，**一个逐元素算子要对每个数做大约 100 次运算，计算时间才赶得上访存时间**。这个「100」其实就是后面屋顶线拐点的另一种说法。

对付 memory-bound 最有效的一招是**算子融合**（operator fusion），视频称它是深度学习编译器里最重要的优化（[【跳转到 06:52】](https://www.bilibili.com/video/BV1KTn16ZEYV/?t=412)）：

![算子融合：两个 cos 分两个 kernel 要 4 次全局读写，融合成一个 kernel 只需 2 次，快 2 倍](assets/Roofline%20屋顶线怎么画：H100%20的峰值算力与峰值带宽交汇在%20295%20FLOP／B/00437.webp)

不融合时 `x.cos()` 之后再 `.cos()`：读 x、写 x1、读 x1、写 x2，一共四次全局内存读写；融合成一个 kernel：读 x、连算两次 cos、再写结果，只剩两次读写，快了一倍。推论是：**融合以后多做几次运算几乎不花时间**，所以 GELU 比 ReLU 多算很多，开销却差不多。

视频用一个微基准把这件事量化了：对同一个张量连乘 repeat 次（`x = x * 2`）并融合成一个 kernel，repeat 每翻一倍运算量就翻一倍，而访存量不变（[【跳转到 07:17】](https://www.bilibili.com/video/BV1KTn16ZEYV/?t=437)）。

![微基准：repeat 从 1 到 32 运行时间几乎不变（memory-bound），过了 64 时间开始跟着运算量上涨（换成 compute-bound）](assets/Roofline%20屋顶线怎么画：H100%20的峰值算力与峰值带宽交汇在%20295%20FLOP／B/00462.webp)

repeat 从 1 到 32，运行时间几乎不变——算力一直闲着，瓶颈是带宽；过了 64，时间开始跟着运算量上涨，瓶颈换成了算力。衡量 compute-bound 的程度就看「实测算力 ÷ 峰值」，这里从 0.2 TFLOPS 一路涨到接近峰值 9.75 TFLOPS。**这张图其实就是屋顶线的雏形：横轴是「每字节做多少运算」，纵轴是性能，先平后升。**

### 3.3 overhead-bound：GPU 在等 CPU 派活

第三类瓶颈不在 GPU 内部，而在 GPU 外面：GPU 没在干活，而是在等 CPU 把下一件活派过来。

- 大 kernel 的时候，CPU 发射得比 GPU 算得快，可以提前排队，开销被完全藏住——就像在火车前面抢先铺轨道；
- 小 kernel 的时候，GPU 一眨眼就算完，只能停下来等 CPU 发下一个，时间线上全是空隙。

量级很吓人：每次启动 kernel 光 CUDA API 就要大约 10 微秒，框架决定挑哪个 kernel 还要再花好几微秒。PyTorch 实测 Python 每秒大约做 3200 万次加法；而在派送一次加法的时间里，A100 能做 975 万次浮点运算——换成 PyTorch，每秒只能做大约 28 万次操作，因为每一次都要检查类型、检查设备、判断要不要建图求导（[【跳转到 08:32】](https://www.bilibili.com/video/BV1KTn16ZEYV/?t=512)）。

常见解法是 CUDA Graphs：把一串 kernel 录成一张图，CPU 只发射一次。**怎么判断是不是 overhead-bound？** 把数据量加大试试：计算和访存都会跟着规模上涨，开销却基本不变，batch 翻倍时间只涨 10%，多半就是开销在卡（[【跳转到 09:11】](https://www.bilibili.com/video/BV1KTn16ZEYV/?t=551)）。

三类瓶颈的对症下药也因此不同：**开销靠减少 Python 和 kernel 启动，带宽靠融合，算力靠 Tensor Core。** 视频最后补了一句提醒：`nvidia-smi` 显示的 GPU 利用率只表示有 kernel 在跑的时间占比，不代表算力用满了。

## 四、屋顶线怎么画：两条线、一个公式

第四章进入正题（[【跳转到 09:45】](https://www.bilibili.com/video/BV1KTn16ZEYV/?t=585)）。

![Roofline 模型：横轴算术强度（对数轴），纵轴性能（对数轴），斜屋顶斜率 = 带宽 3.35 TB/s，平屋顶 = Tensor Core 989 TFLOPS](assets/Roofline%20屋顶线怎么画：H100%20的峰值算力与峰值带宽交汇在%20295%20FLOP／B/00610.webp)

### 4.1 坐标轴：横轴是算术强度，纵轴是性能

- **横轴**：算术强度 $I$，单位 FLOP/B，含义是「这个 kernel 对每个字节的数据做多少次浮点运算」。注意它把整个 kernel 压缩成了一个数——这是 Roofline 唯一的「代码质量」输入。
- **纵轴**：性能 $P$，单位 TFLOPS。两张轴都取对数，因为强度可以横跨好几个数量级（0.01 到 10000）。

### 4.2 两条屋顶线

**斜的屋顶是内存带宽**：强度低的时候，每读一个字节只能做很少的运算，性能完全由「每秒能搬多少字节」决定：

$$
P_{\text{memory}} = \beta \cdot I
$$

其中 $\beta$ 是峰值带宽。这在对数-对数坐标上是一条斜率等于带宽的直线（视频里标的是 H100 的 3.35 TB/s）。

**平的屋顶是算力上限**：强度足够高以后，数据不再是问题，性能被计算单元封顶：

$$
P_{\text{compute}} = \pi
$$

其中 $\pi$ 是峰值算力（视频用 H100 Tensor Core 的 989 TFLOPS）。

### 4.3 取最小值，就得到屋顶线

$$
P = \min\left(\pi,\ \beta \cdot I\right)
$$

这就是屋顶线的全部公式。**为什么是 min 而不是加？** 因为这两条都是「上限」，而实际性能不可能超过任何一个上限，所以只能取更小的那个。

### 4.4 拐点（屋脊点）怎么算

两条线的交点，就是斜屋顶升到平屋顶的那个位置。令 $\beta I = \pi$，解出：

$$
I^{*} = \frac{\pi}{\beta} = \frac{989\ \text{TFLOPS}}{3.35\ \text{TB/s}} \approx 295\ \text{FLOP/B}
$$

**这就是本小节要的「拐点计算」：峰值算力除以峰值带宽。** 视频的说法是「算术强度至少要到 295 左右，才能逃出内存瓶颈」。

### 4.5 怎么判断一个算子落在哪一侧

视频给了三条判据（[【跳转到 10:10】](https://www.bilibili.com/video/BV1KTn16ZEYV/?t=610)）：

1. **落在屋脊左边**（$I < I^{*}$）→ memory-bound，优化方向是提高算术强度（融合、增大 batch、压缩数据）；
2. **落在屋脊右边**（$I > I^{*}$）→ compute-bound，优化方向是换更强的计算单元（用上 Tensor Core）；
3. **不可能落在屋顶上方**——落在斜线上方等于「搬数据比带宽还快」，落在平线上方等于「算得比峰值算力还快」，都违反物理。所以如果你的实测点跑到了屋顶上面，一定是算术强度算错了（比如把缓存命中算成了显存访问）。

![把点投到图上：落在屋脊左边的是 memory-bound，右边的是 compute-bound](assets/Roofline%20屋顶线怎么画：H100%20的峰值算力与峰值带宽交汇在%20295%20FLOP／B/00635.webp)

视频还补了一句很实用的观察：**真实的 kernel 很少顶到屋顶**，中间插的那一截往往就是开销（overhead）。屋顶线给的是上限，不是承诺。

## 五、把真实 kernel 投到图上：三个算例

### 5.1 矩阵加法：算术强度 0.083，离拐点差 3000 多倍

视频拿 CUDA 编程指南里的矩阵加法当第一个算例（[【跳转到 10:35】](https://www.bilibili.com/video/BV1KTn16ZEYV/?t=635)）：

![矩阵加法的算术强度：读 A 4 字节 + 读 B 4 字节 + 写 C 4 字节 = 12 字节，运算只有 1 次加法 = 1 FLOP](assets/Roofline%20屋顶线怎么画：H100%20的峰值算力与峰值带宽交汇在%20295%20FLOP／B/00660.webp)

每个线程从 A 和 B 各读一个 float（4 个字节），再往 C 写回 4 个字节，一共 12 个字节；运算只有中间这一次加法，也就是一个 FLOP。所以：

$$
I = \frac{1\ \text{FLOP}}{12\ \text{B}} \approx 0.083\ \text{FLOP/B}
$$

![MatAdd 的 0.083 与屋脊点 295 差三千多倍：大多数 kernel 的算术强度都很低](assets/Roofline%20屋顶线怎么画：H100%20的峰值算力与峰值带宽交汇在%20295%20FLOP／B/00685.webp)

这里有个容易混淆的点，视频专门澄清：**`float` 这个类型决定了每个数占几个字节、也决定了该用哪种计算单元（也就是峰值算力），但它不改变 FLOP 的次数。** 换成 `double`，字节数翻倍、强度减半，运算次数还是一个。

0.083 离 295 差了 3000 多倍——**大多数 kernel 的算术强度都很低**，这是「GPU 为什么跑不满」最根本的答案。

### 5.2 屋顶要按计算单元分别画

这是全片最容易被忽略、也最重要的一条（[【跳转到 11:25】](https://www.bilibili.com/video/BV1KTn16ZEYV/?t=685)）：

![同一块 H100 上的两条屋顶：Tensor Core 989 TFLOPS，CUDA Core FP32 只有 67 TFLOPS，后者的屋脊点只有约 20](assets/Roofline%20屋顶线怎么画：H100%20的峰值算力与峰值带宽交汇在%20295%20FLOP／B/00710.webp)

同一块 H100，如果用 FP32 的 CUDA Core 来算，屋顶只有 67 TFLOPS，拐点就变成：

$$
I^{*}_{\text{FP32}} = \frac{67}{3.35} \approx 20\ \text{FLOP/B}
$$

**295 和 20，差了将近 15 倍。** 所以「我的算子是不是 compute-bound」这个问题，必须先回答「我打算用哪个计算单元算它」。

### 5.3 经典 kernel 的落点：SAXPY、FFT、矩阵乘

视频在图上标了三个经典 kernel（同一张图里都按 FP32、每个数 4 字节算）：

| kernel | 运算量 | 字节数 | 算术强度 |
| --- | --- | --- | --- |
| SAXPY（$y = a x + y$） | $2N$ | $12N$ | $1/6 \approx 0.17$ |
| FFT | $\tfrac{5}{2} N \log N$ | $16N$ | $\tfrac{5}{32}\log N$ |
| 矩阵乘（$N \times N$） | $2N^3$ | 约 $N^2$ 量级 | $N/8$ |

三者的走势完全不同：

- **SAXPY 的强度是常数 $1/6$**——N 再大也不会变，永远是 memory-bound；
- **FFT 的强度随 $\log N$ 慢慢涨**——涨得很慢；
- **矩阵乘的强度是 $N/8$，随 N 线性涨**——因为运算量是 $N^3$、访存只是 $N^2$。代入 FP32 的拐点 20，得到 $N/8 \approx 20$，即 **N 到 160 左右就越过了 FP32 的屋脊**。

视频的结论：**这是矩阵乘能吃满硬件、神经网络大获成功的关键原因之一**——只要矩阵足够大，它天然落在平屋顶上。

## 六、拐点为什么一代比一代靠右

第四章的最后一段，视频把拐点这个数字放到时间轴上（[【跳转到 12:40】](https://www.bilibili.com/video/BV1KTn16ZEYV/?t=760)）：

![屋脊点一代比一代靠右：A100 BF16 是 156，H100 BF16 是 295，H100 FP8 是 574](assets/Roofline%20屋顶线怎么画：H100%20的峰值算力与峰值带宽交汇在%20295%20FLOP／B/00785.webp)

| 硬件 | 屋脊点（FLOP/B） |
| --- | --- |
| A100 · BF16 | 156 |
| H100 · BF16 | 295 |
| H100 · FP8 | 574 |

原因是**带宽涨得没有算力快**：算力翻倍，拐点就右移一倍，于是「想吃满算力」变得越来越难。视频举了个极端的例子：B200 跑 FP4 的时候，每读一个字节要做 1125 次运算才能逃出内存瓶颈。Roofline 模型的提出者在 2008 年就预言了这一点——内存带宽会成为首要瓶颈。

由此引出一条重要的实践推论：**抬升内存瓶颈时，常常是拿计算换访存。** 压缩数据、梯度检查点，都会提高算术强度。

> 顺带一提：batch 也是把点往右推的手段——视频里用 500B 参数模型的估算说明，把多个请求拼成一个 batch，权重读一遍大家共有，延迟不变、吞吐随 batch 线性上涨，点沿斜屋顶右移，直到撞上平屋顶（[【跳转到 12:15】](https://www.bilibili.com/video/BV1KTn16ZEYV/?t=735)）。具体到 Linear / Attention 在不同 batch、seq 下的落点推导，属于相邻小节的题目，这里只作为「拐点会移动」的例证。

## 七、屋顶线管不到的地方：功耗墙

屋顶线假设「峰值算力」是能拿到的。第五章用一组实测把这个假设打穿了（[【跳转到 13:37】](https://www.bilibili.com/video/BV1KTn16ZEYV/?t=817)）。

Horace He 在《AI 版上册》里举了个真事：用 PyTorch 调用 cuBLAS 跑出 258 TFLOPS，CUTLASS 自带的 profiler 却跑出 288（快 10%），而 CUTLASS 接进 Python 又只有 257。查到最后，原因是 **profiler 默认用整数初始化输入矩阵**——矩阵里装的是什么数，居然会影响速度：

![A100 8192³ 矩阵乘：输入全零 295、全一 291、均匀分布 268、正态分布 217 TFLOPS](assets/Roofline%20屋顶线怎么画：H100%20的峰值算力与峰值带宽交汇在%20295%20FLOP／B/00839.webp)

可运算次数、运算顺序、访问的内存地址完全一样，也没有分支。真凶是**功耗**：晶体管每翻转一次状态都要耗一点电，功耗约等于时钟频率乘以每个周期翻转的晶体管数。这块 A100 的功率上限是 330 瓦，满载跑矩阵乘时两种输入都会撞到上限；撞上线以后芯片就降频——随机数翻转多，只能维持 1010 MHz 左右；全零翻转少，能维持 1210 MHz 左右。

功率上限调得越低，差距越大：150 瓦的时候全零比随机快大约 2.27 倍；反过来把时钟锁低，差距就缩小直到消失——**瓶颈从功耗换成了时钟**。

这也解释了为什么「989 TFLOPS」这个数要小心用：它是 Tensor Core 的数量 × 最高频率 × 每条指令的运算量算出来的，真实负载时根本维持不住最高频率。Harris 的结论是：H100 上的矩阵乘主要是被功耗限制的。视频还举了 NVIDIA 在训练性能评测里的一次提交：模型训练算得很密，Tensor Core 的吞吐可能被 GPU 能拿到的功率卡住，他们用 NVML 的 boost slider 把每张 H100 上 L2 缓存的一部分功率挪给了 SM，总功耗不变、SM 频率更高，端到端快了 4%。

**所以屋顶线画出来的是「硬件允许的上限」，而功耗、散热会把这个上限再往下压一截。** 但视频的结论是：电力和散热也会拖慢 GPU，最重要最常见的瓶颈仍然是计算和内存。

## 八、把整件事串起来

最后一张图把整条优化链串成了一条「瓶颈转移」的路线（[【跳转到 16:07】](https://www.bilibili.com/video/BV1KTn16ZEYV/?t=967)）：

```
开销卡住  →  CUDA Graphs、少用 Python
              ↓ 开销解决了
瓶颈转到带宽  →  融合算子、提高算术强度、上 batch
              ↓ 带宽解决了
瓶颈转到算力  →  用上 Tensor Core
              ↓ 算力也吃满了
还可能撞上功耗墙
```

**瓶颈总会转移**：找出瓶颈、抬升它，再在新的瓶颈上重复。判断工具有三个：

1. **加大规模看时间怎么涨**——涨得慢的是开销，涨得快的是计算或访存；
2. **用 profiler 看 GPU 的空隙**——空隙多说明在等 CPU；
3. **用 Roofline 看算术强度**——算一个数，和拐点比大小。

## 小结

- **屋顶线 = 两条上限线取最小值**：$P = \min(\pi,\ \beta I)$。斜线斜率是峰值带宽，平线高度是峰值算力。
- **拐点（屋脊点）就是峰值算力除以峰值带宽**：$I^{*} = \pi / \beta$。H100 BF16 上是 $989/3.35 \approx 295$ FLOP/B；换成 FP32 CUDA Core（67 TFLOPS）就只有约 20。
- **判断落点只需比较两个数**：算子算术强度 $I$ 与拐点 $I^{*}$。$I < I^{*}$ 是带宽受限，$I > I^{*}$ 是算力受限。
- **屋顶要按计算单元分别画**：Tensor Core 和 CUDA Core 是两条不同的屋顶，混用会得出错误结论。
- **大多数 kernel 的强度都很低**：矩阵加法只有 0.083，离 295 差 3000 多倍；只有矩阵乘这种 $I \propto N$ 的算子才容易吃满算力。
- **拐点一代比一代靠右**：带宽涨得没有算力快，所以「拿计算换访存」成为主流优化手段。
- **屋顶线给的是上限，不是承诺**：开销会往下压、功耗也会往下压，实测点永远在屋顶下方。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| Roofline（屋顶线） | 把「带宽 × 算术强度」和「峰值算力」两条上限画在一张图上取最小值，形如屋顶 |
| 算术强度（Arithmetic / Computational Intensity） | 每搬运一个字节的数据做了多少次浮点运算，单位 FLOP/B |
| 峰值算力 $\pi$（Peak TFLOPS） | 计算单元每秒最多能做多少次浮点运算，H100 Tensor Core BF16 约 989 TFLOPS |
| 峰值带宽 $\beta$（Peak GB/s） | 显存每秒最多能搬多少字节，H100 HBM3 约 3.35 TB/s |
| 拐点 / 屋脊点（Ridge / Knee Point） | 两条屋顶线的交点，横坐标 $I^{*} = \pi/\beta$，低于它是带宽受限，高于它是算力受限 |
| memory-bound | 被带宽卡住，点落在斜屋顶上，优化靠提高算术强度（融合、batch、压缩） |
| compute-bound | 被算力卡住，点落在平屋顶上，优化靠换更强的计算单元（Tensor Core） |
| overhead-bound | GPU 在等 CPU 派活，优化靠 CUDA Graphs、减少 Python 开销 |
| 算子融合（Operator Fusion） | 把多个逐元素算子合成一个 kernel，把 4 次全局读写降到 2 次，直接提高算术强度 |
| 功耗墙（Power Wall） | 撞到功率上限后芯片降频，标称峰值算力在真实负载下维持不住 |
