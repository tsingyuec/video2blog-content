# Warp 分歧的代价：为什么一个 if-else 会让半个 warp 空转

> 视频来源：[GPU Warp Divergence Explained: Why Branches Kill Parallelism (Visual Deep Dive) | M2L4](https://www.youtube.com/watch?v=NQDgzmvm-ss)（YouTube · Parallel Routines）｜时长约 7.6 分钟
> 导读：这支视频只讲一件事——warp 分歧。它先用动画把「掩码 + 串行」的机制演示清楚，再把代价量化成效率百分比，最后给出四类缓解策略。本文按「机制 → 三种形态 → 量化 → 缓解」的顺序复述。

## 本讲要解决的核心问题（SCQA）

**背景**：在 SIMT 执行模型里，线程按 32 个一组打包成 warp，同一 warp 内的 32 个线程共享一条指令流，同时执行同一条指令。

**冲突**：只要代码里出现 `if-else`，就必然有一部分线程想走这条路、另一部分想走那条路。一条指令流没法同时跑两段代码。

**疑问**：硬件到底怎么处理这种「同一条 warp 内的路线冲突」？代价有多大？能不能避免？

**回答（中心思想）**：硬件用**掩码 + 串行**处理分歧——先跑一条路径、掩掉另一批线程，再反过来跑第二条。于是 warp 的总时间变成各条路径时间之和，**并行效率与「唯一执行路径数」成反比**。分歧不是正确性问题，而是纯粹的吞吐损失；它有三种典型形态，也有四类可操作的缓解手段。

## 一、理想情形：32 个线程，一条指令，100% 效率

视频用一个最简单的向量加法开场：

```c
x[tid] = a[tid] + b[tid];
```

32 个线程执行**完全相同的一条指令**，只是操作的数据元素不同。所有线程走同一条路径，同步完美，效率 100%。这是 SIMT 的理想状态。[【跳转到 00:25】](https://www.youtube.com/watch?v=NQDgzmvm-ss&t=25)

## 二、分歧的第一种形态：条件分支

考虑一个 `if-else`：一部分线程满足条件，另一部分不满足。视频的例子中，线程在两条路径间交替分布——路径 A 的线程标蓝，路径 B 的线程标橙。

问题在于：**硬件必须把执行串行化**。它先执行路径 A，同时把走路径 B 的线程掩掉；然后切换，执行路径 B，此时路径 A 的线程被掩掉。[【跳转到 00:50】](https://www.youtube.com/watch?v=NQDgzmvm-ss&t=50)

![条件分支分歧：蓝橙交错的线程分布，硬件先跑路径 A 再跑路径 B，总时间 T = T_A + T_B](assets/Warp%20分歧的代价：为什么一个%20if-else%20会让半个%20warp%20空转/00075.webp)

画面右下角直接写出了结论：

$$
T_{\text{total}} = T_A + T_B
$$

这就是 **serialization penalty（串行化惩罚）**。

## 三、第二种形态：循环次数不一致

第二种分歧来自**可变循环次数**：每个线程的工作量不同，循环跑的次数也不同。

```c
int n = work_count[tid];
for (int i = 0; i < n; i++) {
    process_data(i);
}
```

视频用颜色标出每个线程的工作量：绿色是低（1～3 次迭代）、黄色是中（4～6 次）、红色是高（7～8 次）。[【跳转到 01:40】](https://www.youtube.com/watch?v=NQDgzmvm-ss&t=100)

![可变循环次数：32 个线程的工作量分布为绿黄红三档，柱状图显示最慢线程成为瓶颈](assets/Warp%20分歧的代价：为什么一个%20if-else%20会让半个%20warp%20空转/00100.webp)

warp 内线程锁步执行，先跑完的线程**不能提前退出**（[【跳转到 01:15】](https://www.youtube.com/watch?v=NQDgzmvm-ss&t=75)），只能保持非活跃状态等待。执行必须一直持续到**循环最长的那条线程**结束。柱状图里那根最高的红柱就是瓶颈——整条 warp 被它拖住，整体并行效率因此下降。

## 四、第三种形态：动态函数调用

第三种分歧来自 `switch` 语句里的动态函数调用：

```c
switch (op_type[tid]) {
    case ADD: add(); break;
    case MUL: multiply(); break;
    case DIV: divide(); break;
}
```

视频的例子中，32 个线程被分成加（蓝）、乘（橙）、除（紫）三种操作类型。硬件把这堆调用**串行化成三个执行阶段**，每个唯一函数调用占一个阶段，效率掉到大约 33%。[【跳转到 02:30】](https://www.youtube.com/watch?v=NQDgzmvm-ss&t=150)

## 五、量化：效率与「唯一路径数」成反比

把三种情形放在一起量化，结论非常干净：[【跳转到 03:20】](https://www.youtube.com/watch?v=NQDgzmvm-ss&t=200)

| 分歧情形 | 并行效率 |
| --- | --- |
| 无分歧（100% 活跃） | 100% |
| 50/50 二分（2 条路径） | 50% |
| 四路分歧（4 条路径） | 25% |
| 最坏情形（每条路径 1 个线程） | 约 3% |

![效率柱状图：无分歧 100%、二分 50%、四路 25%、最坏 3%](assets/Warp%20分歧的代价：为什么一个%20if-else%20会让半个%20warp%20空转/00125.webp)

视频把这条规律写成：

$$
\text{Efficiency} \propto \frac{1}{\text{number of unique paths}}
$$

换句话说，**warp 内出现的不同执行路径越多，有效吞吐越低**。最坏情形是 32 个线程各走一条路径，效率只剩 $1/32 \approx 3\%$。

## 六、四类缓解策略

视频随后给出四种从易到难的手段，每一种都明确说了代价。

### 6.1 数据排序：让相似的活进同一个 warp

大规模数据下，未排序的数据会让同一个 warp 里混进异质工作。**在执行前对工作项做全局排序**，相似任务就会被分到同一个 warp，相邻线程处理相似数据，产生「控制流一致」的 warp。[【跳转到 03:28】](https://www.youtube.com/watch?v=NQDgzmvm-ss&t=208)

![数据重排前：全局工作项蓝橙交错，同一个 warp 里混进了异质工作](assets/Warp%20分歧的代价：为什么一个%20if-else%20会让半个%20warp%20空转/00208.webp)

收益是双份的：既消除了 warp 内分歧，又改善了内存合并访问（memory coalescing）。代价是**全局排序本身的开销**，小规模负载上可能得不偿失。

### 6.2 谓词化（predication）：去掉分支，两条都算

第二种策略是把分支彻底拆掉，两条路径的计算**对所有线程都执行**，最后用掩码挑出正确结果：[【跳转到 04:18】](https://www.youtube.com/watch?v=NQDgzmvm-ss&t=258)

```c
// 有分支的写法（会分歧）
if (x > 0) { y = a * x; } else { y = b * x; }

// 谓词化写法（无分支）
mask  = (x > 0);
temp1 = a * x;
temp2 = b * x;
y = mask ? temp1 : temp2;
```

![谓词化改写：分支版改为 mask + 两次计算 + 选择，所有线程一起执行，利用率 100%](assets/Warp%20分歧的代价：为什么一个%20if-else%20会让半个%20warp%20空转/00283.webp)

视频把利弊列得很清楚：无分歧、100% 利用率、适合简单操作；但**在假路径上做了无用计算**，所以只适用于分支本身很便宜的情形，复杂分支不划算。

### 6.3 负载均衡：别让一条线程拖住整个 warp

第三种策略针对循环次数不均：把工作**重新分配**，让每个线程的工作量接近一致，就没人需要空等拖后腿的那条线程。[【跳转到 05:08】](https://www.youtube.com/watch?v=NQDgzmvm-ss&t=308)

具体技术包括：

- **work stealing（工作窃取）**：空闲线程从忙碌线程那里取任务；
- **动态调度**：运行时再分配任务；
- **分块迭代（chunked iteration）**：把迭代切成块来均摊。

### 6.4 算法重设计：从根上消灭分支

有时候最好的办法是**换算法**。视频举的例子是原子直方图统计：

```c
// 分歧写法：每个 bin 一个分支
int bin = value / bin_size;
if (bin == 0)      atomicAdd(&hist[0], 1);
else if (bin == 1) atomicAdd(&hist[1], 1);
// ...

// 收敛写法：用算出来的下标，一条路径
int bin = value / bin_size;
atomicAdd(&hist[bin], 1);   // Single path!
```

![算法重设计：把「每个 bin 一个分支」改成「用算出的下标寻址」，只剩一条路径](assets/Warp%20分歧的代价：为什么一个%20if-else%20会让半个%20warp%20空转/00358.webp)

视频提炼出四条原则：优先无分支计算、用算术代替条件、利用数据并行模式、单趟会产生分歧时考虑多趟算法。

## 小结

- **分歧的本质**：一个 warp 共享一条指令流，两条路径只能排队，硬件用掩码把不参与的线程关掉。
- **代价是串行化**：$T_{\text{total}} = T_A + T_B$，并行效率与唯一路径数成反比，最坏情形只剩约 3%。
- **三种形态**：条件分支、循环次数不一、动态函数调用；循环形态的瓶颈是「最长的那条线程」。
- **四类缓解**：数据排序（代价是排序开销）、谓词化（代价是假路径上的无用计算）、负载均衡、算法重设计。
- **顺序很重要**：先 profile 定位热点，再选手段，最后才考虑改算法。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| warp | 32 个线程组成的硬件执行组，共享一条指令流 |
| warp divergence | 同一 warp 内线程走不同执行路径，被迫串行 |
| serialization penalty | 分歧导致两条路径依次执行、时间相加的损失 |
| masking | 关闭不参与当前路径的线程，使其不写回结果 |
| predication | 去掉分支、让所有线程都算、再用掩码选结果 |
| work stealing | 空闲线程从忙碌线程处取任务的负载均衡技术 |
| memory coalescing | 相邻线程访问相邻地址被合并成一次访存 |
| profile | 用工具测出程序真实的热点，而不是靠猜 |
