# cp.async 双缓冲：只改指令顺序，把 GEMM 从 17.61 提到 23.24 TFLOPS

> 视频来源：[The Two Halves Of A GPU Never Work At Once - CUDA programming 6](https://www.youtube.com/watch?v=bBZy_QVrkGw)（YouTube · AI performance lab）｜时长约 9.7 分钟
> 导读：这是「一级一级爬到 cuBLAS」系列的一集（标题页标为 rung 6：cp.async double buffering），主题是**软件流水线**：用 `cp.async` + 双缓冲把「搬数据」和「算数据」从轮流干活变成同时干活。整集只讲一个技术，但每个数字都来自实跑：17.61 → 21.30 → 23.24 TFLOPS，访存延迟停顿从 1.24 掉到 0.01。本文按「先看清浪费 → 再理解指令 → 再看代码 → 最后逐条核对代价」的顺序复述。

## 本讲要解决的核心问题（SCQA）

**背景**：前面几集搭出来的 GEMM kernel 都是同一个形状——**把 tile 拷进 shared memory，等拷贝完成，在 tile 上计算，然后换下一片**。这个形状跑得通，而且随着分块、寄存器 tile 等优化，性能一级一级往上爬。

**冲突**：这个形状里藏着一个从没被质疑过的浪费——**搬运和计算是轮流干的**。拷贝下一片 tile 的时候，算术单元闲着；算术单元算的时候，访存单元闲着。更糟的是，这个浪费在 profiler 里**看不见**：它表现为一次「延迟停顿（latency stall）」，于是前几集一直在想办法降低延迟，而不是消除等待本身。

**疑问**：能不能让「拷贝下一片」和「计算当前片」同时进行？

**回答（中心思想）**：能。硬件提供了一条**异步拷贝指令 `cp.async`**：线程发起它之后立刻往下走，数据在后台直接落进 shared memory，等需要时再用一条 wait 指令确认。配上**双缓冲（double buffering）**——kernel 同时持有两份 tile，一份在算、一份在填——就得到了软件流水线。核心只有一句话：**提前发起、然后计算、最后等待**。同配置下实测提升 21%，访存延迟停顿从 1.24 降到 0.01。

## 一、先看清浪费：两条时间线，永远只有一条在亮

讲者建议「把这件事画成时间，而不是写成文字」，因为一画出来浪费就非常刺眼。

![老形状：copy → then wait → then compute，任何一个时刻都有一个单元闲着](assets/cp.async%20双缓冲：只改指令顺序，把%20GEMM%20从%2017.61%20提到%2023.24%20TFLOPS/00000.webp)

画成两条泳道就是下面这样：

![时间线：访存管线拷 tile 1 时算术单元空转；算术单元算 tile 1 时访存管线空转](assets/cp.async%20双缓冲：只改指令顺序，把%20GEMM%20从%2017.61%20提到%2023.24%20TFLOPS/00040.webp)

- 上面一行是**访存管线（memory pipe）**：拷 tile 1 → 空闲 → 拷 tile 2 → 空闲……
- 下面一行是**算术单元（arithmetic）**：空闲 → 算 tile 1 → 空闲 → 算 tile 2……

两个单元像在轮流值班，每个都在等对方。结论是**算术大约只跑到它可能速率的一半**——不是因为哪里慢，而是因为拷贝在飞的时候根本没给它活干。

而且这个浪费不是小数目：**拷贝是循环里最慢的一段**，因为它要一路走到内存系统去。所以每一次迭代里，算术单元都有很大一部分时间是闲着的。[【跳转到 01:00】](https://www.youtube.com/watch?v=bBZy_QVrkGw&t=60)

## 二、`cp.async` 是什么：一条「可以忘掉」的拷贝

要重叠，得先让「拷贝」不再阻塞线程。硬件为此提供了一条专门的指令。理解它最好的方式是跟普通 load 对比：

![普通 load 与异步拷贝的对比：普通 load 会阻塞线程，异步拷贝发起后线程立刻继续](assets/cp.async%20双缓冲：只改指令顺序，把%20GEMM%20从%2017.61%20提到%2023.24%20TFLOPS/00100.webp)

| | 普通 load | 异步拷贝 `cp.async` |
| --- | --- | --- |
| 发起后 | 线程**停下来**等数据到达 | 线程**立刻继续**执行后面的算术 |
| 数据去哪 | 先进寄存器 | 直接落进 shared memory |
| 谁来搬 | 线程自己 | 硬件在后台搬 |
| 什么时候能读 | 数据到了才能读 | 需要时用 wait 指令确认 |

讲者的比喻很到位：**这是一次你可以忘掉的拷贝**。线程不需要「收集」任何东西，数据自己会落到 shared memory；等到真要读这片 tile 的时候，一条 wait 指令告诉线程「你之前要的那片已经到了，可以读了」。[【跳转到 01:40】](https://www.youtube.com/watch?v=bBZy_QVrkGw&t=100)

讲者还补了一句值得注意的话：**这条指令是硬件专门为这个模式加进去的**。硬件厂商不会为一个小众写法新增指令，这本身就是「这个模式值得学」的强证据。[【跳转到 02:00】](https://www.youtube.com/watch?v=bBZy_QVrkGw&t=120)

## 三、双缓冲：两份 tile，交替角色

有了异步拷贝，接下来只需要让 kernel **同时持有两份 tile**：

![双缓冲：buffer 0 正在被拷贝填充（async in flight），buffer 1 正在被算术读取（computing now）](assets/cp.async%20双缓冲：只改指令顺序，把%20GEMM%20从%2017.61%20提到%2023.24%20TFLOPS/00140.webp)

- 算术读 buffer 0 的时候，异步拷贝在填 buffer 1；
- 到这一片的末尾，两个 buffer **交换角色**；
- 结果是：算术不停，拷贝也不停。

**代价是明码标价的，必须说清楚**：每个 block 的 shared memory **翻倍**，从 24.58 KB 涨到 49.15 KB。这正是这个 kernel 的 occupancy 不高的原因——我们是在**用容量换重叠**。

还有第二个代价，更隐蔽：两个 buffer 每片都要换角色，所以 kernel 必须**记住哪一块是有效数据、哪一块正在被填**。这份「记账」工作本身也是复杂度。[【跳转到 02:40】](https://www.youtube.com/watch?v=bBZy_QVrkGw&t=160)

## 四、kernel 结构：三件事的顺序就是全部技术

讲者把流水线 kernel 的结构概括成三行伪代码：

```
copy 函数：为 block 需要的每个元素发起异步传输，然后作为一个组提交（commit）
主循环：  先为「下一片」发起拷贝  ← 这一行创造了重叠
          再在当前 buffer 上做算术
循环末尾：等待循环开头发起的那次拷贝，然后 __syncthreads()
```

**顺序就是全部技术**：提前发起（issue early）→ 计算（compute）→ 最后等待（wait）。[【跳转到 03:00】](https://www.youtube.com/watch?v=bBZy_QVrkGw&t=180)

真实代码长这样：

![流水线 kernel 的代码：copy_async 发下一片、commit 成组、在当前片上计算、末尾 wait + __syncthreads](assets/cp.async%20双缓冲：只改指令顺序，把%20GEMM%20从%2017.61%20提到%2023.24%20TFLOPS/00160.webp)

```cuda
copy_async(As[0], A, k0);        // stage 0
copy_async(Bs[0], B, k0);
__pipeline_commit();
for (k0 = 0; k0 < K; k0 += BK) {
  if (k0+BK < K) {               // issue NEXT
    copy_async(As[nxt], A, k0+BK);
    copy_async(Bs[nxt], B, k0+BK);
    __pipeline_commit();
  }
  for (k = 0; k < BK; k++)       // COMPUTE now
    acc += As[cur][..]*Bs[cur][..];
  __pipeline_wait_prior(0);      // WAIT last
  __syncthreads();
}
```

几个细节值得单独点出来：

- **`__pipeline_commit()` 的作用是「把这一批拷贝打成一个组」**，这样后面那条 wait 才能一次性针对整组说「都到了」。没有 commit，wait 就不知道该等谁。
- **`__pipeline_wait_prior(0)` 放在循环末尾**，而不是紧跟在 copy 后面。这一挪就是全部收益的来源：从「发起后立刻等」变成「发起后先算一会儿再等」。
- **`__syncthreads()` 仍然在末尾**。异步拷贝本身不阻塞线程，但「新 tile 已经完整」这件事需要 block 内所有线程达成一致——所以还是要屏障。这里能看出上一节讲的屏障和这一节的流水线是**配合关系**，不是替代关系。[【跳转到 03:20】](https://www.youtube.com/watch?v=bBZy_QVrkGw&t=200)

## 五、实测：21% 的收益，以及一个「消失」的计数器

同一个配置、同一个 block tile、同一个 slice 深度、同一个寄存器 tile，**只改指令顺序**：

![对比：无流水线 17.61，双缓冲 21.30，提升 21%](assets/cp.async%20双缓冲：只改指令顺序，把%20GEMM%20从%2017.61%20提到%2023.24%20TFLOPS/00200.webp)

| 版本 | 吞吐（TFLOPS） | 说明 |
| --- | --- | --- |
| 无流水线（copy, wait, compute） | 17.61 | 基线 |
| 双缓冲 | 21.30 | +21%，全部来自重叠 |
| 双缓冲 + slice depth 16（而非 32） | 23.24 | 达到 cuBLAS 的 74.7% |

讲者特意强调：**23.24 之上再往上的部分，已经不是流水线本身的功劳了**，而是重新调参（retune）带来的形状变化。[【跳转到 03:40】](https://www.youtube.com/watch?v=bBZy_QVrkGw&t=220)

比加速比更有说服力的是**反证**——看那个原本最大的计数器：

![访存延迟停顿：无流水线 1.24，流水线 0.01，低了 124 倍](assets/cp.async%20双缓冲：只改指令顺序，把%20GEMM%20从%2017.61%20提到%2023.24%20TFLOPS/00220.webp)

- 无流水线版本：memory latency stall = **1.24**
- 流水线版本：**0.01**

讲者的措辞很精确：这不是「减少」，而是**消失**——「不是我们把它压下去了，是那个等待根本不存在了」。因为算术要用的那片 tile 是**上一片时就已经发起、现在已经落地**的，所以没有任何时刻需要等拷贝。[【跳转到 04:20】](https://www.youtube.com/watch?v=bBZy_QVrkGw&t=260)

## 六、新的最大 stall 变成 `not selected`，而这是健康信号

延迟停顿消失之后，另一个计数器变成了列表第一名，名字听起来更糟，但讲者说它其实是**好消息**：

![not selected：warp 已经准备好发射指令，只是调度器把这个周期给了别的 warp](assets/cp.async%20双缓冲：只改指令顺序，把%20GEMM%20从%2017.61%20提到%2023.24%20TFLOPS/00280.webp)

**`not selected`** 的含义是：一个 warp **已经就绪**、可以发射指令了，但调度器把这个周期给了另一个 warp。所以：

- 没有任何东西被阻塞；
- 没有任何东西在等数据；
- 只是**可干的活比发射槽多**。

在流水线版本里它是 2.04，排第一。讲者的判断是：「这就是一个忙碌的 kernel 该有的样子」——最大的停顿不再是问题，而是在为一个真正被有用工作塞满的资源排队。他还给了一条实用推论：**一个 `not selected` 很高的 kernel，访存侧已经没什么可修的了**。[【跳转到 05:00】](https://www.youtube.com/watch?v=bBZy_QVrkGw&t=300)

## 七、代价：occupancy 没掉，但它本来就不高

profiler 也会给重叠记账：

![occupancy 31.44%，与无流水线版本相同；代价是每 block 49.15 KB shared memory](assets/cp.async%20双缓冲：只改指令顺序，把%20GEMM%20从%2017.61%20提到%2023.24%20TFLOPS/00300.webp)

- 流水线版本 occupancy = **31.44%**，无流水线调优版本也是 **31.44%**——**没有下降**。
- 但两边都不高，原因相同：**寄存器 tile 很大**（每线程 128 个寄存器），加上双缓冲要 **49 KB** shared memory per block。两者都限制了「一个计算单元上能塞几个 block」。

也就是说，我们只用了大约三分之一的 warp 槽位，kernel 却更快了——因为**驻留的那些 warp 从不空闲**。这句话把「occupancy 高 = 快」这个常见误解纠正了一次。[【跳转到 05:34】](https://www.youtube.com/watch?v=bBZy_QVrkGw&t=334)

## 八、第三个 buffer 反而更慢：优化的边际收益

「既然两份 tile 有用，三份是不是更有用？」讲者直接做了实验：

![三缓冲 20.30，比双缓冲 23.24 慢 13%，还多花 24 KB shared memory](assets/cp.async%20双缓冲：只改指令顺序，把%20GEMM%20从%2017.61%20提到%2023.24%20TFLOPS/00354.webp)

| 版本 | 吞吐（TFLOPS） |
| --- | --- |
| 双缓冲 | 23.24 |
| 三缓冲 | 20.30（慢 13%） |

原因：第三个 buffer 又要多花 24 KB shared memory per block，而**重叠在两份 buffer 时就已经完整了**——没有剩下什么可隐藏的延迟。多出来的 buffer 只是降低了计算单元能容纳的 block 数。

讲者把这条上升成一条通用规律：**任何优化都有边际收益递减点，过了那个点，它消耗的资源开始比它买到的重叠更贵**。[【跳转到 05:54】](https://www.youtube.com/watch?v=bBZy_QVrkGw&t=354)

## 九、换一种换序方式，性能几乎不变：技术不脆弱

还有一个变体值得记一笔：把两个 buffer 的交换顺序**反过来**——拷贝的目标是算术刚刚用完的那一块。

| 版本 | 吞吐（TFLOPS） |
| --- | --- |
| 标准换序 | 21.30 |
| 反向换序 | 20.92 |

差不到 2%。讲者的结论是：**「哪块是哪块」的精确记账并不太重要，只要保证同一时刻拷贝和算术瞄准的是不同的 buffer**。他的一句话总结很好用——**起作用的原理，不是细节**。[【跳转到 06:18】](https://www.youtube.com/watch?v=bBZy_QVrkGw&t=378)

## 十、一个被忽略很久的陷阱：L2 缓存驻留

讲者在这里补了一个「整个系列都成立、但直到现在才有意义」的事实：

![缓存陷阱：2048³ 的三个矩阵共 50.3 MB，装得进 64 MiB 的 L2；4096³ 是 201 MB，装不下](assets/cp.async%20双缓冲：只改指令顺序，把%20GEMM%20从%2017.61%20提到%2023.24%20TFLOPS/00421.webp)

| 规模 | 三个矩阵总量 | 64 MiB L2 |
| --- | --- | --- |
| 2048³ | 50.3 MB | 装得下 |
| 4096³ | 201 MB | 装不下 |

这意味着**同一个 kernel 在两个规模下，profiler 报出来的计数器不一样**：小规模时大量命中缓存，大规模时大量走主存。所以讲者的提醒是：**这个系列里所有与规模相关的结果，都部分地是「缓存驻留」的结果**，比较两次测量时不能忽略这一点。他还顺带解释了为什么前面几级在 2048³ 下看起来那么好——不是那些 kernel 更快，而是**同样的 kernel 在读一个刚好装得下整个问题的缓存**。[【跳转到 07:01】](https://www.youtube.com/watch?v=bBZy_QVrkGw&t=421)

## 十一、最佳配置与整条阶梯

在重新调参之前，流水线的最佳配置是这样的：

![最佳流水线配置：block tile 64×128，slice depth 16，thread shape 16×8，register tile 8×8（64 累加器），2 级双缓冲](assets/cp.async%20双缓冲：只改指令顺序，把%20GEMM%20从%2017.61%20提到%2023.24%20TFLOPS/00441.webp)

| 参数 | 取值 |
| --- | --- |
| block tile | 64 × 128 |
| slice depth | 16（比之前的 32 更小） |

## 十二、这一集没有解决的问题

讲者主动划出了边界，这段比加速比更值得学：

![这一集没有 settle 的东西：stage count × slice depth 的网格没有扫，双缓冲只测了 3 个 slice depth，三缓冲只测了 1 个点](assets/cp.async%20双缓冲：只改指令顺序，把%20GEMM%20从%2017.61%20提到%2023.24%20TFLOPS/00525.webp)

- **stage count × slice depth 的二维网格没有扫**；
- 双缓冲测了 **3 个** slice depth；
- 三缓冲只在 `BK=16` 上测了 **1 个点**。

所以「三个点 + 一个离群点」并不构成一张网格。他能说的是：**三缓冲的结果是真实测量，「更多 buffer 不再有帮助」这个结论有支撑**；但不能说最优 stage 数是多少，只能说在那个配置下**不是 3**。另外**没有锁频**，所以三缓冲那 13% 的惩罚和这里其它数字带着同样的不确定性。[【跳转到 08:45】](https://www.youtube.com/watch?v=bBZy_QVrkGw&t=525)

## 小结

- **老形状的根本浪费**是「搬运」和「计算」轮流干活，且它在 profiler 里伪装成延迟停顿，容易被误诊。
- **`cp.async`** 让线程发起拷贝后立刻继续，数据直接落进 shared memory，需要时用 wait 确认；`__pipeline_commit()` 把一批拷贝打成组，`__pipeline_wait_prior(0)` 等整组。
- **双缓冲**用两份 tile 交换角色实现重叠，代价是 shared memory 翻倍（24.58 → 49.15 KB）和「哪块有效」的记账复杂度。
- **顺序就是技术**：提前发起 → 计算 → 最后等待。同配置提升 21%（17.61 → 21.30），调 slice depth 到 16 后到 23.24（cuBLAS 的 74.7%）。
- **最好的证据是计数器消失**：访存延迟停顿 1.24 → 0.01；新的第一名变成 `not selected`，那是「活多到要排队」的健康信号。
- **occupancy 31.44% 没掉也没高**，因为寄存器 tile 大（128/线程）+ 49 KB shared memory；快的原因是驻留的 warp 从不空闲。
- **第三个 buffer 反而慢 13%**：重叠在两份时就已完整，加 buffer 只花容量。
- **换序变体只差 2%**：原理（拷贝与算术瞄准不同 buffer）比记账细节重要。
- **缓存驻留会影响所有与规模相关的结论**：2048³ 的 50.3 MB 装得进 64 MiB L2，4096³ 的 201 MB 装不下。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| 软件流水线（software pipelining） | 在循环里让「搬下一片」与「算当前片」同时进行 |
| `cp.async` | 异步拷贝指令：发起后线程不阻塞，数据直接落进 shared memory |
| `__pipeline_commit()` | 把已发起的异步拷贝打成一个组，便于统一等待 |
| `__pipeline_wait_prior(0)` | 等待最近一次 commit 的那组拷贝全部完成 |
| 双缓冲（double buffering） | 同时持有两份 tile，一份在算、一份在填，每片交换角色 |
| 延迟停顿（latency stall） | warp 因等待访存数据而无法发射指令的时间比例 |
| `not selected` | warp 已就绪但调度器把周期给了别的 warp，属于「忙」而非「堵」 |
| occupancy | 实际驻留的 warp 数占硬件上限的比例 |
| L2 驻留 | 问题规模是否小到能整个装进 L2，会显著影响 profiler 读数 |
