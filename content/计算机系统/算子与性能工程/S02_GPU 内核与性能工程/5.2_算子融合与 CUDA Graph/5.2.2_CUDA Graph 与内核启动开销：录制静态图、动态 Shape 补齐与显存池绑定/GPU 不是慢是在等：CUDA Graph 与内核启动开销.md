# GPU 不是慢是在等：CUDA Graph 与内核启动开销

> 视频来源：[The GPU Isn't Slow, It's Waiting: How CUDA Graphs Fix LLM Decode Latency](https://www.youtube.com/watch?v=A8CRIEBzja8)（YouTube · SkildCore）｜时长约 14 分钟
> 导读：一支把「启动税」算成具体数字的解说片：从一次内核启动的六跳开始，讲到图捕获状态机、冻结世界契约、分桶与显存池，最后给出图税的 GB 账本与四条硬限制。本文按原片顺序覆盖，不涉及 QKV 合并、RoPE 融合等算子级融合手法（那是 5.2.1 的内容）。

## 本讲要解决的核心问题（SCQA）

**背景**：GPU 执行一条指令不到一纳秒，一个只算一个 token 的注意力内核也只要 5 微秒左右。按理说，小 batch 推理应该被算力限制。

**冲突**：但每个算子都要由 CPU 发一次「启动」，这次启动要穿过驱动、命令缓冲区、PCIe 总线，单次成本 5–10 微秒，几乎全在主机侧串行完成。当内核比启动还短时，GPU 就在两次到达之间空转——你越优化内核，空转越明显。

**疑问**：既然瓶颈不在计算而在「提交工作的方式」，能不能把提交成本一次性摊掉？代价是什么？

**回答（中心思想）**：CUDA Graph 把一段固定的 GPU 工作录成一张有向无环图，此后一次启动就引爆整张图，把「30 次启动」变成「1 次启动」。它不加速任何内核，只消灭派发开销；而这份收益的代价是一份硬契约——地址冻结、形状冻结、控制流上台。真正决定成败的不是捕获本身，而是「哪一段可以进图、形状怎么补齐成桶、显存池怎么绑定」这套分诊工作。

## 一、启动税：一次内核启动要走六跳

### 1.1 六跳路径，5–10 微秒

一次 `cudaLaunchKernel` 并不是「告诉 GPU 一句话」那么简单。原片把这条路径拆成六段，每段都有自己的成本：

![一次内核启动的六跳：从 cudaLaunchKernel 到 block dispatch，合计约 8 微秒，几乎全部发生在主机侧](assets/GPU%20不是慢是在等：CUDA%20Graph%20与内核启动开销/00050.webp)

| 环节 | 做什么 | 片中量级 |
| --- | --- | --- |
| `cudaLaunchKernel` | 运行时校验、打包参数 | 1.2 µs |
| driver ioctl | 流加锁、环形缓冲区预留 | 1.6 µs |
| doorbell write | 写 MMIO 寄存器通知引擎 | 0.8 µs |
| PCIe Express | 命令包 DMA 传输 | 1.4 µs |
| front-end fetch | GPC 命令解析器取指 | 1.5 µs |
| block dispatch | 调度器仲裁、唤醒线程块 | 1.5 µs |

合计约 8 微秒，而且「几乎没有任何一微秒发生在 GPU 上」。片中的一句话很形象：**厨房比服务员快**——GPU 早就把菜做完了，是点单的人太慢。

![5 微秒的启动税：主机侧派发占用 98%，而 GPU 计算只占 23%，大部分时间在等启动队列](assets/GPU%20不是慢是在等：CUDA%20Graph%20与内核启动开销/00025.webp)

[【跳转到 00:25】](https://www.youtube.com/watch?v=A8CRIEBzja8&t=25)

### 1.2 launch-bound：内核越快，缝越宽

把这条路径画到时间线上，病灶就出现了：CPU 一个内核接一个内核地发射，每个花掉几微秒驱动时间；GPU 完成每个内核比这还快，于是在两次到达之间「断粮」。

![launch-bound 区间：主机侧连续 Launch，GPU 侧计算块之间是斜纹的「饥饿」区，设备空闲超过 40%](assets/GPU%20不是慢是在等：CUDA%20Graph%20与内核启动开销/00100.webp)

这就是 **launch-bound（受启动限制）区间**：设备利用率塌到地板，主机却烧掉一整个核在派活。更反直觉的是，你在 GPU 上做的每一项优化，只是把 CPU 要填的那道缝拉得更宽——**你把自己优化进了死角**，加速器被主板上那颗芯片限速了。

[【跳转到 01:15】](https://www.youtube.com/watch?v=A8CRIEBzja8&t=75)

### 1.3 算一遍 decode step 的账

为什么偏偏是 decode 阶段最惨？因为 decode 每生成一个 token 都要把整个模型走一遍，而 batch 很小时，每层的内核都短得可怜。

![decode-step 算术：每步 30 个内核、每次启动 8 微秒，240 微秒的启动税对比 60 微秒真实计算，开销占 80%](assets/GPU%20不是慢是在等：CUDA%20Graph%20与内核启动开销/00125.webp)

- 每步内核数：约 30 个（matmul、layer norm、softmax、逐元素加法……）
- 每次启动：8 µs → 每步 240 µs 的税
- batch = 1 时的真实计算：约 60 µs
- 结果：**80% 的墙钟时间在赶羊**，而不是在算

片中给出的结论很尖锐：吞吐不是由数据手册上的算力决定的，而是由驱动接单的速度决定的。

## 二、摊销：把 30 次启动压成 1 次

### 2.1 捕获、实例化、上传、重放

解法来自一条古老的系统编程直觉：**别按次付调用费，把它摊到一个可重放的对象上**。

![把文书工作摊销：eager 模式每步 30 次启动共 240 微秒；图模式一次启动约 7 微秒，税降为 1/34](assets/GPU%20不是慢是在等：CUDA%20Graph%20与内核启动开销/00175.webp)

图的生命周期在原片里被拆成五个状态：

![捕获机制的五态：NORMAL → CAPTURING → SEALED → COMPILED → ON-DEVICE，每次重放只敲一次门铃](assets/GPU%20不是慢是在等：CUDA%20Graph%20与内核启动开销/00225.webp)

1. **NORMAL**：流处于普通模式，启动立即执行。
2. **CAPTURING**：`cudaStreamBeginCapture` 把流切成录制状态，此时启动**不再执行，只被记录**。每一次内核调用、每一次内存操作都变成一个节点，你在代码里写的顺序变成边。
3. **SEALED**：`cudaStreamEndCapture` 把对象封起来。
4. **COMPILED**：实例化（instantiate）把它编译成调度器能原生理解的、驻留设备侧的形态。
5. **ON-DEVICE**：上传到卡上，此后一次启动就是敲一次门铃，引爆整张依赖网络。

对应到 PyTorch，就是 `torch.cuda.graph` 上下文管理器 + `g.replay()`；对应到 CUDA C，就是 `cudaStreamBeginCapture` / `cudaGraphInstantiate` / `cudaGraphLaunch`。

[【跳转到 03:20】](https://www.youtube.com/watch?v=A8CRIEBzja8&t=200)

### 2.2 图不是列表，是声明式的依赖网络

捕获下来的东西不是「一串按顺序排好的内核」，而是一张图：内核节点保存完整的启动配置（函数指针、grid/block 维度、参数缓冲区），依赖边声明谁必须先退休。

![声明依赖而非队列：layer norm 分出两条分支，matmul QKV、attention、softmax 可以重叠，关键路径只有 4 个节点](assets/GPU%20不是慢是在等：CUDA%20Graph%20与内核启动开销/00250.webp)

因为调度提前声明好了，硬件不再强制单一队列顺序：独立分支可以并发执行，softmax 和残差加法可以重叠，调度器在输入一落地就派发 wavefront。片中的说法是：**设备不再按「线」思考，而开始按「电路」思考**，那些原本被串行化结构性地藏起来的延迟，直接从关键路径上消失了。

[【跳转到 03:45】](https://www.youtube.com/watch?v=A8CRIEBzja8&t=225)

## 三、冻结世界的契约：图的限制清单

### 3.1 一张图能表达什么，不能表达什么

「图是冻结的」这一条约束，解释了 API 里的每一个设计决定。原片给了一张非常实用的对照表：

![冻结世界契约：左侧是捕获区内的禁区（resize、读时钟、print、按设备值分支、改指针），右侧是靠纪律换来的自由](assets/GPU%20不是慢是在等：CUDA%20Graph%20与内核启动开销/00275.webp)

| 捕获区内禁止 | 原因 |
| --- | --- |
| 张量 resize / 重新分配 | 地址会变，烤进参数的指针立刻失效 |
| 读设备时钟 | 每次结果不同，图无法表达「不同的工作」 |
| `printf` / 调试探针 | 同上，且会引入同步 |
| 按设备上的值在主机侧分支 | 图没有表达「选择」的词汇 |
| 指针值变化 | 参数被冻结在捕获时刻 |

反过来，靠纪律可以换来的自由：**把缓冲区钉死**（指针烤进去）、**把 batch 补齐成桶**（形状精确）、**把控制流抬到主机侧**、**让动态数据流经间接表**（见第四节）、**保证每一步工作完全相同**（免费重放）。

### 3.2 违规的四种典型形态

原片在结尾把「图说不」的情形又收拢了一遍，这一页几乎可以直接当检查清单用：

![图说「不」：捕获区内同步、捕获中途懒初始化句柄、热路径上 resize、按设备采样值分支，全部在捕获期中止](assets/GPU%20不是慢是在等：CUDA%20Graph%20与内核启动开销/00775.webp)

- `cudaStreamSynchronize` 出现在捕获区内 → 强制了一种图无法表达的顺序
- 某个库在捕获中途懒初始化句柄 → 产生的工作和录制时不同
- 热路径上 `tensor.resize_` → 地址搬移，烤死的指针全废
- 从设备显存读出采样温度、再在主机上分支 → 分支会改变工作

每一次失败都是同一句话换了件衣服：**你的程序里含有一个图无法表达的事实**。片中的处理原则是：不要删掉约束，而是把动态决策抬到捕获边界之上，边界之下只留那些每一步都可证明完全相同的工作。「大部分性能是在这次分诊里挣到的，而不是在捕获本身。」

## 四、动态 Shape 与显存池：两处必须打的补丁

### 4.1 分桶：把变化的形状补齐成固定的形状

LLM 推理天然是动态的：prompt 长度在变、batch 大小在变、KV cache 每步都在长。图却要求形状精确。原片给出的工程答案是**分桶（bucketing）**：

![引擎变成放图机：prefill 保持 eager（prompt 长度变化大），decode 按 batch=1/2/4/8/16/32 各准备一张图](assets/GPU%20不是慢是在等：CUDA%20Graph%20与内核启动开销/00475.webp)

- **prefill 保持 eager**：prompt 长度变化太大，捕获不划算。
- **decode 全部重放**：形状几乎不变，是 launch-bound 的绝佳案例。
- 启动时按 batch size 各捕获一张图，一个形状一个桶，整个进程生命周期都用它们。
- 小请求 **padding 到最近的桶**，吃掉一点算力浪费。

分桶不只是性能问题，它是**容量规划**问题：

![分桶即容量规划：观测到的 batch 分布（b4 占 22%、b8 占 34%、b16 占 21%）对应每桶 0.4–3.9 GB 的池，6 张图合计钉住 9.1 GB](assets/GPU%20不是慢是在等：CUDA%20Graph%20与内核启动开销/00525.webp)

每张捕获的图都会钉住一组设备缓冲区，而且**捕获本身很贵**（要跑一遍模型、分配池、实例化设备镜像）。所以工程旋钮是「观测到的 batch size 直方图」对「每个桶的 GB 数」：估错了，你要么在几十张图之间把显存碎片化，要么在流量尖峰时掉进慢速的 eager 回退。

[【跳转到 08:20】](https://www.youtube.com/watch?v=A8CRIEBzja8&t=500)

### 4.2 间接层：地址烤死，数据流动

KV cache 是设计里最硬的约束：它每步长一个位置，而图不允许新的分配。解法是让**指针不动、映射动**：

![烤死地址、原地改数据：图的内核参数里 table_ptr 冻结在捕获时刻，block table 的内容每步原地重写，指向不同的物理块](assets/GPU%20不是慢是在等：CUDA%20Graph%20与内核启动开销/00625.webp)

引擎预分配一个 page/block 池，捕获时让内核参数指向 block table——一张**间接表**，内核在重放时才解引用它。于是：

- 图保持冻结；
- 表的内容原地改变；
- 物理块可以换，指针永远不换。

这是静态图里处理每一个动态值的通用范式：**少喂它一点，把数据交给间接层去承载变化**。片中顺手点出它在虚拟内存、文件系统里随处可见——每一个与活系统接触的冻结结构都是这么干的。

[【跳转到 10:25】](https://www.youtube.com/watch?v=A8CRIEBzja8&t=625)

### 4.3 显存池必须绑定：分配器得为图重写

为什么说「显存池绑定」是必需品而不是优化项？因为捕获期间的分配会进入一块**专用池**并被缓存下来：一个会在重放之间搬移内存的分配器，会悄悄毁掉每一个被烤死的指针。

![框架吸收痛苦：PyTorch 用按模型划分的固定地址 arena 做 graph pool，第一次运行以 eager 预热，重放把同样的算子写进同样的缓冲区并返回视图](assets/GPU%20不是慢是在等：CUDA%20Graph%20与内核启动开销/00325.webp)

PyTorch 的做法是：`graph pool` 是一块按模型划分的、设备内地址固定的 arena；第一次运行以 eager 模式执行同时预热池子；重放时同样的算子写进同样的缓冲区并返回视图，用户代码根本察觉不到下面的机械。片中的总结是：**加速器的底层系统必须先被改造，应用接口才可能看起来这么简单**。

[【跳转到 05:00】](https://www.youtube.com/watch?v=A8CRIEBzja8&t=300)
## 五、图与融合的分工：一个治带宽，一个治启动

初学者最容易混淆的一点是：既然图这么好，还要算子融合干什么？原片用一页把两者摆在一起：

![两种攻击，同一份税：融合把三个内核合成一个（少两趟 HBM 往返），图保持内核不变但把三次派发变成一次](assets/GPU%20不是慢是在等：CUDA%20Graph%20与内核启动开销/00375.webp)

| | 算子融合 | CUDA Graph |
| --- | --- | --- |
| 改什么 | 内核本身：三个小内核合成一个 | 派发方式：内核不变，顺序与依赖被冻结 |
| 治什么 | 带宽受限的链（少几趟 HBM 往返） | 启动受限的链（少几次启动） |
| 成本 | 编译器 pass + 新内核 + 每种模式数周验证 | 一次捕获，分钟级 |
| 风险 | 融合错了数值会变 | 违反契约会在捕获期报错 |

所以真实技术栈是把两者**组合**起来：编译器融合它证明得了的部分，图重放剩下的部分，**捕获边界就成了编译区域与手写区域之间的缝**。

这条分工也解释了 `torch.compile` 与图为什么收益可叠加：编译后的内核走的仍然是同一条 5 微秒启动路径；把编译后的函数包进图，追踪只发生一次，编译出的内核只被捕获一次，重放同时跳过 Python 解释器和驱动。片中给的实测结论是「收益常常是可叠加的」：编译去掉冗余算术，图去掉派发开销。

[【跳转到 05:50】](https://www.youtube.com/watch?v=A8CRIEBzja8&t=350)

再往前看一步，片中提到整个技术栈正在收敛到同一个想法：**把程序当作描述跑一次，然后把它当作机器永远执行下去**。FlashDecoding、Flash Attention、persistent kernel 都在往「更少、更胖的内核」推——一个把整个注意力块装进去的持久内核，每层只付一次启动成本；有些研究栈甚至把整个代码栈写成一个内含调度器的微内核。那是启动经济学的逻辑终点：如果启动要花几微秒，最优程序就只启动一次。图是一座桥，让你不用重写 CUDA 就拿到其中大部分收益。

## 六、收益曲线：左侧巨大，右侧收敛

图到底买到了什么？原片给了一条诚实的曲线：横轴是 batch size，纵轴是每步延迟。

![重放的收益：batch 7.6 时 eager 219 µs、图 84 µs；到 batch 46.5 时 eager 84 µs、图反而 185 µs](assets/GPU%20不是慢是在等：CUDA%20Graph%20与内核启动开销/00550.webp)

- **小 batch（交互式服务的左侧）**：每步延迟大约砍一半，在启动主导的区间能到数量级。
- **TTFT 下降**：引擎不再逐层派发。
- **TPOT 下降**：内核间的缝隙塌成一次提交。
- **大 batch（吞吐侧）**：内核长到足以自然掩盖派发，收益趋近于零，甚至因为图带来的额外约束而变慢。

片中特别强调：这些数字只在内核很短的地方出现，而那恰好就是交互式服务所在的位置。这也顺带解释了**投机解码**为什么依赖图：小模型提议若干 token，目标模型在一次前向里全部验证，这个循环必须每一步都跑到尽可能低的延迟；验证步骤形状固定、batch 维度 padding 到提议 token 数，于是整个「提议—验证」循环都落在已捕获的桶里。投机解码让每秒前向次数成倍增长，而每次前向又放大启动问题——图是让这个乘法变成收益而不是税的唯一原因。

## 七、图税：用 GB 计量的代价

### 7.1 显存账本

启动税用微秒计量，图税却用 GB 计量。每一张被捕获的图都会钉住它的显存池，而那些池**不与分配器的通用 arena 共享**：

![图的税以 GB 计：80 GB 的卡上，权重+激活 41.2 GB、6 张图的池钉住 9.1 GB、剩下的 KV cache 只有 21.7 GB](assets/GPU%20不是慢是在等：CUDA%20Graph%20与内核启动开销/00675.webp)

在小模型上这是舍入误差；在大模型、深层堆栈上，graph pool 会吃掉你本来想最大化的 KV cache 的一大块，服务器于是开始拒绝那些用 eager 本可以服务的请求。所以生产调优要直接剖析池子：每个桶的字节数、每张图的池、以及**哪些形状值得冻结**。

[【跳转到 11:15】](https://www.youtube.com/watch?v=A8CRIEBzja8&t=675)

### 7.2 调试：用探针，不用 print

冻结的程序要用另一种方式调试。重放里崩溃只会报 `graph execution failed`，没有行号，因为内核是脱离任何主机栈运行的；栈回溯指向捕获点，而不是出错的那段栈；剖析器把整张图显示成一次提交，隐藏了到底哪个节点卡住。

![电路要用探针诊断：错误只报「graph execution failed」，栈回溯指向捕获点 model.py:142，剖析器只看到一次提交](assets/GPU%20不是慢是在等：CUDA%20Graph%20与内核启动开销/00725.webp)

片中给出的工作方法可以直接照抄：

- **二分**：捕获几张子图，逐段缩小范围；
- **串行化**：用单流重放，把并发问题变成顺序问题；
- **对拍**：在每个节点边界对比 eager 与图的输出；
- **回退开关**：坏发布之后的 30 秒里，把开关留在 eager 回退上。

工具在缩小差距，但心智模型不变：**在图里，你不再写代码，你在描述电路，而电路要用探针诊断，不是用 print**。

## 八、把结论落成一份操作清单

原片最后给了一段「判决」，可以整理成一张可执行的表：

| 步骤 | 做什么 | 判断依据 |
| --- | --- | --- |
| 1. 判断是否 launch-bound | 用剖析器看每步内核数与内核时长，估算「内核数 × 5–10 µs」 | 启动税占比 > 30% 才值得上图 |
| 2. 划定捕获边界 | 只把形状固定、无同步、无主机分支的那段放进图 | 违规会在捕获期报错，这是最仁慈的失败模式 |
| 3. 补齐形状 | 按观测到的 batch 直方图选桶，小请求 padding 到最近的桶 | 桶太多会碎片化，太少会频繁回退 |
| 4. 绑定显存池 | 用框架的 graph pool，地址固定、分配被缓存 | 分配器搬移内存 = 指针全废 |
| 5. 处理动态值 | 用间接表（block table / 索引）承载变化，指针不动 | 「地址烤死，数据流动」 |
| 6. 预算显存 | 把每桶 GB 数当容量规划文档 | 图池会挤压 KV cache |
| 7. 留回退 | eager 路径保留在开关后面 | 图在变化无常的负载上会拖后腿 |

## 小结

- **瓶颈不是数学，是文书工作**：一次内核启动要走六跳、花 5–10 微秒，几乎全在主机侧串行完成；内核越短，这笔税占比越高。
- **decode 是 launch-bound 的教科书案例**：每步约 30 个内核、240 µs 启动税对 60 µs 真实计算，开销占 80%。
- **图的做法是摊销**：捕获（只记录不执行）→ 实例化（编译成设备侧形态）→ 上传 → 重放（一次门铃引爆整张依赖网络），30 次启动变 1 次。
- **图不加速内核**：它只消灭派发开销；融合治带宽受限的链，图治启动受限的链，两者可叠加。
- **静态的代价是契约**：地址冻结、形状冻结、控制流上台；resize、读时钟、print、按设备值分支都会在捕获期中止。
- **动态 shape 靠分桶 + 间接层**：prefill 保持 eager，decode 按桶重放，KV cache 用 block table 让指针不动、映射动。
- **显存池必须绑定**：捕获期分配走专用池并被缓存，分配器不能再搬内存；代价是每张图钉住一份池，图税用 GB 计量。
- **收益有边界**：小 batch 延迟砍半甚至数量级，大 batch 收敛甚至倒退；调试要靠二分、对拍与回退开关。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| 启动开销（launch overhead） | 从 CPU 发起一次内核启动到 GPU 真正看到工作之间的主机侧成本，约 5–10 µs |
| launch-bound | 内核太短、GPU 在两次启动之间空转，性能由派发速度而非算力决定的区间 |
| 图捕获（capture） | 把流切到录制模式，只记录内核与内存操作及其依赖，不真正执行 |
| 实例化（instantiate） | 把捕获到的图编译成调度器可原生执行、驻留设备侧的可执行图 |
| 重放（replay / graph launch） | 用一次 API 调用发射整张图，跳过逐内核的驱动提交 |
| 桶（bucket） | 一组固定形状的图，小请求 padding 到最近的桶以复用已捕获的图 |
| 间接表（block table） | 图的内核参数指向的表，重放时才解引用，让物理地址可变而指针不变 |
| graph pool | 框架为图专门维护的固定地址显存池，捕获期分配从这里出，且不搬移 |
| 图税（graph tax） | 每张图钉住的显存总量，用 GB 计量，会挤压 KV cache |
