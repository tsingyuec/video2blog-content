> 视频来源：[Part 3: CUDA Graphs - Memory Management, Capture Safety, Graph Updates](https://www.youtube.com/watch?v=mtf8E33lfCM)（YouTube · mohit）｜时长约 8 分钟

## 本讲要解决的核心问题（SCQA）

**背景**：前两期已经讲清：正常的 CPU→GPU 执行长什么样、启动开销从哪来、图怎么捕获与重放、以及为什么 decode 阶段最需要图。

**冲突**：一旦真的在项目里用图，就会遇到三类麻烦：重放时图期待的内存地址变了、捕获中途某个操作让捕获失效、以及负载变了但图已经建好。

**疑问**：图到底对显存有什么要求？哪些操作能安全捕获？图建好之后还能改吗？

**回答（中心思想）**：图捕获的是「操作 + 地址」的绑定关系，所以**地址必须稳定、数据可以变**；捕获只接受一段兼容的 GPU 工作序列，同步与主机侧控制流会直接破坏它；图建好之后有三层变更手段——改节点参数、`cudaGraphExecUpdate` 做兼容更新、以及不兼容时重建可执行图。

## 一、显存：地址冻结，数据流动

### 1.1 重放不会重跑你的代码

[【跳转到 00:25】](https://www.youtube.com/watch?v=mtf8E33lfCM&t=25)

关于 CUDA Graph 最重要的一件事：**重放一张图时，我们并不是把原来的 Python 或 CUDA 代码从头再跑一遍**。捕获期间，CUDA 记录的是具体的 GPU 操作序列，而这些操作会引用 GPU 显存里的特定位置。

![显存行为演示：张量在捕获前分配在固定地址，新数据被拷进同一块缓冲区，地址始终不变](assets/CUDA%20Graph%20的显存池、捕获安全与图更新/00050.webp)

举个简单的例子：假设有一个输入张量存在 GPU 的某个地方，我们捕获了一段使用这个张量的操作序列。那么重放这张图时，这些被捕获的操作**期望它们的内存引用依然有效**。这就是「稳定内存地址」对 CUDA Graph 如此重要的原因。

但这并不意味着输入数据永远不能变：每次拿到新输入，我们把新数据拷贝到同一块缓冲区里，然后照常重放图。也就是说：

- **数据**可以在两次重放之间变化；
- **内存地址**必须保持不变。

![图重放：同一张图、同一批内核、同一个输入地址，只是缓冲区里的内容换成了 v2](assets/CUDA%20Graph%20的显存池、捕获安全与图更新/00150.webp)

[【跳转到 01:00】](https://www.youtube.com/watch?v=mtf8E33lfCM&t=60)

### 1.2 显存的另一面：捕获期的分配

显存还有另一面：**捕获期间的分配**。像 PyTorch 这样的框架必须仔细管理与被捕获图相关的分配，这里有一个权衡：

- 如果我们捕获多张图，每张图可能有各自的显存需求，**整体显存占用就会上升**；
- 在某些场景下，如果多张图的执行模式允许，它们**可以共享显存池**，从而缓解这个开销。

[【跳转到 02:30】](https://www.youtube.com/watch?v=mtf8E33lfCM&t=150)

这里要理解的核心是：CUDA Graph 关心的不只是「执行哪些操作」，那些被捕获的操作还依赖「数据住在哪」。这就是为什么一旦在真实负载里用图，**稳定地址、静态缓冲区、显存池管理**就都变得重要。

[【跳转到 02:14】](https://www.youtube.com/watch?v=mtf8E33lfCM&t=134)

## 二、捕获安全：图不是「把你做的一切录下来」

### 2.1 能捕获什么

下一个问题：能不能把任意操作都塞进捕获区？**答案是不能**。CUDA 对「流正在被捕获时哪些事可以安全发生」有明确的规则。

![捕获时间线：上半部分是捕获安全的 GPU 工作（内核启动、异步拷贝），中间是破坏捕获的操作（CPU-GPU 同步、主机侧逻辑、不支持的算子），下半是干净的流水线](assets/CUDA%20Graph%20的显存池、捕获安全与图更新/00250.webp)

- **内核启动**可以被捕获成图里的一个节点；
- **异步内存拷贝**在按「捕获兼容」的方式使用时也可以被捕获；
- 随着更多 GPU 操作被提交，CUDA 把这些操作以及它们之间的依赖捕获下来，构建成图。

### 2.2 什么会破坏捕获

[【跳转到 03:20】](https://www.youtube.com/watch?v=mtf8E33lfCM&t=200)

问题出在那些无法安全落入捕获语义的操作上，最典型的是**同步**：

- 如果在捕获期间做某些同步，尤其是以被禁止的方式同步、或涉及被捕获工作的同步，捕获就会失效；
- 例如在捕获期间调用 `cudaDeviceSynchronize`，会强制 CPU 等待 GPU 工作，从而破坏捕获。

[【跳转到 04:10】](https://www.youtube.com/watch?v=mtf8E33lfCM&t=250)

第二个重要情形是**主机侧逻辑**：比如我们把一个值从 GPU 拷回 CPU，在 Python 或 C++ 里检查它，再决定下一个 GPU 操作发什么。这个 CPU 上的决策本身，普通 CUDA Graph 流是捕获不了的，它不会变成图里的普通节点。图捕获的是捕获期间**实际发生**的 GPU 执行路径，它不会自动把任意主机侧控制流捕获下来、在每次重放时动态执行。

此外还有一些 CUDA API 和操作带有特定的捕获限制：某个操作是否安全取决于**操作本身**和**所用的捕获模式**。一旦出现被禁止的操作，捕获可能失败，或者变得无效——也就是说，我们不能简单地结束捕获然后重放，因为那不再是一张有效的图。

### 2.3 心智模型

所以重要的心智模型是：

> **CUDA Graph 捕获不是「把我程序做的一切都录下来」，它捕获的是一段兼容的 GPU 工作序列及其依赖，好让这个执行结构之后能被高效重放。**

[【跳转到 05:25】](https://www.youtube.com/watch?v=mtf8E33lfCM&t=325)

这就是为什么在给真实负载上图之前，我们必须搞清楚**哪些部分可以安全捕获、哪些部分必须留在捕获区之外**。

[【跳转到 03:25】](https://www.youtube.com/watch?v=mtf8E33lfCM&t=205)

## 三、图更新：三层变更手段

到目前为止我们都把 CUDA Graph 当成「捕获一次、准备好、重放很多次」的东西。但真实负载里事情可能会变。假设我们已经有了这张可执行图，里面有内核 A、B、C。

![参数原地更新：可执行图里 kernel B 的启动参数（grid=128 → grid=256）用 SetParams 直接改掉，不重建图](assets/CUDA%20Graph%20的显存池、捕获安全与图更新/00375.webp)

### 3.1 第一层：改节点参数

最简单的情况是改某个已有节点的某些东西，比如把内核 B 换成不同的启动参数。CUDA 允许我们**直接更新某些节点参数**：这时我们保留同一张可执行图，只更新某个节点需要的东西。

对应到 CUDA API 就是 `cudaGraphExecKernelNodeSetParams`（更新可执行图里某个内核节点的参数）。注意这是「原地更新」——没有重新实例化，也没有重新捕获。

### 3.2 第二层：`cudaGraphExecUpdate`

[【跳转到 06:15】](https://www.youtube.com/watch?v=mtf8E33lfCM&t=375)

但有时候我们手里是一张**改动更多的新图**。为此 CUDA 提供了 `cudaGraphExecUpdate`：它把新图和已有的可执行图做比较，检查能不能在原有图上更新，而不是把一切重建一遍。

- 如果改动是**兼容的**，CUDA 就更新那张已有的可执行图，我们继续正常使用；
- 如果图变化太大，比如结构或拓扑以**不兼容**的方式变了，更新就会失败。

### 3.3 第三层：重建可执行图

[【跳转到 06:40】](https://www.youtube.com/watch?v=mtf8E33lfCM&t=400)

更新失败时，我们可能需要**重新准备一张代表新负载的可执行图**（重新实例化）。这当然更贵，但它是唯一正确的选择。

[【跳转到 07:30】](https://www.youtube.com/watch?v=mtf8E33lfCM&t=450)

![三层手段：改节点参数 → cudaGraphExecUpdate 做兼容更新 → 不兼容时重建可执行图](assets/CUDA%20Graph%20的显存池、捕获安全与图更新/00450.webp)

所以这里其实有三个层次：

| 变更规模 | 手段 | 代价 |
| --- | --- | --- |
| 单个节点的参数（如 grid/block、指针） | 直接更新节点参数 | 最低，图不变 |
| 图级但兼容的改动（增删节点、改依赖） | `cudaGraphExecUpdate` | 中，需要比较新旧图 |
| 拓扑/结构不兼容的改动 | 重新实例化一张可执行图 | 最高，等于重来 |

这些机制之所以有用，是因为**负载并不会永远一模一样**，而 CUDA 给了我们不少办法，在不重建一切的前提下处理一部分变化。

[【跳转到 07:09】](https://www.youtube.com/watch?v=mtf8E33lfCM&t=429)

## 小结

- 图捕获的是「操作 + 地址」的绑定：**地址必须稳定，数据可以变**——新数据拷进同一块缓冲区再重放。
- 捕获期的分配要由框架专门管理；多张图各有显存需求会推高总占用，执行模式允许时可以共享显存池。
- 捕获只接受兼容的 GPU 工作序列：内核启动与异步拷贝可以进图；同步（如 `cudaDeviceSynchronize`）、主机侧分支决策、以及带捕获限制的 API 会破坏捕获。
- 违规的代价通常是**捕获失效**，而不是重放时算错——这是相对温和的失败方式。
- 图建好之后有三层变更手段：改节点参数 → `cudaGraphExecUpdate` → 重建可执行图，按改动规模选择。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| 稳定地址 | 捕获时记录的内存地址在每次重放时都必须有效，数据可以换、地址不能换 |
| 捕获兼容（capture-safe） | 能在流捕获期间安全提交的操作，如内核启动、异步内存拷贝 |
| `cudaDeviceSynchronize` | 强制 CPU 等待 GPU 的同步调用，出现在捕获区内会破坏捕获 |
| 主机侧控制流 | 在 CPU 上根据 GPU 返回值决定下一步发什么，图无法表达 |
| `cudaGraphExecKernelNodeSetParams` | 原地更新可执行图中某个内核节点的参数 |
| `cudaGraphExecUpdate` | 用一张新图去更新已有可执行图，兼容则成功、不兼容则失败 |
| 可执行图（executable graph） | 实例化之后、可直接被启动的设备侧图对象 |
