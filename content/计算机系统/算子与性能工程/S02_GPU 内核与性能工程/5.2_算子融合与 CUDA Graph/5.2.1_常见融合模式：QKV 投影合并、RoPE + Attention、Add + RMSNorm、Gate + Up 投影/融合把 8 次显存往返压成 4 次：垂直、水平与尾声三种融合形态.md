# 融合把 8 次显存往返压成 4 次：垂直、水平与尾声三种融合形态

> 视频来源：[Kernel Fusion and CUDA Graphs, From the Ground Up](https://www.youtube.com/watch?v=_mwx30GqsA4)（YouTube · Sand and Lightning）｜时长约 9 分钟
> 导读：这支短片把「融合到底省了什么」逐条记账——先数清一次「乘 + 加 + sigmoid」的 8 次整张量访存，再把这套账本套到 RMSNorm、QKV 投影和 MLP 上，最后给出垂直、水平、尾声三种融合形态的名字。视频后半段讲 CUDA Graph，那是「发射开销」的另一条线，本文只做交代，机制细节留给 5.2.2。

## 本讲要解决的核心问题（SCQA）

**背景**：在 PyTorch 里，你写一行 `y = torch.sigmoid(x * w + b)`，框架会把它拆成三个算子、发射三个 GPU kernel。每个 kernel 都从显存（HBM，High Bandwidth Memory，显卡上那块大容量高带宽内存）读一整个张量，算完再写回显存。

**冲突**：视频上一集数过一个 Transformer 层里有多少个 kernel——大约 1500 次发射（幻灯片上写着 “episode 4: about 1,500 kernel launches per token”）。可这些 kernel 里绝大多数只做几个乘加，算术量小到 GPU 根本感觉不到，真正的成本全在「把数据搬来搬去」和「一次次把 kernel 发射出去」上。

**疑问**：融合（fusion）究竟省掉了什么？为什么同样的数学，写成一个 kernel 就更快？具体快在几次读写、几次发射？

**回答（中心思想）**：融合只做一件事——**让中间结果不回显存**，留在寄存器或片上 SRAM 里。这一件事同时削掉两笔账：整张量的访存次数，以及 kernel 的发射次数。视频给出三种形态：**垂直融合**接一条链（RMSNorm 内部、Add + RMSNorm），**水平融合**接共享同一份输入的并行分支（QKV 投影合并、Gate + Up 投影合并），**尾声融合**把 bias、激活这类小活儿焊到矩阵乘的尾巴上。而融合管不了「发射」这一笔——那是 CUDA Graph 的事。

## 一、两笔开销：发射与访存

### 1.1 一个层 1500 次发射，藏着一长串小 kernel

视频开场就把账摊开：一个 Transformer 层按 kernel 逐个列出来，是一长串密密麻麻的方块，数量级在 1500 次。这串清单里藏着两笔性质完全不同的开销。[【跳转到 00:25】](https://www.youtube.com/watch?v=_mwx30GqsA4&t=25)

![一个层的 kernel 清单里藏着两笔开销：发射开销在张量小时占主导，访存开销在张量大时占主导](assets/融合把%208%20次显存往返压成%204%20次：垂直、水平与尾声三种融合形态/00050.webp)

- **第一笔是发射开销（launch overhead）**：每个 kernel 都要由 CPU 通过驱动发射到 GPU 上。当张量很小——典型场景是 decode、batch size 为 1——GPU 算完一个 kernel 的时间可能比 CPU 决定下一个发射什么还短，于是 GPU 在等 CPU。
- **第二笔是访存开销（memory traffic）**：每个 kernel 都要把整个张量读一遍、写一遍。当张量很大——典型场景是 prefill、大 batch——这笔开销占主导。

这两笔账对应两个不同的对策：**kernel 融合**去对付访存流量，顺带也砍掉一部分发射；**CUDA Graph** 去对付发射本身。本文只讲第一条。

### 1.2 为什么「小算子」在 GPU 上特别亏

GPU 的强项是同时开几万个线程做同一件事。一个只处理几千个元素的逐元素算子，能喂给 GPU 的并行工作太少，绝大部分 SM（Streaming Multiprocessor，流多处理器）和 CUDA Core 都闲着。更糟的是它还要付一次完整的「读显存—算—写显存」的固定成本。所以在这种算子上，**算力是免费的，搬运才是贵的**——这是后面所有账目的前提。

## 二、把 8 次访存数成 4 次：融合的账本

### 2.1 三个 kernel 的账：5 次读、3 次写

先看最小的例子：`out = sigmoid(x * w + b)`。不融合时它是三个 kernel：

1. `multiply`：读 `x`、读 `w`，写出乘积 `xw`——2 读 1 写；
2. `add`：读 `xw`、读 `b`，写出 `sum`——2 读 1 写；
3. `sigmoid`：读 `sum`，写出 `out`——1 读 1 写。

合计 **5 次整张量读、3 次整张量写，一共 8 趟**。对这么简单的数学，数据在整张量上来回走了 8 趟。[【跳转到 00:50】](https://www.youtube.com/watch?v=_mwx30GqsA4&t=50)

![三个 kernel 各自的访存：乘法 2 读 1 写、加法 2 读 1 写、sigmoid 1 读 1 写，合计 8 趟](assets/融合把%208%20次显存往返压成%204%20次：垂直、水平与尾声三种融合形态/00075.webp)

### 2.2 融合后：3 次读、1 次写

融合版只用一个 kernel：一次把 `x`、`w`、`b` 都读进来，对每个元素在片上直接乘、加、过 sigmoid，然后只存最终结果。两个中间值 `xw` 和 `sum` **根本没有写进显存**。

于是三笔账同时变化：

| 项目 | 融合前 | 融合后 |
| --- | --- | --- |
| 整张量访存 | 8 次（5 读 3 写） | 4 次（3 读 1 写） |
| kernel 发射 | 3 次 | 1 次 |
| 临时张量 | 2 个 | 0 个 |

[【跳转到 01:15】](https://www.youtube.com/watch?v=_mwx30GqsA4&t=75)

![融合后中间结果留在寄存器，访存 8 次变 4 次、发射 3 次变 1 次、临时张量 2 个变 0 个](assets/融合把%208%20次显存往返压成%204%20次：垂直、水平与尾声三种融合形态/00100.webp)

视频在这里给了一句可以直接记住的判断：**当瓶颈是访存而不是算力时，流量砍一半，时间就接近砍一半。** 这句话是后面所有融合模式的价值公式——每种模式能省多少，就看它砍掉了几次整张量读写。

## 三、垂直融合：Add + RMSNorm

### 3.1 不融合的 RMSNorm：八步，每步一个 kernel

RMSNorm 是每个 Llama 层里的归一化。按 HuggingFace transformers 里 `LlamaRMSNorm.forward` 的写法，五行代码展开成八步：转 FP32、平方、求均值、加 epsilon、取倒数平方根（rsqrt）、相乘、转回 BF16、乘学到的权重 `weight`。

$$
\mathrm{RMSNorm}(x) = \frac{x}{\sqrt{\frac{1}{d}\sum_{i=1}^{d} x_i^2 + \epsilon}} \odot w
$$

在 eager 模式的 PyTorch 里，这八步每一步都是一个独立 kernel，而且大多数步骤都要扫一遍整个激活张量。[【跳转到 01:40】](https://www.youtube.com/watch?v=_mwx30GqsA4&t=100)

![HuggingFace 的 LlamaRMSNorm 五行代码展开成八步，eager 模式下每步一个 kernel](assets/融合把%208%20次显存往返压成%204%20次：垂直、水平与尾声三种融合形态/00125.webp)

这个规模有多夸张？视频给了一个具体数字：prefill 一个 8192 token 的 prompt 时，这个激活张量里有 **3300 多万个数**，而为了做一次归一化，要一遍又一遍地扫它。[【跳转到 02:05】](https://www.youtube.com/watch?v=_mwx30GqsA4&t=125)

### 3.2 融合的 RMSNorm：一个 kernel，两趟走

融合版在单个 kernel 里做同样的数学，对每个 token 分两趟走：

1. 第一趟走一遍向量，把平方和加起来（这是求 RMS 必须的归约）；
2. 第二趟走一遍，把每个值缩放并写出。

为什么是两趟而不是一趟？因为归一化的分母依赖整行的平方和——**必须先看完整行才能缩放任何一个元素**。这是归一化类算子与纯逐元素算子的本质区别：逐元素算子可以「读一个算一个」，归一化不行，它有一个跨整行的依赖。[【跳转到 02:30】](https://www.youtube.com/watch?v=_mwx30GqsA4&t=150)

![融合的 RMSNorm：一个 kernel 内两趟走，第一趟累加平方和，第二趟缩放写出](assets/融合把%208%20次显存往返压成%204%20次：垂直、水平与尾声三种融合形态/00150.webp)

### 3.3 vLLM 再往前一步：把残差加法也折进来

视频特别指出 vLLM 的做法：**紧挨着归一化之前的那次残差加法，被折进同一个 kernel**。于是加法、平方、均值、开方、缩放全在一次发射里完成，中间没有任何临时张量。

这就是本小节要列举的第三种模式——**Add + RMSNorm 融合**。把账算清楚：

- **融合前**：残差加法一个 kernel（读 `x`、读 `h`，写 `x+h`），RMSNorm 又要读回 `x+h` 做归约、再读一遍做缩放、再写一次结果。粗算至少 4 读 2 写 = 6 趟整张量访存，2 次发射，外加一个中间张量 `x+h`。
- **融合后**：一个 kernel 读 `x` 和 `h`，在寄存器里做加法、累加平方和、缩放，最后写一次结果。**2 读 1 写 = 3 趟访存，1 次发射，0 个中间张量。**

省下来的正是「残差和」这个中间张量的一次写回和一次读回——而它的大小和整个激活张量一样，在 prefill 长序列时就是几千万个数。

## 四、水平融合：QKV 投影合并

### 4.1 三次矩阵乘，读的是同一份输入

每个注意力层都要把输入投影三次：一次算 Q（query）、一次算 K（key）、一次算 V（value）。这是三次独立的矩阵乘，但**三次读的是同一份输入** `X`。

$$
Q = XW_Q,\qquad K = XW_K,\qquad V = XW_V
$$

### 4.2 把三个权重矩阵堆成一个

既然输入相同，就可以把三个权重矩阵沿输出维度拼成一个大的，做一次矩阵乘，再把输出按列切成三块。视频给的 Llama 3 8B 具体数字是：Q 有 4096 个输出，K 和 V 各 1024 个，合起来一次矩阵乘产出全部 **6144** 个数；输出切成三块时**不需要任何拷贝**——切片只是同一块内存的不同视图。[【跳转到 02:55】](https://www.youtube.com/watch?v=_mwx30GqsA4&t=175)

![Q、K、V 三次投影合成一次矩阵乘：4096×4096 与两个 4096×1024 拼成 4096×6144，输出按视图切三块](assets/融合把%208%20次显存往返压成%204%20次：垂直、水平与尾声三种融合形态/00200.webp)

vLLM 里这个模式有专门的名字：`QKVParallelLinear`。

### 4.3 这笔账怎么算

- **融合前**：三次矩阵乘 = 3 次 kernel 发射；输入 `X` 被读 3 次；输出 Q、K、V 分别写 3 次。
- **融合后**：1 次发射；输入 `X` 只读 1 次；输出仍然要写 3 块（Q、K、V 的数据量没变，但它们在一次 kernel 里连续写出）。

所以 QKV 投影合并省下的是：**2 次 kernel 发射 + 2 次对输入 `X` 的整张量读取**。注意它**没有**省掉输出的写入——输出数据量本来就是那么多。这一点很容易被误解：水平融合省的是「共享输入被重复读」，不是「输出不用写」。

### 4.4 同一个套路用在 MLP 上：Gate + Up 投影合并

视频紧接着说，vLLM 对 MLP 做同样的事：**gate 和 up 两次投影合成一次矩阵乘**，然后**激活和逐元素相乘合成一个融合 kernel**。[【跳转到 03:20】](https://www.youtube.com/watch?v=_mwx30GqsA4&t=200)

SwiGLU 的结构是两条并行投影吃同一份输入，一条过 SiLU 当门、一条当数据，逐元素相乘后再过 down 投影：

$$
\mathrm{SwiGLU}(x) = \big(\mathrm{SiLU}(xW_{gate}) \odot xW_{up}\big)W_{down}
$$

- **融合前**：gate 投影一个 kernel、up 投影一个 kernel、SwiGLU 一个 kernel——3 次发射；`x` 被读 2 次；gate、up 两份中间结果各写一次、又被第三个 kernel 各读一次。
- **融合后**：1 次发射；`x` 只读 1 次；gate、up 的中间结果留在寄存器里直接做 SiLU 和相乘，只写最终结果一次。

具体到「几次显存传输」的精确账目，本小节的另一篇博客（融合 SwiGLU 的 Triton 实现）里会逐笔数到 **7 次变 2 次**。

## 五、第三种形态：把小事焊到矩阵乘的尾巴上

### 5.1 矩阵乘内部早就融合好了

视频在这里澄清了一个容易混淆的点：**没有人手写矩阵乘**，因为一个好的矩阵乘已经在内部做了我们前面描述的这件事——把两个矩阵切成小到能放进片上快速存储的块，一对块只加载一次，然后反复复用里面的每个数，最后才写回显存。流量在内部已经被榨干了，这也是它必须跑在 Tensor Core 上的全部理由。[【跳转到 03:45】](https://www.youtube.com/watch?v=_mwx30GqsA4&t=225)

### 5.2 于是融合发生在「边缘」

既然内部没得省，融合就在矩阵乘的边缘做文章：把共享输入的几个乘起来（水平），把 bias、激活这类小的逐元素工作焊到尾巴上（尾声）。视频说，编译器特别爱用这第三种模式——**让结果在写进显存之前就已经是成品**。[【跳转到 04:10】](https://www.youtube.com/watch?v=_mwx30GqsA4&t=250)

尾声融合的账最简单也最漂亮：bias 加法本来需要「读结果、读 bias、写结果」3 趟，焊到矩阵乘尾部后变成 0 趟——因为结果还在累加器寄存器里没写出去。本小节另一篇博客会给出这个「白拿」的实测例子。

### 5.3 三种形态的名字

![垂直融合接一条链（norm→scale→activation），水平融合接共享同一份输入的并行分支（Q→K→V）](assets/融合把%208%20次显存往返压成%204%20次：垂直、水平与尾声三种融合形态/00225.webp)

- **垂直融合（vertical）**：上一步的输出喂给下一步，接的是一条链。例子：RMSNorm 内部的那些步骤、Add + RMSNorm。
- **水平融合（horizontal）**：几个操作互相独立、但共享同一份输入，可以并成一次。例子：Q、K、V 三次投影，gate 与 up 两次投影。
- **尾声融合（epilogue）**：把小的逐元素工作挂到矩阵乘的尾巴上。例子：bias、激活函数。

这三种形态可以叠加：一次 QKV 合并（水平）之后，输出端还能再焊上 bias（尾声）。

## 六、谁来写这些融合 kernel

### 6.1 手写：最快，但一种模式一个

有些融合 kernel 是人手写的：NVIDIA 的 Apex 里有融合的归一化层；vLLM 自带「融合残差 + 归一化」的定制 kernel；FlashInfer 和 FlashAttention 是手写的注意力 kernel。手写 kernel 通常是最快的选择，但每个只覆盖一种模式、一组有限的形状和数据类型，还得有人保证它在每一代新 GPU 上都能跑。[【跳转到 04:35】](https://www.youtube.com/watch?v=_mwx30GqsA4&t=275)

### 6.2 编译器：一次看整张图

另一个答案是编译器。调用 `torch.compile` 时，一个叫 Dynamo 的组件会看着你的 Python 代码运行，把张量操作捕获成一张图；默认后端 Inductor 一次看整张图，找出可以融合的操作，为它们写出全新的 kernel。在 NVIDIA GPU 上，它写出来的 kernel 用的是 **Triton** 这门语言。PyTorch 文档把融合称为 Inductor 做的**唯一最重要的优化**。[【跳转到 05:00】](https://www.youtube.com/watch?v=_mwx30GqsA4&t=300)

### 6.3 两个 Triton，别搞混

![Triton 是 OpenAI 的 kernel 语言，Triton Inference Server 是 NVIDIA 的推理服务器，只是同名](assets/融合把%208%20次显存往返压成%204%20次：垂直、水平与尾声三种融合形态/00375.webp)

视频专门提醒了这个坑：**Triton 这门语言**来自 OpenAI，让你用类似 Python 的代码写 GPU kernel，再编译成机器码；**Triton Inference Server** 来自 NVIDIA，是一个托管模型、对外提供网络服务的服务器。两者只是同名，别的没关系。等讲到 TensorRT-LLM 时，起作用的是那个服务器。[【跳转到 05:50】](https://www.youtube.com/watch?v=_mwx30GqsA4&t=350)

### 6.4 亲眼看见融合发生

把环境变量 `TORCH_LOGS` 设成 `output_code`（视频里口语说的是 “torch log to output code”），再跑一个编译过的模型，Inductor 会打印它生成的每个 kernel，名字就告诉你什么被融合了。其中一个叫 `fused_add_mul_sigmoid`——就是本文开头那三行，现在成了对显存的一次遍历。[【跳转到 06:15】](https://www.youtube.com/watch?v=_mwx30GqsA4&t=375)

## 七、融合管不了的那一半：发射

### 7.1 batch size 为 1 时，GPU 在等 CPU

融合减少了 kernel 数量，但并没有真正消除发射：一个融合层仍然是一串从 Python 一个接一个发出的 kernel 发射。batch size 为 1 时，GPU 上一个 kernel 跑完的速度可能比 CPU 决定下一个发射什么还快，于是 GPU 在等 CPU——**光靠融合解决不了这个问题**。[【跳转到 06:40】](https://www.youtube.com/watch?v=_mwx30GqsA4&t=400)

![batch size 为 1 时 CPU 决定下一个发射的时间与 GPU 干活的时间交替，GPU 出现空等](assets/融合把%208%20次显存往返压成%204%20次：垂直、水平与尾声三种融合形态/00400.webp)

### 7.2 CUDA Graph：录制一次，重放多次

这正是 CUDA Graph 的用途：把模型跑一遍，同时录制每一次 kernel 发射以及每个 kernel 读写的确切地址；之后 CPU 一次调用就能在 GPU 上重放整段冻结的录制序列，每次发射的开销几乎消失。代价是录制被冻结——它只对当时看到的形状和内存地址有效，新输入要先拷进同样的缓冲区才能重放，换一个 batch size 就要另一份录制。[【跳转到 07:05】](https://www.youtube.com/watch?v=_mwx30GqsA4&t=425)

vLLM 两种技术都用：先用 `torch.compile` 拿到融合 kernel，再对一组 batch size 录制 CUDA Graph，落在中间的 batch 可以补齐到最近的录制尺寸。attention 是最别扭的部分，因为它的输入每个请求都在变形状，所以 vLLM 默认只录制 attention 之间的那些部分，attention 本身放在录制之外跑。[【跳转到 07:30】](https://www.youtube.com/watch?v=_mwx30GqsA4&t=450)

这些都不是免费的：编译在服务器启动时要花时间，每份录制图都占着自己的显存，生成的 kernel 比你自己写的 Python 更难读、更难调；而且当编译器遇到追不下去的代码时，它会把图断开、退回普通执行——模型照样跑对，只是没有你期待的那份加速，而且几乎没有任何提示。[【跳转到 07:55】](https://www.youtube.com/watch?v=_mwx30GqsA4&t=475)

> CUDA Graph 的录制方式、动态 shape 补齐与显存池绑定，属于本系列 5.2.2 的内容，这里只交代它与融合的分工：**融合管访存，图管发射。**

## 小结

- 一个 Transformer 层约 1500 次 kernel 发射，成本分两笔：**发射开销**（张量小时占主导）与**访存开销**（张量大时占主导）。
- 融合的本质只有一句：**让中间结果不回显存**。于是访存次数和发射次数一起下降。
- 最小的账：`sigmoid(x*w+b)` 从 5 读 3 写（8 趟）、3 次发射、2 个临时张量，变成 3 读 1 写（4 趟）、1 次发射、0 个临时张量。
- **垂直融合**接一条链：Add + RMSNorm 从「加法一次 + 归一化多趟」变成 2 读 1 写、1 次发射，省掉残差和这个整张量中间结果。
- **水平融合**接共享输入的分支：QKV 投影从 3 次发射、3 次读 `X` 变成 1 次发射、1 次读 `X`（Llama 3 8B 一次乘出 6144 个数，切片零拷贝）；Gate + Up 同理。
- **尾声融合**把 bias、激活焊到矩阵乘尾部，让结果在写出之前就是成品。
- 矩阵乘内部早已被切块复用榨干，所以融合发生在它的边缘。
- 融合不解决发射：batch size 为 1 时 GPU 仍会等 CPU，那要靠 CUDA Graph。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| kernel | 一次在 GPU 上并行执行的函数；PyTorch 一个算子通常对应一次 kernel 发射 |
| HBM | 显卡上的高带宽显存，容量大、带宽高，但访问延迟远高于片上存储 |
| 访存流量（memory traffic） | 一个 kernel 读写的字节总量；融合主要就是在砍它 |
| 发射开销（launch overhead） | CPU 把 kernel 提交给 GPU 的固定成本，张量小时占主导 |
| 垂直融合 | 把一条链上的相邻操作合成一个 kernel，如 Add + RMSNorm |
| 水平融合 | 把共享同一份输入的独立操作合成一次，如 QKV 投影、Gate + Up 投影 |
| 尾声融合（epilogue） | 把 bias、激活等逐元素工作焊到矩阵乘的输出阶段 |
| 临时张量 | 中间结果落成的显存张量；融合后它留在寄存器里，不再分配 |
| `torch.compile` / Inductor | PyTorch 的编译路径：Dynamo 捕获计算图，Inductor 找可融合处并生成 Triton kernel |
| CUDA Graph | 录制一次 kernel 发射序列后整段重放，用来消除发射开销 |
