# TVM 的图级优化：四类算子的融合边界与一次布局重排

> 视频来源：[TVM: An Automated End-to-End Optimizing Compiler for Deep Learning](https://www.youtube.com/watch?v=oBfzb8UOVf4)（YouTube · 论文精读播客，解读论文 [TVM: An Automated End-to-End Optimizing Compiler for Deep Learning（arXiv:1802.04799）](https://arxiv.org/abs/1802.04799)）｜时长约 20 分钟
> 导读：这是一支「双人对谈式」的论文拆解，全程只有一张论文标题页，没有幻灯片翻页，所以本文只有一张配图。它的价值在于把 TVM 图优化器（graph optimizer）的两件事讲得很清楚：**按数据依赖把算子分成四类，据此决定谁能融谁**；以及**在图这一层就把数据布局换成后端喜欢的形状**。后半段讲张量表达式、虚拟线程与机器学习代价模型，本文按与「图融合、布局、内存」的相关度取舍。

## 本讲要解决的核心问题（SCQA）

**背景**：研究人员在 PyTorch / TensorFlow 里写模型，写的是「层、激活函数、损失」，而不是「怎么在芯片上分配内存、怎么发指令」。要把这些模型搬到手机、嵌入式设备、FPGA 或自研加速器上，传统做法是依赖厂商手写的算子库——NVIDIA GPU 上有 cuDNN，别的芯片上有各自的库。

**冲突**：这套做法有个硬伤——**硬件根本没有标准化**。CPU 擅长标量、GPU 擅长向量、TPU 类加速器擅长整块张量；它们的存储层次也不一样：CPU 用隐式管理的缓存，专用加速器往往要求软件显式管理片上内存。播客里用了一个比喻：这就像你写了一个英文剧本，但每个地区的剧院只听得懂当地方言，你得为每种方言重写一遍；如果某个方言没有专职翻译，那这出戏在那儿就演不了。

**疑问**：能不能不靠「为每种硬件手写一套库」，而是让编译器自己把高层模型翻译成任意硬件的指令？

**回答（中心思想）**：TVM 的办法是**自上而下先做图级优化，再自下而上做算子级代码生成**。图级优化只做两件事，但收益很大：**算子融合**（按数据依赖把算子分成四类，决定融合边界，实测带来 1.2–2 倍加速）与**布局变换**（在图这一层就把数据重排成后端喜欢的形状，避免运行时反复搬运）。当融合组合爆炸到厂商库无法覆盖时，就转向算子级代码生成：用张量表达式把「算什么」和「怎么算」分开，交给调度（schedule）去决定循环、内存块和线程。

## 一、起点：把模型变成一个纯数学的计算图

TVM 从最顶上开始：先把模型转成一张**计算图（computational graph）**，作为中间表示。这张图把 Python 代码全部剥掉，只留下纯粹的数学蓝图 [【跳转到 03:45】](https://www.youtube.com/watch?v=oBfzb8UOVf4&t=225)——**节点是一个作用于张量的数学算子，边是算子之间的数据流依赖**。

这一步的意义在于：在操心「具体是哪块硅片」之前，编译器先拿到一个**全局视角**，在这个视角上找「跨算子的低效」。后面所有图级优化都在这张图上做。

## 二、为什么必须融合：一次「内存往返」有多贵

播客里把「内存往返（memory trip）」拆得很直白： [【跳转到 04:35】](https://www.youtube.com/watch?v=oBfzb8UOVf4&t=275)

1. 你算出一个值；
2. 把它顺着总线推回主存（RAM / HBM）；
3. 下一个操作要把这个值取出来，得**一路回到主存**去拿。

关键在于第 3 步的延迟——**取数的延迟可能比计算本身慢好几个数量级**。所以融合的本质是：**让数据压根不要离开处理器附近的快速存储（寄存器/片上内存）**，把多个操作合成一个无缝的内核。

这也解释了为什么融合的收益常常「不来自多算了什么，而来自少搬了什么」。

## 三、融合的判据：按数据依赖把算子分成四类

融合能走多远，取决于算子的**数据依赖形态**。 [【跳转到 05:00】](https://www.youtube.com/watch?v=oBfzb8UOVf4&t=300)TVM 的图优化器把算子分成四类，每类的融合能力不同：

| 类别 | 含义 | 通俗类比 | 能不能融 |
| --- | --- | --- | --- |
| **injective**（单射） | 一对一映射，如给每个元素加一个常数 | 刷栅栏：可以刷完一块再刷下一块，不需要看整排栅栏 | 最容易融，可以和其他局部算子随意组合 |
| **reduction**（归约） | 压缩数据，如对张量所有元素求和 | 把一叠纸压成一张 | 可融，但要处理「先全看完才能出结果」的约束 |
| **complex-out-fusable**（复杂但输出可融） | 如二维卷积——要扫过一片像素找模式 | 需要仔细管理内存，但输出侧的数据流仍然可预测 | 可以把逐元素的 map 融到它的输出上 |
| **opaque**（不透明） | 如排序——必须看到整个数据集才能开始 | 必须先把整堆东西摊开排好 | **不能融**，只能停下来、存下来、再继续 |

这套分类的价值在于：它把「能不能融」变成了一个**可以按规则机械判断**的问题 [【跳转到 06:15】](https://www.youtube.com/watch?v=oBfzb8UOVf4&t=375)，而不用为每种算子组合手写特例。播客里说，靠这些通用规则，光是把「scale + reduction + sum」这类组合融起来，TVM 就能拿到 **1.2 倍到 2 倍**的加速——**没有多做一个浮点运算**，纯粹是少搬了数据。

注意这里的判据和「算子级融合」的手写技巧不是一回事：这里判断的是**数据依赖的形状**（一对一 / 压缩 / 输出可融 / 全局依赖），而不是「哪几种算子经常一起出现」。

## 四、布局变换：在图这一层就把数据摆好

图级优化的第二件事是**数据布局变换（data layout transformation）** [【跳转到 06:40】](https://www.youtube.com/watch?v=oBfzb8UOVf4&t=400)：把内部数据布局换成目标后端友好的形式。

原因是：**行主序 / 列主序这种「标准」存储格式，对专用张量处理器往往非常低效**。播客举了一个具体例子：如果某个加速器在数据被切成 4×4 的小块（tiling）时访存局部性最好，那么 TVM 就**在图这一层重排数据流，让数据以这种格式喂进去**。

关键的一句是：**在图级完成布局变换，可以让硬件跑在峰值利用率上，而不必在运行时浪费周期去重排数据**。反过来说，如果布局没在图这一层定下来，后面每遇到一次「格式不匹配」，就得插入一次真正的数据搬运（在 GPU 上通常表现为一个额外的 transpose / copy 内核）——这正是布局选择影响端到端性能的机制。

## 五、融合的边界：为什么不能「全融成一个」

播客里主持人问了一个很好的反问：既然融合这么好，把十几个算子全融在一起行不行？ [【跳转到 07:05】](https://www.youtube.com/watch?v=oBfzb8UOVf4&t=425)

答案是不行，而且这恰恰是**传统框架的死穴**：传统框架即使做融合，也还是依赖底层厂商库里**已经写好的那份融合实现**。而随着新算子不断出现，**可能的融合组合数是指数级膨胀的**——手调一个标准 CPU 上的卷积已经够难，手调一个「卷积 + 归约 + 特定布局变换」的融合内核就是组合爆炸的地狱。

这就逼着 TVM 从**自上而下的图优化**转向**自下而上的算子级代码生成**：它必须自己动态生成机器指令，而不是去库里找现成的。

为此 TVM 引入了**张量表达式语言（tensor expression language）** [【跳转到 08:20】](https://www.youtube.com/watch?v=oBfzb8UOVf4&t=500)，把两件事分开：

- **计算规则（compute）**：数学本身，算什么；
- **调度（schedule）**：明确指定跑哪些循环、分配哪些内存块、部署哪些线程。

播客里的比喻是「菜谱」与「厨房设备」：同一份蛋糕配方，用微波炉、篝火还是专业对流烤箱都能烤出来，变的只是执行方式。这个「计算与调度分离」的思路继承自 Halide [【跳转到 09:10】](https://www.youtube.com/watch?v=oBfzb8UOVf4&t=550)，TVM 把它扩展到深度学习加速器上，靠的是 **tensorization**——把厂商的专用张量指令（比如矩阵乘硬件原语）从调度里分离出来，厂商用张量表达式声明新指令的行为，编译器再把它接进生成的代码里。

## 六、内存这一侧：延迟隐藏与虚拟线程

融合解决的是「少搬」，但「搬的时候别让芯片闲着」是另一个问题。

CPU 靠硬件多线程隐藏访存延迟 [【跳转到 10:25】](https://www.youtube.com/watch?v=oBfzb8UOVf4&t=625)：等数据的时候切到另一个线程。但 TPU 类加速器用的是 **DAE（decoupled access-execute，访存与执行解耦）** 架构——它们把复杂的多线程硬件砍掉，腾出面积放更多算术单元，于是**调度访存的复杂度全部推给软件**。软件如果不显式地「在算当前这批数据时去取下一批」，整个芯片就停住。

手写这种代码极其痛苦，要手动插入细粒度的依赖令牌（读完才能写、写完才能读）。TVM 的对策是 **virtual threading（虚拟线程）** 调度原语 [【跳转到 11:15】](https://www.youtube.com/watch?v=oBfzb8UOVf4&t=675)：程序员按「硬件有多线程」的假设写一个数据并行程序，TVM 自动把它 lowering 成**一条精心编排的指令流**，并注入必要的显式同步（read-after-write / write-after-read 依赖）。效果是：编译器把取数指令**塞进处理器本来会空转的那些微秒里**，让 DAE 流水线保持满载。

## 七、调度怎么选：机器学习代价模型 + 真机设备池

一旦有了「循环展开、tile 大小、虚拟线程调度、数据布局」这些旋钮 [【跳转到 12:30】](https://www.youtube.com/watch?v=oBfzb8UOVf4&t=750)，一段代码的可能跑法就爆炸到**几十亿种**。黑盒自动调优要把每种配置都编译、跑一遍、量一次——单次评估可能要几秒，乘以几十亿就是几十年，完全不可持续。

TVM 的答案是**用机器学习模型当编译器的「大脑」**：给定一个调度配置，直接**预测**它的性能，不用真跑。具体用的是梯度提升树（XGBoost） [【跳转到 13:20】](https://www.youtube.com/watch?v=oBfzb8UOVf4&t=800)，特征直接从循环程序的抽象语法树上抽：

- **每一层循环里每个 buffer 的访存次数**（数据被复用了多少次）；
- **内存占用（footprint）**，用来判断能不能塞进对应硬件的缓存；
- **循环注解**：这个循环是被展开了、还是被向量化了。

模型输出预测执行时间。研究者也试过 TreeRNN，预测质量相当且不需要手工特征工程，但因为**编译成千上万个模型时速度更重要**，最终默认选了训练更快的 XGBoost。

那遇到从没见过的新硬件怎么办？ [【跳转到 14:35】](https://www.youtube.com/watch?v=oBfzb8UOVf4&t=875)TVM 用一套基于 RPC 的**分布式设备池**：把手机、嵌入式 CPU、FPGA 板子接到编译器的数据库上，编译一小段代码、通过网络发到真机上跑、把耗时精确到毫秒地测回来，再作为新训练数据喂给代价模型。**调度探索器**用代价模型指路，只把「看起来有希望」的配置发到真机上验证——于是模型对当前目标硬件的预测越来越准。

## 八、实测：赢过手写库的地方在哪

播客最后念了论文里的四组结果： [【跳转到 16:15】](https://www.youtube.com/watch?v=oBfzb8UOVf4&t=975)

| 平台 | 对比对象 | 结果 |
| --- | --- | --- |
| NVIDIA Titan X（服务器 GPU） | TensorFlow / MXNet（底层是高度优化的 cuDNN） | 1.6×–3.8× |
| ARM Cortex A53（嵌入式 CPU） | 手工优化的 TensorFlow Lite | 反超，且支持 2-bit 激活 / 1-bit 权重 |
| ARM Mali（移动 GPU） | 同上 | 1.2×–1.6× |
| FPGA（自建的 Vanilla Deep Learning Accelerator） | 在嵌入式 CPU 上跑 | 卸载到加速器的卷积上最高 40× |

最说明问题的是那个 **3.8×**：它出现在一个深度 Q 网络（DQN）负载上，用的是**不常见的 4×4 卷积**。厂商库对 3×3 这类常见配置优化到极致，遇到边角情况就失灵；而 TVM 不依赖「预先写好的假设」，它是**算出来的**最优路径。同理，2-bit/1-bit 那种极端量化需要把数据打包进更宽的标准类型、并用位运算替代乘法，厂商库不支持这种精度组合，TVM 生成的代码就赢了。

播客的收尾抛了个有趣的想法：既然代价模型能把「软件 ↔ 硅片」的关系量化，理论上也可以**反过来跑**——给定神经网络，自动设计出最合适的硬件架构。

## 小结

- 图级优化的第一步是**把模型变成纯数学的计算图**，在全局视角上找跨算子的低效。
- **融合的判据是数据依赖的形状**：injective（一对一，最好融）、reduction（压缩）、complex-out-fusable（如卷积，输出侧可融）、opaque（如排序，不能融）。靠这套规则，仅减少访存就能拿 **1.2–2×**。
- **布局变换也在图这一层做**：把数据换成后端喜欢的格式（例如 4×4 分块），避免运行期反复重排——布局不一致的代价就是多出来的搬运内核。
- 融合不能无限做：组合数指数爆炸，厂商库覆盖不了，于是转向**算子级代码生成**（张量表达式 + 调度 + tensorization）。
- 内存侧靠**虚拟线程**把取数指令塞进 MXU 的空转间隙，解决 DAE 架构的延迟隐藏问题。
- 调度的搜索空间有几十亿种，用**机器学习代价模型**预测性能 + **RPC 真机设备池**持续校准，避免黑盒穷举。
- 实测在 GPU 上赢过 cuDNN 1.6–3.8×，在嵌入式 CPU 上反超 TFLite，在 FPGA 上拿到 40×——赢的地方都是「厂商库没有预先假设」的边角负载。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| 计算图（computational graph） | 节点是数学算子、边是数据依赖的中间表示，图级优化都在它上面做 |
| 内存往返（memory trip） | 算出的值写回主存、下一个算子再读回来；延迟可能比计算本身慢几个数量级 |
| injective / reduction / complex-out-fusable / opaque | TVM 用来判断融合边界的四类算子形态 |
| 布局变换（layout transformation） | 把内部数据布局换成后端友好的形状，避免运行期反复重排 |
| 张量表达式（TE） | 把「算什么」与「怎么算」分离的语言，前者是 compute，后者是 schedule |
| tensorization | 把厂商专用张量指令从调度里分离出来，让新硬件原语能接进代码生成 |
| DAE 架构 | 访存与执行解耦的加速器架构，砍掉多线程硬件，把调度访存的活交给软件 |
| 虚拟线程（virtual threading） | 让程序员按多线程写、由编译器 lowering 成单指令流并自动插入同步 |
| 代价模型 | 用 XGBoost 从循环 AST 特征预测调度性能，替代黑盒穷举 |
| RPC 设备池 | 把手机、嵌入式 CPU、FPGA 接到编译器上做真机微基准，持续校准代价模型 |
