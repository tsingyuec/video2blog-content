# TVM 的两级 IR：NNVM 管图，TVM 的底层 IR 管贴硬件

> 视频来源：[Tianqi Chen - An End to End IR Stack for Deep Learning Systems](https://www.youtube.com/watch?v=wRWfX3cvYYU)（YouTube · ACM SIGARCH，2017-10）｜时长约 15 分钟
> 导读：这是 TVM 作者陈天奇在 2017 年的一支短演讲（含问答），讲的是 TVM 的**设计动机与 IR 分层**：为什么一个"图"不够，为什么还要再造一层更贴近硬件的 IR。视频字幕为 YouTube 自动字幕，人名与术语按上下文订正。本文只讲 TVM 的定位与输入，融合与布局选择的具体做法留给下一小节。

## 本讲要解决的核心问题（SCQA）

**背景**：深度学习框架（MXNet、TensorFlow 等）用**计算图**表达模型：节点是数据点，边是数据依赖。这张图很好用，可以在上面做自动并行、内存优化、算子融合。

**冲突**：图这一层离硬件太远了。同一个"矩阵乘"落到硬件上，要回答一堆图里根本表达不了的问题——用什么精度、要不要融合、要不要预取到本地 buffer、GPU 上怎么选线程模式才能让访存合并。而且硬件种类在爆炸：手机、AMD GPU、树莓派、FPGA、各种自研加速器，让每个框架去逐个适配根本不可能。

**疑问**：既然高层图不够、直接写硬件内核又太贵，中间应该加什么？

**回答（中心思想）**：TVM 的答案是**两级 IR**。上层继续用计算图（NNVM）做与硬件无关的图级变换；下层新造一个**基于索引表达式的张量描述语言**（TVM 的底层 IR），把"每个元素怎么算、数据放在哪、怎么并行"显式写出来，再下降到 LLVM / CUDA / OpenCL / Metal 等后端。它在这三种编译器里的位置是：**最贴近硬件的那一层**——XLA 管整张图，TorchInductor 管框架自己的图，TVM 把"一个算子内部怎么算"也纳入了编译范围。

## 一、动机：框架与硬件之间的鸿沟

### 1.1 硬件在爆炸，框架跟不上

视频开场给了一张很直白的对照图：上面是"框架"，下面是一排硬件后端——GPU、Intel 至强 CPU、各种开发板、手机、FPGA。当年几乎所有框架都能支持 NVIDIA GPU 和 CPU，但硬件越来越多之后，**框架与硬件之间的缺口越拉越大**。[【跳转到 02:23】](https://www.youtube.com/watch?v=wRWfX3cvYYU&t=143)

![框架与硬件后端之间的鸿沟：硬件种类在增长，而每个框架只能逐个手写内核去适配](assets/TVM%20的两级%20IR：NNVM%20管图，TVM%20的底层%20IR%20管贴硬件/00193.webp)

后果很具体：要支持一块新硬件，框架作者就得为它写定制内核、写各种适配层，然后在这块硬件上重建一套框架。**成本随硬件数量线性增长**，没人扛得住。[【跳转到 02:48】](https://www.youtube.com/watch?v=wRWfX3cvYYU&t=168)

### 1.2 解法：在框架与硬件之间插入中间表示

TVM 的思路是引入**中间表示（IR）**作为公共层：框架往下降到 IR，IR 再往下降到各种硬件。这样"框架 × 硬件"的乘法就被拆成了两个加法。[【跳转到 03:13】](https://www.youtube.com/watch?v=wRWfX3cvYYU&t=193)

## 二、第一级：NNVM，把计算图当作高层 IR

### 2.1 图本身就是一种 IR

计算图的形态很自然：节点代表数据，边代表数据依赖。MXNet 选择把这张图直接当作**高层 IR**，叫 **NNVM**。

![NNVM 把计算图当作高层 IR：图之上可以做自动微分、内存规划、算子融合，图之下对接各种硬件后端](assets/TVM%20的两级%20IR：NNVM%20管图，TVM%20的底层%20IR%20管贴硬件/00227.webp)

在这一层能做的事，正是"图级优化"的经典清单：

- **自动微分**（Auto Differentiation）
- **内存规划**（Memory Plan）
- **算子融合**（Operator Fusion）
- 以及自动并行等

视频举了两个 NNVM 上的实际成果，说明这一层的价值。[【跳转到 04:12】](https://www.youtube.com/watch?v=wRWfX3cvYYU&t=252)

### 2.2 例子一：用图变换把训练显存从线性降到平方根

训练时的显存复杂度通常是**层数的线性函数**，因为反向传播需要保留每一层的中间结果。后果是硬上限：一块 12 GB 的 GPU 大约只能放 200 层 ResNet。

NNVM 的做法是**换一张图**：算出同样的梯度，但主动丢弃一部分中间结果，在反向阶段重新计算。这样显存复杂度降到**平方根级**，单卡就能训 1000 层 ResNet。注意这不是"换页到 CPU"之类的系统技巧，而是**在图上做变换**——这正是高层 IR 的用武之地。

### 2.3 例子二：同一张图改写成推理友好的形态

推理场景下，可以直接对图做变换：把 32 位浮点转成 8 位整型；做**数据布局重排**（data layout retuning），让内核访存更高效。

![高层图上的两类变换：量化（32 位浮点 → 8 位）与布局重排，都是"改图"而不是"改内核"](assets/TVM%20的两级%20IR：NNVM%20管图，TVM%20的底层%20IR%20管贴硬件/00252.webp)

### 2.4 但高层图到此为止

问题在于：NNVM 给出的是一份"要算什么"的描述，可**把它落到硬件上**这一步，缺口依然巨大。对图里的每一个张量运算，硬件上都有一堆选择要定：

- 用哪种**精度**；
- **load balance** 与**布局**怎么定；
- 哪些算子要**融合**在一起；
- 要不要**预取**到本地 buffer（局部性）；
- 在 GPU 上选哪种**线程模式**，才能让共享内存访存**合并**（coalescing）。

这些都不是"图"能表达的。所以必须再往下加一层。[【跳转到 06:24】](https://www.youtube.com/watch?v=wRWfX3cvYYU&t=384)

## 三、第二级：TVM 的底层 IR，一个基于索引的张量描述语言

### 3.1 对底层 IR 的期望清单

在造这一层之前，先列了需求：

1. **表达简洁紧凑**；
2. 能表达**所有**要表达的运算；
3. 能**显式控制内存布局**以及所有影响性能的选项；
4. 能**显式控制数据局部性**；
5. 支持**张量化**（tensorization）——传统 IR 如 LLVM 是向量化的，很难直接表达一条 RISC 指令；而加速器的计算单元不再是向量，而是矩阵乘、卷积，所以**张量应当是 IR 的基本原语**；
6. 同时支持**定点与浮点**。

### 3.2 核心思想：用"索引 → 值"的规则描述运算

TVM 的底层 IR 是一个**基于索引的张量描述语言**：你给出张量的形状，再给出"第 `i, j` 个元素怎么算"的数据流描述。以 `C = dot(A, B.T)` 为例：

![TVM 的索引式描述：`tvm.placeholder` 声明输入，`tvm.compute`（给输出形状 + 给逐元素计算规则） 给出输出形状与逐元素计算规则](assets/TVM%20的两级%20IR：NNVM%20管图，TVM%20的底层%20IR%20管贴硬件/00493.webp)

```python
m, n, h = tvm.var('m'), tvm.var('n'), tvm.var('h')
A = tvm.placeholder((m, h), name='A')
B = tvm.placeholder((n, h), name='B')

k = tvm.reduce_axis((0, h), name='k')
C = tvm.compute((m, n), lambda i, j: tvm.sum(A[i, k] * B[j, k], axis=k))
```

三个要素一眼可见：**输入**（placeholder）、**输出形状**（`(m, n)`）、**计算规则**（对 `k` 归约的逐元素表达式）。

这种描述的好处是**极其灵活**：几乎深度学习里所有计算都能用这一个原语写出来。唯一的例外是**循环/递归**，所以还需要额外支持 `scan`：

![用 tvm.scan 表达 cumsum：s_init 给初值、s_update 给递推规则，就能表达带状态依赖的循环计算](assets/TVM%20的两级%20IR：NNVM%20管图，TVM%20的底层%20IR%20管贴硬件/00518.webp)

有了"逐元素计算"与"带状态的递推"这两个原语，就能覆盖全部张量计算。[【跳转到 07:48】](https://www.youtube.com/watch?v=wRWfX3cvYYU&t=468)

### 3.3 在 IR 之上再加一层：schedule（调度）

光有"算什么"还不够，还要说"怎么算"。TVM 在 IR 之上提供**变换规则与调度（schedule）**，用来指定：

- **局部性**（locality）——数据放在哪一级存储；
- **布局**（layout）；
- **并行模式**（parallelization pattern）。

这就是 TVM 与 Halide 同源的地方：**把"算什么"（compute）与"怎么算"（schedule）分离**。视频在问答里明确说，TVM 的调度"在精神上与 Halide 非常相似"，只是**专门针对深度学习负载**——比如把递归（recurrence）作为原语内建，以及面向 GPU 加速器的 Tensor Core、跨 GPU 线程等新东西。[【跳转到 14:43】](https://www.youtube.com/watch?v=wRWfX3cvYYU&t=883)

### 3.4 输出：一张多后端的下降目标清单

调度完成之后，TVM 把计算下降到多个后端：

- **CUDA**
- **OpenCL**
- **Metal**（Apple 移动 GPU）
- **LLVM**（覆盖绝大多数 CPU 设备）
- 以及通过合作接入的**自研加速器**（视频里提到一个与 TPU 相似的 FPGA 原型）

![TVM 的端到端栈：高层是 NNVM 图与自动微分、内存规划，中间是 TVM（含内存复用与并行模式），底部是 FPGA/TPU、LLVM、OpenCL、Metal、CUDA 等后端](assets/TVM%20的两级%20IR：NNVM%20管图，TVM%20的底层%20IR%20管贴硬件/00620.webp)

这张图把两级 IR 的分工画得很清楚，从上往下：

1. **Framework** → **NNVM Graph** → **Auto Differentiation** → **Memory Plan**：与硬件无关的图级层；
2. **TVM**，内部再分 **Memory Reuse**（内存复用）与 **Parallel Pattern**（并行模式）：与硬件相关的算子级层；
3. **FPGA/TPUs、LLVM、OpenCL、Metal、CUDA**：具体后端。

右侧还有一条分叉：**Predefined Operators**（预定义算子库）——也就是说，并非所有算子都要走 TVM 生成，能直接调到现成的高性能库时就走那条路。[【跳转到 10:20】](https://www.youtube.com/watch?v=wRWfX3cvYYU&t=620)

## 四、TVM 的定位：不是"最好的硬件"，而是"最容易接新硬件的基础设施"

### 4.1 硬件厂商的接入成本

视频反复强调一个立场：TVM 并不主张自己能造出最好的硬件，那个 FPGA GEMM 加速器只是**概念验证**（proof of concept）。真正的目标是：**让"把一个新硬件接进来"这件事变便宜**。

![TVM 合作方做的 FPGA GEMM 加速器原型：4×4 的 GEMM Core，每周期 256 个 4-bit FMA（或 1024 个 1-bit FMA）](assets/TVM%20的两级%20IR：NNVM%20管图，TVM%20的底层%20IR%20管贴硬件/00573.webp)

逻辑是：如果你设计了一块硬件，只要为它写一个**新的后端**，TVM 里现成的软件栈就能用上——不用再为这块芯片重建整个框架。[【跳转到 09:08】](https://www.youtube.com/watch?v=wRWfX3cvYYU&t=548)

### 4.2 远程执行（RPC）：把"验证"的成本也降下来

嵌入式开发有个隐性成本：编译在服务器上，运行在设备上，来回搬运很麻烦。TVM 因此提供了 **remote execution**：把 TVM runtime 部署到手机、FPGA 等设备上，编译器留在服务器端，通过 **TVM RPC** 把生成的 kernel 和数据发到真实设备上跑，再把结果取回来。

效果是：**在服务器上写脚本的体验，与在真实设备上验证的体验，被拉平到同一层**。这对做新硬件的人尤其重要——调一次内核不用来回折腾。[【跳转到 09:33】](https://www.youtube.com/watch?v=wRWfX3cvYYU&t=573)

### 4.3 两级 IR 拼起来才是"端到端"

视频最后把整个设计收拢成一句话：**高层 IR 负责高层变换与计算/内存优化，底层 IR 负责下降到具体硬件，两者合起来才是一个端到端（end-to-end）的栈**——它既能让新硬件插进来，也能让更多前端框架用上各种硬件。[【跳转到 10:20】](https://www.youtube.com/watch?v=wRWfX3cvYYU&t=620)

## 五、问答里最关键的一句：XLA 与 TVM 差在哪

演讲后的问答里，有人直接问："XLA 和你的中间表示有什么不同？"这是理解三种编译器定位最好的一段材料。陈天奇的回答可以概括为：

> **XLA 更像一个高层的图描述语言，做的是张量这一层的事，我会把 XLA 类比成 NNVM；而 TVM 更底层，更贴近硬件，允许你在语言里表达具体的布局与调度。**

![问答中给出的分层对照：NNVM（图级）对应 XLA 的位置，TVM（算子级）在它下面，再往下才是硬件后端](assets/TVM%20的两级%20IR：NNVM%20管图，TVM%20的底层%20IR%20管贴硬件/00468.webp)

也就是说，**XLA 与 TVM 不是同一层的竞品**：XLA 那一层管的是"整张图怎么优化、怎么落到某个设备"，TVM 那一层管的是"这个算子内部怎么切循环、怎么排布局、怎么并行"。在 TVM 的栈里，NNVM 才是与 XLA 对位的那一层。[【跳转到 13:53】](https://www.youtube.com/watch?v=wRWfX3cvYYU&t=833)

问答里还有两个值得记下的点：

- **怎么在编译器里描述硬件属性？** 两条路：一是把**原语做得足够多**，让你能表达硬件能做的事；二是在原语之上做**自动化工具**，把下降过程自动化。当时的重心在第一条，第二条（自动下降）还在做，这也是要开源整条流水线的原因。
- **能不能自动调度多个执行单元的并行？** TVM 有一个调度引擎，能处理数据流依赖，也能处理网络依赖等，这也是 MXNet 能较好扩展到多 GPU 与分布式的原因。

## 六、把 TVM 放回三种编译器的坐标系里

| 维度 | TVM |
| --- | --- |
| 定位 | 端到端深度学习编译栈，重点是**算子级**的代码生成与硬件适配 |
| 输入 | 两级：高层是**计算图**（NNVM，来自 MXNet 等框架）；低层是**基于索引的张量描述**（`tvm.compute` / `tvm.scan` + schedule） |
| 图从哪来 | 多前端：框架直接产出计算图，或经 NNVM 转入；不绑定某一个框架 |
| 中间表示 | NNVM 图（高层）+ TVM 底层 IR（算子级，索引表达式 + schedule） |
| 后端与目标 | LLVM（CPU）、CUDA、OpenCL、Metal，以及通过新后端接入的自研加速器/FPGA |
| 典型适用场景 | 硬件种类多、需要为**新硬件**快速建立软件栈；需要精细控制布局/并行/局部性；边缘与嵌入式部署（RPC 远程调优） |
| 主要代价 | 两级 IR 意味着更多手工/半自动的调度工作；当年自动下降（自动调度）尚在建设中 |

三者摆在一起，可以这样记：

- **XLA**：输入 **StableHLO**（跨框架的高层图），管"整张图"，卖点是跨硬件。
- **TorchInductor**：输入 **FX 图**（PyTorch 自己的图，降到 Aten/Prim IR），管"框架自己的图到代码"，卖点是零改码。
- **TVM**：输入 **计算图 + 索引式张量描述**，管"算子内部怎么落到具体硬件"，卖点是**接新硬件的成本最低**。

用一句话概括这条分工线：**越往下，编译器对"怎么算"的控制越细，能覆盖的硬件越多，但要交给它的信息也越多**。

## 小结

- 动机是**框架与硬件之间的鸿沟**：硬件种类爆炸，让每个框架逐个适配的成本无法承受，所以要在中间插入 IR。
- **第一级 IR 是计算图（NNVM）**：能自动微分、做内存规划、做算子融合，甚至把训练显存从线性降到平方根、把图改写成量化+重排后的推理形态。
- 高层图**表达不了硬件细节**：精度、布局、融合、预取、线程模式、访存合并，这些都必须在更低一层显式写出来。
- **第二级 IR 是索引式张量描述语言**：给形状 + 给"每个元素怎么算"的规则（`tvm.compute`），用 `tvm.scan` 补上递归，再在 IR 之上用 **schedule** 指定局部性、布局与并行。
- **输出是多后端**：LLVM、CUDA、OpenCL、Metal，以及通过新后端接入的自研加速器；另有预定义算子库这条捷径。
- TVM 的目标不是"最好的硬件"，而是**让接新硬件的成本最低**；**RPC 远程执行**把设备验证的成本也压了下来。
- 问答里的关键定位：**XLA 类比 NNVM（图级），TVM 更底层（算子级）**——两者不在同一层。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| IR（中间表示） | 介于框架与硬件之间的程序表示，编译器的操作对象 |
| NNVM | TVM 栈里的高层 IR，直接以计算图形式表达模型 |
| 计算图 | 节点是数据、边是数据依赖的图，框架表达模型的基本方式 |
| 算子融合 | 把相邻算子合成一个内核，省掉中间的显存往返 |
| 内存规划 | 在图上分析张量生命周期，复用或丢弃中间结果以省显存 |
| `tvm.compute` | TVM 的索引式描述接口：给输出形状 + 给逐元素计算规则 |
| `tvm.scan` | TVM 表达带状态递推（循环）的原语，补上 `compute` 的例外 |
| schedule（调度） | 在"算什么"之上指定"怎么算"：局部性、布局、并行模式 |
| tensorization（张量化） | 用矩阵乘/卷积这类张量原语而非向量原语做代码生成 |
| Halide | 把 compute 与 schedule 分离的 DSL，TVM 的调度思想来源之一 |
| TVM RPC | 远程执行机制：编译器在服务器、运行时在设备，跨机验证内核 |
| 后端（backend） | 代码生成的最终目标，如 LLVM、CUDA、OpenCL、Metal |
