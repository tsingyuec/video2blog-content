## 本讲要解决的核心问题（SCQA）

**背景**：大模型推理时最核心的算子就是注意力。它要从键值缓存（KV Cache）里读出历史上下文，再结合当前查询向量算出结果。分页存储（paged）已经是推理引擎的标配。

**冲突**：真实服务里键值缓存的布局远不止一种——有分页页表，有前缀树（radix tree），有稀疏掩码；请求形态也各不相同——有预填充（prefill），有逐步解码（decode），有前缀复用，还有推测解码带来的树形结构。每个系统围绕其中一部分特征各写一套注意力实现，维护成本高，还容易留下性能短板。

**疑问**：能不能用一套统一的存储表示和一套可定制的代码生成，同时覆盖这些布局与变体，并且还能在长短请求混跑时把 GPU 吃满？

**回答（中心思想）**：FlashInfer 用三件事把注意力算子做成一个「系统组件」而不是一堆特例：**块稀疏（block-sparse）格式**把页表、前缀树、稀疏掩码统一成同一个稀疏矩阵；**JIT 模板**让用户只写十几行「注意力说明」就能生成一个专用核函数；**负载均衡调度器**按工作量而不是按请求数把键值缓存切块分给线程阵列。论文报告：相比编译器后端，token 间延迟降低 29% 到 69%，长上下文延迟降低 28% 到 30%，并行生成场景加速 13% 到 17%。[【跳转到 00:00】](https://www.bilibili.com/video/BV1cqYe6QEZC/?t=0)

## 一、三点设计：一张图看清 FlashInfer 的骨架

讲者把论文的贡献归纳成三句话，正好对应系统图里的左右两部分。[【跳转到 00:25】](https://www.bilibili.com/video/BV1cqYe6QEZC/?t=25)

1. **统一的块稀疏格式**：用同一种表示承载各种键值缓存布局，减少冗余、提升访存效率；
2. **可定制的注意力模板**：通过即时编译（JIT）适配不同的注意力变体；
3. **负载均衡的调度框架**：应对输入长度的动态变化，同时保持与 CUDA Graph 的兼容。

![FlashInfer 系统设计：左侧把页表、前缀树、稀疏掩码都映射成块稀疏矩阵，右侧 JIT 编译器按变体说明生成核函数、负载均衡调度器按序列长度分派工作块](assets/FlashInfer%20论文精读：块稀疏格式、JIT%20模板与负载均衡调度/00170.webp)

图的左半部分是「统一键值缓存格式」：最上面是分页注意力用的页表，中间是前缀树，下面是稀疏掩码——三种看起来完全不同的数据结构，都被映射成中间那个块稀疏矩阵。右半部分是「动态感知的编译器与运行时」：任务信息、注意力变体说明、键值缓存布局说明三路输入进 JIT 编译器，生成具体的注意力核函数；序列长度信息进负载均衡调度器，决定工作块如何分派给各个线程阵列（CTA）。编译器产出的核函数与调度器产出的计划信息一起写进工作区缓冲区（workspace buffer），作为注意力核函数的输入，最后得到输出。[【跳转到 02:50】](https://www.bilibili.com/video/BV1cqYe6QEZC/?t=170)

这里有个容易被忽略的分工：**编译器管「用哪个核函数」，调度器管「这个核函数怎么切活」**。两者互不干涉，才使得同一个核函数能同时服务于定长和变长负载。

## 二、注意力状态：先解决「切开的注意力怎么拼回去」

要理解块稀疏和负载均衡，得先理解论文的第二个基本量——**注意力状态（attention state）**。

### 2.1 两个基本量：LSE 与 O

对一个键集合 $\mathcal{I}$，论文定义两个量。第一个是注意力尺度（log-sum-exp，LSE）：

$$
\mathrm{LSE}(\mathcal{I}) = \log \sum_{i \in \mathcal{I}} \exp\left(\mathbf{q} \cdot \mathbf{k}_i\right)
$$

第二个是注意力输出：

$$
\mathbf{O}(\mathcal{I}) = \sum_{i \in \mathcal{I}} \frac{\exp\left(\mathbf{q} \cdot \mathbf{k}_i\right)}{\exp\left(\mathrm{LSE}(\mathcal{I})\right)} \cdot \mathbf{v}_i
$$

![注意力状态的两个基本量：LSE 是查询与所有键点积的指数和再取对数，O 是各键指数权重对值向量的加权求和](assets/FlashInfer%20论文精读：块稀疏格式、JIT%20模板与负载均衡调度/00264.webp)

为什么要把 LSE 单独拆出来？因为 **LSE 是一个标量，记录的是归一化需要的分母信息**；而 $\mathbf{O}$ 记录的是还没有归一化的部分和。只要同时保留这两项，后面就可以把不同分块上分别算出的结果重新拼起来，得到与整体计算完全一致的结果。[【跳转到 03:59】](https://www.bilibili.com/video/BV1cqYe6QEZC/?t=239)

### 2.2 组合律：注意力状态可以任意分组

论文最核心的公式给出注意力状态的组合规律——两个键集合合并后的状态，可以由各自的状态通过一个组合操作符 $\oplus$ 得到：

$$
\begin{bmatrix} \mathbf{O}(\mathcal{I} \cup \mathcal{J}) \\ \mathrm{LSE}(\mathcal{I} \cup \mathcal{J}) \end{bmatrix}
= \begin{bmatrix} \mathbf{O}(\mathcal{I}) \\ \mathrm{LSE}(\mathcal{I}) \end{bmatrix} \oplus
\begin{bmatrix} \mathbf{O}(\mathcal{J}) \\ \mathrm{LSE}(\mathcal{J}) \end{bmatrix}
= \begin{bmatrix}
\dfrac{\exp(\mathrm{LSE}(\mathcal{I}))\mathbf{O}(\mathcal{I}) + \exp(\mathrm{LSE}(\mathcal{J}))\mathbf{O}(\mathcal{J})}{\exp(\mathrm{LSE}(\mathcal{I})) + \exp(\mathrm{LSE}(\mathcal{J}))} \\[2mm]
\log\left(\exp(\mathrm{LSE}(\mathcal{I})) + \exp(\mathrm{LSE}(\mathcal{J}))\right)
\end{bmatrix}
$$

![注意力状态的组合律：合并后的输出按各自尺度的指数加权平均，合并后的尺度取两部分指数和的 log-sum-exp](assets/FlashInfer%20论文精读：块稀疏格式、JIT%20模板与负载均衡调度/00294.webp)

读法很简单：**输出做加权平均，权重是各自 LSE 的指数；尺度做 log-sum-exp**。这个操作符满足结合律和交换律，也就是说多个集合的注意力状态可以按任意顺序、任意分组来组合，结果完全一致。[【跳转到 05:19】](https://www.bilibili.com/video/BV1cqYe6QEZC/?t=319)

这条性质是整个系统的地基：**正因为可以任意分组，键值缓存才能被任意切分、并行计算再规约**。FlashInfer 就把注意力状态作为注意力算子的标准输出，把组合操作符作为标准的规约算子——地位相当于矩阵乘法里的求和。后面第三节的块稀疏、第五节的切块调度，全部建立在这条性质上。

## 三、块稀疏格式：三种布局，一个矩阵

### 3.1 从页表到块稀疏矩阵

先看最熟悉的分页注意力。页表本身是「请求 → 物理页号」的映射，把它换个视角看：**把请求当作行、把物理页号当作列**，就得到一个矩阵——非零的块表示这个请求实际访问到的键值缓存页，空白表示没有访问。[【跳转到 05:54】](https://www.bilibili.com/video/BV1cqYe6QEZC/?t=354)

![页表映射成块稀疏矩阵：请求号为行、物理页号为列，非零块表示实际访问的缓存页；行块大小对应查询分块，列块大小对应页大小](assets/FlashInfer%20论文精读：块稀疏格式、JIT%20模板与负载均衡调度/00354.webp)

图中左上角是逻辑上的键值缓存块（按请求号索引，每块大小为 token 数乘以头维度），右上角是物理上的键值缓存（K 和 V 分开存放）。论文用**块压缩稀疏行（BSR，block compressed sparse row）**格式存储这个矩阵：行块大小 $B_r$ 对应查询分块大小，列块大小 $B_c$ 对应页大小，而且两者都可以按需设置。图中例子是 $B_c = 1$、$B_r = 4$，三个请求的查询长度分别是 8、4、4。

一旦写成 BSR，分页注意力就落进了这个抽象里；前缀树、稀疏掩码同样可以落进来。这就是「统一格式」的含义——**不是把数据搬成一种布局，而是把各种布局描述成同一种索引结构**。

### 3.2 可组合格式：共享前缀用大块，独有后缀用小块

统一格式解决了「能不能表示」，可组合格式解决「表示得好不好」。

![可组合格式的共享前缀分解：1×1 的细粒度块只能走全局内存或二级缓存，把共享同一段前缀的查询合并成 3×1 的块后可共用键值缓存，访问落在共享内存和寄存器里](assets/FlashInfer%20论文精读：块稀疏格式、JIT%20模板与负载均衡调度/00443.webp)

图的上半部分是最细粒度的情况，块大小 $1\times 1$：每个查询占一行，按线程块索引 1 到 6 排列，每个线程块各自算出一份输出和注意力尺度，最后再组合成总输出。问题在于，这种细粒度块下**每个查询只能在自己的线程块里访问键值缓存**，访问走的是低带宽的全局内存或者二级缓存——图右侧那个金字塔画的就是存储层次：寄存器 → 共享内存 → 二级缓存 → 全局内存，越往下带宽越低。

图的下半部分把前六行的查询合并成一个块大小为 $3\times 1$ 的块稀疏矩阵：因为这几行查询共享同一段前缀，可以共用同一份键值缓存，访问就发生在高带宽的共享内存和寄存器里；剩下的独有键值缓存仍然用 $1\times 1$ 的格式存储。**同一个稀疏矩阵按需拆成不同块大小的子矩阵，这就是可组合格式**。[【跳转到 07:48】](https://www.bilibili.com/video/BV1cqYe6QEZC/?t=468)

对初学者来说，可以这样记：块越大，越省重复搬运，但块内「凑不齐」的空洞也越多；块越小，越不会浪费算力，但每个查询都得自己去低带宽的内存里捞数据。可组合格式的做法是——**该大的地方大（共享前缀），该小的地方小（独有后缀）**。

## 四、JIT 编译：写一小段说明，生成一整个核函数

存储统一之后，第二个问题是：注意力变体太多了。GQA、滑动窗口、ALiBi、各种带自定义 mask 或自定义 score 变换的变体，如果每个都在 FlashAttention 代码库里改一遍，就要同时改 CUDA 实现、C++ 与 Python 之间的胶水代码，既费时又很难合回上游。

FlashInfer 的做法是**模板 + 说明**：CUDA 模板固定，用户只写一小段「注意力说明」（attention specification）。

![JIT 编译器把注意力变体映射到核函数模板：左侧 Python 说明定义 FlashSigmoid 变体，右侧 CUDA 模板分核参数结构体、核特征类、核主体、算子注册四部分](assets/FlashInfer%20论文精读：块稀疏格式、JIT%20模板与负载均衡调度/00491.webp)

图里最左边是 Python 里写的注意力说明，定义了一个叫 `FlashSigmoid` 的变体：里面写明了要使用的变体函数（比如对 logits 做缩放的变换函数），同时声明了额外的标量参数和数据类型。中间和右边是 CUDA 模板的四个部分：

1. **核参数结构体**（Kernel Params）：把张量、标量、类型打包成一份参数；
2. **核特征类**（Kernel Traits）：声明头维度、是否稀疏等编译期常量；
3. **核主体**（Kernel Body）：真正跑在 GPU 上的循环体，调用说明里定义的那些变体函数；
4. **算子注册**：把生成好的算子注册成 PyTorch 自定义算子。

整张图的配色标出了对应关系：同样的颜色表示同一份信息被插入到模板的哪个位置。这样用户不需要为每个变体重写一个完整的库和算子，**只写一小段说明，编译器把它填进模板，生成高度优化的代码**。[【跳转到 08:36】](https://www.bilibili.com/video/BV1cqYe6QEZC/?t=516)

可用的变体函数包括查询、键、值的变换，输出的变换，以及作用在 logits 上的变换和掩码——因此也能支持不使用 softmax 的注意力变体（比如用 sigmoid 代替 softmax 的变体）。

## 五、负载均衡调度：按工作量切块，不按请求数切块

### 5.1 为什么按请求分活会拖尾

解码阶段每个请求只有一行查询，但键值长度可以差几百倍。如果「一个请求一个线程阵列」，那么分到长请求的线程阵列要跑很久，其余线程阵列早早空转——这就是**尾部拖长（tail effect）**。所以必须允许把**一个请求的键值缓存切开**，分给多个线程阵列，最后再按第二节的组合律归约。

### 5.2 调度算法：最长的工作优先给最空闲的执行单元

![负载均衡调度算法：先定义工作块代价为查询长度与键值长度的线性组合，再用总工作量除以线程阵列数算出最大分块长度，把工作块按长度降序排序，用优先队列把最长的块分给累计代价最小的线程阵列](assets/FlashInfer%20论文精读：块稀疏格式、JIT%20模板与负载均衡调度/00565.webp)

算法六步，逐条对照幻灯片：[【跳转到 09:20】](https://www.bilibili.com/video/BV1cqYe6QEZC/?t=560)

1. **输入**：每个请求的查询（输出）长度 $l_{qo}(i)$、键值长度 $l_{kv}(i)$，以及查询分块大小 $T_q$；
2. **定义工作块代价**：$l_q, l_{kv}$ 的线性组合，两个系数是超参数：

$$
\mathrm{cost}(l_q, l_{kv}) = \alpha \, l_q + \beta \, l_{kv}
$$

3. **算最大分块长度**：用所有请求的总工作量除以协作线程阵列的数量，得到每个线程阵列平均要处理的键值长度：

$$
L_{kv} \leftarrow \frac{\sum_i \left\lceil l_{qo}(i) / T_q \right\rceil \cdot l_{kv}(i)}{\#\mathrm{CTA}}
$$

4. **切块**：把每个查询分块对应的键值缓存按 $L_{kv}$ 切成若干块，每块有一个工作索引 $w$ 和对应长度 $l_{kv}(w)$；
5. **排序**：把所有工作块按长度从大到小排序；
6. **贪心分配**：建立一个以 CTA 为元素的优先队列，初始累计代价为 0；每轮取出累计代价最小的 CTA，把当前最长的工作块分给它，更新代价后放回队列。

伪代码（按幻灯片整理）：

```text
输入: {l_qo(i), l_kv(i)}, 查询分块大小 T_q
cost(l_q, l_kv) = α·l_q + β·l_kv
L_kv = Σ_i ceil(l_qo(i)/T_q) · l_kv(i) / #CTA
W = {(w, l_kv(w))}            # 切块并按长度降序排序
Q = PriorityQueue({(c, 0)})   # (CTA 编号, 累计代价)
while W 非空:
    c, cur = Q.pop_min()
    w, len = W.pop()          # 取最长的一块
    assign(w -> c)
    Q.push((c, cur + cost(T_q, len)))
```

这个贪心策略的作用是：**最长的工作优先安排给最空闲的执行单元**，从而把整体完成时间压下来。论文也提到它受 Stream-K 启发，但没有采用 Stream-K 的原子聚合——因为大模型推理要求输出确定，而原子加法的浮点累加顺序不确定。[【跳转到 10:40】](https://www.bilibili.com/video/BV1cqYe6QEZC/?t=640)

### 5.3 运行时流程：plan 在 CPU，run 在 GPU

![运行时调度器工作流程：调度器把工作块分派给多个协作线程阵列，注意力核先产出注意力状态，再由收缩核按组合操作符归约；plan 跑在 CPU 不被 CUDA Graph 捕获，run 跑在 GPU 会被捕获](assets/FlashInfer%20论文精读：块稀疏格式、JIT%20模板与负载均衡调度/00646.webp)

图中左上角是输入（每个请求的查询与键值长度、查询分块大小），调度器把工作块编号 0 到 6，分派给五个协作线程阵列。可以看到请求 2 的键值缓存特别长，被切成工作块 5 和工作块 6，分别交给线程阵列 0 和线程阵列 4——**长请求被拆开，就不会成为整体短板**。右上角是每个线程阵列的工作队列；中间是规约映射，说明每个最终输出由哪些工作块负责（比如输出 1 由工作块 1 和工作块 2 组合而成）。[【跳转到 10:46】](https://www.bilibili.com/video/BV1cqYe6QEZC/?t=646)

因为键值缓存被切开了，注意力核函数**不会直接产出最终结果**，而是先产出每个工作块的部分输出（输出 + 注意力尺度组成的注意力状态），再由收缩核函数（contraction kernel）按第二节的组合操作符做规约。这些计划信息会被缓存到 GPU 端，作为核函数的输入。

论文还提到一个时间上的安排：**计划（plan）函数运行在 CPU 上，因此不会被 CUDA Graph 捕获；执行（run）函数运行在 GPU 上，会被捕获进计算图**。这种划分借鉴了编译领域里的「检查器与执行器」模型。[【跳转到 12:01】](https://www.bilibili.com/video/BV1cqYe6QEZC/?t=721)

这一点对工程实现很关键：CUDA Graph 要求「录制一次、重放多次」，而每个解码步的序列长度都在变，调度结果也每步都变。把会变的部分（plan）留在图外，把不变的部分（run）录进图里，才既拿到负载均衡又拿到 CUDA Graph 的低启动开销。

## 六、效果：从端到端到算子级

### 6.1 端到端：SGLang 换后端

![SGLang 搭配 Triton 与 FlashInfer 后端的端到端对比：四种设置下 FlashInfer 都占优，70B 模型 ShareGPT 负载上 token 间延迟从约 48 毫秒降到约 24 毫秒](assets/FlashInfer%20论文精读：块稀疏格式、JIT%20模板与负载均衡调度/00731.webp)

### 6.2 算子级：变长分布才是调度器的主场

![算子级性能：上两幅是解码阶段带宽利用率，下两幅是预填充阶段浮点利用率，横轴是恒定、均匀、偏斜三种序列长度分布；均匀与偏斜分布下 FlashInfer 优势特别明显](assets/FlashInfer%20论文精读：块稀疏格式、JIT%20模板与负载均衡调度/00777.webp)

这张图特别值得看：横轴是三种序列长度分布——**恒定长度、均匀分布、偏斜分布**。在恒定长度下两者差不多（因为没有可均衡的差异），而在均匀和偏斜分布下 FlashInfer 的优势特别明显——**这正是负载均衡调度器发挥作用的地方**：请求长度参差不齐时，调度器能把长任务和短任务搭配着分配。[【跳转到 12:57】](https://www.bilibili.com/video/BV1cqYe6QEZC/?t=777)

解码场景下 FlashInfer 的优势也很明显，原因是它提供了多种可选的块大小，而 FlashAttention 在解码时用的块大小并不是最优的。图里同时对比了多头注意力（MHA）和分组查询注意力（GQA），两种设置下 FlashInfer 都更好。

### 6.3 长上下文：把 RoPE 融进注意力

![长上下文结果：FlashInfer 算子接入 Streaming-LLM、模型为 Vicuna 13B；最低那条线是融合旋转位置编码与注意力的核函数，带宽利用率高出 1.6 到 3.7 倍](assets/FlashInfer%20论文精读：块稀疏格式、JIT%20模板与负载均衡调度/00839.webp)

实验把 FlashInfer 的算子接到 Streaming-LLM 里，模型是 Vicuna 13B。上面两幅是 token 间延迟，横轴是最近窗口大小（1000 到 4000 个 token）：最低的那条线是 FlashInfer 把旋转位置编码（RoPE）和注意力融合在一起的核函数，中间那条是 FlashAttention 没有融合的方案，最上面是原始实现。融合之后延迟明显更低，而且窗口越大优势越稳定；下面两幅的带宽利用率显示，融合后高出 1.6 倍到 3.7 倍。[【跳转到 13:54】](https://www.bilibili.com/video/BV1cqYe6QEZC/?t=834)

这条结果的因果链很直白：**位置编码本来要在注意力之外单独跑一遍、把结果写回显存再读出来；用 JIT 模板把它融进核函数，就省掉了这一趟往返**。这正是「可定制模板」在长上下文场景下的价值。

### 6.4 并行生成：可组合格式的收益

![可组合格式在并行生成场景的效果：横轴是启用可组合格式的延迟，纵轴是单一格式的延迟，多数点落在对角线上方说明可组合格式更快，并行度为 4 时加速最明显](assets/FlashInfer%20论文精读：块稀疏格式、JIT%20模板与负载均衡调度/00894.webp)

### 6.5 GQA 头组融合与因果注意力算力

![GQA 头组融合：把查询头维度与查询长度维度合并，同组查询头只需从共享内存加载一次键值缓存](assets/FlashInfer%20论文精读：块稀疏格式、JIT%20模板与负载均衡调度/00962.webp)

分组查询注意力里多个查询头共享同一组键值头。如果直接给每个查询头分配一个线程块，查询长度较短时键值缓存复用会很不充分。FlashInfer 把**查询头维度和查询长度维度合并**：分组大小 $g=5$、查询长度 $l_{qo}=3$ 时，融合后得到 15 行。换算关系是：

$$
i = i' / g, \qquad \mathrm{qo\_head\_idx} = \mathrm{kv\_head\_idx} \times g + (i' \bmod g), \qquad l'_{qo} = g \cdot l_{qo}
$$

融合后同一组里所有查询头只需从共享内存加载一次键值缓存，复用更充分，GQA 吞吐就上去了。论文说明这个策略主要在查询长度较短时使用——长度足够大时，查询本身的工作量已经能充分利用硬件资源。[【跳转到 16:02】](https://www.bilibili.com/video/BV1cqYe6QEZC/?t=962)

![因果注意力算力对比表：序列长度从 512 到 16384，FlashInfer 在所有长度上都高于 FlexAttention，最长一档达 612 TFLOPs、FlexAttention 约 454](assets/FlashInfer%20论文精读：块稀疏格式、JIT%20模板与负载均衡调度/01037.webp)

最后是因果注意力的算力对比（单位 TFLOPs，越高越好）：序列长度从 512 一直增加到 16384，FlashInfer 在所有长度上都更高，而且越长优势越明显——最长一档 FlashInfer 达到 612，FlexAttention 约 454。论文把差距归因于用到了 Hopper 架构的特性，比如线程束专用化（warp specialization）和张量内存加速器（TMA），以及 CUDA 提供的更细粒度寄存器级资源控制。[【跳转到 17:12】](https://www.bilibili.com/video/BV1cqYe6QEZC/?t=1032)

## 小结

- **一句话结论**：FlashInfer 不是「更快的注意力 kernel」，而是把注意力当成一个系统组件来做——存储统一、代码生成可定制、调度按工作量均衡，三者缺一不可。
- **块稀疏格式**把页表、前缀树、稀疏掩码统一成 BSR 稀疏矩阵，行块对应查询分块、列块对应页大小，两者都可调。
- **可组合格式**在同一个矩阵里混用不同块大小：共享前缀用大块（走共享内存/寄存器），独有后缀用小块（不浪费算力）。
- **注意力状态（LSE + O）及其组合律**是并行切分与归约的数学基础：满足结合律、交换律，所以键值缓存可以任意切开再拼回。
- **JIT 模板**让用户只写十几行说明（变换函数、额外标量、数据类型），编译器把它填进 CUDA 模板，生成专用核函数并注册成 PyTorch 算子。
- **负载均衡调度**先按总工作量除以 CTA 数确定最大分块长度，再按「最长块给最空闲 CTA」的贪心策略分配，避免长请求拖尾；不用原子聚合以保证输出确定。
- **plan 在 CPU、run 在 GPU** 的划分，让调度既能每步自适应，又不破坏 CUDA Graph 的录制重放。
- 实测：端到端 token 间延迟最多降一半（70B 模型 48 ms → 24 ms）；变长分布下算子利用率优势最明显；RoPE 融合带来 1.6 到 3.7 倍带宽利用率。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| 键值缓存（KV Cache） | 推理时缓存历史 token 的 K/V 向量，避免每步重算 |
| 分页注意力（PagedAttention） | 把键值缓存按固定大小的页管理，用页表映射逻辑块到物理块 |
| 前缀树（Radix Tree） | 把共享前缀组织成树，前缀只存一份，多个请求共用 |
| 块稀疏矩阵（Block-Sparse Matrix） | 稀疏矩阵的最小元素不是标量而是一个小矩阵块 |
| BSR（块压缩稀疏行） | 用行指针、列索引、值三组数组存储块稀疏矩阵的格式 |
| 可组合格式（Composable Format） | 同一矩阵里按需混用不同块大小，共享前缀用大块、独有部分用小块 |
| 注意力状态（Attention State） | 由输出 $\mathbf{O}$ 与尺度 $\mathrm{LSE}$ 组成的二元组，可组合、可归约 |
| LSE（log-sum-exp） | 注意力权重的归一化分母的对数，标量 |
| 线程阵列（CTA） | CUDA 的线程块，一个 CTA 通常跑在一个 SM 上 |
| Split-K | 把键值序列维切开分给多个 CTA 并行算，再归约 |
| 尾部拖长（Tail Effect） | 少数长任务拖住整体完成时间，其余执行单元空转 |
| CUDA Graph | 把一串 kernel 启动录制成图后重放，降低启动开销 |
| JIT 编译 | 运行前按具体配置即时生成并编译 kernel，而不是事先全量编译 |
| 线程束专用化（Warp Specialization） | 把不同 warp 分工成生产者/消费者，隐藏访存与计算延迟 |
| TMA（张量内存加速器） | Hopper 引入的异步批量搬运单元，只适合连续张量访问 |
