# FlashInfer 作者亲讲（1）：从 PagedAttention、RadixAttention 到统一块稀疏表示

> 视频来源：[Lecture 41: FlashInfer | GPU MODE](https://www.youtube.com/watch?v=iOLBJwENuvA)（YouTube · GPU MODE，讲者 Zihao Ye）｜全长约 69 分钟，本篇覆盖前 25 分钟（存储部分）
> 导读：作者本人讲的 FlashInfer 综述，比论文多出大量「为什么这样设计」的现场解释。本文是第一篇，只讲**存储**：先把推理引擎里四种键值缓存布局摆出来，再说明它们如何被同一个块稀疏格式（BSR）吞下、为什么块大小要小到「一列」、以及可组合格式怎样把共享前缀变成高带宽访问。演讲中的现场提问保留了与设计直接相关的部分。

## 本讲要解决的核心问题（SCQA）

**背景**：vLLM 的 PagedAttention 把键值缓存按页管理，解决了变长请求带来的显存碎片，页表设计如今已经是推理引擎的标配。

**冲突**：页表只是键值缓存管理的一种选择。SGLang 的 RadixAttention 把共享前缀组织成基数树；推测解码（Medusa、SpecInfer）要把候选 token 组织成树；QUEST 一类工作只保留 top-k 页。**这四种布局在内存里长得完全不一样**，每来一种就要写一套新的注意力 kernel。

**疑问**：能不能不写四套 kernel，而是找到一种「都能表示」的存储抽象？如果能，这种抽象要满足什么条件才能不牺牲 GPU 的算力利用率？

**回答（中心思想）**：FlashInfer 用**块稀疏矩阵（block-sparse matrix）**统一描述这四种布局——把请求当行、把物理页当列，非零块就是实际访问的缓存页。为了让这种表示既省显存又不浪费 tensor core，作者把块大小降到「列数为 1」的**列向量稀疏**，并用**可组合格式**在同一矩阵里混用不同块大小：共享前缀用大块走共享内存，独有后缀用小块不浪费算力。[【跳转到 01:40】](https://www.youtube.com/watch?v=iOLBJwENuvA&t=100)

## 一、先看清战场：四种键值缓存布局

### 1.1 分页：把操作系统那套搬到显存

大模型推理的请求长度是变的。如果给每个请求都预留最大序列长度，显存会被切得七零八落——这就是**碎片（fragmentation）**。PagedAttention 的方案是：把键值缓存组织成一个个「页」，每页大约 16 个 token；页表本身借用了操作系统的概念，于是换入换出、按需分配这些手段都能直接用上。[【跳转到 02:05】](https://www.youtube.com/watch?v=iOLBJwENuvA&t=125)

配套的 kernel 也很关键：**不需要先把散落的键值缓存 gather 成连续内存再调用 FlashAttention**，而是写一个直接按页表访问的 kernel，这样访存效率最高。作者说这套页表设计已经是推理引擎的标准做法。

### 1.2 基数树：把共享前缀显式建模成树

SGLang 观察到大量请求共享同一段前缀，于是提出把键值缓存组织成**基数树（radix tree）**。它其实是页表的一个特例：**页大小等于 1**——每页只放一个 token。好处是碎片更少，且开启前缀缓存时命中率更高：页大小为 1 时，两个请求只要 token 相同就能匹配；页大小为 16 时，必须 16 个 token 全对齐才能匹配。[【跳转到 03:45】](https://www.youtube.com/watch?v=iOLBJwENuvA&t=225)

两者的另一个显著差别是：基数树**显式地把共享前缀建模成树结构**，而分页方案要靠前缀缓存（prefix caching）去间接实现类似效果。

### 1.3 推测解码：树形掩码

推测解码（Medusa、SpecInfer 等）用一个小模型一次生成多个候选 token，再让大模型并行验证。这些候选不是一条链，而是**一棵树**——大模型要验证树里是否存在一条路径与自己的输出一致。这给键值缓存和注意力 kernel 都出了难题：候选部分的键值缓存要按树组织，注意力掩码也变成树形。[【跳转到 05:25】](https://www.youtube.com/watch?v=iOLBJwENuvA&t=325)

### 1.4 压缩：只算重要的页

还有一类工作干脆不显式使用全部键值缓存。QUEST 的做法是：键值缓存仍然按页组织，但注意力分两轮——第一轮用每页的「精简键」（reduced keys）估算每个页块的重要性，第二轮只对 top-k 页做真正的注意力计算。这样即使上下文长到几百万 token，只要 $k$ 取得合理，第二轮要读的数据量也可控；而第一轮只按页粒度算精简键，IO 同样很小。[【跳转到 08:45】](https://www.youtube.com/watch?v=iOLBJwENuvA&t=525)

![QUEST 的两阶段稀疏注意力：第一轮用精简键估算每个页块的重要性并做 top-k 选择，第二轮只在选中的页上做稀疏注意力](assets/FlashInfer%20作者亲讲（1）：从%20PagedAttention、RadixAttention%20到统一块稀疏表示/00600.webp)

### 1.5 现场提问：这个方向还有多少空间

主持人问了两个很实在的问题。第一个是「键值缓存管理还会是活跃研究方向吗？」作者的回答是：现有的键值缓存设计基本只盯着 GPU 显存，而把 DRAM、SSD 纳入进来的分层方案还缺少被广泛认可的成本模型；另外像「页块之间相似就合并」这类压缩思路也还在探索中。[【跳转到 06:40】](https://www.youtube.com/watch?v=iOLBJwENuvA&t=400)

第二个问题是「为什么各家推理框架往往锁定一种键值缓存管理方式，而不是随意替换？」作者的看法是各家有自己的优先级——比如 SGLang 重视结构化生成（大量共享前缀），所以选基数树。**正因为各家选择不同，才更需要一层统一的表示**。

## 二、块稀疏表示：一个格式吞下四种布局

### 2.1 什么是块稀疏

FlashInfer 的答案叫**块稀疏表示（block-sparse representation）**：它是对普通稀疏矩阵的推广，唯一的区别是——**稀疏矩阵的最小元素不是单个标量，而是一个 $B_r \times B_c$ 的小矩阵**。[【跳转到 11:47】](https://www.youtube.com/watch?v=iOLBJwENuvA&t=707)

为什么大家偏爱这种格式？因为 GPU 的 tensor core 有最小 MMA 形状：Ampere 上是 $16 \times 8 \times 16$，Hopper 上更大（$64 \times N \times 16$）。**如果不对稀疏结构加约束，就得先把零散的非零元素攒成一个 MMA 形状的块**——这既费时间，很多情况下也攒不出来（非零元素太多）。块稀疏格式相当于在数据结构层面就把「块」对齐到硬件形状。

### 2.2 BSR 怎么存：三组数组

具体存储用 **BSR（block compressed sparse row，块压缩稀疏行）**，包含三组数组：

- **indptr**（index pointer）：记录每一行在打包数据里的起始偏移；
- **indices**：记录每个非零块的列索引；
- **value**：块内的值，**可选**——如果块内还需要掩码或具体数值就需要它。

![BSR 格式示例（$B_r, B_c = 4, 2$）：indptr 记录每行起始偏移，indices 记录非零块的列号，value 可选](assets/FlashInfer%20作者亲讲（1）：从%20PagedAttention、RadixAttention%20到统一块稀疏表示/00716.webp)

幻灯片这个例子很值得手算一遍：$3 \times 6$ 的块网格，行块数 3、列块数 6，块大小 $(B_r, B_c) = (4, 2)$。第 0 行有列 1 和列 5 两个非零块，第 1 行有列 2 和列 4，第 2 行有列 1 和列 3。于是

```text
indptr  = (0, 2, 4, 6)          # 每行起始偏移，长度 = 行块数 + 1
indices = (1, 5, 2, 4, 1, 3)    # 按行拼接的非零块列号
value   = Optional[(6, 4, 2)]   # 块内数值，按需提供
```

**行指针 + 列索引 + 可选值**，就是全部。任何「哪些页被哪些请求访问」的关系，都能写成这三组数组。

### 2.3 页表就是块稀疏矩阵

把逻辑地址空间当成列、把请求当成行，页表立刻变成块稀疏矩阵：每个请求用到的物理页，就是这个矩阵里的非零块。[【跳转到 14:01】](https://www.youtube.com/watch?v=iOLBJwENuvA&t=841)

![页表建模成块稀疏矩阵：请求为行、物理页号为列，非零块表示实际访问的页，行块大小对应查询分块、列块大小对应页大小](assets/FlashInfer%20作者亲讲（1）：从%20PagedAttention、RadixAttention%20到统一块稀疏表示/00866.webp)

图中三个请求的查询长度是 $\{l_{qo}\} = (8, 4, 4)$，页大小 $B_c = 1$，查询分块 $B_r = 4$。作者顺带指出了一个有意思的「反向借鉴」：图形学社区这些年一直在用页表、树等数据结构去加速稀疏矩阵的查找；而 FlashInfer 做的是反过来的事——**用稀疏矩阵的表示去描述页表**。[【跳转到 14:51】](https://www.youtube.com/watch?v=iOLBJwENuvA&t=891)

## 三、把块缩到一列：列向量稀疏

### 3.1 $16\times16$ 的块在树掩码上浪费惊人

块稀疏有个隐含代价：**块越大，块内的零越多**。作者举了推测解码的例子——树形掩码本身就非常稀疏，如果最小块是 $16 \times 16$，那么每个被激活的块里「零比非零还多」，大部分 FLOPs 都白算了。而多数块稀疏库用的块更大（比如 $128 \times 128$），浪费只会更夸张。[【跳转到 15:16】](https://www.youtube.com/watch?v=iOLBJwENuvA&t=916)

![树形掩码本质上是稀疏矩阵：基数树与 token 树天然稀疏，用 $128\times128$ 的块表示仍会留下大量碎片](assets/FlashInfer%20作者亲讲（1）：从%20PagedAttention、RadixAttention%20到统一块稀疏表示/00941.webp)

### 3.2 解法：块列数取 1

FlashInfer 的做法是**仍然用块稀疏矩阵，但把块的列数设为 1**——也就是「列向量稀疏」。这个想法受六年前一篇结构化稀疏的 tensor core kernel 工作启发。[【跳转到 16:31】](https://www.youtube.com/watch?v=iOLBJwENuvA&t=991)

收益可以用一道算术题说清：以前 $16 \times 16$ 的块里只要有一个非零元素，整个块都要算，**最多浪费 255/256 的乘加**；现在只有长度为 16 的向量里有一个非零元素才激活这个向量，**只浪费 15/16**。虽然还是浪费，但已经好得多。

![列向量稀疏编码（块稀疏且块列数为 1）：csrVal、csrRowPtr、csrColInd 三组数组即可描述，显著降低碎片](assets/FlashInfer%20作者亲讲（1）：从%20PagedAttention、RadixAttention%20到统一块稀疏表示/00991.webp)

### 3.3 为什么向量稀疏还能用上 tensor core

初学者最容易卡在这里：块都变成「一列」了，还能用 tensor core 吗？作者的答案是能，靠的是**先 gather 到共享内存**：A 矩阵的列在内存里不连续、X 矩阵的行也不连续，但可以先把它们从全局内存搬到共享内存，共享内存上的数据是连续的，再喂给 tensor core。[【跳转到 17:46】](https://www.youtube.com/watch?v=iOLBJwENuvA&t=1066)

这里有两个「恰好」让 gather 变得便宜：

1. **最后一维是头维度（head dim），它在内存里本来就是连续的**——所以 HBM 到共享内存的搬运不会退化成逐元素随机访问；
2. **头维度足够大**（常见 128 左右），能对齐 GPU 的 cache line，于是搬一行的带宽利用率仍然很高。[【跳转到 19:01】](https://www.youtube.com/watch?v=iOLBJwENuvA&t=1141)

作者还补充说，这种「把稀疏行/列搬到共享内存再用 tensor core」的做法在 HPC 与图形学文献里早有先例，FlashInfer 是把它搬到了注意力这个场景。

## 四、可组合格式：同一矩阵，两种块大小

### 4.1 共享前缀值得用更大的块

第二个发现来自基数树：共享前缀部分被很多请求同时访问，**如果还按 $1\times1$ 的块算，每个请求都要自己去全局内存/二级缓存里捞同一份数据**，重复搬运。既然这段前缀是共享的，就可以用**更大的块**表示，让一个线程块内的多个查询共用一次加载。[【跳转到 20:58】](https://www.youtube.com/watch?v=iOLBJwENuvA&t=1258)

![可组合格式：前缀共享的查询用 $3\times1$ 的大块（走共享内存/寄存器），独有后缀仍用 $1\times1$ 的小块；右侧金字塔是存储层次，越往下带宽越低](assets/FlashInfer%20作者亲讲（1）：从%20PagedAttention、RadixAttention%20到统一块稀疏表示/01258.webp)

图左侧是四个用户向同一本书提问，共享同一段文档前缀；右侧上半部分是 $1\times1$ 的细粒度格式——每个线程块各算各的，访问键值缓存要走全局内存或 L2；下半部分把前三行合并成 $3\times1$ 的大块，共享前缀的访问落在共享内存和寄存器里，独有部分仍用 $1\times1$。

### 4.2 本质是「分解」，不是「改数据」

作者强调，可组合格式在矩阵层面的含义是：**把一个稀疏矩阵分解成若干个不同块大小的稀疏矩阵**。这样做的好处是：

- 大块部分可以走**软件管理的缓存**（先把键值缓存预取到共享内存再复用），而小块部分只能靠**硬件管理的 L1/L2**；
- 当「前缀很长、独有后缀很多」时，软件管理的共享内存明显优于硬件管理的缓存。[【跳转到 22:13】](https://www.youtube.com/watch?v=iOLBJwENuvA&t=1333)

更关键的是工程上的好处：**这种分解只改索引和数据结构，不改数据本身**。推理引擎只需要记录「哪一段用哪种块大小」，键值缓存的内容一个字节都不用动——这对一个要被 vLLM、SGLang、MLC 共同使用的库来说，是能否落地的分水岭。[【跳转到 24:18】](https://www.youtube.com/watch?v=iOLBJwENuvA&t=1458)

## 小结

- **问题不是「哪种键值缓存布局最好」，而是「能不能用一套表示描述所有布局」**：分页、基数树、推测解码的树、top-k 压缩，本质都是「哪些查询访问哪些页」的稀疏关系。
- **块稀疏矩阵就是那个统一表示**：行是查询块、列是物理页，非零块表示真实访问；用 BSR 的 `indptr` + `indices` + 可选 `value` 三组数组存储。
- **块大小要小到一列**：$16\times16$ 的块在树形掩码上会浪费 255/256 的乘加，列向量稀疏把浪费降到 15/16。
- **向量稀疏仍可用 tensor core**：先把稀疏行/列 gather 到共享内存，头维度连续且能对齐 cache line，所以 gather 的带宽损失可控。
- **可组合格式 = 稀疏矩阵分解**：共享前缀用大块（软件管理缓存、共享内存复用），独有后缀用小块（不浪费算力），且只改索引不改数据。
- **设计动机来自「多家引擎各选一种布局」的现实**：正因为 SGLang 选基数树、vLLM 选分页，才需要一层谁都能接的统一抽象。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| 键值缓存（KV Cache） | 缓存历史 token 的 K/V 向量，避免解码时重复计算 |
| PagedAttention | 把键值缓存切成固定大小的页，用页表把逻辑块映射到物理块 |
| 基数树（Radix Tree） | 把共享前缀组织成树，等价于「页大小为 1」的页表 |
| 块稀疏矩阵（Block-Sparse Matrix） | 稀疏矩阵的最小元素是一个 $B_r \times B_c$ 的小块，而不是标量 |
| BSR | 块压缩稀疏行，用 indptr、indices、value 三组数组存块稀疏矩阵 |
| 列向量稀疏（Column Vector Sparse） | 块稀疏矩阵的块列数取 1，显著降低块内零元素造成的算力浪费 |
| MMA 形状 | tensor core 一次矩阵乘加的最小形状，如 Ampere 的 $16\times8\times16$ |
| 可组合格式（Composable Format） | 把一个稀疏矩阵分解成多个不同块大小的子矩阵，按需混用 |
| 前缀缓存（Prefix Caching） | 多个请求共享同一段前缀时复用其键值缓存，避免重算 |
| 推测解码（Speculative Decoding） | 小模型先草拟多个候选 token，大模型并行验证 |
| 精简键（Reduced Keys） | 对每页的键做压缩表示，用于第一轮粗筛页块重要性 |
| 软件管理缓存 | 由 kernel 显式把数据预取到共享内存并复用，区别于硬件自动管理的 L1/L2 |
