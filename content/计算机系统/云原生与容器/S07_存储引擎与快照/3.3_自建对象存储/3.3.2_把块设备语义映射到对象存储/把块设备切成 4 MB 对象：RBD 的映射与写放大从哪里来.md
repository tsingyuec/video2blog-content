# 把块设备切成 4 MB 对象：RBD 的映射与写放大从哪里来

> 视频来源：[Ceph Tech Talks: RBD — Josh Durgin](https://www.youtube.com/watch?v=qA-Xqu2hCqU)（YouTube · Ceph，2015 年的技术分享）｜时长约 56 分钟
>
> 导读：这是一场把「块设备怎么架在对象存储上」从头拆到尾的技术分享。讲者先给出对象布局（哪几个对象存元数据、数据对象怎么按偏移编号），再逐条走过写路径、快照、克隆、watch/notify、独占锁和 object map，最后列出 Hammer 版本里为「少拷贝、少往返」加的若干优化。本文按本小节的题目重排：**先讲映射，再讲放大**——放大从哪来、哪一处被 RBD 消掉了、哪一处消不掉。视频里的 Ceph 术语（RADOS、OSD、CRUSH、librbd）首次出现时都会解释；末尾有一节把这种映射与 S3 这类纯对象存储做对照，那一节不是视频内容，是为呼应小节主题补的。

## 本讲要解决的核心问题（SCQA）

**背景**：对象存储对外只有「整个对象读、整个对象写、整个对象删」，而虚拟机要的是一块盘：固定 512 字节或 4 KB 的块、可以原地覆写第 100 万块、读写顺序由 guest 决定。

**冲突**：这两种语义看起来根本对不上——对象存储没有「写第 100 万块」这种请求。可现实里 RBD（RADOS Block Device）就是拿对象存储当盘用，虚拟机在里面装文件系统、跑数据库，一点也感觉不到背后是对象。

**疑问**：一块盘究竟是怎么被拆成对象的？拆完之后，一次 4 KB 的写会不会被放大成一次 4 MB 的写？

**回答（中心思想）**：映射靠两件事——**固定大小的对象**加**一份元数据索引**：盘按 4 MB 切块，第 $n$ 个对象就是盘上 $[4n, 4n+4)$ MB 那一段，元数据对象（header）里记着前缀、大小、快照和特性。写放大则要分两类看：**普通写几乎没有放大**，因为 RADOS 的对象支持部分覆写，4 KB 的写就是 4 KB 的写；**放大出现在「共享」上**——快照、克隆、flatten 这些要让多个逻辑盘共享同一批对象的操作，一律以**整个 4 MB 对象**为复制单位，于是「改 4 KB」变成「拷 4 MB」。此外还有一类放大是**元数据与协调**：每次打快照都要改 header 并通知所有持有者，克隆读要先问「这个对象在不在」。

## 一、RBD 的位置：对外是块设备，对内是对象

先看它在 Ceph 里的坐标。Ceph 有三张脸：对象存储（RGW，兼容 S3/Swift）、块设备（RBD）、文件系统（CephFS），三者都坐在 librados 之上，librados 之下是 RADOS——一个由一堆自愈、自管理的 OSD 组成的分布式对象存储。

![Ceph 的三张脸：RGW、RBD、CEPHFS 都建在 LIBRADOS 之上，最底下是 RADOS 对象存储](assets/把块设备切成%204%20MB%20对象：RBD%20的映射与写放大从哪里来/00030.webp)

RBD 有两种被消费的方式，二者在 guest 眼里没有区别：

- **用户态**：`librbd` 被链接进 QEMU 这类 hypervisor，虚拟机看到的就是一块普通磁盘，分不出背后是 RBD 还是本地盘；
- **内核态**：`rbd map` 把镜像映射成宿主上的一个块设备（`/dev/rbd0` 或 udev 生成的 `/dev/rbd/$pool/$image`），可以格式化、挂载文件系统，也可以再通过 iSCSI、NFS、Samba 导出。

[【跳转到 01:25】](https://www.youtube.com/watch?v=qA-Xqu2hCqU&t=85)

对外它声称「我是一块块设备」，对内它做的事是：**把这块盘的数据摊在整个集群（至少一个 pool）里**。它还有两个只有对象存储才做得出的能力——只读快照，以及写时复制的克隆（快速复制一块盘而不占额外空间）。这两件事正是后面写放大的主角。

[【跳转到 02:26】](https://www.youtube.com/watch?v=qA-Xqu2hCqU&t=146)

## 二、对象 + 索引：偏移怎么变成一个对象名

### 2.1 元数据对象：目录、父子关系、header

RBD 的元数据不是存在一张表里，而是**也存在对象里**。每个 pool 里有几类固定用途的对象：

![RBD 的元数据对象：rbd_directory 存名字与 ID 的双向索引、rbd_children 按父快照列出克隆、rbd_id.<image_name> 存内部 ID、rbd_header.<image_id> 存每个镜像的元数据](assets/把块设备切成%204%20MB%20对象：RBD%20的映射与写放大从哪里来/00336.webp)

- `rbd_directory`：镜像名 ↔ ID 的双向索引，`rbd ls` 就靠它；
- `rbd_children`：按父快照索引，列出 pool 里所有克隆。它的用处是：取消保护一个快照之前，必须遍历各 pool 的 `rbd_children`，确认没有克隆还引用它；
- `rbd_id.$image_name`：把用户起的名字映射到内部 ID。有了这一层，镜像改名不用去动克隆里的引用；
- `rbd_header.$image_id`：**真正的每镜像元数据**。它按 ID 命名（所以改名不影响它），里面装着数据对象的名字前缀、镜像大小、快照列表、每个快照的元数据、哪些块被占用、以及启用了哪些特性。

[【跳转到 05:36】](https://www.youtube.com/watch?v=qA-Xqu2hCqU&t=336)

注意 `rbd_children` 的存在说明了一件事：**引用关系要单独记账**。「这个快照还有没有人用」不能靠扫数据对象猜出来，得有一份索引。这是后面「元数据本身也是写放大来源」的第一个伏笔。

### 2.2 数据对象：编号就是偏移除以 4 MB

数据对象的命名规则极简：

- 共享前缀 `rbd_data.<镜像ID>.`，前缀本身存在 header 里；
- 后缀是一个从 0 开始递增的编号；
- 第 $n$ 个对象对应盘上第 $n$ 个 4 MB 区间。

![数据对象 rbd_data.* 的五个特点：按镜像内偏移命名、初始不存在、对象里就是裸数据、快照由 RADOS 处理、常常是稀疏的](assets/把块设备切成%204%20MB%20对象：RBD%20的映射与写放大从哪里来/00536.webp)

于是「读盘上的某个偏移」变成一次除法：

$$
n = \left\lfloor \frac{\text{offset}}{4\ \text{MB}} \right\rfloor,\qquad
\text{in-object offset} = \text{offset} \bmod 4\ \text{MB}
$$

不需要查表，不需要 B 树——这就是「对象 + 索引」里最省事的一种索引：**编号即地址**。

镜像是**精简置备**的：刚创建时只有元数据对象，一个数据对象都没有。读到不存在的对象就当全是零，等价于文件系统里的空洞；数据对象里存的就是裸字节，没有任何额外格式（快照那些事由 librbd 和 RADOS 管，不占对象内的空间）。

[【跳转到 05:51】](https://www.youtube.com/watch?v=qA-Xqu2hCqU&t=351)

对象还可以是**稀疏**的：默认按 4 MB 切，但写入往往小得多，一整个 4 MB 可能压根没被分配。这一句很关键，它说明「对象大小」和「写大小」本来就是两回事。

### 2.3 4 MB 是怎么定下来的

为什么是 4 MB，不是 4 KB，也不是 64 MB？讲者给了四条理由：

![条带化：对象大小统一、默认按 4 MB 切分设备、由 CRUSH 随机分布到各 OSD、并行工作摊到多块盘、没有哪组服务器专门负责一个镜像、小对象降低空间利用率方差](assets/把块设备切成%204%20MB%20对象：RBD%20的映射与写放大从哪里来/00736.webp)

1. **单次请求的上限**：4 MB 是 RADOS 一次请求能做的最大尺寸；
2. **一次寻道**：按机械盘「一次寻道能读到的数据量」优化，大到值得一次 IO，又小到不必等太久；
3. **并行**：对象按 CRUSH 随机落到各个 OSD，一块盘因此被摊到很多块盘上，请求可以并行；也**没有哪一组服务器专门负责某个镜像**，同时坏掉三台节点只影响一部分镜像的一部分数据；
4. **空间方差的约束**：RADOS 是随机放置，必须压住各 OSD 的空间利用率方差——只要有一个 OSD 快满就得阻止写入（日志还需要空间），所以对象不能太大。讲者的原话是「大到一次寻道能读完，但不要更大」。

[【跳转到 07:36】](https://www.youtube.com/watch?v=qA-Xqu2hCqU&t=456)

这四条理由里，第 4 条其实已经在暗示放大的代价：**对象的粒度是「空间管理」和「写放大」之间的折中**。粒度越大，元数据越少、顺序读越爽，但每次「共享」时要拷的东西也越大。

## 三、写路径：普通写为什么几乎不放大

### 3.1 关键前提：对象支持部分覆写

RBD 之所以能架在 RADOS 上而不被放大，靠的是 librados 的接口比「PUT 整个对象」丰富得多：

![LIBRADOS 接口：字节数据 + 属性 + 键值数据、对已有数据做部分覆写、单对象上的复合原子操作、RADOS classes（存储过程）](assets/把块设备切成%204%20MB%20对象：RBD%20的映射与写放大从哪里来/00311.webp)

- 对象 = 字节数据 + 一组属性/键值；
- **可以对已有数据做部分覆写、部分读**；
- 支持单对象上的复合原子操作，例如「检查某属性等于某值，再写入」；
- 还支持 RADOS classes（存放在 OSD 里的存储过程），RBD 用它屏蔽了不少底层细节。

[【跳转到 03:11】](https://www.youtube.com/watch?v=qA-Xqu2hCqU&t=191)

有了「部分覆写」，一次 4 KB 的写就只是往某个对象的某个区间写 4 KB，**不需要先把整个 4 MB 读上来、改完再写回去**。这是本讲最重要的一条对照：对象存储能不能当盘用，取决于它给的是「整对象 PUT」还是「区间写」。

### 3.2 IO 路径与 RBD cache

真实的 IO 路径是这样走的：

![IO 路径：VM 的 IO 经 hypervisor 里的 librbd 与 cache，再分发到 RADOS 集群里的多个 OSD](assets/把块设备切成%204%20MB%20对象：RBD%20的映射与写放大从哪里来/00811.webp)

虚拟机的 IO 先过自己的 page cache，再由 hypervisor 调 librbd。librbd 有自己的 cache：

- **write-back**：写进内存就立刻返回成功，几秒后或 cache 满了才真正写回集群；
- **write-through**：等数据真的落到集群才返回。

[【跳转到 08:36】](https://www.youtube.com/watch?v=qA-Xqu2hCqU&t=516)

这里有一个容易被误解的点，讲者专门澄清：cache 虽然「按对象组织」，但实际做的是**细粒度 IO**——一个 4 KB 的写写回时还是 4 KB，它只写虚拟机请求过的那部分，不会去读-改-写整个对象。

[【跳转到 09:11】](https://www.youtube.com/watch?v=qA-Xqu2hCqU&t=551)

Hammer 里 cache 默认以「安全模式」打开：在收到 guest 的 flush 之前是 write-through，看到 flush 才切到 write-back。这样它的行为和一块行为良好的硬盘 cache 一致——guest 要 flush 就落盘；代价是如果 guest 太老、或者关掉了 barrier，就可能丢数据（有人为了性能这么干）。cache 的真正价值是**合并写、削掉突发写的延迟**。

[【跳转到 10:11】](https://www.youtube.com/watch?v=qA-Xqu2hCqU&t=611)

小结这一节：**普通写这条路，放大系数接近 1**。4 KB 进去，4 KB 落到对象上。真正要付代价的是下面三件事。

## 四、写放大之一：快照以整个对象为单位做 COW

### 4.1 快照 context：把「快照」塞进每一次写

RBD 的快照不是在 pool 层做的，而是**在 RADOS 里按对象做写时复制**，靠一个叫 snapshot context 的东西维护：一个快照 ID 列表，加上当前最高的快照 ID。

![快照：粒度是对象；snapshot context 存在 rbd 的 header 里、随每次写发送；快照 ID 由 monitor 分配；删除是异步的；RADOS 记录每对象覆写统计所以 diff 很容易](assets/把块设备切成%204%20MB%20对象：RBD%20的映射与写放大从哪里来/01098.webp)

每次写都带上这个 context，于是可以在**单个镜像**上打快照，而不必对整个 pool 打快照。这种「自己管 context、存在 RBD 层」的做法叫 self-managed snapshot；快照 ID 由 monitor 分配，删除是异步的（OSD 在后台慢慢回收），RADOS 还按对象记录覆写统计，所以算 diff 很容易，增量备份直接建在它上面。

[【跳转到 10:58】](https://www.youtube.com/watch?v=qA-Xqu2hCqU&t=658)

### 4.2 第一次写到某个对象：拷整个 4 MB

讲者用两张图把这个过程讲得很清楚。假设镜像还没有快照，context 是空列表 `(∅, 7)`，最高快照 ID 是 7：

![写入时带上 snapshot context (∅, 7)，OSD 看到没有快照 ID，不需要做写时复制](assets/把块设备切成%204%20MB%20对象：RBD%20的映射与写放大从哪里来/01220.webp)

此时写入直接落盘，不复制任何东西。接着打一个快照，从 monitor 分配到 ID 8，librbd 更新 header、把 8 加进列表；之后的写都带 `([8], 8)`：

![打快照 8 之后再写同一个对象：OSD 发现该对象在快照 8 里还没被写过，于是先把整个对象拷一份，再写新数据](assets/把块设备切成%204%20MB%20对象：RBD%20的映射与写放大从哪里来/01320.webp)

OSD 发现「这次写落在快照 8 之后、且这个对象还没为快照 8 拷过」，于是：

1. 先把**整个对象**复制一份（XFS/ext4 上是全量拷贝；btrfs 上可以用 clone range，省掉这次拷贝）；
2. 记下元数据，表示这个对象在快照 8 上已经拷过；
3. 再写新数据。

[【跳转到 13:20】](https://www.youtube.com/watch?v=qA-Xqu2hCqU&t=800)

**这就是第一处放大**：打快照之后，第一次碰到某个 4 MB 对象，不管只改其中 4 KB，都要先搬 4 MB。放大系数最坏是

$$
\frac{4\ \text{MB}}{4\ \text{KB}} = 1024
$$

而且这个代价是**按对象摊的**：一个 100 GB 的盘，如果快照之后随机改了 1000 个分散的对象，就要拷 1000 × 4 MB = 4 GB。改的块越零散，放大越接近最坏值；改得越集中，越接近 1。

顺带一提，这也是「快照之后写入会变慢」的根因，而不是快照本身占了多少空间。

## 五、写放大之二：克隆的 copy-up 与 flatten

### 5.1 克隆是「整个镜像粒度」的写时复制

克隆是可写的，同样是写时复制，但层次不同：RADOS 只支持**单对象**上的事务，RBD 的克隆相当于把这件事做到**整个镜像**的粒度上。

![克隆的读：克隆里对象不存在时，直接去父镜像读](assets/把块设备切成%204%20MB%20对象：RBD%20的映射与写放大从哪里来/01851.webp)

克隆刚创建时没有任何数据对象，只有 header 和 id 对象，header 里按 ID（镜像 ID、pool ID）引用父快照。读的时候，如果克隆里对象不存在，就回退到父镜像去读。

克隆可以有完全不同的设置：条带策略、启用的特性、对象大小，甚至放在不同的 pool。讲者举的例子很实用——父镜像放 SSD pool，克隆放慢速 pool，因为克隆主要是读父镜像。

[【跳转到 17:26】](https://www.youtube.com/watch?v=qA-Xqu2hCqU&t=1046)

### 5.2 写一次 = 读整个对象 + copy-up + 写

克隆的写路径比快照更绕，因为它必须先判断「这个对象在不在克隆里」：

![克隆的写：先发一个"对象不存在就失败"的写；若不存在，则从父镜像读回整个对象、copy-up，再落这次写](assets/把块设备切成%204%20MB%20对象：RBD%20的映射与写放大从哪里来/01926.webp)

1. 先发一个带「对象不存在就失败」条件的写请求。**如果对象已存在，一次操作就够了**；
2. 如果失败，说明对象还不在克隆里，于是从父镜像把整个对象（或这次写覆盖的那段逻辑区间）读出来；
3. 再发一个操作：只有当对象**仍然**不存在时才做 copy-up——这是为了防止两个客户端同时 copy-up 同一个对象、互相覆盖；
4. 最后在这份数据之上落这次写。

[【跳转到 18:46】](https://www.youtube.com/watch?v=qA-Xqu2hCqU&t=1126)

**这是第二处放大**：克隆里第一次写某个对象，代价是「读 4 MB + 写 4 MB」，而不是「写 4 KB」。而且它比快照的 COW 更贵，因为快照的拷贝发生在同一份数据上（本地拷贝），克隆的 copy-up 要跨对象、跨 pool 把父镜像的数据拉过来。

Hammer 为此加了一个开关 **copy-on-read**：把 copy-up 从「写时」挪到「读时」——读的时候就把整个对象取回来并在后台 copy-up。对跨地域、高延迟的集群特别划算：反正迟早要拷，不如在顺序读的时候顺手拷完，避免在写路径上付这笔延迟。

[【跳转到 24:43】](https://www.youtube.com/watch?v=qA-Xqu2hCqU&t=1483)

### 5.3 flatten：把「共享」一次性还清

克隆对父镜像的依赖只能靠一种方式解除：把数据全部拷过来，这就是 flatten——对克隆里的每个对象触发一次 copy-on-write，然后删掉父引用（包括 `rbd_children` 里那条记录）。

[【跳转到 17:56】](https://www.youtube.com/watch?v=qA-Xqu2hCqU&t=1076)

**这是第三处放大，也是最直白的一处**：flatten 的代价是「整个镜像有多大就搬多少」，与「改了多少」无关。它和快照/克隆的 COW 是同一条逻辑的极端情形——**只要共享的单位是对象，解除共享的单位也只能是对象**。

## 六、写放大之三：元数据与协调

数据之外还有两类写：改 header，以及让所有持有者知道 header 变了。

### 6.1 打快照要改 header，还要通知所有人

因为每次写都要带 snapshot context，虚拟机在跑的时候怎么打快照？靠 RADOS 的 watch/notify：

![watch/notify：hypervisor 里的 librbd 和 /usr/bin/rbd 都在 header 对象上设置 watch](assets/把块设备切成%204%20MB%20对象：RBD%20的映射与写放大从哪里来/01476.webp)

- 打开镜像时，librbd 在 header 上设一个 watch；
- header 一有变化（改大小、flatten、加/删快照），就通知所有 watch 同一个 header 的客户端；
- 收到通知的客户端在**下一次操作前**重新读 header，确保拿到最新的 context 和大小。

打快照的流程因此是：从 monitor 拿快照 ID → 更新 context、保存快照元数据（大小、特性等不可变状态）→ 发 notify → **等所有 watcher 回应或超时**，全部 ACK 才算完成。

[【跳转到 15:26】](https://www.youtube.com/watch?v=qA-Xqu2hCqU&t=926)

这里的放大不是字节数，而是**往返与阻塞**：一次快照要等所有持有者的 ACK；一次 header 变更会让所有客户端重新读一遍 header。客户端越多，这笔账越大。

### 6.2 一次写要持锁，读克隆要先问「在不在」

Hammer 引入的 **exclusive locking** 让写、打快照、改大小、discard 都要在 header 对象上持锁，并和 watch/notify、RADOS 的锁机制配合，防止多个客户端同时写。持锁者会收到其他客户端的请求通知，于是快照、改大小这类操作会被**转给持锁者执行**，而不是各干各的。

[【跳转到 28:18】](https://www.youtube.com/watch?v=qA-Xqu2hCqU&t=1698)

它还用上了 RADOS 的 blacklisting：如果发现旧的持锁者已经不再 watch，就把它拉黑（地址 + 会话 nonce 写进 OSD map），之后它的所有操作都被拒绝。这解决的是「虚拟机卡在别处、其实已经在别处重启」的经典问题。

还有一处隐性开销：克隆读的时候要先判断「这个对象在不在克隆里」，不在就回退父镜像。**克隆链有多深，就要问多少次**。Hammer 的 **object map** 就是为这个加的索引——记录镜像里哪些对象存在，一次请求就能定位，还能顺手统计「快照占了多少空间」「克隆比父镜像多了多少」。它默认关闭，且当时只能对新建镜像启用。

[【跳转到 29:53】](https://www.youtube.com/watch?v=qA-Xqu2hCqU&t=1793)

## 七、把放大压下去：Hammer 里的几件工具

讲者列了一张清单，基本都是围绕「少拷贝、少往返、少重复缓存」：

![Hammer 新增特性清单：copy-on-read、librbd cache 默认安全模式、启动期预读、LTTng tracepoint、allocation hints、cache hints、exclusive locking（默认关）、object map（默认关）](assets/把块设备切成%204%20MB%20对象：RBD%20的映射与写放大从哪里来/02418.webp)

- **copy-on-read**：把 copy-up 挪到读时，见 5.2；
- **cache 安全模式默认开启**：write-through 直到看到 flush，见 3.2；
- **启动期预读**：顺序 IO（比如虚拟机启动）时，RBD cache 会预读最多 50 MB；到 50 MB 就停，因为之后 guest 里的内核自己会做预读。启动早期 BIOS 只会发很小的请求，预读对老式总线提升明显；
- **allocation hints**：告诉 RADOS「这些对象最终会是 4 MB」，第一次写就整块分配。在 XFS 上这能显著降低碎片——**这是直接针对「小写造成碎片」的补救**；
- **IO hints**：读写调用可以标注顺序/随机、是否要缓存。RBD cache 写回时用它避免在 OSD 的 page cache 里重复缓存；对 import/export 这类只读一次的顺序写也有用；
- **LTTng tracepoint + 回放工具**：采集真实 IO 的轨迹（时间、大小、偏移），再回放到镜像上做基准测试，比合成基准更贴近真实负载。

[【跳转到 26:53】](https://www.youtube.com/watch?v=qA-Xqu2hCqU&t=1613)

把这几件工具和前面的放大对照一下，会发现它们各自只治一处：预读治读延迟，allocation hints 治碎片，copy-on-read 治 copy-up 的时机，object map 治「逐层问父镜像」。**没有一件能改变「复制单位是对象」这个事实**——那是布局决定的。

### 8.1 QEMU/libvirt 与内核客户端

几个容易踩的坑：

- **cache 要两边都开**：如果 QEMU 侧没设成 writeback，guest 的 flush 根本不会传到 librbd；
- **总线选 virtio**：virtio-blk / virtio-scsi 性能好于 IDE；
- **discard 支持不完整**：RBD 支持 discard（TRIM），但 QEMU 需要特殊参数才传给 guest，virtio-blk 干脆不支持，得走 virtio-scsi。

内核侧简单得多：`rbd map` 一条命令，udev 生成好认的软链。但它**不支持全部特性**（比如 striping v2），大多数选项（包括 rbd cache）只对用户态有效——内核路径靠上层文件系统的 page cache，不需要 RBD 再套一层。

### 8.2 与 S3 这类纯对象存储的对照（本文补充，非视频内容）

视频里的 RADOS 是「对象存储」，但它不是 S3。把两者放在一起看，才能回答「为什么云上做块设备不直接用 S3」：

| 维度 | RADOS 上的 RBD（本视频） | S3 这类纯对象存储 |
| --- | --- | --- |
| 写接口 | 支持对对象做区间写、部分读 | 只有整对象 PUT、GET、DELETE |
| 改 4 KB 的代价 | 写 4 KB | 读回整个对象、改、再 PUT（读-改-写） |
| 对象是否可变 | 可变，可原地覆写 | 不可变，覆写等于产生新对象 |
| 元数据 | header 对象 + object map 索引 | 需自建索引，且索引本身也要写 |
| 每次操作的开销 | 一次 RADOS 请求（集群内） | 一次 HTTP 往返 + 鉴权 |

由此可以列出**纯对象存储做块设备时，写放大的五个来源**：

1. **最小写单位是对象**：改 4 KB 也要重传整个 4 MB；
2. **对象不可变**：覆写 = 新对象 + 更新索引，旧对象要等 GC；
3. **索引本身的写**：每次写都要更新「逻辑块 → 对象 key」的元数据；
4. **HTTP 开销**：每个对象一次 PUT，小 IO 被放大成网络往返；
5. **副本/纠删码**：对象存储内部再放大一遍（RBD 这边同样有，只是发生在 RADOS 层）。

对应的缓解手段也就顺理成章：**更小的 chunk**（把 4 MB 降到 64 KB～1 MB，用元数据量换写放大）、**日志结构 / 写合并**（把随机小写攒成顺序大对象）、**本地缓存 + 写回**（RBD cache 就是这个思路）、**multipart 上传与 Range GET**（把一次大对象拆成多次可并行的请求）、以及 S3 Express 这类为小对象低延迟设计的存储类。视频里的 RBD 恰好是把其中两条做到极致：**对象可变**（消掉第 1、2 条）和**缓存合并写**（消掉第 4 条的一部分）。这也解释了为什么 EBS 这类云盘不做成纯对象存储——块设备的语义要求和对象存储的不可变性天然冲突。

## 小结

- **映射 = 固定大小的对象 + 一份元数据索引**。RBD 的做法最省：第 $n$ 个数据对象就是盘上第 $n$ 个 4 MB 区间，偏移除以 4 MB 就是对象编号，不需要查表。
- **索引本身也是对象**：`rbd_directory`、`rbd_children`、`rbd_id.$image_name`、`rbd_header.$image_id`。它们承担了「名字、引用关系、快照、特性」这些对象存储不提供的东西。
- **4 MB 是折中**：单次请求上限、一次寻道、CRUSH 随机分布的并行度，以及必须压住的空间利用率方差。
- **普通写几乎不放大**，因为 librados 支持对对象的区间写；4 KB 进去，4 KB 落到对象上。这一条是 RBD 能成立的前提。
- **放大出现在共享上**：快照的 COW 拷整个 4 MB 对象；克隆的 copy-up 是「读 4 MB + 写 4 MB」；flatten 是整盘拷贝。放大系数最坏到 $4\ \text{MB} / 4\ \text{KB} = 1024$。
- **还有一类放大是协调**：打快照要改 header 并等所有 watcher 的 ACK；克隆读要先问「对象在不在」，链有多深就问多少次（object map 就是为这个加的索引）。
- **优化只治单点**：copy-on-read 挪时机、allocation hints 治碎片、预读治读延迟、object map 治逐层查询——没有一件能改变「复制单位是对象」这个由布局决定的事实。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| RADOS | Ceph 底层的分布式对象存储，由一堆自愈的 OSD 组成 |
| librados / librbd | RADOS 的客户端库；librbd 在它之上实现块设备语义 |
| RBD | RADOS Block Device，把镜像当块设备用；镜像数据被切成 4 MB 对象 |
| OSD | Object Storage Daemon，真正存对象、做复制与恢复的进程 |
| CRUSH | RADOS 的伪随机放置算法，决定对象落在哪些 OSD 上 |
| rbd_header | 每个镜像的元数据对象，存前缀、大小、快照列表、特性 |
| snapshot context | 快照 ID 列表 + 最高快照 ID，随每次写发送，决定要不要 COW |
| COW（写时复制） | 写之前先把旧数据复制一份，供快照/克隆继续引用 |
| copy-up | 克隆里第一次写某对象时，把父镜像的数据拷进克隆 |
| flatten | 把克隆对父镜像的依赖彻底解除，代价是整盘拷贝 |
| watch/notify | librados 客户端之间的低频通知机制，用于 header 变更广播 |
| exclusive lock | 在 header 上持锁，串行化写、快照、改大小、discard |
| object map | 记录镜像里哪些对象存在的索引，省掉克隆读时逐层查父 |
| allocation hints | 告诉 RADOS 对象最终大小，第一次写就整块分配，减少碎片 |
| 精简置备 | 先只给元数据，数据对象按需分配；读到不存在的对象返回全零 |
