# 共享到数据块而不是文件：reflink 的引用计数与按块分裂的代价

> 视频来源：[16·native 与 btrfs：一个靠拷贝，一个靠 reflink｜containerd 源码深读](https://www.bilibili.com/video/BV1b8xP6bEWC/)（Bilibili · 隔岸的灯塔_）｜时长约 8 分钟
>
> 导读：讲者用 containerd 的两个快照器实现做对照——`native` 整目录拷贝、`btrfs` 靠子卷快照共享数据块，把「共享的粒度」这件事讲得很具体。本文顺着这条线，落在本小节的题目上：共享的数据块靠什么记账、部分写入时被写的那一块怎么从共享集合里分裂出来、以及分裂之后要还的账（碎片化、空间延迟释放）。`native` 的四步流程与三种快照器的选型只保留与「粒度」相关的部分；分裂过程中锁与事务的细节见同小节的另一篇《一次写时复制不是原子的》。

## 本讲要解决的核心问题（SCQA）

**背景**：容器镜像是一层一层叠出来的，每一层在磁盘上对应一个快照。要新建一个可写快照，最直白的做法就是把父层的目录整个复制一份——`native` 快照器就是这么干的，代码不到 800 行，逻辑清楚到没有失败模式。

**冲突**：同一个动作换成 `btrfs` 快照器，耗时从「和父层大小成正比」变成毫秒级，`df` 几乎不涨。更奇怪的是，这个几乎没花时间的副本随后可以随便改，改完原件纹丝不动；而 `native` 那份老老实实复制出来的目录，反而要占掉一整个镜像的空间，解一个 1G 的镜像要几分钟。

**疑问**：既然数据一个字节都没搬，副本凭什么能独立修改？「改副本」这个动作，究竟改到了磁盘上的什么东西？

**回答（中心思想）**：因为共享的粒度不是文件，而是**数据块**。克隆只是让两个子卷的元数据指向同一批块，并在元数据里记下「这些块还有人用」；真正写入时，文件系统只把**被写的那一块**从共享集合里分裂出来、复制成新块，再改这一个子卷的映射。分裂的单位就是块，所以克隆是 O(1)，而分裂的代价按「改了多少块」而不是「文件多大」来计——但引用计数把旧块一直留在盘上，这笔账要在删除和碎片化上还。

## 一、两种「复制」：整目录拷贝与共享数据块

### 1.1 native：把父层整个复制一份

`native` 快照器的思路是「一个目录一个快照」：`snapshots/<id>/` 里装着那一层的完整内容，没有任何上下层叠加。

![native 快照器的四个特点：一个目录一个快照、拷贝时保留权限属主 xattr 硬链接时间戳、不支持 copy-up、可作为兜底](assets/共享到数据块而不是文件：reflink%20的引用计数与按块分裂的代价/00052.webp)

一次 Prepare 分四步落地：

![native 的 Prepare 四步：建临时目录 new-XXXX、递归拷贝父层并保留属性、原子改名、bind 挂载](assets/共享到数据块而不是文件：reflink%20的引用计数与按块分裂的代价/00087.webp)

1. 在快照根目录下建一个 `new-` 开头的临时目录；
2. 如果有父层，递归拷贝父层，权限、属主、扩展属性、硬链接、时间戳全都保留；
3. 把临时目录原子改名成自己的 id；
4. 返回 bind 挂载，把这个目录直接挂给容器。

[【跳转到 01:27】](https://www.bilibili.com/video/BV1b8xP6bEWC/?t=87)

第 3、4 步的顺序很讲究：**先改名再返回挂载**，保证返回的那一刻目录已经就位。临时目录的意义是失败可回滚——拷到一半出错，把 `new-` 开头的删掉就行，不会污染已有快照。

拷贝过程中有个细节值得记住：扩展属性复制失败时走的是 `ignore` 错误处理器，直接跳过，不让整个操作失败。

![native 的核心三行代码：MkdirTemp 建临时目录、CopyDir 递归拷贝父层（xattr 失败跳过）、Rename 原子落位](assets/共享到数据块而不是文件：reflink%20的引用计数与按块分裂的代价/00127.webp)

原因是像 `security` 这类属性在容器外往往没权限，为了它让整个快照创建失败不值得。这也说明 `native` 的「完整拷贝」其实是有损的：拷的是它拷得动的那部分。

它的价值不在快，而在**可预测**：任何时候进目录看，看到的就是那个快照的全部内容；别的快照器跑不起来的文件系统，它照样能跑。代价同样好算——时间上是层数乘以每层大小，解一个 1G 的镜像可能要几分钟；空间上每个快照都是完整的一份，六个层叠下来就是六份增量，磁盘占用比 overlay 高一个数量级；并发也差，两个容器同时解包，磁盘直接被打满。

### 1.2 btrfs：让文件系统替你复制

`btrfs` 的思路完全相反：它不复制，让文件系统干活。

![btrfs 快照器的四个特点：子卷不是目录、快照等于一次 reflink、写时复制、只读视图直接建成 readonly 子卷](assets/共享到数据块而不是文件：reflink%20的引用计数与按块分裂的代价/00205.webp)

关键在于「子卷不是目录」：子卷是文件系统里一棵可以独立快照的树。建快照就是发一个 reflink，**所有数据块共享，只复制元数据**，所以是常数时间；之后改哪个块才复制哪个块，这就是写时复制。只读视图更简单，直接建成只读子卷，就一条 ioctl，快到可以忽略。

## 二、共享的粒度：从「文件」降到「数据块」

讲者用一句话点出了本节的关键差别：

> 它和 overlay 的差别在力度：overlay 共享到文件，btrfs 共享到数据块——同一个文件改一半，只复制改的那部分。

这句话要拆成两层来读：

- **共享单位**：overlay 的 lower 层里，一个文件要么整份被共享，要么整份被 copy-up 到 upper 层；btrfs 里共享的单位是数据块，一个文件可以「前一半共享、后一半私有」。
- **分裂单位**：因此写一个字节时，overlay 要把**整个文件**复制上去；btrfs 只把**被写的那一块**分裂出来。

所谓「extent 分裂」，说的就是这个动作：一个 extent 在磁盘上是一段连续块，克隆之后它被多个子卷（或多个 inode）共同指向。当有人只写其中一小段时，这一段必须从共享的 extent 里「切」出来——切出来的部分复制成新块、挂到写入方的映射上，剩下的部分继续按原样共享。

```
克隆后：
  子卷 A ──┐
           ├──> extent E（块 100..131，32 个块，共享）
  子卷 B ──┘

A 写了块 110：
  子卷 A ──> extent E1（块 100..109，仍共享）
         ──> 新块 N（块 110 的内容副本，A 私有）
         ──> extent E2（块 111..131，仍共享）
  子卷 B ──> extent E（完整 32 个块，一个字节都没动）
```

一次部分写入之后，原来的一个 extent 在 A 的映射里变成了三段（前段共享、中段私有、后段共享），而 B 那边看到的还是原来那个完整的 extent。**分裂是按块发生的，不是按文件发生的**——这正是 btrfs 能「同一个文件改一半只复制改的那部分」的原因。

## 三、引用计数：谁还在用这些块

克隆之所以是 O(1)，是因为它只做了两件事：让新子卷的元数据指向同一批块，并把「这些块现在有两个主人」这件事记下来。这份记录就是**引用计数**：每个共享的块（或一段共享 extent）都有一个计数，表示当前有多少个引用指向它。

它带来两个必须记住的推论。

### 3.1 引用不为零，块就不能释放

删除文件时，文件系统做的是「把引用减一」，而不是「把块清零回收」。只要还有别的子卷（别的快照）引用着这些块，它们就必须原样留在盘上。

这就是那个让很多人困惑的现象：**btrfs 里删了镜像，`df` 却没变**。

[【跳转到 06:40】](https://www.bilibili.com/video/BV1b8xP6bEWC/?t=400)

![五个现场问题：解包慢是不是落到 native、删了镜像 df 没变说明快照链没断、能不能混用快照器、子卷删不掉怎么办、native 值不值得留](assets/共享到数据块而不是文件：reflink%20的引用计数与按块分裂的代价/00400.webp)

讲者的答案是：说明快照链没断，旧数据块还被别的快照引用着。空间不是「没释放」，而是**按引用计数的规则还不能释放**。

### 3.2 删除的顺序：元数据是唯一真相

正因为块的生命周期由引用决定，删除一个快照就不是「删目录」这么简单。btrfs 快照器的做法是在一个事务里做两件事：

![删除快照的代码：先 storage.Remove 删元数据记录，再 btrfs.SubvolDelete 删子卷，失败只告警](assets/共享到数据块而不是文件：reflink%20的引用计数与按块分裂的代价/00336.webp)

1. 先从元数据里删记录；
2. 再去删子卷。

[【跳转到 05:32】](https://www.bilibili.com/video/BV1b8xP6bEWC/?t=332)

为什么是这个顺序？因为如果先删子卷再删元数据，中间崩了，就会留下一条指向不存在子卷的记录，后续所有操作都可能出错。反过来，子卷删失败只告警不报错：元数据已经删了，这时候回滚更麻烦，不如留一个孤儿目录，等下次清理时收拾。

讲者把这条总结成快照器的通用原则：**元数据是唯一真相，磁盘上的东西可以慢慢对账**。这句话放在引用计数上同样成立——先让账本（元数据、引用）正确，块什么时候真正回收可以晚一点。

顺序错了的后果很具体：删子卷必须先卸载再删目录，顺序错了会留下一个删不掉的**幽灵子卷**，只能等下次挂载再清。

![btrfs 快照器的磁盘结构：snapshots/1 是独立子卷，snapshots/2、3 用父 id 共享数据块，active 是可写层](assets/共享到数据块而不是文件：reflink%20的引用计数与按块分裂的代价/00259.webp)

顺带说明一下为什么 btrfs 快照器必须要求根目录真的在 btrfs 上：挂载时用的不是路径而是**子卷 id**，换到 ext4 上会直接初始化失败。

## 四、分裂要还的账

把成本从「准备快照」挪到「写入」，账单不会消失，只是换了个时间点付。讲者列了 btrfs 的四个真实麻烦：

![btrfs 的四个麻烦：删子卷要两步、空间不立刻释放、碎片化、要定期 balance](assets/共享到数据块而不是文件：reflink%20的引用计数与按块分裂的代价/00302.webp)

1. **删子卷要两步**：先卸载再删目录，顺序错了留幽灵子卷；
2. **空间不立刻释放**：快照链不断，旧块就一直被引用着；
3. **碎片化**：频繁的写时复制会让文件散落各处，读性能慢慢下滑；
4. **要定期 balance**：不跑越来越慢，跑了又抢 IO。

[【跳转到 05:02】](https://www.bilibili.com/video/BV1b8xP6bEWC/?t=302)

第 3 条是「按块分裂」的直接代价。`native` 的拷贝是顺序写一大段，落盘位置天然连续；而 CoW 每次分裂都要在空闲空间里另找位置放新块，写得越碎、分裂次数越多，一个逻辑上连续的文件在物理上就越散。这也是为什么「按块分裂」省下了拷贝时间，却可能在小块随机写上输回去。

对比之下，`native` 的坑特别朴素：慢、占空间、并发差——都能提前算出来，不会半夜给你惊喜。

## 小结

- **共享的粒度决定分裂的粒度**：overlay 共享到文件，btrfs 共享到数据块；同一个文件改一半，只有被写的那一块被复制。
- **克隆是 O(1) 的原因**：只改元数据、只给共享块记引用，不搬数据；`native` 的整目录拷贝则是层数乘以每层大小的线性成本。
- **引用计数决定块的生命周期**：删文件只是减引用，只要快照链还在引用，块就不释放，所以会出现「删了镜像 `df` 没变」。
- **分裂的代价被推迟了**：碎片化、空间延迟释放、要定期 balance，都是把成本从 prepare 挪到写入与运维的结果。
- **顺序与账本优先**：删除时先删元数据再删子卷，失败只告警——元数据是唯一真相，磁盘上的东西可以慢慢对账。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| 数据块（block） | 文件系统分配空间的最小单位，reflink 共享与分裂都以它为单位 |
| extent | 一段连续的块，用一个「起始块 + 长度」描述，比逐块列表省元数据 |
| reflink | 让两个文件或子卷指向同一批数据块、只复制元数据的操作，代价与数据量无关 |
| 引用计数 | 记录一段共享块还被多少个引用指向；不为零就不能回收 |
| 写时复制（CoW） | 写入前先把要改的部分复制成私有副本，再改副本，原件保持不变 |
| 分裂（split） | 部分写入时把一个共享 extent 拆成「前段共享 + 新块私有 + 后段共享」的过程 |
| 子卷（subvolume） | btrfs 里一棵可以独立快照的树，不是普通目录，有自己的子卷 id |
| 幽灵子卷 | 删除顺序错误后残留、普通方式删不掉的子卷，要等下次挂载清理 |
| balance | btrfs 的后台整理操作，重新分布数据块以缓解碎片化，会占用 IO |
