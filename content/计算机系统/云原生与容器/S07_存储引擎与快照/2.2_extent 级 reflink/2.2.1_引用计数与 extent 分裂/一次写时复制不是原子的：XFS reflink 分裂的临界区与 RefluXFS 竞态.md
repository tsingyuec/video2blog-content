## 本讲要解决的核心问题（SCQA）

**背景**：reflink 让「复制 10GB 数据」变成瞬间完成的事——原文件和副本暂时指向磁盘上同一批物理块，谁都不搬数据。当其中一个文件被修改时，XFS 应该先创建一个新的私有块再写入，这就是写时复制。

**冲突**：正常情况下这层保护很可靠，原件不会被副本的修改波及。但 2026 年披露的 RefluXFS（视频给出的编号是 CVE-2026-64600）打破了这个假设：两个线程几乎同时写同一个 reflink 副本，结果**数据倒流回了原来那个受保护的文件**。一个普通本地账号就可能借此覆盖同一卷上任何可读文件，包括 `/etc/passwd` 或 SUID root 程序。

**疑问**：写时复制听起来只是「写之前先复制一块」，为什么会存在一个能被别的线程插进去的窗口？一次分裂究竟由哪几步组成？

**回答（中心思想）**：因为**一次分裂不是一条原子指令，而是一段跨越锁与事务的临界区**：读旧块映射 → 释放 inode 锁 → 等待文件系统事务 → 返回后按手里的映射写入。锁一旦在中间放开，另一个线程就可能完成自己的写时复制并把副本搬到新块上，此时旧块只剩原文件一个引用；第一个线程返回时没有刷新映射，仍然握着旧地址，于是把数据写进了原文件。

「暂时」两个字是全部问题的起点。共享期间，磁盘上那批块是**一份数据、两个主人**；只要有一方要写，就必须先把「共有」变成「私有」，否则写副本就等于写原件。这一步转换就是分裂：

![reflink 的工作方式：原文件与副本都指向 Block X；副本被修改时应先创建一个新的私有块 Block Y](assets/一次写时复制不是原子的：XFS%20reflink%20分裂的临界区与%20RefluXFS%20竞态/panel_reflink.webp)

[【跳转到 01:14】](https://www.youtube.com/watch?v=pIvI61o5Odo&t=74)

注意图里那条分界线：**分界线之上是共享状态，分界线之下是分裂之后的状态**。写时复制要做的，就是把「副本 → Block X」这条箭头改指到 Block Y，同时让 Block X 的引用数减一。这个「改指 + 减引用」必须一起完成，中间不能有别人看见半成品——漏洞恰恰出在这里。

## 二、一次分裂的四步，以及中间那个窗口

视频把写路径拆成了四步，这也是本小节最值得记住的一张图：

![竞态条件：线程 A 的写路径是读旧映射、释放 inode 锁、等待事务、返回后仍写旧块；线程 B 在此期间完成 CoW 并把副本搬到 Block Y](assets/一次写时复制不是原子的：XFS%20reflink%20分裂的临界区与%20RefluXFS%20竞态/panel_race.webp)

线程 A（写路径）：

1. **读到旧的块映射**：Block X；
2. **释放 inode 锁**；
3. **等待文件系统事务**；
4. 事务完成后返回，**仍然按手里的旧映射写入 Block X**。

线程 B（CoW 路径）在同一个窗口里做了两件事：

1. 完成了写时复制；
2. 把副本搬到了 Block Y。

[【跳转到 01:34】](https://www.youtube.com/watch?v=pIvI61o5Odo&t=94)

把两条时间线并排看，问题就很直观了：

```
时间 →
线程 A:  [读映射=Block X] [放锁] ...... [等事务] ...... [写 Block X]
线程 B:                          [完成 CoW] [副本→Block Y]
                                        ↑
                        此刻 Block X 只剩原文件一个引用
```

线程 B 完成 CoW 之后，Block X 的所有权发生了变化：**它现在只属于原文件了**。而线程 A 手里握的还是分裂之前的地址，它并不知道自己等的这段时间里世界变了。

这里有两个概念值得单独解释，因为它们是理解整个漏洞的钥匙：

- **inode 锁**：保护一个 inode 的元数据（包括它的块映射）不被并发修改的锁。谁要改映射，先拿锁。
- **文件系统事务**：文件系统把「分配新块、改映射、更新引用」这些元数据改动打包成一个原子提交单元。分配和记账要走事务，而事务可能要等、要写日志。

于是第 2 步和第 3 步之间就出现了一个矛盾：**要等事务，就不能一直握着 inode 锁**（否则别人全被堵住）；可一旦放锁，自己手里的映射就成了「过期快照」。

## 三、陈旧映射：一次分裂失败会写坏谁

视频对这个后果的描述很准确：

> 但第一个线程返回时没有刷新自己的块映射，它手里还握着旧的磁盘地址。于是用户看起来是在写自己拥有的文件，数据却会倒流回原来那个受保护的文件。

[【跳转到 01:54】](https://www.youtube.com/watch?v=pIvI61o5Odo&t=114)

它给了一个很贴切的类比：**就像你在改一份复印件，结果发现被锁住的原件反而被改了。**

这正是「分裂」这件事的要害。分裂的目的本来是让写入方拿到一块**私有**的块，从此写它不影响任何人；而陈旧映射让写入方以为自己在写私有块，实际写的是那块已经归原文件独占的旧块——共享关系已经解除，但写入方还按共享时代的地址在写。

后果的严重性来自三个叠加：

1. **越权范围是整个卷**：攻击者能覆盖同一个开了 reflink 的 XFS 卷上任何可读的文件；
2. **目标可以是提权跳板**：`/etc/passwd` 这样的口令数据库，或者一个 SUID root 程序，都能通向完整 root 权限；
3. **痕迹很小**：视频引述 Qualys 的报告说，这个改动可以直接写到磁盘、能熬过重启，而且不会留下明显的 kernel log。

[【跳转到 02:14】](https://www.youtube.com/watch?v=pIvI61o5Odo&t=134)

边界也要说清楚：这是**本地漏洞，不是远程攻击**。攻击者必须已经能在机器上执行代码，而且系统必须使用开启了 reflink 的 XFS。

## 四、从漏洞反推：分裂必须满足的三条约束

这个 bug 藏了将近九年，但它反过来说明了「引用计数 + 分裂」这套机制对实现的要求有多硬。把视频里的时间线翻译成设计约束，可以列出三条：

1. **映射与引用必须一起变**：Block X 从「两个主人」变成「一个主人」的那一刻，所有持有旧映射的写入方都必须被同步到新状态。账本（引用）和视图（映射）不能分开更新。
2. **锁的作用域要覆盖整段临界区**：从「读映射」到「按映射写」之间，任何放锁都必须伴随一次映射校验或重新获取。视频里线程 A 的问题不是放锁本身，而是放锁之后**没有刷新**。
3. **事务等待不能成为正确性缺口**：等事务是性能上的必要（不能长期占锁），但它把一次分裂拉长成了一个可以被并发观察的区间，因此必须有机制保证「等完之后手里的地址仍然有效」。

这也解释了为什么这类 bug 特别难找：它不是某一行写错了，而是两个各自合理的决定（放锁避免阻塞、等事务保证原子提交）拼在一起，在极窄的时间窗里产生了错误。视频里说，这个漏洞是 Qualys 用 AI 在内核代码里找「类似 Dirty COW 的漏洞」时发现的。

## 小结

[【跳转到 04:08】](https://www.youtube.com/watch?v=pIvI61o5Odo&t=248)

- **reflink 的共享是「暂时」的**：原文件与副本指向同一批物理块，写入前必须先把共有变成私有。
- **一次分裂是四步，不是一步**：读旧映射 → 释放 inode 锁 → 等文件系统事务 → 按映射写入；中间那段是临界区，不是原子的。
- **放锁 + 等事务 = 可能拿到陈旧映射**：别的线程在此期间完成 CoW 并把副本搬到新块，旧块只剩原文件引用，而写入方还按旧地址写。
- **后果是「数据倒流」**：看似在写自己的副本，实际写进了受保护的原文件，可覆盖 `/etc/passwd` 或 SUID 程序，且改动直接落盘、熬过重启、无 kernel log。
- **约束**：引用与映射必须同步更新；锁的作用域要覆盖「读映射 → 写」全程；事务等待之后必须重新校验地址有效性。
- **边界**：本地漏洞，需要已能在机器上执行代码，且卷开启了 reflink；修复方式是安装内核更新并重启。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| reflink | 让两个文件指向同一批物理块、只复制元数据的操作，克隆代价与数据量无关 |
| 写时复制（CoW） | 写入前先把要改的部分复制成私有块，再改私有块，原件不受影响 |
| 分裂 | 部分写入时把共享块从「共有」切成「私有」的过程，本漏洞就出在这段过程里 |
| 块映射（extent map） | inode 里记录「逻辑偏移对应哪个物理块」的表，分裂就是改这张表 |
| inode 锁 | 保护单个 inode 元数据（含块映射）不被并发修改的锁 |
| 文件系统事务 | 把分配、改映射、更新引用等元数据改动打包原子提交的单元 |
| 陈旧映射（stale mapping） | 放锁期间映射已被别人改掉，自己手里还留着旧地址的状态 |
| 引用计数 | 记录一块共享数据还被多少个引用指向；减到零才能回收 |
| SUID root 程序 | 运行即获得 root 权限的可执行文件，常被用作提权跳板 |
