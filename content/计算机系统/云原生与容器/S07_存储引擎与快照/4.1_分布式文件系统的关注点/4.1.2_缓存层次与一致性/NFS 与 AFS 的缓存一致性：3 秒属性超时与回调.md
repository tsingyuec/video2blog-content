# NFS 与 AFS 的缓存一致性：3 秒属性超时与回调

> 视频来源：[CS 537: OS - 24 | Persistence: Distributed File Systems: NFS, AFS](https://www.youtube.com/watch?v=L0nW9UoFvHg)（YouTube · University of Wisconsin-Madison）｜时长约 75 分钟
> 导读：这是一堂把「缓存一致性」拆成三段来算账的课：服务端缓存、客户端写回、客户端属性缓存，每一段各自划出一条边界。NFS 把边界定在时间上（属性 3 秒过期、close 必须刷回），AFS 把边界定在 open/close 上（整文件缓存 + 回调）。本篇只讨论缓存与一致性，不讲 NFS 的完整 RPC 语义；自动字幕里的 `item potent`、`P read` 等已订正为 idempotent、pread。

## 本讲要解决的核心问题（SCQA）

**背景**：在单机文件系统里，两个进程读写同一个文件是「立刻可见」的。因为它们共享同一份内核 buffer cache：一个进程写进内存的数据块，另一个进程下一次读就直接读到了，不需要等磁盘，也不需要等 close [【跳转到 07:47】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=467)。

**冲突**：一旦文件放在服务器上、由多个客户端挂载，这份「共享的缓存」就不存在了。每个客户端有自己的缓存，服务器自己也有一层缓存，一次写要跨过三段路才能被别人看到。于是同一个 `read()` 系统调用，在分布式环境下可能返回旧数据。

**疑问**：客户端到底在什么时候才能看到别人的写？系统又凭什么敢让客户端缓存——不怕读到过期数据吗？

**回答（中心思想）**：分布式文件系统的一致性边界不是一条线，而是**三层缓存各划一段**：服务端缓存决定「写什么时候真正落盘」，客户端数据缓存决定「写什么时候传回服务器」，客户端属性缓存决定「客户端什么时候发现别人改过」。NFS 用**超时**给这三段各贴一个时间戳（属性 3 秒过期、close 必须刷回），代价是语义怪异；AFS 用**回调（callback）**把边界钉在 open/close 上，代价是服务器必须记住谁打开了什么。

## 一、跨机器之后，「立刻可见」这件事就没了

讲者一上来就把 NFS 和 AFS 的取舍讲清楚了：NFS 的核心创新是**无状态（stateless）**——服务器崩了重启，什么都没丢，协议照样工作；代价是性能差、扩展性差，而且有一个「非常奇怪的缓存一致性协议」，你很难说清一个客户端会读到什么 [【跳转到 02:47】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=167)。

AFS 走的是反方向：服务器**记录状态**，记住哪些客户端正在操作哪些文件。因为握有状态，它反而更可扩展，一致性模型也更符合直觉。

### 1.1 单机的一致性来自共享缓存，而不是来自协议

单机上的一致性其实是个「免费赠品」：所有进程共享同一个 buffer cache。任何一个进程写了一个数据块，只要它在内存里，别的进程读同一个块就立刻看到新内容。不需要等刷盘，不需要等 close，什么都不用等。

分布式文件系统把这份共享拆成了多份：

| 缓存位置 | 缓存内容 | 谁负责失效 |
| :--- | :--- | :--- |
| 服务端 page cache | 刚收到的写、刚读出的块 | 服务端自己（刷盘策略） |
| 客户端数据缓存 | 文件数据块 | 客户端自己（靠协议约定） |
| 客户端属性缓存 | inode 属性、mtime、size | 客户端自己（靠超时或回调） |

三层里任何一层不同步，用户看到的就是「旧数据」。所以「缓存一致性」这个问题，本质上是**给每一层指定一个失效责任人和一个失效时机**。

### 1.2 结构：客户端挂载的是目录树的一段

NFS 的部署形态很朴素：一台文件服务器跑着本地文件系统（比如 ext4），几百个客户端通过 RPC 连上来 [【跳转到 12:02】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=722)。

![NFS 架构：客户端各自持有缓存，通过 RPC 访问带本地文件系统的文件服务器](assets/NFS%20与%20AFS%20的缓存一致性：3%20秒属性超时与回调/00722.webp)

客户端这边，`mount` 决定的是「目录树的哪一段归谁管」：`/` 在本机 ext4 上，`/backups` 在另一块盘上，`/home/tyler` 则在 NFS 上 [【跳转到 14:23】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=863)。

![mount 把不同文件系统拼进同一棵目录树：/ 与 /backups 是本地盘，/home/tyler 来自 NFS](assets/NFS%20与%20AFS%20的缓存一致性：3%20秒属性超时与回调/00863.webp)

这一层的存在很关键：它意味着**「文件在哪」对应用透明**。同一份 `read()` 代码，读本地文件就走 ext4，读 home 目录就走 NFS 客户端代码。也正因为透明，用户才会误以为两边语义一样——而后面所有麻烦都来自这个错觉。

## 二、NFS 的起点：把状态全部推给客户端

要理解 NFS 的缓存策略，得先理解它为什么长成那样。答案是：**它不许服务器记住任何东西**。

### 2.1 第一版设计：让服务器替客户端记住 fd，直接失败

最自然的想法是「把系统调用原样转发」：客户端 `open`，服务器 `open` 并返回一个文件描述符，客户端之后 `read` 就把这个 fd 号发回去。

问题在于 fd 里装的是**状态**：inode 号加上当前的读写偏移量。偏移量由服务器推进，服务器就记住了「这个客户端读到哪了」 [【跳转到 17:38】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=1058)。

![把 fd 留在服务器上：服务器内存里要维护每个客户端的 fd 表，这是状态](assets/NFS%20与%20AFS%20的缓存一致性：3%20秒属性超时与回调/01058.webp)

服务器一崩，这些 fd 全没了，客户端手里那个「fd 2」在重启后的服务器上毫无意义。把状态持久化到磁盘又太慢，而且会引出更麻烦的问题：你得信任客户端——它可能开一堆文件再也不关，服务器就得无限期替它记着。

### 2.2 无状态的含义：每个请求自带全部信息

于是 NFS 改成：**每个请求把要做什么完整写清楚**，服务器不需要回忆任何历史。讲者特意补了一句精确表述：服务器**可以**保留状态，但**不能依赖**它——缓存、提示都可以有，一旦丢掉，正确性不能受影响，最多是性能差一点 [【跳转到 21:30】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=1290)。

具体到接口，就是文件句柄（file handle）：

```
fh = open(char *path);
pread(fh, buf, size, offset);
pwrite(fh, buf, size, offset);
```

![文件句柄 = 卷 ID + inode 号 + generation 号，对客户端完全不透明](assets/NFS%20与%20AFS%20的缓存一致性：3%20秒属性超时与回调/01697.webp)

句柄里塞了 `generation` 号，是为了解决 inode 复用：inode 号会被回收给新文件，generation 每分配一次就加一，于是「inode 号 + generation」在时间上唯一。客户端不许解释句柄内容，只当它是个不透明的令牌 [【跳转到 28:17】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=1697)。

### 2.3 无状态的代价：只能有幂等操作

无状态还带来一条硬约束。RPC 提供的是**至少一次（at-least-once）**语义：调用返回成功，只说明它至少执行了一次，可能执行了两次。所以协议里只能有**幂等（idempotent）**操作——执行一次和执行多次效果相同 [【跳转到 31:37】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=1897)。

![幂等操作的定义：f() 与 f();f();…;f() 效果相同](assets/NFS%20与%20AFS%20的缓存一致性：3%20秒属性超时与回调/01897.webp)

`read` 天然幂等；`pwrite` 写到固定偏移也幂等（重复写同一段数据结果一样）；但 `append` **不幂等**——重放一次就多出一个 B。`mkdir` 和 `creat` 属于「实践上幂等」：最终状态一样，但返回码不同（已存在时报错）。

结论是：**append 从协议里被删掉了**，改由客户端翻译。客户端保留 fd 表，fd 里存「服务器给的句柄 + 当前偏移」，append 就是「按自己记的偏移做一次 pwrite」 [【跳转到 37:27】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=2247)。

![客户端逻辑：fd 表在客户端，偏移由客户端推进，发出去的是带偏移的 pread](assets/NFS%20与%20AFS%20的缓存一致性：3%20秒属性超时与回调/02314.webp)

这一步值得停一下：**偏移量这个状态从服务器搬到了客户端**。搬走之后，服务器就彻底无状态了，但也意味着「服务器不知道客户端读到哪」，后面它同样不会知道「客户端缓存了什么」。

## 三、第一层缓存：服务端写成功不等于写进磁盘

讲者把缓存问题拆成三个，第一个就是服务端的。

如果 `pwrite` 的 RPC 要等服务器真的写进磁盘才返回，那太慢了。所以服务器通常写完内存 buffer 就返回。可一旦服务器在「已返回」和「已刷盘」之间崩溃，磁盘上就会出现**不属于任何一个时间点的状态** [【跳转到 42:58】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=2578)。

![服务端崩溃的例子：客户端依次写 A/B/C 再写 X/Y/Z，磁盘最后是 X、B、Z，没有任何一次写失败](assets/NFS%20与%20AFS%20的缓存一致性：3%20秒属性超时与回调/02578.webp)

拆开看就明白了：X 写进块 0 并刷盘了；Y 写进块 1 但没刷盘；此时崩溃重启；客户端接着写 Z 到块 2 并刷盘。最终磁盘是 X、B、Z——每一次写都「成功」了，可这个组合从未真实存在过。

讲者说修复只有两条路 [【跳转到 44:22】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=2662)：

1. **不缓冲**，每次写完才返回——性能差；
2. **让内存不丢**：给内存加电池备份或额外供电，掉电也不丢数据。

这也解释了一个商业现象：早年卖 NFS 服务器的多是硬件厂商，卖点就是「我们给缓存配了电池」。

## 四、第二层缓存：客户端的写，什么时候传回服务器

第二个问题才是本节的主角：多个客户端缓存同一个文件，谁先看到谁的修改。

客户端必须缓存，否则几百个客户端每个读都打到服务器，服务器立刻成为瓶颈 [【跳转到 45:01】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=2701)。于是问题变成两个子问题：

- 客户端 A 改了缓存块，**什么时候**传回服务器？
- 服务器有了新数据，客户端 B **怎么知道**自己的缓存过期了？

### 4.1 回传时机：close 是唯一硬保证

回传有几种可能的设计 [【跳转到 47:13】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=2833)：

- 每次写立刻回传：等于放弃缓存，太慢；
- 每隔固定时间回传：语义奇怪；
- **NFS 的选择：`close()` 时必须把所有改过的块刷回服务器**，其他时候（比如内存紧张）也可能刷，但不保证。

![NFS 的更新可见性：close 时必须刷回；但文件刷回不是原子的，两个客户端同时刷会交错](assets/NFS%20与%20AFS%20的缓存一致性：3%20秒属性超时与回调/02833.webp)

注意这张幻灯片最后两行——它们正是 NFS 没解决的问题：

- **刷回不是原子的**：一次只刷一个块，中途别人可能看到半新半旧的文件；
- **两个客户端同时 close**：各自的块以任意顺序到达，服务器把两组修改交错合并，没有「谁赢」的规则 [【跳转到 48:03】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=2883)。

### 4.2 失效通知：服务器不能主动推，只能客户端来问

B 怎么知道缓存过期？最直接的办法是服务器主动告诉 B「你缓存的那个块变了」。讲者说这在 NFS 里**根本行不通**：要通知 B，服务器就得记住 B 缓存了什么——这又是状态 [【跳转到 49:03】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=2943)。

所以 NFS 把责任推给客户端：**用之前先问一句**。

![过期缓存的解法：客户端在使用缓存前先向服务器确认，而不是让服务器推送失效](assets/NFS%20与%20AFS%20的缓存一致性：3%20秒属性超时与回调/03018.webp)

具体做法是发一次 `stat`（getattr）：「这个文件的 mtime 是多少？」如果服务器上的 mtime 比客户端拿到副本的时间更新，客户端就丢弃缓存重新取。

### 4.3 现实打脸：stat 占了 90% 的请求

这个方案能用，但扩展性很差。讲者给出实测结论：它撑不过几十个客户端，因为客户端全在发 `stat`，服务器 **90% 的时间在回答「文件变了没」这种问题** [【跳转到 53:13】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=3193)。

![Measure then build：NFS 开发者发现 stat 占了服务器 90% 的请求，因为客户端频繁复查缓存](assets/NFS%20与%20AFS%20的缓存一致性：3%20秒属性超时与回调/03218.webp)

于是有了 NFS 最著名的那个妥协：**属性缓存 3 秒**。

![减少 stat：客户端缓存 stat 的结果，但如果不设过期，就永远看不到更新](assets/NFS%20与%20AFS%20的缓存一致性：3%20秒属性超时与回调/03243.webp)

机制很朴素：客户端记住上次 `stat` 的结果，并在 3 秒后（讲者特意说明这是个**可配置参数**）把它忘掉。忘掉之后下次用到属性就得重新问服务器。效果是每个客户端最多每 3 秒问一次 [【跳转到 53:38】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=3218)。

代价写在语义里：**别的客户端改完之后，你最多要等 3 秒才能看到** [【跳转到 54:53】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=3293)。

顺带一个容易忽略的细节：NFS 客户端对属性极其饥渴，所以服务器在**每次交互**（包括每次读）的回复里都捎带属性。客户端不必额外发 `stat`，只要它手上的属性还没超过 3 秒就直接用；超过了才补一次 getattr [【跳转到 70:40】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=4240)。

### 4.4 到这里，NFS 的一致性边界可以写清了

把三段拼起来，NFSv2 给的是这样一个模型：

- 写：`close()` 时保证刷回，之前不保证；
- 读：本地缓存可以直接用，但属性超过 3 秒就要重新确认；
- 冲突：两个客户端同时 close，块级交错，没有赢家。

讲者也承认这不是什么优雅设计：NFS 靠一堆「hacky」的补丁让它在实践中够用，但从语义上讲很难说清一个读会返回什么 [【跳转到 46:41】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=2801)。

## 五、AFS：把边界从「时间」换成「open/close」

AFS（Andrew File System，卡内基梅隆大学 1980 年代的产物）的目标写得很直白：更合理的并发访问语义、更好的扩展性，**愿意为此牺牲简单性和无状态** [【跳转到 56:14】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=3374)。

### 5.1 先测量，再设计：整文件缓存

AFS 的第一个决定是**按整个文件传输**，而不是按块。依据是测量结果：绝大多数情况下，你读了一个块，就会把整个文件读完；只读一小段的情况非常罕见 [【跳转到 57:04】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=3424)。

![AFS 整文件缓存：open 时取回整个文件，close 时刷回，open 到 close 之间用的是同一份版本](assets/NFS%20与%20AFS%20的缓存一致性：3%20秒属性超时与回调/03424.webp)

这一条同时解决了两件事：

- **语义**：从 open 到 close，客户端看到的是同一份文件，不会中途被别人的修改「插进来」；
- **性能**：只有 open/close 需要找服务器，read/write 全部本地完成。

### 5.2 回传：整文件覆盖，最后 close 的人赢

close 时把整个文件刷回服务器。和 NFS 的块级交错不同，AFS 保证**一次 close 的写全部完成之后，才开始处理另一次 close 的写**，所以最后 close 的那个客户端版本会成为服务器上的最终版本 [【跳转到 59:09】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=3549)。

这仍然是「最后一次写覆盖前面所有写」，不是合并。讲者提醒：如果你真的在意谁赢，得在文件系统之上再加锁或调度机制——文件系统只保证「结果是一个完整的版本」，不保证「你的修改被保留」。

### 5.3 失效：回调（callback）

第三个问题——B 怎么知道 A 改过了——AFS 的答案是：**服务器记着谁打开了什么，主动通知**。

![AFS 用回调消除过期缓存：服务器记住哪些客户端打开了这个文件，被覆盖时打断回调](assets/NFS%20与%20AFS%20的缓存一致性：3%20秒属性超时与回调/03654.webp)

机制是这样的 [【跳转到 60:54】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=3654)：

1. B `open` 文件 Z，服务器记下「Z 正被 B 缓存」，这就是建立了一个**回调（callback）**；
2. B 之后所有读都用本地副本，完全不问服务器；
3. A 写了 Z，服务器**打断**（break）B 的回调；
4. B 并不会立刻被抢走数据——它这次 open 期间仍然用旧副本，保证「open 到 close 同一版本」；
5. B 下一次 `open` 时发现回调已被打断，才重新取一份新文件。

关键在第 4 步：**回调只在 open 时检查**，不是每次 read 都查 [【跳转到 69:25】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=4165)。这让 AFS 的语义非常好描述：一个客户端在 open/close 之间看到的世界是稳定的。

## 六、把两条路径放进同一个 workload

讲者最后用一张时间表把两种协议摆在一起：客户端 A 反复读，客户端 B 在 t=40 打开、t=50 写、t=70 关闭，A 在 t=80 再读、t=90 关闭、t=100 重新打开 [【跳转到 64:00】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=3840)。

![同一份 workload 在 NFS 与 AFS 下的对照表：每个时刻客户端做了什么、服务器要做什么](assets/NFS%20与%20AFS%20的缓存一致性：3%20秒属性超时与回调/03840.webp)

结论可以直接背下来：

| 时刻 | NFS 下客户端 A 看到什么 | AFS 下客户端 A 看到什么 |
| :--- | :--- | :--- |
| t=60，B 已写未 close | 旧数据（B 还没刷回） | 旧数据（B 还没刷回） |
| t=80，B 已 close | 新数据（属性超时后重新 stat） | **旧数据**（本次 open 期间版本不变） |
| t=100，A 重新 open | 新数据 | 新数据（回调已断，重新取） |

最后一行是 AFS 最漂亮的地方：服务器在 t=70 收到 B 的 close 时就打断了 A 的回调，但 A 直到 t=100 重新 open 才去检查，于是它「该看到新版本的时候」自然就看到了 [【跳转到 67:20】](https://www.youtube.com/watch?v=L0nW9UoFvHg&t=4040)。

![缓存一致性对照：NFS 是「别人 close 后 3 秒」，AFS 是「别人 close 后你下次 open」](assets/NFS%20与%20AFS%20的缓存一致性：3%20秒属性超时与回调/03769.webp)

讲者把两种模型的差别浓缩成一句话：

- **NFS**：单块读，别人 close 之后 **3 秒**，你才可能看到更新；
- **AFS**：整文件，别人 close 之后你**下一次 open**，保证看到更新。

## 七、这套取舍今天还在用

把这一讲放回「缓存层次与一致性」的框架里，可以得到几条可迁移的判断：

1. **一致性的成本由「谁记住谁」决定**。NFS 拒绝让服务器记住客户端，于是只能让客户端反复确认，代价是 90% 的 stat 流量；AFS 让服务器记住「谁打开了什么」，于是能做主动失效，代价是服务器复杂、崩了要恢复状态。
2. **TTL 与回调是同一个问题的两种答案**。TTL 不需要任何状态，但一致性边界只能精确到「时间」；回调需要状态，但边界可以精确到「事件」（open/close）。
3. **粒度决定冲突语义**。NFS 按块刷回，两个客户端同时 close 会交错出「不属于任何人的文件」；AFS 按整文件覆盖，最后 close 者赢，至少结果是一个完整版本。
4. **服务端缓存是独立的一层**。即使客户端全部正确，服务器「写完内存就返回」也会在崩溃后留下不属于任何时间点的磁盘状态——这层只能靠不缓冲或电池备份内存解决。

## 小结

- 单机的一致性来自共享 buffer cache；分布式把这份共享拆成服务端缓存、客户端数据缓存、客户端属性缓存三层，每层都要单独指定失效责任。
- NFS 为了崩溃后能直接重启，坚持无状态：请求自带全部信息（文件句柄 = 卷 ID + inode + generation），协议里只允许幂等操作，`append` 被挪到客户端翻译。
- 服务端缓存不落盘就返回，会在崩溃后产生「没有任何一次写失败、但磁盘状态不属于任何时间点」的结果；修复只有不缓冲或让内存不掉电。
- NFS 的写回边界是 `close()`；失效边界是 **3 秒属性超时**，因此别人改完最多 3 秒后可见，且两个客户端同时 close 会块级交错。
- AFS 用整文件缓存 + 回调把边界换成 open/close：open 取全文件、close 整文件刷回、最后 close 者赢；回调只在 open 时检查。
- 两种模型的本质区别：NFS 把一致性交给**时间**，AFS 把一致性交给**事件**。

## 关键术语速查

| 术语 | 一句话解释 |
| :--- | :--- |
| 无状态协议 | 服务器不依赖任何跨请求的记忆；可以缓存，但丢了不能影响正确性 |
| 文件句柄 | NFS 给客户端的令牌，内含卷 ID、inode 号与 generation 号，客户端不得解析 |
| generation 号 | inode 每次被重新分配给新文件时递增，用来避免 inode 复用导致的「读写到错文件」 |
| 幂等操作 | 执行一次与执行多次效果相同；RPC 的至少一次语义要求协议只含幂等操作 |
| close-to-open | 关闭时刷回、下次打开时取新版本的一致性语义；NFS 是它的弱化版，AFS 是它的标准形态 |
| 属性缓存 | 客户端缓存的 inode 属性（mtime、size 等），NFS 里默认 3 秒过期 |
| 回调（callback） | 服务器记住谁打开了文件，文件被改时打断回调，客户端下次 open 时重新取 |
| 至少一次语义 | RPC 返回成功只表示至少执行一次，可能重复执行 |
