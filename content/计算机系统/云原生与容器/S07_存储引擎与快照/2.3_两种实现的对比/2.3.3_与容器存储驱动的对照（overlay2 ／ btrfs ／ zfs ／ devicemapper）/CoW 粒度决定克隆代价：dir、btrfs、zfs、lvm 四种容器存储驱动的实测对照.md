# CoW 粒度决定克隆代价：dir、btrfs、zfs、lvm 四种容器存储驱动的实测对照

> 视频来源：[Benchmarking LXD storage drivers](https://www.youtube.com/watch?v=z_OKwO5TskA)（YouTube · LXD 官方频道，讲者 Stéphane Graber）｜时长约 28 分钟
>
> 导读：这是一次**动手量的**对照，不是概念介绍。讲者在同一台 12 核 NVMe 机器上，用 `lxd.benchmark` 依次把 dir、zfs、btrfs、lvm 设成默认存储池，各创建 100 个容器，记下耗时与磁盘占用。本文顺着这组数字，把「CoW 粒度」这件事落到一张可以查的对照表上——它和本系列 2.1（文件级 copy-up）、2.2（extent 级 reflink）讲的是同一件事的两种极端，这里看的是**真实驱动上的代价**。字幕为平台自动字幕，术语已逐窗口核对纠正（如 "borofs"→btrfs、"cfs"→zfs、"lex d"→LXD、"quarters"→quotas）。

## 本讲要解决的核心问题（SCQA）

**背景**：容器镜像是一层一层叠出来的，起一个容器不该把几百兆的镜像整份复制一遍——这是容器能"秒起"的前提。第 2.1、2.2 节我们已经从机制上拆过两条路：文件级 copy-up（改文件就整份复制）和 extent 级 reflink（只分裂被写的那一块）。

**冲突**：机制讲清了，可落到具体驱动上，差距大得离谱。同一台机器、同一个 ubuntu 镜像：用 dir 驱动创建 100 个容器要 **216 秒**、吃掉 **47 GB**；换成 btrfs 只要 **5.14 秒**、占**单份镜像那点空间**（zfs 上实测约 300 MB）。差了四十倍，空间差了上百倍。

**疑问**：这四十倍到底省在了哪一步？是"创建"这个动作本身变便宜了，还是把成本挪到了别处？

**回答（中心思想）**：差别在 **CoW 的粒度**，而粒度决定了「新建一个实例」要不要搬数据。dir 根本没有 CoW，每个实例都得把镜像的文件重新写一遍，所以耗时与**镜像大小 × 实例数**成正比；btrfs、zfs 的克隆只改元数据、让新实例指向同一批数据块，耗时与镜像大小**无关**；lvm 走块级 thin pool，克隆按块做，粒度比 extent 粗、每实例还有一笔建块设备的固定开销。粒度越细，"克隆"越接近 $O(1)$，而"第一次写"的代价被推迟到真正写入的那一刻。

## 一、先看清单：六种驱动，差别在"数据放哪"

LXD 的文档里列了六种存储驱动，讲者说通常算五种，因为后两种（ceph 与 cephfs）是同一套分布式存储的两种形态。

![LXD 文档的存储驱动清单与"数据放哪"矩阵：dir 只能与宿主共享，btrfs/lvm/zfs 可用专用盘或 loop 文件](assets/CoW%20粒度决定克隆代价：dir、btrfs、zfs、lvm%20四种容器存储驱动的实测对照/00050.webp)

[【跳转到 00:42】](https://www.youtube.com/watch?v=z_OKwO5TskA&t=42)

清单是：**dir（Directory）**、**btrfs**、**lvm**、**zfs**、**ceph（RBD）**、**cephfs**。文档那张矩阵说明的是另一件重要的事——**数据放在哪**：dir 只能"与宿主共享文件系统"，btrfs / lvm / zfs 既能用专用盘或分区，也能退而求其次塞进一个 loop 文件里，ceph 系则把数据放到远端。

讲者的态度很直接：**没有银弹**。LXD 一般推荐 zfs，但 zfs 不在内核主线里，不是到处都有；而且它也不是万能的——如果你要在容器里再跑 Docker，btrfs 往往更合适。选型的朴素版本是"顺着你已有的东西走"：系统本来就在 btrfs 上就用 btrfs，本来就在用 LVM 就用 lvm，只想快速做几次测试、不想预分配任何存储，那 dir 正合适。

先把实验台搭起来。讲者把 alpine 与 ubuntu 两个镜像拷到本地（**不能让下载时间混进基准结果**），此时默认存储池是 dir：

## 二、dir：没有 CoW，每个实例都把镜像重新解包一遍

第一组是 dir + alpine，100 个容器。alpine 很小，所以这是"最好情况"：

![dir 驱动创建 100 个 alpine 容器用 7.38 秒，删除 100 个用 1.50 秒](assets/CoW%20粒度决定克隆代价：dir、btrfs、zfs、lvm%20四种容器存储驱动的实测对照/00526.webp)

[【跳转到 08:46】](https://www.youtube.com/watch?v=z_OKwO5TskA&t=526)

7.38 秒，还行。但这只是"小镜像 + 快盘"造成的错觉。换成 ubuntu：

![dir 驱动创建 100 个 ubuntu 容器用 216.296 秒，同一批删除只要几十秒](assets/CoW%20粒度决定克隆代价：dir、btrfs、zfs、lvm%20四种容器存储驱动的实测对照/00551.webp)

[【跳转到 09:11】](https://www.youtube.com/watch?v=z_OKwO5TskA&t=551)

**216.296 秒**，三分半。讲者一边等一边看另一台终端：系统负载冲到 **70 以上**，而机器只有 12 核。

原因写在字幕里，很朴素：

> 每一个实例都要把整个镜像重新解包一遍，这注定很慢。

这句话可以写成一条成本公式。设镜像解包一次要 $t_{\text{unpack}}$，创建 $n$ 个实例：

$$
T_{\text{dir}} \approx n \times t_{\text{unpack}}
$$

空间同理，每个实例都是完整的一份：

$$
S_{\text{dir}} \approx n \times S_{\text{image}}
$$

实测数字对得上：创建 100 个 ubuntu 容器时，存储池已经写了将近 **40 GB**，跑完总共 **47 GB**。讲者特意强调，这正是"能 CoW 就一定要 CoW"的理由——省的不只是时间，是整份整份的磁盘。

[【跳转到 07:09】](https://www.youtube.com/watch?v=z_OKwO5TskA&t=429)

注意这里**没有"第一次写"的惩罚**：dir 在创建时就把所有代价付清了。这也是后面所有对照的基准——CoW 驱动省下的创建时间，迟早要在别的地方还。

## 三、btrfs 与 zfs：克隆不搬数据，创建时间与镜像大小无关

换 zfs。第一个实例明显慢一些，因为它得**真正解包一次**：

之后就是关键的一步——同样 100 个 **ubuntu** 容器：

![zfs 驱动创建 100 个 ubuntu 容器用 7.813 秒；屏幕左下角的手写笔记显示 alpine 是 7.7 秒](assets/CoW%20粒度决定克隆代价：dir、btrfs、zfs、lvm%20四种容器存储驱动的实测对照/00676.webp)

[【跳转到 11:16】](https://www.youtube.com/watch?v=z_OKwO5TskA&t=676)

**7.813 秒**。而刚才 100 个 alpine 是 **7.7 秒**——几乎一模一样。屏幕左下角那三行笔记就是讲者随手记下的对照：

```
dir:   7.3  216.2
zfs:   7.7    7.8
```

这组数字是整支视频最有说服力的一处。它说明 zfs 上创建容器的耗时**与镜像大小无关**，而这正是一个 CoW 文件系统该有的表现：

> 它只创建增量，而增量源有多大并不影响创建时间。

换成公式，克隆的代价与镜像大小 $S_{\text{image}}$ 无关，只与实例数有关：

$$
T_{\text{cow}} \approx n \times t_{\text{clone}}, \qquad t_{\text{clone}} \ll t_{\text{unpack}}
$$

空间上也一样：讲者说磁盘占用"实际上就是单个实例那 **300 MB** 左右，不管你建多少个都不会涨，直到它们真的开始写——那才是写时复制的触发点"。

讲者还试了一件"理论上应该更快"的事：zfs 默认建在 ext4 上的一个 loop 文件里（也就是 dir 后端那一套），那就换成直通 NVMe 分区试试。结果**更慢了**，再跑一次还是一样。

他的结论不是"直通分区没用"，而是：**这正是基准工具的意义**——你可以试不同的存储配置，也可以更细地调 zfs、btrfs、lvm 的参数，再跑这些循环看 LXD 到底快不快。别把"理论上更快"当成结论。

## 四、lvm：块级 thin pool，固定成本最高的一档

lvm 这一轮讲者没有现场跑完，但给了结论：lvm 也能用同样的方式创建，只是**通常比 zfs 和 btrfs 慢不少**；不过在创建大批 ubuntu 实例时，它**仍然比 dir 快**。总体顺序是 btrfs、zfs 在前，lvm 居中，dir 垫底。

这个结论在他们每天跑的基准看板上更清楚：

![LXD 每日基准看板：Create 128 containers 一格里 btrfs 约 9 秒、dir 约 13 秒、lvm 约 59 秒、ceph 约 2 分钟](assets/CoW%20粒度决定克隆代价：dir、btrfs、zfs、lvm%20四种容器存储驱动的实测对照/01648.webp)

[【跳转到 27:28】](https://www.youtube.com/watch?v=z_OKwO5TskA&t=1648)

看板分四格：创建单个、创建 128 个、启动单个、启动 128 个，每格里按驱动给出 min / max / avg。在"创建 128 个"这一格上：

| 驱动 | 创建 128 个容器（avg） |
| --- | --- |
| btrfs | 约 9 秒 |
| dir | 约 13 秒 |
| lvm | 约 59 秒 |
| ceph | 约 2 分钟 |

为什么 lvm 比 btrfs 慢这么多？把它的位置摆清楚就明白了：lvm 的 CoW 发生在**块级**——每个容器对应一个 thin pool 里的块设备，克隆是按块（chunk）做的，粒度比 extent 粗；而且每个实例都要**建一个块设备、配一套映射**，这笔固定成本在小规模上摊不开。讲者说的"zfs 每实例要跑一堆命令"是同一类成本，lvm 上更重。

这也解释了本系列 2.3.1 讲过的那个结论：**粒度越粗，单位操作的固定开销越大，但元数据越省**。块级 CoW 的优点是每容器一个真正的块设备（配额、迁移都方便），缺点是每次创建都要在块层走一遍。

## 五、把四种驱动按 CoW 粒度归位

把上面这些数字和机制合起来，就是本节要的那张表：

| 驱动 | CoW 粒度 | 新实例怎么落地 | 空间占用 | 第一次写的代价 | 实测 100 个 ubuntu |
| --- | --- | --- | --- | --- | --- |
| dir（Docker 里对应 vfs） | 无 CoW，整份复制 | 把镜像的文件全部写一遍 | 与实例数成正比 | 无（创建时已付清） | 216 秒 / 47 GB |
| btrfs | extent（子卷快照） | 元数据指向同一批数据块 | 单份 | 分裂被写的那一块 | 5.14 秒 / 单份 |
| zfs | record / extent（dataset 克隆） | 同上 | 单份 | 分裂被写的那一块 | 7.8 秒 / 约 300 MB |
| lvm | 块（thin pool 的 chunk） | 建块设备 + 块映射 | 单份 | 分配并复制块 | 未现场测（128 个约 59 秒） |

再把这四种粒度对到 Docker 的驱动名上（这一步是本文的归纳，不是视频里的原话，但每一格都能由上面的机制推出来）：

- **overlay2 / aufs**：**文件级** copy-up。它介于 dir 与 btrfs 之间——创建新容器几乎不花时间（只叠一层空的 upper），但**第一次写某个文件时要整份复制那个文件**。所以"创建快、写大文件慢"是它的特征，这也是本系列 2.1.2 讲的"第一次写大文件会卡住"。
- **btrfs / zfs 驱动**：**extent 级**。创建是克隆，写时才分裂被写的那一块，创建耗时与镜像大小无关——正是本节实测到的那条曲线。
- **devicemapper**：**块级** thin pool。和 lvm 是同一套内核机制（device mapper 的 thin provisioning target），代价结构也一致：每容器一个块设备，粒度是块。
- **vfs**：就是这里的 dir，不做任何 CoW，最慢最占空间，只在"别的都用不了"时兜底。

一句话记住这张表：**CoW 粒度决定"新建"要不要搬数据**。不搬（extent / 块级）→ 创建是 $O(1)$；整份搬（dir / vfs）→ 创建是 $O(S_{\text{image}})$；只搬被写的文件（overlay2）→ 创建是 $O(1)$，但第一次写是 $O(S_{\text{file}})$。

## 六、怎么自己量一遍：工具、坑与读法

工具是 `lxd.benchmark`（snap 自带；不用 snap 的发行版可能提供 `lxd-benchmark` 包，都没有就得自己编译）。它支持几种动作：单纯创建、创建并启动、启动、停止、删除；可以指定批次大小与并行度，也能把结果输出成 CSV 方便画图——讲者他们的每日看板就是这么来的。

几条实测出来的经验：

1. **先把镜像拷到本地**，别让下载时间混进结果；
2. **测存储就只测创建**。讲者用 `launch` 起 500 个 alpine（创建 + 启动一起做），结果花了 **528.9 秒**，还挂了几个：

![500 个容器的 launch 批次用 528.929 秒，日志里出现多条 context deadline exceeded 的创建失败](assets/CoW%20粒度决定克隆代价：dir、btrfs、zfs、lvm%20四种容器存储驱动的实测对照/01479.webp)

[【跳转到 24:39】](https://www.youtube.com/watch?v=z_OKwO5TskA&t=1479)

这批里既有存储开销，也有每个实例启动、拿 IP、起进程的 CPU 开销，混在一起就量不准存储了。日志里的 `context deadline exceeded` 说明批次开得太大时会撞上超时——这本身也是个有用的信号：**你能承受多大的批次**。

3. **别只看秒表，也看 `htop`**：到底是在等存储，还是 CPU 已经跑满在解包？这两种慢要用完全不同的办法治。
4. **小心系统层面的天花板**。讲者一边跑一边提醒：实例数上去以后，先撞上的往往不是存储，而是 Linux 网桥 `lxdbr0` 的 4096 上限；默认网桥又是 /24 子网，只有 253 个左右可用 IP，超过之后后面的实例拿不到 IP。

## 小结

- **粒度决定克隆代价**：dir 没有 CoW，每个实例把镜像重新解包一遍，耗时与镜像大小 × 实例数成正比；btrfs、zfs 克隆只改元数据，创建耗时与镜像大小无关。
- **一组可复现的数字**：同一台 12 核 NVMe 机器上，100 个 ubuntu 容器——dir 216.3 秒 / 47 GB，btrfs 5.14 秒，zfs 7.8 秒；后两者空间都只有单份镜像大小（zfs 上实测约 300 MB）。
- **创建时间与镜像大小无关，是 CoW 的指纹**：zfs 上 100 个 alpine 是 7.7 秒、100 个 ubuntu 是 7.8 秒，几乎相同；dir 上是 7.3 秒对 216 秒。
- **块级比 extent 级多一笔固定成本**：每日看板上创建 128 个容器是 btrfs 约 9 秒、dir 约 13 秒、lvm 约 59 秒——lvm 每实例要建块设备与块映射，这笔固定开销在批量创建时最明显。
- **CoW 不是免费的**：dir 在创建时把代价付清，CoW 驱动把它推迟到"第一次写"，还附送碎片化与空间延迟释放（见本系列 2.2 与 2.3.2）。
- **量之前先想清楚在量什么**：先本地拷镜像、只测创建、别把启动混进来，也别把网桥与 IP 的上限当成存储的瓶颈。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| CoW 粒度 | 写时复制以什么为单位发生：整个文件、一段 extent，还是一个块 |
| dir 驱动 | LXD 里最简单的存储驱动，普通目录 + 解包文件，没有共享机制，对应 Docker 的 vfs |
| 子卷（subvolume） | btrfs 里可以独立做快照的目录单元；快照只复制元数据 |
| dataset / clone | zfs 里可独立快照的数据集，克隆同样只改元数据、共享数据块 |
| thin pool | 块级精简供给池，按需分配块；lvm 与 devicemapper 都靠它做块级 CoW |
