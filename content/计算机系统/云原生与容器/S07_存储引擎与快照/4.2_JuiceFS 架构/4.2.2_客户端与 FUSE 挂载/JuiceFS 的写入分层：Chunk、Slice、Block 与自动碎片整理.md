# JuiceFS 的写入分层：Chunk、Slice、Block 与自动碎片整理

> 视频来源：[JuiceFS 是怎么处理文件写入的？Chunk / Slice / Block 三层拆分一次看懂](https://www.bilibili.com/video/BV1hP596gEs2/)（Bilibili · JuiceFS 官方）｜时长约 2 分钟
> 导读：这支短片只用一张不断演化的示意图，把 JuiceFS 写入路径上最反直觉的一点讲透了——**改文件不是改数据，而是新增一条记录**。它讲的是客户端 `write()` 之后、对象存储 PUT 之前的那段「记账」逻辑：文件怎么切成 chunk，一次写入怎么变成 slice，slice 怎么变成 4 兆的 block，以及反复改写同一区域后为什么要靠后台 compact 收拾残局。本篇是 4.2.2 的写入侧补充，客户端整体分层与挂载参数见同目录另一篇。

## 本讲要解决的核心问题（SCQA）

**背景**：对象存储是**不可变**的——一个对象写进去之后不能原地改，想改只能重新上传整个对象。JuiceFS 用对象存储存文件数据，就必须绕开这个限制。

**冲突**：如果按「一个文件对应一个对象」来存，那么往一个 100 GB 的文件末尾追加几百 KB，也要重新上传 100 GB。这显然不可接受。

**疑问**：既然不能原地改，那「修改文件中间的一段」这件事，在对象存储上到底怎么表达？

**回答（中心思想）**：JuiceFS 把「改」翻译成「追加一条新记录」。文件先按 64 兆切成 **chunk**，每次写入产生一个 **slice**（携带数据 + 它在文件中的位置，不改已有数据），slice 再切成 4 兆的 **block** 上传到对象存储。于是「修改」= 新增一个覆盖该区间的 slice，旧 slice 原封不动；读的时候由元数据引擎把所有 slice 叠起来算出该读哪一块。代价是同一区域改多了会产生层叠的碎片，需要后台 **compact** 合并。

## 一、三层结构：chunk 定位置，slice 记写入，block 存数据

当你向 JuiceFS 写入一个文件，它并不是简单地存成一整块。首先按照 64 兆字节的边界把文件切分成若干个 chunk [【跳转到 00:00】](https://www.bilibili.com/video/BV1hP596gEs2/?t=0)。

一个 100 兆的文件自然就被划分为两个 chunk：chunk 0 负责前 64 兆，chunk 1 负责剩下的部分。

![文件按 64 兆切成 chunk 0 与 chunk 1；chunk 0 里第一条 slice 0 覆盖全部 64 兆，chunk 1 里 slice 1 覆盖从头开始的 36 兆](assets/JuiceFS%20的写入分层：Chunk、Slice、Block%20与自动碎片整理/00038.webp)

三层各自的职责可以这样记：

| 层 | 大小 | 职责 | 类比 |
| :--- | :--- | :--- | :--- |
| chunk | 固定 64 MiB | 文件的逻辑分区，用来快速定位要访问的那部分数据 | 书的「章」 |
| slice | 不定，取决于一次写入的长度 | 一次连续写入的记录，携带数据 + 它在文件中的位置 | 章的「修订页」 |
| block | 固定 4 MiB | 真正存在对象存储里的数据单元，可独立上传/读取、可并行 | 修订页的「张」 |

写入开始了，**每写一次都会产生一个新的 slice** [【跳转到 00:00】](https://www.bilibili.com/video/BV1hP596gEs2/?t=0)。chunk 0 中产生的第一条记录叫 slice 0，它覆盖了这个 chunk 的全部 64 兆字节；chunk 1 中也写入了 slice 1，覆盖了从头开始的 36 兆。

这里已经能看出关键设计：**slice 记录的是「哪一段区间被这一次写入覆盖了」，而不是「这个文件现在长什么样」**。所以写入永远是增量的，不需要改动已有的数据。

## 二、改写与追加：都是新增一条 slice

接下来有人修改了文件中间的一段内容，这次改写落在 chunk 0 的 20 到 46 兆区间，产生了一条新的记录 slice 2 [【跳转到 00:18】](https://www.bilibili.com/video/BV1hP596gEs2/?t=18)。

注意发生了什么：slice 0 依然完整地覆盖 0 到 64 兆，slice 2 只是**叠在它上面**，声明「20 到 46 兆这一段以我为准」。旧数据一个字节都没动，也没有被删除。

然后有人在文件末尾追加了 16 兆的内容，chunk 1 中出现了 slice 3，紧接在 slice 1 之后 [【跳转到 00:38】](https://www.bilibili.com/video/BV1hP596gEs2/?t=38)。

![追加 16 兆后文件变成 116 兆：chunk 1 里 slice 3 紧接在 slice 1 之后，覆盖 100 到 116 兆](assets/JuiceFS%20的写入分层：Chunk、Slice、Block%20与自动碎片整理/00058.webp)

追加之所以便宜，也是同一个原因：它只是在 chunk 1 的末尾多了一条记录，不需要动 slice 1。

这些 slice 最终会被切成每块 4 兆字节的 block，写入底层的对象存储 [【跳转到 00:38】](https://www.bilibili.com/video/BV1hP596gEs2/?t=38)。切成 4 兆的意义在于：block 能独立上传或读取，多个 block 可以同时并行操作，从而充分利用网络带宽。

## 三、反复改写同一区域：slice 会层叠

现在把镜头聚焦在 chunk 0 上，看看如果反复修改同一区域会发生什么。

第三次改写，新的 slice 4 覆盖了 15 到 50 兆的区间；第四次改写 slice 5 再次覆盖了 0 到 35 兆。此刻 chunk 0 里已经积累了四条 slice 记录，彼此层叠、相互覆盖 [【跳转到 00:58】](https://www.bilibili.com/video/BV1hP596gEs2/?t=58)。

![chunk 0 里叠了四条 slice：slice 0（0-64 兆）、slice 2（20-46 兆）、slice 4（15-50 兆）、slice 5（0-35 兆），后写的覆盖先写的](assets/JuiceFS%20的写入分层：Chunk、Slice、Block%20与自动碎片整理/00087.webp)

这就是「不可变对象存储」换来的代价：**每一次改写都留下一条记录，谁最后写谁说了算**。四条记录叠在一起，逻辑上只有最上面那层是有效的，下面三层大部分区间都是被覆盖的死数据。

## 四、读的时候：元数据引擎负责「叠图」

假设现在要读取这个文件的前 40 兆字节。元数据引擎需要读取 chunk 0 中的所有 slice，从而计算、找到相应的数据块 [【跳转到 01:15】](https://www.bilibili.com/video/BV1hP596gEs2/?t=75)。

这一步是整条路径上最容易被忽略的：**读一个区间，不是查一次就完事，而是要把这个 chunk 里所有 slice 都取出来做一次「叠图计算」**，才能知道 0 到 40 兆这段区间里，每一小段最终该用哪一条 slice 的数据。

经过计算，我们成功定位到了目标数据块所在的 slice [【跳转到 01:19】](https://www.bilibili.com/video/BV1hP596gEs2/?t=79)，然后在对象存储中把目标数据块读取出来 [【跳转到 01:27】](https://www.bilibili.com/video/BV1hP596gEs2/?t=87)。

所以读路径是：**先问元数据引擎（可能要取多条 slice 记录）→ 算出该读哪些 block → 再去对象存储取 block**。slice 层数越多，第一步的计算量和元数据量就越大——这就是碎片需要被收拾的原因。

## 五、compact：把四条 slice 合并成一条

chunk 0 里这几条层叠的 slice 正是碎片，JuiceFS 会在后台自动触发 compact [【跳转到 01:32】](https://www.bilibili.com/video/BV1hP596gEs2/?t=92)。

![compact 进行中：chunk 0 里四条层叠的 slice 被重新读出来、按最终有效内容合并](assets/JuiceFS%20的写入分层：Chunk、Slice、Block%20与自动碎片整理/00101.webp)

它将这些碎片整理合并，四条 slice 记录消失 [【跳转到 01:37】](https://www.bilibili.com/video/BV1hP596gEs2/?t=97)，取而代之的是一条全新的 slice 6，干净地覆盖了整个 chunk 0 的 64 兆字节 [【跳转到 01:41】](https://www.bilibili.com/video/BV1hP596gEs2/?t=101)。

![compact 之后：chunk 0 只剩一条 slice 6，覆盖整个 64 兆；chunk 1 仍是 slice 1 与 slice 3](assets/JuiceFS%20的写入分层：Chunk、Slice、Block%20与自动碎片整理/00110.webp)

此后同样的 40 兆读取请求，只需访问一个 slice 对象，一次完成。这就是 JuiceFS 自动碎片整理的意义 [【跳转到 01:46】](https://www.bilibili.com/video/BV1hP596gEs2/?t=106)。

compact 的收益非常直接：**读放大变小、元数据量变小、读路径从「取四条记录再算」变成「取一条记录直接读」**。而且它是后台任务，发生在客户端进程里，不需要用户干预。

## 小结

- **三层结构各司其职**：chunk（64 MiB）负责定位，slice 记录一次写入覆盖的区间，block（4 MiB）是对象存储里的实际数据单元。
- **写入永远是增量的**：每写一次产生一个新 slice，不改已有 slice、不改已有 block。这让「修改对象存储里的文件」变成「追加一条记录」。
- **覆盖由顺序决定**：同一区间被多次改写时，slice 会层叠，后写的覆盖先写的；旧 slice 仍然完整存在，只是逻辑上失效。
- **读要先算再取**：读一个区间时，元数据引擎要把该 chunk 里所有 slice 取出来做叠图计算，定位到具体 block，再去对象存储读。
- **碎片必须收拾**：层叠的 slice 会让读路径变长、元数据变多，后台 compact 把它们合并成一条覆盖整个 chunk 的新 slice，此后同样的读只需访问一个 slice 对象。
- 这条链路上，「切 chunk / 记 slice / 切 block」都在客户端完成，「存 block」才落到对象存储；因此碎片合并也发生在客户端进程里，属于客户端的后台任务。

## 关键术语速查

| 术语 | 一句话解释 |
| :--- | :--- |
| chunk | 文件的逻辑分区，固定 64 MiB，用来快速定位要访问的那部分数据 |
| slice | 一次连续写入产生的记录，携带数据和它在文件中的位置；写入是增量的 |
| block | 真正存储在对象存储里的数据单元，默认 4 MiB，可独立上传/读取、可并行 |
| 层叠（overlap） | 同一区间被多次改写后，多条 slice 相互覆盖，后写的生效 |
| compact | 后台碎片合并：把层叠的多条 slice 合并成一条覆盖整个 chunk 的新 slice |
| 读放大 | 实际读取的数据量大于应用请求的量；slice 层数多、prefetch 过大都会造成 |
