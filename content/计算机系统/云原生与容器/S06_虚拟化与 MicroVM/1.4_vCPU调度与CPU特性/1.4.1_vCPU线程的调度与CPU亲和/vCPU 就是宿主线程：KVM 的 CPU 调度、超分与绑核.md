# vCPU 就是宿主线程：KVM 的 CPU 调度、超分与绑核

> 视频来源：[Why Your VM Is Slow: KVM CPU & Memory Tuning | KVM & DC Networking #12](https://www.youtube.com/watch?v=9YkTaH0iu5g)（YouTube · XOR）｜时长约 9 分钟
> 导读：这是「KVM 与数据中心网络」系列第 12 集，讲性能调优的上半场——CPU 与内存。它把「vCPU 只是一个宿主线程」这一句话，一步步推到超分、steal time、绑核、拓扑、NUMA 这些具体旋钮上，正好覆盖本小节要讨论的全部要点。文中命令与数字均来自视频引用的 RHEL 9 文档与内核文档，字幕中的英文术语已按原意保留。

## 本讲要解决的核心问题（SCQA）

**背景**：一台虚拟机在客户机里看起来和物理机没区别：有自己的内核、自己的 CPU 编号、自己的 `top`。但它底下跑的还是宿主 Linux。

**冲突**：既然 vCPU 只是宿主上的一个线程，那么宿主调度器随时可以把它换下去。客户机却完全看不见这件事——它以为自己一直在跑，实际上时间被偷走了。于是「虚拟机为什么慢」这个问题，答案常常不在客户机的代码里，而在宿主的调度器里。

**疑问**：vCPU 作为普通线程被 CFS 调度，具体会带来哪些后果？超分能超到什么程度？绑核（亲和）到底解决什么问题、又会牺牲什么？

**回答（中心思想）**：vCPU 是宿主上的普通线程，所以宿主的 CFS 对它有完全的调度权；由此派生出三件事——可以超分（但收益有上限）、会出现 steal time（客户机唯一能观测到的被抢占证据）、可以用绑核与 NUMA 亲和把调度权部分收回来（代价是失去负载均衡的自由）。理解这三件事的取舍，比记住任何单个参数都重要。

## 一、vCPU 只是宿主上的一个线程

### 1.1 一句话定义的三个推论

视频在讲性能之前先回到第一集的结论：**每一个 vCPU 就是宿主上的一个线程，由 Linux 像调度其它线程一样调度它**。[【跳转到 00:35】](https://www.youtube.com/watch?v=9YkTaH0iu5g&t=35)

这句话不是修辞，它直接推出三个可操作的结论：

1. **vCPU 数可以大于物理核数**。因为线程数本来就可以多于核数，宿主调度器会分时复用。这就是超分（overcommit）。
2. **vCPU 会被抢占**。宿主上任何一个普通进程（包括另一个 VM 的 vCPU、包括宿主自己的 `systemd`）都可能把某个 vCPU 挤下 CPU。
3. **客户机对这件事没有控制权**。客户机里的调度器只看得见自己的 vCPU，它不知道宿主上有谁在抢。

下图是这一集的骨架画面：宿主的 8 个 CPU 上，`web1`、`db1`、`app1` 三台虚拟机的 vCPU 线程交错铺开——每一格都是一个独立线程，谁上谁下由宿主决定。

![宿主 CPU 上交错排布的多个虚拟机 vCPU 线程，说明 vCPU 就是可被任意安置的普通线程](assets/vCPU%20就是宿主线程：KVM%20的%20CPU%20调度、超分与绑核/00060.webp)

### 1.2 超分：能超，但要算清收益边界

既然 vCPU 是线程，把 8 核的宿主切出 40 个 vCPU 在技术上完全可行。视频引用了 Red Hat 的建议，给出了两条很具体的经验线 [【跳转到 01:00】](https://www.youtube.com/watch?v=9YkTaH0iu5g&t=60)：

- **生产环境没有充分测试就不要超分**；
- 如果要超分，在负载不超过 100% 的前提下，**每物理 CPU 约 5 个 vCPU 通常是安全的**，Red Hat **不建议超过 10 个**。

更重要的是一条反向建议：**给每台 VM 它工作负载需要的最少 vCPU**。因为当所有 vCPU 都在抢同一批核时，更多的 vCPU 不会更快——这是超分最容易被忽视的一面：vCPU 数量本身不产生算力，它只产生排队。

![给每台虚拟机最少的 vCPU，而不是更多 vCPU 更快](assets/vCPU%20就是宿主线程：KVM%20的%20CPU%20调度、超分与绑核/00085.webp)

为什么「多给几个 vCPU」经常反而更慢？可以这样理解：假设一台 VM 有 $n$ 个 vCPU，宿主上可用的物理核只有 $m$ 个且 $n > m$，那么任一时刻平均只有 $m/n$ 比例的 vCPU 在真正执行。客户机内部那些需要「所有 CPU 一起到达某个点」的操作（自旋锁、屏障、并行任务同步）会被这个比例直接放大——等待时间不再由客户机的算法决定，而由宿主的调度决定。

### 1.3 steal time：客户机唯一能看到的证据

客户机怎么知道自己被抢了？答案是一个专门的指标：**steal time（被偷走的时间）**。[【跳转到 01:25】](https://www.youtube.com/watch?v=9YkTaH0iu5g&t=85)

KVM 会告诉客户机：**每个 vCPU 想要运行、但没能运行的时间有多长**——因为宿主把 CPU 给了别的东西。在客户机里，`top` 把它显示为 `st` 这一列。

这个指标有两个关键性质：

- **空闲时间不计入 steal**。所以 `st` 高说明的是「我本来想干活，但没轮到我」，指向的是宿主上的争抢，而不是客户机应用自己的问题。
- **steal 是客户机唯一能观测到宿主争抢的窗口**。客户机看不到宿主进程列表，只能通过 KVM 喂给它的这个计数器反推。

从客户机内部看，被抢占的那段时间「时间就停住了」：墙上时钟在走，但 vCPU 一条指令都没执行。这就是为什么在超分的环境里，客户机内的计时、超时判断、心跳都可能出现跳变——它们依赖的是墙上时间，而 vCPU 实际获得的时间更少。

## 二、绑核：把调度权部分收回来

### 2.1 默认不绑，绑了会怎样

默认情况下，一台 VM 的所有线程**可以跑在任意宿主 CPU 上**。绑核（pinning / CPU 亲和）则是把每个 vCPU 钉到你指定的那颗物理 CPU 上，视频引述 Red Hat 的说法：这**可以显著提升性能**。[【跳转到 01:50】](https://www.youtube.com/watch?v=9YkTaH0iu5g&t=110)

但别只盯着 vCPU。QEMU 进程里还有别的线程：

- **emulator 线程**（主循环，负责设备模拟与 VM exit 处理）；
- **I/O 线程**（块设备、网络后端）。

libvirt 允许把这些线程也绑到**另外的** CPU 上，避免它们和 vCPU 抢同一颗核。

要做到最低延迟，还要把**宿主自己的工作**从这些核上赶走。视频给了三条路径 [【跳转到 02:12】](https://www.youtube.com/watch?v=9YkTaH0iu5g&t=132)：

1. 启动参数 `isolcpus`：开机时就把这些 CPU 从通用调度里摘出去；
2. **cgroup cpuset 分区**：用 cgroup v2 的 cpuset 把 CPU 划成一个专用分区；
3. 限制 `systemd` 启动宿主服务的位置（`systemd-system.conf` 里的 CPU 亲和设置），让宿主守护进程不去踩这些核。

libvirt 的「实时（real-time）配方」做的正是这件事：**每个 vCPU 独占一颗隔离出来的物理 CPU，emulator 线程被挡在外面**。下图是这个模型的示意——下面一排是物理 CPU，上面是若干 vCPU，`systemd` 与其它 daemons 被安排到了别处。

![绑核模型：vCPU 各自钉在物理 CPU 上，systemd 与宿主守护进程被挡在这些核之外](assets/vCPU%20就是宿主线程：KVM%20的%20CPU%20调度、超分与绑核/00132.webp)

### 2.2 「把所有东西都绑上」是误区

视频明确点出了这个误区（myth）：**pin everything**。事实是 [【跳转到 02:37】](https://www.youtube.com/watch?v=9YkTaH0iu5g&t=157)：

- 绑核**拿走了调度器平衡负载的自由**。核被钉死之后，某个 vCPU 忙、另一个核闲着，宿主也没法把它们挪到一起。
- 像 OpenStack 这样的平台，对于**被 dedicate（专属分配）出去的 CPU，会拒绝再做超分**。也就是说绑核与超分在资源模型上是互斥的：你一旦承诺「这颗核是你的」，就不能再把它卖第二次。

所以结论是：**给需要它的工作负载绑核，其余让它漂着**。延迟敏感型（NFV、实时业务、数据库主库）值得绑；批处理、开发测试环境绑了只是浪费密度。

## 三、你告诉客户机的拓扑必须是真的

### 3.1 sockets / cores / threads 不是装饰

创建 VM 时你可以选择客户机看到的 CPU 布局：几个 socket、每 socket 几个 core、每 core 几个线程（超线程）。视频强调**这不是装饰性的**：客户机的调度器会把同一个 core 的两个线程当作**共享硬件的 siblings** 来对待。[【跳转到 02:37】](https://www.youtube.com/watch?v=9YkTaH0iu5g&t=157)

![客户机视角的拓扑：core 0 上的 vCPU 0 与 vCPU 1 被视为共享硬件的兄弟线程](assets/vCPU%20就是宿主线程：KVM%20的%20CPU%20调度、超分与绑核/00182.webp)

这带来一条硬约束：**如果你告诉客户机它有超线程，就必须把这些成对的 vCPU 绑到宿主上真正互为 sibling 的线程上**。[【跳转到 03:02】](https://www.youtube.com/watch?v=9YkTaH0iu5g&t=182) 否则客户机基于「我们共享 L1/L2」做出的调度决策（比如把两个协作紧密的线程放到同一 core 的两个线程上，或者反过来避开）就全错了——它拿到的是一份假情报。

### 3.2 超线程还有安全含义

同一个地方，视频补了一句安全提醒：Intel 的 **L1TF**（L1 Terminal Fault）漏洞允许一个 hyperthread 上的客户机**读到它 sibling 上的数据**——那个 sibling 可能是另一台 VM，也可能是宿主自己。

这句话的含义是：超线程在**隔离边界**上是有代价的。对多租户环境，把不受信任的租户放在同一物理 core 的两个线程上，等于让它们共享 L1 数据缓存这条侧信道。

## 四、NUMA 亲和：vCPU 和它的内存要在同一个节点

大服务器上，内存属于某个 **NUMA 节点**（通常就是一个 socket）。访问另一个节点的内存要跨过更慢的互联链路。[【跳转到 06:15】](https://www.youtube.com/watch?v=9YkTaH0iu5g&t=375)

所以原则很直接：**把一台 VM 的 vCPU 和它的内存放在同一个 NUMA 节点上**。libvirt 里对应的旋钮是 `numatune`，默认模式 `strict` 会把内存**限制在你指定的节点上**。

如果一台 VM 大到装不进一个节点呢？视频的答案是：**给它一套自己的虚拟 NUMA 布局，镜像宿主的拓扑**，这样客户机内部也能做出和宿主一致的「就近访问」选择。[【跳转到 06:40】](https://www.youtube.com/watch?v=9YkTaH0iu5g&t=400)

另外一个判断值得记住：Red Hat 认为**手工 NUMA 调优比自动工具更可能带来显著改善**。手工调之前先看现状——`numastat -c qemu-kvm` 能显示每台 VM 的内存实际落在哪些节点上。

![手工 numatune 加绑核比自动的 numad 与 numa_balancing 更可能带来显著收益；numastat 用来查看内存真实落点](assets/vCPU%20就是宿主线程：KVM%20的%20CPU%20调度、超分与绑核/00425.webp)

### 4.1 大页与 TLB：为什么它和调度有关

视频开头先讲了一件看似无关的事：在裸机上，一次 TLB miss 走四级页表要读四次；而在 VM 里，**客户机读的每一级页表、以及最终地址本身，都还要再翻译一次**。AMD 的研究者在 2008 年数过：**一个地址最多二十四次页表读取，是裸机的六倍**。[【跳转到 00:00】](https://www.youtube.com/watch?v=9YkTaH0iu5g&t=0)

大页之所以有效，是因为**每个 TLB 表项只映射一个页**：4 KiB 页时 TLB 覆盖的内存很少，换成 2 MiB 或 1 GiB 页后，每个表项覆盖的范围大得多，每次遍历也更短。[【跳转到 05:07】](https://www.youtube.com/watch?v=9YkTaH0iu5g&t=307) 内核文档说得很直白：**大页让 TLB miss 更快，在虚拟化场景下尤其如此**；宿主与客户机两侧都开最好，只开一侧也有帮助。AMD 2008 年的模拟器研究里，在页表遍历缓存已经改进之后，hypervisor 侧使用大页还能再带来 **3% 到 22%** 的提升。

大页有两种 [【跳转到 05:57】](https://www.youtube.com/watch?v=9YkTaH0iu5g&t=357)：

| 类型 | 分配方式 | 是否可换出 | 可靠性 |
| --- | --- | --- | --- |
| 静态大页（hugetlbfs） | 开机时用 `hugepages=` 预留，最好在内存碎片化之前 | 永不换出 | 高，VM 在 memoryBacking 里显式申请 |
| 透明大页（THP） | 内核自动合并 | 可换出 | 无需预留，但也没有保证 |

![静态大页与透明大页的对比：前者开机预留、永不换出，后者自动但无保证](assets/vCPU%20就是宿主线程：KVM%20的%20CPU%20调度、超分与绑核/00375.webp)

Red Hat 的建议是：大页对**内存密集型 VM**（比如数据库服务器）有帮助，对**非常大的 VM** 推荐使用。

## 五、先测量，再调优

视频反复强调的顺序是**测量优先**。[【跳转到 07:05】](https://www.youtube.com/watch?v=9YkTaH0iu5g&t=425)

- `perf kvm stat` 按原因统计 VM exit。Red Hat 特别指出：**大量 pause 指令退出，意味着宿主跟不上这台 VM 的 vCPU 了**——这是一个非常直接的「宿主调度不足」信号。
- `tuned` 有现成 profile：宿主上用 `virtual-host`，客户机里用 `virtual-guest`。
- 还有一个用功耗换延迟的旋钮：**halt polling**。当 vCPU 空闲时，KVM 会短暂自旋等待，等待时间按 vCPU 自适应，x86 上默认上限 **200 微秒**。把这个上限调得太大，一台空闲的宿主也能烧掉一整个 CPU。

![tuned 的两套现成 profile：宿主用 virtual-host，客户机用 virtual-guest](assets/vCPU%20就是宿主线程：KVM%20的%20CPU%20调度、超分与绑核/00450.webp)

所以，一台「慢」的 VM，问题可能出在**调度**或**内存**上，而不是代码上。[【跳转到 07:30】](https://www.youtube.com/watch?v=9YkTaH0iu5g&t=450)

## 小结

视频最后的收尾清单，本身就是一份可执行的调优顺序 [【跳转到 07:55】](https://www.youtube.com/watch?v=9YkTaH0iu5g&t=475)：

- **给能工作的最少 vCPU，并盯住 steal time**。vCPU 数量不是性能，`st` 才是宿主争抢的体温计。
- **给延迟敏感的那几台绑核，连它们的 QEMU 线程一起绑**。绑核是「用密度换确定性」，不是默认选项。
- **超分内存要谨慎**；KSM 不要用在互不信任的邻居之间（它有侧信道问题：2011 年有人通过合并页的写延迟判断另一台 VM 在跑什么程序；2016 年的 Flip Feng Shui 把 KSM 和 Rowhammer 组合起来改写了邻居的内存位）。
- **大 VM 给大页**，宿主与客户机两侧都开最好。
- **把每台 VM 的处理器和内存放在同一个 NUMA 节点上**，手工 `numatune` 加绑核通常比自动工具更有效。
- 如果只记一件事：**每个 vCPU 都是宿主线程，每次 TLB miss 都要走两套页表**。两边都要调，而且调之前调之后都要测。

把这条主线接回本小节的其它内容：既然 vCPU 只是线程，那么「客户机内时间跳变」「锁持有者被抢占导致整台 VM 卡住」这些现象，本质上都是宿主 CFS 在 vCPU 之间做时间片切分的结果；而绑核、cpuset、NUMA 亲和，就是把这个切分的粒度从「毫秒级随机」收紧到「可预测」的手段。

| 术语 | 一句话解释 |

| vCPU | 客户机眼中的一个处理器，在宿主上就是一个普通线程 |
| 超分（overcommit） | 分配的 vCPU 总数超过物理核数，靠宿主分时复用兑现 |
| steal time（`st`） | vCPU 想跑却没轮到的累计时间，由 KVM 报给客户机 |

| siblings | 同一物理 core 上的两个超线程，共享 L1/L2 等硬件 |
| L1TF | Intel 的 L1 终端故障漏洞，可跨超线程读到 sibling 的数据 |
