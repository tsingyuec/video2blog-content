# vCPU 被抢占的代价：双重调度与按需优先级提升

> 视频来源：[Dynamic vCPU priority boosting in KVM for latency sensitive workloads](https://www.youtube.com/watch?v=47YzSIWUXeI)（YouTube · Linux Plumbers Conference · Google ChromeOS 内核性能与虚拟化团队）
> 导读：这支演讲是「vCPU 被 CFS 抢占」这件事最直接的一份病例分析。ChromeOS 上跑 Android 应用，音频爆音、视频卡顿，根源被定位为**宿主与客户机两个调度器互相看不见对方**——作者称之为「双重调度」。他们的解法不是把 vCPU 一律提到实时优先级（那会把宿主搞坏），而是让客户机把「我现在在跑重要东西」这个意图告诉宿主，宿主按需提升、及时撤销。本文按问题—根因—方案—数据的顺序展开，并保留了他们实测的延迟数字。

## 本讲要解决的核心问题（SCQA）

**背景**：vCPU 在宿主上就是一个普通 CFS 任务。客户机内部有自己的调度器，宿主内部也有自己的调度器。

**冲突**：两个调度器**互相看不见对方**。宿主不知道这个 vCPU 正在跑什么，客户机不知道自己的 vCPU 被排到了哪颗核、前面还排着谁。结果在负载高的宿主上，客户机里的音频和视频出现爆音与卡顿——演讲里给出的量级是**几百毫秒的延迟**。

**疑问**：这个延迟该怎么治？把 vCPU 提到实时优先级行不行？如果不行，代价是什么？

**回答（中心思想）**：单纯提高 vCPU 的优先级只是把延迟从客户机搬到宿主，是零和博弈。真正的解法是**让两个调度器交换信息**——客户机把「我即将/正在运行延迟敏感上下文」的意图告诉宿主，宿主据此**按需**提升 vCPU 的优先级，并在客户机离开敏感上下文时**同步撤销**。实测在繁忙宿主上，客户机最大延迟从约 200 毫秒降到 70 毫秒以内，音频爆音从 1365 次降到 67 次。

## 一、问题：延迟敏感负载在超分宿主上被饿着

### 1.1 现象

ChromeOS 在低端设备上跑 Android 应用，而 Android 跑在一台 VM 里。宿主本身很忙（ChromeOS 是「a busy system on a low-end device」）。于是**音频出现 glitch、视频播放不流畅**。[【跳转到 01:25】](https://www.youtube.com/watch?v=47YzSIWUXeI&t=85)

演讲把问题写成两条：

- 客户机在宿主有负载时会经历**可观的延迟**（有时几百毫秒）；
- 原因是**物理 CPU 被超分**——多台 VM、宿主进程都在抢。

![问题陈述：宿主超分时客户机经历数百毫秒延迟，表现为音频爆音与视频卡顿](assets/vCPU%20被抢占的代价：双重调度与按需优先级提升/00085.webp)

### 1.2 用 trace 看见「runnable but preempted」

最有说服力的是那张 trace 截图 [【跳转到 02:40】](https://www.youtube.com/watch?v=47YzSIWUXeI&t=160)。图上每一行是一个实体：

- 第 2、3 行是 **vCPU 线程**（`crosvm_vcpu0`、`crosvm_vcpu1`）；
- 接下来两行是**物理 CPU**（CPU 0、CPU 1）；
- 再往下是**虚拟 CPU**（CPU 100、CPU 101）。

颜色编码是关键：**深绿 = vCPU 正在跑，浅绿 = runnable 但被抢占**。视频卡顿发生时，可以看到**相当长的一段时间都是浅绿**——vCPU 明明想跑，却一直排在运行队列里。

![trace 示例：vCPU 线程大量时间处于 runnable but preempted（浅绿），对应视频卡顿](assets/vCPU%20被抢占的代价：双重调度与按需优先级提升/00160.webp)

这就是本小节要讨论的核心现象：**vCPU 被抢占的直接后果，是客户机内的时间感知与实际执行脱节**。客户机里的音频线程按 2 毫秒周期被唤醒，但它所在的 vCPU 可能几十毫秒都没被调度上——从客户机看，就是「时间跳变」。

## 二、根因：双重调度（double scheduling）

### 2.1 两个调度器，两套盲区

演讲把根因命名为 **double scheduling** [【跳转到 01:50】](https://www.youtube.com/watch?v=47YzSIWUXeI&t=110)：

- **宿主调度 vCPU 线程**，但不知道 vCPU 里正在跑什么；
- **客户机调度内部任务**，但不知道自己的 vCPU 在物理上跑在哪、前面排着谁。

两个调度器各自都「公平」，合起来却不公平：宿主调度器**追求公平（fair）**，完全不知道客户机内部的优先级需求。[【跳转到 02:15】](https://www.youtube.com/watch?v=47YzSIWUXeI&t=135)

![根因：双重调度。宿主调度 vCPU 线程、客户机调度内部任务，两个调度器互不知情](assets/vCPU%20被抢占的代价：双重调度与按需优先级提升/00110.webp)

后果不止延迟：演讲列出的是**延迟、功耗、资源利用率**三类问题。这一点值得注意——被抢占不只是「慢」，还会让客户机做出错误决策（比如为了赶进度而提频、或者反复重试），从而浪费功耗。

### 2.2 第一反应：把 vCPU 提到实时优先级，为什么不行

最直接的想法是：既然是优先级不够，那就把 vCPU 提到 RT。[【跳转到 03:30】](https://www.youtube.com/watch?v=47YzSIWUXeI&t=210)

结果**问题反过来了**：宿主上也有延迟敏感的应用要跑，而 vCPU 现在带着一个普通任务却享有 RT 优先级，于是它**抢占了宿主**，延迟从客户机转移到了宿主。演讲的原话是「not ideal」。

这就是本小节要强调的取舍：**在超分环境下，优先级是一个零和资源**。你把确定性给了一方，就从另一方拿走。

## 三、方案：让客户机把「意图」告诉宿主

### 3.1 从「调优先级」转向「合作调度」

演讲的转折点是：问题的本质不是优先级，而是**盲目的双重调度**。所以让宿主和客户机**交换信息**——共享调度参数、共享调度状态，双方就能做出「有依据的决策」。[【跳转到 04:20】](https://www.youtube.com/watch?v=47YzSIWUXeI&t=260)

他们把这个方向叫 **cooperative guest-host scheduling**（客户机与宿主协同调度），而本讲的实现只是它的一个特例：**只需要把客户机的优先级需求传给宿主**——客户机说「我要跑重要东西，请让我跑」，宿主据此行动。[【跳转到 05:10】](https://www.youtube.com/watch?v=47YzSIWUXeI&t=310)

完整的机制有四条 [【跳转到 06:00】](https://www.youtube.com/watch?v=47YzSIWUXeI&t=360)：

1. **宿主主动提升**：当宿主**知道**这个 vCPU 即将运行延迟敏感的工作（例如注入中断）时，主动提升它；
2. **客户机请求提升**：宿主不知道时，客户机通过 hypercall 表达意图，宿主据此提升；
3. **客户机请求撤销**：不再运行敏感负载时撤销；
4. **安全兜底**：宿主必须实现**限流（throttling）与强制撤销**，以防客户机内核有 bug 或是恶意内核。

![动态 vCPU 优先级管理：宿主主动提升、客户机请求提升与撤销、宿主侧限流与强制撤销](assets/vCPU%20被抢占的代价：双重调度与按需优先级提升/00360.webp)

### 3.2 什么算「延迟敏感的客户机上下文」

这是整个方案的定义核心 [【跳转到 06:25】](https://www.youtube.com/watch?v=47YzSIWUXeI&t=385)：

- **NMI、中断、softirq**——需要尽快处理；
- **优先级高于 `SCHED_OTHER` 的任务**——即 `SCHED_RT` 及以上；
- **客户机里关闭了抢占的时刻**。

![延迟敏感的客户机上下文：NMI、中断与 softirq，优先级高于 SCHED_OTHER 的任务，以及客户机关闭抢占的时刻](assets/vCPU%20被抢占的代价：双重调度与按需优先级提升/00385.webp)

### 3.3 顺带解决锁持有者被抢占（lock holder preemption）

第三条「关闭抢占」正是本小节要讲的 **lock holder preemption** 问题的钥匙。演讲专门讨论了它 [【跳转到 06:50】](https://www.youtube.com/watch?v=47YzSIWUXeI&t=410)：

> 动态提升之后，有些 vCPU 是提升状态、有些没有。如果**一个未提升的 vCPU 拿到了自旋锁然后被抢占**，而一个**已提升的 vCPU 阻塞在这把锁上**，就出问题了。

这就是经典的锁持有者被抢占：锁的持有者被换下 CPU，等锁的人（哪怕优先级更高）只能干等。演讲称其为**有界的优先级反转**（bounded priority inversion）。

他们的解法不是专门为锁写代码，而是**把「抢占被禁用」本身定义为延迟敏感上下文**——而自旋锁天然会禁用抢占，所以这个问题**自动被覆盖**了。这是一个很漂亮的设计：用一个更一般的判据，顺带解决了一个特例。

## 四、实现：共享内存 + hypercall + 按需提升

### 4.1 信息通道

客户机分配一块结构体，通过 **MSR 写入它的 GPA（客户机物理地址）**告诉宿主这块内存在哪；宿主读这个 MSR 就知道位置。[【跳转到 08:05】](https://www.youtube.com/watch?v=47YzSIWUXeI&t=485)

默认的提升目标是 **`SCHED_RR`、优先级 8**（可调），撤销则回到 **`SCHED_OTHER`**。[【跳转到 08:30】](https://www.youtube.com/watch?v=47YzSIWUXeI&t=510)

![实现（POC）：客户机用 MSR 告知共享内存的 GPA，提升到 SCHED_RR 优先级 8，撤销回 SCHED_OTHER](assets/vCPU%20被抢占的代价：双重调度与按需优先级提升/00510.webp)

特性通过 **CPUID** 位向客户机通告，并且可以按 VM 单独开关。

### 4.2 提升走异步，撤销必须同步

这是实现上最关键的取舍 [【跳转到 10:10】](https://www.youtube.com/watch?v=47YzSIWUXeI&t=610)：

- **提升（boost）可以异步**：客户机只更新共享内存，宿主在**下一次 VM exit** 时才读它并决定是否提升。这样可以**省掉大量 hypercall**。
- **撤销（un-boost）必须同步**：一旦重要的工作跑完，就**不能**让不重要的任务继续以 RT 优先级运行，所以必须立刻通过 hypercall 通知宿主。

撤销的判定条件很具体 [【跳转到 11:00】](https://www.youtube.com/watch?v=47YzSIWUXeI&t=660)：当客户机调度器要从 RT 切到 `SCHED_OTHER` 时，从调度器里发 hypercall；中断退出路径上，如果**没有待处理的 softirq、中断发生在抢占使能区、且没有打断任何 RT 任务**，也请求撤销。

### 4.3 hypercall 的开销够不够低

团队一开始的担心是 hypercall 开销。实测结论 [【跳转到 12:40】](https://www.youtube.com/watch?v=47YzSIWUXeI&t=760)：**在今天的主流硬件上 hypercall 非常快**（除非开了嵌套虚拟化）。而他们要对抗的延迟是几十到几百毫秒，**10~20 微秒的 hypercall 开销完全可以接受**。

### 4.4 主动提升的两个场景

除了客户机请求，宿主还有两种「未卜先知」的提升时机 [【跳转到 15:52】](https://www.youtube.com/watch?v=47YzSIWUXeI&t=952)：

1. **注入中断时**：模拟设备的虚拟中断，或 VFIO 直通设备的中断。vCPU 可能正在睡眠，宿主必须在**唤醒它之前**就把它提升——因为「让 vCPU 自己在 VM enter 路径上提升自己」是鸡生蛋问题：它进入时优先级还不高。
2. **vCPU halt 时**：客户机 vCPU 进入 halt（空闲）时**直接保持提升状态**。因为 vCPU 反正没在跑，等它被唤醒时必然是要去跑中断/中断处理，那时它已经是提升状态，**醒过来就不用再撤销**。演讲者称这是「一个非常聪明的想法」。

### 4.5 共享内存里的三个字段

结构体只有三个字段 [【跳转到 24:12】](https://www.youtube.com/watch?v=47YzSIWUXeI&t=1452)：

| 字段 | 谁写 | 谁读 |
| --- | --- | --- |
| boost request（提升请求） | 客户机 | 宿主 |
| preemption disabled（抢占是否禁用） | 客户机 | 宿主 |
| boost status（当前是否已被提升） | 宿主 | 客户机 |

方向分开是有意义的：**客户机写意图，宿主写事实**。客户机读 `boost status` 就知道「宿主有没有真的提升我」，从而避免重复请求或无谓的撤销 hypercall。

## 五、数据：按需提升在客户机上接近 RT，在宿主上不伤性能

测试环境是一台**低端设备 Intel N4020，双核、无超线程**。合成负载用 **cyclictest**（以 RT 优先级同时跑在客户机和宿主上），真实负载用 **OboeTester** 统计音频爆音次数。[【跳转到 25:27】](https://www.youtube.com/watch?v=47YzSIWUXeI&t=1527)

三个对照：

- **vanilla**：宿主 6.1、客户机 5.10，无补丁；
- **vcpu_boost**：宿主与客户机都打上补丁；
- **static_rt**：vanilla + 用 `chrt` 把 vCPU 线程静态设为 RT——这是「理想但有害」的对照组。

## 六、被质疑的地方，以及他们的回答

### 6.1 「为什么不干脆给客户机一组高优先级 vCPU」

有听众提出：与其动态提升，不如给客户机两组 vCPU——一组高优先级、一组低优先级，让客户机自己把实时工作放到高优先级那组上。

回答是三条 [【跳转到 17:57】](https://www.youtube.com/watch?v=47YzSIWUXeI&t=1077)：

1. **需要客户机配合配置**，而他们的目标是「同一个内核丢进去就能用」（他们说这是一种 paravirtual scheduling）；
2. 客户机还得知道哪些应用是重要的，并且**把中断也分配到重要的 CPU 上**，配置面很大；
3. 最致命的：**RT vCPU 会抢占正在持锁的 CFS vCPU**——正是 3.3 节说的 lock holder preemption。而在他们的设计里，持锁的 vCPU 因为「抢占被禁用」已经自动被提升了，所以不会出现这种互踩。

### 6.2 安全性：恶意客户机可以一直要求提升

这是最尖锐的质疑 [【跳转到 20:02】](https://www.youtube.com/watch?v=47YzSIWUXeI&t=1202)：如果客户机一直要求 boost 却从不撤销，其它 VM 就被饿死了。

回答分两层：

- **机制上**：宿主有护栏——**定时器会在客户机没有及时撤销时强制收回提升**；同时宿主可以做限流。
- **策略上**：这取决于你对客户机的控制程度。ChromeOS 自己提供客户机内核，所以可以打开；**如果是公有云跑陌生租户的 VM，他们倾向于关掉**，除非有更好的安全模型。特性做成完全可配置、可调优，正是为此。

有听众补充说公有云其实也有需求（客户 VM 有时在意延迟、有时不在意），但前提是**必须有一条清晰的安全路径**。

### 6.3 用 nice 值提升行不行

有人问能不能用 nice / latency nice 代替 RT。回答是：**CFS 不是严格的优先级调度**。[【跳转到 42:07】](https://www.youtube.com/watch?v=47YzSIWUXeI&t=2527)

用 nice 值提升的 vCPU 会拿到更多 vruntime，但**一旦它把 runtime 用完，即使来了中断也没法让它立刻跑**。只有严格的优先级调度才能做到「中断来了必须马上跑」。所以他们的结论是：**两种都可以，取决于用例**，并且计划把「提升到 CFS 还是 RT、提升到哪个优先级」都做成可调项。

## 七、更大的图景：协同调度还能做什么

演讲最后把话题拉回一般情形 [【跳转到 31:42】](https://www.youtube.com/watch?v=47YzSIWUXeI&t=1902)。提升优先级只是一个特例，**协同调度**可以双向扩展：

- **宿主 → 客户机**：宿主把物理 CPU 的负载、压力、放置信息告诉客户机，客户机据此决定「在哪跑什么」。他们真实的痛点是：trace 里经常出现「这个 vCPU 在那种情况下根本不该被选中」的情况，因为客户机不知道宿主上发生了什么。
- **客户机 → 宿主**：客户机把自己的工作负载信息告诉宿主，宿主据此决定 vCPU 的物理放置。

一个具体的设想是：CFS 本来就会把 RT 运行、IRQ 等**压力信号**纳入计算，那为什么不给「宿主侧的压力」也加一个信号？现场有人指出这与「steal time / CPU capacity」机制有重叠——客户机里已经在跟踪被其它 VM 偷走的时间与可用容量，应该复用而不是另造一套。

另一个真实用例是 **RCU**：Android 里 RCU 的优先级提升依赖 RCU kthread 被设为 RT，但宿主不知道客户机在做这些事，于是客户机里出现 **RCU stall**。[【跳转到 36:17】](https://www.youtube.com/watch?v=47YzSIWUXeI&t=2177) 现场还有人提到，早年有学术工作专门处理「vCPU 在 RCU 读临界区中间被抢占导致 stall」的问题，做法是让 RCU grace period 机制向 hypervisor 发提示——与这里的思路同源，只是他们的方案更一般。

## 小结

- **根因是双重调度，不是优先级不够**。宿主调度 vCPU 线程、客户机调度内部任务，两个调度器互相看不见，各自公平、合起来不公平。
- **把 vCPU 一律提到 RT 是零和博弈**：客户机的延迟被搬到宿主。实测静态 RT 把宿主最坏延迟从 1.5 毫秒推到 16 毫秒（空闲）和 27 毫秒（繁忙）。
- **解法是交换意图**：客户机通过共享内存（MSR 传 GPA）声明「我在跑延迟敏感上下文」，宿主按需提升、客户机及时撤销。提升走异步（省 hypercall），撤销必须同步（防止不重要的工作继续以 RT 跑）。
- **延迟敏感上下文的定义**是 NMI/中断/softirq、优先级高于 `SCHED_OTHER` 的任务、以及**客户机禁用抢占的时刻**——最后一条顺带把 **lock holder preemption** 这个特例自动覆盖了。
- **收益**：繁忙宿主上客户机最大延迟从约 200 毫秒降到 70 毫秒以内（500 微秒间隔下 217 毫秒 → 14 毫秒），音频爆音从 1365 次降到 67 次，而宿主侧不受损。
- **代价与边界**：需要客户机配合（共享内存 + hypercall），需要宿主侧限流与强制撤销，公有云陌生租户场景要谨慎。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| double scheduling | 宿主调度 vCPU 线程、客户机调度内部任务，两个调度器互不知情 |
| runnable but preempted | vCPU 处于可运行状态但没拿到物理 CPU，trace 上表现为浅绿 |
| vCPU priority boost | 把 vCPU 线程从 CFS 提升到 SCHED_RR 优先级 8，可配置 |
| cooperative scheduling | 宿主与客户机交换调度信息，共同做出放置与优先级决策 |
| lock holder preemption | 持锁的 vCPU 被抢占，导致等锁者（含更高优先级者）阻塞 |
| bounded priority inversion | 因锁持有者被抢占而产生的、时间有上界的优先级反转 |
| halt boosting | vCPU 进入 halt 时保持提升状态，唤醒后无需再提升 |
| posted interrupt | 客户机直接处理中断、宿主不参与的中断投递方式 |
| OboeTester | Android 音频延迟测试工具，用于统计爆音（glitch）次数 |
| cyclictest | 实时延迟基准工具，报告平均与最大唤醒延迟 |
