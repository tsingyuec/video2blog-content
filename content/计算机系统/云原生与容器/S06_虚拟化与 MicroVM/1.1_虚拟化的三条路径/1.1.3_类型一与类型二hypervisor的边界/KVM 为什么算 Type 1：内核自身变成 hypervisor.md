# KVM 为什么算 Type 1：内核自身变成 hypervisor

> 视频来源：[KVM Explained | Linux Type-1 Hypervisor Architecture](https://www.youtube.com/watch?v=A3wFtfrCjxg)（YouTube · The Explainer）｜时长约 7 分钟
> 导读：这篇回答一个具体的归类问题——KVM 既没有独立安装介质，又和普通应用一样由用户态程序驱动，它凭什么被算作 Type 1（裸金属型）？本文沿着视频的讲解路径，从"hypervisor 的职责"讲到"KVM 站在内核里"，最后给出三条可复用的判断依据。姊妹篇《Type 1 与 Type 2 hypervisor：谁直接跑在硬件上》给出了两类 hypervisor 的完整对比。

## 本讲要解决的核心问题（SCQA）

**背景**：上一节我们得到了一条清晰的分界线——hypervisor 与物理硬件之间隔不隔着宿主操作系统。不隔是 Type 1（裸金属型），隔着是 Type 2（宿主型）。按这条线，ESXi 独占一台机器、装完没有桌面环境，是 Type 1；VirtualBox 双击安装、和浏览器并排运行，是 Type 2。

**冲突**：KVM 两边都不像。它没有独立的安装介质，你没法"装一个 KVM"；它也不是一个独立进程，你甚至无法在任务管理器里找到它。真正干活的用户态程序叫 QEMU，而 KVM 只是 Linux 内核里的一段代码——**Linux 既是你要用的操作系统，又是 hypervisor 本身**。那么它到底该算哪一类？

**疑问**：如果一台机器上"操作系统"和"hypervisor"是同一个东西，那条分界线还画得出来吗？

**回答（中心思想）**：KVM 算 Type 1。分界线问的不是"hypervisor 是不是一个独立产品"，而是"hypervisor 和硬件之间有没有隔着另一个操作系统"。KVM 的代码跑在**内核态**，直接使用 CPU 的虚拟化能力和内存管理，它和硬件之间没有第二层操作系统——Linux 内核自己就是那个直接管硬件的层。所以 KVM 是 Type 1 的**内核内嵌变体**：不是"hypervisor 跑在操作系统上"，而是"操作系统自己变成了 hypervisor"。

## 一、先把 hypervisor 的职责说清楚：它是硬件的调度员

在讨论归类之前，得先明确这个被归类的对象在干什么。

hypervisor 是让一台计算机同时跑多个操作系统的那个软件。视频给了一个很贴切的类比：它是**计算机硬件的空中交通管制员**，调度所有的 CPU 算力、内存等等，确保每个操作系统都拿到自己需要的东西，彼此不撞车。[【跳转到 00:37】](https://www.youtube.com/watch?v=A3wFtfrCjxg&t=37)

![hypervisor 的定义：创建并运行虚拟机，把硬件资源分配给每台虚拟机](assets/KVM%20为什么算%20Type%201：内核自身变成%20hypervisor/00058.webp)

这个职责可以拆成两半：

1. **虚拟化 CPU 和内存**——让每台虚拟机以为自己独占一颗 CPU、一段内存；
2. **隔离**——保证一台虚拟机里的操作不会影响另一台，也不会影响硬件本身。

记住这两半，因为后面判断 KVM 属于哪一类时，关键就在于**这两件事分别由谁、在哪一层完成**。

## 二、常规 hypervisor 的两种存在形式，KVM 都不是

视频先描述了"大多数时候" hypervisor 的样子：它是你必须另外安装的一个独立东西，**要么跑在你的操作系统之上，要么在某些情况下，它本身就是整个操作系统**。[【跳转到 00:58】](https://www.youtube.com/watch?v=A3wFtfrCjxg&t=58) [【跳转到 01:20】](https://www.youtube.com/watch?v=A3wFtfrCjxg&t=80)

这两句话正好对应上一节的两类：

- "跑在你的操作系统之上" = Type 2，宿主型。VirtualBox 就是这样，它是你 Windows 里的一个程序。
- "它本身就是整个操作系统" = Type 1，裸金属型。ESXi 就是这样，装完之后这台机器上只有它。

那么 KVM 呢？它既不是你操作系统上的一个程序（你找不到它的进程），也不是整个操作系统（你明明还在用 Ubuntu 的 shell、apt、systemd）。**KVM 落在第三种形态上**，而这第三种形态正是归类争议的来源。

## 三、KVM 的答案：不是装上去的，是被激活的

视频把这一点称为"理解 KVM 的绝对关键"：**KVM 不是你另外去装的某个独立程序，它是 Linux 内核的一个特性，它把内核本身变成了一个高性能的裸金属 hypervisor**。所以你不是在添加一个 hypervisor，你只是把一直藏在 Linux 里的那个激活了。[【跳转到 01:35】](https://www.youtube.com/watch?v=A3wFtfrCjxg&t=95)

![KVM 不是独立程序，而是 Linux 内核的一个特性，把内核本身变成高性能裸金属 hypervisor](assets/KVM%20为什么算%20Type%201：内核自身变成%20hypervisor/00095.webp)

这句话里有两个词值得停下来看：

- **"内核的一个特性"**：KVM 的代码编译进内核（或作为内核模块加载），运行在**内核态**。它不是一个用户态进程，因此它不受进程调度器的普通约束，也不需要为了访问硬件而发起系统调用——它自己就在系统调用接口的另一侧。
- **"裸金属 hypervisor"**：这不是修辞。当 KVM 被激活后，这台机器上负责虚拟化 CPU 和内存的，就是那个同时负责文件系统、网络栈、进程管理的 Linux 内核。它确确实实直接跑在硬件上。

对比一下就清楚了：ESXi 是"把操作系统换成一个 hypervisor"，KVM 是"让操作系统兼职当 hypervisor"。两者都满足"hypervisor 与硬件之间没有隔着宿主 OS"，只是到达这个状态的方式不同。

## 四、内核里的 hypervisor 怎么被使用：一扇门和三把钥匙

如果 hypervisor 藏在核心里，用户态程序怎么用它？KVM 的答案是 Linux 的老规矩——**一切皆文件**。整个体系围绕一个特殊的设备文件 `/dev/kvm` 转，那就是"前门"；程序只要打开这个文件，就拿到了整个 KVM 王国的钥匙。[【跳转到 02:14】](https://www.youtube.com/watch?v=A3wFtfrCjxg&t=134)

![KVM 的接口以 /dev/kvm 这个设备文件为入口](assets/KVM%20为什么算%20Type%201：内核自身变成%20hypervisor/00134.webp)

打开这扇门之后是一个清晰的层级：先打开 `/dev/kvm` 拿到主句柄；在这个句柄上用一个特殊命令（ioctl）请 KVM 创建一台虚拟机，拿回一个只属于那台 VM 的文件描述符；再用这个句柄请它给 VM 一个虚拟 CPU，又拿回一个文件描述符。[【跳转到 02:35】](https://www.youtube.com/watch?v=A3wFtfrCjxg&t=155)

![创建一台虚拟机的三步：打开 /dev/kvm → KVM_CREATE_VM → KVM_CREATE_VCPU](assets/KVM%20为什么算%20Type%201：内核自身变成%20hypervisor/00155.webp)

视频把这个结构比作**俄罗斯套娃**：每个娃娃都是通往机器更深一层的遥控器。这个比喻点出了一件对归类很重要的事——**控制面在用户态，执行面在内核态**。用户态程序负责"下命令"（创建 VM、创建 vCPU、登记内存），而真正让 vCPU 跑起来、真正做地址翻译的，是内核里的 KVM。这正是 Type 1 的形态：核心工作在核内完成，用户态只是驱动者。

（这三层文件描述符的从属关系与具体 ioctl 清单属于本系列 1.2 节的内容，此处只借它说明"控制面在执行面之外"。）

## 五、设备模拟不在内核里：QEMU 与核空间/用户空间的分工

到这里会冒出一个很自然的反驳：既然 KVM 这么能干，为什么大家总说"KVM + QEMU"？如果 KVM 是完整的 hypervisor，QEMU 又是干什么的？

视频专门澄清了这个常见误解：**KVM 和 QEMU 不是竞争关系，而是一对搭档**。KVM 是 F1 的引擎，擅长那些真正困难、对性能极其敏感的部分——虚拟化 CPU、以极快的速度管理内存；但它**根本不知道硬盘是什么、网卡是什么、USB 口是什么**。[【跳转到 03:05】](https://www.youtube.com/watch?v=A3wFtfrCjxg&t=185) [【跳转到 03:23】](https://www.youtube.com/watch?v=A3wFtfrCjxg&t=203)

![KVM 在内核里做 CPU 和内存虚拟化；硬件模拟（存储、网络）依赖用户态搭档](assets/KVM%20为什么算%20Type%201：内核自身变成%20hypervisor/00203.webp)

分工是这样的：

| 组件 | 职责 | 运行环境 |
| --- | --- | --- |
| KVM | 核心的 CPU 与内存虚拟化 | 内核态（Kernel Space） |
| QEMU | 硬件与设备模拟（假磁盘、假网卡等） | 用户态（User Space） |

![KVM 与 QEMU 的职责与运行环境对照表](assets/KVM%20为什么算%20Type%201：内核自身变成%20hypervisor/00223.webp)

视频对这个分工的评价是"天才"：重活拿到了内核的极致性能，其他一切又享有用户空间程序的安全与灵活。[【跳转到 03:43】](https://www.youtube.com/watch?v=A3wFtfrCjxg&t=223)

**这个分工不改变归类结论，反而印证了它。** 判断 Type 1 还是 Type 2，看的是"虚拟化 CPU 和内存"这件核心工作发生在哪一层——它发生在内核态，与硬件之间没有宿主 OS。至于设备模拟放在用户态，那是"hypervisor 产品怎么组装"的问题，不是"hypervisor 站在哪一层"的问题。ESXi 也有用户态的设备模拟组件，没有人因此说它不是 Type 1。

## 六、三条判断依据：KVM 为什么归入 Type 1

把前面的线索收拢，可以提炼出三条可复用的判断依据。以后遇到任何形态可疑的 hypervisor，都可以拿这三条去套。

**依据一：核心虚拟化工作与硬件之间有没有隔着另一个操作系统。**
KVM 的 CPU 虚拟化和内存管理都在内核态完成，Linux 内核本身就是直接管理硬件的那个层。中间没有第二层操作系统。→ 符合 Type 1。

**依据二：hypervisor 是不是这台机器上唯一的"硬件管理者"。**
Type 2 的典型特征是"宿主 OS 管硬件，hypervisor 通过宿主 OS 间接访问硬件"。KVM 不是这样：它和 Linux 的进程调度、内存管理是同一个内核里的邻居，共享同一套硬件访问路径。→ 符合 Type 1。

**依据三：激活它需不需要先有一个正在运行的操作系统。**
Type 2 必须先有宿主 OS，hypervisor 才能作为应用被启动。KVM 不需要"先有 OS 再有 hypervisor"——加载 KVM 模块的那一刻，这个 OS 就变成了 hypervisor。它不是叠加在 OS 之上，而是把 OS 改造了。→ 符合 Type 1。

三条都指向同一个结论，所以 KVM 通常被归为 **Type 1 的内核内嵌变体**（有时也叫"内核内 hypervisor"）。这个归类不是文字游戏，它解释了为什么 KVM 的性能接近原生——因为它真的就在核心里。

## 七、这个归类带来的三个好处，和一个必须承认的边界

**好处一：接近原生的性能。** 因为它就在内核里，虚拟化路径最短。[【跳转到 05:58】](https://www.youtube.com/watch?v=A3wFtfrCjxg&t=358)

**好处二：继承 Linux 的安全能力。** 视频举的例子是 SELinux——KVM 不是另建一套安全模型，而是直接复用 Linux 久经战阵的那一套。

**好处三：开源生态。** 它是 Linux 的一部分，背后有庞大的全球开发者队伍持续改进，也因此成为驱动开源云的一大引擎，从 OpenStack 一直到你笔记本上可能在用的工具。[【跳转到 06:23】](https://www.youtube.com/watch?v=A3wFtfrCjxg&t=383)

![KVM 的四个优势：性能、安全、开源、生态](assets/KVM%20为什么算%20Type%201：内核自身变成%20hypervisor/00358.webp)

还有一个能说明"内核内嵌"这个定位有多认真的例子：**内核同页合并（KSM，Kernel Samepage Merging）最初就是专门为 KVM 开发的**，目标是在虚拟机之间聪明地共享相同的内存块，从而在一台物理服务器上塞进越来越多的虚拟机。[【跳转到 05:34】](https://www.youtube.com/watch?v=A3wFtfrCjxg&t=334)

![KSM 最初为 KVM 开发，目的是把更多虚拟机塞进物理内存](assets/KVM%20为什么算%20Type%201：内核自身变成%20hypervisor/00334.webp)

这件事的意味比它听起来更深：为了让虚拟化更高效，Linux 内核**专门长出了一个新特性**。这已经不是"操作系统顺便支持一下虚拟化"，而是"操作系统的设计目标里包含了虚拟化"。

**必须承认的边界**：KVM 不是一个可以直接交付给用户的完整 hypervisor 产品。它只负责 CPU 和内存，设备模型要靠用户态的搭档（QEMU 或其他 VMM）补上；它也没有自己的管理界面、没有自己的存储栈。所以严格说，KVM 是"一个 Type 1 的虚拟化引擎"，而不是"一个 Type 1 的成品"。日常口语里说"KVM 是 Type 1 hypervisor"，指的是引擎这一层的归类。

顺带一提，正因为 KVM 只是内核里的一个特性，它可以被加载进一台虚拟机——这就是嵌套虚拟化（L0 物理机跑 KVM，L1 虚拟机里再加载 KVM 变成客户机 hypervisor，它再创建 L2）。[【跳转到 04:14】](https://www.youtube.com/watch?v=A3wFtfrCjxg&t=254) 这属于本系列 7.1 节的内容，此处只作为"KVM 是内核特性"的一个旁证：能被加载进客户机，说明它确实是内核的一部分，而不是需要独占硬件的固件。

## 八、这个归类真正的意义：操作系统不再只是跑应用的平台

视频结尾给出了一个更大的判断：KVM 不只是造出了一个新的 hypervisor，它**从根本上改变了"操作系统是什么"**。操作系统不再只是跑应用的平台，现在它是跑整台计算机的平台。[【跳转到 06:23】](https://www.youtube.com/watch?v=A3wFtfrCjxg&t=383)

把这句话翻译回本文的问题：Type 1 / Type 2 这个二分法，是在"hypervisor 是一个独立产品"的年代形成的。那个年代里，hypervisor 要么取代操作系统（Type 1），要么寄居在操作系统里（Type 2）。KVM 把第三条路走通了——**让操作系统自己成为 hypervisor**。它没有打破分界线，而是把分界线的一端扩展成了一个区间：从"hypervisor 就是整个 OS"，到"OS 的一部分是 hypervisor"，都属于 Type 1。

## 小结

- **KVM 算 Type 1**，准确说是 Type 1 的**内核内嵌变体**：虚拟化核心工作在核内，与硬件之间没有第二层操作系统。
- **判断依据看的是层次位置，不是产品形态**：核心虚拟化工作在哪一层、谁在管硬件、激活它需不需要先有一个运行中的 OS。
- **KVM 是内核的一个特性**，不是独立程序；激活它等于把 Linux 内核改造成 hypervisor，所以性能接近原生。
- **控制面在用户态、执行面在内核态**：`/dev/kvm` 加 ioctl 负责下命令，真正让 vCPU 跑起来的是内核。
- **设备模拟在用户态**：KVM 只管 CPU 和内存，磁盘、网卡由 QEMU 这类搭档模拟。这不影响归类——ESXi 也有用户态组件。
- **边界要承认**：KVM 是一个 Type 1 的虚拟化引擎，不是一个完整的 Type 1 产品。
- **归类不是文字游戏**：它解释了 KVM 为什么快、为什么能继承 Linux 的安全模型、为什么连 KSM 这种内核特性都是为它而生的。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| KVM | Kernel-based Virtual Machine，内建于 Linux 内核的虚拟化特性，把内核变成裸金属 hypervisor |
| 内核态 / 核空间（kernel space） | 操作系统内核运行的特权环境，可直接操作硬件，KVM 就在这里 |
| 用户态 / 用户空间（user space） | 普通应用运行的环境，QEMU 这类设备模拟程序在这里 |
| `/dev/kvm` | KVM 暴露给用户态的字符设备文件，是用上 KVM 的唯一入口 |
| ioctl | 对设备文件发号施令的系统调用，KVM 用它完成创建 VM、创建 vCPU 等操作 |
| QEMU | 用户态的设备模拟器，与 KVM 分工合作，负责模拟磁盘、网卡等硬件 |
| VMM | Virtual Machine Monitor，虚拟机监视器，通常指用户态那个组装并驱动整台虚拟机的程序 |
| KSM | Kernel Samepage Merging，内核同页合并，最初为 KVM 开发，用于在虚拟机间共享相同内存页 |
| 嵌套虚拟化 | 在虚拟机里再加载 hypervisor 并运行更下层的虚拟机，分 L0 / L1 / L2 三层 |
| SELinux | Linux 的安全模块，KVM 直接继承它的安全模型 |
