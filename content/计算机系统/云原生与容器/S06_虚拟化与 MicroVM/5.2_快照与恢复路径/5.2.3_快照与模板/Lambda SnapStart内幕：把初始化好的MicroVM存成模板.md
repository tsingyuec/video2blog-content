# Lambda SnapStart 内幕：把初始化好的 MicroVM 存成模板，恢复只要百毫秒

> 视频来源：[SnapStart for AWS Lambda – Under the hood](https://www.youtube.com/watch?v=zrl8t9q0pTg)（YouTube · Devoxx UK，讲者 Mark Sailes 与 Matthew Meckes，AWS）｜时长约 48 分钟
> 简要导读：AWS 工程师把 SnapStart 拆开讲了一遍——快照怎么造、为什么恢复快、以及"精确克隆"带来的唯一性麻烦。本文只挑**模板**这条线：模板由什么构成、省的是哪段时间、当模板变成要长期管理的资产时会遇到什么。快照的冻结顺序与恢复路径细节见 5.2.1 / 5.2.2，模板文件的持久化与跨机传输归 S07。

## 本讲要解决的核心问题（SCQA）

**背景**：AWS Lambda 按请求执行代码，执行环境（execution environment）是按需创建的。为了省钱，没有流量时会缩到零；为了应对突发，会快速扩出成千上万个执行环境。

**冲突**：AWS 这一侧已经把"创建环境"压到了几百毫秒，但**客户代码自己的初始化**压不下去。一个 Spring Boot 应用启动时要跑依赖注入、连数据库、解析一大堆配置，这一段能吃掉 10~12 秒（[【跳转到 23:07】](https://www.youtube.com/watch?v=zrl8t9q0pTg&t=1387)）。而这部分工作是每次新建环境都要重做一遍的重复劳动。

**疑问**：既然每次都在做同一件事，能不能**只做一次**？

**回答（中心思想）**：能。SnapStart 的做法是：让应用在离线环境里完整初始化一次，然后**把整台 MicroVM 拍成快照存起来当模板**；之后每个执行环境都从这份模板恢复，而不是从零启动。代价是模板是"精确克隆"，凡是必须唯一的东西（随机数、UUID、时间戳）都得在恢复后重新播种；而且模板动辄几十 GB，只能切成小块、按需加载。

## 一、冷启动的时间到底花在哪

讲者用一张直方图把一次调用的延迟拆成了几段（[【跳转到 16:21】](https://www.youtube.com/watch?v=zrl8t9q0pTg&t=981)）：

![图注：调用延迟的构成——从左到右依次是 invoke、initialize、runtime、code、sandbox；理想情况是延迟集中在 invoke（真正干活的代码）附近，实际却堆在右边](assets/Lambda%20SnapStart内幕：把初始化好的MicroVM存成模板/00981.webp)

- `sandbox`：创建一台 Firecracker MicroVM；
- `code` / `runtime`：把代码放进去、启动语言运行时（比如 JVM）；
- `initialize`：跑客户的初始化代码；
- `invoke`：真正处理请求。

AWS 先解决了前两段。他们引入了一个叫 **Worker Manager** 的组件，它记得哪些 worker 之前被创建过，可以保留一段时间，下一次调用直接复用（[【跳转到 16:46】](https://www.youtube.com/watch?v=zrl8t9q0pTg&t=1006)）。

![图注：Worker Manager 在调用链里的位置——它向 Placement 申请扩容、创建 Sandbox，并把已有的 Worker 预留（Reserve）给下一次调用](assets/Lambda%20SnapStart内幕：把初始化好的MicroVM存成模板/01006.webp)

这就是"预热池"：**把创建环境的成本摊到多次调用上**。于是调用分成两条路径——热的快路径和冷的慢路径。但预热池只解决了 AWS 这一侧的成本，`initialize` 那一段还在，而且对 Java 来说它恰恰是最长的一段。

顺带说一句底座：一台 Lambda 的 worker 是裸金属 EC2 实例（比如 M5 metal，接近 400GB 内存），上面跑 KVM，再上面是许多台 Firecracker MicroVM，每台 MicroVM 就是一个隔离的执行环境（[【跳转到 22:01】](https://www.youtube.com/watch?v=zrl8t9q0pTg&t=1321)）。

![图注：一台 worker 里塞着许多台 Firecracker MicroVM，每台是一个独立的执行环境，共用宿主内核（KVM）](assets/Lambda%20SnapStart内幕：把初始化好的MicroVM存成模板/01311.webp)

## 二、模板是怎么造出来的：先离线初始化，再拍快照

SnapStart 的流程可以概括成四步（[【跳转到 25:21】](https://www.youtube.com/watch?v=zrl8t9q0pTg&t=1521)）：

1. 你上传代码、创建一个**函数版本**，并勾选启用 SnapStart；
2. 这个版本**不立刻接流量**，而是被送到一台单独的 worker 上；
3. 在那台 worker 上，代码被加载、JVM 被启动、初始化代码被完整跑完——应用进入"随时可以处理请求"的状态；
4. 此时对整台 MicroVM 拍快照，存进对象存储（S3）。

![图注：设计草图的第一步——一台已经初始化完成的 VM 被"Create"成一份快照](assets/Lambda%20SnapStart内幕：把初始化好的MicroVM存成模板/01545.webp)

![图注：第二步——快照上传到 S3，另一台 worker 把它下载成一份本地副本，然后从这份副本恢复](assets/Lambda%20SnapStart内幕：把初始化好的MicroVM存成模板/01564.webp)

这里有个容易被忽略的工程含义：**模板的"内容"是由一次真实的冷启动决定的**。你在初始化代码里做了什么，模板里就带着什么。所以"模板"其实由三块拼成：

| 组成 | 里面有什么 | 在 SnapStart 里对应什么 |
| --- | --- | --- |
| 根文件系统（rootfs） | 只读块设备镜像 | 装好运行时（如 Java 17）、依赖库的系统盘 |
| 内存快照 | 客户机 RAM 的完整镜像 | 已经启动完的 JVM 堆、已加载的类、Spring 容器、连接池 |
| 设备与 vCPU 状态 | 寄存器、MSR、virtio 队列状态 | 让恢复出来的机器从"暂停点"继续，而不是重新引导 |

第三块决定了恢复和重启的本质区别：恢复出来的不是一台刚开机的机器，而是**一台在初始化刚完成那一刻被按下暂停键的机器**。所以 JVM 不用重启，Spring 不用重新装配。

## 三、为什么恢复快：映射，而不是拷贝

讲者用了一个很贴切的类比来回答"难道每次都要把整个快照搬过来吗"（[【跳转到 29:02】](https://www.youtube.com/watch?v=zrl8t9q0pTg&t=1742)）：

![图注：像在线看视频一样——播放位置附近的数据在本地，后面的数据还在远端，用到才取](assets/Lambda%20SnapStart内幕：把初始化好的MicroVM存成模板/01742.webp)

看在线视频时，你不需要先把整部片子下载完；播放位置附近的数据在本地，剩下的还在远端。快照恢复也是这个思路：**把快照文件映射进内存和磁盘，而不是把它拷进内存**。客户机访问到哪一页，才去取哪一页。这就是"恢复时间与内存大小基本无关"的来源——它只和"恢复后第一段时间里真正被访问到的页数"有关。

这一点在后面的分块设计里会被用到极致。

## 四、模板的工程约束

演讲最硬核的部分，是把"精确克隆"这四个字的代价一条条摊开。

### 4.1 唯一性：模板里的一切都"太像"了

从一份快照恢复出来的多台 VM，是原 VM 的**精确副本**：同样的内存、同样的设备状态、同样的变量值（[【跳转到 27:03】](https://www.youtube.com/watch?v=zrl8t9q0pTg&t=1623)）。

![图注：一份快照恢复出三台 VM，它们连 vm_id 都一模一样（都是 0x5bxn），远端主机因此无法区分它们](assets/Lambda%20SnapStart内幕：把初始化好的MicroVM存成模板/01623.webp)

讲者的原话是："这些是完整的克隆，是原件的精确复制——这让我脑子里响了铃：有些东西必须不一样。"他举的第一个例子就是**随机数**：如果多台机器产生同一串随机数，密码学会被破坏，数据库标识符会重复（[【跳转到 27:10】](https://www.youtube.com/watch?v=zrl8t9q0pTg&t=1630)）。

![图注：哪些层需要"重新播种"——从下往上：RNG（内核随机源）、RNGs/TLS、UUIDs/Timestamps、openssl，每一层都有自己的唯一性来源](assets/Lambda%20SnapStart内幕：把初始化好的MicroVM存成模板/01650.webp)

为此 AWS 向上游开源项目提交了改动，涉及 **OpenJDK、OpenSSL 和 Linux**，确保这些"唯一性来源"在恢复后被正确重新播种，而不是继续沿用快照里的旧状态（[【跳转到 27:55】](https://www.youtube.com/watch?v=zrl8t9q0pTg&t=1675)）。

对写应用的人来说，这条约束会以很具体的形式出现。问答里讲者提到，SnapStart 的推荐模式里包含一种叫 **priming（预热）** 的做法：在拍快照之前，主动去连一次下游服务、必要时重试甚至把连接杀掉重建，目的是让"连接建立"这件事发生在快照之前，而不是发生在恢复之后（[【跳转到 44:46】](https://www.youtube.com/watch?v=zrl8t9q0pTg&t=2686)）。换句话说：**模板里该留什么、不该留什么，是需要设计的**，不是拍下来就完事。

> 这也解释了为什么"模板"和"镜像"不是一回事：镜像是文件系统的静态内容，模板是**带着运行时状态的一整台机器**，所以它必须额外处理"状态里哪些东西不能共享"。

### 4.2 体积：50MB 的代码可以生成 30GB 的快照

第二个约束是尺寸。讲者给了一个很直观的例子：你上传一个 50MB 的 Java 包，快照可能有 **30GB**（[【跳转到 28:21】](https://www.youtube.com/watch?v=zrl8t9q0pTg&t=1701)）。在几百上千台 worker 上各下载一份 30GB 的文件，光下载就要十几秒——比原来的按需创建还慢。

于是他们把快照**切成 512KB 的块**，每块记在一份清单（manifest）里，读的时候不直接读盘，而是经过一层间接层（[【跳转到 29:27】](https://www.youtube.com/watch?v=zrl8t9q0pTg&t=1767)）。

![图注：把整份快照切成 512KB 的块，用清单管理，读取时按需取块](assets/Lambda%20SnapStart内幕：把初始化好的MicroVM存成模板/01767.webp)

间接层背后是三级缓存（[【跳转到 29:52】](https://www.youtube.com/watch?v=zrl8t9q0pTg&t=1792)）：

![图注：读取路径——VM 读内存触发缺页，经过间接层，先查本地缓存（1），再查可用区内的分布式缓存（2），最后才回源到 S3](assets/Lambda%20SnapStart内幕：把初始化好的MicroVM存成模板/01792.webp)

1. **本地缓存**：在宿主上，命中就是微秒级；
2. **分布式缓存**：在同一可用区内，比回源快得多；
3. **S3**：完整快照的最终来源，是最后手段。

讲者特别强调要尽量避免"回源到 S3"，因为那一段延迟和本地缓存差了几个数量级。

### 4.3 共享：不同函数的模板其实大量重复

块化的另一个好处是**跨租户共享**。Alice 和 Bob 的函数看起来毫不相干，但它们的快照里绝大部分块是一样的：都基于 Amazon Linux 2、都用 Java 17 运行时、都链接了一堆相同版本的公共库（[【跳转到 30:42】](https://www.youtube.com/watch?v=zrl8t9q0pTg&t=1842)）。

![图注：fn1 与 fn2 的快照有大量相同的块（common chunks），这部分只需要在缓存里存一份](assets/Lambda%20SnapStart内幕：把初始化好的MicroVM存成模板/01842.webp)

所以真正"独有"的只有函数自己的代码那一小部分。这也解释了为什么缓存会**随着流量自我加热**：函数刚上线时缓存是冷的，冷启动偏慢；随着扩容，越来越多的块被拉到本地缓存，后续的恢复就越来越快（[【跳转到 31:32】](https://www.youtube.com/watch?v=zrl8t9q0pTg&t=1892)）。

### 4.4 版本绑定：模板属于"某一个版本"

模板不是"这个函数"的模板，而是"这个函数的**某个版本**"的模板。只有当你上传新代码、创建新版本时，才会重新走一遍"初始化 + 拍快照"。这也意味着：**新版本刚上线时，它的模板缓存是冷的**，前一批恢复会比后面慢。

演讲末尾的实测数据正好印证了这一点：讲者说这是"开场前刚部署的新函数"，所以缓存层还没被填满（[【跳转到 39:54】](https://www.youtube.com/watch?v=zrl8t9q0pTg&t=2394)）。

## 五、效果：冷启动少了 4 倍，慢的那部分快了 3 倍

讲者用同一份代码、同样的压测（从 100 请求/秒拉到 500 请求/秒）跑了两遍，一遍不开 SnapStart，一遍开。

**并发环境数量**（也就是需要多少台执行环境来扛）：不开 SnapStart 时峰值冲到 259 台，开 SnapStart 后只需要 55 台（[【跳转到 35:19】](https://www.youtube.com/watch?v=zrl8t9q0pTg&t=2119)）。

![图注：左侧是未开 SnapStart 的并发曲线，峰值 259；右侧开 SnapStart 后只需 55——因为每个环境"上线"得更快，不需要提前堆容量](assets/Lambda%20SnapStart内幕：把初始化好的MicroVM存成模板/02119.webp)

**延迟分布**（约 33 万次调用）：

| 指标 | 未开 SnapStart | 开启 SnapStart |
| --- | --- | --- |
| 冷启动次数 | 259 | 53 |
| 冷启动 p50 | 2841 ms | 891 ms |
| 冷启动 p90 | 2996 ms | 1012 ms |
| 冷启动 p99 | 3391 ms | 1236 ms |
| 热调用 p50 | 6.3 ms | 6.5 ms |

![图注：未开 SnapStart 的日志查询结果——259 次冷启动，p50 约 2.84 秒，最慢 3.67 秒](assets/Lambda%20SnapStart内幕：把初始化好的MicroVM存成模板/02269.webp)

![图注：开启 SnapStart 后同一份查询——冷启动只有 53 次，p50 降到 891 毫秒；热调用仍是 6 毫秒量级](assets/Lambda%20SnapStart内幕：把初始化好的MicroVM存成模板/02344.webp)

两个结论值得记住：

- **热调用完全没变**（6 毫秒量级）。模板只影响"环境怎么来"，不影响"代码怎么跑"。
- **冷启动的次数和时长同时下降**。次数下降是因为每个环境上线更快、不需要提前堆容量；时长下降是因为恢复跳过了初始化。

讲者也坦率地说：冷启动没有被"消灭"，热路径是单数字毫秒，冷路径仍是几百毫秒，两者之间还有差距（[【跳转到 31:57】](https://www.youtube.com/watch?v=zrl8t9q0pTg&t=1917)）。

## 六、这条链路的边界

- **镜像 vs 模板**：OCI 镜像的分层、构建与仓库归 S03；本文讲的只是"用镜像冷启动一次 → 把结果存成模板 → 反复恢复"这条链路。模板的起点仍然是镜像（rootfs），只是它多带了一份内存与设备状态。
- **探针 vs 快照点**：S03 里的就绪探针（readiness probe）回答"服务能不能接流量"；SnapStart 的拍快照时刻回答的是同一个问题——**只有应用真正就绪，拍下来的模板才有意义**。拍早了，恢复出来的机器还得补做初始化；拍晚了，白等。
- **恢复路径 vs 模板**：从 mmap 到 `KVM_RUN` 的具体步骤、冻结与序列化的先后顺序，见 5.2.1 与 5.2.2；本文只讲"模板"这个工程做法。
- **持久化与传输**：分块、清单、远端缓存这些机制背后的存储格式与跨机传输，归 S07。

## 小结

- 模板 = 一次真实冷启动的完整结果：rootfs + 内存快照 + 设备与 vCPU 状态。它把"初始化"从每次执行里拿出来，只做一次。
- 省时间的位置很明确：跳过 JVM 启动、依赖注入、连接建立这些"准备"；真正的业务代码执行不受影响（热调用延迟不变）。
- 恢复之所以快，是因为快照被**映射**而不是被拷贝，只有真正访问到的页才从缓存或 S3 取回。
- 模板是"精确克隆"，所以必须处理唯一性：随机数、UUID、时间戳、TLS 都要重新播种，AWS 为此改了 OpenJDK、OpenSSL 和 Linux；应用侧则要靠 priming 之类的模式，把"该在快照前完成的事"提前做完。
- 模板体积可达几十 GB，必须切成 512KB 的块、走三级缓存，并利用不同函数之间的公共块来共享。
- 模板与"函数版本"绑定：新版本意味着新模板，也意味着缓存要重新加热。
- 效果：冷启动次数 259 → 53，冷启动 p50 2841ms → 891ms，而热调用保持 6ms 量级。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| 执行环境（execution environment） | Lambda 里跑一次函数调用的隔离单元，底层是一台 Firecracker MicroVM |
| 冷启动 | 没有现成执行环境可用，必须新建一个再执行代码的那条慢路径 |
| 快照（snapshot） | 把一台运行中 VM 的磁盘、内存、设备与 vCPU 状态完整序列化下来的结果 |
| 模板 | 一份被当作"起点"反复恢复的快照，加上它的版本与配置标识 |
| 精确克隆（exact clone） | 从同一份快照恢复出的多台 VM 状态完全相同，因此唯一性来源必须重新播种 |
| priming（预热） | 在拍快照之前主动建立连接、加载数据，让恢复后的机器少做准备工作 |
| 间接层（indirection layer） | 读取快照时不直接读盘，而是先经过一层可编程的查找，决定块从哪一级缓存来 |
| 分布式缓存 | 同一可用区内的共享缓存层，介于本地缓存与 S3 之间 |
