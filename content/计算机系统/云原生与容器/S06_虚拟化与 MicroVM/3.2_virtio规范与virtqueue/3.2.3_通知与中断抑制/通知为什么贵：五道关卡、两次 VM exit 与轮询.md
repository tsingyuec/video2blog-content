# 通知为什么贵：一次 kick 要过五道关卡，少一次通知能换来 70% 吞吐

> 视频来源：[网络IO痛点：硬核解密Virtio架构](https://www.bilibili.com/video/BV1oKu76eEHg/)（B 站 · 衡水铁头哥）｜时长约 8 分钟
> 导读：这支视频用"架构演进史"的讲法，把纯 Virtio、vhost-net、vhost-user 三代数据面串成一条线。本文沿着它的主线，只追问一个问题：**每一次通知到底走了多长的路，后来又是怎么被缩短甚至取消的**。virtqueue 的环结构见本节 3.2.2，vhost 的进程模型见 3.3.3。

## 本讲要解决的核心问题（SCQA）

**背景**：virtio 用 vring 这块共享内存，让客户机驱动和宿主后端直接交换数据，避免了全虚拟化时代"每个寄存器访问都要陷入"的笨重模拟。

**冲突**：共享内存只解决了"数据放在哪儿"，没有解决"对方怎么知道有新数据"。于是双方必须互相通知：驱动提交完要敲设备，设备处理完要敲驱动。而通知是要跨过客户机与宿主边界的动作，边界越厚，敲一次越贵。

**疑问**：一次通知究竟贵在哪里？把后端从用户态搬到内核、再搬到独立进程，为什么能让同一条通知变便宜，甚至干脆不要通知？

**回答（中心思想）**：通知的成本不在"写一个地址"这个动作本身，而在它引发的**连锁反应**——陷入、唤醒、上下文切换、内存拷贝。三代架构做的事情是同一件：**把这条连锁反应缩短**。纯 Virtio 是五次过关，vhost-net 用 `ioeventfd` / `IRQFD` 把通知留在内核，vhost-user 则用轮询把通知整个取消。代价也随之转移：从"每次通知都付钱"变成"常驻一个核在空转"。

## 一、共享内存解决了"数据放哪儿"，没解决"怎么通知"

视频先回到全虚拟化的年代。那时 hypervisor 要假装成一块真实的网卡，客户机驱动每碰一次寄存器，CPU 就得从虚拟机里陷入出来，让 hypervisor 扮演那块卡 [【跳转到 01:34】](https://www.bilibili.com/video/BV1oKu76eEHg/?t=94)。网卡这种设备被碰得极其频繁，于是这套模拟成了性能天花板。

Virtio 的破局点是把"递纸条"换成"共享白板"：

![vring 的定义：一块共享内存，严格解耦控制逻辑与数据逻辑](assets/通知为什么贵：五道关卡、两次%20VM%20exit%20与轮询/00094.webp)

过去虚拟机和宿主机传递数据，像两个人隔着一堵墙递纸条，麻烦且容易出错；vring 出现后，相当于两人中间放了一块共享白板，数据直接写在白板上，然后指着白板说"数据在那儿，你自己看"。这种机制严格解耦了控制逻辑和数据逻辑，在虚拟机和宿主机之间建立起一条零拷贝高速公路 [【跳转到 01:54】](https://www.bilibili.com/video/BV1oKu76eEHg/?t=114)。

但"指着白板说一声"这个动作，就是通知。数据面可以零拷贝，通知却没法零成本——因为说这一声，必须跨过边界。

## 二、纯 Virtio：一次 kick 要过五道关卡

![第二部分的分隔页：纯 Virtio 开销，被视频称为虚拟化的黑暗时代](assets/通知为什么贵：五道关卡、两次%20VM%20exit%20与轮询/00133.webp)

视频把纯 Virtio 架构下的发送路径拆成了五个环节 [【跳转到 02:19】](https://www.bilibili.com/video/BV1oKu76eEHg/?t=139)：

![纯 Virtio 发送执行链条：客户机 OS、KVM 截获、唤醒 QEMU、环形转换、VM Entry](assets/通知为什么贵：五道关卡、两次%20VM%20exit%20与轮询/00159.webp)

1. **客户机 OS 写入寄存器**，触发特权异常；
2. **KVM 截获**，触发 VM Exit，把控制权交给 KVM 模块；
3. **唤醒 QEMU**，经过一次昂贵的上下文切换；
4. **环形转换**，从内存提取数据，拷贝到内核的 TAP 设备；
5. **VM Entry**，KVM 恢复 CPU 状态回到虚拟机内部。

视频的比喻是"你寄个快递要过五道海关" [【跳转到 02:59】](https://www.bilibili.com/video/BV1oKu76eEHg/?t=179)。而真正致命的是它给出的量化：在数据包一来一回的完整周期里，系统要忍受**两次上下文切换、两次 VM Exit、两次 VM Entry** [【跳转到 03:05】](https://www.bilibili.com/video/BV1oKu76eEHg/?t=185)。

![一堵看不见的墙：通知引发的连锁反应在吞噬 CPU 周期](assets/通知为什么贵：五道关卡、两次%20VM%20exit%20与轮询/00185.webp)

这就是"通知贵"的第一层答案：**通知不是一个动作，而是一条链**。驱动写一个地址只是链头，后面跟着陷入、唤醒、调度、拷贝。在海量小包面前，这条链会被走几十万次每秒，不仅耗尽 CPU 的时钟周期，频繁的内存拷贝还会急剧消耗内存带宽，也就是视频说的"内存墙效应" [【跳转到 03:25】](https://www.bilibili.com/video/BV1oKu76eEHg/?t=205)。

## 三、第一次缩短：vhost-net 把通知留在内核

既然用户态的 QEMU 搬运数据是灾难，工程师换了个思路：把数据面搬进内核。Linux 引入了 vhost-net 模块，直接在宿主机内核里建立专门的工作线程，完全接管数据面，彻底绕过用户态的 QEMU [【跳转到 03:47】](https://www.bilibili.com/video/BV1oKu76eEHg/?t=227)。

关键在于它用了两个内核机制，正好对应我们这一节的两条通知路径：

- **`ioeventfd`**：让虚拟机发送数据的通知**直接唤醒内核线程**。驱动的 kick 不再需要把 QEMU 从睡眠里叫起来，KVM 收到写事件后直接踢醒 vhost 工作线程。
- **`IRQFD`**：让数据到达时，内核能**直接给虚拟机注入中断**。设备侧那次中断不再需要绕道用户态。

![vhost-net 之后，路径从"绕远路"变成"直连"](assets/通知为什么贵：五道关卡、两次%20VM%20exit%20与轮询/00227.webp)

对比很清楚：纯 Virtio 有多次数据拷贝和极其沉重的用户态上下文切换，而 vhost-net 在内核模式下直接实现了**零用户态切换** [【跳转到 04:26】](https://www.bilibili.com/video/BV1oKu76eEHg/?t=266)。

但视频特意提醒了细节：虽然它极大消灭了 QEMU 上下文切换带来的性能抖动，数据从共享内存到 TAP 设备之间**依然存在一次内存拷贝**，内核线程的调度也多多少少还有微小开销 [【跳转到 04:46】](https://www.bilibili.com/video/BV1oKu76eEHg/?t=286)。

![从"背着货箱的蜗牛"到"火箭"：vhost-net 消掉的是用户态切换这一段](assets/通知为什么贵：五道关卡、两次%20VM%20exit%20与轮询/00286.webp)

换句话说，vhost-net 缩短的是**通知路径的长度**，没有取消通知本身。kick 还是要 kick，中断还是要注入，只是它们不再穿过用户态。这也正是本小节与 3.3.3 的分界：vhost 把后端搬到哪里，属于 3.3.3 的话题；对我们来说，它改变的是"通知要跨几道边界"。

## 四、第二次缩短：vhost-user 干脆不要通知

要应对万兆甚至更高速率的网络，连内核态那一点调度开销都变得无法忍受 [【跳转到 05:07】](https://www.bilibili.com/video/BV1oKu76eEHg/?t=307)。于是 vhost-user 把后端逻辑从内核里剥离出来，交给像 DPDK 这样的独立用户态进程 [【跳转到 05:31】](https://www.bilibili.com/video/BV1oKu76eEHg/?t=331)。

它是怎么做到的：初始化时 QEMU 通过 UNIX 域套接字，把代表虚拟机内存的文件描述符传给 DPDK 进程，DPDK 通过 `mmap` 把这些 fd 直接映射到自己的虚拟地址空间。这意味着 DPDK 进程可以直接看到并操作虚拟机的物理内存，不需要任何系统调用来搬数据。

真正和通知有关的，是 DPDK 引入的 **PMD（Poll Mode Driver，轮询模式驱动）**：它像一个不知疲倦的哨兵，利用死循环在一个专用 CPU 核上不断探测状态，**彻底消灭了所有的中断唤醒开销**，最终实现真正意义上的零次内存拷贝 [【跳转到 06:11】](https://www.bilibili.com/video/BV1oKu76eEHg/?t=371)。

这是抑制通知最彻底的一种做法：不是把通知变便宜，而是**不问"有没有新数据"，直接一直看**。代价也很直接——那个专用核从此不能干别的，无论有没有流量都在满速空转。

视频给出的收益数字是：在特定的 VM 到 VM 测试中，配合真正的零拷贝机制，再加上 TCP 分段卸载，系统吞吐量实现了超过 70% 的跃升 [【跳转到 06:27】](https://www.bilibili.com/video/BV1oKu76eEHg/?t=387)。

| 架构模式 | 数据平面层级 | 发送瓶颈 | 接收瓶颈 | 内存拷贝 |
| --- | --- | --- | --- | --- |
| 纯 Virtio | 宿主机用户态 | 切换与 VM Exit | 切换与 VM Entry | 多次 |
| vhost-net | 宿主机内核态 | 线程调度与 ioeventfd | irqfd 中断开销 | 1 次 |

这张表的读法是：**每一行都在把"通知"这一列的成本往下压**。第一行的瓶颈是通知引发的陷入与切换；第二行把通知留在内核，瓶颈退化成线程调度和中断注入本身；第三行干脆用轮询替代通知，瓶颈变成"必须有人一直看着"。

## 六、判断规则：什么时候该让通知变便宜，什么时候该取消它

把视频的三代架构翻译成选择规则，其实就是三个问题：

1. **通知频率高不高？** 如果每秒只有几百次 IO，纯 Virtio 那五道关卡完全不是问题，架构越简单越好。
2. **能不能接受一次拷贝？** 如果只是中等吞吐，vhost-net 的"零用户态切换 + 一次拷贝"是性价比最高的位置——通知还在，但路径短了。
3. **有没有一个核可以专门用来空转？** 只有当吞吐高到"内核调度那一点点开销也无法忍受"，并且愿意付出一个专用 CPU 核时，vhost-user 的轮询才划算。视频里那句"哪怕是内核态那一点点调度开销现在也变得完全无法忍受"，说的正是这个门槛 [【跳转到 05:07】](https://www.bilibili.com/video/BV1oKu76eEHg/?t=307)。

反过来说，交互式、低延迟、低负载的场景不该盲目上轮询：轮询换来的低延迟，是用一个永远在跑的核买来的；没有足够流量摊薄，这笔钱就是纯亏。

## 小结

- 共享内存解决了"数据放哪儿"，**通知**解决"对方怎么知道"，而通知必须跨边界，所以它天然昂贵。
- 纯 Virtio 的一次 kick 要走五道关卡，一来一回是两次上下文切换、两次 VM Exit、两次 VM Entry。
- vhost-net 用 `ioeventfd` 唤醒内核线程、用 `IRQFD` 注入中断，把通知路径从"穿过用户态"缩短到"留在内核"，但保留了一次内存拷贝。
- vhost-user 用 PMD 轮询**取消**通知：不问有没有新数据，一直看。代价是一个专用核持续空转。
- 三代架构的演进方向一致：**让每次通知更便宜，直到不需要通知**；吞吐提升的 70% 来自这条链上每一段的缩短。
- 选择规则看三件事：通知频率、能否接受一次拷贝、有没有多余的核可以空转。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| kick | 驱动通知设备"有新请求"，在纯 Virtio 里表现为一次寄存器写，会触发 VM Exit |
| VM Exit / VM Entry | CPU 从客户机陷入宿主、再从宿主返回客户机的两次切换动作 |
| `ioeventfd` | KVM 的机制：客户机对某个地址的写直接唤醒内核里等待的线程，省掉用户态中转 |
| `IRQFD` | KVM 的机制：内核侧可以直接向客户机注入中断，不必绕道用户态 |
| vhost-net | 把 virtio 后端放进宿主内核的数据面实现，通知不再穿过 QEMU |
| vhost-user | 把后端放进独立用户态进程（如 DPDK），通过共享内存 fd 直接访问客户机内存 |
| PMD | Poll Mode Driver，轮询模式驱动：死循环探测状态，彻底不用中断 |
| 内存墙 | 频繁拷贝把内存带宽吃满，成为比 CPU 更早出现的瓶颈 |
| 通知成本 | 写一次地址本身很便宜，贵的是它引发的陷入、唤醒、切换与拷贝 |
