# InChI 的边界：标准化做到哪一步，哪些结构还算不清

> 视频来源：[News from the InChI](https://www.youtube.com/watch?v=g5hb6YJOE9k)（YouTube · NFDI4Chem 线上报告，InChI 项目组主讲，InChI Trust 技术总监参与）｜时长约 32 分钟
> 导读：这是一份「InChI 项目进展通报」：它先说清 InChI 的目标与读法，再逐条交代哪些化学结构还算不清、工作组各自做到哪一步、版本与参数意味着什么。相比 1.2.1 的 SMILES 语法和同节另一篇的分层原理，本文聚焦**标准化的边界与版本纪律**——也就是「什么时候可以相信两条 InChI 相等」。

## 本讲要解决的核心问题（SCQA）

**背景**：InChI 已经是化学数据的事实标准。报告给出的规模是：EBI 的 UniChem 有 1.57 亿条带 InChI 的记录，PubChem 1.2 亿条，ChemSpider 7100 万条，Reaxys 6000 万条。跨库合并、查重、检索都靠它。

**冲突**：但 InChI 是二十多年前定下的设计。无机与有机金属化合物、互变异构、聚合物、混合物、纳米材料，都是后来才被认真对待的；项目本身还在改代码、发版本，而**换版本、换参数就可能换串**。使用者如果只记住「InChI 唯一」，很容易在边界上踩坑。

**疑问**：所谓 **Standard InChI** 到底「标准」在哪？哪些结构它现在还算不清？拿它做身份判定时，必须遵守哪些纪律？

**回答（中心思想）**：标准 InChI = **一套固定的计算参数 + 一个明确的版本 + 一段固定的预处理规则**。InChI 用分层设计把这些不确定性隔离在可选的层里，把还没解决的结构类型交给专门的工作组；因此使用者的正确姿势是：**记录版本与是否标准、看清组分、不从 InChIKey 反推结构、把 InChI 当索引而不是结构描述**。

## 一、InChI 的目标：免费、非专有、能从结构自己算出来

### 1.1 「免费」是硬指标，不是口号

报告一开场就解释为什么非要一个免费标识符不可：CAS 号当然好用，但它是**注册制**——你得向 CAS 登记才能拿到号，而且这套服务不是免费的。对一个要覆盖「所有物质」的标识体系来说，收费和登记这两道门槛都不可接受。

更要紧的是那些**还不存在的分子**：只存在于理论计算里、只存在于实验设计里的化合物，根本没法去登记 CAS 号，但它们同样需要被标识、被检索、被链接。这是 InChI 从设计之初就必须「由结构算出来」的根本原因。

### 1.2 化学结构本身就是元数据

报告把 InChI 放进 FAIR 原则（可发现、可访问、可互操作、可复用）里讲：化学结构不是一张插图，它**自己就是元数据**——连接关系、拓扑结构都在里面。要让化学数据可发现、可互操作，就必须有一个唯一标识符把这些信息串起来。

讲者的判断很直接：数据只有在有唯一标识符的前提下才可能被复用。这也解释了为什么 InChI 不只服务学术界：产业界、政府监管机构（比如要处理新药、新毒物、新专利的部门）都在同一条链上。

## 二、一条 InChI 怎么读：`1S` + 分子式 + `/c` `/h` `/q` `/t` `/i`

### 2.1 分层：从「版本」到「同位素」

报告用一张标注图把 InChI 的每一段拆开：

| 片段 | 含义 |
| --- | --- |
| `InChI=1S` | 版本 1，`S` 表示这是**标准 InChI**（也存在非标准的 InChI，普通用户一般用不到） |
| 分子式 | 例如 `C2H4ClNO2`，按 Hill 顺序排列 |
| `/c` | 原子连接子层：谁和谁相连 |
| `/h` | 氢原子子层：氢挂在哪里 |
| `/q` 或 `/p` | 电荷层：例如整体带 +1 |
| `/t` `/m` `/s` | 立体化学层 |
| `/i` | 同位素层 |

讲者特别强调第一段的那个 `1S`：它不只是版本号，还声明了「这条串是用标准参数算出来的」。这一点在第四节会展开。

### 2.2 InChIKey 是 InChI 的哈希

同一张图的下半部分讲了 InChIKey：它是 InChI 的**哈希版本**，用来做紧凑表示，方便丢进 Google 之类的搜索引擎。幻灯片把 Key 也按段标注了：主层、立体化学与同位素、版本、质子（电荷）信息。

哈希意味着两件事：**长度固定**（便于数据库字段与搜索框），以及**不可逆**（拿到 Key 无法还原结构）。后面第六节会看到，社区专门为此做了一个 Resolver 服务。

### 2.3 它不是给人读的

报告专门用一页说明：InChI 字符串**不是**为普通人类读者设计的，也不打算让人直接读懂。它像条形码、像二维码——「不要派一个人去做机器该做的事」。

这句话点出了 InChI 与 SMILES 的分工：SMILES 追求人也能读写（代价是不唯一），InChI 追求机器可算且唯一（代价是难读）。

## 四、「标准」的确切含义：一套参数 + 一个版本 + 一段预处理

### 4.1 三步流水线

报告把 InChI 的计算拆成三段，并说明新代码要按这个结构重组：

1. **结构规范化预处理器（normalization preprocessor）**：先把结构「洗干净」——处理互变异构、有机金属键等表示差异。讲者说这一步对互变异构特别关键，对有机金属同样必要。
2. **规范化与连接性（canonicalization / connectivity）**：图同构编号，决定原子顺序。
3. **后处理（post-processing）**：拼装各层、输出字符串。

这个拆法解释了为什么「同一个分子不同画法得到同一条串」：差异在第一步就被抹平了。

### 4.2 20 到 25 个参数，只有一种组合叫「标准」

报告里有一句极重要、但很容易被忽略的话：InChI 的生成程序有 **20 到 25 个可调参数**，而**只有一种参数组合**算出来的才叫 **Standard InChI**。

这意味着：

- 同一份结构，用不同参数跑，会得到**不同的 InChI 串**，但它们都「合法」；
- 只有以 `InChI=1S/` 开头的那条，才是各方默认互认的标准串；
- 如果你用某个软件算出的串和数据库里的对不上，第一件要查的事就是：**它是不是标准 InChI、用的是哪套参数**。

### 4.3 版本：1.05、1.06，以及「改版会改串」

报告交代了发布状态：**InChI 1.06 已于 2020 年 12 月发布**，可从 InChI Trust 网站下载；1.05 里发布过聚合物的基本支持，1.06 修正了一些问题。同时提到 1.06 之后修复了 Google 报告的内存泄漏等问题——Google 是 InChI 的重度用户，安全要求很严。

对使用者来说，这意味着**版本号必须跟着数据一起存**。如果你在 2020 年前后用不同版本给同一批结构算过 InChI，就需要重新核对一遍；这也是很多数据库会同时保存「InChI + 计算版本」的原因。

### 5.1 有机金属与无机：金属键不再断开

这是报告里讲得最细的一块。InChI 早期的一个基本决定是**把金属键切断**，只保留断开后的有机片段——这导致无机与有机金属化合物长期「算不准」。新方案的核心改动是：

- 接受 **bond type 9**（按 Biovia 规范解释的配位键）；
- 接受**多中心连接键**（`*` 原子，例如二茂铁里指向环中心的那种键）；
- **不再断开**与金属相连的键（no disconnection）；
- 唯一保留的例外是**盐的断开**：像氯化钠这样的盐，仍然按传统方式断开处理；
- 提供**重连 InChI（Reconnection InChI）**作为可选输出；
- 配位立体化学（四方平面 SP-4、三角双锥 TB-5、八面体 OC-6）用新的 `/ma` 层表达。

![有机金属的状态：不断开金属键、保留盐断开、用 /ma 层表达配位立体化学](assets/InChI%20的边界：标准化进度、版本与结构类型限制/01604.webp)

[【跳转到 26:44】](https://www.youtube.com/watch?v=g5hb6YJOE9k&t=1604)

这里对「盐」的处理值得单独记住：**盐在 InChI 里是被拆成组分的**。所以同一药物分子的游离碱和盐酸盐，会得到不同的 InChI——它们本来就是不同的物质（一个含 HCl 组分，一个不含）。做身份比对时，必须明确你要比的是「活性成分」还是「上市形态」。

### 5.2 互变异构：靠预处理归一，但界线仍在讨论

报告把互变异构列为「困难」项，并说明新架构里它归**规范化预处理器**管：把官能团的互变形态按一套规则统一处理，再进入编号阶段。讲者提到这套规则（tautomer rules）已经有上百条，目的只有一个——保证同一物质在不同画法下仍然得到同一条串。

但界线问题没有消失：把所有互变异构体都归一，会让某些在反应机理上有区别的形态变得无法区分；不归一，又会让同一瓶试剂产生多条 InChI。这是 InChI 社区至今仍在讨论的取舍（同节另一篇有具体例子）。

### 5.3 立体化学：扩展立体化学与糖化学

立体化学被列为「需求基本就绪、即将实现」的一项，重点是**扩展立体化学**（enhanced stereochemistry）与特殊糖化学——即那些用现有的 `/t` `/m` `/s` 表达不了的复杂立体关系。

### 5.4 其余清单

- **同位素体（isotopologues）**：范围较小，正在讨论输入格式；
- **聚合物**：基本框架已完成（用括号表示重复单元、共聚物用多组括号），少数类型（如接枝聚合物）尚未实现；
- **大分子**：还在划定范围，HELM 可能扮演重要角色；
- **混合物**：正在做原型，例如「正丁基锂的己烷溶液」这种商品试剂，本身就不是纯化合物；
- **纳米材料**：报告承认这一项最难——它甚至不是「一个标识」而是「一组标识」，因为多数企业不公开纳米材料的全部信息；
- **可变分子 / Markush**：专利里常见的通式结构，属于讨论组。

报告对这些项的态度很务实：能做的先做（聚合物、有机金属），难的先划范围（大分子、纳米），有争议的先讨论（互变异构界线、Markush）。

### 6.1 Resolver 的存在，恰好证明了 Key 不可逆

Resolver 的动机讲得很清楚：**你没法从 InChIKey 倒推出 InChI**。所以社区的做法是「去网上找」——如果某个 Key 已经在公开数据库里发布过，就把它对应的 InChI 取回来。

这给使用者一个明确的操作结论：InChIKey 只能当**检索键**，不能当**结构存档**。要长期保存结构身份，必须存 InChI 本体（并记录版本）。

### 6.2 反应与二维码

RInChI 解决的是「分子有了标识，反应还没有」的问题：现在检索反应只能依赖化学文摘社这类二次出版商，如果反应本身有标识符，就能直接检索。

QR InChI 则是一个很实用的落地场景：站在试剂柜前，扫一下瓶子上的二维码就知道里面是什么，不用去猜标签上的俗名。

## 七、给使用者的四条纪律

把整场报告压成可执行的规则，就是下面四条：

1. **记录版本与是否标准**。存 InChI 时同时存「1S 还是非标准」「由哪个版本算出」。跨版本、跨软件比对前先确认参数一致——这是「同一结构不同串」最常见的来源。
2. **看清组分再比**。盐在 InChI 里是拆成组分的，游离碱与盐酸盐是两条不同的串；混合物、聚合物、纳米材料目前只有部分支持，别指望一条串说清全部。
3. **不要从 Key 反推结构**。哈希不可逆，需要结构就存 InChI 或原始结构文件；只有 Key 时，走 Resolver 之类的查表路径。
4. **把 InChI 当索引，不当描述**。它不含三维构象、不含电子分布、不含反应性；这些要另存（构象问题见 1.2.3）。

## 小结

- **目标**：免费、非专有、可由结构自算——这三点决定了 InChI 必须开源，也决定了它能覆盖「还不存在的分子」。
- **读法**：`1S` 声明标准与版本，随后是分子式与 `/c` `/h` `/q` `/t` `/i` 各层；InChIKey 是它的定长哈希，便于检索但不可逆。
- **标准的含义**：20~25 个参数中只有一种组合叫 Standard InChI；版本（1.05、1.06）会变，串也可能变，所以版本必须随数据一起存。
- **边界**：有机金属/无机（不断开金属键、保留盐断开、`/ma` 层）、互变异构（预处理归一，界线仍在讨论）、扩展立体化学、同位素体、聚合物、混合物、纳米材料、Markush 通式——各自有工作组在推进。
- **盐与多组分**：盐被拆成组分，所以游离形式与盐形式是两条不同的 InChI，比对前要先想清楚比的是哪一个。
- **应用层**：RInChI 管反应、Resolver 补 Key 不可逆、QR 管实物、MInChI 管混合物、NInChI 管纳米材料。
- **纪律**：记版本、看组分、不反推、当索引。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| Standard InChI | 用唯一一套默认参数算出的 InChI，串以 `InChI=1S/` 开头 |
