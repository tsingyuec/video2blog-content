## 本讲要解决的核心问题（SCQA）

**背景**：让模型返回 JSON 最直觉的做法，是在提示词里写一句「请返回 JSON」。

**冲突**：这句提示本质上是在跟大模型**商量**，依赖的是它的指令遵循能力。但自然语言本身是模糊的，模型经常会「加戏」：在外面套一层 markdown 标签，或者加上一句「好的，这是你要的 JSON」，甚至随意更改数据类型，把数字 `123` 搞成字符串。这完全是一个不可控的概率游戏 [【跳转到 00:13】](https://www.bilibili.com/video/BV1aKnb6WEFY/?t=13)。

![「请返回 JSON」是一句自然语言请求，模型听不听全靠它心情](assets/约束解码：把%20JSON%20Schema%20编译成状态机，把非法%20token%20的%20logit%20打成负无穷/00013.webp)

**疑问**：模型底层到底是怎么做到「听话」的？把 schema 交给推理引擎之后，它凭什么能保证输出合法？

**回答（中心思想）**：因为约束解码把「概率性文本生成」变成了「确定性结构输出」。推理引擎先把 schema 编译成有限状态机（或上下文无关文法），预先设定好所有合法的状态路径；生成每个词时执行**动态词表屏蔽**，把当前状态下不合法的 token 概率强制设为负无穷。于是模型在物理上就不可能输出不符合规范的字符——**100% 的格式稳定是被机制保证的，不是被祈祷出来的** [【跳转到 01:45】](https://www.bilibili.com/video/BV1aKnb6WEFY/?t=105)。

## 一、从「概率文本」到「确定性结构」

视频用一张对照表把两种范式摆开 [【跳转到 01:08】](https://www.bilibili.com/video/BV1aKnb6WEFY/?t=68)：

| 概率性文本生成 | 确定性结构输出 |
| --- | --- |
| 预测下一个词，整个词表一起算概率 | 合法路径预先定死（schema 编译成状态机） |
| 按概率采样，同一个问题两次答案不同 | 只在合法分支里走（非法选项概率清零） |
| 结果不可复现，下游代码无法依赖 | 结果可预期，下游可以放心反序列化 |

![概率文本 vs 确定性结构：左侧是「整表算概率 + 采样 + 不可复现」，右侧是「合法路径预编译 + 只在合法分支走 + 可预期」](assets/约束解码：把%20JSON%20Schema%20编译成状态机，把非法%20token%20的%20logit%20打成负无穷/00068.webp)

注意这张表里没有说「模型变聪明了」。模型本身的分布一点没变，变的是**采样空间**：原本 $|V|$ 个候选，现在只剩下当前语法状态下合法的那些。

## 二、第一步：把 schema 编译成状态机

喂进 schema，底层把它编译成**有限状态机**（FSM），也可以编译成**上下文无关文法**（CFG）——视频说这是「同一份契约的两种等价表示」 [【跳转到 01:28】](https://www.bilibili.com/video/BV1aKnb6WEFY/?t=88)。以 JSON 为例，状态机的走法大致是：

1. **起始**：遇到 `{`；
2. **字段名**：只认 schema 里声明过的键；
3. **取值**：类型必须对得上（字符串/整数/布尔/枚举）；
4. **结束**：文法闭合才收口。

![schema 编译出的状态机：起始（遇到 {）→ 字段名（只认 schema 里的键）→ 取值（类型必须对得上）→ 结束（文法闭合才收口）](assets/约束解码：把%20JSON%20Schema%20编译成状态机，把非法%20token%20的%20logit%20打成负无穷/00088.webp)

状态机的关键作用是：**给定已经生成的前缀，它能算出「下一个字符允许是哪些」**。这一步把「形状」从一个抽象约定，变成了每一步都可以查询的集合。

## 三、第二步：动态词表屏蔽，把非法 token 的概率置为负无穷

有了合法字符集合，解码时就能做屏蔽。视频举的例子最直观：如果 schema 规定当前字段必须是一个布尔值，那么模型在生成这个字段时，除了 `true` 和 `false` 对应的词表项，其他所有选项的概率都会在底层被强制设为负无穷 [【跳转到 01:28】](https://www.bilibili.com/video/BV1aKnb6WEFY/?t=88)。

写成式子，第 $t$ 步先算出掩码 $m_t$，再作用到 logits 上：

$$
\text{logits}'_t = \text{logits}_t + m_t,\qquad
m_t[i] =
\begin{cases}
0, & i \in \mathcal{A}(s_t) \\
-\infty, & i \notin \mathcal{A}(s_t)
\end{cases}
$$

其中 $s_t$ 是当前状态机状态，$\mathcal{A}(s_t)$ 是该状态下合法的 token 集合。softmax 之后非法项的概率为 0：

$$
p_t(i) = \frac{\exp(\text{logits}'_t[i])}{\sum_j \exp(\text{logits}'_t[j])},\qquad
p_t(i)=0 \ \text{当} \ i \notin \mathcal{A}(s_t)
$$

于是「模型在物理上就不可能输出不符合规范的字符」，从而实现百分百的格式稳定 [【跳转到 01:45】](https://www.bilibili.com/video/BV1aKnb6WEFY/?t=105)。视频还补了一句应用面：现在大模型调用外部工具的底层逻辑，同样依赖这个机制来约束参数格式。

![100% 格式稳定率：不是被祈祷出来的，是被机制保证的](assets/约束解码：把%20JSON%20Schema%20编译成状态机，把非法%20token%20的%20logit%20打成负无穷/00105.webp)

## 四、代价：硬约束不是免费的

视频紧接着说「听着很神，但实际工程落地时水其实很深」，并列出四个必须避开的问题 [【跳转到 01:56】](https://www.bilibili.com/video/BV1aKnb6WEFY/?t=116)：

1. **性能开销**。把复杂的 schema 实时编译成状态机要消耗 CPU，可能导致首次延迟明显增加，用户体验就是「模型回复变慢了」。
2. **模型卡死或逻辑崩坏**。如果 schema 太复杂，或者强制要求模型输出它在当前上下文里推导不出来的内容，模型可能因为概率被强行截断而输出无意义的乱码，甚至陷入死循环 [【跳转到 02:21】](https://www.bilibili.com/video/BV1aKnb6WEFY/?t=141)。这是很多新手容易踩的坑：约束只保证「合法」，不保证「有解」。
3. **动态键值难处理**。如果业务需要用户自定义的键（比如任意标签名），严格的 schema 处理起来就会比较吃力。
4. **上下文占用**。庞大的 schema 本身也要占上下文窗口，不仅增加 API 成本，还容易分散模型对核心任务的注意力。

这四条合起来，正好回答了「约束解码的代价是什么」：它买到的是**形式保证**，付出的是**编译开销、表达力限制、以及可能损害生成质量**。

## 五、工程对策：缓存、代码生成 schema、把思考放在最前面

针对上面的痛点，视频给了一套成熟做法：

- **文法缓存**。在推理引擎端（比如 vLLM）开启 schema 缓存机制，对高频使用的 schema 预编译，把生成的状态机缓存起来，下次请求直接命中缓存，就能把编译延迟降到零 [【跳转到 02:46】](https://www.bilibili.com/video/BV1aKnb6WEFY/?t=166)。
- **用框架定义数据模型，不要手写 schema 字符串**。通常用 pydantic 或类似框架定义数据模型，利用框架自带的方法动态生成 schema 传给大模型，拿到结果后直接反序列化，实现端到端的类型安全。
- **解耦：把「思考过程」放在 schema 最前面**。这是视频里最实用的技巧——在 schema 的最前面预留一个宽松的字符串字段，让模型先在这个字段里做思维链推理、把逻辑理顺，然后再输出后面严格的结构化字段，这能大幅降低模型输出乱码的概率 [【跳转到 03:11】](https://www.bilibili.com/video/BV1aKnb6WEFY/?t=191)。它同时缓解了上面第 2 条痛点：给模型留一块不受约束的「草稿纸」。

![文法缓存的四步：高频 schema 先预编译 → 缓存状态机 → 请求命中直接复用 → 首个 token 不再被拖慢](assets/约束解码：把%20JSON%20Schema%20编译成状态机，把非法%20token%20的%20logit%20打成负无穷/00166.webp)

## 六、最后一道：约束解码保证格式，不保证事实

视频在结尾把边界划得很清楚：**约束解码虽然保证了格式百分百正确，但不能保证业务逻辑没有幻觉**。所以工程上依然需要配合代码的校验器；如果业务校验失败，要把错误信息包装成新的提示词喂给模型，让它进行自我修正 [【跳转到 03:31】](https://www.bilibili.com/video/BV1aKnb6WEFY/?t=211)。

这句话把三种控制方式的分工讲透了：

- **提示词**：说清要什么，靠模型的指令遵循，概率性生效；
- **约束解码**：锁死长什么样，靠状态机 + logit 屏蔽，对文法可描述的部分是形式保证；
- **校验器（生成后）**：检查内容对不对，靠代码规则，能查语义但要付出重试成本。

视频的总结是：靠提示词约束格式已经是过去式，注入 JSON Schema 配合约束解码，把不可控的概率游戏变成可预测、可校验的 API 调用 [【跳转到 03:41】](https://www.bilibili.com/video/BV1aKnb6WEFY/?t=221)。

## 小结

- 「请返回 JSON」是商量，不是约束：模型会加寒暄、套 markdown、改类型，结果不可复现。
- 约束解码把 schema 编译成 FSM 或 CFG，预先定死所有合法状态路径。
- 每步生成前查一次状态机，得到合法 token 集合，把其余 token 的 logit 置为 $-\infty$，softmax 后概率为 0。
- 因此格式稳定率是 100%，但这是「机制保证」而非「模型变强」。
- 代价有四项：编译延迟、强制输出导致乱码甚至死循环、动态键难表达、schema 占用上下文。
- 对策：文法缓存（vLLM 预编译 + 命中缓存）、用 pydantic 定义模型自动生成 schema、在 schema 最前面留一个宽松的思考字段。
- 约束解码只保证格式，业务事实仍需代码校验器，失败时把报错包装成新提示词让模型自修。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| 约束解码 | 生成时只保留符合文法/格式的 token，把其余候选排除出采样空间 |
| 有限状态机（FSM） | 由「当前前缀」决定「下一字符合法集合」的状态图，正则与 JSON 语法都可编译成它 |
| 上下文无关文法（CFG） | 比正则更强的形式文法，能表达嵌套结构，与 FSM 是同一契约的不同表示 |
| 动态词表屏蔽 | 每一步按当前状态重算合法 token 集合，把非法项 logit 置为 $-\infty$ |
| 文法缓存 | 预编译并缓存 schema 对应的状态机，避免每次请求重复编译 |
| 解耦（思考字段） | 在 schema 最前面放一个宽松字符串字段，让模型先推理再输出严格结构 |
| 端到端类型安全 | 用 pydantic 定义模型 → 自动生成 schema → 结果直接反序列化回对象 |
