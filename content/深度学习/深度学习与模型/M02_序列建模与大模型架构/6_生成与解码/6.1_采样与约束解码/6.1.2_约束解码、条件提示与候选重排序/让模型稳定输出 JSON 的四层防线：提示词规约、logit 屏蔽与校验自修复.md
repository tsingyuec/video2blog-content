# 让模型稳定输出 JSON 的四层防线：提示词规约、logit 屏蔽与校验自修复

> 视频来源：[面试官问：大模型如何稳定地输出 JSON？](https://www.bilibili.com/video/BV191TY6KEJX/)（Bilibili · Agent开发实战）｜时长约 5 分 36 秒
> 导读：这支视频用「面试答题」的口吻，把「让大模型稳定输出 JSON」拆成一条从软约束到硬约束、再到工程兜底的防线。它讲清了三件事：为什么 next-token 机制注定会丢括号；约束解码（logit masking）到底把什么置成了负无穷；以及为什么格式 100% 之后仍然需要 pydantic 校验。本文按四层防线整理，并在最后把「提示」「约束解码」「生成后校验」三种控制方式的保证强度与代价放在一张表里比较。

## 本讲要解决的核心问题（SCQA）

**背景**：Agent 调工具时，模型的输出要直接喂给下游解析器。JSON 少一个逗号、引号没闭合，整条调用链就崩。

**冲突**：很多人对这个问题的回答只有一句「写好 prompt」。但 prompt 是自然语言，模型听不听、听多少，取决于它的指令遵循能力；而模型是一个 token 一个 token 往外写的，它在写左花括号的那一刻，并不承诺后面一定会补上右花括号 [【跳转到 00:22】](https://www.bilibili.com/video/BV191TY6KEJX/?t=22)。

**疑问**：如果不能靠「请」,那靠什么？把约束下沉到解码器之后，是不是就彻底安全了？

**回答（中心思想）**：视频的主张是「用确定的软件工程防线，去包裹非确定的生成模型」，具体是四层：**提示词规约（软约束）→ 生成控制（原生 structured outputs 或 logit masking 硬拦截）→ 工程校验与自修复 → SFT 训练态兜底**。前三层解决「格式」，第四层把确定性从工程兜底提升到模型本能；而即便格式做到 100%，**业务逻辑的幻觉仍然要靠代码校验器** [【跳转到 04:56】](https://www.bilibili.com/video/BV191TY6KEJX/?t=296)。

## 一、病根：为什么连个花括号都闭合不了

视频把原因归到三个维度 [【跳转到 00:22】](https://www.bilibili.com/video/BV191TY6KEJX/?t=22)：

1. **next token 机制**。模型是概率性的文字接龙，每吐一个 token 只看下一个词的概率，脑子里没有语法树，不知道左花括号一定要配右花括号，它只是觉得「这时候该出个引号」，并不承诺一定闭合。
2. **RLHF 的副作用**。模型被训练得太礼貌，拿到指令总想先客气一句「好的，这是为您准备的数据」，这直接炸掉下游的 JSON 解析器。
3. **token 编码分布**。花括号、引号在词表里的编码权重不稳，当生成序列异常、注意力一散，括号就容易丢。

![三个病根：Next Token 机制（无语法树）、RLHF 副作用（礼貌寒暄）、Token 权重漂移（长序列注意力分散导致标点丢失）](assets/让模型稳定输出%20JSON%20的四层防线：提示词规约、logit%20屏蔽与校验自修复/00022.webp)

本质就一句话：**大模型的随机性是稳定性最大的天敌**。我们要的不是「大概率正确」，而是「绝对确定」——所以不能靠模型的灵光一闪，必须用确定性的工程防线去包裹它 [【跳转到 00:47】](https://www.bilibili.com/video/BV191TY6KEJX/?t=47)。

## 二、第一层：提示词规约（语义软约束）

这是成本最低、见效最快的防线，但绝不是喊一句「请输出 JSON」就完了 [【跳转到 01:17】](https://www.bilibili.com/video/BV191TY6KEJX/?t=77)。具体做法：

- **Schema 注入 + Few-Shot**：直接把 TypeScript 接口或标准 JSON Schema 糊在 prompt 里，把字段名、类型、是否必填都写死，同时给两到三个真实填充范例。视频的说法是「模型是视觉动物」，看到样例才知道数字不能带单位、布尔不能写字符串。
- **利用近因效应（recency effect）**：大模型有记性但容易丢三落四，上下文越长越容易忘掉开头的格式要求。所以要把「仅输出 JSON，禁止任何解释、寒暄、markdown 标记」这种严厉指令放在 prompt 的**最后 100 个 token** 里。
- **用 XML 标签把输出区域框死**：解析时直接按标签提取，稳得多 [【跳转到 02:07】](https://www.bilibili.com/video/BV191TY6KEJX/?t=127)。

![第一层防线的两块拼图：Schema 注入 + Few-Shot，以及把严厉指令放在末尾并用 XML 标签定界](assets/让模型稳定输出%20JSON%20的四层防线：提示词规约、logit%20屏蔽与校验自修复/00077.webp)

视频给这一层的定量估计是：**能兜住大概 60% 的基础问题**。这个数字是讲者的经验值，但它准确传达了这一层的性质——**概率性改善，不是保证**。

## 三、第二层：生成控制，把约束放进解码

如果第一层还是偶尔翻车，就得上「物理手段」，视频把它叫生成控制，分两条路线 [【跳转到 02:18】](https://www.bilibili.com/video/BV191TY6KEJX/?t=138)。

### 3.1 路线一：闭源 API 的原生 structured outputs

主流接口不仅提供 JSON mode，还演进出了更严格的 structured outputs：它在**解码阶段**就把你定义的 schema 预编译到推理引擎里，像给火车铺了死铁轨，模型想跑偏都没机会，格式遵循率接近百分之百 [【跳转到 02:23】](https://www.bilibili.com/video/BV191TY6KEJX/?t=143)。能用原生能力就不自己折腾，这一层再吃掉 20% 的问题。

### 3.2 路线二：开源模型私有化部署，自己做 logit masking

这里才是真正拉开差距的地方：借助 outlines、guidance 等库构造一个**有限状态机**，实时控制解码。在模型预测下一个 token 的概率分布时，状态机根据当前 JSON 语法状态算出允许出现的合法字符集合（比如现在该写双引号了），然后把**词表中所有非法 token 的概率直接置为负无穷** [【跳转到 02:48】](https://www.bilibili.com/video/BV191TY6KEJX/?t=168)。

![第二层防线的两条路线：闭源 API 把 schema 预编译进推理引擎；开源部署用 FSM 算出合法集合，把非法词概率置为负无穷](assets/让模型稳定输出%20JSON%20的四层防线：提示词规约、logit%20屏蔽与校验自修复/00168.webp)

用公式写出来，就是每一步在 logits 上加一个掩码 $m_t \in \{0, -\infty\}^{|V|}$：

$$
\text{logits}'_t = \text{logits}_t + m_t, \qquad
m_t[i] =
\begin{cases}
0, & \text{若 token } i \text{ 在当前语法状态下合法} \\
-\infty, & \text{否则}
\end{cases}
$$

再做 softmax，非法 token 的概率就是 $e^{-\infty}=0$，永远不会被采样到：

$$
p_t(i) = \frac{\exp(\text{logits}'_t[i])}{\sum_j \exp(\text{logits}'_t[j])}
$$

视频把这种「基于逻辑掩码的解码」称为**从数学上杜绝幻觉**：哪怕是 7B 小模型也能输出百分百合法的 JSON，解码层硬拦截把格式正确率做到百分之百 [【跳转到 03:13】](https://www.bilibili.com/video/BV191TY6KEJX/?t=193)。

注意这里「100%」的准确含义：它保证的是**输出属于该文法定义的语言**，也就是形状合法；它不保证字段值符合业务事实。这一点视频在第三、四层反复强调。

## 四、第三层：工程校验与自修复（容错自愈）

成熟的架构师永远假设模型会出错，所以必须兜底 [【跳转到 03:13】](https://www.bilibili.com/video/BV191TY6KEJX/?t=193)。流程是：

1. 拿到模型输出后，立刻用 **pydantic** 做字段级校验：字段全不全、类型对不对。
2. 对于缺括号、多余逗号这类微小格式瑕疵，先用 **json_repair** 这类自动修复库抢救一把。
3. 如果校验失败，**千万别只是简单重试**：要把 pydantic 或解析器的具体报错信息原封不动地喂回模型，告诉它「你刚才输出的内容里这个地方写错了，请根据这个错误信息重新输出一份完整的正确结果」。大模型最擅长的就是纠错和改写，通常反思一次就能完全修正 [【跳转到 03:38】](https://www.bilibili.com/video/BV191TY6KEJX/?t=218)。
4. 对超长结构还可以上**流式解析**：边吐 token 边校验，一旦发现键名写错就立即中断生成并重来，大幅节省 token 和响应时间 [【跳转到 04:03】](https://www.bilibili.com/video/BV191TY6KEJX/?t=243)。

![第三层的闭环：大模型生成 → pydantic 强校验（失败先 json_repair 抢救）→ 校验通过则放行，否则把报错原封不动喂回模型做 self-correction](assets/让模型稳定输出%20JSON%20的四层防线：提示词规约、logit%20屏蔽与校验自修复/00218.webp)

这一层与前两层的分工很清楚：前两层让「不该出现的字符不出现」，这一层处理「出现了但内容不对」以及「约束之外的业务规则」。它也是三种控制方式里唯一能检查**语义**的一层。

## 五、第四层：训练态终极手段（SFT）

面对 schema 极复杂、对延迟要求极高、或者需要大批量稳定产出的场景，可以直接走 SFT 监督微调：用目标 schema 构造海量高质量训练对，让模型形成「肌肉记忆」，只要看到特定指令就条件反射式吐出严格格式的结果 [【跳转到 04:19】](https://www.bilibili.com/video/BV191TY6KEJX/?t=259)。

![第四层：用目标 schema 构造海量问答对做 SFT，让「见指令即输出严格格式」变成条件反射](assets/让模型稳定输出%20JSON%20的四层防线：提示词规约、logit%20屏蔽与校验自修复/00259.webp)

视频对它的定位是「确定性从工程兜底上升到了模型本能」。代价也很明显：需要训练数据、需要重训周期，而且它改变的是模型的倾向，仍然不是形式化保证——真正要 100%，还是得回到第二层的解码约束。

## 六、四层叠起来：一张图与三种控制方式的比较

![四层防线的组合：Schema Prompt + Few-Shot、Structured Outputs、Logit Masking、Pydantic 校验 + 反馈自修复，合起来把格式错误率压到 0.1% 以下](assets/让模型稳定输出%20JSON%20的四层防线：提示词规约、logit%20屏蔽与校验自修复/00296.webp)

视频给出的组合拳是：**提示词给 schema 和样例 → API 开 structured output → 推理端加概率掩码约束解码 → 工程端见错反馈的自修复重试**，这套方案做下来足以把格式错误率压到 0.1% 以下 [【跳转到 04:56】](https://www.bilibili.com/video/BV191TY6KEJX/?t=296)。

把三种控制方式按「保证强度」和「代价」拆开对比：

| 控制方式 | 在哪一步起作用 | 保证强度 | 主要代价 | 视频里的定位 |
| --- | --- | --- | --- | --- |
| 提示词规约（schema + few-shot + 末尾指令 + XML 定界） | 生成之前，靠模型遵循 | 概率性，约 60% 基础问题 | 几乎为零；但占上下文、要调 prompt | 成本最低、见效最快的软约束 |
| 约束解码（structured outputs / logit masking） | 生成之中，逐步过滤候选 | 形式上 100% 合法（只对文法可描述的部分） | 需要 schema、要接推理引擎、闭源 API 只能被动依赖 | 硬拦截，从数学上杜绝格式幻觉 |
| 生成后校验与自修复（pydantic + json_repair + 报错回喂） | 生成之后，检查与重试 | 只对写出来的规则有效，但能查语义 | 多一次调用/多一轮延迟、要维护校验器 | 兜底，假设模型一定会错 |

三者的关系不是替代而是**串联**：提示负责「说清要什么」，约束负责「锁死长什么样」，校验负责「确认内容对不对」。任何一层单独用都不够——只靠提示会漏，只靠约束会「格式对、内容错」，只靠校验则要承担重试成本。

> **本文边界**：这支视频的控制手段止于「单条输出的校验与重试」，没有讨论「生成 N 个候选再打分挑选」这类候选重排序（best-of-N / rerank）的做法。后者与第三层同属「生成后控制」，但需要额外的打分器与预算分配，不在本视频范围内，本文不作展开。

## 小结

- 丢括号不是模型「不会 JSON」，而是 next-token 机制 + 礼貌性寒暄 + 长序列标点漂移共同造成的。
- 第一层提示词规约要写足三件事：schema 注入、真实范例、把严厉指令放在末尾并用 XML 定界。
- 第二层才是硬约束：闭源 API 用 structured outputs，开源部署用 FSM + logit masking，把非法 token 的概率置为负无穷。
- logit masking 的保证是「输出属于该文法」，等价于形状 100% 合法，与内容正确无关。
- 第三层假设模型一定会错：pydantic 校验、json_repair 抢救、把报错原封不动回喂让模型自修复，超长输出用流式解析提前中断。
- 第四层 SFT 把确定性训练进模型，用于 schema 复杂、延迟敏感、大批量产出的场景。
- 四层叠加的目标是把格式错误率压到 0.1% 以下；而业务正确性永远需要代码校验器。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| next token 机制 | 模型每次只根据已生成前缀预测下一个 token 的概率，没有全局语法结构的概念 |
| 近因效应（recency effect） | 上下文末尾的内容对生成影响更大，所以关键指令要放在最后 |
| Structured Outputs | 厂商提供的「按 JSON Schema 输出」能力，在解码阶段强制遵守 |
| Logit Masking | 在 softmax 之前给非法 token 的 logit 加 $-\infty$，使其概率为 0 |
| FSM（有限状态机） | 把正则/schema 编译成「当前前缀 → 允许的下一字符集合」的状态图 |
| json_repair | 修补缺括号、多余逗号等小瑕疵的自动修复库 |
| pydantic | Python 数据校验库，用类型声明做字段级校验与反序列化 |
| Self-Correction | 把校验器的报错原样喂回模型，让它重新生成正确结果 |
| SFT | 监督微调，用目标格式的高质量样本训练模型形成固定输出习惯 |
