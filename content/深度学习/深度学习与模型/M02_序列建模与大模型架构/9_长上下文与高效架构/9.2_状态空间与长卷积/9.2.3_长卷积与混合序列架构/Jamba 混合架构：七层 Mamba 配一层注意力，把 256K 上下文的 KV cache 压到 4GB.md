# Jamba 混合架构：七层 Mamba 配一层注意力，把 256K 上下文的 KV cache 压到 4GB

> 视频来源：[Jamba开源模型性能超越 Mixtral8x7B 采用最先进混合架构](https://www.bilibili.com/video/BV1Yx4y1v7PW/)（B 站 · 小工蚁创始人 · 时长约 10 分钟）
> 本文基于视频演说图文稿整理，配图截自视频。讲者是逐页翻 Jamba 论文讲的：先摆出"纯注意力贵、纯 Mamba 省但会丢东西"这两笔账，再给出 1:7 的层间配比、MoE 的稀疏激活，最后用 KV cache 体积、吞吐曲线和"为什么混合有效"的对照表收尾。字幕里的"肩膀/歼八"是 Jamba，"MANA/member/M8"是 Mamba，"mixture"是 Mixtral，本文已统一改正。

## 本讲要解决的核心问题（SCQA）

**背景**：Transformer 靠自注意力把任意两个位置直接连起来，所以输出质量好；代价是推理时要为每个 token 存一份 K 和 V（KV cache），上下文越长，这份缓存越大，长上下文推理既吃显存又吃带宽。

**冲突**：Mamba 这类状态空间模型把历史压进一个固定大小的隐状态，显存不随长度涨、吞吐也高，但"选择性存储"意味着它只留一部分信息，遇到需要精确回忆或严格照格式作答的任务就会掉链子。两条路各有一个致命短板：一个贵，一个丢。

**疑问**：能不能不让它们二选一——大部分层用便宜的那条路，少数层用贵但精确的那条路，把两种能力拼在一个模型里？

**回答（中心思想）**：Jamba 就是这么做的：**每 8 层里 7 层是 Mamba、1 层是完整注意力**（$a{:}m=1{:}7$），再叠上 MoE 稀疏激活，得到 52B 总参数、12B 激活参数。结果是 256K 上下文下 KV cache 只要 4GB（Mixtral 8x7B 同样 256K 要 32GB，8 倍差距），长上下文吞吐约为同级 Transformer 的 3 倍，单张 80GB 卡能撑 140K 上下文；而"混合比纯 Mamba 强在哪"的证据也很直白——纯 Mamba 在 IMDB/QuAC/NarrativeQA 上大幅落后，混合后基本追平纯注意力。

## 一、先算清两条路的账

### 1.1 Transformer：质量好，是因为"全部存储"

讲者把差异压成一句话：Transformer 有自注意力机制，输出质量比较好，但它需要的资源比较多、效率比较差。资源花在哪？花在**把每个 token 的 K/V 都留在显存里**——这就是 KV cache。上下文翻倍，缓存跟着线性涨，长上下文推理的瓶颈往往不是算力而是这份缓存的体积与搬运 [【跳转到 02:05】](https://www.bilibili.com/video/BV1Yx4y1v7PW/?t=125)。

![Jamba 论文首页对三种架构的定位：Transformer 质量最高但吞吐与显存差，Mamba 吞吐与显存好但质量弱，Jamba 三项都打勾](assets/Jamba%20混合架构：七层%20Mamba%20配一层注意力，把%20256K%20上下文的%20KV%20cache%20压到%204GB/00150.webp)

这张表是整支视频的提纲：三列是三种架构，三行是"最高输出质量 / 高吞吐 / 低显存占用"。Transformer 只在第一行有勾，Mamba 只在后两行有勾，Jamba 三行都有勾。**混合架构的目标不是折中，而是同时拿三项**。

### 1.2 Mamba：省，是因为把历史压进一个隐状态

Mamba 的架构更像 RNN 那一路：它把一个中间状态保持起来，也就是隐状态 $h$，把历史信息存进一个矩阵里，因此**不需要把原来的 token 重新算一遍**。

$$
h_t = A_t h_{t-1} + B_t x_t,\qquad y_t = C_t h_t
$$

这里 $A_t,B_t,C_t$ 随输入变化（这就是"选择性"，递推细节见 [§9.2.2 选择性状态空间模型](../../../README.md#m02-9-2-2)），所以 $h_t$ 是一个**固定大小**的状态，不随序列长度增长——显存占用恒定，这就是它省的原因 [【跳转到 03:59】](https://www.bilibili.com/video/BV1Yx4y1v7PW/?t=239)。

但讲者紧接着点出它的两个代价：

- **并行能力不如 Transformer**：RNN 式地依赖中间状态，每一步都要算，状态又是全局的，所以并行度受限（Mamba 用并行扫描缓解，但这是工程层面的补救）。
- **选择性存储会丢东西**：Transformer 是"全部都存储"，Mamba 是"有选择地存储"，被丢掉的信息就真没了，于是模型性能会受影响。

一句话总结这两条路：**注意力用显存换精确，Mamba 用精确换显存。**

## 二、Jamba 的拼装方式：1:7 的层间配比 + MoE

### 2.1 七层 Mamba 夹一层注意力

Jamba 由 AI21 推出，名字来自 Joint Attention and Mamba。它的做法是把两种层**交替排布**，比例是 $a{:}m=1{:}7$——注意力层与 Mamba 层的比例为 1 比 7，也就是"大部分层走便宜的路，少数层保留精确回忆" [【跳转到 05:45】](https://www.bilibili.com/video/BV1Yx4y1v7PW/?t=345)。

![Jamba 的实现配置：4 个 Jamba block，每个 block 8 层，注意力与 Mamba 层按 1:7 排布，MoE 每两层替换一次 MLP，共 16 个专家、每个 token 取 top-2](assets/Jamba%20混合架构：七层%20Mamba%20配一层注意力，把%20256K%20上下文的%20KV%20cache%20压到%204GB/00418.webp)

论文给出的具体配置是：模型由 **4 个 Jamba block** 组成，每个 block 有 $l=8$ 层，其中注意力层与 Mamba 层的比例是 $a{:}m=1{:}7$；MoE 每隔 $e=2$ 层替换一次普通 MLP，共 $n=16$ 个专家，每个 token 只激活 $K=2$ 个。这个 1:7 的比例是消融实验选出来的——在质量相近的几种配置里它最省算力。

讲者的口头版本略有出入（说成"八个层构成的块、16 个专家、每个 token 两个专家"），与幻灯片上的 $l=8$、4 个 block 对照着看就清楚了：**8 是每个 block 的层数，不是整个模型的层数**。

### 2.2 顺便叠一层 MoE

Jamba 的第二个正交设计是 MoE：总参数 52B，每个 token 只激活 12B。这样做有两个好处：一是**单卡装得下**（论文明确说这个配置是为了塞进一张 80GB 显卡），二是 MoE 只搬运被激活的那部分权重，配合 Mamba 层本来就小的缓存，长上下文推理的显存压力进一步下降 [【跳转到 06:33】](https://www.bilibili.com/video/BV1Yx4y1v7PW/?t=393)。

![论文对 Jamba 的一句话定位：52B 总参数、12B 激活参数，设计目标是装进单张 80GB GPU](assets/Jamba%20混合架构：七层%20Mamba%20配一层注意力，把%20256K%20上下文的%20KV%20cache%20压到%204GB/00345.webp)

## 三、混合到底省下了什么：三组硬指标

### 3.1 KV cache：256K 上下文下 4GB vs 32GB

这是最能说明问题的一组数字。因为只有那 1/8 的注意力层需要缓存 K/V，其余 Mamba 层只保留固定大小的状态，所以**缓存体积直接按注意力层的比例缩水** [【跳转到 06:08】](https://www.bilibili.com/video/BV1Yx4y1v7PW/?t=368)。

![论文 Table 1：同样 256K 上下文、16bit 精度下，LLaMA-2 6.7B 需要 128GB KV cache，Mistral 7.2B 与 Mixtral 8x7B 需要 32GB，Jamba 只要 4GB](assets/Jamba%20混合架构：七层%20Mamba%20配一层注意力，把%20256K%20上下文的%20KV%20cache%20压到%204GB/00368.webp)

| 模型 | 可用参数 | 激活参数 | KV cache（256K 上下文，16bit） |
| --- | --- | --- | --- |
| LLaMA-2 | 6.7B | 6.7B | 128GB |
| Mistral | 7.2B | 7.2B | 32GB |
| Mixtral | 46.7B | 12.9B | 32GB |
| Jamba | 52B | 12B | 4GB |

Mixtral 8x7B 的激活参数（12.9B）和 Jamba（12B）几乎一样，但 256K 上下文的缓存差了 8 倍。**参数规模相当，缓存却差一个量级**——差别不在参数，在层类型。

### 3.2 吞吐：长上下文约为同级 Transformer 的 3 倍

![论文的端到端吞吐曲线：横轴是上下文窗口（1K 到 128K），Jamba 在长上下文端明显高于 Llama-2 70B 与 Mixtral 8x7B，128K 处约 3 倍](assets/Jamba%20混合架构：七层%20Mamba%20配一层注意力，把%20256K%20上下文的%20KV%20cache%20压到%204GB/00200.webp)

曲线在 8K 之前三条线差不多，过了 32K 开始分叉，到 128K 时 Jamba 约为对照模型的三倍。讲者的解释是：Mixtral 8x7B 到 64K 基本就跑不动了（out of memory），滑动窗口方案虽然比原生注意力省一点，但和 Jamba 比仍差三倍左右 [【跳转到 03:20】](https://www.bilibili.com/video/BV1Yx4y1v7PW/?t=200)。

### 3.3 单卡容量：80GB 卡上 140K 上下文

在 80GB 的 GPU 上做推理，Jamba 可以做到 140K 上下文 token，而对照的 Transformer 模型只能到 16K 量级。这个差距直接决定"能不能一次性读完一整份长文档"：讲者提到 256K 上下文相当于二十多万中文字符，可以整篇放进模型推理，不用切分——**切分本身就会破坏跨段的语义连贯** [【跳转到 03:45】](https://www.bilibili.com/video/BV1Yx4y1v7PW/?t=225)。

### 3.4 长上下文能力有没有被牺牲：大海捞针

省了显存，会不会把长上下文能力也省掉了？讲者用"大海捞针"（needle-in-a-haystack）来检验：在一大段无关文本里藏一句话，再问模型那句话是什么，看它能不能捞出来 [【跳转到 07:46】](https://www.bilibili.com/video/BV1Yx4y1v7PW/?t=466)。

![论文 5.2.1 节：Jamba 在 needle-in-a-haystack 上表现很好，而它的实现只用了 4 个注意力层](assets/Jamba%20混合架构：七层%20Mamba%20配一层注意力，把%20256K%20上下文的%20KV%20cache%20压到%204GB/00471.webp)

讲者给的结论是：128K 之内几乎百分之百准确，虽然有些误差，但准确度仍然很高。幻灯片补了一句关键限定——**整个模型只有 4 个注意力层**（$4\times8=32$ 层里的 4 层），这说明"少量精确层 + 大量线性层"的组合足以撑住检索类任务。

## 四、为什么必须混合，而不是纯 Mamba

如果纯 Mamba 又省又准，就没必要混合了。视频里最关键的证据是一张对照表：同样 1.3B 参数、同样训练 250B token，比较纯注意力、纯 Mamba、注意力-Mamba 混合三种模型 [【跳转到 08:32】](https://www.bilibili.com/video/BV1Yx4y1v7PW/?t=512)。

![论文 Table 6：纯 Mamba 在 IMDB、QuAC、NarrativeQA 上大幅落后，混合模型基本追平纯注意力](assets/Jamba%20混合架构：七层%20Mamba%20配一层注意力，把%20256K%20上下文的%20KV%20cache%20压到%204GB/00512.webp)

| 模型 | IMDB | QuAC | NarrativeQA |
| --- | --- | --- | --- |
| Attention | 84.1 | 27.9 | 45.8 |
| Mamba | 48.8 | 20.2 | 27.7 |
| Attention-Mamba | 90.9 | 26.6 | 43.7 |

纯 Mamba 在通用困惑度上表现还不错，但在这三个任务上明显落后。论文进一步查了原因：**纯 Mamba 经常不遵守答案格式**。IMDB 的选项只有 Positive / Negative，注意力模型会老实回答这两个词，纯 Mamba 却会输出 "Very Good"、"Very Positive"、"Funny"、"3/10" 这类答案——意思可能对，但格式不对，评测就判错。

这暴露了纯状态空间模型的一个真实短板：**它擅长"续写"，不擅长"照格式做事"**。而要在上下文里学会"输入-输出格式"这种模式，需要能精确回看前文的注意力层。所以混合不是性能折中，而是**能力互补**：Mamba 层负责便宜地处理长程信息，注意力层负责精确回忆与格式遵循 [【跳转到 04:49】](https://www.bilibili.com/video/BV1Yx4y1v7PW/?t=289)。

## 五、边界与后续

讲者没有回避这套方案的局限：

- **语言覆盖**：这个模型目前主要支持英文，对中文支持力度不好。
- **上下文还没到目标**：目前发布的是 25 万 token 级别，而"一兆"（100 万）级别的上下文是下一步目标，还差约四倍。讲者判断，如果按 Jamba 这种混合思路继续放大，长上下文能力会更强、所需资源更少。
- **多卡协同**：单卡 140K 之外，多块 GPU 做上下文协同还能继续扩展，这部分要靠已有的上下文并行机制 [【跳转到 09:35】](https://www.bilibili.com/video/BV1Yx4y1v7PW/?t=575)。

他的判断是：这种"Transformer + Mamba"的混合路线会成为一个趋势，国内厂商很快会跟进复刻，把这种结构吸收消化成自己的模型 [【跳转到 09:18】](https://www.bilibili.com/video/BV1Yx4y1v7PW/?t=558)。

## 小结

- **两条路的本质差异在"存什么"**：注意力把每个 token 的 K/V 都存下来（精确但贵），Mamba 把历史压进固定大小的隐状态（省但会丢）。
- **Jamba 用层间配比把两种能力拼起来**：$a{:}m=1{:}7$，4 个 block、每 block 8 层，再叠 16 专家 top-2 的 MoE，得到 52B 总参数 / 12B 激活参数。
- **省下来的主要是 KV cache**：256K 上下文下 Jamba 4GB，Mixtral 8x7B 32GB，LLaMA-2 6.7B 128GB；参数相当而缓存差 8 倍。
- **吞吐与容量同步改善**：长上下文吞吐约为同级 Transformer 的 3 倍，单张 80GB 卡可跑 140K 上下文。
- **混合的正当性来自纯 Mamba 的失败**：IMDB/QuAC/NarrativeQA 上纯 Mamba 大幅落后，原因是它不遵守输出格式；混合后基本追平纯注意力。
- **这条路线后来被更广泛地复用**：混合的对象可以是 Mamba，也可以是线性注意力/门控增量网络，配方都是"多数线性层 + 少数完整注意力层"。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| 混合序列架构（hybrid） | 同一模型里混用两类层（如注意力层与状态空间层），按比例交替堆叠 |
| KV cache | 推理时缓存历史 token 的 K/V，避免重算；体积随上下文长度线性增长 |
| 状态空间模型（SSM） | 用固定大小的隐状态 $h_t$ 递推地压缩历史，显存不随长度增长 |
| 选择性（selective） | 状态转移矩阵随输入变化，模型可以"按内容决定记什么、忘什么" |
| 并行扫描（parallel scan） | 把递推式状态更新改写成可并行的前缀计算，弥补 RNN 的串行劣势 |
| MoE（混合专家） | 每层放多个专家网络，每个 token 只激活其中少数几个，参数多但算得少 |
| 激活参数 | 单次前向真正参与计算的参数量，决定算力与带宽开销 |
| 大海捞针（needle-in-a-haystack） | 在长文本中藏一句话再让模型找回，用来测长上下文检索能力 |
| 层间混合 vs 层内混合 | 前者按层交替（Jamba），后者在同一层内拆注意力头（如部分头走线性） |
