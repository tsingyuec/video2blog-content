# GQA 的形状账：KV 头数从 H 缩到 G，读时用 repeat_interleave 广播回 H

> 视频来源：[Grouped-Query Attention (GQA) | The KV Cache Is the Real Bottleneck | 20-Min Deep Dive](https://www.youtube.com/watch?v=UHCaG8g7Vpw)（YouTube · 逐行推导 GQA 原论文的讲解）
> 本文基于视频演说图文稿整理，配图截自视频。字幕里的 `cache` 曾被识别成 `cash`，正文按上下文订正。

## 本讲要解决的核心问题（SCQA）

**背景**：大模型生成文字时一次只出一个 token，而这个 token 的 query 必须回头看前面所有 token。为了不每步重算历史，我们把这些 token 的 key 和 value 缓存下来——这就是 KV Cache（键值缓存）。它按「每个 token、每层、每个 KV 头、每个头维度」存放，写一次，之后每一步都读。

**冲突**：这份缓存不是「大一点」那么简单，它每一步都要整块重读一遍。按 Llama-2-70B 的形状、一个 4000 多 token 的会话、半精度来算，一次对话就要 10 GiB，32 路并发就是 320 GiB——比四张 H100 的显存还多，而这些卡只是在「记事」。更糟的是，把它当容量问题去解决是错的：瓶颈是带宽，不是显存。

**疑问**：字节公式里到底哪一项可以动？动了之后张量形状怎么变？广播（broadcast）回多头形状这一步怎么写才不出错？

**回答（中心思想）**：**公式里唯一没人动过的是 KV 头数 $h_{kv}$；把 $h_{kv}$ 从 query 头数 $H$ 改成组数 $G$，缓存就缩到 $1/G$，读的时候沿头轴用 `repeat_interleave` 把它扩回 $H$ 份。** 注意力的浮点运算量一点没变，变的只是搬进来的字节数，于是算术强度从 1 flop/byte 变成 $H/G$。这就是 GQA（Grouped-Query Attention，分组查询注意力）的全部形状账。

---

## 一、KV 缓存是一张写一次、读几千次的草稿纸

生成的时候，一次前向只产出一个 token；这个 token 的 query 要和它之前所有 token 的 key 做点积，再把对应的 value 加权求和。每一步都把历史 K/V 重算一遍是「二次方级别的疯狂」，所以做法是：token 第一次出现时算一次 key 和 value，然后永远留着——**写一次，之后每一步都读** [【跳转到 01:13】](https://www.youtube.com/watch?v=UHCaG8g7Vpw&t=73)。

这听起来是纯赚的，直到你把「读」的次数数清楚：第 1 步只读 1 个 token 的量，第 1000 步要读 1000 个 token 的量。也就是说，缓存不只是占地方，它被**整块反复重读**几千次；每生成一个词，都要把整段历史从显存里拖过总线 [【跳转到 01:38】](https://www.youtube.com/watch?v=UHCaG8g7Vpw&t=98)。

![讲者把 KV 缓存的字节数写成一行公式：2 × h_kv × d × 2B × L × T × B，并代入 Llama-2-70B 的 MHA 假设形状](assets/GQA%20的形状账：KV%20头数从%20H%20缩到%20G，读时用%20repeat_interleave%20广播回%20H/00173.webp)

## 二、字节公式：只有头数那一项是自由的

对一个 token 的一层来说，要存一份 key 和一份 value，所以先乘 2；每个 KV 头各有一根长度为 $d$ 的向量，所以再乘 $h_{kv} \times d$；半精度下每个数字 2 字节，于是得到：

$$
\text{KV bytes} = 2 \times h_{kv} \times d \times 2 \times L \times T \times B
$$

其中 $L$ 是层数、$T$ 是 token 数、$B$ 是批大小。代入 Llama-2-70B 的形状（但**假装它用的是普通多头注意力**）：64 个头、头维度 128，于是每个 token 每层是 $2 \times 64 \times 128 \times 2 = 32$ KiB；乘 80 层是 2.5 MiB 一个 token；乘 4096 个 token 是 **10 GiB**；再乘 32 路并发是 **320 GiB**。

值得注意的是公式里**缺席**的东西：hidden size、前馈层宽度、参数总量，一个都没出现。缓存是模型的另一张账单，而且这张账单会随着对话变长而长大。

## 三、每次搬 4 字节只换来 4 次浮点：这是带宽问题，不是容量问题

10 GiB 听起来像「装不装得下」的问题，但讲者强调它是「读得多快」的问题。算一下：在注意力这一步，每个 query 头对每个被缓存的元素做 2 次乘加——一次是跟 key 的点积，一次是往 value 的加权求和，合 4 次浮点运算；而要拿到这 4 次运算，多头注意力下要搬来 1 个 key 元素加 1 个 value 元素，半精度共 4 字节。**4 次浮点除以 4 字节，正好 1 flop/byte。**

把这个数字和硬件的胃口放在一起看：A100 大约需要 150 flops/byte 才能让算术单元不挨饿，H100 更接近 300。你只给得起 1。于是解码阶段的矩阵乘法单元有 99% 以上时间是闲置的——你不是在算，是在等 [【跳转到 02:53】](https://www.youtube.com/watch?v=UHCaG8g7Vpw&t=173)。

内存受限内核的常规解法是批处理：权重只载入一次，给 32 条序列复用，flops/byte 直接涨 32 倍。这对权重矩阵效果极好，**但对 KV 缓存一点用都没有**：每条序列都有自己的缓存，batch 翻倍就是字节翻倍、浮点也翻倍，比值纹丝不动，永远停在 1 flop/byte。批处理救得了前馈层，救不了注意力 [【跳转到 03:43】](https://www.youtube.com/watch?v=UHCaG8g7Vpw&t=223)。

## 四、公式里能动的那一项：把 KV 头数从 $H$ 改成 $G$

既然瓶颈锁死了，就逐个排除公式里的项：层数少一点是换一个模型；每个数字用更少字节是量化（跟这件事正交，本来也该做）；上下文短一点不是优化，是投降。排除完毕，只剩一个没人碰过的项——**KV 头的数量** [【跳转到 04:33】](https://www.youtube.com/watch?v=UHCaG8g7Vpw&t=273)。

在普通多头注意力里，三个投影矩阵都把模型维度映射到 $H \cdot d$，reshape 之后 query、key、value 的形状都是「序列 × $H$ × $d$」，第 7 个头的 query 只会遇见第 7 个头的 key，也就是 $H$ 个并排的小注意力问题，各自拿一份私有的历史切片。而缓存里的头数之所以等于 $H$，纯粹是历史原因：最早有人把它和 query 头数绑在一起，随后两年没人想过解开。2019 年 Noam Shazeer 把它解开了，那篇论文的副标题大意就是「一个写头就够」[【跳转到 05:23】](https://www.youtube.com/watch?v=UHCaG8g7Vpw&t=323)。

![多查询注意力：8 个 query 头全部指向同一个共享的 key 与 value，投影矩阵从 d_model × H·d 缩到 d_model × d](assets/GQA%20的形状账：KV%20头数从%20H%20缩到%20G，读时用%20repeat_interleave%20广播回%20H/00373.webp)

这就是 MQA（Multi-Query Attention，多查询注意力）：保留全部 $H$ 个 query 头（它们仍然在问不同的问题），但 key/value 投影从 $d_{model} \times H d$ 缩成 $d_{model} \times d$，只剩一个 key 头、一个 value 头。缓存张量直接**少掉一整根轴**，变成 $[B, S, d]$ 再乘 2，是原来的 $1/H$；64 个头的模型就是 64 倍的流量削减，算术强度从 1 flop/byte 升到 64 [【跳转到 05:48】](https://www.youtube.com/watch?v=UHCaG8g7Vpw&t=348)。

代价是实实在在的。那 $H$ 个 key 头不是装饰，它们是模型对「什么值得被检索」的 $H$ 种不同意见；塌成 1 个之后，每个 query 头都只能审同一份「历史的摘要」。query 头仍然各不相同，所以不是全盘皆输，但 key 是索引，你把 64 个索引换成了 1 个，容量下降，测出来的质量跟着下降 [【跳转到 06:13】](https://www.youtube.com/watch?v=UHCaG8g7Vpw&t=373)。更糟的一点很少出现在摘要表里：它会让训练不稳——作者从头训 MQA 模型时看到预训练反复出现尖峰，微调后的模型在长输入任务上直接崩，以至于他们要把三次微调的结果取平均才敢报一个诚实的数字。还有一个更隐蔽的成本：跨芯片切分时，标准布局会把那唯一一组 KV 头**复制到每个分区**，一部分节省就这样悄悄蒸发——这一点作者没有藏，写在附录里 [【跳转到 07:03】](https://www.youtube.com/watch?v=UHCaG8g7Vpw&t=423)。

## 五、GQA 把「开关」变成「旋钮」：把 $H$ 个 query 头排成 $G$ 组

为什么要在这两个极端里二选一？把 $H$ 个 query 头排成 $G$ 组：组内所有头共享一个 key 头和一个 value 头，每组各有一套。缓存访问就从 $H$ 变成 $G$。$G = H$ 时每个头都有自己的一对，那就是多头注意力；$G = 1$ 时大家共享一套，那就是多查询注意力；中间任意 $G$ 都是两者的连续插值。缩减系数就是：

$$
\text{reduction} = \frac{H}{G}
$$

64 个头、8 组，意味着每组 8 个 query 头、带宽削到八分之一，并且模型保留了 8 个彼此独立的历史视角，而不是 1 个 [【跳转到 08:03】](https://www.youtube.com/watch?v=UHCaG8g7Vpw&t=483)。

![把 H = 64 个 query 头按 G 分组后，缓存的头轴长度就是 G；下方旋钮标出 MHA（G = 64）、GQA-8（G = 8）、MQA（G = 1）三个位置](assets/GQA%20的形状账：KV%20头数从%20H%20缩到%20G，读时用%20repeat_interleave%20广播回%20H/00483.webp)

把「组」翻译成索引：设每组有 $m = H/G$ 个 query 头，那么第 $h$ 个 query 头该用的 KV 头是

$$
g(h) = \left\lfloor \frac{h}{m} \right\rfloor
$$

一个整数除法加一次向下取整就够了，没有任何查表。这也解释了为什么分组必须**连续**——连续性是这个公式能成立的前提。

## 六、形状账的关键一步：缓存是 $[B,S,G,d]$，读出来要 $[B,S,H,d]$

缓存的形状变成 $[B, S, G, d]$，可是每个 query 头都想要一份形状匹配的 key 和 value。所以读的时候要沿头轴把每份缓存复制 $R = H/G$ 次。在 PyTorch 里这一步是 `repeat_interleave`，**不是** `repeat`，而两者的差别不是美观问题：

```python
import torch

B, S, H, d = 2, 8, 8, 128      # 批、序列、query 头数、头维度
G = 2                          # 组数（这里取 2 只为让下标看得清；真实模型常见 8）
R = H // G                     # 每组几个 query 头

K = torch.randn(B, S, G, d)    # 缓存里只有 G 个 key 头
K_broadcast = K.repeat_interleave(R, dim=2)   # -> [B, S, H, d]，组内连续
# 下标映射：0,0,0,0, 1,1,1,1

# 反例：repeat 把整组循环拼接
K_wrong = K.repeat(1, 1, R, 1)                # 下标映射：0,1,0,1,0,1,0,1
```

`repeat_interleave` 给出的是 `0,0,0,0,1,1,1,1`（组内连续），所以第 0 到第 3 个 query 头都落在第 0 组；而 `repeat` 是把整组循环拼接（本例是 `0,1,0,1,0,1,0,1`），第 0 个和第 4 个 query 头又会悄悄撞到同一个 key 头上——配图里用 H = 8、G = 4 画的是同一件事：`0,1,2,3,0,1,2,3`。这跟你建权重时用的分组对不上了。模型照样能跑，只是会静静地变差，这是最难查的一类 bug [【跳转到 08:28】](https://www.youtube.com/watch?v=UHCaG8g7Vpw&t=508)。

![扩张的正确与错误写法对照：repeat_interleave 得到 0,0,0,0,1,1,1,1 并与分组一致；repeat 得到 0,1,2,3,0,1,2,3，导致 q0 与 q4 撞车](assets/GQA%20的形状账：KV%20头数从%20H%20缩到%20G，读时用%20repeat_interleave%20广播回%20H/00558.webp)

讲者在这一点上的表述是「扩张是一个视图，不是复制，内存里永远只有 $G$ 个 key 头」。**评注（非讲者原话）**：PyTorch 的 `repeat_interleave` 实际上会新建张量，真正想零拷贝，得在注意力 kernel 内部直接按 $g(h)$ 去索引对应的缓存头，而不是先把张量铺开。工程上更常见的做法是把 KV 头当作广播维度，交给内核处理。

## 七、九行前向：只有三处是新的，注意力数学一点没动

把上面这些写成一次前向，只需要九行：

```python
# 1  q = x @ W_Q                  # H 个 query 头，和原来一样
# 2  k = x @ W_K                  # G 个 key 头（新：矩阵变窄）
# 3  v = x @ W_V                  # G 个 value 头（新：矩阵变窄）
# 4  K, V = cache.append(k, v)    # 缓存里只有 G 个头，所有节省都发生在这一行
# 5  R = H // G                   # 每组包含几个 query 头
# 6  K = repeat_interleave(K, R, dim=head)   # 新：读时扩回 H 份
# 7  V = repeat_interleave(V, R, dim=head)   # 新：读时扩回 H 份
# 8  scores = (q @ K.transpose(-1, -2)) / sqrt(d)
# 9  out = softmax(scores + causal_mask) @ V
```

第 8、9 行是原来的缩放点积注意力，一字未改；softmax、$1/\sqrt{d}$ 缩放、因果掩码、旋转位置编码全部照旧——**注意力数学根本不需要知道发生过什么** [【跳转到 11:48】](https://www.youtube.com/watch?v=UHCaG8g7Vpw&t=708)。新的东西只有三件：K/V 投影改成 $G$ 个头、缓存按 $G$ 个头增长、以及读路径上那一次 `repeat_interleave`。

## 八、三种配置的账：FLOPs 不变，字节数变成 $1/G$

分组**完全不改变浮点运算量**：每个 query 头照样做完整的点积、完整的加权求和，$H$ 个头份量的算术一次不少。变的是字节——你读 $G$ 个 KV 头而不是 $H$ 个，于是算术强度从 1 flop/byte 变成

$$
\text{arithmetic intensity} = \frac{H}{G} \quad (\text{flops per byte})
$$

64 头、8 组就是 8；MQA 就是 64。换句话说，$G$ 就是旋钮在 Roofline 图上的位置，而你要付的货币只有一种：模型还能保留几种彼此不同的「历史视角」[【跳转到 09:43】](https://www.youtube.com/watch?v=UHCaG8g7Vpw&t=583)。

![算术强度的分子被 H 冻住、分母只剩 G，因此比值就是 H/G；右侧 Roofline 图上，GQA-8 落在强度为 8 的位置](assets/GQA%20的形状账：KV%20头数从%20H%20缩到%20G，读时用%20repeat_interleave%20广播回%20H/00608.webp)

把三种配置都用同一套形状算一遍（80 层、64 个 query 头、头维度 128、fp16、4096 个 token）：

| 配置 | KV 头数 | 每 token 每层 | 每 token（× 80 层） | 4096 token | 32 路并发 |
| --- | --- | --- | --- | --- | --- |
| MHA | 64 | 32 KiB | 2.5 MiB | 10 GiB | 320 GiB |
| MQA | 1 | 512 B | 40 KiB | 160 MiB | 5 GiB |
| GQA-8 | 8 | 4 KiB | 320 KiB | 1.25 GiB | 40 GiB |

两个交叉验证：10 GiB ÷ 64 = 160 MiB，10 GiB ÷ 8 = 1.25 GiB，都对得上。放到 32 路并发上，只有后两种能跟 140 GiB 的权重挤在同一批卡里 [【跳转到 10:33】](https://www.youtube.com/watch?v=UHCaG8g7Vpw&t=633)。

![同一套形状下三种注意力的字节数对照：每 token 每层 32 KiB / 512 B / 4 KiB，4096 token 后是 10 GiB / 160 MiB / 1.25 GiB，乘 32 路并发是 320 GiB / 5 GiB / 40 GiB](assets/GQA%20的形状账：KV%20头数从%20H%20缩到%20G，读时用%20repeat_interleave%20广播回%20H/00658.webp)

还有一个没人宣传的附带收益：K/V 投影矩阵本身也变窄了。在这个形状上，大约 90 亿参数「直接不存在了」——回想第二节那张公式，缓存账单里根本不出现参数总量，而这一次省下来的恰恰是参数 [【跳转到 10:58】](https://www.youtube.com/watch?v=UHCaG8g7Vpw&t=658)。

至于「已有的检查点怎么改成 GQA、$G$ 到底取几」，属于同一小节另一篇《为什么是 8 组》的内容：一句话版本是，组内把 K/V 投影矩阵按元素取平均（因为投影是线性的，平均矩阵作用于 token 就等于平均它原本会产出的 key），再用原配方继续训练原步数的 5%。

## 小结

- **先看瓶颈**：解码每步都要把整个 KV 缓存重读一遍，所以代价在带宽不在算力；多头注意力下每次搬 4 字节只换 4 次浮点，算术强度 1 flop/byte，而 A100 想要约 150、H100 约 300。
- **批处理救不了缓存**：它能让权重被 32 条序列复用，但每条序列有各自的缓存，字节和浮点一起翻倍，比值不变。
- **唯一自由的项是 KV 头数**：层数、精度、上下文都不能当解法。MQA 把它砍到 1，换来 64 倍流量削减，也换来容量、质量和训练稳定性的代价（还有分片复制这种隐蔽浪费）。
- **GQA 把开关变成旋钮**：$H$ 个 query 头切成 $G$ 组，组内共享一对 K/V，缩减系数就是 $H/G$；$G = H$ 是 MHA，$G = 1$ 是 MQA，中间都是插值。
- **形状账落在一次广播上**：缓存是 $[B,S,G,d]$，读时用 `repeat_interleave` 沿头轴扩 $R = H/G$ 次变回 $[B,S,H,d]$；用 `repeat` 只会把整组循环拼接（`0,1,2,3,0,1,2,3`），$q_0$ 与 $q_4$ 撞车，模型照跑但静默变差。
- **FLOPs 不变、字节变少**：算术强度升级为 $H/G$；80 层 64 头 4096 token 的形状下，10 GiB 分别变成 160 MiB（MQA）与 1.25 GiB（GQA-8），32 路并发是 320 GiB / 5 GiB / 40 GiB。
- **顺带省参数**：K/V 投影矩阵变窄，这个形状上约 90 亿参数不再存在。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| KV Cache（键值缓存） | 把历史 token 的 key/value 存下来，避免每步重算；写一次、之后每步整块读。 |
| $h_{kv}$（KV 头数） | 缓存张量头轴的真正长度；多头注意力里它等于 query 头数，GQA 里它等于组数 $G$。 |
| 头维度 $d$ | 单个注意力头向量的长度，Llama-2-70B 是 128；缓存每存一个头就是 $d$ 个数字。 |
| MHA（多头注意力） | 每个 query 头配一套自己的 K/V，容量最大、缓存最大。 |
| MQA（多查询注意力） | 所有 query 头共享一套 K/V，缓存缩到 $1/H$，质量与训练稳定性有代价。 |
| GQA（分组查询注意力） | 把 query 头分 $G$ 组，组内共享一套 K/V，缓存缩到 $1/G$，是 MHA 与 MQA 之间的旋钮。 |
| 算术强度（arithmetic intensity） | 每搬 1 字节能换来多少次浮点运算；解码注意力约 1，GQA-8 约 8。 |
| Roofline 拐点 | 硬件峰值算力与峰值带宽的交汇点；算术强度低于它就只能等内存。 |
| `repeat_interleave` | 沿某一维做连续重复（0,0,0,0,1,1,1,1），与 GQA 的分组语义一致。 |
| `repeat` | 沿某一维做整组循环重复（0,1,2,3,0,1,2,3），不是组内连续，会让不同组的 query 头撞到同一个 KV 头。 |
