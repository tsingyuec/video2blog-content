# 为什么是 8 组：GQA 用八分之一的缓存，换回几乎全部质量，只补训百分之五

> 视频来源：[Grouped Query Attention (GQA) Explained: A Smaller KV Cache](https://www.youtube.com/watch?v=LOP2BRozd0s)（YouTube · 用 10 分钟讲清 GQA 的分组数与取舍）
> 本文基于视频演说图文稿整理，配图截自视频。字幕里的 `cache` 曾被识别成 `cash`、`Llama 3 8B` 曾被连写成 `llama 38 billion`，正文按上下文订正。

## 本讲要解决的核心问题（SCQA）

**背景**：生成文字时，模型要把每个历史 token 的 key 和 value 存下来（KV Cache，键值缓存），缓存大小直接决定一张卡能同时服务多少用户。缓存里的一项——KV 头的数量——是可以由人选的。

**冲突**：有一个配置的缓存最小、解码最快，它叫 MQA（Multi-Query Attention，多查询注意力，所有头共享一套 K/V）。可是 Llama、Mistral 以及许多开源模型**故意绕开它**，选了存得更多、搬得也更多的 GQA（Grouped-Query Attention，分组查询注意力）；而且在这类模型的配置表里，你反复看到的数字是 **8**。

**疑问**：头共享之后模型到底丢了什么？共享到什么程度算过分？8 这个数字是从哪来的？

**回答（中心思想）**：**8 组不是推导出来的理论最优，而是实测曲线上「质量几乎不丢、速度几乎不亏」的拐点。** 在 T5 XXL 上，8 组把「每个样本 1.51 秒、47.2 分」的多头注意力变成「0.28 秒、47.1 分」——用八分之一的缓存换回几乎全部质量；而把一个已有的多头模型改造成这样，只需要在组内把 K/V 投影取平均，再补训原训练量的约 5%。

---

## 一、先把账建起来：缓存的大小只跟「几个头」线性相关

注意力里每个 token 拿到三根向量：**query** 说明它在找什么，**key** 说明它提供什么，**value** 是它交出去的东西。模型会并行做很多份，每一份叫一个头（head），每个头有自己的 query、key、value；而这些向量都是投影——token 的向量乘一个矩阵，被压到更小的空间里，query、key、value 各有一个矩阵。单个头干的事情一行就能写完：query 和 key 比对出分数，分数变成权重，再用权重把 value 混起来 [【跳转到 00:50】](https://www.youtube.com/watch?v=LOP2BRozd0s&t=50)。

生成时模型一次只写一个 token，每个新 token 都要回头看所有更早的 token；而它们的 key 和 value 从不改变，所以模型把它们存起来——这就是 KV 缓存 [【跳转到 01:27】](https://www.youtube.com/watch?v=LOP2BRozd0s&t=87)。

![生成时的 KV 缓存：每个 token 的 keys 与 values 一旦算出就「永不再变」，缓存按「8 个头」堆叠成一张表](assets/为什么是%208%20组：GQA%20用八分之一的缓存，换回几乎全部质量，只补训百分之五/00112.webp)

它的体积是四个数的乘积：每个 token 要存 key 和 value（所以有个 2）、每层都要存、每个 KV 头都要存、每个头里有一串数字。其中**层数**和**头的大小**是模型定死的，我们唯一能改的是 **KV 头的数量** [【跳转到 01:52】](https://www.youtube.com/watch?v=LOP2BRozd0s&t=112)。

## 二、两个显而易见的答案，其实都不好

对「要几个 KV 头」这个问题，最直觉的回答只有两个：

1. **每个 query 头配一个**——这就是标准多头注意力（MHA）：容量最大，缓存也最大。
2. **所有头共用一套**——这就是多查询注意力（MQA）：缓存直接缩小「头数」那么多倍，在小模型上效果还出奇地能用 [【跳转到 02:16】](https://www.youtube.com/watch?v=LOP2BRozd0s&t=136)。

问题是把这个方案放到大模型上。一个 64 个头的模型里，每个 token 的 key 在每层原本装着大约 4000 个数字；只留一个共享头，就只剩 64 个。每个头都只能在这条窄缝里找自己要的东西。在大模型上实测：质量下降，训练有时还会变得不稳定 [【跳转到 03:00】](https://www.youtube.com/watch?v=LOP2BRozd0s&t=180)。

一边是把一切都留下，另一边是把几乎一切都扔掉，两个极端都不是想去的地方。于是讲者给出那句关键的话：**不要在两者之间做选择，在它们之间装一个旋钮。**

## 三、旋钮怎么造：把 query 头分进 $G$ 个组

做法很朴素：把 query 头分成若干组，每组共享一个 key 头和一个 value 头。32 个 query 头配 8 组，就是每个 key 头服务 4 个 query 头。写成公式只是一处小改动：第 $h$ 个头不再用自己那套 K/V，而是用它所属那一组的那套；找组号也简单——数一数每个 key 头被几个 query 头共享（记作 $m$），把头编号除以 $m$ 再向下取整：

$$
g(h) = \left\lfloor \frac{h}{m} \right\rfloor, \qquad m = \frac{H}{G}
$$

请注意什么没变：**每个头都保留自己的 query**，所以每个头仍然在问自己的问题。再看旋钮的两端：把组数设成等于头数，就退回多头注意力；设成 1，就是多查询注意力；中间的 $1 < G < H$ 全是 GQA [【跳转到 04:01】](https://www.youtube.com/watch?v=LOP2BRozd0s&t=241)。

![旋钮刻度从 32（多头）一路到 1（多查询），停在 8；32 个 query 头被划成 8 组，每组 4 个头共享一套 key 与 value](assets/为什么是%208%20组：GQA%20用八分之一的缓存，换回几乎全部质量，只补训百分之五/00266.webp)

## 四、缓存公式：把 $H$ 换成 $G$，Llama-3-8B 从 4 GiB 降到 1 GiB

回头看缓存大小，其实只变了一个数：KV 头数从「头数」变成了「组数」。写开来，每个 token 存的数字个数是

$$
2 \times L \times G \times d_k
$$

其中 $L$ 是层数、$d_k$ 是每个头里的数字个数。所以缓存缩小的比例，就是头数与组数之比 $H/G$ [【跳转到 04:26】](https://www.youtube.com/watch?v=LOP2BRozd0s&t=266)。

![缓存体积的四个因子：2（keys + values）× 层数 L × 组数 G × 每头数字数 d_k，其中只有 G 是人为选的](assets/为什么是%208%20组：GQA%20用八分之一的缓存，换回几乎全部质量，只补训百分之五/00291.webp)

拿一个真实模型算一遍——Llama 3 的 8B 版本：32 层、32 个 query 头、8 个 KV 头、每个头 128 个数字、上下文 8192 个 token。如果它给每个 query 头都存一套 K/V，一个 token 就要 $2 \times 32 \times 32 \times 128 = 262{,}144$ 个数字，整个上下文要 4 GiB 出头；而有 8 组时只要八分之一，约 1 GiB。比例为 $H/G = 4$，正好四倍 [【跳转到 04:51】](https://www.youtube.com/watch?v=LOP2BRozd0s&t=291)。

![Llama 3 8B 的形状：32 层、32 个 query 头、8 个 KV 头、每头 128 个数字、上下文 8192 token，缩小比例 H/G = 4](assets/为什么是%208%20组：GQA%20用八分之一的缓存，换回几乎全部质量，只补训百分之五/00316.webp)

| 同一个 Llama 3 8B 形状 | 每 token 的数字个数 | 8192 token 上下文的缓存 |
| --- | --- | --- |
| 假想：每个 query 头一套 K/V（$G = 32$） | 262,144 | 约 4 GiB |
| 真实配置：8 组（$G = 8$） | 65,536 | 约 1 GiB |

这还只是**一次对话**。一台服务器同时装很多条对话，所以这个比例直接决定了**一张卡上能塞几个用户**。省下来的时间走的也是同一套逻辑：每一步都要把整块缓存从内存搬到处理器，缓存小四倍，要搬的就少四倍——不过别指望四倍缓存能换来四倍加速，因为你每步还得把权重完整载入一遍，缓存从来不是唯一的开销项。

## 五、为什么几组就够：一组相当于一张「排布图」

为什么区区几组就够用？先想清楚 key 是干什么的：它们把 token 安排进一个空间里，而每个头从**自己的方向**去搜索这个空间。如果所有头共用一套 key，那每个头就都在搜索同一张排布图——一张图应付所有类型的问题，这当然有代价：一个头能产出的分数，是由它能看见的 key 决定的；如果每个头看到的都是同样的几个数，它们的模式就没法各自自由变化，被绑在了一起 [【跳转到 05:58】](https://www.youtube.com/watch?v=LOP2BRozd0s&t=358)。

![「为什么几组就够」的直觉图：key 把 token 铺成一个空间，不同方向的箭头代表不同头在从各自角度搜索](assets/为什么是%208%20组：GQA%20用八分之一的缓存，换回几乎全部质量，只补训百分之五/00358.webp)

8 组则是 8 张不同的图：一组可以按语法排布 token，另一组按语义，再一组按位置。而且**组内**的头仍然从不同方向提问，所以它们看到的模式仍然不同。回到那个 64 头的大模型：一个共享 head 只给它 64 个数字，8 组给它 512 个——仍然是完整设计的八分之一，但已经足够让这些头不再互相碍事 [【跳转到 06:38】](https://www.youtube.com/watch?v=LOP2BRozd0s&t=398)。

## 六、实测：8 组用 0.28 秒拿到 47.1 分，多头是 1.51 秒 47.2 分

直觉之后看测量。提出 GQA 的研究者在 T5 XXL 上试了三种设置，三个数字决定了后面的一切 [【跳转到 07:03】](https://www.youtube.com/watch?v=LOP2BRozd0s&t=423)：

| 设计 | 平均分（越高越好） | 每样本推理时间（越短越快） |
| --- | --- | --- |
| 完整多头注意力 | 47.2 | 1.51 s |
| 多查询注意力 | 46.6 | 0.24 s |
| GQA（8 组） | 47.1 | 0.28 s |

多查询注意力快了约六倍，但分数掉到 46.6；8 组的 GQA 几乎把质量全拿回来了（只比完整多头低 0.1），速度却接近多查询——大约四分之一秒。讲者还提了一个他最喜欢的细节：他们还测了一个**用完整注意力的小模型**，结果大的分组模型比小的完整模型**又准又快**（46.0 分 / 0.37 秒对 47.1 分 / 0.28 秒）。所以对大模型来说，这不是「各让一步」的交换，而接近「两样都要」[【跳转到 07:28】](https://www.youtube.com/watch?v=LOP2BRozd0s&t=448)。

![T5 XXL 上三种设计的散点与得分表：多头 47.2/1.51 s、多查询 46.6/0.24 s、8 组 47.1/0.28 s；右下还并列了一个完整注意力的小模型 T5 Large 的 46.0/0.37 s](assets/为什么是%208%20组：GQA%20用八分之一的缓存，换回几乎全部质量，只补训百分之五/00473.webp)

## 七、改造成本：组内取平均 + 约 5% 的补训

GQA 扩散得快，还有一个更现实的原因：**不用从头训一个新模型**。拿一个已经是完整多头注意力的模型，在每组内部把各头的 key 投影矩阵按元素平均成一个，value 投影同样处理，query 原封不动 [【跳转到 07:53】](https://www.youtube.com/watch?v=LOP2BRozd0s&t=473)。

平均后的模型不会立刻完美，所以要补一小段训练：大约是原始训练量的 **5%**。研究者还比了另外两种起手式——只保留每组里的一个头，或者让共享头从随机数开始——结果是**取平均最好** [【跳转到 08:25】](https://www.youtube.com/watch?v=LOP2BRozd0s&t=505)。换句话说，一个已经存在的模型，只花它造价的一小部分就能完成改造。

![改造已有模型：先组内平均各头的 K/V 投影，再补训原始步数的 α = 0.05，即多花 5%](assets/为什么是%208%20组：GQA%20用八分之一的缓存，换回几乎全部质量，只补训百分之五/00505.webp)

（为什么取平均是合理的、而不是碰巧——那需要「投影是线性映射，所以平均矩阵作用在 token 上等于平均它原本会产出的 key」这一步推导，见同小节的另一篇《GQA 的形状账》。）

## 八、今天在哪里见到 8：Llama 2 最大版本、Llama 3、Mistral

它现在出现在哪里？Llama 2 在它最大的版本上用了 GQA；Llama 3 用它；Mistral 也用它。而在 Llama 3 和 Mistral 7B 里，设置是同一个：**32 个 query 头、8 个 KV 头** [【跳转到 08:25】](https://www.youtube.com/watch?v=LOP2BRozd0s&t=505)。

Mistral 团队把理由说得直白：更快的推理、解码阶段更少的内存占用，意味着可以开更大的 batch、拿到更高的吞吐 [【跳转到 08:50】](https://www.youtube.com/watch?v=LOP2BRozd0s&t=530)。

那自己的模型该怎么选组数？讲者给的经验是这样的 [【跳转到 09:04】](https://www.youtube.com/watch?v=LOP2BRozd0s&t=544)：

- **模型小、内存是第一位**：一个共享头（$G = 1$，即 MQA）可能就够了；
- **模型大**：留几组，用几乎同样的速度保住质量；
- **模型越长越大、头数增加时**：分组让你在任何规模上都保住**同一比例的节省**，而不是越切越狠。

最后一条值得多说一句：头数越多，若组数不变，共享比例 $H/G$ 就会被稀释。讲者的意思不是把 8 当常数抄，而是让组数跟着头数一起走，让“省下的比例”成为不随规模漂移的量。

## 九、把整件事串起来

一组旋钮、三个数字、一步补训，就是这支视频的全部。**缓存随 KV 头数增长，多头保留每个 query 头一套，多查询只保留一套，GQA 在两者之间装了旋钮：把头分成组，每组共享一套 K/V，缓存按头数与组数之比缩小。** 而 8 这个数字，是「大模型用大约 8 组就能保住几乎全部质量」这条实测经验的落点。

更有意思的其实是一个设计上的教训：**当两个显而易见的选项都不对时，去找藏在它们中间的那个旋钮**——MHA 与 MQA 看上去是两种架构，其实是同一根旋钮的两端，而 GQA 只是旋钮停在中间。视频最后还留了一个思考题：如果一组之内的头连 query 也一起共享，会坏在哪里？

## 小结

- **缓存是瓶颈**：生成时每个新 token 都要回看历史，K/V 存下来之后不再改变；缓存体积是「2 × 层数 × KV 头数 × 每头数字数」的乘积，层数和头大小由模型定死，只有 KV 头数可选。
- **两个极端都不好**：多头注意力每个 query 头一套 K/V，容量最大、缓存也最大；多查询注意力只留一套，缓存缩到头数分之一，但在 64 头的大模型上质量下降、训练有时不稳。
- **GQA 是中间的旋钮**：$H$ 个 query 头分成 $G$ 组，组内共享一套 K/V，组号是 $\lfloor h/m \rfloor$；$G = H$ 退回多头，$G = 1$ 退回多查询，缓存按 $H/G$ 缩小。
- **真实规模上的账**：Llama 3 8B（32 层、32 Q、8 KV、每头 128 个数字、8192 上下文）从约 4 GiB 降到约 1 GiB；这个比例决定一张卡能装几个用户。
- **8 组为什么够**：一组对应一张「key 排布图」，8 组给 64 头模型 512 个数字而不是 64 个，够各头不再互相碍事。
- **实测**：T5 XXL 上多头 47.2 分 / 1.51 秒，多查询 46.6 分 / 0.24 秒，8 组 47.1 分 / 0.28 秒；而 8 组的大模型比完整注意力的小模型又准又快。
- **改造成本低**：组内平均 K/V 投影（queries 不动），再补训原训练量的约 5%；平均优于「只留一个头」与「随机初始化」。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| KV Cache（键值缓存） | 存下历史 token 的 key 和 value，避免每步重算；它会随对话变长而变大。 |
| 头（head） | 注意力并行做的一份副本，各有自己的 query、key、value 投影。 |
| MHA（多头注意力） | 每个 query 头配一套 K/V，容量最大、缓存也最大。 |
| MQA（多查询注意力） | 所有 query 头共用一套 K/V，缓存缩到头数分之一，质量与训练稳定性有代价。 |
| GQA（分组查询注意力） | query 头分 $G$ 组、组内共享一套 K/V；$G$ 是 MHA 与 MQA 之间的旋钮。 |
| $H$ 与 $G$ | $H$ 是 query 头数，$G$ 是组数（= KV 头数）；缓存缩小比例就是 $H/G$。 |
| 共享比例 | 每个 KV 头被几个 query 头共享，等于 $H/G$；8 组配 32 头就是 4 个头共享一套。 |
| 补训（extra training） | 把已有模型改成 GQA 后，用原配方再训一小段，约原始训练量的 5%。 |
