# 从低秩分解到 MLA：DeepSeek 为什么只缓存一条 512 维隐向量

> 视频来源：[Deepseek课程L03: KV cache 有多大，MLA 怎么压缩它](https://www.bilibili.com/video/BV1oSx36ZEc4/)（Bilibili · UP 主 garman2）｜时长约 13 分钟
> 导读：这是一节从零讲起的课：先算清 KV Cache 有多大，再用一个 6×6 矩阵和一团三维点讲明白「低秩」是什么，然后才把 MLA 的三步（压成 c、吸收矩阵、解耦 RoPE）一层层搭起来，最后去 DeepSeek-V3 的推理源码里核对缓存形状。字幕里的口误（`kvcash`→KV cache、`低质`→低秩、`影像量`→隐向量、`点击`→点积、`受场`→瘦长、`投`→头）已按上下文订正。

## 本讲要解决的核心问题（SCQA）

**背景**：模型一个字一个字往外写。每写一个新字，都要用它的 query 和前面所有字的 key、value 做一遍注意力。前面那些字的 key 和 value 一旦算出来就不再变，所以推理时把它们存起来，下一步直接拿来用——这就是 KV Cache。

**冲突**：这份缓存随对话长度线性增长，而且每个 token 都要为每一层、每一个头各存一份 K 和 V。按 DeepSeek-V3 的配置，一条 128K 的对话光缓存就要 655 GB，比一整台八卡 80 GB 的服务器还多——模型装得下，不代表能服务长对话。

**疑问**：能不能让缓存比 GQA 还小，效果却不输 MHA？

**回答（中心思想）**：能。MLA 借的是**低秩分解**这个数学工具：一个矩阵如果所有列都能由少数几个方向拼出来，就不必存整个矩阵，只存那几个方向加系数。MLA 把每个 token 的隐藏状态压成一条 512 维的 $c$，让 K 和 V 都从这一条还原出来，缓存里只留 $c$；再用矩阵结合律把还原矩阵吸收进 query，让 $c$ 直接参与点积；最后因为 RoPE 挡住了吸收，把位置信息拆到一条 64 维的小旁路上。缓存最终是 $512+64=576$ 个数，一条 128K 对话从 655 GB 降到 9.2 GB。[【跳转到 11:26】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=686)

## 一、先把 KV Cache 的账算清楚

### 1.1 缓存是怎么来的

用一个具体的句子：「小猫坐在垫子上」。模型处理到最后一个字，要决定该去参考前面哪些词 [【跳转到 00:50】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=50)：

- 每个词都会算出一个 **key**，可以理解成贴在自己身上的标签；
- 当前这个词再算出一个 **query**，表示它要找什么；
- query 和每个 key 做点积得到分数，两个箭头方向越接近，点积越大；
- 分数经过 softmax 变成权重，加起来等于一；
- 最后用这些权重把每个词的 **value**（它真正携带的内容）加权求和，就是这一步的输出。

模型一个字一个字往外写，每写一个新字，都要用它的 query 和前面所有字的 key、value 做一遍注意力。而前面那些字的 key 和 value 一旦算出来就不会再变，所以推理时把它们存起来，下一步直接拿来用，只为新字算一次——这就是 KV Cache。[【跳转到 01:40】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=100)

![KV Cache 的动机：新字的 query 要和前面所有字的 key、value 做注意力，所以历史 K、V 必须留下来](assets/从低秩分解到%20MLA：DeepSeek%20为什么只缓存一条%20512%20维隐向量/00100.webp)

### 1.2 一个 token 要存多少

代价是显存：对话越长，缓存越大，而且是线性增长。每个 token 的缓存量等于

$$
2 \times \text{层数} \times \text{头数} \times \text{每头维度} \times \text{每个数的字节数}
$$

这里的 2 是 key 和 value 各一份。[【跳转到 01:40】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=100)

先看一个参照：DeepSeek 的 insights 论文列过 Qwen2.5-72B，它用 GQA（分组查询注意力），每个 token 的缓存约 328 KB，乘上 128K 上下文约 42.9 GB。换成 V3 的 61 层、128 个头，每个头的 key 是 192 维（128 维内容 + 64 维位置，讲到 RoPE 时就明白为什么是 192），每个 token 接近 5 MB，是那个参照的 15 倍左右；乘上 128K 上下文，就是开头那 655 GB。[【跳转到 02:05】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=125)

### 1.3 四类压缩思路，MLA 属于哪一类

业界压缩 KV Cache 大致有四类办法 [【跳转到 02:30】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=150)：

| 思路 | 代表做法 | 省的是 |
| --- | --- | --- |
| 多个头共用 K、V | MQA、GQA | 存几份 |
| 只留最近一段 | 滑动窗口 | 存多长 |
| 每个数存得更省 | 量化（FP8 等） | 每份多宽 |
| 少搬几次数据 | FlashAttention | 带宽，不省容量 |

![四类压缩思路：多个头共用、只留最近一段、每个数存得更省、减少数据搬运](assets/从低秩分解到%20MLA：DeepSeek%20为什么只缓存一条%20512%20维隐向量/00200.webp)

MLA 最接近第一类，所以先看第一类怎么做。标准多头注意力里每个头都有自己的一份 key 和 value，缓存就要存这么多份；能不能让几个头共用一份？分成几组、组内共用，叫 GQA；更极端一点，所有头共用一份，叫 MQA。[【跳转到 02:55】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=175)

![MHA、GQA、MQA 的差别：8 个头从各存一份，到分 2 组共用，到全部共用一份](assets/从低秩分解到%20MLA：DeepSeek%20为什么只缓存一条%20512%20维隐向量/00175.webp)

缓存确实小了，组越少越省。但代价是表达能力：不同的头被迫看同样的 key 和 value，效果会打折扣。DeepSeek-V2 论文的表 1 把这个取舍写得很直白：MHA 强、GQA 中等、MQA 弱。**有没有办法让缓存比 GQA 还小，效果却不输 MHA？** 要回答这个问题，先要认识一个数学工具。

## 二、先补一个数学工具：低秩分解

### 2.1 一个 6×6 的矩阵

先离开注意力，看一个小例子：一个 6 行 6 列的矩阵，一共 36 个数，乍一看没什么规律。但仔细看会发现，每一列都是两个列向量 $u$ 和 $v$ 的组合——第一列正好是 $u+v$，第二列正好是两倍的 $u$，六列全是这样。[【跳转到 03:45】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=225)

![6×6 矩阵的低秩结构：36 个数其实由两个列向量 u、v 加每列的两个系数决定](assets/从低秩分解到%20MLA：DeepSeek%20为什么只缓存一条%20512%20维隐向量/00245.webp)

所以只要存下 $u$、$v$ 这两列（6+6 个数），再加上每一列的两个系数（12 个数），一共 24 个，就能把整个矩阵原样还原出来。存储量从 36 降到 24；矩阵越大，省得越多——一个 $1000 \times 1000$ 的矩阵如果也只有两个方向组合而成，100 万个数只需要存 4000 个。[【跳转到 04:10】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=250)

### 2.2 秩是什么

**拼出所有列最少需要几个方向，这个数就叫矩阵的秩。** 刚才那个矩阵的秩是 2。把一个大矩阵拆成两个瘦长矩阵相乘，就叫**低秩分解**。[【跳转到 04:10】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=250)

### 2.3 几何视角：三维的点躺在二维平面上

换个几何的角度更好懂：三维空间里有一团点，每个点要三个数来描述；转一下视角就会发现，它们其实全都躺在同一个平面上。既然都在一个平面上，每个点只要记住它在平面上的两个坐标就能找回来，第三个数是多余的——这就是压缩：用平面上的两个方向，把三维降到二维存起来，需要时再用这两个方向还原回三维。[【跳转到 04:35】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=275)

![几何视角：三维空间里的点其实都落在一个平面上，每个点只要两个坐标就能还原](assets/从低秩分解到%20MLA：DeepSeek%20为什么只缓存一条%20512%20维隐向量/00300.webp)

## 三、MLA 只缓存 c

### 3.1 h 7168 维压成 c 512 维

回到 MLA。每个 token 的隐藏状态 $h$ 有 7168 维，MLA 先用一个矩阵把它压成 512 维的向量 $c$；需要的时候，再用另外两个矩阵把 $c$ 还原成全部 128 个头的 key 和 value。这和刚才的 $u$、$v$ 是同一个道理。[【跳转到 05:00】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=300)

![MLA 的第一步：h 的 7168 维经过下投影矩阵 W^DKV 压成 512 维的 c](assets/从低秩分解到%20MLA：DeepSeek%20为什么只缓存一条%20512%20维隐向量/00310.webp)

这里要分清两样东西 [【跳转到 05:25】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=325)：

- 那几个 $W$ 是**模型权重**，整个模型只存一份，不随对话变长；
- $c$ 才是**每个 token 都要存的缓存**。

所以缓存里只放 $c$：每层每个 token 从四万多个数降到 512 个。

### 3.2 不是事后压缩，是训练时就限制

有个容易误解的地方要说清：真实模型里的 key 并不会严格躺在一个低秩平面上；MLA 也不是训练完再去压缩，而是**从训练一开始就规定 key 和 value 必须从 512 维还原出来**，让模型自己学会在这个限制下表达。[【跳转到 05:25】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=325)

这个限制伤不伤效果？V2 论文的对比实验给出的答案是：不但没伤，还略好于标准多头注意力。[【跳转到 05:50】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=350)

## 四、矩阵吸收：让 c 直接参与点积

### 4.1 一个 2 维 / 3 维的小例子

缓存是省了，但还有个问题：每生成一个字，难道要把缓存里所有的 $c$ 都还原成 K 再做点积吗？那每一步都要做 $T$ 次还原，算力全花在这上面了。[【跳转到 05:50】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=350)

先看一个小例子：$q$ 是 2 维，$c$ 是 3 维，$W$ 负责把 3 维的 $c$ 还原成 2 维的 $k$。

![结合律的小例子：q 是 2 维、W 是 2×3、c 是 3 维，先还原再点积，和先变换 q 再点积，结果一样](assets/从低秩分解到%20MLA：DeepSeek%20为什么只缓存一条%20512%20维隐向量/00375.webp)

- 左边的算法：先用 $W$ 把 $c$ 还原成 $k$，再和 $q$ 点积，得到 3；
- 右边换个顺序：先用 $W$ 的转置去变换 $q$，得到 $[1, 2, 4]$，再直接和 $c$ 点积，结果还是 3。

两条路结果完全一样，但右边有个好处：**变换 $q$ 只要做一次**，不管缓存里有多少个 $c$，都能直接拿来点积。[【跳转到 06:15】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=375)

### 4.2 放回注意力

放回注意力里就是这个式子：

$$
q^\top \left( W^{UK} c_j \right) = \left( (W^{UK})^\top q \right)^\top c_j
$$

也就是说，query 先被映射到 512 维的潜在空间，然后直接和缓存里的 $c$ 做点积，**key 从头到尾都不用真的算出来**。论文的说法是：$W^{UK}$ 被吸收进了 query 的投影里。[【跳转到 06:40】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=400)

![矩阵吸收放回注意力：q 和 W^UK 乘 c 的点积，等于先把 q 变换一次，再和每个 c 直接点积](assets/从低秩分解到%20MLA：DeepSeek%20为什么只缓存一条%20512%20维隐向量/00400.webp)

### 4.3 value 侧同理

value 那边也一样：按注意力权重把 $c$ 加权求和，最后只还原一次，这一步还能并进输出投影。于是缓存里只有 $c$，计算也不用还原，看起来很完美——但还差最后一块：位置编码。[【跳转到 06:40】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=400)

## 五、RoPE 挡住了吸收，所以要解耦

### 5.1 注意力怎么知道词的顺序

先回答一个问题：注意力怎么知道词的顺序？看「猫吃鱼」——「吃」对「猫」和「鱼」的注意力分数，把句子换成「鱼吃猫」意思完全反了，可分数一点没变。因为点积只看两个向量本身，不看它们排在第几。[【跳转到 07:05】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=425)

![点积不看位置：「鱼吃猫」意思反了，「吃」对两个词的注意力分数却一点没变](assets/从低秩分解到%20MLA：DeepSeek%20为什么只缓存一条%20512%20维隐向量/00450.webp)

所以必须额外把位置信息告诉模型。GPT-2 的做法是给每个位置学一个向量，直接加到词向量上，这叫绝对位置编码。它有两个问题：第一，模型真正关心的往往是两个词隔多远，而不是各自排第几；第二，训练时如果最长只见过 2048 个位置，再往后的位置向量根本就没学过。[【跳转到 07:30】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=450)

### 5.2 RoPE：按位置旋转

所以我们想要一种位置编码：放进去之后，注意力分数只取决于两个词隔多远。RoPE（旋转位置编码）换了个思路，不往上加东西，而是**转**：把 query 向量里的数每两个分成一组，看成平面上的一支箭头，词在位置 $m$ 就把这支箭头旋转 $m\theta$ 的角度，$\theta$ 是一个固定的小角度。同一个词放在不同位置，箭头的方向就不同，位置信息就这样编码进去了。[【跳转到 07:55】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=475)

关键在下一步：query 在位置 5 转了 $5\theta$，key 在位置 2 转了 $2\theta$，点积只取决于两支箭头的长度和夹角。现在把两个词整体往后挪 100 个位置，到 105 和 102，两支箭头一起多转了 $100\theta$，夹角不变，点积也就不变。也就是说，每个词只按自己的绝对位置转，可算出来的注意力分数只和两个词的相对距离有关。[【跳转到 08:20】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=500)

写成公式就是：

$$
(R_m q)^\top (R_n k) = q^\top R_{n-m} k
$$

两个旋转合在一起，只剩下相差的 $n-m$。另外，箭头转一圈就会回到原处，位置就分不清了，所以 RoPE 把 64 维分成 32 组，每组的转速都不一样——就像钟表的秒针、分针、时针，转得快的组能分辨相邻几个词，转得慢的组能分辨很远的距离。[【跳转到 08:45】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=525)

### 5.3 放回 MLA，吸收就失效了

现在把 RoPE 放回 MLA。$k$ 是从 $c$ 还原出来的，再按位置旋转，注意力分数就变成

$$
(R_i q)^\top \left( R_j W^{UK} c_j \right) = q^\top R_{j-i} W^{UK} c_j
$$

问题出在中间：旋转矩阵正好夹在 $q$ 和 $W^{UK}$ 之间，而且它随两个词的距离变化。之前我们只要把 $q$ 变换一次就能和所有的 $c$ 点积，现在每个历史位置对应的旋转都不同，就得为每一个 $c$ 单独变换一次——这和把所有 K 都还原出来没有区别，**吸收就这样失效了**。[【跳转到 09:35】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=575)

![把 RoPE 放回 MLA：旋转矩阵 R_{j-i} 夹在 q 和 W^UK 之间，还随距离变化，吸收因此失效](assets/从低秩分解到%20MLA：DeepSeek%20为什么只缓存一条%20512%20维隐向量/00575.webp)

### 5.4 解耦 RoPE：主路 + 旁路

DeepSeek 的解法叫**解耦 RoPE**：把位置信息拆出来，单独走一条小路。[【跳转到 10:00】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=600)

- **主路负责内容**：每个头 128 维，不做旋转，照样可以被吸收，缓存的还是 512 维的 $c$；
- **旁路负责位置**：每个 token 另算一个 64 维的小 key，专门做旋转，而且 128 个头共用这一个。

注意力分数就是两部分相加：

$$
\text{score}_{ij} = \tilde{q}_i^\top c_j + (R_i q_i^R)^\top (R_j k_j^R)
$$

前一半看内容，可以吸收；后一半看位置，带着旋转，但它只有 64 维，算起来很便宜。所以缓存最终存两样：512 维的 $c$ 加 64 维的位置 key，每层每个 token 576 个数。这也解释了前面算账时每头为什么是 192 维——128 维内容加 64 维位置。[【跳转到 10:25】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=625)

![解耦 RoPE：主路 512 维内容不旋转、可吸收；旁路 64 维位置单独旋转、128 个头共用](assets/从低秩分解到%20MLA：DeepSeek%20为什么只缓存一条%20512%20维隐向量/00620.webp)

## 六、去 V3 的源码里验证

最后去 DeepSeek-V3 的官方推理代码里验证一下。文件是 `inference/model.py` 里的 `MLA` 类，它有两种实现 [【跳转到 10:37】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=637)：

- **naive 模式**：缓存是 `k_cache` 和 `v_cache`，形状里带着头数，每个头都存一份完整的 key 和 value；
- **默认的 absorb 模式**：缓存只剩 `kv_cache` 和 `pe_cache`，一个是 512 维的 $c$，一个是 64 维的位置 key，**形状里已经没有头数这一维了**。

![V3 源码里的两种缓存：naive 模式的 k_cache、v_cache 带头数；默认 absorb 模式只有 kv_lora_rank 和 qk_rope_head_dim](assets/从低秩分解到%20MLA：DeepSeek%20为什么只缓存一条%20512%20维隐向量/00655.webp)

再看计算部分：把还原矩阵里 key 的那一部分乘到 `q_nope` 上，这就是吸收，query 从此变成 512 维；接着把这一步的 $c$ 和位置 key 分别写进两个缓存，分数正是两个 `isum` 相加——一个和 `kv_cache` 点积看内容，一个和 `pe_cache` 点积看位置，和刚才的公式一一对应。[【跳转到 10:55】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=655)

## 七、回到账本

按 V3 的配置，标准做法每层每个 token 要存 40960 个数，MLA 只存 576 个，少了大约 71 倍；一条 128K 的对话，缓存从 655 GB 降到 9.2 GB。[【跳转到 11:26】](https://www.bilibili.com/video/BV1oSx36ZEc4/?t=686)

![回到账本：同一条 128K 对话，标准多头注意力 655 GB，MLA 9.2 GB，每层每 token 从 40960 个数降到 576 个](assets/从低秩分解到%20MLA：DeepSeek%20为什么只缓存一条%20512%20维隐向量/00700.webp)

> 口径提示：71 倍是「40960 ÷ 576」的结果。如果把每头 192 维（128 内容 + 64 位置）全部计入，同配置 MHA 是 49152 个数，比值就变成 85.3 倍。两个数都是「每 token 每层元素数之比」，只是分母口径不同，不能混用。

## 小结

- KV Cache 是拿显存换计算：历史 token 的 K、V 存下来，下一步只为新字算一次。
- 低秩分解是把大矩阵拆成两个瘦长矩阵：一个 6×6 矩阵如果秩是 2，36 个数只要存 24 个；三维的点如果都在一个平面上，每个点只要两个坐标。
- MLA 只缓存 512 维的 $c$，K 和 V 都从它还原；这不是训练完再压缩，而是训练开始就规定的结构约束，效果反而略好于 MHA。
- 矩阵吸收用结合律把还原矩阵并进 query：$q^\top(W^{UK}c) = ((W^{UK})^\top q)^\top c$，key 从头到尾不必算出来。
- RoPE 按位置旋转让点积只依赖相对距离，但旋转矩阵夹在 $q$ 和 $W^{UK}$ 之间且随距离变化，吸收失效；解法是解耦 RoPE，位置另走一条 64 维共享小路。
- 缓存最终是 512 维 $c$ 加 64 维位置 key，共 576 个数；V3 源码的 absorb 模式里，缓存形状确实已经没有头数这一维。
- 一条 128K 对话从 655 GB 降到 9.2 GB。但省下的是「存多少」，每生成一个 token 仍要把全部历史缓存读一遍——上下文到了百万级，这是下一个要解决的问题。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| KV Cache | 解码时缓存历史 token 的 key、value，避免每步重算 |
| 低秩分解 | 把大矩阵拆成两个瘦长矩阵相乘，只存少量方向加系数 |
| 秩 | 拼出矩阵所有列最少需要的方向数 |
| MLA | 多头潜在注意力，把 K、V 联合压成一条 512 维隐向量再缓存 |
| 矩阵吸收 | 用结合律把还原矩阵并进 query / 输出投影，避免显式还原 K、V |
| RoPE | 旋转位置编码，按绝对位置旋转向量，使点积只依赖相对距离 |
| 解耦 RoPE | 位置信息不走低秩主干，另开一条 64 维共享 key 旁路 |
| GQA / MQA | 分组共享 / 全部共享 K、V，压的是「存几份」 |
