# MLA 低秩 KV 压缩：把 K 与 V 压成一条 576 维隐向量

> 视频来源：[【Transformer】MLA：把 KV Cache 压成一个隐向量](https://www.bilibili.com/video/BV1gTWo6MEag/)（Bilibili · UP 主 Dexphase）｜时长约 24 分钟
> 导读：这支视频不讲感觉，只讲账。它先按 DeepSeek-V3 的 config 把「一个 token 的 KV Cache 有多大」算到字节，再用同一套维度把 MLA 的 512+64=576 复算一遍，最后把论文 Table 1、权重吸收、解耦 RoPE、FlashMLA 的 kernel 常量逐条对上。本文按这条「算账 → 对拍 → 复算」的线索整理；字幕里的口误（`canfake`→config、`影像量`→隐向量、`低质`→低秩、`仿存`→访存、`投`→头、`点击`→点积）已按上下文订正。矩阵吸收的完整推导留给同系列 §8.3.3，本文只讲到「为什么它能成立、为什么缓存因此只剩 576 个数」。

## 本讲要解决的核心问题（SCQA）

**背景**：Transformer 解码时，前面每个 token 的 key 和 value 算过一次就不会再变，所以推理框架把它们存进显存，这就是 KV Cache（键值缓存）。缓存让每一步解码不必重算历史，只算新 token 的 query。

**冲突**：这份缓存的大小与上下文长度成正比。按 DeepSeek-V3 的公开配置，一个 token 在 61 层里要占将近 6 MB；一条 128K 上下文的对话，光缓存就要 786 GB，比八张 80 GB 显卡的全部显存还多——一张 80 GB 的卡连一个请求都放不下，能同时服务的用户数是 0。

**疑问**：既然长上下文推理先撞的墙是这份缓存，那能不能不存完整的 K 和 V？

**回答（中心思想）**：MLA（Multi-head Latent Attention，多头潜在注意力）的答案是**不存 K、也不存 V，只存一条低维隐向量**：用下投影矩阵 $W^{DKV}$ 把每个 token 的隐藏状态压成 512 维的 $c_t^{KV}$（K 和 V 共用这一条），推理时缓存里只留它；需要时再用两个上投影矩阵 $W^{UK}$、$W^{UV}$ 还原出各头的 K 和 V。再单开一条 64 维的共享位置分支，缓存就变成 $512+64=576$ 个数——相对同配置的 MHA 压缩 85.3 倍，而论文 Table 1 里它的能力一栏标的是 Stronger（更强）。[【跳转到 02:55】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=175)

## 一、长上下文先撞墙的是 KV Cache，不是算力

### 1.1 一笔账：一个 token 在 V3 里要占 6 MB

UP 主先不解释原理，直接按 DeepSeek-V3 的 config 算一遍 [【跳转到 00:00】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=0)：

- 61 层，128 个注意力头，每头 128 维（不带位置），再加 64 维位置维度；
- 一个 token 在一层里，K 和 V 一共 $128 \times (128+64) \times 2 = 49152$ 个数；
- BF16 每个数 2 字节，一层就是 98304 字节；
- 61 层叠起来，**一个 token 全程要 5,996,544 字节，差不多 6 MB**。

把这个数乘上 128K 上下文：$131072 \times 5{,}996{,}544 \approx 786$ GB。模型权重还没算，缓存已经把一台八卡 80 GB 的服务器吃穿了。

换成 MLA 之后，同一个 token 只存 576 个数，全程 72,072 字节；同样 128K 上下文，单请求只要 9.21 GB，一张 80 GB 的卡能并发 8 个。整张卡全拿来放缓存的话，MHA 只能放 13,340 个 token，MLA 能放 1,138,433 个——**差 85 倍**。[【跳转到 00:25】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=25)

### 1.2 为什么省的是带宽而不是算力

UP 主强调，长上下文推理的钱大半花在**搬运**这份缓存上，不是花在算力上。FlashAttention 那篇论文把这笔账摊得很清楚：A100 的 HBM 是 40–80 GB、带宽 1.5–2.0 TB/s，而片上 SRAM 只有 192 KB、带宽却有 19 TB/s，差一个数量级 [【跳转到 00:50】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=50)。

所以 FlashAttention 用分块（tiling）把那个 $N \times N$ 的注意力矩阵留在片上、不写回 HBM，把 HBM 访问次数最多压到 1/9，注意力计算提速 7.6 倍——但**计算量一分没少**，甚至因为重算还多了一点 [【跳转到 01:15】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=75)。

KV Cache 是另一笔账：它随上下文线性增长，解码每一步都要把整份缓存从 HBM 搬一遍，FlashAttention 帮不了它。于是过去几年大家一直在做同一件事——**把每 token 每层要存的 KV 数往下压** [【跳转到 01:40】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=100)。

### 1.3 按头共享这条路，天花板是 MQA

历史路线可以排成一张条形图，横轴就是「每 token 每层 KV 元素数」：

| 机制 | 每 token 每层元素数 | 相对 MHA | 论文能力列 |
| --- | --- | --- | --- |
| MHA | 49152 | 1.0× | Strong |
| GQA-8 | 3072 | 16.0× | Moderate |
| GQA-4 | 1536 | 32.0× | Moderate |
| MQA | 384 | 128.0× | Weak |
| MLA | 576 | 85.3× | Stronger |

![历史路线：MHA 的 49152 个元素一路压到 MQA 的 384 个，MLA 停在 576 个却把能力列从 Weak 拉回 Stronger](assets/MLA%20低秩%20KV%20压缩：把%20K%20与%20V%20压成一条%20576%20维隐向量/00125.webp)

2019 年的 MQA（Multi-Query Attention，多查询注意力）最狠：所有 query 头共享同一组 K 和 V，每 token 每层只要 384 个数，但质量掉了，论文表里写的是 Weak。2023 年的 GQA（Grouped-Query Attention，分组查询注意力）折中一下，把头分成 8 组、组内共享，3072 个数，能力 Moderate。标准 MHA 每个头独立存，49152 个数，能力 Strong。[【跳转到 02:05】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=125)

![论文 Table 1 的复刻：四种机制每 token KV 缓存的元素数公式，以及能力列 Strong / Moderate / Weak / Stronger](assets/MLA%20低秩%20KV%20压缩：把%20K%20与%20V%20压成一条%20576%20维隐向量/00550.webp)

注意这条路线有一个共同点：**它压的是「存几份」，不是「存什么」**。K 和 V 两个矩阵始终要完整地存下来，只是少存了几份。所以压到 MQA 就到头了——再往下压就得拿质量换。

MLA 走了另一条路：一个 token 只存 576 个数，比 GQA-8 还少五倍多，相对 MHA 是 85.3 倍，但论文表里能力标的是 **Stronger**。这个反差就是整个 MLA 的立项依据。[【跳转到 02:30】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=150)

![GQA 到 MLA 的那一跳：左边是「按头共享」这条路的天花板，右边 MLA 换掉了缓存里到底存什么](assets/MLA%20低秩%20KV%20压缩：把%20K%20与%20V%20压成一条%20576%20维隐向量/00175.webp)

## 二、MLA 的答案：不存 K 也不存 V，只存一个隐向量

### 2.1 联合低秩压缩的三步

MLA 的回答是：**干脆不存 K 也不存 V，把两者一起压进一个低维隐向量，推理时再上投影回各个头**。缓存里躺着的就不再是两个完整的注意力矩阵，而是一串压缩向量。[【跳转到 02:55】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=175)

具体做法分三步 [【跳转到 04:10】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=250)：

1. **下投影**：用 $W^{DKV}$ 把每个 token 的隐藏状态 $h_t$ 压成一个 $d_c$ 维的隐向量 $c_t^{KV}$。DeepSeek-V2 里这个维度是 512。
2. **只缓存一份**：推理时缓存里只有这一个 $c_t^{KV}$，不再存完整的 K 和 V。关键在于 K 和 V **共用同一个隐向量**，所以缓存只留一份而不是两份。
3. **上投影回头**：要用的时候，靠两个上投影矩阵 $W^{UK}$ 和 $W^{UV}$ 把 $c_t^{KV}$ 还原成各头的 K 和 V。

![联合低秩压缩的四步：下投影 → 只缓存一份 → 上投影回各头 → 总缓存公式 (d_c + d_h^R)·l](assets/MLA%20低秩%20KV%20压缩：把%20K%20与%20V%20压成一条%20576%20维隐向量/00275.webp)

### 2.2 对着论文的式子写一遍

对应到 DeepSeek-V2 论文 §2.1.1 的式 (9)(10)：

$$
c_t^{KV} = W^{DKV} h_t
$$

$$
k_t^{C} = W^{UK} c_t^{KV}, \qquad v_t^{C} = W^{UV} c_t^{KV}
$$

注意力输出再过一个输出投影 $W^{O}$。这里值得停一下：**K 和 V 不是分别压的，是共用同一个隐向量**。这是「联合」两个字的含义，也是缓存能只留一份的原因。[【跳转到 04:35】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=275)

### 2.3 超参表：论文数字与 config 字段逐行对拍

UP 主把论文正文 §3.1.2 的超参摆成一张表，再和 HuggingFace 上 `config.json` 的原始字段一一对拍 [【跳转到 05:00】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=300)：

| 字段 | 论文正文 | config.json |
| --- | --- | --- |
| 层数 | 60 层 | `num_hidden_layers` 为 60 |
| hidden 维度 | 5120 | `hidden_size` 为 5120 |
| 注意力头数 | 128 头 × 128 维 | `num_attention_heads` 为 128 |
| KV 压缩维 $d_c$ | 512 维 | `kv_lora_rank` 为 512 |
| query 压缩维 | 1536 维 | `q_lora_rank` 为 1536 |
| 解耦 RoPE 每头维 | 64 维 | `qk_rope_head_dim` 为 64 |

![超参对拍：左边论文正文，右边线上 config.json 的原始字段，逐行对得上](assets/MLA%20低秩%20KV%20压缩：把%20K%20与%20V%20压成一条%20576%20维隐向量/00325.webp)

这不是二手转述，是快照里能 grep 到的字段。压缩维 512 与解耦维 64 是后面所有账的输入。

### 2.4 代价：多出 20.45 M 参数

低秩压缩不是免费的。按 V3 的维度（hidden 7168、$d_c$=512、128 头 × 128 维）算一遍 [【跳转到 05:50】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=350)：

| 矩阵 | 形状 | 参数量 |
| --- | --- | --- |
| $W^{DKV}$ 下投影 | $d_c \times d$ | 3.67 M |
| $W^{UK}$ 的 K 上投影 | $n_h \times d_h \times d_c$ | 8.39 M |
| $W^{UV}$ 的 V 上投影 | $n_h \times d_h \times d_c$ | 8.39 M |
| 合计 | 下投影 + 两路上投影 | 20.45 M |

![参数量账：低秩压缩多出来的三块矩阵合起来约 20.45 M 参数，省的是显存与访存，不是 FLOPs](assets/MLA%20低秩%20KV%20压缩：把%20K%20与%20V%20压成一条%20576%20维隐向量/00400.webp)

也就是说，**MLA 省的是 KV Cache 的显存和 decode 时的访存，参数量和计算量一点没少**，甚至多了一次下投影、两次上投影。这是后面要反复强调的一句话：省显存不省算力。[【跳转到 06:15】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=375)

## 三、位置编码不能塞进低秩主干

### 3.1 RoPE 挡住了矩阵吸收

麻烦从位置编码开始。DeepSeek-V2 正文里有一句写得很直白：**RoPE 与低秩 KV 压缩不兼容**。[【跳转到 06:40】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=400)

原因在矩阵乘法不服从交换律。如果直接在压缩后的键上做旋转位置编码（RoPE，Rotary Position Embedding），那个位置敏感的旋转矩阵会被夹在查询投影和 K 的上投影中间，两个矩阵换不了位置——上投影就没法再被吸收进查询投影。吸收不了，每一步 decode 都得对所有前缀 token 重新算一遍带位置的 key，论文说这会显著拖慢推理。[【跳转到 07:05】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=425)

这个代价有多大？UP 主按 128K 上下文估了一遍：131072 个前缀 token、61 层，不吸收的话每生成一个新 token 都要重新上投影 $131072 \times 61 \approx 799$ 万次；吸收之后每步只需投影当前这一个 token，61 层就是 61 次。两者差 131072 倍。再按 $W^{UK}$ 的 8.39 M 参数、每次乘加算两个 FLOP 估一下，单步多出大约 $1.34 \times 10^{14}$ FLOPs。[【跳转到 07:30】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=450)

> 这是量级估算，不是实测吞吐；但足够说明为什么论文宁可单开一条 RoPE 分支，也不肯让上投影留在计算图里。

### 3.2 解耦 RoPE：一条 64 维的共享旁路

解法叫**解耦旋转位置编码（decoupled RoPE）**。论文的措辞是「用额外的多头 query 和一条共享的 key 来承载位置信息」，具体做法是 [【跳转到 07:55】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=475)：

1. **主干照常压**：不带位置的 query 与 key 一起压进 $c_t^{KV}$；
2. **另开位置分支**：单独生成带 RoPE 的 $q^R$ 和一条共享的 $k^R$，每条 query 头都有自己的 $q^R$，但 **key 只有一条共享的 $k^R$**，每头 64 维；
3. **拼接算注意力**：主干部分和位置部分拼起来再一起做点积；
4. **缓存两样**：一个 512 维的 $c_t^{KV}$，加一条 64 维的共享 $k^R$，合起来 576 个数。

![解耦 RoPE 的四步：主干照常压、另开位置分支、拼接算注意力、缓存两样；关键在共享 key 只有一条](assets/MLA%20低秩%20KV%20压缩：把%20K%20与%20V%20压成一条%20576%20维隐向量/00500.webp)

「key 只有一条、不按头展开」正是能压到 576 的关键。如果反过来，每个头各存一份 64 维位置 key，缓存就变成 $512 + 128 \times 64 = 8704$ 个数，压缩比立刻从 85.3 倍掉到 5.65 倍。[【跳转到 10:00】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=600)

![512+64=576 的来历：576 相当于 2.25 组 GQA 的缓存，而按头展开位置维会变成 8704 个数](assets/MLA%20低秩%20KV%20压缩：把%20K%20与%20V%20压成一条%20576%20维隐向量/00600.webp)

## 四、权重吸收：让上投影从计算图里消失

### 4.1 结合律给出的第二条路

缓存里只有 $c_t^{KV}$，那每算一步注意力都要先把它上投影成 K——这看起来又是一笔开销。MLA 的第二个技巧是**权重吸收（weight absorption）**：靠矩阵乘法的结合律，把 $W^{UK}$ 直接乘进查询投影、把 $W^{UV}$ 直接乘进输出投影，合成新的权重矩阵，离线一次性做完。论文原话说的很重：**推理时甚至不必把 KV 算出来**。[【跳转到 10:50】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=650)

![权重吸收：吸收前每步都要把 c 上投影成 K、V；吸收后 W_UK 进查询投影、W_UV 进输出投影，两条路径的注意力结果一模一样](assets/MLA%20低秩%20KV%20压缩：把%20K%20与%20V%20压成一条%20576%20维隐向量/00650.webp)

按 V3 的维度把三步形状写出来 [【跳转到 11:40】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=700)：

1. 原式：$q = W^{UQ} x$，$k = W^{UK} c^{KV}$，点积是 $q^\top k$；
2. 展开转置：$q^\top k = x^\top (W^{UQ})^\top W^{UK} c^{KV}$，两个上投影挪到了中间；
3. 先乘中间：$(W^{UQ})^\top W^{UK}$ 得到一个 $1536 \times 512$ 的合并矩阵，78 万多个参数，训练完离线算一次就行。

输出侧同理，$W^{O} W^{UV}$ 合并成 $7168 \times 512$。合并之后，decode 每一步只需要拿 $c^{KV}$ 直接参与注意力，上投影这一步从计算图里消失了。

### 4.2 训练侧为什么不能吸收

那训练时为什么不干脆吸收掉？因为要算梯度。训练时上投影必须留在计算图里，梯度要经过 $W^{UK}$ 与 $W^{UV}$ 回传。DeepSeek-V3 正文里专门列了一条叫**重算（recomputation）**：RMSNorm 和 MLA 上投影的输出激活不持久化，用的时候重算——这是用计算换显存。[【跳转到 12:30】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=750)

所以吸收是**推理侧的离线操作**：权重训完、合并一次、存成新权重，之后每一步 decode 都受益。[【跳转到 12:55】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=775)

![训练侧不能吸收：上投影必须留在计算图里让梯度回传，V3 用重算换激活显存；吸收只是推理侧的离线合并](assets/MLA%20低秩%20KV%20压缩：把%20K%20与%20V%20压成一条%20576%20维隐向量/00800.webp)

> 吸收的完整代数推导与 kernel 层面的实现，见同系列 §8.3.3「MLA 中的矩阵吸收技巧」。

## 六、复算与跨模型验证

### 6.1 四种实现，数值等价

光算账不够，UP 主用 torch 手写了四个等价实现验了一遍：固定随机种子，`d_model` 取 512、8 个头、每头 64 维，构造同一套随机权重，让 MHA、GQA、MQA、MLA 表达同一个注意力函数。结果四种实现的前向输出全部 `allclose`，最大绝对误差是零；从压缩隐向量用 $W^{UK}$、$W^{UV}$ 上投影回 K、V，数值也和原始 K、V 完全相等。[【跳转到 16:40】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=1000)

这说明换掉的是**缓存的组织方式**，不是注意力函数本身。同一个小模型里四种实现的每 token 每层缓存元素数分别是 MHA 1024、GQA 256、MQA 128、MLA 128，对应论文表里的四个公式 $2n_h d_h l$、$2n_g d_h l$、$2 d_h l$ 以及 $(d_c + d_h^R)l$。[【跳转到 17:30】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=1050)

![四种实现数值等价、缓存组织不同：玩具配置下 MLA 和 MQA 恰好都是 128 个元素，因为这里的 d_c 取了 128](assets/MLA%20低秩%20KV%20压缩：把%20K%20与%20V%20压成一条%20576%20维隐向量/01050.webp)

小模型里 MLA 和 MQA 恰好都是 128，是因为这个玩具配置下 $d_c$ 取了 128；真模型里维度大得多，差距要到高维才拉开。V2 的真实 $d_c$ 是 512、加 64 维位置共 576，同配置 MHA 是 49152，85.3 倍就是这么来的。所以看这张表别只记数字，要记公式：**缓存跟着头数组数（或压缩维）走**。[【跳转到 17:55】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=1075)

### 6.2 从 V2 到 GLM5.2：512 这个数几乎没动过

把八份 config 摊成一张大表，按每 token 每层缓存的字节数排序：Qwen3-235B 是纯 GQA、4 个 KV 头、1024 字节，排在最省；其余七家——DeepSeek-V2、V2-Lite、V3、V3.2-Exp、GLM5、GLM5.2、Kimi Linear——都用 MLA，`kv_lora_rank` 一律 512，加 64 维位置，576 个数、1152 字节。[【跳转到 18:27】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=1107)

这里能读出一个很硬的结论：**512 这个压缩维从 2024 年的 V2 一路带到 2026 年的 GLM5.2，跨了几家厂商、几代模型，几乎没动过**。变的是别的字段，比如 `index_topk` 和 indexer 的层结构。[【跳转到 18:52】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=1132)

### 6.3 kernel 里：每 token 一条记录

最后把 576 落到 kernel 里。DeepSeek 官方的 FlashMLA 仓库里，`kv_cache_format.h` 只定义三个维度常量：`D_QK` 为 512、`D_ROPE` 为 64、`D_NOPE` 为 448（等于 `D_QK` 减 `D_ROPE`），再加一个每 token 字节数 `bytes_per_token`（量化字节加 scale 字节）。README 写得更直白：每个 token 先把量化数据存完，紧跟自己的 scale。[【跳转到 20:54】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=1254)

关键在结构上：**一条 token 只有一份 64 维位置，没有按 128 头复制**。所以把 576 按 128 头展开成 8704 在 kernel 里根本没有对应的存法——每 token 就是一条 512 维记录，FP8 下 528 字节。作为对照，V3 那一代按 BF16 存 576 个数是 1152 字节；两个数不是一个量，别比大小。[【跳转到 21:19】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=1279)

![kernel 字段与源码字面：D_QK=512、D_ROPE=64、D_NOPE=448，每 token 一条记录，FP8 下 528 字节](assets/MLA%20低秩%20KV%20压缩：把%20K%20与%20V%20压成一条%20576%20维隐向量/01304.webp)

一句话：**MLA 的缓存是每 token 一条记录、不按头展开**，这才是它能压到几百字节的原因。[【跳转到 21:44】](https://www.bilibili.com/video/BV1gTWo6MEag/?t=1304)

## 小结

- 长上下文推理先撞墙的不是算力，是 KV Cache。按 V3 的 config，128K 单请求 MHA 要 786 GB，MLA 只要 9.21 GB，一张 80 GB 卡的并发从 0 变成 8。
- MLA 的做法不是在「共享几个头」上继续做文章，而是**不存 K、也不存 V，把两者一起压进一个 512 维隐向量 $c_t^{KV}$**，缓存公式变成 $(d_c + d_h^R)l$。
- 位置编码必须解耦：RoPE 的旋转矩阵夹在查询投影和 K 上投影之间，吸收不了就每步都要重算全部前缀的 key。于是另开一条 64 维共享位置分支，缓存变成 $512+64=576$。
- 权重吸收靠矩阵结合律，把上投影离线合进查询投影和输出投影，decode 时才真正成立；训练侧因为要算梯度，只能重算，不能吸收。
- 三个压缩倍数分母不同：85.3× 是结构压缩（对同配置 MHA），5.65× 是位置维按头存的对照，14.9× 是官方 93.3% 对 DeepSeek 67B 整模型的降幅。别相加、别换算。
- 省的是显存与访存，不是 FLOPs：多出来的下投影、上投影、训练重算都是实打实的计算开销（约 20.45 M 参数）。
- 四种实现的手写复算最大绝对误差为零，等价性验证过；kernel 里每 token 只有一条记录，64 维位置不按头复制。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| KV Cache | 解码时把历史 token 的 key、value 存下来，避免每步重算 |
| MLA | 多头潜在注意力，把 K 和 V 联合压成一个低维隐向量再缓存 |
| $c_t^{KV}$ | 联合压缩后的隐向量，V2 里 512 维，是缓存里唯一的主体 |
| 下投影 / 上投影 | $W^{DKV}$ 把隐藏状态压小；$W^{UK}$、$W^{UV}$ 把它还原成各头的 K、V |
| 解耦 RoPE | 位置信息不走低秩主干，另开一条 64 维共享 key 分支 |
| 权重吸收 | 用矩阵结合律把上投影离线合进查询/输出投影，推理时不必显式算 K、V |
| 重算 | 训练时不持久化 RMSNorm 与上投影的激活，反向时重算，用计算换显存 |
| MQA / GQA | 所有头共享一组 KV / 分组共享 KV，压的是「存几份」而不是「存什么」 |
