# 大 EP 为什么让 decode 更快：MoE 推理在为权重字节付账

> 视频来源：[大 EP 为什么让 decode 更快｜01/03 系列《大规模专家并行（Wide EP）》](https://www.bilibili.com/video/BV1cHyazsEPA/)（Bilibili · UP 主「何语-P2501」）｜时长约 44 分钟
> 导读：这是一支把账算到小数点后的硬核分析片。UP 主用一张工作站卡实测 + DeepSeek 公开的部署说明，回答一个反直觉的问题：为什么把专家拆到几十张 GPU 上，decode 反而更快？答案是「decode 的一步在为权重字节付账」。本文按他的推导链整理，保留全部关键数字与 roofline 判据。字幕中的口误（`deepsick`、`memory band`、`ROFLIGHT`、`抵扣`、`一部` 等）已订正为 DeepSeek、memory-bound、roofline、decode、一步。

## 本讲要解决的核心问题（SCQA）

**背景**：MoE 模型推理时，每个 token 只走少数几个专家。听上去很省——一个 token 只用 384 个专家里的 6 个，那是不是只读 6 个专家的权重就够了？

**冲突**：不够。decode 一步里，**只要某个专家被用到，就要把它整个读一遍**，哪怕它这次只分到 1 个 token。一个专家 18.8 兆，读它一次至少要 11.5 微秒——而它算 1 个 token 只需要零点几微秒。于是 GPU 的算力单元大部分时间在等显存。

**疑问**：既然瓶颈在「读权重」，那把专家分散到更多 GPU 上，为什么能让 decode 变快？收益从哪来，又到哪里为止？

**回答（中心思想）**：decode 的一步本质上是在**为权重字节付账**。把专家分散到 $E$ 张 GPU 上（Wide EP），每张卡持有的专家变少，一步要读的字节就变少；同时每个专家分到的 token 数会随 $E$ 线性增长，把「读一整个专家」这笔固定开销摊到更多 token 上。但收益有天花板：当每个专家的 token 数超过这张卡的 **roofline**（实测 103 个）时，下限从「读」变成「算」，再变宽就只省字节、不省时间了。[【跳转到 00:44】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=44)

## 一、先把账目摆清楚：模型、布局、token 数

UP 主全片只用一个例子，从头算到尾，这一点非常重要——MoE 的性能讨论一旦离开具体配置就会变成空话。

### 1.1 模型：40 层、每层 384 个路由专家、top-6

例子是 **DeepSeek V4.1-Flash**：40 层，每一层都是 MoE，每层 384 个路由专家，一个 token 用其中 6 个。此外还有一个**共享专家**，每个 token 都要经过它，它从不参与路由。路由专家的权重是 4 位量化，每 32 个权重共用一个 8 位的 scale。[【跳转到 01:53】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=113)

由此可以算出单个专家的体积：

$$
\text{每权重位数} = 4 + \frac{8}{32} = 4.25 \text{ bit} = 0.53125 \text{ 字节}
$$

一个专家 3540 万个权重，乘 0.53125 字节，得 **18.8 兆**——UP 主强调这是「精确值，由格式决定」。一层 384 个专家是 7.22G，全部 40 层是 **288.8G**，远远超过他手上那张 96G 的工作站卡。[【跳转到 05:43】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=343)

这就是「总参数量巨大导致的显存容量压力」最直白的样子：**一张卡连一层的专家都放不下**，更别说 40 层。

### 1.2 布局：注意力 DP64，专家 EP64，张量并行 TP1

DeepSeek 的部署说明随推理服务代码一起发布，写的是 64 到 128 张 GPU。UP 主取 64 张：

- **注意力是数据并行的（DP64）**：每张 GPU 为自己的请求跑注意力，用自己那一份注意力权重和自己的 KV cache；
- **没有张量并行（TP1）**：没有哪张 GPU 和别的 GPU 分摊同一个请求的注意力；
- **只有路由专家分散到这 64 张 GPU 上（EP64）**。

用 DeepSeek 的原话说：张量并行「暂时不用」。[【跳转到 02:43】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=163)

![EP64 布局：384 个专家分给 64 张 GPU，每张 6 个，是连续的一段；一个专家要么在某张 GPU 上，要么不在](assets/大%20EP%20为什么让%20decode%20更快：MoE%20推理在为权重字节付账/00643.webp)

注意这里的「整个的专家，从不切开」——不是把每个专家切一块分给多张卡，而是整个专家落在某一张卡上。这一点决定了后面所有账目的算法。

### 1.3 「一步」里有多少 token

UP 主把最简单的情况叫**单 token 的一步**：一张 GPU 上 64 个 decode token，也就是 64 个请求各生成一个新 token。

这里有个容易混淆的定义，他专门澄清了：**「每张 GPU 的 token 数」严格指这一步里这张 GPU 用自己的注意力处理过的每一个 position**。之后每个 position 对专家来说都是一个普通的 token，被路由到 384 个专家中的 6 个，发往持有它们的 GPU 去做矩阵乘。[【跳转到 04:53】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=293)

因为注意力是数据并行的，别的 GPU 没有这些请求，所以**全组的 token 数就是把每张卡的 token 加起来**：$64 \times 64 = 4096$。UP 主反复强调这是「数出来的，所以是精确值」。

## 二、decode 的时间到底花在哪

### 2.1 vLLM 在 GB200 上的一次运行

UP 主引用了 vLLM 公布的一次运行（GB200，比他的工作站卡快）。那次运行用了**投机解码**：一个小草稿模型先为请求提出接下来的几个 token，再由主模型在同一步里检查它们。所以一个请求在一步里过模型的 position 是 6 个而不是 1 个。[【跳转到 03:58】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=238)

前向计算（模型把所有层完整跑一遍）用了 **21.56ms**，其中：

- **专家 + GPU 之间的交换：13.43ms，占 62%**；
- 注意力 + 挑选要读哪些先前 position 的 indexer：占 13%。

![vLLM 在 GB200 上的一次 decode 一步：6 个 position，前向计算 21.56ms，其中 MoE 部分占大头](assets/大%20EP%20为什么让%20decode%20更快：MoE%20推理在为权重字节付账/00238.webp)

### 2.2 为什么值得检查草稿 token

「因为 decode 是 memory-bound 的：不管一步只装了几个 token，时间大多花在读显存上，所以多几个 position 几乎不费什么。」[【跳转到 04:28】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=268)

这句话是理解全片的钥匙。它有两个推论：

1. 既然时间花在读权重而不是算 token，那**多塞 token 进来几乎免费**——这就是投机解码、大 batch、MTP 在 MoE 上特别划算的原因；
2. 既然时间花在读权重，那**减少要读的权重字节**就是最直接的优化方向——这就是 Wide EP 的立足点。

## 三、一个专家 18.8 兆，读它一次要多久

### 3.1 实测：token 从 1 个加到 128 个，调用时间几乎不变

UP 主在自己的卡上给单个专家计时：喂 1 个 token、2 个、4 个，一路到 128 个，**同样一次调用**：

- 1 个 token 时 **42.6 微秒**；
- 128 个 token 时 **41.6 微秒**。

摊到每个 token：单个时 42.6 微秒，128 个时 $41.6 \div 128 = 0.325$ 微秒，**便宜了 131 倍**。[【跳转到 06:33】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=393)

![token 再少，调用也一样：专家调用的耗时几乎与 token 数无关，是一条水平线](assets/大%20EP%20为什么让%20decode%20更快：MoE%20推理在为权重字节付账/00393.webp)

这条水平线就是 MoE 推理困境的图形化表达：**每次调用都要把整个专家读一遍**。按这张卡实测的读取速率每秒 1641G，18.8 兆至少要 11.5 微秒——这是下限，实际调用还要更慢，因为它「太小，填不满这张卡，一次给的活太少，没法让卡上所有的处理单元都忙起来」。[【跳转到 06:58】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=418)

### 3.2 计算强度：每读一个字节只做 3.765 次乘加

再看专家拿这些字节做了什么。一个权重用在一个 token 上，就是一次乘法加一次加法，2 flops。一个权重占 0.53125 字节，所以

$$
\text{每 token 每字节 FLOPs} = \frac{2}{0.53125} = 3.765
$$

一次调用为它所有的 token **只读一遍权重**，最多 128 个 token，所以它每读一个字节做的 FLOPs（也就是计算强度）等于

$$
\text{计算强度} = 3.765 \times (\text{这次调用里的 token 数})
$$

这就是为什么 token 越多越划算：**读取量不变，计算量线性增长**，计算强度跟着涨。[【跳转到 07:23】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=443)

### 3.3 roofline：这张卡的平衡点是 103 个 token

这张卡自己的比值是：在这个模型的专家乘法上，每秒最多算 **638 万亿 flops**，每秒读 **1641G**——两者都是实测。于是

$$
\text{每字节 FLOPs} = \frac{638 \times 10^{12}}{1641 \times 10^{9}} = 389
$$

一个专家要多少个 token，计算才和读取一样费时？

$$
\frac{389}{3.765} \approx 103
$$

**103 就是这张卡的 roofline**。UP 主对它的定位说得很克制：「它是一个检验，不是预测。」每个专家的 token 更少时，调用在**等读取**；更多时，在**等计算**。至于 kernel 实际跑多快，roofline 不回答。[【跳转到 08:13】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=493)

![这张卡的 roofline：638 TFLOPS/s 除以 1641 GB/s 得每字节 389 FLOPs，再除以 3.765 得 103 个 token](assets/大%20EP%20为什么让%20decode%20更快：MoE%20推理在为权重字节付账/00493.webp)

### 3.4 稀疏不等于省读取：36.5% 的专家根本不用读

MoE 听上去很省：一个 token 只用 384 个专家里的 6 个。但一张 GPU 上有 64 个 token，每个选 6 个：

$$
64 \times 6 = 384 \text{ 次选择}
$$

384 次选择分给 384 个专家，**平均每个专家一次**。UP 主提醒：平均值是对全体合起来成立的，不是对每一个都成立。

把选择看作随机挑选，一个 token 没选中某个指定专家的概率是 $378/384$，64 个 token 全都没选中它的概率是

$$
\left(\frac{378}{384}\right)^{64} \approx 0.365
$$

所以 **36.5% 的专家一个 token 也没分到，根本不用读**；其余 63.5% 被激活，平均是 243.8 个。每个被激活的专家都要整个读一遍：

$$
243.8 \times 18.8\text{ 兆} = 4.58\text{ G}
$$

占这一层的 7.22G 的 63%。而每个被激活的专家平均只分到 $384 \div 243.8 \approx 1.57$ 个 token——离 103 差得远。[【跳转到 09:51】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=591)

这就是「单次激活稀疏导致的访存碎片化」的定量版本：**token 只用了少数专家，但每个被用到的专家都要付一整份读取成本，而摊到它头上的 token 平均只有 1.57 个**。读取被碎片化了，每次读取都填不满带宽，也填不满算力。

## 四、变宽为什么有效：每个专家的 token 数随 GPU 数线性增长

### 4.1 关键公式

把专家分散到 $E$ 张 GPU 上（EP64 就是 64 张），每张卡持有 $384/E$ 个专家。全组 token 数是 $E \times 64$（每张卡带来自己的 64 个）。于是每个专家分到的 token 数是：

$$
\text{每个专家的 token 数} = \frac{\text{每卡 token 数} \times \text{每 token 专家数}}{\text{每卡专家数}}
$$

代入 EP64：$64 \times 6 \div 6 = 64$。UP 主把它写成更直观的形式：因为 $64 \times 6 = 384$ 正好等于专家数，所以**结果正好等于 GPU 数**——4 张卡时每个专家 4 个 token，64 张时 64 个，128 张时 128 个。[【跳转到 13:27】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=807)

![每个专家的 token 数 = 每卡 token 数 × 每 token 专家数 ÷ 每卡专家数](assets/大%20EP%20为什么让%20decode%20更快：MoE%20推理在为权重字节付账/00807.webp)

这个公式只在「DP 等于 GPU 数、每张卡带来自己的 token」时成立；batch 大小不一时就要回到逐个数。但它已经足够说明 Wide EP 的核心机制：**变宽同时做了两件事——每张卡持有的专家变少（读取量下降），每个专家分到的 token 变多（读取被摊薄）**。

UP 主还点破了一个常见的误解：人们常把「每个专家的 token 更多」和「每张 GPU 的专家更少」当成两份可以叠加的收益，其实它们是同一件事的两端——

$$
(\text{每个专家的 token 数}) \times (\text{每卡专家数}) = (\text{每卡 token 数}) \times (\text{每 token 专家数})
$$

等式右边在我们这一步是 384 次选择，**任何宽度都一样**。[【跳转到 17:12】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=1032)

### 4.2 实测：从 4 张卡到 128 张卡，专家耗时 61ms 降到 5ms

UP 主在自己的卡上把整体测了一遍：一张 GPU 在一层上的路由专家工作（64 个 decode token、随机挑选），4 张卡时 1531 微秒，128 张时 126 微秒；乘 40 层（假定每层开销相同）得到每步 **61ms 对比 5ms**。比值不需要估算：$1531 \div 126 = 12$。[【跳转到 30:23】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=1823)

![一张 GPU 的全部专家工作：4 张卡时 61.2ms，128 张时 5.1ms，约 12 倍](assets/大%20EP%20为什么让%20decode%20更快：MoE%20推理在为权重字节付账/01823.webp)

但要看清几件事：

- **时间降得没有字节多**。一张 GPU 的专家从 96 个变成 3 个，每层从 1805 兆变成 56.4 兆（少了 32 倍），时间却只降到 1/12。原因是调用越小，离把这张卡跑满就越远：它达到的读取速率从每秒 1.13T 降到 0.45。[【跳转到 30:48】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=1848)
- **12 倍说的是「每卡做完自己 token 的专家工作」快了 12 倍**，而整组服务的请求是原来的 32 倍（4 张卡 256 个 token，128 张卡 8192 个）。
- **如果请求总数不变**（256 个请求分到 128 张卡），每个专家还是只分到 4 个 token，128 张卡合起来读的字节和 4 张卡一样多——**没有哪次读取被更多 token 分摊，变宽就白变**。[【跳转到 32:24】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=1944)

### 4.3 一整步只快了 1.41 倍：专家之外的部分没变

再看 vLLM 那次运行：从 4 张卡到 32 张，专家部分从 13.43ms 降到 5.95ms（缩小 2.26 倍），但其余部分一直在 10.46 到 10.94ms 之间。所以一整步只从 23.89ms 降到 16.89ms，**每张 GPU 每秒输出的 token 是原来的 1.41 倍**，而专家部分是 2.26 倍。[【跳转到 33:14】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=1994)

![一整步的账：MoE 从 13.43ms 降到 5.95ms，但前向计算之外的草稿模型与采样、以及注意力部分没变](assets/大%20EP%20为什么让%20decode%20更快：MoE%20推理在为权重字节付账/01994.webp)

到 32 张卡时，这一部的其余部分占了 16.89ms 里的 10.94ms，是**大头**。这是个很重要的工程判断：**Amdahl 定律在 MoE 推理里同样成立**，把专家部分优化到极致，也只能拿到整步的一部分收益。

### 4.4 batch 很小时，变宽换不来多少

UP 主还推演了一个极端情况：64 张 GPU 上每张只放 1 个 decode token，全组 64 个 token、384 次选择，平均每个专家 1 个 token——而 roofline 要 103 个。这时一张 GPU 的 6 个专家大多仍被激活（36.5% 的概率一个都没选中），所以读取量只缩小了 1.5 倍；而在每卡 64 个 token 时缩小了大约 16 倍。[【跳转到 34:29】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=2069)

结论：**Wide EP 的收益依赖 batch**。一张 GPU 只读「分到了 token 的专家」，batch 太小时，大部分专家仍被零星激活，变宽省不下多少字节。

## 五、变宽的第二个效应：显存腾出来了

UP 主把「省字节」叫第一个效应，把「省显存」叫第二个效应，并强调**它是独立的**。

四张一组时，一张 GPU 每层持有 96 个专家，40 层下来是 72.2G（67.24GiB）。其余 11.52GB 是两样东西：一是每张 GPU 都完整持有的 9.17（注意力 4.8、嵌入和 lm head 2.47、共享专家 1.32、其他小部件 0.59），二是它分摊的草稿模型 2.35。[【跳转到 19:10】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=1150)

![第二个效应：空间。四张一组时一张 GPU 的路由专家占 67.24GiB，几乎吃掉整张 96GB 卡](assets/大%20EP%20为什么让%20decode%20更快：MoE%20推理在为权重字节付账/01150.webp)

64 张一组时，一张 GPU 每层只持有 6 个专家，4.2GB，其余部分降到 9.94。腾出来的空间全部可以给 **KV cache**：按这个模型的 cache 格式，一个请求（32768 个 token）占 32.1 兆，81.86GB 能放 2000 到 2740 条序列，是四张一组时（577 条）的 4.75 倍。[【跳转到 21:15】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=1275)

这一段把「显存容量压力」的两面都讲清了：**权重占满了显存，KV cache 就没地方放；KV cache 放不下，batch 就上不去；batch 上不去，decode 的吞吐就上不去。** 而 Wide EP 一次解决两件事——每卡权重变小，空出的显存变成并发能力。

## 六、那张量并行呢？DeepSeek 为什么用 TP1

UP 主专门算了一个 DeepSeek **并不使用**的例子：两路张量并行，64 张 GPU 变成 32 队，每队两张卡共用一个 batch。

### 6.1 专家侧：TP 什么也没减半

每队 128 个请求时，32 个 DP rank × 128 = 4096 个 token，×6 = 24576 次选择，分给 384 个专家，每个专家还是 64 个——和 DP64 数出来的一样。**TP 在专家这一侧什么也没减半**。[【跳转到 22:11】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=1331)

### 6.2 注意力侧：KV cache 被重复存了两份

问题出在这个模型的注意力结构上：一个 token 的 KV 是**一个 512 个数的向量**，全部 64 个 query head 都读它。张量并行把头拆开（每张 GPU 32 个），但**一个向量没法按头拆**。所以按 vLLM 的跑法，两张 GPU 都要为全部 128 个请求构建整份 cache，也都要跑 indexer。[【跳转到 23:51】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=1431)

结果：这一对的每张 GPU 都保存全部 128 个请求的 cache（3.82GB），而 DP64 的一张 GPU 是 1.91GB。UP 主顺手引了另一个开源推理引擎 SGLang 的理由：这类只有一个 KV head 的模型，「张量并行会让 KV cache 重复存放，按 DP 来跑 KV cache 就小得多，从而能跑更大的 batch」。[【跳转到 27:03】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=1623)

### 6.3 通信账：多出的 0.4 到 0.7ms，比省下的 0.19ms 还多

这一对真正多出来的是通信：每一层每张 GPU 先要收集另一张的 64 个 token（一个 token 在层与层之间携带 5120 个数），注意力之后两张再把每个结果的两半相加然后分回去。两次交换、每个数二字节，每张 GPU 每层至少发送 1.31 兆，每步 52.4 兆。[【跳转到 28:43】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=1723)

在一个四卡 GB200 节点的两张 GPU 之间，allreduce 最小的一次是 5.3 微秒，NVLink 的 8.7 微秒。这一对每步至少调用 80 次（40 层 × 2），约 **0.4 到 0.7ms**。而少读的字节在 GB200 上省下的下限只有 **0.19ms**（从 1.81ms 降到 1.62ms）。[【跳转到 29:08】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=1748)

DeepSeek 自己的理由写在说明里：**张量并行的通信开销很高，只要模型放得近显存、而且不用它也能满足延迟 SLA，他们就不用。** 所以张量并行是给「放不下的模型」或者「不用它就守不住延迟承诺」的情况用的。DeepSeek 这一步两样都不需要，于是 TP1。[【跳转到 29:33】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=1773)

## 七、到哪里为止：过了 roofline 就是计算

### 7.1 生产环境的一步：每卡约 275 个 token

DeepSeek 线上跑这个模型时用的是自己的投机解码（DeepSeek 的草稿模型为每个请求提出 5 个 token，再由主模型决定验证其中几个）。在它的基准测试集上，每张 GPU 约 60 个请求时，平均每个请求验证 3.58 个草稿 token，加上请求自己的 token 就是 4.58 个 position：

$$
60 \times 4.58 \approx 275
$$

这是估算（请求数是「约 60」，又把一个平均值当成了每一步的值）。[【跳转到 14:42】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=882)

把 275 代进公式：EP64 下每卡 6 个专家，每个专家分到 274.8 个 token；EP8 下每卡 48 个专家，每个专家只有 34.35 个。组里每多一张 GPU，每个专家就多分到 $274.8 \times 6 \div 384 \approx 4.29$ 个 token。所以：

- 在 UP 主这张卡（roofline 103）上，大约 **24 张 GPU** 时一个专家就达到平衡点；
- 在 GB200（roofline 166）上，大约 **39 张 GPU**。

### 7.2 冗余专家：DeepSeek 比 24 和 39 都多

DeepSeek 还为繁忙的专家准备**冗余专家**，每个分担原专家的一部分 token。decode 时它的说明从「每卡一个冗余专家」起步：EP64 下是 6 个专家 + 1 个冗余专家 = 7 份副本；EP8 下是 48 + 1 = 49 份。[【跳转到 34:54】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=2094)

于是每份副本分到的 token 变少：EP64 下 $1648.8 \div 7 = 235.5$ 个（是这张卡 103 的 2.28 倍，GB200 的 166 的 1.42 倍），EP8 下 $1648.8 \div 49 = 33.6$ 个。这解释了为什么 DeepSeek 选的宽度比 24 和 39 都大：**算上冗余专家，每份副本分到的 token 变少了，需要更宽才越过 roofline**。[【跳转到 35:19】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=2119)

### 7.3 下限降了 3.1 倍，不是 8 倍

把读取和计算分别算成下限，取较长的那个：

- **EP8**：49 份副本读取要 $49 \times 11.454 = 561.2$ 微秒；1648.8 次选择的计算要 182.9 微秒。下限由**读取**决定。
- **EP64**：7 份副本读取只要 $7 \times 11.454 = 80.2$ 微秒；计算仍是 182.9 微秒。下限改由**计算**决定。

$$
\frac{561.2}{182.9} \approx 3.1
$$

**从 EP8 到 EP64，副本数少了 7 倍，下限只降了 3.1 倍。** 因为一旦越过 roofline，下限就锁死在计算上，而计算在每种宽度下都得一分不少地做完。[【跳转到 36:34】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=2194)

![它的下限：EP8 由读取决定（561.2 微秒），EP64 由计算决定（182.9 微秒），比值 3.1 而不是 7 或 8](assets/大%20EP%20为什么让%20decode%20更快：MoE%20推理在为权重字节付账/02194.webp)

### 7.4 DeepSeek 的规则：允许多大就用多大

DeepSeek 的说明给了一条很干脆的规则：**decode 时可用的 GPU 允许多大的 EP 和 DP 就用多大**，因为大 EP 能削减专家每一步的访存量。它在超节点上做 decode，64 到 128 张 GPU 由专用链路（NVLink）相连，共用一个超节点，链路的不同任务会互相拖慢，所以 DeepSeek 把整个超节点都给一个 EP 组。[【跳转到 39:54】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=2394)

## 八、代价：80 次交换，以及等最慢的那张卡

UP 主在结尾特意把账的另一半摊开：「这一切都不是免费的。」

1. **通信轮次**：40 层里的每一层，token 都要去到它的专家那里再回来，decode 的一步就有 **80 次交换**——而他在一张卡上的测量一次都没包含这些。
2. **木桶效应**：一步要等**分到活最多的那张 GPU**。按模型真实的路由，有些专家分到的 token 比别的多得多。[【跳转到 40:19】](https://www.bilibili.com/video/BV1cHyazsEPA/?t=2419)

## 小结

- **MoE 的稀疏只省算力，不省读取**：一个专家只要被用到，就要整个读一遍，哪怕只分到 1 个 token。18.8 兆、11.5 微秒的读取，换来的可能只是 0.3 微秒的计算。
- **decode 是 memory-bound 的**：多塞几个 position 几乎免费，所以投机解码、大 batch 在 MoE 上特别划算。
- **一个专家值不值得读，看它分到多少 token**：这张卡的平衡点（roofline）是 103 个 token，由「每字节 389 FLOPs ÷ 每 token 每字节 3.765 FLOPs」算出。
- **变宽同时做两件事**：每卡持有的专家变少（读取量下降），每个专家分到的 token 变多（读取被摊薄）。两者是同一件事的两端。
- **收益有天花板**：过了 roofline，下限变成计算，变宽只省字节不省时间。实测从 EP8 到 EP64 副本少 7 倍，下限只降 3.1 倍。
- **第二个效应是显存**：每卡专家从 67.24GiB 降到 4.2GiB，腾出来的空间给 KV cache，序列容量涨 4.75 倍。
- **张量并行在专家侧帮不上忙**，还会让单 KV head 的模型重复存 KV cache；多出的通信（0.4–0.7ms）比省下的读取（0.19ms）还贵，所以 DeepSeek 用 TP1。
- **代价是通信与木桶效应**：一步 80 次交换，还要等最忙的那张卡。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| Wide EP（大规模专家并行） | 把专家分散到几十张 GPU 上，每张只持有很少几个完整专家 |
| decode 一步 | 每个请求生成一个新 token 的那一轮前向计算；含投机解码时一步有多个 position |
| position | 一步里过模型的一个 token 位置；对专家来说它就是一个普通 token |
| memory-bound | 时间主要花在读显存而不是算数上；MoE decode 的常态 |
| roofline | 读取下限与计算下限的交点；每个专家的 token 数低于它就等读取，高于它就等计算 |
| 计算强度 | 每读一个字节做多少次 FLOPs；这里每 token 每字节 3.765 |
| 冗余专家 | 为繁忙专家额外复制的副本，用来分担 token、缓解热点 |
| 共享专家 | 每个 token 都经过、从不参与路由的专家，每张卡都完整持有 |
