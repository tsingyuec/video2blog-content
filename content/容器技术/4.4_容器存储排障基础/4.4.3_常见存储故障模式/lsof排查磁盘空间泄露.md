# 文件删了磁盘还是满的：用 lsof 揪出「隐形」的已删除文件句柄

> 视频来源：Bilibili 视频 [lsof排查磁盘空间泄露](https://www.bilibili.com/video/BV1nQKU6WEVJ/)（约 1 分 44 秒，中文讲解）。本文基于视频演说图文稿整理，时间戳可跳转到原视频对应位置，配图取自视频画面。字幕来自 B 站 AI 字幕，术语与错拼已逐窗口核对纠正（如 `lsof`、`lsof -n | grep delete | grep data2`、`lsof -p 9340`、`/proc/9340/fd/3`、`df -hT`、`du`）。

## 本讲要解决的核心问题（SCQA）

**背景**：磁盘写满，大家第一反应是「把大文件删掉」。多数时候这招确实有效——删了文件，`df` 一看空间就回来了。[【跳转到 00:00】](https://www.bilibili.com/video/BV1nQKU6WEVJ/?t=0)

**冲突**：线上服务器有一种**最隐蔽**的磁盘故障——**文件已经删掉了，空间却一点没释放**。更麻烦的是，你进到那个目录里 `ls` 一看，**根本看不到任何文件**；用 `df` 看磁盘又是满的。这种「看不到文件、磁盘却满」的现象就是**磁盘空间泄漏（space leak）**。它极具欺骗性，因为用常规命令（`ls`、`du`）根本查不出来。

**疑问**：既然文件都「没有了」，空间到底被谁占着？该用什么工具把它揪出来？找到之后又该怎么安全地释放？

**回答（中心思想）**：空间被**「已被删除、但进程仍然持有打开句柄（file handle）」的文件**占用着——在 Linux 里，删除文件只是**移除文件名指针**，只要还有进程开着这个文件的句柄，**内核就不会回收磁盘空间**。要看到它们，必须用 **`lsof`**：把输出里标记为 **`(deleted)`** 的条目筛出来，就能定位「隐形文件」及其持有它的进程。释放办法有两种：**杀掉进程**（生产环境常常不能停）或**直接清空那个文件句柄**（如 `echo "" > /proc/<pid>/fd/<fd>`）。三种工具的分工是：**`df` 看整体磁盘、`du` 看目录文件、`lsof` 才是排查磁盘泄漏的精准工具**。[【跳转到 01:36】](https://www.bilibili.com/video/BV1nQKU6WEVJ/?t=96)

![展示 `disk_run.py` 脚本：打开 `/data2/big_log.tmp`，以 400MB 为上限持续写入并 `flush`；运行后打印「进程已启动，持续写入文件…」，随后删除数据文件来模拟故障](assets/lsof排查磁盘空间泄露/00014.webp)

脚本的关键动作（视频画面）：

- 启动后打印提示，**此时把数据文件删除**（`rm -f /data2/big_log.tmp`）——这就是「服务正在写盘、文件却被删除」的现场。

> 为什么要模拟这一步？因为生产环境里，**日志轮转、运维脚本、误操作**都会造成「文件被删、进程却还在写」；而运维人员**根本不会另开一个终端**去时刻盯着这件事——故障就这样悄悄发生了。[【跳转到 00:07】](https://www.bilibili.com/video/BV1nQKU6WEVJ/?t=7)

## 二、为什么删了文件空间却不释放：Linux 的删除语义

先看「病象」。用 `df -hT` 看这个挂载点：

```bash
df -hT /data2/
# Filesystem                    Type  Size  Used Avail Use% Mounted on
# /dev/mapper/ubuntu--vg-data2  ext4  452M  401M   17M  96% /data2
```

![`df -hT /data2/` 显示 Use% 已到 96%；`cd /data2/` 后 `ls -A` 却是空的——磁盘满、目录里却没文件](assets/lsof排查磁盘空间泄露/00046.webp)

结果很矛盾：**磁盘已用 96%**（452M 里占了 401M），可 `cd /data2/` 之后 **`ls -A` 什么都没列出来**。空间确实被占了，文件却「看不见」。

**原因是 Linux 的删除语义**：删除文件时，内核做的是**移除「文件名 → 数据」这个指针**；**数据本身只有当「不再有任何进程引用它」时才会被真正回收**。[【跳转到 00:46】](https://www.bilibili.com/video/BV1nQKU6WEVJ/?t=46)

> 打个比方：文件数据像一间房，**文件名是门牌号**。删文件只是**把门牌摘掉**；只要还有进程（人）在里面待着（持有打开的文件句柄），**房间就不会被清空、不会腾出来**。于是你就得到一间「没有门牌、却仍占着地」的隐形房间。

所以「文件删了、空间没释放」的真正含义是：**某个进程还开着那个已经被删掉的文件**。

## 三、用 lsof 定位「隐形文件」

### 3.1 筛出所有 `(deleted)` 的条目

既然常规命令看不到，就换 `lsof`（list open files，列出「当前被进程打开的文件」）。[【跳转到 00:21】](https://www.bilibili.com/video/BV1nQKU6WEVJ/?t=21)

```bash
lsof -n | grep delete | grep data2
```

- **`lsof -n`**：列出被打开的文件；`-n` 表示**不把 IP/端口反解成域名**（避免 DNS 查询拖慢速度）。
- **`| grep delete`**：只留标记为 **`(deleted)`** 的条目——它们就是**「已被删除、但进程仍持有句柄」的隐形文件**。
- **`| grep data2`**：再按路径收窄到这个挂载点。

视频里的输出（关键一行）：

```
python3  9340  root  3w  REG  252,1  419440000  11  /data2/big_log.tmp (deleted)
```

看到 `(deleted)` 且没有目录项，就说明「这个文件在目录里已经不存在了，但**有个 python3 进程还开着它**」。

### 3.2 逐字段读懂 lsof 的输出

把那一行拆开看，每个字段都有用：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| COMMAND | `python3` | **打开该文件的进程名** |
| PID | `9340` | **进程 ID**——后续操作要靠它 |
| USER | `root` | **运行该进程的用户** |
| FD | `3w` | **文件描述符**：`3` 是描述符编号，`w` 是**写入**权限（还有 `r` 读、`u` 读写） |
| TYPE | `REG` | **普通磁盘文件**（相对地，`DIR` 是目录、`CHR` 是字符设备等） |
| SIZE/OFF | `419440000` | **该文件当前占用的字节数**（约 400MB，正是脚本写的上限） |
| NAME | `/data2/big_log.tmp (deleted)` | 文件名，末尾 `(deleted)` 标明已被删除 |

记住这几点：**进程名 + PID + 用户名**告诉你「谁在占」，**FD 里的数字**是后面清空句柄要用的「门牌」，**`(deleted)`** 就是隐形文件的标志。[【跳转到 00:46】](https://www.bilibili.com/video/BV1nQKU6WEVJ/?t=46)

### 3.3 用 `-p` 看某个进程占用的全部资源

如果只想看**某一个进程**打开了什么，用 `-p` 加 PID：[【跳转到 00:46】](https://www.bilibili.com/video/BV1nQKU6WEVJ/?t=46)

```bash
lsof -p 9340
```

![`lsof -p 9340` 列出该进程打开的全部文件：cwd/rtd/txt/mem 等（程序本身、加载的库），最后一行正是 `3w ... /data2/big_log.tmp (deleted)`](assets/lsof排查磁盘空间泄露/00071.webp)

输出会把该进程的所有文件都列出来，包括它自己的可执行文件（`txt`）、加载的共享库（`mem`）、工作目录（`cwd`）、终端设备，以及**那一行关键的 `3w ... big_log.tmp (deleted)`**。一眼就能确认：**就是它占着那 400MB**。

## 四、两种解决办法：杀进程 vs 清空句柄

定位到之后，怎么释放？视频给了两条路。[【跳转到 01:11】](https://www.bilibili.com/video/BV1nQKU6WEVJ/?t=71)

**方法一：杀掉进程，释放资源。**

```bash
kill 9340        # 进程退出 → 句柄关闭 → 内核回收被删文件占用的空间
```

最直接，但**生产环境里这个进程往往不能停**（停了业务就断了），所以常常用不了。

**方法二：不杀进程，直接清空那个文件句柄。**

既然空间被「文件的数据」占着，那就**把这个文件的内容清掉**，同时**不打断进程**：

```bash
echo "" > /proc/9340/fd/3
```

![在 `/proc/9340/fd/3` 上执行 `echo "" > …` 清空句柄后，再 `df -hT /data2/`：Use% 从 96% 掉到 1%，空间被释放](assets/lsof排查磁盘空间泄露/00096.webp)

- **`/proc/<pid>/fd/<fd>`** 是 Linux 提供的「**进程打开的文件描述符**」的访问入口——`/proc/9340/fd/3` 就是 9340 号进程的第 3 号描述符（即那个已删除文件）。
- **`echo "" > …`** 相当于**向该文件写入零字节内容**，把它**清空**。文件句柄依旧被进程持有、进程照常运行，但**被它占用的磁盘空间立刻被释放**。
- 视频验证：清空后再 `df -hT /data2/`，**Use% 从 96% 降到 1%**（Used 从 401M 变为 140K）——空间回来了。

> 权衡：**方法二更快、更「无感」**，适合不能停进程的线上服务；但它清空的是文件内容，**原有日志/数据会丢失**，执行前要确认这份数据确实可以丢弃。**方法一**彻底但会中断服务。

## 五、三种工具的职责边界：df / du / lsof

排查磁盘问题常用三个工具，把它们的「分工」记牢，就不容易踩坑。

- **`df`：看整体磁盘大小**——面向**文件系统**，回答「这块盘一共多大、用了多少、还剩多少」。
- **`du`：看文件目录大小**——面向**目录/文件**，回答「这个目录下的文件各占多大」。
- **`lsof`：排查磁盘泄露**——面向**进程打开的文件**，回答「**谁**开着**哪个**（可能已被删除的）文件」。视频的结论是：这才是排查磁盘泄漏的**唯一精准工具**。[【跳转到 01:36】](https://www.bilibili.com/video/BV1nQKU6WEVJ/?t=96)

为什么 `df` 满、`du` 却对不上？因为 **`du` 只统计目录里「还能看到」的文件**；被删除、但被进程持有的文件**不在任何目录里**，`du` 自然统计不到，只有 `lsof` 能看到它。

## 小结

- **现象**：磁盘满（`df` 显示 96%）但目录里 `ls` 看不到文件——典型的**磁盘空间泄漏**。
- **原因**：Linux 删除文件只移除**文件名指针**；只要进程还持有该文件的**打开句柄**，内核就**不回收空间**。
- **定位**：`lsof -n | grep delete | grep <挂载点>` 筛出 `(deleted)` 条目；读懂 **COMMAND / PID / USER / FD / TYPE / SIZE / NAME** 各字段；也可用 `lsof -p <pid>` 看单进程的全部打开文件。
- **释放**：`kill <pid>`（彻底但会中断进程）或 `echo "" > /proc/<pid>/fd/<fd>`（清空句柄、进程不停，但内容会丢）。
- **工具分工**：`df` 看整体磁盘、`du` 看目录文件、`lsof` 排查泄漏；`df` 满而 `du` 不满，多半就是句柄泄漏。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| 磁盘空间泄漏（space leak） | 文件被删除但空间未释放，导致磁盘满而目录里看不到文件 |
| `lsof` | list open files，列出当前被进程打开的文件；排查句柄泄漏的核心工具 |
| `(deleted)` 标记 | `lsof` 输出中表示该文件已被删除、但进程仍持有其句柄 |
| 文件句柄 / 文件描述符（FD） | 进程打开文件后得到的引用（编号）；只要未关闭，内核就不回收该文件的空间 |
| `lsof -n` | 列出打开的文件且不做 IP/端口反向域名解析（更快） |
| `lsof -p <pid>` | 列出指定进程打开的所有文件 |
| `/proc/<pid>/fd/<fd>` | Linux 中访问某进程某文件描述符的入口，可用于清空被删文件 |
| `echo "" > /proc/<pid>/fd/<fd>` | 向该句柄写入零字节以清空文件、释放空间，且不中断进程 |
| `df` | 显示文件系统（磁盘/分区）的总量、已用、可用 |
| `du` | 统计目录/文件占用大小；看不到已被删除但仍被持有的文件 |
