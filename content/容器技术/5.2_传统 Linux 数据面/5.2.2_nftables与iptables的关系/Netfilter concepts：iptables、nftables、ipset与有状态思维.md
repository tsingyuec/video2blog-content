# Netfilter 概念地图：iptables、nftables、ipset 与「有状态思维」

> 本文整理自 YouTube 视频《Netfilter concepts：iptables、nftables、ipset 与有状态思维》。它不教你怎么背命令，而是帮你搭一张**概念地图**：**netfilter 是内核里的引擎，iptables 和 nftables 只是不同的「控制面板」**。看懂这张图，工具怎么换、语法怎么变，你都能推得动防火墙的行为。

## 本讲要解决的核心问题（SCQA）

**背景**：听到 iptables 和 nftables 这两个名字，很多人以为它们只是「同一个防火墙的两种拼写」，谁用哪个全看发行版偏好。

**冲突**：一旦把它们当成「两套防火墙」，就会陷入两个坑——**换工具就懵**；以及**只知道命令、不知道规则为什么被这样求值**。可真正的内核能力只有一个，工具只是它的不同外壳。

**疑问**：iptables、nftables、ipset 到底是什么关系？它们背后共同的「引擎」是什么？规则按什么顺序生效？「返回流量为什么能自己进来」？

**回答（中心思想）**：这几个名字都指向一个内核级能力——**netfilter**，它是内核里的一组 **hook（检查点）**，在数据包穿越协议栈的特定时刻**检查、修改、接受或丢弃**数据包。**iptables / nftables 是人类用来「描述策略」的接口，真正执行的是 netfilter。** 而 **ipset** 负责「集合化」的大批量匹配，**有状态思维**负责让防火墙管理「会话」而不只是「单个包」，**规则意图（rule intent）**则把所有工具串成一条线——**只要你能说清规则的意图，无论用哪个工具，判断都能保持一致**。

## 一、先立总纲：netfilter 是引擎，工具只是控制面板

**netfilter 是内核级的框架**，Linux 上很多防火墙与包过滤决策，最终都由它强制执行。iptables、nftables 这类工具，只是**人类用来定义策略、再由 netfilter 执行**的方式。

[【跳转到 00:25】](https://www.youtube.com/watch?v=8lL_3hKcMdg&t=25)

![netfilter 是引擎、工具是控制面板：理解这一层，语法变化也不会困惑](assets/Netfilter concepts：iptables、nftables、ipset与有状态思维/00025.webp)

一旦接受「**netfilter 是引擎、工具是不同的控制面板**」这个设定，**即使语法变了，你也能推理防火墙的行为**。

### 1.1 netfilter 的本质：内核里的一组「检查点」

把 netfilter 理解成**内核里的一组 hook**：数据包在网络栈中移动时，可以**在这些检查点被检查、修改、接受或丢弃**。

[【跳转到 01:25】](https://www.youtube.com/watch?v=8lL_3hKcMdg&t=125)

![数据包在协议栈中沿途经过多个处理阶段，netfilter 在其中的关键时刻插入检查点](assets/Netfilter concepts：iptables、nftables、ipset与有状态思维/00125.webp)

一个到达网卡的数据包，**不会凭空出现在应用里**：它要穿过一系列处理阶段，比如**路由决策**和**本地投递逻辑**。netfilter 就沿着这条路径**插入检查点**，让规则在「有意义的时刻」生效。

**这一点为什么重要？** 因为**防火墙行为取决于「规则在什么时候被应用」，而不只是「规则匹配了什么」**：

- 有些规则在**路由之前**生效；
- 有些在**路由之后**；
- 有些则**只作用于发往本机的流量**。

> 考试级别的思考不需要背下每个 hook 的名字，但你要知道：**存在不同的处理阶段，规则可以挂到这些阶段上**。这正是 **chain（链）**和 **table（表）** 的由来——它们是「绑定到不同处理上下文」的规则的**组织结构**。

## 二、iptables：传统的 netfilter 规则接口

**iptables 是配置 netfilter 规则的经典用户态工具**，在很长时间里都是许多管理员在 Linux 上表达防火墙策略的默认方式。

### 2.1 iptables 的模型：表 + 链，按序求值

[【跳转到 02:55】](https://www.youtube.com/watch?v=8lL_3hKcMdg&t=175)

![iptables 模型：规则被组织进表与链，链是一串按顺序求值的规则](assets/Netfilter concepts：iptables、nftables、ipset与有状态思维/00175.webp)

- 规则被组织进**表（table）**和**链（chain）**；
- **链是一条有序的规则列表**，**按顺序逐条求值**；
- 规则匹配数据包的属性，比如**源地址、目的地址、协议、端口**；
- 匹配后施加一个**动作（action）**，例如 **accept（接受）**或 **drop（丢弃）**。

### 2.2 一个关键纠正：iptables 不是「防火墙本身」

初学者常把 iptables 当成防火墙本身，但更准确的说法是：**iptables 是一个「配置接口」，它告诉 netfilter 该做什么**。

[【跳转到 03:20】](https://www.youtube.com/watch?v=8lL_3hKcMdg&t=200)

![iptables 是配置接口而非防火墙本身，这解释了为什么同一内核上还能有别的工具](assets/Netfilter concepts：iptables、nftables、ipset与有状态思维/00200.webp)

**这个区分很有用**：它解释了**为什么同一个内核框架上还可以存在其他工具**。iptables 之所以让人感觉复杂，是因为它**暴露了大量底层概念、并且要求小心处理顺序**；但它也强大，因为它**提供了精确的控制**。用抽象的话说：**iptables 代表「传统的 netfilter 规则接口」**——知道它的**概念角色**，比记住它的精确语法更重要。

## 三、nftables：同一内核的现代化规则框架

**nftables 是更新的规则框架与工具集**，目标是**现代化、简化 netfilter 策略的表达与管理**。

[【跳转到 04:10】](https://www.youtube.com/watch?v=8lL_3hKcMdg&t=250)

![nftables 是一次「规则如何组织与应用」的演进，而不是外加的补丁](assets/Netfilter concepts：iptables、nftables、ipset与有状态思维/00250.webp)

理解它的最好方式，**不是把它当成一个附加项（add-on），而是把它看成「规则如何被组织和应用」的一次演进**：

- 它提供**更统一的语法**，并在**不同种类的流量之间给出一致的模型**，从而降低复杂度；
- 它引入**更灵活的数据结构**，让**规则求值更高效、也更好维护**。

> 考试级要点：**nftables 是通往内核包过滤的另一个接口**，在很多环境中被定位为 **iptables 的继任者**。比起记住「具体功能差异」，更重要的是认清这个**概念关系**：**两者都是「描述规则意图与匹配条件」的方式，再由内核去强制执行**。

[【跳转到 04:35】](https://www.youtube.com/watch?v=8lL_3hKcMdg&t=275)

**不变的那部分**才是要害：**工具可以不同，内核级强制执行的概念始终不变。**

## 四、ipset：让「一大批匹配值」变得可管理

**ipset 是高效处理「大量地址或其他匹配元素」的技术**，它之所以重要，是因为防火墙经常需要**对很多条目应用同一条策略**。

[【跳转到 05:00】](https://www.youtube.com/watch?v=8lL_3hKcMdg&t=300)

![ipset：把大量地址/网络/端口存成集合，一条规则即可引用整个集合](assets/Netfilter concepts：iptables、nftables、ipset与有状态思维/00300.webp)

想象你要**封禁成千上万个已知恶意地址**，或者**放行一串内部网络**——**一个地址写一条规则**很快就会变得**无法维护、而且很慢**。ipset 提供了一种方式：**把地址、网络或端口的集合存进一个结构里，让规则去引用它**，从而**一条规则就能匹配整个集合**。

### 4.1 ipset 的价值：性能 + 可维护性

[【跳转到 05:25】](https://www.youtube.com/watch?v=8lL_3hKcMdg&t=325)

![ipset 的价值：集合可以独立更新，无需重写整份规则列表](assets/Netfilter concepts：iptables、nftables、ipset与有状态思维/00325.webp)

**价值有两层：性能与可维护性**——因为**集合可以在不改写整份规则列表的前提下更新**。这也是它常被作为「考试级概念」的原因：它说明**防火墙不只是「单条规则」，更是「可扩展的策略管理」**。

> 一个初学者必须记住的边界：**ipset 本身不是防火墙**，它是一个**辅助机制**，让防火墙在处理大量匹配值时更高效。

用「规则意图」的语言说：意图可能是「**封禁这一批来源**」，而**集合让这个意图变得可管理**。一旦你把 ipset 看成「**一个被规则引用的列表容器**」，它的角色就清楚了。

[【跳转到 05:50】](https://www.youtube.com/watch?v=8lL_3hKcMdg&t=350)

## 五、有状态思维：防火墙管理的是「会话」，不是「单个包」

**有状态思维是 netfilter 里最重要的概念之一**，因为它解释了**为什么防火墙能放行「会话」，而不只是「单个数据包」**。

[【跳转到 06:15】](https://www.youtube.com/watch?v=8lL_3hKcMdg&t=375)

网络通常是**来来回回的双向交换**。如果防火墙把**每个包都当成互不相关**的个体，那么**想放行正常流量，就不得不开很多过宽的洞**。

**有状态防火墙会跟踪连接状态**——它能识别出「**一个数据包属于一个已建立（established）的会话**」。这就支撑了一种常见的安全姿态：**入站连接受到限制，但「出站连接所对应的返回流量」被自动放行**。

### 5.1 一个大家天天见过的现象

[【跳转到 07:05】](https://www.youtube.com/watch?v=8lL_3hKcMdg&t=425)

![为什么入站受限的主机仍能正常上网：出站请求创建了连接状态，返回包属于已建立会话](assets/Netfilter concepts：iptables、nftables、ipset与有状态思维/00425.webp)

这解释了一个很常见的观察：**一台入站防火墙很严的机器，照样能正常浏览网页**——因为**出站请求创建了连接状态，返回的数据包作为「已建立状态」的一部分被放行**。

**如果没有状态跟踪**，你就得写出复杂的规则来放行返回流量，而这些规则往往**过于宽松**。所以：**有状态思维同时支撑了可用性和安全性。**

> 见到「已建立连接（established connections）」或「返回流量（return traffic）」这类说法时，正确的概念钩子就是——**有状态行为（stateful behavior）**。

### 5.2 不是所有流量都「单端口、好建模」

[【跳转到 07:30】](https://www.youtube.com/watch?v=8lL_3hKcMdg&t=450)

![多端口/动态协商协议的症状：会话能建立、二次数据传输却失败](assets/Netfilter concepts：iptables、nftables、ipset与有状态思维/00450.webp)

有状态思维也帮你理解**为什么某些流量类型表现异常**——尤其是**那些无法整齐落入状态模型的协议**。有些协议**使用多个端口或动态端口协商**，这时**状态跟踪必须识别「相关的连接」，而不只是「一条连接」**。

初学者遇到的表现是：**某个服务「部分能用」**——比如**会话能建立起来，却在二次数据传输时失败**。即便不懂深层协议细节，你也能把这类症状解释为**状态与「相关连接」的问题**：**防火墙放行了会话的一部分，却挡住了另一部分**。

考试级结论：**不是所有流量都是「单端口的一次对话」**，防火墙策略有时必须考虑**多步流程**。但**基本原则不变**：有状态防火墙就是为「连接建立后放行响应流量」这个**最常见情形**设计的。**当你把防火墙看成「会话管理器」而不是「数据包闸门」，你的心智模型会准得多。**

## 六、规则意图：把工具之间的差异「抹平」

**规则意图是让所有这些工具和概念保持一致的那面透镜**，因为它把「低层匹配」与「高层目的」连接起来。

[【跳转到 09:10】](https://www.youtube.com/watch?v=8lL_3hKcMdg&t=550)

![规则意图：一条规则本质是一句策略声明，匹配条件说「怎么识别」、动作说「怎么办」](assets/Netfilter concepts：iptables、nftables、ipset与有状态思维/00550.webp)

**防火墙规则不只是技术性的一行代码，它是一句策略声明**，比如：

- 「允许发往这台服务器的入站安全 Web 流量」；
- 「拒绝来自不受信任网络的入站远程访问」；
- 「允许来自某个子网的内部管理流量」。

[【跳转到 08:45】](https://www.youtube.com/watch?v=8lL_3hKcMdg&t=525)

拆开来看，规则由两半组成：

- **匹配条件**：用**源、目的、协议、端口**等属性来表达「**怎么识别**这些流量」；
- **动作**：表达「**识别到之后做什么**」。

**为什么意图重要？** 因为它**帮你避免过拟合于某个工具的语法**：**无论你用 iptables 还是 nftables 表达，意图可以是同一个**。它还能帮你**识别风险**——**过宽的规则往往违反最小权限，暴露了不必要的服务**。

## 七、顺序与求值：规则列表是一个「决策过程」

[【跳转到 10:00】](https://www.youtube.com/watch?v=8lL_3hKcMdg&t=600)

![顺序与求值：宽泛规则放在前面会覆盖后面的具体规则，把具体放行放到宽泛拒绝之前](assets/Netfilter concepts：iptables、nftables、ipset与有状态思维/00600.webp)

**防火墙规则列表通常是按顺序求值的。** 在 iptables 这类模型里，**第一条匹配的规则就可能决定结果**——这意味着**一条宽泛的规则放得太靠前，会覆盖后面更具体的规则**。

初学者常犯的错是：**写了一条看起来正确的放行规则，却把它放在一条「先命中、先把流量拒掉」的拒绝规则之后**，于是百思不得其解。

**概念上的解法**是：**让规则顺序与意图对齐**——在合适的时候，**把「具体的放行规则」放在「宽泛的拒绝规则」之前**。nftables 可以不同地表达策略，但**「求值结构很重要」这个大原则依然成立**。

### 7.1 ipset 在这里也能帮忙

**这也是 ipset 这类集合发挥作用的地方**：它们能**减少长串的单条匹配规则**，从而**简化求值、让意图更清晰**。

[【跳转到 10:25】](https://www.youtube.com/watch?v=8lL_3hKcMdg&t=625)

> 考试场景里，如果「规则明明存在、流量却仍被挡住」，**规则优先级与顺序**就是一个合理的解释。**理解防火墙不只是一串许可，而是一个决策过程**，才能推理这类情形。

## 八、角色决定「哪些流量类别才重要」

netfilter 概念还包含一层：**流量可以按它与主机的「关系」来分类**，因为防火墙可能对**「发往本机的流量」**和**「穿过本机被转发的流量」**应用不同策略。

[【跳转到 10:50】](https://www.youtube.com/watch?v=8lL_3hKcMdg&t=650)

一台 Linux 机器可以扮演：

- **主机（host）**：接收流量；
- **路由器（router）**：转发流量；
- **或者两者兼有**。

**在容器宿主（container host）上，转发与地址转换（translation）会成为日常工作负载的一部分。** 当机器在转发时，防火墙规则可能要考虑**转发的路径**，而不只是**本地投递**。

[【跳转到 11:15】](https://www.youtube.com/watch?v=8lL_3hKcMdg&t=675)

![机器角色决定关注点：作为路由器时，转发流量的策略变得相关](assets/Netfilter concepts：iptables、nftables、ipset与有状态思维/00675.webp)

**这也是 netfilter 要用 hook 和上下文来设计的原因之一**：数据包可以走不同的路径。**角色化思维把防火墙行为与系统用途连起来**，也解释了为什么**服务器、路由器、容器宿主的防火墙配置各不相同**。

## 九、上层工具：firewalld 与 UFW 都跑在 netfilter 之上

最后要把 netfilter 概念**连回你更早学过的上层防火墙工具**——因为它们**底层常常就是 netfilter**。

[【跳转到 12:05】](https://www.youtube.com/watch?v=8lL_3hKcMdg&t=725)

![firewalld / UFW 是简化管理层，按自己的模型（如 zone 或意图式命令）生成并管理 netfilter 规则](assets/Netfilter concepts：iptables、nftables、ipset与有状态思维/00725.webp)

**firewalld 和 UFW 提供简化的管理层**，按**自己的模型**（比如 **zone（区域）**或**意图式命令**）去**生成并管理 netfilter 规则**。这意味着：**理解 netfilter 概念，仍然能帮你排查 firewalld 或 UFW 的行为**，因为**最终在内核里执行包决策的还是它**。

[【跳转到 12:30】](https://www.youtube.com/watch?v=8lL_3hKcMdg&t=750)

如果上层工具表现异常，**底层的解释往往涉及三件事**：

- **状态（state）**；
- **规则优先级（rule precedence）**；
- **本地流量与转发流量的上下文差异**。

**你不需要退回到裸规则管理，就能从概念理解中受益。** 要点是：**netfilter 是基础，管理工具只是它之上的不同用户体验**。把基础放在心上，你就**不容易被工具差异绕晕，也更可能聚焦于真实的流量与策略意图**。

## 小结

- **总纲**：**netfilter 是内核级引擎**（一组 hook，在包处理旅程的特定时刻生效），**iptables / nftables 只是描述策略的接口**。
- **iptables**：传统接口，把规则组织成**有序的链**，匹配属性后施加 accept/drop 等动作；**它本身不是防火墙**。
- **nftables**：更新的规则框架，用**更统一的语法与一致的模型**简化表达，是 iptables 的继任者。
- **ipset**：把大量地址/网络/端口**集合化**，一条规则即可引用整个集合，兼顾性能与可维护性；它**不是防火墙本身**。
- **有状态思维**：跟踪连接状态，**已建立会话的返回流量自动放行**，兼顾易用与安全；多端口/动态协商协议会带来「部分可用」的症状。
- **规则意图**：关注规则背后的**策略目的**而非语法，帮你设计**最小权限**、判断流量为何被放行或阻挡。
- **顺序与求值**：规则列表是一个**决策过程**，宽泛规则前置会覆盖具体规则，ipset 能减少长串匹配。
- **角色与上层工具**：机器是主机还是路由器，决定哪些流量类别才重要；firewalld / UFW 都跑在 netfilter 之上。

**当你能把这些概念讲成一个连贯的模型，你就有能力在不同工具与环境下，稳稳地推理 Linux 防火墙问题。**

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| **netfilter** | Linux 内核中在内核处理路径上检查、修改、接受或丢弃数据包的框架（一组 hook） |
| **hook（检查点）** | 内核包处理路径上的特定时刻，规则可以挂载到这里生效 |
| **table（表）** | 规则按功能划分的组织结构 |
| **chain（链）** | 绑定到某个处理上下文的、有序的规则列表 |
| **iptables** | 传统的 netfilter 规则配置接口，把规则组织成表与链 |
| **nftables** | 更现代的规则框架，统一语法与模型，常被视为 iptables 的继任者 |
| **ipset** | 把大量地址/网络/端口存成可被规则引用的集合的高效匹配机制 |
| **stateful（有状态）** | 防火墙跟踪连接状态，允许已建立会话的返回流量 |
| **rule intent（规则意图）** | 规则背后的策略目的，独立于具体工具的语法 |
| **firewalld / UFW** | 跑在 netfilter 之上的简化管理工具，按 zone 或意图式命令生成规则 |
