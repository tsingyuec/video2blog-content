# 用户命名空间：福音与隐忧——从容器三大命名空间讲到用 BPF LSM 管住它

> 视频源：[[Linux]Linux 用户命名空间：福音与隐忧](https://www.bilibili.com/video/BV1EbvhBBEsY/)（Bilibili，Cloudflare 工程师 Ignat 的会议演讲，约 39 分钟）。本文基于视频演说图文稿整理，时间戳可跳转到原视频对应位置。

## 本讲要解决的核心问题（SCQA）

**背景**：现代容器其实就是一组 **Linux 命名空间（namespace）**。其中有一个特殊的成员——**用户命名空间（user namespace）**：它能让一个**没有任何特权的普通用户**，在自己的「小世界」里变成 root。无根容器、浏览器标签页沙箱、systemd 处理内核转储，都建立在它之上。

**冲突**：可几乎每一份 Linux 安全指南（比如 Arch Linux 的内核安全指南）都建议**把用户命名空间关掉**。一个「让安全架构更好」的特性，为什么反而被安全圈当成风险点？

**疑问**：用户命名空间到底做了什么？它为什么既是「福音」又是「隐忧」？我们能不能既保留它带来的能力，又管住它带来的风险？

**回答（中心思想）**：用户命名空间靠 **UID 映射**，让非特权进程在命名空间内成为 root，并让这个命名空间**「拥有」其他命名空间**——这正是无根沙箱的地基。但代价是：它把内核里原本只有特权代码才走得到的路径**开放给了普通用户**，于是内核里的普通 bug 被**升级成可被利用的提权漏洞**。二者可以兼得——答案是 **LSM（推荐 BPF LSM）**：按应用白名单，细粒度地决定「谁才允许创建非特权用户命名空间」。[【跳转到 35:23】](https://www.bilibili.com/video/BV1EbvhBBEsY/?t=2123)

## 二、挂载命名空间：从 chroot 到 pivot_root，容器为什么更安全

### 2.1 先理解「文件系统树」

要理解挂载命名空间，必须先有 **文件系统树** 的概念：典型的 Linux 有一个根文件系统挂在 `/`，然后在不同目录下再挂别的文件系统，比如 `/dev`、`/boot`、`/home`。**这一系列挂载点的集合，就是系统上的文件系统树。**

![一套根文件系统加上各处挂载点，构成了系统的「文件系统树」](<assets/[Linux]Linux 用户命名空间：福音与隐忧/00141.webp>)

### 2.2 创建命名空间 = 复制一棵树，然后随便折腾副本

创建挂载命名空间时，**内核会在内部数据结构里把这棵文件系统树复制一份**。关键就在于这份**副本**：你现在可以对副本卸载文件系统、挂载新文件系统，**完全不影响最初的（根）命名空间**。

![创建挂载命名空间时，内核复制一份文件系统树，改动只落在副本上](<assets/[Linux]Linux 用户命名空间：福音与隐忧/00191.webp>)

这正是它对容器化和沙箱有用的原因。

**演示**：讲者在终端里用 `unshare` 创建一个新的挂载命名空间，在里面把某个由 systemd 挂载的 `tmpfs` 卸载掉，验证它「不再被挂载」；而退出之后，**宿主机（根）命名空间毫发无损**——因为改的只是副本。[【跳转到 06:06】](https://www.bilibili.com/video/BV1EbvhBBEsY/?t=366)

### 2.3 chroot：最早的沙箱，为什么不够

`chroot` 是最早的沙箱技术之一，至今仍在用。它的核心思想是：在文件系统里找一个目录，用它启动另一个「类 Linux 环境」，再通过 `chroot` 系统调用，**限制应用程序对宿主机文件系统的视图**。

但它**只在大多数情况下有效**。如果 `chroot` 配置不当，应用仍有多条路影响宿主机文件系统：**打开的文件描述符、`/proc` 文件系统、绑定挂载（bind mount）** 等等。也就是说，你并没有真正把它关进笼子。

### 2.4 pivot_root：容器用的那一招

容器不用 `chroot`，而是执行 **`pivot_root`**——注意，它操作的不是原始文件系统树，而是**那棵副本**。

流程是：先创建一个新的根文件系统，然后执行 `pivot_root`，相当于把文件系统树「掉个头」——**新根成为根目录 `/`，旧根被挪到一个旧目录里**。因为操作的是副本，你可以放心地把旧根卸载掉，再启动那个「可能恶意」的应用。

![pivot_root 把文件系统树掉个头：新根变成根，旧根变成旧目录](<assets/[Linux]Linux 用户命名空间：福音与隐忧/00291.webp>)

**好处**：如果有人试图逃逸，**无处可逃**——因为在这棵文件系统树里，压根没有挂载宿主机的原始文件系统。这比 `chroot` 安全得多。[【跳转到 05:41】](https://www.bilibili.com/video/BV1EbvhBBEsY/?t=341)

## 三、网络命名空间：一个「空盒子」加一条虚拟网线

**网络命名空间隔离的是网络资源**：网络接口、路由配置、防火墙配置、以及各种与网络相关的操作系统参数（比如 TCP 可调参数）。[【跳转到 06:56】](https://www.bilibili.com/video/BV1EbvhBBEsY/?t=416)

它和挂载命名空间的行为**不一样**：创建网络命名空间时，**你得到的不是「复制」，而基本是一个空对象**——唯一的例外是它会给你一个**专属的 loopback（`lo`）实例**。

![创建网络命名空间得到的是「空盒子」，只自带一个 loopback 实例](<assets/[Linux]Linux 用户命名空间：福音与隐忧/00416.webp>)

有了这个空盒子，你就可以**把资源移进去**（比如把某张网卡移入该命名空间），在里面拥有独立于宿主机的路由、防火墙和系统配置。容器环境里常做的另一件事，是创建一种特殊接口——**veth（虚拟以太网对）**。

![veth pair 像一条虚拟网线：从一端发出的数据立刻出现在另一端](<assets/[Linux]Linux 用户命名空间：福音与隐忧/00491.webp>)

**veth 总是成对创建**，两端像被一根虚拟网线连起来：从一端发出的数据，立刻出现在另一端。这很有用——**把一端放进网络命名空间**，就能让两个网络命名空间像两台独立机器一样通信。[【跳转到 08:11】](https://www.bilibili.com/video/BV1EbvhBBEsY/?t=491)

**演示**：讲者先创建网络命名空间（起初只有 loopback，需要手动启用），再创建一个 veth 对并命名为 `left` / `right`，**创建时就让 `left` 直接进入新命名空间**。于是新命名空间里只有 `right`，根命名空间里则多出一个 `left`。两边各配 IP 后 `ping` 通。妙处在于：**一旦退出命名空间，操作系统会自动销毁该命名空间的全部资源，包括对端的那个虚拟接口**。这对各种**测试配置**非常方便——不用手工清理，清掉命名空间就一切复原。[【跳转到 09:26】](https://www.bilibili.com/video/BV1EbvhBBEsY/?t=566)

## 四、PID 命名空间：新空间里的「1 号进程」

内核启动后，最先启动的是 **进程 1（现代系统通常是 systemd）**，由它再启动别的进程，层层展开成**进程树**。

创建 PID 命名空间时，**你得到的同样「不是什么复制」**：你会创建另一个**仍然运行在宿主机上**的进程，但它在**新命名空间里成为 1 号进程**。

![新 PID 命名空间里的进程「同时存在」：在宿主命名空间有某个 PID，在自己空间里是 1 号](<assets/[Linux]Linux 用户命名空间：福音与隐忧/00691.webp>)

换句话说，它**同时存在于两个命名空间**：在宿主机命名空间里它有某个进程号，在自己的空间里它是 1 号，并且作为 1 号还能再创建别的进程。

**演示**：当前 shell 运行在 PID（如）7551，讲者用 `unshare --fork --pid` 创建新的 PID 命名空间，此时 `echo $$` 显示 **1**；但他仍能从 **`/proc` 文件系统里查到自己的原始 ID**——注意，这本身就是一个「容器逃逸」的缩影：他创建了 PID 命名空间，却仍能确定自己在宿主命名空间里的 PID，**因为并没有把 `/proc` 容器化（没有挂载新的 `/proc`）**。再 `ps` 一下，能看到进程树，甚至显示出发生了命名空间切换。[【跳转到 11:56】](https://www.bilibili.com/video/BV1EbvhBBEsY/?t=716)

## 五、用户命名空间：普通用户如何「在自己的世界里变成 root」

前面几个命名空间，讲的是「看得见什么」；用户命名空间讲的是**身份**。

先看常规的用户世界：有一个 **UID 0（root，拥有全部权限）**；还有一批系统用户（`daemon`、`sshd`、`gdm` 等）；以及普通用户（通常是 1000 起的 `alice`、`bob`）。

创建用户命名空间时，**你得到的依然「不是复制」**——但接下来能做一件「魔法」：**建立映射**。你可以把自己的用户，**映射成命名空间里的 root**。讲者说，这是最强大的功能：**把自己映射成 root，你就成了 root**。

![用户命名空间的核心：把某个 UID 映射成命名空间里的 root（UID 0）](<assets/[Linux]Linux 用户命名空间：福音与隐忧/00841.webp>)

讲者说，这是最强大的功能——**把自己映射成 root，你就成了 root**。

![「把自己映射成 root，你就成了 root」——用户命名空间最强大的能力](<assets/[Linux]Linux 用户命名空间：福音与隐忧/00939.webp>)

### 5.1 非特权用户命名空间：不用任何权限也能变 root

对比一下就懂了：

- 创建**挂载命名空间**，需要**管理员权限**；
- 创建**用户命名空间**，**不需要任何权限**——普通用户自己就能建，并在里面成为 root。

这就叫 **非特权用户命名空间（unprivileged user namespace）**，也是后面一切「福音」与「隐忧」的根源。[【跳转到 15:49】](https://www.bilibili.com/video/BV1EbvhBBEsY/?t=949)

### 5.2 但「root」是有边界的：操作会检查「所属」用户命名空间

别高兴太早。如果你只创建了用户命名空间，却去动**初始挂载命名空间**里的东西（比如想挂一个 `tmpfs`），会收到**权限被拒绝**。

原因是用户命名空间很特殊：**它「拥有」属于它的其他所有命名空间**。当一个特权操作发生时，**权限检查针对的是「拥有该命名空间的那个用户命名空间」里的你的 UID**。你在新用户命名空间里是 root，但你想影响的初始挂载命名空间，是由**初始用户命名空间**拥有的——你在那里只是普通用户 1000，所以被拦下。

![用户命名空间「拥有」其他命名空间；特权操作检查的是所属用户命名空间中的 UID](<assets/[Linux]Linux 用户命名空间：福音与隐忧/01034.webp>)

### 5.3 解决办法：在自己的命名空间里干活

既然检查看的是「所属」命名空间，那就**让要动的命名空间归属于你自己新建的用户命名空间**：再创建一个**新的挂载命名空间**（它由你的用户命名空间拥有），然后就能在里面挂 `tmpfs`、改配置——权限检查这次针对的是你自己的用户命名空间，于是放行。[【跳转到 18:29】](https://www.bilibili.com/video/BV1EbvhBBEsY/?t=1109)

这套「用户命名空间 + 它拥有的其他命名空间」的组合，正是构建**非特权容器**与**代码沙箱**的基础。

## 六、福音：非特权用户命名空间的安全价值

从高层看，我们要解决的问题是：应用会接收来自互联网的流量（可能是恶意的），应用本身有漏洞时也可能**变坏**；**没有沙箱**的话，它就能威胁你的整个基础设施。容器化模型允许我们构建沙箱来隔离「潜在恶意的应用」。[【跳转到 19:37】](https://www.bilibili.com/video/BV1EbvhBBEsY/?t=1177)

几个真实例子：

- **Chrome 浏览器**就是这么干的：**每个标签页分配一个专用 Linux 进程**；如果某个标签页变坏，就借助操作系统的内存地址空间隔离把它关住。因为浏览器本身是以**普通用户**运行的（不是 root），它正好**依赖用户命名空间来创建非特权容器**，还在上面再加**第二层沙箱**。
- **systemd 的系统转储（coredump）处理**：把系统核心转储当成**不受信任的输入源**，于是它用用户命名空间**把自己容器化**，从而更安全地处理转储。
- **模糊测试框架、伪 root 应用**等，也常借此构建沙箱。

**结论**：非特权用户命名空间，是**应用程序自建有效沙箱、切实增强安全性的强大工具**。[【跳转到 21:33】](https://www.bilibili.com/video/BV1EbvhBBEsY/?t=1293)

## 七、隐忧：它如何把「内核 bug」升级成「安全漏洞」

但如果你翻开 Arch Linux 的内核安全指南，会发现它**建议禁用用户命名空间**来增强安全性。事实上，**几乎每份安全指南都建议禁用**。既然这么好用，为什么还要关掉它？[【跳转到 21:55】](https://www.bilibili.com/video/BV1EbvhBBEsY/?t=1315)

![发行版的内核安全指南往往开口就建议「禁用用户命名空间」](<assets/[Linux]Linux 用户命名空间：福音与隐忧/01299.webp>)

### 7.1 一个来自 Cloudflare 的内核漏洞故事

- **更早（约 2019 年）**：Cloudflare 的一位工程师在测试 ClickHouse 集群配置时导致**内核崩溃**，并**负责任地把复现步骤报给了内核团队**。当时没人回应、也不被视为关键问题：因为复现需要**特权**，而管理员本来就能用受支持的 API 让系统崩溃，所以「不算严重漏洞」。
- **快进到 2022 年**：讲者本人在折腾网络命名空间时，突然想起这个复现程序，于是**把它放进用户命名空间里再试**——**同样的结果**。

**这就是「内核 bug」被升级为「安全漏洞」的那一刻**：原来的复现需要特权，现在用**非特权用户**就能触发。

![把内核 bug 放进用户命名空间复现，就从「要特权」变成了「人人可触发」](<assets/[Linux]Linux 用户命名空间：福音与隐忧/01379.webp>)

他把这套复现（非特权用户 + 把自己映射成 root + 配置 loopback + 创建用户/网络命名空间 + 在副本里操纵**流量控制**）拿去试，**只要一个数据包经过接口（给自己发个 ping），系统立刻断线/崩溃**。联系公司的 Kubernetes 集群后，他再试一次，竟然**把 Kubernetes 集群也搞崩了**——团队于是开始打补丁。[【跳转到 24:35】](https://www.bilibili.com/video/BV1EbvhBBEsY/?t=1475)

### 7.2 为什么这不是孤例：无特权访问了「特权代码」

一旦开始搜索，会发现这类漏洞**层出不穷**。它们的本质是：

**内核的权限检查通常靠 capability（能力位）**——你在这里拥有某项 capability，才能执行对应的特权操作。问题是，**特权操作里本身也可能有 bug，而且往往测试不够充分**（因为过去只有特权代码能走到那里）。而**非特权用户命名空间让你在没有系统权限的情况下，也能访问到这些代码**。

![权限检查与能力位：特权操作里藏着测试不足的 bug，非特权 userns 让普通用户也能碰到](<assets/[Linux]Linux 用户命名空间：福音与隐忧/01516.webp>)

所以：**用户命名空间本身不是漏洞，但它能把系统里已有的 bug「升级」为安全漏洞**，因此必须加以管控。

## 八、管控之道：从「一关了之」到 BPF LSM 细粒度策略

### 8.1 简单粗暴的做法

- **在内核配置里禁用**用户命名空间——但这要重新编译内核；
- 或改 `max_user_namespaces`（系统允许创建的用户命名空间数量上限），**设为 0** 就再也建不出来。

![把 `max_user_namespaces` 设为 0，就再也创建不出用户命名空间](<assets/[Linux]Linux 用户命名空间：福音与隐忧/01579.webp>)

讲者评价这类做法**像拿大锤砸**——虽然有效，但把好东西一起砸掉了。[【跳转到 26:19】](https://www.bilibili.com/video/BV1EbvhBBEsY/?t=1579)

### 8.2 更温和但没进主线的 sysctl

还有一个大家都推荐的 `sysctl` 参数（`kernel.unprivileged_userns_clone` 一类的开关）：它**保持用户命名空间可用**（Docker 仍能跑），但**不允许非特权用户创建**——于是只有管理员才能建。这个补丁由 **Debian 开发、被 Ubuntu 和 Arch 采用，但从未被上游内核接纳**。[【跳转到 27:09】](https://www.bilibili.com/video/BV1EbvhBBEsY/?t=1629)

**为什么没进主线？** 因为它引发争议：一方说「非特权用户命名空间带来更多漏洞，该禁」；另一方说「不，用户命名空间让架构更安全，不该禁——**问题不在用户命名空间，而在内核的其他 bug，应该去修那些 bug**」。

争论最终落到一个**策略问题**：如何**只允许受信任的应用**（比如 Chrome）创建用户命名空间，同时禁止其他应用？这需要**更细粒度的控制**——于是想到 **LSM（Linux Security Modules，Linux 安全模块）**。[【跳转到 28:20】](https://www.bilibili.com/video/BV1EbvhBBEsY/?t=1700)

### 8.3 Cloudflare 的选择：BPF LSM

市面上有 SELinux、Yama 这类 LSM（讲者曾在三星参与 Android 早期采用 SELinux 的工作）。而 Cloudflare **喜欢 BPF**，于是用 **BPF 来实现 LSM**。

思路很简单：**把安全策略写成代码（BPF 程序）**，挂到内核的**安全钩子（security hook）** 上。当应用尝试使用某个内核功能（比如系统调用）时，**你的程序会被调用并当场做出决策**。

![BPF 安全策略：把程序挂到内核安全钩子上，应用调用相关功能时被拦截决策](<assets/[Linux]Linux 用户命名空间：福音与隐忧/01760.webp>)

**难点一**：Linux 的安全钩子数量有限，得挑合适的位置。他们发现，管控用户命名空间的合理位置**只有 `cred_prepare` 阶段**。但在这个钩子上监控会产生奇怪副作用：**当你阻止用户创建用户命名空间时，用户态收到的错误是「无法分配内存（OOM）」**——因为那段代码**从来没检查该函数的返回码**，失败就一律按 OOM 处理。明明策略返回的是「拒绝权限」，用户却看到「内存不足」，系统一脸困惑。[【跳转到 30:10】](https://www.bilibili.com/video/BV1EbvhBBEsY/?t=1810)

![在错误的位置拦截，会返回误导性的错误码（把「拒绝」显示成「内存不足」）](<assets/[Linux]Linux 用户命名空间：福音与隐忧/01810.webp>)

**难点二**：他们尝试**给内核打补丁让它返回正确的错误码**，结果在上游邮件列表碰壁——先是被告知「`cred_prepare` 安全钩子不是用来做策略决策的」；后来又被告知「也许你需要为**用户命名空间开发一个专用钩子**」。于是他们提交了专用钩子的代码，但**用户命名空间子系统的维护者强烈反对**：他担心一旦开始监管用户命名空间，大家就不再用它，也就无法构建更好的安全架构。这场讨论**持续了六个月**。[【跳转到 31:39】](https://www.bilibili.com/video/BV1EbvhBBEsY/?t=1899)

Linux 是开源项目，人人意见都被听取，**但 Linus 拍板**。讲者向他陈述：我们已经有监管「打开文件」这类操作的安全钩子，却**没有监管「创建非特权用户命名空间」这种更危险操作**的钩子。尽管维护者反对，社区里也有其他维护者支持——**这个钩子最终被合并进主线**（讲者记得是 **Linux 6.2** 起，或 6.1）。[【跳转到 32:44】](https://www.bilibili.com/video/BV1EbvhBBEsY/?t=1964)

![监管「创建非特权用户命名空间」的安全钩子最终进入内核主线](<assets/[Linux]Linux 用户命名空间：福音与隐忧/01964.webp>)

### 8.4 一个「故意很无聊」的策略示例

讲者给出一个完整但**极其没用的** BPF 玩具策略：**只要运行程序的名称以字母 `t` 开头，就允许它创建新命名空间**。流程是：用 C 写一段 BPF 程序（通过特殊宏指定挂到哪个安全钩子，这里对应用户命名空间创建操作）→ 编译得到 BPF 程序本身 → 生成**骨架（skeleton）文件**把程序注入头文件 → 写一个小程序加载它 → **内核执行各种校验后把它挂到钩子上** → 策略开始生效。[【跳转到 33:43】](https://www.bilibili.com/video/BV1EbvhBBEsY/?t=2023)

**演示**：以非特权用户身份尝试创建用户命名空间，**收到正确的错误码「操作不被允许」**；把 `unshare` 程序**改名成以 `T` 开头的 `trust`** 再执行同样操作，**就成功了**——玩具策略生效。[【跳转到 34:58】](https://www.bilibili.com/video/BV1EbvhBBEsY/?t=2098)

![把程序名改成以 `t` 开头，玩具策略就放行——证明按应用白名单管控是可行的](<assets/[Linux]Linux 用户命名空间：福音与隐忧/02098.webp>)

生产环境里策略要复杂得多：他们会**列出所有合法使用非特权用户命名空间的服务**，放行它们、拦下其他——这样攻击者就无法利用当前的内核漏洞。而且用的是**白名单 + 拉取请求**的方式：新服务在生产环境启动、需要合法访问用户命名空间时，**开发者提交 PR 申请权限**即可，非常**对开发者友好**。

## 小结

- **容器 = 一组命名空间**。挂载命名空间「复制」文件系统树，网络/PID/用户命名空间则是「新建」——这个差异决定了各自的行为。
- **用户命名空间的核心是 UID 映射**：它让非特权用户在自己的世界里成为 root，并让这个命名空间**「拥有」其他命名空间**——这是**无根容器、浏览器沙箱、systemd 转储处理**等地基。
- **隐忧在于攻击面**：非特权用户命名空间让普通用户也能碰到**只应特权访问、且测试不足的内核代码**，把内核 bug **升级为可提权的安全漏洞**（Cloudflare 的流量控制崩溃案例就是活例子）。
- **一关了之是「大锤」**；更细粒度的办法是**用 LSM 做策略**。
- Cloudflare 的方案是 **BPF LSM**：把策略写成 BPF 程序挂到内核安全钩子，按**应用白名单**决定谁可以创建非特权用户命名空间。为此还给内核加了一个**专用安全钩子**（约 Linux 6.2 进入主线）。
- 讲者的态度：**非特权用户命名空间是好东西**，值得用它构建更好的应用与无根容器、减少对 setuid 程序的依赖；**但要能控制它**——「我们完全可以两者兼得」。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| 命名空间（namespace） | 限制进程「能看见什么」的内核机制；容器就是一组命名空间的集合 |
| 挂载命名空间 | 给进程一棵**复制的**文件系统树，改副本不影响宿主机 |
| chroot | 早期沙箱，只改应用的根目录视图；配置不当时可被绕过 |
| pivot_root | 容器用它的「掉头」操作：新根成为 `/`、旧根挪走，比 chroot 更安全 |
| 网络命名空间 | 隔离网卡、路由、防火墙等网络资源；自带一个 loopback |
| veth | 「虚拟网线」，成对出现；一端可放进另一个网络命名空间 |
| PID 命名空间 | 新空间里该进程成为 1 号；在宿主命名空间仍有自己的 PID |
| 用户命名空间 | 通过 UID 映射让非特权用户在自己空间里变成 root |
| 非特权用户命名空间 | 不需要任何权限即可创建的用户命名空间；无根容器/沙箱的地基 |
| LSM | Linux 安全模块，用策略在安全钩子上决定内核操作是否放行 |
| BPF LSM | 用 BPF 程序实现 LSM 策略；Cloudflare 用它按白名单管控用户命名空间 |
| `cred_prepare` | 内核安全钩子之一，曾被当作拦截用户命名空间创建的位置 |
