# Pod 内容器通信与共享网络栈

> 本文整理自视频 *Pods and Containers - Kubernetes Networking | Container Communication inside the Pod*（[YouTube 原视频](https://www.youtube.com/watch?v=5cNrTU6o3Fw)），讲清楚一件事：**同一个 Pod 里的多个容器，为什么能像在同一台机器上一样，用 `localhost` 互相访问**。

## 本讲要解决的核心问题（SCQA）

- **背景**：Kubernetes 里最小的调度单位不是容器，而是 **Pod**。一个 Pod 通常只跑一个主容器，但有时会塞进多个容器。
- **冲突**：如果直接在宿主机上跑容器，就得为每个容器做端口映射，容器一多，端口就管不过来；而且大家会疑惑——既然往往只有一个主应用，为什么要多包一层 Pod？
- **疑问**：Pod 这层抽象到底解决了什么问题？同一个 Pod 里的多个容器又是怎么互相通信的？
- **回答（中心思想）**：**Pod 是"自带独立网络命名空间的一台迷你主机"**。它给一组容器分配一个独立的 IP 和一段独立的端口空间，让它们共享同一个网络栈——因此同 Pod 内的容器可以直接用 `localhost:端口` 互相访问，而不同 Pod 之间则不会互相抢端口。

---

## 一、为什么需要 Pod：从"端口打架"说起

### 1.1 容器直接跑在宿主机上时，靠端口映射对外暴露

先看没有 Pod 的世界。假设你有一个 PostgreSQL 容器，应用在容器内监听标准端口 **5432**。当你直接用 Docker 把容器跑在宿主机上时，需要把**宿主机端口**绑定到**容器内端口**：

```bash
docker run -p 5432:5432 postgres      # 宿主机 5432  -> 容器 5432
docker run -p 5000:5432 postgres      # 宿主机 5000  -> 容器 5432（换个宿主端口也行）
```

`docker ps` 会告诉你：宿主机的 5000 端口，映射到了容器内的 5432。要再跑一个 Postgres 容器也没问题——只要把它绑到宿主机**另一个**端口上（比如 5432 和 5001），两个容器各占一个宿主端口即可。

### 1.2 容器一多，端口分配就失控了

![没有 Pod 时，每个容器都要在宿主机上单独分配一个端口](assets/Pod%20内容器通信与共享网络栈/00077.webp)

问题出在规模上：当一台服务器上跑几百个容器时，你怎么记得住**哪些宿主机端口还空着**？随着容器增多，靠人工维护端口映射表会很快变得不可维护。

![容器端口映射的痛点：宿主机端口需要人工分配，越多越乱](assets/Pod%20内容器通信与共享网络栈/00184.webp)

Kubernetes 的解法，就是用一个更高层的抽象——**Pod**——把容器"包"起来。

---

## 二、Pod 就是一台"迷你主机"

### 2.1 每个 Pod 有独立的网络命名空间

**Pod 像一台独立的小机器，拥有自己的 IP 地址**，里面通常跑一个主容器。当一个 Pod 被创建到某个节点上时，它会：

- 获得**自己的网络命名空间（network namespace）**；
- 获得一条到节点底层网络的**虚拟以太网连接（veth pair）**。

![Pod 抽象：为 Postgres 容器提供独立的网络命名空间](assets/Pod%20内容器通信与共享网络栈/00197.webp)

### 2.2 有 IP、有端口空间，Pod 就像一台主机

换个角度看，**Pod 跟你自己的笔记本一样，是一台"主机"**：两者都有 IP 地址，也都有一整段可以分配给内部容器的端口。

![Pod 是一台主机：拥有自己的 IP 地址和可分配的端口范围](assets/Pod%20内容器通信与共享网络栈/00230.webp)

### 2.3 于是，十个都监听 8080 的微服务可以共存

正因为每个 Pod 都是自成一体的隔离机器，你可以在**同一台服务器**上跑 10 个微服务，它们**全都监听 8080 端口也互不冲突**，因为它们分别运行在 10 个不同的 Pod 里。

![没有冲突：不同 Pod 各自持有独立端口空间，8080 可以重复使用](assets/Pod%20内容器通信与共享网络栈/00260.webp)

> 顺带一提，正因为抽象发生在 Pod 这一层，**替换容器运行时**（比如把 Docker 换成别的运行时）时，Kubernetes 的配置基本不用改——它并不绑定在某个具体运行时实现上。

## 三、一个 Pod 里的多个容器：sidecar 模式

既然一个 Pod 往往只有一个主容器，那什么时候会放多个容器进去？答案是：当你需要给主应用配一个**辅助应用**时。

![一个 Pod 里可以有多个容器](assets/Pod%20内容器通信与共享网络栈/00394.webp)

这类"跑在主应用旁边、给它打下手"的容器，被称为 **sidecar（边车）容器**。典型用途包括：

- **备份**：定期给主应用做备份；
- **同步**：多个数据库 Pod 之间同步数据；
- **调度器**、**认证网关**等。

![辅助应用 / sidecar 容器：为主应用提供同步、备份、调度等辅助能力](assets/Pod%20内容器通信与共享网络栈/00418.webp)

## 四、同一 Pod 内容器如何互相通信：localhost

### 4.1 关键原理：它们共享同一个网络命名空间

记住一句话：**Pod 是一台带独立网络命名空间的隔离虚拟主机，而 Pod 里的所有容器都运行在这同一个网络命名空间里**。

![Pod 内的多个容器共享同一个网络命名空间](assets/Pod%20内容器通信与共享网络栈/00429.webp)

这意味着，Pod 里的容器可以**直接用 `localhost` 加端口号**互相访问——就像你在自己笔记本上同时跑多个应用，用 `localhost` 让它们互相调用一样。

### 4.2 实测：在 sidecar 里 curl 主容器的服务

视频里做了一个很直观的实验：建一个 Pod，里面放两个容器——

- 一个 **nginx** 容器（主容器，监听 80 端口）；
- 一个 **curl** 容器（sidecar，镜像里自带 `curl` 和 `netstat`，方便我们进容器验证）。

进入 curl 容器后：

```bash
netstat        # 能看到 nginx 正在监听 80 端口
curl localhost:80   # 直接拿到 nginx 的 "welcome to nginx" 首页
```

去 nginx 的日志里看，这些请求来源都显示为 **localhost**——也就是说，请求是从同 Pod 的 curl 容器发出来的，因为两者共享同一个网络栈。

> 这正是"同一个 Pod 内容器通过 `localhost` 通信"的实证：**同网络命名空间 = 同 IP、同 `localhost`、同端口空间。**

## 五、让共享成为可能的"幕后英雄"：pause（sandbox）容器

### 5.1 每个 Pod 都有一个 pause 容器

上面的共享之所以成立，靠的是每个 Pod 里的一个特殊容器——**pause 容器**，也叫 **sandbox（沙箱）容器**：

![每个 Pod 里都有一个 pause 容器，它与主容器共同持有网络命名空间](assets/Pod%20内容器通信与共享网络栈/00575.webp)

它的**唯一职责**，就是**预留并持有这个 Pod 的网络命名空间**，让 Pod 内所有容器共享。正是 pause 容器，才使得容器之间能够互相通信。

### 5.2 容器挂了 IP 不变，Pod 挂了才换新 IP

pause 容器带来的一个重要特性是**网络身份的稳定性**：

- **容器**崩溃重建时，Pod 依然存在，**IP 地址保持不变**；
- 但如果整个 **Pod** 被销毁重建，新 Pod 会**拿到一个新的 IP 地址**。

![同一 Pod 内的容器共享同一个 IP 地址](assets/Pod%20内容器通信与共享网络栈/00600.webp)

![Pod 被重建后会获得新的 IP 地址](assets/Pod%20内容器通信与共享网络栈/00611.webp)

### 5.3 在 Minikube 里亲眼看看 pause 容器

视频最后演示了怎么"看见"pause 容器。因为 Minikube 跑在虚拟机里，本机的 `docker ps` 看不到集群内的容器，需要先把 Docker 客户端指向 Minikube：

```bash
eval $(minikube docker-env)   # 把 docker 客户端指向 Minikube
docker ps                     # 现在能看到集群里的容器了
```

命令的输出里有一大串 **pause** 容器，它们的名字里都带着**所属 Pod 的名字**——可见每个 Pod 都对应一个自己的 pause 容器。

## 小结

- **Pod 是最小调度单位**，它是对容器的抽象，而不是简单地把容器堆在一起。
- **Pod = 一台自带网络命名空间的迷你主机**：拥有独立 IP 与独立端口空间，所以不同 Pod 即使监听相同端口也不冲突。
- **容器直连宿主机**要靠端口映射，容器一多端口就难管理——这正是需要 Pod 的原因。
- **一个 Pod 可含多个容器**：辅助主应用的容器叫 **sidecar（边车）**，常见于备份、同步、调度、认证网关等场景。
- **同 Pod 内容器通过共享的网络命名空间通信**：彼此可用 `localhost:端口` 直接互访。
- 共享的载体是 **pause（sandbox）容器**：它持有 Pod 的网络命名空间；容器重启 IP 不变，Pod 重建才换 IP。

## 关键术语速查

| 术语 | 一句话解释 |
| :--- | :--- |
| Pod | Kubernetes 的最小调度单位，是一组共享网络（和存储）的容器的封装 |
| 网络命名空间（network namespace） | Linux 提供的网络隔离单元，一个命名空间拥有独立的网卡、IP、路由表和端口空间 |
| veth pair（虚拟以太网对） | 一对虚拟网线，一端在 Pod 命名空间里、另一端在节点上，把 Pod 接进节点网络 |
| sidecar 容器 | 与主容器同处一个 Pod、为主容器提供辅助功能的容器 |
| pause / sandbox 容器 | 每个 Pod 中的"占位"容器，负责持有并共享该 Pod 的网络命名空间 |
| localhost | 指向本机（这里是本命名空间）的地址，同 Pod 容器用它互相访问 |
