# K8S 存储卷的类型与来源：从配置卷、本地卷到网络卷

> 本文整理自 B 站视频《[5.简单懂点K8S的存储(Volume/PV/PVC/StorageClass)](https://www.bilibili.com/video/BV1a3411G7Sh/)》。文中的机制、术语与结论均来自该视频的「图-字幕」图文稿，可逐句核对。本地卷 `emptyDir`、`hostPath` 的动手细节，另见同目录的 [《本地存储卷 emptyDir 与 hostPath》](<B站最清晰讲解,掌握k8s(kubernetes)-本地存储volume卷[emptyDir、hostPath].md>)。

## 本讲要解决的核心问题（SCQA）

**背景（S）**：容器里的数据默认是「用完即弃」的——容器启动时从镜像的可读写层开始，容器一旦重启或销毁，写进去的文件也就没了。这一点和 Docker 里没有挂数据卷时的行为完全一样。[【跳转到 00:00】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=0)

**冲突（C）**：可真实的应用偏偏需要把各式各样的数据带进容器：应用的配置、账号密码这类敏感信息、容器自身的元数据、临时交换的文件、以及必须长期保留的数据。这些数据来源不同、生命周期也不同——有的想随容器一起消失，有的必须比容器活得久。

**疑问（Q）**：Kubernetes 用什么统一的方式，把这些五花八门的数据「挂」进容器？

**回答（中心思想 A）**：Kubernetes 把这些存储资源统一封装成一个叫**存储卷（Volume）**的资源对象，再挂载到容器里使用[【跳转到 00:00】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=0)。所以理解 Kubernetes 存储，第一件事就是搞清楚存储卷**有哪些类型、数据从哪来**。本讲就沿着「来源清单」把存储卷的类型一次讲清，并顺带交代它们在更大框架里的位置（PV/PVC/StorageClass、CSI、快照）。

## 一、K8S 的存储理念：把一切存储统一成「卷」

Kubernetes 的存储理念很朴素：**把各种各样的存储资源统一封装起来**。现实中我们要用的存储五花八门——本地磁盘、NAS、各家公有云的对象存储；Kubernetes 不会为每种存储单独设计一套用法，而是把它们统一封装成一个「存储卷」资源对象，再挂到容器中让我们使用[【跳转到 00:00】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=25)。这套思路和我们熟悉的 Docker 挂载是一样的：把一个文件或目录挂进容器里用。

![K8S 的存储设计理念：把各种存储资源统一封装成「存储卷」再挂进容器](assets/5.简单懂点K8S的存储(Volume／PV／PVC／StorageClass)/00000.webp)

## 二、存储卷的来源：哪些东西能被挂进容器

既然卷是一个「容器」，那**能往里面装什么**就成了关键。视频给出了一张「volume 来源」清单，可以按用途归成四类[【跳转到 01:02】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=62)。

![volume 来源清单：ConfigMap、Secret、Downward API、Projected Volume、Service Account Token 等](assets/5.简单懂点K8S的存储(Volume／PV／PVC／StorageClass)/00062.webp)

### 2.1 配置类：ConfigMap 与 Secret

第一类是「配置」：**ConfigMap** 与 **Secret**。ConfigMap 放的是明文的、应用运行所需的配置；Secret 放的则是需要保密的账号、密码等信息[【跳转到 01:02】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=62)。这类资源的一个共同特点是：**它们要以卷（volume）的形式挂载进容器**，供程序读取。

### 2.2 元数据类：Downward API

第二类是「元数据」：如果容器想**知道自己所属 Pod 的信息**（例如 Pod 的名字、标签），可以用 **Downward API**。它会把这类元数据以文件的方式挂进容器里，让容器自己去读[【跳转到 01:27】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=87)。

### 2.3 组合类：Projected Volume

第三类是「组合」：上面每种对象默认都会各自挂成一个独立的目录；如果你想把**多种来源挂到同一个目录下**，就用 **Projected Volume**。它在自己的 `sources` 下面分别指定每种对象，于是多种来源就被合并挂载到同一个目录，方便在同一个目录里一起使用[【跳转到 01:52】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=112)。

### 2.4 身份凭据类：ServiceAccount Token

第四类是「身份凭据」：应用有时需要调用 API Server，这时靠的是 **ServiceAccount Token**。它的机理是：先为 Pod 创建一个 **ServiceAccount** 对象，该对象会被转换成一份 token 文件挂进容器；容器访问 API Server 时带上这份 token，API Server 就能识别「你是谁」[【跳转到 02:17】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=137)。

![ServiceAccount Token：应用访问 API Server 时携带的身份凭据](assets/5.简单懂点K8S的存储(Volume／PV／PVC／StorageClass)/00137.webp)

## 三、本地存储卷：emptyDir 与 hostPath

讲完「来源」，视频把应用运行中会用到的存储按**生命周期**分成两类：一类是**临时存储**，一类是**持久化存储**[【跳转到 03:21】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=201)。

- **临时存储 `emptyDir`**：生命周期与 Pod 相同——Pod 结束或被删除后，这份临时空间（连同里面的数据）也就没了。它很像 Linux 里的临时目录，会被定时清理。它默认使用磁盘；也可以把 `medium` 设成 `memory`，改用内存来存储，速度更快[【跳转到 03:21】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=201)。
- **持久化存储 `hostPath`**：把宿主机上的文件或目录挂进容器。它常用于「在容器里访问宿主机上的东西」的场景，比如某些安全插件需要读取宿主机的 Docker 文件系统。它的代价是**数据持久化取决于宿主机**，而且**不推荐把有状态的容器数据持久化到宿主机**：因为 Pod 会随调度**发生漂移**——Pod 原本跑在 A 节点，A 节点故障后被调度到 B 节点，此时它之前写在 A 节点上的数据就找不到了[【跳转到 04:11】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=251)。

![本地存储卷：emptyDir 是临时的，hostPath 是宿主机上的持久目录](assets/5.简单懂点K8S的存储(Volume／PV／PVC／StorageClass)/00196.webp)

> 本讲的另外一篇《本地存储卷 emptyDir 与 hostPath》会用完整的实验把这两类卷的机制、目录结构与生命周期跑一遍，这里只做定位。

## 四、网络存储卷：PV、PVC 与 StorageClass

最后一类来源是**网络存储**。我们会用到各种各样的网络存储，它们统一通过 **PV/PVC** 的方式挂载到 Pod 里[【跳转到 05:26】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=326)。围绕它有三个核心概念：**PV、PVC、StorageClass**。

![PV / PVC / StorageClass 之间的关系：Pod 引用 PVC，PVC 绑定 PV，PV 指向真实存储](assets/5.简单懂点K8S的存储(Volume／PV／PVC／StorageClass)/00226.webp)

### 4.1 为什么要 PV 和 PVC

在 Kubernetes 早期其实**没有 StorageClass**，只用 PV 和 PVC 就够了[【跳转到 05:51】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=351)：

1. 存储使用者（比如某个部门）告诉集群管理员「我要用哪一块存储」；
2. 管理员为这块存储创建一个 **PV**——它的含义是「这块存储现在可以在 Kubernetes 里用了」；
3. 用户再创建一个 **PVC**，把它绑定到 PV 上，这样才能真正使用。

也就是说，早期用一次网络存储要走「管理员建 PV → 用户建 PVC 绑定」两步[【跳转到 06:41】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=401)。

### 4.2 StorageClass：把「反复求管理员」变成一次配置

问题在于：每个人都要用存储、需求不断提出，管理员只能不停地手工建 PV/PVC，非常麻烦[【跳转到 07:06】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=426)。于是诞生了 **StorageClass**。新的流程是：

1. 管理员（为某块存储）**一次性**创建一个 StorageClass 对象，放在那里；
2. 某个用户需要 5G 存储时，自己创建一个 PVC，在 PVC 里写明容量（5G）和所用 **storageClass**；
3. 集群里的**存储管理模块 / 存储控制器**（自带支持的存储由 Kubernetes 源码内置，第三方存储则需部署对应的存储控制器到集群中）发现「有一个用到我管理的存储的 PVC 被创建了」，就根据 StorageClass 和 PVC **自动创建一个 PV**，并把它与 PVC 绑定[【跳转到 09:11】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=526)。

此后管理员只需要管一次 StorageClass，剩下的都由用户创建 PVC、系统自动完成[【跳转到 09:36】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=576)。

### 4.3 StorageClass 的常见配置参数

StorageClass 上一般有几类配置[【跳转到 09:36】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=576)：

- **存储提供商（Provisioner）**：这块存储是由谁提供的；
- **回收策略（ReclaimPolicy）**：一般是 `Delete`（不用了、PVC 删除后就把存储也删掉、释放空间），另一种是保留（PVC 删除后 PV 依然保留）[【跳转到 09:54】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=594)；
- **是否允许扩容**：比如申请 PVC 时写 5G，能否扩到 10G——这取决于底层存储本身是否支持扩容[【跳转到 10:19】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=619)；
- **绑定模式（VolumeBindingMode）**：创建 PVC 后是**立刻**与一个 PV 绑定，还是**等到有 Pod 来消费时才创建 PV 并绑定**（前者先锁定存储，后者推迟到真正被使用才占用存储）[【跳转到 10:44】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=644)。

![StorageClass 的典型配置项：Provisioner、ReclaimPolicy、AllowVolumeExpansion、VolumeBindingMode](assets/5.简单懂点K8S的存储(Volume／PV／PVC／StorageClass)/00576.webp)

### 4.4 PV 的状态流转

PV 会经历几种状态，这决定了它当前能不能用[【跳转到 11:28】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=688)：刚创建时会短暂处于 **Pending**，很快变成 **Available**（可以被 PVC 绑定）；被 PVC 绑定后变成 **Bound**；当绑定的 PVC 被删除后，PV 会进入 **Released**。由于 PV 与 PVC 是**一一对应**的，PVC 删除后不能拿一个全新的 PVC 去绑同一个 PV，于是该 PV 要么被删除，要么一直留在 Released（出问题时还可能变成 Failed）[【跳转到 11:53】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=713)。

![PV 的状态流转：Pending → Available → Bound → Released](assets/5.简单懂点K8S的存储(Volume／PV／PVC／StorageClass)/00688.webp)

## 五、存储扩展：In-tree 与 CSI（Out-of-tree）

Kubernetes 自带的存储是**和 Kubernetes 代码库一起发布、紧耦合**的，这种方式叫 **in-tree**（内置）[【跳转到 12:48】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=768)。但如果集群想用公司自研的存储，或第三方存储呢？Kubernetes 提供了另一种扩展方式 **CSI（Container Storage Interface，容器存储接口）**：存储厂商按 CSI 协议开发自己的存储控制器，注册到集群后，使用该存储时 Kubernetes 会去调用这个控制器来创建存储[【跳转到 13:13】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=793)。

这种由存储开发商自己维护、与 Kubernetes 代码相互独立的方式叫 **out-of-tree**，也是现在的趋势——它会逐步把原本 in-tree 的存储驱动都挪到 out-of-tree，于是「集群里要用什么存储，就装什么存储插件」[【跳转到 14:03】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=843)。

![存储扩展：in-tree 内置驱动与 out-of-tree 的 CSI 驱动](assets/5.简单懂点K8S的存储(Volume／PV／PVC／StorageClass)/00763.webp)

## 六、存储快照

最后一个功能是**存储快照**：把磁盘当前的数据形态以快照的形式保存下来，便于后续回退[【跳转到 14:28】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=868)。比如在当前数据上再做别的计算、可能把数据弄坏，就可以用之前的快照把应用恢复回来。

它的设计与 PV/PVC 很相似：用户需要定义一个 **VolumeSnapshot** 对象，它指向一个 **VolumeSnapshotClass**；集群再根据它创建出真正的快照，对应的对象是 **VolumeSnapshotContent**[【跳转到 15:18】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=918)。使用时，把 Pod 所引用的 PVC 上的 `dataSource` 字段指向创建好的 VolumeSnapshot，容器再次启动时就会从快照数据中恢复出来[【跳转到 16:08】](https://www.bilibili.com/video/BV1a3411G7Sh/?t=968)。

![存储快照：VolumeSnapshot / VolumeSnapshotClass / VolumeSnapshotContent 的组织方式](assets/5.简单懂点K8S的存储(Volume／PV／PVC／StorageClass)/00768.webp)

## 小结

- **存储卷是 Kubernetes 的统一抽象**：把各种存储资源封装成「卷」对象，再挂进容器。
- **来源可归为几类**：配置卷（ConfigMap/Secret）、元数据卷（Downward API）、组合卷（Projected Volume）、身份凭据卷（ServiceAccount Token）、本地卷（emptyDir/hostPath）、网络卷（PV/PVC）。
- **本地卷**：`emptyDir` 是临时的，随 Pod 消亡；`hostPath` 挂在宿主机上、能持久，但存在 Pod 漂移导致数据「跟不过去」的风险。
- **网络卷**：通过 PV/PVC/StorageClass 供给。StorageClass 把「管理员反复手工建 PV」变成「一次性建 StorageClass + 用户自助申请」，由存储控制器自动置备并绑定 PV；PV 会经历 Pending→Available→Bound→Released 的状态流转。
- **扩展与快照**：in-tree 驱动与 Kubernetes 紧耦合，CSI（out-of-tree）是扩展标准；快照用 VolumeSnapshot 系列对象实现，用于回退恢复。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| Volume（存储卷） | Kubernetes 统一封装的存储抽象，供容器挂载使用 |
| ConfigMap / Secret | 以卷形式挂进容器的配置 / 敏感信息 |
| Downward API | 把 Pod/容器的元数据以文件形式暴露给容器 |
| Projected Volume | 把多种来源合并挂载到同一个目录 |
| ServiceAccount Token | 应用访问 API Server 的身份凭据 |
| emptyDir | 与 Pod 生命周期绑定的临时卷（可用内存） |
| hostPath | 把宿主机文件/目录挂进容器，持久但有漂移风险 |
| PV / PVC | 集群里的存储资源 / 用户对存储的申请 |
| StorageClass | 描述一类存储、支持自动置备 PV 的对象 |
| Provisioner | StorageClass 里「这块存储由谁提供」 |
| ReclaimPolicy | PV 回收策略：Delete（删）或 Retain（留） |
| VolumeBindingMode | 立即绑定，还是等有 Pod 消费时再绑定 |
| CSI | 容器存储接口，out-of-tree 的存储扩展标准 |
| VolumeSnapshot | 存储快照对象，配合 Class/Content 使用 |
