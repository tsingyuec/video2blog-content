## 本讲要解决的核心问题（SCQA）

**背景**：CNI 的根本诉求很简单——给每个 Pod 发一个全局唯一的 IP，然后让它们互相能说话。Calico 最初的梦想也是让这一切完全透明。

**冲突**：现实很骨感。真实的数据中心和公有云（比如 AWS 或 Azure）规矩极其严苛，底层物理网络有一套死板的**源 IP 地址审查机制**：一旦物理交换机发现你发出的数据包源 IP 不是它分配给物理网卡的那个 IP（比如遇到了未知的 Pod IP），就会毫不留情地把这些报文**静默丢弃**。更糟的是，集群一横向扩容，网络就可能像蜗牛一样慢，监控面板一片绿、没有错误日志，却出现**幽灵般的静默丢包和延迟飙升**。

**疑问**：面对底层网络的严格审查，Calico 到底怎么应对？BGP 原生路由与隧道封装该怎么选？为什么节点一多，网络会变慢甚至卡死？

**回答（中心思想）**：**Calico 有两套生存策略——BGP on underlay（无封装的纯三层路由，追求裸机级性能）与 overlay 隧道（IPIP/VXLAN，用封装绕过网络审查，但带来拆装开销）。** 两者的性能差距**不只是多几十字节封装那么简单**，真正的魔鬼藏在 **CPU 的多核调度（RSS 哈希）** 里；而**现代智能网卡的 VXLAN 硬件卸载**又能把这笔开销抹平。规模大了，还要用**路由反射器（RR）** 解决控制面的 O(n²) 灾难，最后靠 **MTU 与内核 sysctl** 调优兜住"最后一公里"。[【跳转到 00:00】](https://www.bilibili.com/video/BV1Nzb367Ejn/?t=0)

## 一、CNI 的根本诉求，撞上底层网络的"源 IP 审查"

[【跳转到 01:32】](https://www.bilibili.com/video/BV1Nzb367Ejn/?t=92)

CNI 的根本诉求非常简单粗暴：**给每个 Pod 发一个全局唯一的 IP，然后让它们互相能说话**。Calico 最初也想让这一切完全透明。但真实世界的数据中心和公有云（如 AWS、Azure）规矩极其严苛 [【跳转到 01:32】](https://www.bilibili.com/video/BV1Nzb367Ejn/?t=92)：

- 底层物理网络有一套**死板的源 IP 地址审查机制**；
- 一旦物理交换机发现你发出的数据包**源 IP 不是它分配给物理网卡的那个 IP**（比如碰到了未知的 Pod IP），就会**静默丢弃**这些报文。

这种严酷的环境，直接逼着架构师们不得不做出妥协。可以说，**"要不要封装"这个选择，本质上是被底层网络能不能"认识" Pod IP 决定的**。

## 二、两套生存策略：BGP on Underlay 与 Overlay 隧道

[【跳转到 02:27】](https://www.bilibili.com/video/BV1Nzb367Ejn/?t=147)

这两种模式，恰好说明了 Calico 的两套生存策略 [【跳转到 02:27】](https://www.bilibili.com/video/BV1Nzb367Ejn/?t=147)：

- **BGP on underlay 模式**：追求极致性能的"裸机级"方案。它**没有任何额外的隧道头部封装**，纯粹靠 **Linux 主路由表和物理网卡转发**，速度快如闪电。打个通俗的比方，BGP 就像你**直接把信件交给邮递员**，没有伪装、高效透明。
- **Overlay 隧道模式（IPIP、VXLAN）**：为了在受限环境里活下来才发明的。它把 Pod 原始的 IP 报文当成**数据载荷**，在外面套上一层**节点物理 IP 的"马甲"**——就像把一封不符合本地邮局规定的信，**强行塞进一个顺丰的盒子里**去骗过底层网络。虽然成功绕过了审查，但你拆装这个盒子，**不可避免地增加了性能开销**。

一句话：**Underlay 用"能被网络认识"换性能，Overlay 用"封装换通用性"**。

![BGP Underlay：无封装纯三层路由转发，提供裸机级极速吞吐性能 —— 对比 IPIP/VXLAN Overlay：封装报文绕过网络审查，但增加 CPU 拆装开销](assets/BGP%20原生还是隧道封装：Calico%20底层架构解密/00147.webp)

## 三、性能博弈：VXLAN 为什么被 IPIP 甩开，又被智能网卡救回

[【跳转到 03:31】](https://www.bilibili.com/video/BV1Nzb367Ejn/?t=211)

### 3.1 先看数据：打破直觉的基准测试

在没有特殊硬件加速的情况下，跨节点 Pod 通信的吞吐量基准测试结果非常有意思，甚至有点打破工程直觉 [【跳转到 03:31】](https://www.bilibili.com/video/BV1Nzb367Ejn/?t=211)：

| 模式 | 吞吐量 | 说明 |
| --- | --- | --- |
| **BGP（underlay）** | **约 9.2 Gbps** | 几乎榨干了万兆网卡的极限 |
| **IPIP（overlay）** | **约 4.51 Gbps** | 明显低于 BGP，但**远高于 VXLAN** |
| **VXLAN（overlay）** | **约 1.57 Gbps** | 垫底 |

神奇的反转就在这里：**IPIP 居然把 VXLAN 远远甩在后面**。难道仅仅因为 VXLAN 多加了 50 字节的报文头部，性能就会发生这种断崖式暴跌吗？其实**真正的魔鬼隐藏在 CPU 的多核调度里**。

![跨节点 Pod 吞吐量基准对比：揭示网络封装开销的影响（BGP 最高，VXLAN 最低）](assets/BGP%20原生还是隧道封装：Calico%20底层架构解密/00211.webp)

### 3.2 真正的魔鬼：RSS 哈希与"一核有难、多核围观"

刚才的数据是基础测试；可一旦到了**海量并发的企业生产环境**，IPIP 就暴露出一个致命的阿喀琉斯之踵 [【跳转到 04:21】](https://www.bilibili.com/video/BV1Nzb367Ejn/?t=261)：

- **IPIP 使用的是协议号为 4 的纯三层封装**，它**压根没有 TCP 或 UDP 的端口号**这个概念；
- 而现代高速服务器极其依赖网卡的 **RSS（Receive Side Scaling，接收端缩放）技术**：它靠计算数据包的**四元组哈希值**，把巨大流量均匀分配给各个 CPU 核心；
- **但 IPIP 没有端口号，哈希算不出来**——结果成千上万的并发连接最后全部挤在**同一个 CPU 核心**上。这就是典型的**"一核有难、多核围观"**：单核满载，网络就这样被活活憋死。

**反观 VXLAN**：它巧妙地把流量**封装在 UDP 里**，那些动态变化的 **UDP 源端口**完美激活了 RSS 引擎，让流量在所有 CPU 核心上**均匀打散**。这正是 VXLAN 在基础测试中"暂时落后"、却在真实并发场景中"翻盘"的底层原因。

![IPIP 缺乏端口号导致网卡 RSS 哈希引擎失效，引发极端单核性能瓶颈](assets/BGP%20原生还是隧道封装：Calico%20底层架构解密/00261.webp)

### 3.3 反转：智能网卡硬件卸载抹平 VXLAN 开销

[【跳转到 05:11】](https://www.bilibili.com/video/BV1Nzb367Ejn/?t=311)

不过，当我们引入**现代基础设施**时，游戏规则被彻底改变了 [【跳转到 05:11】](https://www.bilibili.com/video/BV1Nzb367Ejn/?t=311)：

- 现在的高速**智能网卡普遍内置了对 VXLAN 协议的硬件卸载引擎**；
- 原本需要消耗大量 CPU 周期去计算的**巨型封包和解包动作**，被直接下放到**网卡硬件层面**，瞬间就能完成——等于**免了 CPU 的税**；
- VXLAN 原本高昂的报文开销被**直接抹平**，再配合上**完美的多核哈希调度**，它的极限吞吐能力被瞬间释放出来。

这段逻辑值得记住：**同一套封装，CPU 来做是负担，网卡来做几乎是免费的**。这也解释了为什么"选 IPIP 还是 VXLAN"不能只看协议头部大小。

![智能网卡硬件卸载引擎完美接管巨型封包计算，彻底抹平高昂的封装开销](assets/BGP%20原生还是隧道封装：Calico%20底层架构解密/00311.webp)

## 四、规模上来了：控制面灾难与路由反射器

[【跳转到 06:10】](https://www.bilibili.com/video/BV1Nzb367Ejn/?t=370)

如果你有一个允许跑 BGP 的优质底层网络、并且想追求极致性能，那么当你**扩大集群规模**时，就必须面对**控制平面的灾难**了 [【跳转到 06:10】](https://www.bilibili.com/video/BV1Nzb367Ejn/?t=370)：

- Calico 默认开启的是 **BGP 全网状（full mesh）拓扑**——**每个节点都要和其他所有节点保持长连接**；
- 几台机器时你没感觉，可一旦节点规模突破 **100 大关**，这种 **O(n²)** 的复杂度就会像脱缰野马，疯狂吞噬控制平面的 **CPU 和内存**；
- 这时你新建一个 Pod，网络可能要**卡很久才能通**。

拯救一切的终极方案就是部署**路由反射器（Route Reflector，RR）** [【跳转到 06:35】](https://www.bilibili.com/video/BV1Nzb367Ejn/?t=395)：它就像一个巨大的**网络通信枢纽**，把原本极其复杂的**全网状连接**瞬间降维成高效清爽的**星型模型**——每个普通节点只需和少数几个反射器建立连接，由反射器负责把路由再分发给其他节点。

![路由反射器（RR）：将全网状拓扑降维成星型辐射组网，彻底解决大规模集群控制面瓶颈](assets/BGP%20原生还是隧道封装：Calico%20底层架构解密/00425.webp)

**在生产环境落地的三步操作** [【跳转到 07:05】](https://www.bilibili.com/video/BV1Nzb367Ejn/?t=425)：

1. 在集群里挑几个稳定的节点，给它们打上**路由反射器的标签**；
2. 给它们配置**全局统一的 cluster id**，赋予它们反射器的合法身份；
3. 创建一个 **BGPPeer 资源**发号施令，让所有普通工作节点**切断彼此之间的私下联系，转而只跟这些中心反射器建立连接**。

搞定这三步，庞大的集群就能在**频繁创建/销毁 Pod** 时依然稳如老狗，保持极速的路由收敛。

![路由反射器三步部署逻辑：标记节点 → 配置集群 ID → 建立对等连接](assets/BGP%20原生还是隧道封装：Calico%20底层架构解密/00450.webp)

## 五、最后一公里：MTU 与内核 sysctl 调优

[【跳转到 07:50】](https://www.bilibili.com/video/BV1Nzb367Ejn/?t=470)

### 5.1 MTU：吞吐量低下和幽灵丢包的头号嫌疑

这是一张"价值百万"的踩坑备忘录：**MTU（最大传输单元）配置适当，绝对是集群吞吐量低下和幽灵丢包的头号罪魁祸首** [【跳转到 07:50】](https://www.bilibili.com/video/BV1Nzb367Ejn/?t=470)。

- 因为隧道协议加了额外的头部：**IPIP 加了 20 字节，VXLAN 加了 50 字节**；
- 如果你的物理网卡 MTU 还是标准的 **1500**，而你又没把虚拟接口的 MTU 降下来，**Linux 内核就会被逼着对每一个大数据包进行极其昂贵的 IP 分片和重组**，吞吐速度瞬间崩溃。

记住这个口诀：**如果底层不支持巨型帧（Jumbo Frame），BGP 设 1500、IPIP 设 1480、VXLAN 必须设 1450。** 如果能在物理交换机上开启巨型帧，整体性能还能再翻个倍。

![MTU 配置：数据包路径上的分片与重组（封装让可用 MTU 变小）](assets/BGP%20原生还是隧道封装：Calico%20底层架构解密/00470.webp)

### 5.2 内核参数：给突发流量留够缓冲

[【跳转到 08:47】](https://www.bilibili.com/video/BV1Nzb367Ejn/?t=527)

除了 MTU，**Linux 内核参数也必须跟上节奏**。面对微服务架构下高频的短连接浪涌，系统默认的那点参数简直不堪一击，你必须大刀阔斧地去调 `sysctl` [【跳转到 08:47】](https://www.bilibili.com/video/BV1Nzb367Ejn/?t=527)：

- **`nf_conntrack_max` 拉升到 100 万以上**，彻底杜绝业务高峰期连接表被打满导致的丢包；
- **`rmem_max` / `wmem_max` 拉高到 128MB**，同时**扩大 TCP 缓冲区**——这好比拓宽了高速公路的匝道，只有给足网络缓冲空间，集群才能在突发流量的猛烈冲击下稳如泰山。

![关键内核 sysctl 调优：nf_conntrack_max 提到 100 万以上；rmem_max/wmem_max 提高到 128MB；TCP 缓冲同步扩大](assets/BGP%20原生还是隧道封装：Calico%20底层架构解密/00527.webp)

## 小结

- **问题的根源**：底层物理网络会按**源 IP** 审查，Pod IP 不被认识就被静默丢弃——这正是"要不要封装"的由来。
- **两套生存策略**：**BGP on underlay** 无封装、纯三层路由、裸机级性能；**Overlay 隧道（IPIP/VXLAN）** 用封装绕过审查，代价是拆装开销。
- **性能博弈不只看头部大小**：基础测试里 BGP ≈ 9.2 Gbps、IPIP ≈ 4.51 Gbps、VXLAN ≈ 1.57 Gbps，但真正的魔鬼是 **RSS 哈希**——IPIP 没有端口号导致流量挤在一个 CPU 核上；VXLAN 用 UDP 源端口打散流量。
- **硬件卸载是反转点**：智能网卡内置 VXLAN 卸载，把封包/解包下放到硬件，几乎抹平封装开销。
- **规模化的代价**：BGP 全网状是 O(n²)，节点上千就压垮控制面；用**路由反射器（RR）** 把拓扑降维成星型（标记节点 → 配 cluster id → 建 BGPPeer）。
- **最后一公里**：MTU 要随封装下调（BGP 1500 / IPIP 1480 / VXLAN 1450），并调大 `nf_conntrack_max`、`rmem_max`、`wmem_max` 等内核缓冲，才能扛住突发流量。

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| **Underlay** | 底层网络转发，直接依赖物理/三层网络，不额外封装 |
| **Overlay** | 叠加网络，把 Pod 报文封装后再跨节点传输（IPIP/VXLAN） |
| **BGP** | 边界网关协议；Calico 用它宣告并学习 Pod 网段路由 |
| **IPIP** | 一种三层隧道封装（协议号 4），无端口号，跨节点封一层 |
| **VXLAN** | 用 UDP 承载的隧道封装，有 50 字节开销，但源端口能激活 RSS 负载均衡 |
| **no-encap** | 不封装模式：完全不打隧道，靠 BGP 直接转发 |
| **RSS** | Receive Side Scaling，网卡按四元组哈希把流量分给多个 CPU 核 |
| **巨型帧** | Jumbo Frame，MTU 大于 1500 的以太网帧；开启后可减少分片、提升吞吐 |
| **MTU** | 最大传输单元；封装会缩小可用 MTU，配置不当引发分片与丢包 |
| **路由反射器（RR）** | BGP 中用于避免全网状连接的角色，把拓扑降维成星型 |
| **cluster id** | BGP 中标识集群的 ID，路由反射器部署需要全局统一配置 |
| **BGPPeer** | Calico 的自定义资源，用来声明 BGP 对等连接关系 |
| **nf_conntrack_max** | 内核连接跟踪表容量上限，过小会在高并发下丢包 |
| **rmem_max / wmem_max** | 套接字读/写缓冲上限，调大可提升突发流量承载能力 |
| **sysctl** | Linux 内核参数的运行时配置接口 |
| **eBPF** | 内核级可编程技术；新一代数据面可绕过 iptables，提升性能 |
