## 本讲要解决的核心问题（SCQA）

**背景（S）**：Cilium 是 CNCF 的毕业项目，很多托管 K8s 把它当作默认或核心的网络与安全底座。

**冲突（C）**：它和 Calico、Flannel 有一个根本区别——**Cilium 的整个数据面建立在 eBPF 之上**。它不在 iptables 里堆规则，而是把**网络、安全、可观测**三件事**全部编译进内核里跑**。这也让它的源码体量惊人：光 Go 代码就 **91 万行**，外加 300 多个 eBPF C 文件。它到底凭什么「复杂」？又复杂在哪儿？

**疑问（Q）**：Cilium 为什么能同时做网络、安全、可观测三件事？它的核心设计思想是什么？

**回答（中心思想 A）**：Cilium 的钥匙有两把——**一是 eBPF**，让内核变成可编程的、把逻辑从慢路径搬进内核快路径；**二是「身份（identity）而不是 IP」**，让策略不再绑死会漂移的地址。围绕这两点，它把网络、安全、可观测合并成**同一份身份、同一套数据面**，所以策略写完、四件事自动对齐。

## 一、Kubernetes 只提要求，没给实现

起点要从 Kubernetes 自己说起：**K8s 自己不实现网络**，它只提出三条**硬要求**：

1. **每个 Pod 一个独立 IP**，不借用宿主机的、不共享；
2. **任意两个 Pod 之间必须能直接通信**，中间不能做地址转换，对方看到的就是 Pod 的**真实 IP**；
3. **每个节点都要知道其他节点上的 Pod 网段怎么走**。

注意，**这三条只规定了「结果」，没规定「手段」**——用什么封装、用什么转发、要不要经过用户态，K8s 一概不管。**这个空白，就是所有 CNI 方案分道扬镳的地方**，也是后面每一次对比的基准。

## 二、分叉：传统 iptables 路线 vs eBPF 原生路线

同样是为了让 Pod 互通，两条路线差别巨大：

| | 传统路线（iptables） | Cilium（eBPF） |
| :--- | :--- | :--- |
| 规则形态 | 所有规则用**链表**串起来，逐条**遍历匹配** | 查**哈希表** |
| 匹配依据 | 基于 **IP 和端口** | 基于**身份** |
| 服务负载均衡 | 额外跑一个 **kube-proxy** | eBPF 原生实现 |
| 规模变化 | 地址一变就得重算，规模一大**规则数就爆炸**、更新越来越慢 | 查表，规模几乎不撞上限 |
| 能力上限 | 三、四层 | 一路做到**第七层**（HTTP、gRPC） |
| 可观测 | 需外挂 | **原生内置** |

一句话：**传统路线把规则堆进内核的链表中，Cilium 把逻辑编译进 eBPF 程序**。

## 三、eBPF 是什么：内核里的可编程钩子

要理解 Cilium，得先理解 **eBPF**。**它不是内核模块**，而是 Linux 内核自带的一套**安全沙箱**：

1. 你用 **C 写一段逻辑、编译成字节码**；
2. 由内核的**验证器**检查，保证它不会把内核搞崩、而且**一定会终止**；
3. 然后 **JIT 编译器**把它翻译成 CPU 原生指令，**直接在内核态运行，不落到用户态**；
4. 触发是**事件驱动**的：网卡收包、发包、进程发起连接，或者某段内核代码被执行，都可以挂程序；
5. 程序之间的状态放在 **map** 里——一张**内核和用户态共享的哈希表或数组**。

**一句话：eBPF 让内核变得可编程，而且不用改内核、不用加载模块、不用重启任何服务。**

## 四、身份（identity），而不是 IP

第二个核心是**身份**。在微服务环境里，**Pod 的 IP 可能只活几秒钟**——拿它当安全边界，等于**把门牌号当身份证**。

Cilium 干脆**不用 IP 当身份**，它把一组**标签集合映射成一个数字**，叫**安全身份 identity**（取值范围 1 ~ 2³²−1）。负责 IP → 身份翻译的是 **ipcache**；数据面做策略匹配时**比的是身份，不是 IP 和端口**。

好处非常直接：**Pod 重建了、IP 漂移了，身份不变，策略就不用重写**。这就是 Cilium 跟所有以 IP 为中心的方案**最根本的分野**。

## 五、数据面：eBPF 六大件

Cilium 的 eBPF 程序**不是一个大文件**，而是按**挂载点**分成六类，作者把它叫做「**六大件**」：

| 程序 | 挂载点 | 负责什么 |
| :--- | :--- | :--- |
| **bpf_xdp** | XDP（网卡驱动最早的入口） | 性能最好，主要给 **DSR 和加速**用 |
| **bpf_host** | 主机网卡的 TC 钩子 | 主机侧出入口、NAT |
| **bpf_lxc** | 容器的 **veth** 网卡 | **策略的主战场** |
| **bpf_overlay** | 隧道口 | 处理 overlay 的收发包 |
| **bpf_sock** | socket 层 | 应用发起连接时拦截，做 **socket 层负载均衡** |
| **bpf_wireguard** | — | 节点之间的**流量加密** |

## 六、一个 agent，吃掉四件事

Cilium 的第四个核心是：**一个 agent 吃掉四件事**——网络、安全、可观测、服务网格。在传统架构里，这通常是**四套独立的系统**，各自一套配置、各自一套状态；Cilium 把它们**合并**了：

- **网络**：联通、路由、服务负载均衡，直接替代 kube-proxy；
- **安全**：三到七层的策略、身份与加密；
- **可观测**：Hubble flow 和指标，由数据面**天然产生**；
- **服务网格**：Ingress、网关，加上 mTLS 和七层治理。

**关键不在于功能多，而在于它们共享同一份身份、同一套数据面**——所以策略写完，四件事**自动对齐**。这是理解 Cilium 为什么能同时干这么多活的钥匙。

## 七、一个包的一生：从 Pod A 到 Pod B

默认走 **overlay** 模式时，一个跨节点包的旅程有六步：

1. 包从容器出来，经过 **veth** 网卡，被 **bpf_lxc** 拦下做**出向策略检查**；
2. 进入主机，由 **bpf_host** 处理、查路由；
3. 如果走 overlay，就给包加上 **VXLAN 外层封装**（若开了加密，这一步会先加密）；
4. 封装好的包从节点 A 的网络接口发出，经过物理网络到节点 B；
5. 节点 B 上由 **bpf_overlay** 剥掉外层；
6. 交给本地的 **bpf_lxc** 做**入向策略检查**，最后送进 Pod B。

**特别注意第 3 步是可选的**：切到 **native routing** 模式就完全不封装，直接靠路由。

![一个包的一生：Pod A → Pod B（跨节点）的六步旅程，第三步封装可选](assets/01·Cilium%20是什么？把网络、安全与可观测全塞进%20eBPF（Cilium%20源码深读）/00331.webp)

[【跳转到 05:31】](https://www.bilibili.com/video/BV1AcH16dEon/?t=331)

而更能说明 Cilium 思维方式的，是**身份如何从标签一路落到内核数据面**：

1. Pod 带着它的 **label** 被整理成一组**确定性的标签集合**；
2. **身份分配器 identity allocator** 把这组标签映射成一个数字（同样标签集合共享同一个 identity）；
3. **ipcache** 把这个 Pod 的 **IP 和它的 identity** 对应起来、下发出去；
4. 到了数据面，**策略匹配时只比 identity，不比 IP**。

整条链路的因果关系很干净：**地址变了，identity 不变；identity 不变，策略就不用重写**。这也解释了为什么 Cilium 在 Pod 频繁重建的环境里依然稳。

## 八、一个 Cilium 集群里跑了什么

- **cilium-agent**：每个节点跑一个，最重要的进程，管着这个节点**所有的 eBPF 程序和状态**；
- **cilium-dbg**：随 agent 一起装的本机调试工具，直接连本节点 agent 的接口，能看 **eBPF map 的原始状态**；
- **Hubble 服务端**：**内嵌在 agent 里**，负责产出 flow 和指标；
- **Cilium CNI 插件**：Pod 被调度或删除时，Kubernetes 会调用它；
- **cilium-operator**：只干那些**全集群做一次**的事，比如地址分配、资源清理。**关键点是它不在转发的关键路径上**——它挂了，网络照样通；
- **Hubble Relay / UI**：负责跨节点聚合和图形界面。

agent 之间靠什么传状态？默认用 **Kubernetes 的 CRD**，也可以选 etcd。

### 一条策略，怎么走到每个节点

1. 你用 `kubectl` 提交一个 **CiliumNetworkPolicy**；
2. 它被存进 Kubernetes 的 API Server，成为一个 **CRD 资源**，也就是「集群事实」；
3. 每个节点上的 agent 都在 **watch** 这个资源，变更一发生就收到通知；
4. 各节点的**策略引擎**开始算这条策略影响本地的哪些 **endpoint**，算出一个**期望状态**；
5. agent 把结果**编译成对应的 eBPF 程序和 map 更新**，落到数据面。

**整条链路最关键的一点是：没有中心节点统一下发，每个 agent 自己算自己那一份。** 这正是 Cilium 能**水平扩展**的原因——节点越多，越是分摊，而不是压在中心。

## 十、收益与代价

Cilium 换来的东西很实在：

- **规模**：查表代替遍历规则，几乎撞不到上限；
- **安全**：身份加七层策略，地址怎么飘都不怕；
- **可观测**：天生就有，不用额外买点；
- **性能**：逻辑在内核里跑，不落用户态。

但**代价同样真实**：

1. **内核版本要求高**：能用哪些特性跟内核强相关，老内核上会退化成兼容模式；
2. **调试门槛明显更高**：得懂 eBPF、懂内核，不然出了问题无从下手；
3. **排障路径长**：数据面程序是在 agent 里**现场编译**的，比一张静态规则表复杂得多；
4. **可见性受限**：逻辑一旦埋进内核，很多**用户态工具就看不全了**。

所以记住这句话：**Cilium 复杂，是因为它把要求定得高；你拿到这套能力，也要接受它的门槛。**

## 小结

- **K8s 只提三条硬要求（独立 IP、直连、知道其他节点网段），不给实现**——这个空白正是各家 CNI 分道扬镳的地方。
- **两条路线分叉**：传统方案把规则堆进 iptables 链表，Cilium 把逻辑编译进 eBPF；差别不只是性能，还有规则形态、匹配依据、能力上限和可观测。
- **eBPF 让内核可编程**：C 写逻辑 → 字节码 → 验证器 → JIT → 内核态运行，状态放 map，不用改内核、不用重启。
- **身份是 Cilium 的灵魂**：用标签集合映射出的 identity 代替 IP 做策略匹配，Pod 重建、IP 漂移都不影响策略。
- **数据面六大件**（xdp / host / lxc / overlay / sock / wireguard）按挂载点分工，`bpf_lxc` 是策略主战场。
- **一个 agent 吃掉四件事**（网络、安全、可观测、服务网格），因为它们共享同一份身份、同一套数据面。
- **控制面没有中心下发**：每个 agent 自己 watch CRD、自己算期望状态，这带来水平扩展能力。
- **收益很实在，代价也真实**：内核要求高、调试门槛高、排障路径长、用户态工具看不全。
