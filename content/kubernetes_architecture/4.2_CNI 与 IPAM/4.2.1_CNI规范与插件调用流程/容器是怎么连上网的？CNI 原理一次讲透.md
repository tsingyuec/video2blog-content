# 容器是怎么连上网的？——CNI 规范：一张给容器网络立下的「标准契约」

> 本文整理自 B 站视频《[容器是怎么连上网的？CNI 原理一次讲透](https://www.bilibili.com/video/BV1ek416xEj8/)》（「容器网络课」第一期，时长约 3 分钟）。文中机制描述、配置示例与结论均来自该视频的图文稿，可核对。

## 本讲要解决的核心问题（SCQA）

**背景（S）**：你启动一个容器，它马上就有了一个独立的 IP，还能对外联网。对使用者来说，这一切「理所当然」。

**冲突（C）**：可你有没有想过——这个 IP 到底是谁分配的？它在哪个网段？路由是怎么规划的？Docker 会去配这些，Kubernetes（Kubelet）也会去配。如果**每一种容器引擎都各写一套网络接入逻辑**，网络插件想同时支持它们，就得挨个适配，越搞越乱。

**疑问（Q）**：有没有一个**统一的约定**，让所有容器引擎、所有网络插件都按同一套规矩来对接？

**回答（中心思想 A）**：有，这就是 **CNI（Container Network Interface，容器网络接口）**。它是一套由 CNCF 维护的标准：把「怎么给容器配网络」这件事标准化，让**容器引擎负责按标准调用插件、网络插件负责照规范实现**，两边各干各的、又能严丝合缝地对接。CNI 的价值不在于让网络更快，而在于**让网络接入变得标准化**。本讲用三个问题讲透它：网络是谁配的 → CNI 是什么 → 三条命令管什么。

## 一、网络是谁配的：问题出在「没有统一约定」

先说那个困惑：容器明明有 IP、能上网，可它到底是怎么连上网的、背后的网络是谁给它配的？

答案的关键在于：**给容器配网络，不是容器引擎「自带」的功能，而是靠一整套机制临时搭建出来的。** 一次容器启动，背后要发生这些事：

- 给容器**分配一个 IP**——这个 IP 属于哪个网段、由谁管？
- 决定**路由怎么规划**——容器内外的流量该往哪走？
- 把**网卡、网桥、防火墙规则**等网络资源都配置好。

问题就在于，这些事**Docker 会做、Kubernetes 的 Kubelet 也会做**。而它们各自的实现方式、配置格式、调用接口如果都不一样，就会带来一个尴尬：一个网络插件（比如 Calico、Flannel）想同时支持 Docker 和 Kubernetes，就得为每一家单独写一套适配——**引擎越多，适配的组合越多，越搞越乱**。[【跳转到 00:25】](https://www.bilibili.com/video/BV1ek416xEj8/?t=25)

## 二、CNI 是什么：一套标准，由三样东西组成

CNI 的全称是 **Container Network Interface（容器网络接口）**，是云原生基金会 **CNCF** 旗下的项目。它的定位不是某个具体插件，而是**一份标准**——规定好「容器引擎该怎么调用网络插件、插件做完了该返回什么」。

具体来说，CNI 由**三样东西**组成：

![CNI 的三个组成部分：① 规范 Spec——容器引擎怎么调用插件、插件返回什么；② SDK（libcni）——给容器引擎用的调用库；③ 插件骨架 Skeleton——给写插件的人用的模板](assets/容器是怎么连上网的？CNI%20原理一次讲透/00050.webp)

| 组成 | 面向谁 | 作用 |
| :--- | :--- | :--- |
| **① 规范（Spec）** | 所有人 | 规定容器引擎怎么调用插件、插件做完该返回什么。是「契约」本身。 |
| **② SDK（libcni）** | 写容器引擎的人 | 一个调用库（libcni），省得你手动去拼参数、执行插件，按接口调用即可。 |
| **③ 插件骨架（Skeleton）** | 写插件的人 | 一个模板，照着填就能写出一支符合规范的 CNI 插件。 |

**对比一下就明白了**：没有 CNI 时，Docker 一套逻辑、Kubernetes（Kubelet）一套逻辑，网络插件想同时支持两套就得挨个适配；有了 CNI 之后，容器引擎只负责「按标准调用插件」，而插件只要「照规范实现」，就能被所有平台识别。

所以，**CNI 的价值不是让网络快多少，而是让接入变得标准化**——这是理解后面所有 CNI 行为的出发点。[【跳转到 01:15】](https://www.bilibili.com/video/BV1ek416xEj8/?t=75)

## 三、三条命令管一切：ADD / DEL / CHECK

既然 CNI 是「容器引擎 → 网络插件」之间的契约，那么契约的接口长什么样？答案很简洁：**容器引擎（runtime）靠三条命令来指挥插件。**

![ADD / DEL / CHECK——CNI 规范定义的三条核心命令：ADD 把容器加进网络、DEL 把网络清理干净、CHECK 验证网络是否按配置配好](assets/容器是怎么连上网的？CNI%20原理一次讲透/00099.webp)

| 命令 | 何时调用 | 插件要做什么 |
| :--- | :--- | :--- |
| **ADD** | 容器被加入网络时 | 给容器建虚拟网卡、分配 IP、配置路由——真正把网络搭起来。 |
| **DEL** | 容器被删除时 | 把之前占用的网络资源清理干净，一个不剩（释放 IP、拆除网卡等）。 |
| **CHECK** | 需要校验时 | 验证网络是不是真的按配置配好了。 |

用视频里的话说，插件就是「**听这三条命令**」的：ADD 负责「建」，DEL 负责「拆」，CHECK 负责「查」。容器引擎在合适的时机发出合适的命令，插件照着执行——**两边都不需要知道对方的内部细节**。[【跳转到 01:39】](https://www.bilibili.com/video/BV1ek416xEj8/?t=99)

## 四、网络由配置决定：一份 JSON 走天下

那插件到底该怎么配、配成什么样？CNI 的做法是把**网络配置写成一份 JSON**，由容器引擎通过**标准输入**交给插件——**网络由配置决定**。

![一份 CNI 网络配置：cniVersion 是版本、name 是网络名、plugins 是一个插件列表；runtime 把这份 JSON 通过标准输入交给插件](assets/容器是怎么连上网的？CNI%20原理一次讲透/00128.webp)

一份典型的 CNI 配置大致长这样：

```json
{
  "cniVersion": "0.4.0",
  "name": "mynet",
  "plugins": [
    { "type": "bridge", "bridge": "cni0", "isGateway": true, "ipMasq": true,
      "ipam": { "type": "host-local", "subnet": "10.85.0.0/16" } },
    { "type": "firewall" }
  ]
}
```

它由三部分构成：**`cniVersion`（版本）**、**`name`（网络名）**、**`plugins`（一个插件列表）**。容器引擎把这份 JSON 交给插件后，**插件看列表里的 `type` 字段，就知道自己该干什么**：

- 第一个插件是 **`bridge`**：建一张叫 `cni0` 的网桥，并让它里面的 **IPAM（IP 地址管理器）`host-local` 从 `10.85.0.0/16` 网段里分配一个 IP**。
- 第二个插件是 **`firewall`**：负责配置防火墙规则。

关键在于：**这个插件列表是「串」起来的**——前一个插件的处理结果，会作为输入传给下一个插件，一个接一个依次执行。这就是 CNI 的**链式调用（chained plugins）**。[【跳转到 02:08】](https://www.bilibili.com/video/BV1ek416xEj8/?t=128)

## 小结

本期用三个问题把 CNI 讲透了，记住三点即可：

1. **CNI 是一套标准**：它把「怎么给容器配网络」规范化，让容器引擎和网络插件无缝对接。它由**规范、SDK（libcni）、插件骨架**三样东西组成。
2. **三条命令管一切**：**ADD** 把容器加进网络、**DEL** 把网络清理干净、**CHECK** 验证网络是否配好。插件就是听这三条命令干活的。
3. **网络由配置决定**：一份 JSON（`cniVersion` + `name` + `plugins`）走天下；插件按列表里的 `type` 依次执行，前一个的结果传给下一个，形成链式调用。

第一期到这里告一段落。但「知道 CNI 是什么」还不够——**一条 ADD 命令到底是怎么把容器接进网络的**？runtime 怎么调用、libcni 怎么找插件、网络资源怎么落地？这些留给了第二期《一条 ADD 命令的完整旅程》。

## 关键术语速查

| 术语 | 一句话解释 |
| :--- | :--- |
| **CNI** | Container Network Interface，容器网络接口，CNCF 旗下的一套容器网络标准。 |
| **Spec / 规范** | 规定容器引擎如何调用网络插件、插件应返回什么。 |
| **libcni** | CNI 的 SDK，容器引擎用它来调用插件，而不必手写调用逻辑。 |
| **Skeleton / 骨架** | 编写 CNI 插件的模板。 |
| **ADD / DEL / CHECK** | CNI 定义的三条核心命令：加入网络 / 清理网络 / 校验网络。 |
| **IPAM** | IP Address Management，IP 地址管理，负责给容器分配 IP（如 `host-local`）。 |
| **链式调用** | 多个插件按列表顺序依次执行，前一个的结果传给下一个。 |
