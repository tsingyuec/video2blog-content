# 一条 ADD 命令的完整旅程——CNI 插件调用链：从 runtime 发令到插件落地

> 本文整理自 B 站视频《[一条 ADD 命令，容器怎么就被接进网络了？CNI 调用链一次讲透](https://www.bilibili.com/video/BV1Td4162Er3/)》（「容器网络课」第二期，时长约 4 分钟）。文中调用链步骤、命令与字段均来自该视频的图文稿，可核对。

## 本讲要解决的核心问题（SCQA）

**背景（S）**：上一期我们知道了 CNI 是什么，也提了一句——**runtime 靠 ADD / DEL / CHECK 三条命令指挥插件**。

**冲突（C）**：可「发一条 ADD 命令」和「容器真的被接进网络」之间，隔着好几层东西：runtime 怎么找插件？配置和参数怎么传给插件？插件内部又怎么把网卡、IP、路由真的配出来？这些环节看不见、摸不着，一旦网络不通，就无从下手。

**疑问（Q）**：**一条 ADD 命令，究竟经过了哪些环节，才把容器接进网络的？**

**回答（中心思想 A）**：一条 ADD 命令要经过**五个站点**，才真正把网络搭好——**runtime 发令 → libcni 找插件 → 执行（invoke）→ 插件内部 `cmdAdd` 干活 → 结果回传并缓存**。贯穿全程的是两条主线：**责任分层**（runtime、libcni、插件各管一段）和**两个输入来源**（环境变量说「干什么」、标准输入给「怎么配」）。把这条链走通，后面所有 CNI 问题——不通、慢、IP 冲突——都能顺着这条链去定位。

## 一、全景图：一条 ADD 命令要过五个站点

先看全景。一条 ADD 命令从发出到完成，会经过**五个站点**：

![一条 ADD 命令要过 5 个站点：站1 runtime 发令 → 站2 libcni 找插件 → 站3 invoke 执行 → 站4 插件内部 cmdAdd → 站5 结果回传与缓存](assets/一条%20ADD%20命令，容器怎么就被接进网络了？CNI%20调用链一次讲透/00030.webp)

| 站点 | 谁在做事 | 做什么 |
| :--- | :--- | :--- |
| **站 1 · 发令** | runtime | `containerd` / `kubelet` 调用 **libcni 的 `AddNetworkList`**。 |
| **站 2 · 找插件** | libcni | 按配置里的 **`type` 字段**，在 **`CNI_PATH`** 里找到对应的插件程序。 |
| **站 3 · 执行** | libcni | 把**配置和参数打包好**，直接去执行那个插件。 |
| **站 4 · 干活** | 插件 | 程序内部由 **skeleton 模板分发到 `cmdAdd`**，真正开始搭网络。 |
| **站 5 · 回传** | 插件 / libcni | 插件返回**结果 JSON**，libcni **缓存**起来，交回给 runtime。 |

## 二、前两站：runtime 发令，libcni 找插件

拆开前两站来看。runtime 调用 **`libcni` 的 `AddNetworkList`**，传入的是一个**网络配置列表**（就是上一期那份 JSON 里的 `plugins` 数组）。如果列表里有**多个插件**，libcni 会**挨个处理**它们。

在真正执行每一个插件之前，libcni 先做两件事：

1. **`findPlugin`（找插件）**：按配置里的 `type` 字段（比如 `bridge`），在 **`CNI_PATH`** 指定的那堆目录里，**定位到插件的二进制文件**。
2. **`buildOneConfig`（拼配置）**：把**当前插件自己的配置**，加上**上一个插件传下来的结果（`previous result`）**，拼成一份**完整的配置**——就像把它打包成一个「快递包裹」。

![runtime 发令 → libcni 找插件：AddNetworkList 先把每个插件的配置与上一个插件的结果拼成一份完整配置，再交给插件执行](assets/一条%20ADD%20命令，容器怎么就被接进网络了？CNI%20调用链一次讲透/00080.webp)

这里第一次出现了**链式调用**的关键动作：**上一个插件的结果，会成为下一个插件的输入**。

## 三、站长看「快递」：插件收到的两个输入

在执行插件的那一刻，插件到底收到了什么？答案是**两样东西**：

- **环境变量**：告诉插件「用哪条命令、干哪件事」。
- **标准输入（stdin）**：那份**网络配置 JSON**。

具体到环境变量，有几个关键字段：

| 环境变量 | 含义 |
| :--- | :--- |
| **`CNI_COMMAND`** | 要执行哪条命令，这里是 **`ADD`**。 |
| **`CNI_CONTAINERID`** | 容器的唯一 ID。 |
| **`CNI_NETNS`** | 容器那个**网络命名空间（netns）**的路径。 |
| **`CNI_IFNAME`** | 容器里网卡的名字，一般是 **`eth0`**。 |
| **`CNI_PATH`** | 去哪里找别的插件或工具。 |

而**网络配置 JSON 不走环境变量，走标准输入**。所以——**插件从不去猜自己要干嘛**，全靠这两个来源：**环境变量说「干什么」，标准输入给「怎么配」**。[【跳转到 01:32】](https://www.bilibili.com/video/BV1Td4162Er3/?t=92)

## 四、第四站：插件内部，`cmdAdd` 究竟干了什么

进到插件内部，才是真正「干活」的地方。插件程序一启动，**skeleton 模板先读环境变量**，看到 `CNI_COMMAND` 是 `ADD`，就**分发到 `cmdAdd` 函数**。

以最常见的 **`bridge`** 插件为例，`cmdAdd` 里大致干**三件事**：

1. **`ns.GetNS`**：拿到容器那个网络命名空间。
2. **调 `host-local` 这个 IPAM**：从网段里**分配一个 IP**。
3. **`setupVeth`**：建一对 **veth 网卡**——**一头插在主机、一头挪进容器的命名空间**，再把 IP 配上去。

搞完这三件事，插件返回一个**结果 JSON**。[【跳转到 01:57】](https://www.bilibili.com/video/BV1Td4162Er3/?t=117)

> **补充**：把网卡「一头在主机、一头在容器」正是 Linux **`veth` pair（虚拟以太网对）**的典型用法，它也是后面章节里 Pod 网络真正落地的物理基础。

## 五、最后两站：结果回传、链式串联与缓存

插件干完活后，把**结果 JSON 写回标准输出**，libcni 把它**解析成标准的结果对象**。

接着发生两件重要的事：

- **链式串联**：这个结果会作为 **`previous result`**，**传给网络列表里的下一个插件**——这就是上一期提过的「链式调用」。
- **结果缓存**：等列表里所有插件都跑完，`AddNetworkList` 会调 **cache** 把结果**缓存下来**。

![结果回传 + 链式串联 + 缓存：插件结果作为 previous result 传给下一个插件形成链；AddNetworkList 最后把结果缓存起来，供 CHECK / DEL 时复用](assets/一条%20ADD%20命令，容器怎么就被接进网络了？CNI%20调用链一次讲透/00142.webp)

**为什么要缓存？** 因为以后要 **`CHECK` 验证**、或者容器删除时 **`DEL` 清理**，都靠这份缓存**记住当初配了啥**——不然插件就不知道要拆掉哪些网卡、释放哪个 IP 了。[【跳转到 02:41】](https://www.bilibili.com/video/BV1Td4162Er3/?t=161)

## 小结

第二期到这里，一条 ADD 的完整旅程你就走了一遍。记住三点：

1. **责任分层**：**runtime 只管发命令**，**libcni 负责找插件、打包、执行**，**插件才真正干活**——三段各司其职。
2. **全靠两个输入**：**环境变量说「干什么」**（`CNI_COMMAND` 等），**标准输入给「怎么配」**（配置 JSON）。
3. **结果会传会存**：插件结果作为 `previous result` **传给下一个插件**（链式串联），**最后被缓存**，供 `CHECK` / `DEL` 等时机复用。

原理都懂了，就差动手了——下一期基于 skeleton 模板，从零手写一个能跑的 CNI 插件（`cmdAdd` / `cmdDel` 一行行撸出来）。

## 关键术语速查

| 术语 | 一句话解释 |
| :--- | :--- |
| **AddNetworkList** | libcni 提供给 runtime 的入口，负责遍历插件列表并逐个调用。 |
| **findPlugin** | libcni 按配置的 `type` 字段在 `CNI_PATH` 里定位插件二进制。 |
| **buildOneConfig** | 把当前插件配置与上一个插件的 `previous result` 拼成完整配置。 |
| **CNI_COMMAND** | 环境变量，告诉插件当前要执行哪条命令（ADD/DEL/CHECK）。 |
| **previous result** | 上一个插件返回的结果，作为下一个插件的输入，实现链式调用。 |
| **cmdAdd** | CNI 插件里处理 ADD 命令的函数（如 bridge 插件建网桥、分 IP、插 veth）。 |
| **veth pair** | 虚拟以太网对，一头在主机、一头在容器命名空间，用于打通 Pod 与主机网络。 |
| **结果缓存** | libcni 把 ADD 的结果缓存，供后续 CHECK / DEL 复用。 |
