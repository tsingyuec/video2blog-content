## 本讲要解决的核心问题（SCQA）

**背景**：你已经在上一讲知道了 Kubernetes 的 IPAM 大致由 CNI 插件负责，`host-local` 插件用「一个目录、一个 IP 一个文件」来记录租约。

**冲突**：但真实生产里更常见的不是 `host-local`，而是 **Calico**。Calico 的 IPAM 和 `host-local` 完全不同——它**不是每个节点各管一段固定网段**，而是先定义一个**大 IP 池**，再**动态地把池子切成小块、按节点分发、随需增长**。这套机制叫什么、怎么看、出问题怎么查？

**疑问**：为什么 Pod 不能像普通主机那样用 DHCP 拿地址？Calico 从「一个 IP 池」到「某个 Pod 的具体 IP」，中间到底发生了什么？那些一闪而过的 `IPPool`、`block affinity` 到底是什么？为什么一个跑了 22 个 Pod 的集群只用了 12 个 IP？

**回答（中心思想）**：**Calico 的 IPAM 是「池 → 块 → 亲和性」三级结构。** 你给它一个 **IP Pool（地址池）**，它把池子切成固定大小的 **IP Block（IP 块）**，再把块按需**分配（affinity）给节点**；节点上早已预留好一块地址，Pod 一起来就**从本节点已分配的块里**拿 IP。块用满就再分一块。这套结构让分配**无需中心协调、也不会跨节点冲突**；而「22 个 Pod 只用了 12 个 IP」，则是因为**控制面组件用的是宿主网络，根本没走 Pod 网络**。

## 一、为什么 Pod 需要专门的 IPAM，DHCP 为什么不行

Pod 是 Kubernetes 里工作负载的**原子单位**，本质上「和你在网络里遇到的任何工作负载一样」——服务器、虚拟机、甚至笔记本。普通工作负载靠网络里的 **DHCP 服务器（动态主机控制协议服务器）** 在它们上线时分配 IP。[【跳转到 00:21】](https://www.youtube.com/watch?v=G-IGFsMSmrA&t=21)

但**典型 DHCP 服务器无法给 Pod 分配地址**。原因在于 Pod 的生命周期与网络模型都和传统主机不同：数量大、生命周期短、还要求「每个 Pod 一个可路由的扁平地址」。为此需要一种叫 **IPAM 插件**的东西，**Calico 就是这样一个 IPAM 插件**，而 IPAM 功能通常**由 CNI 提供**。[【跳转到 00:51】](https://www.youtube.com/watch?v=G-IGFsMSmrA&t=51)

![Pod 的 IPAM：Pod 通过 veth/eth0 接入节点的 Pod 网络，地址由 IPAM 插件（此处为 Calico）分配而不是 DHCP](assets/01. Calico IP Address Management (IPAM) for Kubernetes/00026.webp)

而对 IPAM 插件来说，光「发得出地址」还不够，它必须同时满足三个目标：[【跳转到 01:05】](https://www.youtube.com/watch?v=G-IGFsMSmrA&t=65)

1. **高效**：要保证集群里 Pod 的**快速启动**；
2. **不冲突**：分配出去的地址彼此不能重复；
3. **管理高效**：地址块/地址空间要管理得高效，才能**支撑跨多个节点的 Pod 间通信**。

下面就看 Calico 如何同时做到这三点。

## 二、Calico 的分配模型：池 → 块 → 亲和性

一句话概括 Calico IPAM 的三级结构：

1. **IP Pool（地址池）**：你定义一个 CIDR，告诉 Calico「这一大段地址可以发给 Pod」；
2. **IP Block（IP 块）**：Calico 从池子里**切出固定大小的小块**（这是它内部管理的粒度）；
3. **Block Affinity（块亲和性）**：把某个块**分配给某个节点**，并用一个 Kubernetes 资源把它记下来。

它的目标很明确：**当 Pod 在某节点上启动时，该节点上「已经有一块预先分配好的地址块」**，Pod 直接从这块里取地址——**不用临时向中心服务要地址，因此又快又不冲突**。[【跳转到 16:09】](https://www.youtube.com/watch?v=G-IGFsMSmrA&t=969)

当一块地址用尽（例如一个 `/26` 提供 64 个地址），Calico 会**再给该节点分配一个新块**。[【跳转到 16:39】](https://www.youtube.com/watch?v=G-IGFsMSmrA&t=999)

## 三、动手看：从一个 kind 集群和一份 IP 池配置开始

实验环境是**用 containerlab 起的一个三节点 kind 集群**（1 个控制面节点 + 2 个工作节点），**装上 Calico CNI**，并使用 **`192.168.0.0/16`** 作为 Pod 地址空间。[【跳转到 01:53】](https://www.youtube.com/watch?v=G-IGFsMSmrA&t=113)

![实验拓扑：一个三节点 kind 集群，用 192.168.0.0/16 作为 Pod 地址空间，集群先不带默认 CNI，随后安装 Calico](assets/01. Calico IP Address Management (IPAM) for Kubernetes/00153.webp)

有两个配置点必须对上号：

- **kind 集群配置**：集群**刻意不带默认 CNI**（因为稍后要自己装 Calico），并**指定 pod 子网为 `192.168.0.0/16`**。[【跳转到 02:58】](https://www.youtube.com/watch?v=G-IGFsMSmrA&t=178)

![kind 集群配置：不部署默认 CNI，并显式指定 podSubnet 为 192.168.0.0/16](assets/01. Calico IP Address Management (IPAM) for Kubernetes/00203.webp)

- **Calico 配置**：在 Calico 的 `Installation` 自定义资源里定义一个 **`IPPool`**，其 **CIDR 也设为 `192.168.0.0/16`**。[【跳转到 04:43】](https://www.youtube.com/watch?v=G-IGFsMSmrA&t=283)

![Calico 的 Installation 自定义资源：其中 IPPool 的 CIDR 必须与集群的 Pod 子网一致（此处均为 192.168.0.0/16）](assets/01. Calico IP Address Management (IPAM) for Kubernetes/00283.webp)

> **一条铁律**：**任何 Kubernetes 集群里，Pod 的 CIDR 都应与你在 Calico 里配置的 IP Pool CIDR 一致。** 不一致会出问题，视频作者把它留到后续「Pod 网络 / 路由」课程再展开。

部署脚本本身很直接：用 containerlab 拉起拓扑 → 取出 kubeconfig 并设为环境变量 → 安装 `calicoctl`（一个用来在终端里查看 Calico 配置的工具）→ 安装 Calico → 等待 Calico API Server 和各个 Calico 组件就绪。就绪后 `kubectl get tigera status` 显示**所有 Calico 组件均为可用（available）**。[【跳转到 08:20】](https://www.youtube.com/watch?v=G-IGFsMSmrA&t=500)

## 四、眼见为实：看 IP 池用量与 Block Affinity

集群起来后，几条命令就能把 Calico IPAM 看个透。

### 4.1 `calicoctl ipam show`：看地址池用量

运行 **`calicoctl ipam show`**，会输出这个集群分配的 CIDR 范围：**这块地址一共提供 65,000 多个 IP，当前只用了 12 个**，其余可用。[【跳转到 10:55】](https://www.youtube.com/watch?v=G-IGFsMSmrA&t=655)

![calicoctl ipam show：显示地址池范围（192.168.0.0/16，提供 6 万多个 IP）与当前用量（12 个在用、其余可用），用于查看地址空间利用率](assets/01. Calico IP Address Management (IPAM) for Kubernetes/01041.webp)

> 这个命令非常适合用来**评估某个集群 IP 地址空间的使用情况**。

### 4.2 为什么 22 个 Pod 只用了 12 个 IP？

`kubectl get pods -A` 显示集群里其实有 **20 多个 Pod**，为什么只有 12 个在用 IP？关键在于**有一类 Pod 并不使用 Pod 网络**：[【跳转到 11:45】](https://www.youtube.com/watch?v=G-IGFsMSmrA&t=705)

- **使用宿主网络的 Pod**：像 **Calico API Server** 这类 Pod 用 Pod 网段的 IP（`192.168.x.x`）；而**控制面组件**（如 `etcd`、`kube-apiserver`、`calico-node`）**使用宿主网络的 IP**——它们拿到的是**节点本身的 IP**（如 `172.x`）。[【跳转到 12:29】](https://www.youtube.com/watch?v=G-IGFsMSmrA&t=749)

![用宿主机网络的 Pod：etcd、kube-apiserver、calico-node 等控制面/关键 Pod 直接复用节点 IP，因此不计入 Pod 网络地址](assets/01. Calico IP Address Management (IPAM) for Kubernetes/00749.webp)

**为什么这些关键 Pod 要用宿主网络？** 因为**Pod 网络并不是集群运转的必要条件**：如果 Pod 网络出故障，只要这些组件走宿主网络，**控制面依然可用**，集群仍能维持运转。[【跳转到 14:19】](https://www.youtube.com/watch?v=G-IGFsMSmrA&t=859)

![节点上的两类网络：普通 Pod 拥有独立 Pod 网络命名空间、IP 由 IPAM 插件分配；而关键组件挂到宿主网络命名空间，直接使用节点网卡与节点 IP](assets/01. Calico IP Address Management (IPAM) for Kubernetes/00834.webp)

所以本集群里**只有 12 个 Pod 真正使用 Pod 网络、由 Calico 分配了 IP**。

### 4.3 `block affinity`：把「块」分给节点的记录

**Block Affinity 是一个 Kubernetes 资源，代表「分配给某节点的 IP 块」。** Calico 拿到 IP Pool 后会**从中切出更小的块**，并**把这些块分配给集群中的节点**。这样做的好处是：**Pod 起来时，它所在节点早已预留好一块地址，Pod 直接从这块里拿 IP**；块里地址用尽，则再分配一块。[【跳转到 15:37】](https://www.youtube.com/watch?v=G-IGFsMSmrA&t=937) 来回顾整条链：[【跳转到 16:14】](https://www.youtube.com/watch?v=G-IGFsMSmrA&t=974)

![Calico 从 IP Pool 切出 IP Block 并分配给节点：每个节点预先持有若干块，Pod 从本节点的块中取地址，保证分配快且不冲突](assets/01. Calico IP Address Management (IPAM) for Kubernetes/00958.webp)

![IP 块被分配给各节点：块里的地址由该节点上的 Pod 消费；块用满时 Calico 再为该节点分配新块](assets/01. Calico IP Address Management (IPAM) for Kubernetes/00974.webp)

因为实验集群有 3 个节点，`kubectl get blockaffinities` 会显示 **3 个 block affinity**。其命名规则是 **`calico-ipam-<节点名>-<IP 块>`**——例如某个块的名称里带着 **`192.168.18.64/26`**，也就是一个 **`/26`（64 个地址）** 的块。[【跳转到 17:21】](https://www.youtube.com/watch?v=G-IGFsMSmrA&t=1041)

![block affinity 资源：3 个节点对应 3 个块亲和性；命名形如 calico-ipam-<节点名>-<IP块>，如 192.168.18.64/26 表示一个含 64 个地址的 /26 块](assets/01. Calico IP Address Management (IPAM) for Kubernetes/01092.webp)

想看细节，用 `kubectl get blockaffinities -o yaml`（或库克里的详细输出命令）可以看到**这个块、它被分配给哪个节点、以及块的状态**：[【跳转到 18:12】](https://www.youtube.com/watch?v=G-IGFsMSmrA&t=1092)

- **`confirmed`**：块正在被**积极使用**；
- **`pending`**：块**正在被分配**给节点的过程中。

![block affinity 详细输出：显示块、被分配到的节点、以及状态（confirmed 表示正在被使用，pending 表示正在分配中）](assets/01. Calico IP Address Management (IPAM) for Kubernetes/01117.webp)

如果只想要简明的输出，还有一条命令能直接给出**亲和性名称、所属节点、以及被分配的 IP 块**三列。[【跳转到 18:48】](https://www.youtube.com/watch?v=G-IGFsMSmrA&t=1128)

## 小结

- **Pod 用不了 DHCP**（生命周期、规模、扁平寻址要求都不同），因此需要专门的 **IPAM 插件**，Calico 就是一个，功能由 CNI 提供。
- Calico IPAM 是 **三级结构**：**IP Pool（池）→ IP Block（块）→ Block Affinity（块亲和性，把块分给节点）**。
- **块预先分配给节点**，Pod 起来直接从本节点的块取地址——**快、且天然不冲突**；块用满再分新块。
- 配置铁律：**Calico `IPPool` 的 CIDR 必须与集群的 Pod 子网一致**。
- **`calicoctl ipam show`** 看地址池用量；**`kubectl get blockaffinities`** 看块与节点的对应关系；块状态有 **`confirmed`（在用）/ `pending`（分配中）**。
- 「Pod 数多于已用 IP 数」的常见原因：**控制面等关键组件走宿主网络、复用节点 IP**，不消耗 Pod 网络地址。

## 关键术语速查

| 术语 | 一句话解释 |
| :--- | :--- |
| IPAM | IP 地址管理，负责给 Pod 分配地址的职责 |
| DHCP | 动态主机控制协议，传统主机自动拿 IP 的机制；**不适合**给 Pod 分配地址 |
| IP Pool | Calico 的地址池（一个 CIDR），声明「哪些地址可以发给 Pod」 |
| IP Block | Calico 从池里切出的固定大小地址块，是内部分配的粒度（如 /26 = 64 个地址） |
| Block Affinity | 一个 Kubernetes 资源，记录「某 IP 块被分配给了某节点」 |
| `calicoctl ipam show` | 查看集群 IP 地址池范围与使用情况的命令 |
| 宿主网络（hostNetwork） | Pod 直接使用节点网络命名空间与节点 IP，不消耗 Pod 网络地址 |
| tigera status | 查看 Calico 各组件是否可用的命令 |
