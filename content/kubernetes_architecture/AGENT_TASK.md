## 0. 运行模型

- 每次定时触发 = **一次独立运行**，运行间无记忆。进度只存在于 README 的行尾标记里，每次运行必须重读 README 定位。
- 一次运行**只处理一个条目**，完成即结束。
- **不设并发限制**：每 20 分钟触发一次，而单个条目（下载 + 抽帧 + 字幕 + 图文稿 + 博客）常要更久，因此**多轮运行并行是常态**。各运行自行认领**互不相同**的条目，互不等待、互不取消。
- 并发安全靠两条约定：**认领用「局部替换 + 重读校验」**，**README 只改自己那一行**。
- **待处理条目**：README 中以 `-` 开头（前可有空格）、且行尾**既无** `【处理中】` **也无** `【已完成】` 标记的行。

## 1. 认领

1. 重读 README，按出现顺序列出待处理条目（无任何标记的行）。若一条都没有，结束本次运行。
2. 从第一个候选开始尝试认领：在该行行尾追加 `**【处理中】**`。
   - 写入**只能精确替换这一行**（如 `python3` 读全文 → 按内容匹配唯一行 → 只替换该行 → 写回；或先 `grep -n` 定位行号后用 `sed -i "<行号>s/$/ **【处理中】**/"`），**严禁整体重写覆盖文件**；
   - 写完**立即重读该行**确认：仍以 `**【处理中】**` 结尾，且未被别的运行改成 `【已完成】`；
   - 若该行已被别的运行抢先标记（变成 `【处理中】` 或 `【已完成】`）或写入被覆盖丢失，**回到步骤 2 换下一个候选**。
3. 若所有候选都是在被处理中，**结束本次运行**（不等待、不重试、不排队）。
4. 认领成功后再开工（先标记后干活）。

### 1.1 已有 `**【处理中】**` 标记的行怎么对待（只做回收，不做限流）

扫描候选时，遇到标记为 `**【处理中】**` 的行：

| 情形 | 处理 |
|---|---|
| 该条目博客已落位 | 只是没来得及写完成标记：**补写完成标记**（链接已有博客）后结束本次运行 |
| 博客未落位，`temp/kubernetes_architecture/<条目名>/` **近 60 分钟内仍有文件变动** | 别人正在做，**跳过**，看下一个候选 |
| 博客未落位，且 temp 目录不存在或**已超 60 分钟无变动** | 中断残留：清理 temp、把该行标记回滚为空，随后可作为候选重新认领 |

- 回收只针对「明显已死」的残留（超 60 分钟无动静），**不要**因为「感觉慢」去抢别人的条目。

## 2. 探索视频

以条目内容（含编号、括号注记）构造中英文关键词，在 Bilibili / YouTube 探索：

1. **筛选**：按标题、简介剔除不相关或低质视频。
2. **精排**：对前 5~8 个候选**抓取字幕**，按内容详细程度与质量排序（是否系统覆盖知识点、是否适合初学者、信息密度）。
3. **同分时 Bilibili 优先于 YouTube**。
4. 选出 **1~3 个**视频；单个视频已充分覆盖则只选 1 个。

**选题取向（本系列特有）**：本系列讲的是 Kubernetes 的**内部机制**（组件职责、控制循环、调度框架、CNI/CRI/CSI 调用链、数据面实现），不是入门操作课。

- 优先 KubeCon / CNCF / DevConf / 官方文档解读 / 源码剖析 / 深度长文类视频；
- 纯「手把手装集群 / 敲命令建 Deployment」的入门 Demo 只在它能**实证机制**（如抓包看 watch、`iptables-save` 看 Service 规则、`crictl` 看 CRI 调用）时才选；
- 条目之间避免选用同一支视频的大段重复内容；若某视频同时覆盖相邻两条，优先归给它讲得更透的那条。

**与已有系列去重**：仓库里已有 `content/kubernetes`（RBAC 权限控制）与 `content/kubernetes_cursor`（40 天 Kubernetes 挑战 / CKA）。

- 若这两个目录下已有博客**完整覆盖**当前条目，可直接复用：不重复处理视频，在完成标记里链接该博客（相对路径，如 `../../kubernetes_cursor/blog/Day08_Deployment与ReplicaSet.md`），并在括号中注明「复用已有博客」；
- 只是部分相关的不要复用——本系列要的是机制深度，宁可另找视频也不要把入门课当机制课。

### 3.1 字幕获取降级链与限流应对

**字幕获取优先级**：
1. **首选**：kedou.life（与 video2blog skill 默认一致）；
2. **kedou 限流 / 失败时**：用 yt-dlp + B 站登录 cookie 直接抓取官方 AI 字幕：

   ```bash
   yt-dlp --cookies .agents/bili-subtitle/cookies.txt \
     --write-subs --sub-langs "ai-zh,zh-CN,zh" --sub-format srt --skip-download \
     -o "temp/kubernetes_architecture/<条目名>/subs/%(id)s" "<视频URL>"
   ```

3. 两者都失败且已重试无效 → 按第 6 节异常处理回滚。

**Cookie 约束（重要）**：

- cookie 文件固定在仓库根 `.agents/bili-subtitle/cookies.txt`（该目录已在 `.gitignore` 中，不会进 git），**严禁**复制到仓库其它位置、提交、上传或写入博客；
- cookie 有效期约 6 个月（当前这枚至 2027-04）。若 yt-dlp 报「Subtitles are only available when logged in」或返回未登录，用官方接口检查：`curl -s -G 'https://passport.bilibili.com/x/passport-login/web/cookie/info' --data-urlencode 'csrf=<bili_jct值>' -b <cookie文件>`——`refresh: true` 或未登录时**不要反复重试**，在回滚标记时注明「cookie 需更换」，等待人工处理。

**远程中转（限流兜底）**：

- **触发条件**：下载或字幕抓取遇到限流（HTTP 429、风控验证、频繁失败）且本地重试无效时。
- **唯一允许的远程机器**：`jdcloud`（`~/.ssh/config` 已配置，即 `root@117.72.151.12`）。**严禁接触、扫描或登录任何其它远程机器**。
- **中转流程**：
  1. `ssh jdcloud`，在远程用 yt-dlp 等工具下载视频 / 抓取字幕；
  2. 用 `scp` 将产物传回本地 `temp/kubernetes_architecture/<条目名>/` 对应子目录（视频放 `videos/`、字幕放 `subs/`）；
  3. **确认本地文件完整**（大小一致、能正常读取）后，**必须删除 jdcloud 上的临时下载文件**，不留残留；
  4. 断开连接，继续本地流程（抽帧及后续步骤仍在本地做）。
- 若 jdcloud 也被限流，记录原因并按第 6 节异常处理回滚，不得寻找其它机器。
